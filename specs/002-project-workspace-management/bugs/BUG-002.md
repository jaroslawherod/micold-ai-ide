# Bug Report: A project opened through a symlinked path shows every worktree as `invalid`

**Type**: Implementation defect (with a spec gap behind it)
**Severity**: High
**Feature**: 002-project-workspace-management (project identity is the filesystem path — FR-012);
manifests in 008-worktree-sidebar-refinement / 014-hide-agent-worktrees (the worktree list)
**Reported**: 2026-08-21
**Status**: Open
**Found by**: the 014-hide-agent-worktrees T034 manual pass
([evidence](../../014-hide-agent-worktrees/evidence/T034-manual-procedure.md)) — the harness reached
its fixture repos through a symlink, and every worktree in every fixture came up unhealthy.

## Description

If the folder the user picks is a symbolic link (or has a symlinked ancestor), the app opens the
project happily, but its worktree list is entirely wrong:

- **every** app-managed worktree is badged `invalid`,
- **none** of them shows a branch,
- and the rows that are shown are orphan rows the app invented, not the git records.

Nothing is actually broken on disk. Opening *the same repository* by its real path shows every one
of those worktrees healthy, with branches. One variable, opposite results.

`bug-002-symlink-compare.png` is that comparison: the red-bordered frame is the project opened via
`~/.aaa-vp83/repo` (a symlink), the blue-bordered frame is the identical repository opened via its
real path. Same repo, same commit, same worktrees, same instant.

## Reproduction

```
$ ln -s /path/to/real/repo ~/link-to-repo
```

1. Open `~/link-to-repo` as a project.
2. Look at the worktree sidebar.

**Expected**: the same rows as opening `/path/to/real/repo` — healthy, each with its branch.
**Actual**: every row badged `invalid`, no branches. Reproduced on a fixture with 2 worktrees and
again on one with 50.

## Root Cause

`micold-core/src/worktree.rs:229-268` (`reconcile`). Two path sources are compared with `==`, and
only one of them is canonical:

```rust
for rec in records {
    if rec.path.parent() != Some(worktrees_root) {
        continue;                       // ← every record is dropped here
    }
    ...
}

// Directories present on disk but not registered with git → Invalid (orphan).
for name in on_disk_dir_names {
    if !registered_dirs.contains(name) {
        out.push(Worktree { branch: None, status: WorktreeStatus::Invalid, .. });
    }
}
```

`records` comes from `git worktree list`, which reports **resolved** paths — git canonicalises them.
`worktrees_root` is derived from the project path as the user picked it and as the catalog stored
it, i.e. still containing the symlink. So `rec.path.parent()` (`/real/repo/.claude/worktrees`) never
equals `worktrees_root` (`/home/u/link-to-repo/.claude/worktrees`), every git record is skipped, and
the second loop then sees directories on disk that no record claimed and classifies each as an
orphan — `Invalid`, `branch: None`. The output is not "the worktrees, degraded"; it is a set of rows
about worktrees the app has decided do not exist.

`reconcile` is pure and this is not its fault: it compares what it is given. The defect is that the
caller hands it one canonical set and one non-canonical one.

## The spec gap behind it

**FR-012** says *"project identity is the filesystem path"* and requires that opening a
known project activates the existing entry rather than duplicating it. It does not say **which**
path — as typed, or as resolved. With the literal reading, a symlink and its target are two
identities, so:

- the same repository can be added twice, listed twice, and carry two independent sets of sessions
  and display-name overrides, with no indication they are the same repo; and
- FR-012's own anti-duplication guarantee does not hold for a user who reaches their repo through a
  symlink once and directly the next time.

That second consequence is a real FR-012 violation, not just an unhappy interaction: the requirement
promises no duplicate, and this produces one. Symlinked checkouts are ordinary (`~/src/foo` →
`/mnt/data/foo`, `/home` on another volume, per-user convenience links), so this is not an exotic
input.

## Recommended Fix

1. **Canonicalise the project path once, at the boundary** — when a folder is chosen and when the
   catalog is loaded — and use the canonical form as project identity everywhere downstream
   (`worktrees_root`, session location keys, the catalog key FR-012 speaks of). Keep the path the
   user picked, if anything, only as a display detail.
2. **Amend FR-012** to say identity is the *canonical* filesystem path (symlinks resolved), so that
   opening a symlink to a known project activates that project instead of creating a second one.
   Add an edge case for it beside the existing "folder gone since it was added".
3. **Cover it in `micold-core`**: `reconcile` already takes its facts as parameters, so a test that
   passes canonical `records` against a non-canonical `worktrees_root` pins the failing shape
   without touching the filesystem — and the fixed caller makes it pass.
4. Consider whether `reconcile` should be defensive as well as correct: "no record matched, yet
   there are directories on disk" is a shape that means *"my root is wrong"* far more often than it
   means *"every single worktree was orphaned"*, and it is currently reported to the user as the
   latter with no hint of the former.
