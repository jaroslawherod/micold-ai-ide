# Bug Report: Reopening a known project never updates the persisted last-active project

**Type**: Implementation defect
**Severity**: Medium
**Feature**: 002-project-workspace-management (FR-010, FR-011)
**Reported**: 2026-08-21
**Status**: Open
**Found by**: the T047 manual walkthrough
([evidence](../evidence/T047-manual-walkthrough.md)), steps 10–12

## Description

`projects.json`'s `last_active` is written when a project is opened **through the folder
selector**, and never when the same project is reopened **from the known-projects list** — which
is the route FR-011 exists to provide and the one a user takes every day.

The consequence is visible on the next launch: the app restores whichever project was last opened
*by browsing*, not the one the user was actually working in when they quit.

## Reproduction

Two known projects, A and B, both opened through the selector at some point, B most recently.

1. Reopen **A** from Known projects (or from the top-bar switcher). The shell switches: heading,
   chip and active marker all read A. Correct so far.
2. Read the catalog while the app is still running:

   ```
   $ cat "$XDG_DATA_HOME"/micold-ai-ide/projects.json
   { "schema_version": 1, "last_active": ".../B", "projects": [ ... ] }
   ```

   `last_active` still names **B**.
3. Quit and relaunch. The app comes up in **B**.

Observed exactly this way during T047: after reopening `My Project` (step 11) the store still read
`"last_active": "/home/jaro/.aaa-vp83d/w2-git-b"`, and the following relaunch (step 12) opened
`w2-git-b`.

This is not a lost-write-on-exit: the rename in step 8 was persisted immediately, from the same
run, and the folder-chosen route updated `last_active` immediately at steps 6 and 7.

## Root Cause

The daemon's `Catalog` is the single writer of `projects.json`
(`crates/micold-client/src/shell/persist.rs:50`), and the only message that moves its idea of the
active project is `ProjectAdd`:

```rust
// crates/micold-daemon/src/catalog.rs:417
pub fn add_project(&mut self, path: &Path, scanner: &dyn FolderScanner) -> io::Result<()> {
    self.workspace.open_or_activate(path.to_path_buf(), scanner);
    self.persist()
}
```

`persist` serializes `last_active: self.workspace.active.clone()` (`catalog.rs:198`).

The selector route sends it (`shell/workspace.rs:126`). The reopen route deliberately does not:

```rust
// crates/micold-client/src/shell/workspace.rs:137
pub(crate) fn on_known_project_reopened(app: &mut App, path: PathBuf) -> Task<Message> {
    ...
    if app.core.switch_active(&path) {
        ...
        // Already a known project (no ProjectAdd); just move the daemon attachment.
        switch_daemon_attachment(app, previous, &path);
    }
```

`switch_daemon_attachment` sends `Detach` + `Attach` + `SetViewedSession`
(`shell/daemon_sync.rs:151`), and the daemon's `Attach` handler (`server.rs:377` →
`state.rs:447`) records an attachment; it does not touch `workspace.active`. So the switch is
client-side only, and the client is not allowed to write the catalog.

The comment is right that a `ProjectAdd` would be redundant for an already-known project — but
that is the message that also carries "this is now the active one", and dropping it drops both.

## Recommended Fix

Give the daemon a way to record activation without re-adding. Either:

- reuse `ProjectAdd` on this path (`open_or_activate` is idempotent for a known path — it is
  exactly what step 7 exercises, and it produced no duplicate), or
- add a narrow `ProjectActivate { req, path }` that calls `Workspace::activate` + `persist`, which
  has the additional merit of routing through the FR-023 availability guard in
  `Workspace::activate` (`micold-core/src/workspace.rs:237`).

The second is preferable: `activate` already refuses an unavailable project, so the catalog can
never come to name one as last-active. See [BUG-004](./BUG-004.md), which is what happens when a
`last_active` that *is* unavailable reaches boot.

## Note for whoever picks this up

No test covers it. `crates/micold-client/tests/switch_active.rs` asserts the in-memory switch;
nothing asserts what the catalog holds afterwards, because the client cannot write it and the
daemon-side tests never see the reopen path.
