# Bug Report: On launch, a last-active project whose folder is gone is made the active working space

**Type**: Implementation defect
**Severity**: Medium
**Feature**: 002-project-workspace-management (FR-023)
**Reported**: 2026-08-21
**Status**: Open
**Found by**: the T047 manual walkthrough
([evidence](../evidence/T047-manual-walkthrough.md)), step 12

## Description

FR-023: *"The system MUST NOT activate a project whose folder is unavailable."*

The known-projects list honours it — the row's primary action is replaced by a disabled
**Unavailable** button, and pressing it does nothing. The **boot path does not**. If the folder
named by `last_active` has been deleted, moved or renamed since the last run, the app opens
straight into it: the heading reads `Active project: <name>`, the top-bar chip names it, its
(nonexistent) path is shown beneath, and the row in Known projects carries the active check marker
**and** the unavailable warning marker at the same time.

![the same row is both active and unavailable](../evidence/w12-unavailable-yet-active.png)

The app does not crash — that half of the quickstart's step 12 passes — but it spends the session
attached to a project that is not there: a worktree discovery, an `Attach` and a
`SetViewedSession` are all issued against the missing path.

## Reproduction

1. Open project B; quit. (`projects.json` now has `"last_active": ".../B"`.)
2. With the app closed, `mv B B-renamed`.
3. Relaunch.

Observed: `Active project: B`, path `.../B`, and B's row shows both markers. Expected: no active
working space (or a fall back to an available project), plus the unavailability communicated.

## Root Cause

Two correct pieces that are never connected.

`Store::load` restores `active` from `last_active`, filtered only for membership in the catalog —
availability is not persisted, so it cannot be consulted here:

```rust
// crates/micold-core/src/store.rs:287
// A `last_active` that does not match a known project is treated as no active
// project (storage-schema contract).
let active = self
    .last_active
    .filter(|path| projects.iter().any(|p| &p.path == path));
```

Boot then refreshes availability — and stops:

```rust
// crates/micold-client/src/shell/startup.rs:102
core.workspace = store.load().workspace;
core.workspace.refresh_availability(caps.scanner());
```

`refresh_availability` marks the project `Unavailable` but never revisits `active`. The FR-023
guard exists, but it lives in `Workspace::activate`, which this path never calls:

```rust
// crates/micold-core/src/workspace.rs:237
/// Rejected (returns `false`, leaving the current active unchanged) if the path is
/// unknown or the project is `Unavailable` (FR-013, FR-023).
pub fn activate(&mut self, path: &Path) -> bool {
```

So every route a *user* can take is gated, and the one route the application takes for them is not.

## Recommended Fix

Clear the restored `active` when the refresh finds it unavailable — cheapest inside
`refresh_availability` itself, so no caller can forget:

```rust
// at the end of `refresh_availability`
if let Some(active) = &self.active {
    if self
        .projects
        .iter()
        .any(|p| &p.path == active && p.availability == Availability::Unavailable)
    {
        self.active = None;
    }
}
```

That lands the shell on the empty state (FR-016) with the unavailable row visible in Known
projects, which is what step 12 describes. Whether to say more than that — a notice naming the
project that could not be reopened — is FR-023's *"communicate the unavailability"* clause and is
worth deciding with it; the row's marker alone is thin when the user expected to land in that
project.

Note the interaction with [BUG-003](./BUG-003.md): because reopening from the list does not update
`last_active`, the project this defect strands the user in is not even necessarily the one they
were last working in.

## Note for whoever picks this up

`crates/micold-client/tests/switch_active.rs:74`
(`switch_to_unavailable_is_rejected_and_leaves_state_unchanged`) covers the *switch*; the boot
restore has no equivalent. A test for this belongs beside `Store::load` + `refresh_availability`
in `micold-core` — it needs no GUI.
