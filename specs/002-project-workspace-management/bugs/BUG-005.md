# Bug Report: The known-projects list does not scroll, so projects past the window's bottom edge are unreachable

**Type**: Untested flow — the spec sizes the catalog at "tens to a few hundred" projects, and nothing
states or checks what the list does once they no longer fit.
**Severity**: High — every project below the fold is unreachable from the list: it cannot be
reopened, renamed or forgotten there, and nothing on screen says it exists.
**Feature**: 002-project-workspace-management (FR-011, FR-022, User Story 2)
**Reported**: 2026-09-27
**Status**: **Fixed** — both lists scroll (PR #416; gated by `crates/micold-client/tests/known_projects_overflow.rs`, visual pass in [evidence/BUG-005-visual-pass.md](../evidence/BUG-005-visual-pass.md)).
**Patched**: 2026-09-27
**Fixed**: 2026-09-27 — PR #416, merged as 4bdec2cf.

## Description

With more known projects than fit in the window's height, the shell body's "Known projects" list
is cut off at the bottom edge. No scrollbar is drawn, and the mouse wheel does not move the list.
The rows below the edge are laid out but never shown, so the user cannot reach their Open, Rename
or Forget actions.

Reproduce: know enough projects that their rows are taller than the window (four rows at the
default 1280×800 window, under the "No project open" header; fewer in a short window or below the
reflow breakpoint, where each row's actions move to a second line), with no project active. The
last rows are clipped and the list cannot be scrolled.

Reproduced 2026-09-27 on `origin/main` (23a0e0ee) with a throwaway headless probe: 20 known
projects, `ui::view` painted at the default 1280×800 through `support::layout::painted_text_settled`.
The body painted the rows of `proj-00`…`proj-03` (name origins y = 352, 432, 512, 592; 80dp pitch)
and nothing for `proj-04`…`proj-19`. The same state with `switcher_open: true` painted switcher rows
`proj-00`…`proj-14` (y = 87…758.5, 48dp pitch) and nothing for `proj-15`…`proj-19` or "Add
project…". Neither tree contains a `Scrollable` on either path, so the wheel has nothing to move.

**Sibling surface — same defect, different owner.** The top-bar project switcher (feature 008) has
the same shape: its panel is `MenuOverlay`, whose `item_column` is a plain `column` with no height
cap and no `Scrollable`, so a long catalog runs the panel off the bottom of the window and the
trailing "Add project…" row (008 FR-009) with it — from 15 known projects at the default window
size, "Add project…" is no longer shown. This report traces the body list; the switcher
panel is fixed here too (decided with the user 2026-09-27): its requirement is 002 FR-011a, with a
clarification note on 008 FR-005.

## Root Cause Analysis

`crates/micold-client/src/ui/shell.rs:93` builds the list as a plain `column!`, pushes it into the
body `column` (`:169`), and hands that to a `container` with `height(Length::Fill)` (`:173-177`).
A `column` has no scrolling of its own: content taller than its container is laid out past the
edge and clipped. The body is not inside any scrollable further up — `ui/mod.rs:309` and `:330`
render `shell::view` directly.

It is a spec oversight rather than drift: the plan states the catalog size, and neither the spec,
the tasks nor the quickstart ever ran the list at that size. Every recorded pass used a handful of
projects, which fit.

The switcher panel's instance has the same cause one level down: `ui/material/menu.rs:170`
(`item_column`) is a bare `column` inside `menu_panel`, and `MenuOverlay` (`:342-349`) gives it no
maximum height. The select control's dropdown already solves this — `material/picker.rs:231` caps
its list in a `Scrollable` with `height(Length::Shrink)`.

   *Decided 2026-09-27 (ledger D1, with the user): fixed here.*
2. Run `/speckit.bugfix.verify` to confirm consistency.
