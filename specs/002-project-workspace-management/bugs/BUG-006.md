# Bug Report: A `projects.json` or project state file with no version number is treated as corrupt

**Type**: Spec gap with an implementation defect downstream of it — the storage-schema contract
lists `schema_version` without ever saying whether a reader may do without it, its compatibility
rules default only the fields it calls *optional*, and the on-disk shapes answered the question the
contract left open by rejecting a document that omits it
**Severity**: High (a version-less `projects.json` empties the known-projects list and the
last-active pointer; a version-less project state file withholds that project's sessions, worktree
display names, last-viewed session, included worktrees and worktree provenance on **every** launch.
Nothing is said in either case)
**Feature**: `002-project-workspace-management` (FR-008, FR-009, FR-010, FR-012a, SC-003;
`contracts/storage-schema.md`, including its BUG-001 per-project storage split) — seam with
`029-worktree-provenance` FR-011, which decides what an unreadable project state file does, and
with `003-material-design-layout` BUG-003, the same defect in `settings.json`
**Reported**: 2026-09-27
**Status**: **Fixed** — artifacts and code (T070–T072): both documents load without `schema_version`
**Fixed**: 2026-09-27 — PR #415, merged as cb076e99.
**Patched**: 2026-09-27 (FR-012c, new edge case, the contract's field table, compatibility rules
and a new versioning section; plan.md; tasks T070–T072)

*(Line numbers below cite `store.rs` on `origin/main` 23a0e0ee; the symbol names are the stable reference.)*

**Found by**: the review of 003 BUG-003 (PR #412), which fixed the same shape in `settings.json`
and recorded these two fields as a follow-up (`specs/003-material-design-layout/bugs/BUG-003.md`,
"Sibling stores").

## Description

`crates/micold-core/src/store.rs` holds the on-disk shapes of both documents this feature owns:
`StoredCatalog` (`projects.json`) and `StoredProjectState` (one file per project under
`projects/`, added by BUG-001). Every field of both carries a serde default except one:
`StoredCatalog::schema_version` (`store.rs:88`) and `StoredProjectState::schema_version`
(`store.rs:389`) are bare `u32`s, so serde requires them. The doc comments beside the fields around
them make the "additive and defaulted, so no `schema_version` bump" argument five times over.

A document that omits the number fails to deserialize, and neither load path can tell that from a
truncated file:

- **Catalog.** `JsonFileStore::load` (`store.rs:626-660`) renames `projects.json` to
  `projects.json.bak` and returns an empty catalog with `LoadStatus::Recovered`. Every known
  project, its display name, its git flag and the last-active pointer are gone from the
  application. The next save writes an empty `projects.json` over the gap. And because every
  project's state file is looked up through the catalog's `projects[]`, all of them are orphaned
  with it.
- **Project state.** `load_project_state` (`store.rs:537-554`) returns `ProjectStateLoad::Corrupt`.
  The file is **not** moved aside, unlike the catalog. `029-worktree-provenance` FR-011 deliberately leaves it in
  place, marks the project in `Workspace::unreadable_projects`, drops its sessions, worktree display
  names, included worktrees, provenance and last-viewed session for the run, and `save`
  (`store.rs:773-781`) declines to overwrite the file. That makes the loss permanent: the file is
  never rewritten with a version, so it fails the same way on every launch. And because provenance
  is unreadable, every worktree of that project is classed as the user's own (029-worktree-provenance FR-011's
  fail-visible rule).

The bug report that opened this said the project state file is moved to a `.bak`. That is true of
the catalog only; the per-project behaviour is the one described above, and it is worse.

The field that costs all of this is one nothing reads. `schema_version` is written from
`SCHEMA_VERSION` by `StoredCatalog::from_workspace` and `StoredProjectState::from_workspace`, and
it is consumed nowhere. There is no migration keyed on it (BUG-001's pre-split migration is keyed on
a state file being *missing*, not on a version), no gate, and `into_workspace` drops it.

These files are also written by hand here, which the BUG-003 note assumed they were not. The
client binary has no command line, so the `visual-pass` skill seeds a `projects.json` to open a
project headlessly, and so do the recorded passes of `018-material3-visual-system`, `021-mvu-slice-architecture`,
`025-last-session-memory`, `029-persistent-session-names` and `031-clickable-terminal-links`. The 025
quickstart (`specs/025-last-session-memory/quickstart.md:594`) already warns that a seed which fails
to deserialize is moved to `projects.json.bak` and the app opens on "No project open". A seed that
leaves out the number is one of those.

## Reproduction

On `origin/main` (`23a0e0ee`), a scratch integration test in `crates/micold-core/tests/` wrote each
document with and without `"schema_version": 1` into a temp directory and loaded it through
`JsonFileStore::load`:

```jsonc
// projects.json
{ "last_active": "/a",
  "projects": [ { "path": "/a", "display_name": "Alpha", "is_git_repo": true },
                { "path": "/b", "display_name": "Beta",  "is_git_repo": false } ] }

// projects/<project_id("/a")>.json, beside a projects.json that does carry its version
{ "worktree_display_names": { "feat-x": "Feature X" },
  "provenance_migrated": true, "created_worktrees": ["feat-x"] }
```

Observed:

```text
catalog with_version=true:  status=Loaded    projects=2 active=Some("/a") bak_exists=false original_exists=true
catalog with_version=false: status=Recovered projects=0 active=None       bak_exists=true  original_exists=false
state   with_version=true:  names=Some({"feat-x": "Feature X"}) provenance=Some({"feat-x"}) migrated=true  unreadable=false
state   with_version=false: names=None                          provenance=None             migrated=false unreadable=true  file_still_there=true bak_exists=false
```

Adding `"schema_version": 1` and nothing else makes either document load every value in it.

## Artifact Traceability

### spec.md

- **Affected user stories**: User Story 2 (reopen a known project after a restart) for the catalog;
  the per-project state that BUG-001 moved under FR-012a for the state file.
- **Affected requirements**:
  - **FR-008** / **SC-003** — the known-projects list survives restarts, and 100% of previously
    opened projects reappear. A list in a document without a version number reappears as nothing.
  - **FR-009** / **FR-010** — the records and the last-active pointer are lost with it.
  - **FR-012a** — a storage fault is scoped to at most one project. That holds: a version-less
    state file costs only its own project. But FR-012a's "fault" is meant for a damaged file, and
    here a complete, well-formed one is classed as damaged.
- **Gap identified**: the spec says what happens to a corrupt file and never says which parts of a
  stored document are load-bearing. The contract does not say either: it defaults "missing optional
  fields" and lists `schema_version` without saying whether it is one of them. The code resolved that
  silence as *required*, which is the one answer that costs data. It costs data for a field nothing
  reads.

### contracts/storage-schema.md

- **Affected sections**: the field table (`schema_version` is "Used for forward-compatible
  migration", but nothing uses it), the compatibility rules ("missing optional fields" without saying
  which fields are optional), and the BUG-001 per-project split. That section describes the state
  file's contents and write discipline and inherits "same forward-compatibility rules" in the code,
  but not in the contract.
- **Impact**: `schema_version` becomes optional in both documents, defaulting to `0`. The rule is
  stated once for every field of both documents: an absent field takes its default and never makes
  a document unreadable — except the identity fields (`projects[].path`, `projects[].display_name`,
  a session's `id`), which have no meaningful default and stay required. A *present* field still can: a wrong-typed value, or a session `provider`
  naming a CLI this build does not know. `StoredAiCli` is deliberately without `#[serde(other)]`
  (`store.rs:164-172`) so that a newer build's Pi session is not read as Claude Code and started as
  the wrong agent. The contract says so, so that the asymmetry is not later "fixed". A new
  versioning section records that no reader branches on the value, what `0` means, and why a future
  migration gate must not treat it as older than v1.

### plan.md

- **Affected sections**: "Bugfix: per-project storage split (BUG-001)". The corrupt-degrades
  pattern it describes is right. The defect is that a readable document was classed as corrupt.

### tasks.md

- **Affected tasks**: T025 (the serialization form: "`schema_version` (=1)") and T050–T051 (the
  per-project state shape and the split load/save). No false completion. T025 asked for a field that
  is written as `1`, and it is. The roundtrip, corruption and fault-isolation tests those tasks and
  T044/T048–T049 left behind all pass. Every fixture in them carries `"schema_version":1`, which is
  why a document without it was never tested.
- **Added**: T070 and T071 (a failing regression test per document) and T072 (the fix), Phase 12.

## Root Cause Analysis

The contract made `schema_version` part of the document's shape ("Present on every write") and
described it as the migration mechanism. It never decided whether a *reader* depends on it. The
implementation gave it the only non-defaulted slot in either struct, and every later feature added
defaulted fields around it. Each feature's own "no bump" argument confirms that nothing ever needed
the number. It is the same oversight 003 BUG-003 fixed for `settings.json`, in the file beside it.

## Recommended Fix

`StoredCatalog::schema_version` and `StoredProjectState::schema_version` take `#[serde(default)]`,
so an absent version number reads as `0`, the version no build writes. That is the choice 003
FR-022 made, for the same reason: nothing reads the field, so the default only decides what the
number claims. `0` says the document named no version, where `SCHEMA_VERSION` would claim this
build wrote a file it knows nothing about. The comment beside each field carries 003's warning to
the author of any future migration gate: `0` means *unknown*, not *older than v1*. No migration path
is added. There is none to extend.

What this does not change: saves still write `"schema_version": 1`; a present-but-unreadable field
still fails the read (catalog → `.bak` and empty; state file → left in place and unreadable, per
`029-worktree-provenance` FR-011); an unknown key is still ignored, so a misspelled key in a hand-written seed is still
silently a default. That last point is 003 BUG-003's residue, and the same rule applies here.
