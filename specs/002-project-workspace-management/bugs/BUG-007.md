# Bug Report: A `projects.json` that fails to parse resets the project list without telling the user

**Type**: Implementation drift — the recovery was designed to be reported: 010 data-model C4,
written when the daemon took ownership of the catalog, says the `Recovered` status is "now surfaced
to the client rather than swallowed", tightening 002 data-model's looser "so the app can optionally
note the recovery". No reader of the status ever reported it. 002's spec never said it MUST be, so
it is also a gap FR-012d closes.
**Severity**: Medium (no data is destroyed — the file is kept as `projects.json.bak` — but the user
sees an empty list with no explanation and no pointer to the file that holds their projects; the
next save writes an empty `projects.json`, so a user who re-adds one project has no reason to look
for the `.bak`)
**Feature**: `002-project-workspace-management` (FR-008, SC-003, FR-012b; `data-model.md`
§Storage abstractions; `contracts/storage-schema.md` "Unparseable / corrupt file";
`contracts/ui-contract.md` C7) — seam with `010-daemon-session-persistence` data-model C4, and with
010 BUG-025, which fixed the same silence for `settings.json`
**Reported**: 2026-09-27 — GitHub issue #433
**Status**: Patched
**Patched**: 2026-09-27 (FR-012d, new edge case, storage-schema and UI contracts, data-model note, plan.md; tasks T073–T078)

*(Line numbers cite `origin/main` 2bd447b2; the symbol names are the stable reference.)*

**Found by**: review A of BUG-006's milestone (PR #415), recorded there as a follow-up.

## Description

`JsonFileStore::load` (`crates/micold-core/src/store.rs:648-685`) answers a `projects.json` it
cannot parse by renaming it to `projects.json.bak` and returning an empty catalog with
`LoadStatus::Recovered`. That status reaches two readers, and neither tells the user:

- **The client, at launch.** `restore_catalog` (`crates/micold-client/src/shell/startup.rs:123-152`)
  does `core.workspace = store.load().workspace;` and drops the status on the floor. This read runs
  on every launch, before anything starts or dials the daemon (`boot` calls `restore_from_disk`;
  feature 028: only the application starts the service), and the sandboxed daemon reads the same
  file through its state mount (`sandbox::STATE_CONTAINER_DIR`). So it is always the first reader
  of a file damaged since the daemon last loaded it:
  - **Cold launch** (no daemon running): the client moves the file aside, the daemon it then starts
    sees `Missing`, and the user lands on an empty list with no word.
  - **Warm launch** (028 FR-006: the daemon outlives the app for 30 idle minutes and never re-reads
    the file): the client still moves the file aside, but the daemon's in-memory catalog arrives
    in `Welcome` and `reconcile_catalog` (`crates/micold-client/src/catalog_sync.rs`) restores the
    list on screen. It does **not** reach the disk: the daemon writes the catalog only on a change,
    so if nothing changes before its 30-minute idle stop, the next launch finds no `projects.json`
    (`Missing`, silent) and the list is gone for good, with only the damaged `.bak` left (found by
    review A of M1). So the notice FR-012d asks for must say only what is true in both cases — the
    file could not be read, and where it was kept; it must not claim the list was reset — and a
    running daemon must write its list back when the file has gone.
- **The daemon, at start.** `server::run` (`crates/micold-daemon/src/server.rs:149`) logs the
  status at `info`. The diagnostics ring that the client's "recent issues" request reads keeps only
  WARN and ERROR (`crates/micold-daemon/src/logging.rs:88-89`), so even a user who asks for
  diagnostics is not told. This reader meets a damaged file first only when the daemon starts
  without a client launch in front of it: a restart after the service died while the app stayed
  open, or the "Keep the sandbox running" container coming back after a reboot before the app is
  opened.

`settings.json` had exactly this defect and 010 BUG-025 fixed it with `notify_settings_recovery`
(`crates/micold-client/src/shell/persist.rs:131`, called from `startup.rs:191`), which names the
`.bak`. The catalog has no counterpart.

Reachable: `projects.json` is hand-seeded in practice (the `visual-pass` skill, the 025
quickstart), and BUG-006 removed only one trigger (an absent `schema_version`). A typo, a trailing
comma or a truncated write from another tool still takes this path.

## Reproduction

On `origin/main` (2bd447b2):

1. Write `{ "projects": [ { "path": "/a", ` (truncated JSON) to a `projects.json` in a temp
   directory.
2. Launch through `restore_from_disk` with a `JsonFileStore` at that path — the regression test
   `a_launch_that_recovers_the_project_list_tells_the_user_where_the_old_one_went` in
   `crates/micold-client/src/shell/startup.rs` does exactly this.

Observed: `projects.json.bak` exists, the workspace has no projects, and the notification queue is
empty — the test fails at "a project list that had to be recovered was reset without a word"
with `notice: ""`.

By hand: quit the app **and make sure no `micold-daemon` is running** (wait out the 30-minute idle
stop, or sign out and back in), put a trailing comma into `projects.json` in the data directory,
launch. The app opens on "No project open" with no message; `projects.json.bak` is beside the new
file. (With a daemon still running, the list comes back from its memory and only the silent rename
to `.bak` is observable.)

- **Affected requirements**: FR-008 / SC-003 (the list survives restarts; 100% of projects
  reappear) — when a damaged file makes that impossible, the user is not told. FR-012b states the
  principle for the write side: a persistence failure MUST be surfaced, not silently discarded,
  because the user must be able to tell that their data may not have survived. Nothing says the
  same for the read side.
- **Gap identified**: no requirement says a recovered catalog is reported. Added as FR-012d, with
  an edge case.

  the app can optionally note the recovery". No reader does.

  client rather than swallowed". It is surfaced only to the daemon's own log, at a level the

- `contracts/storage-schema.md` "Unparseable / corrupt file" and `contracts/ui-contract.md` C7:

## Root Cause Analysis

The recovery status was built to be reported and then every caller used only `.workspace`. When
the daemon became the catalog's owner (010), C4 promised to surface it, but the one line that reads
it logs at `info`, and the client's own launch read — the one that actually meets a damaged file,
because it runs before the daemon starts — kept discarding it. 010 BUG-025 found and fixed the
identical pattern in `settings.json` without looking at the file beside it.

## Recommended Fix

1. **Client (the fix).**
   `restore_catalog` keeps the status and the copy's path (item 3) and hands them to a
   `notify_catalog_recovery` beside `notify_settings_recovery`: `Recovered` raises a notice — "Your saved project list could not be
   read. The unreadable file was kept as …" — that is true on a cold and a warm launch alike (it
   does not say the list was reset), naming the kept file when it exists
   (an unreadable-but-not-renamed file has none, and the notice then omits the path); `Missing` and
   `Loaded` say nothing.
2. **Daemon.** When the daemon itself recovers the catalog, it logs at `warn` naming the `.bak`, so
   the recovery lands in the diagnostics ring the client's "recent issues" request reads (C4,
   over the existing protocol). No wire change.

3. **Store** (review A of M1). `LoadOutcome` carries `preserved`, the copy **this** load made —
   never inferred from a `.bak` being on disk, which may be an older recovery's. The rename never
   lands on an existing copy (`projects.json.bak`, then `.bak.2`, …): a second recovery must not
   destroy the list the first notice pointed at. A file that cannot be read as text at all is moved
   aside too, instead of being left for the next save to overwrite.
4. **Daemon writes back.** On each connection, before `Welcome`, a daemon holding projects whose
   `projects.json` has gone writes it back (`Catalog::restore_missing_file`), closing the
   warm-launch loss above.

The notice is raised at the error level (10 s rather than 4 s), as 002 BUG-004's boot notice is: it
carries a path the user needs to read.

**Not done, deliberately**: pushing the daemon's own recovery to the client unprompted. That needs
a new protocol field or message (a `PROTOCOL_VERSION` bump) for the two rare paths above where the
daemon reads first; a launch's own read always precedes the daemon it starts. Recorded as a
follow-up.
