# Bug Report: Theme flashes to light and reverts on its own when the CPU is busy

**Type**: Implementation drift (primary) + Spec gap (secondary)
**Severity**: High
**Feature**: 003-material-design-layout (branch `fix/theme-is-change-periodically-when-cpu-is-busy`)
**Reported**: 2026-07-21
**Status**: Patched
**Patched**: 2026-07-21

## Description

While following the system theme (`ThemePreference::FollowSystem`), the app periodically and
spontaneously flashes to the light ("default white") theme for one poll cycle, then reverts to
the correct theme (e.g. Dark) on its own — with no OS theme change and no user action. It
correlates with CPU load: it happens noticeably more often when the machine is busy (e.g.
running a `cargo build`/`cargo test` in one of the app's own terminals, or general system
load), which is also exactly when a developer using this IDE is most likely to be looking at it.

## Artifact Traceability

### spec.md

- **Affected user story**: User Story 2 — "Light and dark themes following the system" (P2),
  specifically the Edge Cases (`spec.md:107-108`): "What happens when the OS theme changes
  rapidly or repeatedly while the app runs? The app settles on the latest reported preference
  without flicker or stuck intermediate states."
- **Affected requirements**:
  - **FR-006** (`spec.md:129-130`) — "While following the system, the application MUST update
    its theme live when the operating system's preference changes, without requiring a
    restart." The live-update *mechanism* this requirement created (a poller) is exactly what
    manufactures a phantom "change" here — the OS preference never changed, but the poll still
    fires `SystemThemeChanged`.
  - **FR-018** (`spec.md:155-156`) — "When the OS theme preference is unavailable and the app is
    following the system, the application MUST fall back to a defined default theme." This
    requirement is written for **genuine, sustained** unavailability (e.g. a Linux box with no
    XDG portal, per Assumptions/R3) — it does not distinguish that from a **transient,
    single-poll detection failure**, which is the case actually being hit.
  - **SC-003** (`spec.md:178-179`) — "Changing the OS theme while the app follows the system
    updates the app's theme within 1 second and without a restart." This success criterion is
    what guarantees the bug is self-correcting (the next successful poll, ≤ 1s later, flips it
    back) — which is why it presents as a flash-and-revert rather than a stuck wrong theme.
- **Gap identified**: The Edge Cases section only considers *real* OS preference changes
  ("changes rapidly or repeatedly") and unavailability that is *permanent* for the session. It
  never considers "the poll's underlying OS query intermittently fails/times out for reasons
  unrelated to the actual OS preference" as a distinct case from "the OS has no preference." FR-018's
  fallback-to-light behavior is being applied to a case it wasn't written for.

### plan.md

- **Affected sections**:
  - `research.md` **R3** (`research.md:39-53`) — "**Decision**: Use the `dark-light` crate,
    version 1.x, calling `dark_light::detect() -> Mode`. **Rationale**: One synchronous,
    **infallible** call returns `Mode::{Dark, Light, Default}`... `dark-light` 2.x adds
    `detect() -> Result` ... but is **not the pinned version**; staying on 1.1.1 avoids an
    unnecessary churn." This is now false of the actual dependency (see Root Cause).
  - `research.md` **R4** (`research.md:55-71`) — the polling `Subscription` design ("emitting
    only on change prevents render churn/flicker") assumes the only source of a changed reading
    is a real OS change; it does not anticipate the poll itself occasionally reading garbage.
  - `plan.md` Technical Context, **Performance Goals** (`plan.md:58-61`) — documents the
    500 ms/1 s poll cadence and the "no flicker" goal, silent on detection-call reliability.
- **Impact**: `research.md` R3's rationale for staying on `dark-light` 1.1.1 (infallible
  `detect()`) no longer matches `Cargo.toml`, which pins `dark-light = "2.0"` (`Cargo.toml:38`)
  — a fallible `detect() -> Result<Mode, Error>`. The research doc needs to be corrected to
  reflect the 2.x dependency actually in use and to explicitly decide how a `detect()` error is
  distinguished from a genuine `Mode::Unspecified`/`Default` reading, since that distinction is
  exactly what's missing today.

- **False completions**: None — T020/T021 are implemented as literally specified. The task

  OS reading, so this isn't a task done wrong; it's a task whose spec never named the failure
  mode.
- **Missing tasks**:
  1. Change `detect_system_scheme()` (`src/main.rs:1565-1569`) to distinguish a `dark_light::detect()`
     `Err` (in particular `Error::Timeout`) from a real `Ok(Mode::Unspecified)`, and have the
     poller (`os_theme_poll`, `src/main.rs:1571-1573`) keep the **last-known** `system_scheme` on

  2. Update `research.md` R3 to reflect the actual pinned `dark-light = "2.0"` dependency

## Root Cause Analysis

`dark-light` 2.0.0's Linux backend (`~/.cargo/registry/.../dark-light-2.0.0/src/platforms/freedesktop.rs:9-21`)
implements `detect()` as a D-Bus round-trip to the XDG Desktop Portal wrapped in a **hardcoded
25 ms timeout**:

```rust
pub fn detect() -> Result<Mode, Error> {
    task::block_on(future::timeout(Duration::from_millis(25), async {
        let settings = XdgPortalSettings::new().await...;   // D-Bus proxy/connection
        let color_scheme = settings.color_scheme().await...; // D-Bus property read
        Ok::<Mode, Error>(color_scheme.into())
    }))
    .map_err(|_| Error::Timeout)?
}
```

25 ms is enough for the D-Bus connection + two round trips *only* when the process gets
scheduled promptly and the session bus responds quickly. Under CPU contention — the process's
own thread getting descheduled, or `dbus-daemon`/the portal service itself waiting for CPU time
— this routinely blows the 25 ms budget and returns `Err(Error::Timeout)`.

The binary's boundary mapping (`src/main.rs:1565-1569`) silently swallows *any* error into the
same bucket as a genuine "OS has no preference":

```rust
fn detect_system_scheme() -> SystemScheme {
    dark_light::detect()
        .map(map_system_scheme)
        .unwrap_or(SystemScheme::Unspecified)
}
```

This is called every poll tick (`os_theme_poll`, `src/main.rs:1571-1573`, every 500 ms focused /
1 s unfocused), on boot (`src/main.rs:367`), and on refocus (`WindowFocusChanged(true)`,
`src/main.rs:1057-1067`). `theme::resolve` (`src/theme.rs:75-85`) then applies FR-018's fallback:
`FollowSystem + Unspecified → Light`. So the sequence under CPU load is:

1. OS is actually in Dark; `state.system_scheme == Dark`, app renders Dark.
2. A poll tick's `dark_light::detect()` call times out (CPU busy) → `Err(Timeout)` →
   collapsed to `SystemScheme::Unspecified` → `SystemThemeChanged(Unspecified)` dispatched
   (it "changed" from `Dark`, so the no-op-on-same-value guard in T021 doesn't suppress it).
3. `resolve(FollowSystem, Unspecified) → Light` — the app flashes to the white/light theme.
4. The next poll (≤ 500 ms–1 s later), CPU pressure has usually eased, `detect()` succeeds,
   returns `Dark` again → app reverts to Dark.

This exactly matches the reported symptom: a periodic flash to white that self-corrects,
correlated with CPU load. The doc comment on `SystemScheme` (`src/theme.rs:58-59`) even records
this as deliberate: *"the binary performs the mapping (Dark→Dark, Light→Light,
Unspecified→Unspecified, and any detection `Err`→Unspecified)"* — but that decision was made
under the (now-stale) assumption from `research.md` R3 that `detect()` on the pinned version was
**infallible**. The actual pinned dependency, `dark-light = "2.0"` (`Cargo.toml:38`), has a
fallible, 25 ms-timeout-bounded `detect()` — the infallible-1.1.1 rationale in `research.md` no
longer describes the code. This is implementation drift from the documented research decision,
compounded by a spec gap: FR-018's "unavailable" fallback was written for sustained
unavailability, not single-poll transient failures, and the Edge Cases section never
anticipated the detection call itself being unreliable under load.

## Recommended Fix

1. Run `/speckit.bugfix.patch` to update spec artifacts:
   - Correct `research.md` R3 to describe the actual `dark-light = "2.0"` dependency and its
     fallible, timeout-bounded `detect()`.
   - Clarify FR-018 / the Edge Cases section to require that a **transient** detection failure
     hold the last-known system scheme (no visible change) rather than being treated the same as
     a genuine, sustained "OS reports no preference."
   - Reopen T020/T021 (or add follow-up tasks) to implement the last-known-value-on-error
     behavior in `detect_system_scheme()`/`os_theme_poll`, plus a testable seam and regression
     test for the timeout path.
2. Run `/speckit.bugfix.verify` to confirm consistency.
3. Resume `/speckit.implement` to apply the code fix at `src/main.rs:1565-1573` (and the
   equivalent boot/refocus call sites) so a `dark_light::detect()` error no longer overwrites a
   previously-known-good `system_scheme`.
