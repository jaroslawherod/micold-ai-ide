# Bug Report: A `settings.json` with no version number is discarded and every setting in it is lost

**Type**: Spec gap with an implementation defect downstream of it — the settings-schema contract
makes `settings_version` the one required field of the document, and the on-disk shape enforces
that by rejecting a document without it
**Severity**: High (every setting in the file — theme, scrollback, the environment-include trio,
the default AI CLI, service placement and the whole sandbox profile — is replaced by defaults, and
nothing is said. The file is moved to `settings.json.bak`, so the values are recoverable only by a
user who knows to look there)
**Feature**: `003-material-design-layout` (FR-009, FR-019;
`contracts/settings-schema.md`) — seam with `010-daemon-session-persistence`, whose FR-010c and
BUG-025 cover the neighbouring way stored settings become defaults
**Reported**: 2026-09-27
**Status**: **Fixed** — artifacts and code
**Patched**: 2026-09-27 (FR-022, the contract's field table, compatibility rules and versioning
section; plan.md §Storage; tasks T040–T041)
**Fixed**: 2026-09-27 (Phase 8, T040–T041)

**Found by**: a headless run of the application that lost an attempt. A settings file was written
by hand to point the run at a chosen environment-include script; the application ignored it and
started on defaults, which sourced the developer's own `~/.bashrc` instead.

## Description

`StoredSettings` in `crates/micold-core/src/settings.rs` is the on-disk shape of `settings.json`.
Every field of it carries a serde default — `theme`, `scrollback_lines`, the three
environment-include fields, the `daemon` block, `default_ai_cli`, `pi_activity_component` — and the
doc comments beside them record, one feature at a time, why each new field was additive and
defaulted and therefore did not move `settings_version`. `settings_version` itself was the single
exception: it had no default, so serde required it.

A document that omits it therefore fails to deserialize. `JsonFileSettingsStore::load` cannot tell
that failure from a truncated or corrupt document, so it takes the recovery path the contract
prescribes for an unparseable file: rename `settings.json` to `settings.json.bak`, return
`Settings::default()` with `LoadStatus::Recovered`. Nothing in the document is read, and nothing is
reported to the user — `Recovered` is the same status a genuinely corrupt file produces, and the
settings that were lost are ones the user chose deliberately.

The field that costs them is the one field nothing in the application reads. `settings_version` is
written by `StoredSettings::from_settings` and consumed nowhere: there is no migration, no gate, no
branch on its value, and `into_settings` drops it. It is documentation on disk. The document had to
carry a number that does nothing, and a number no one writing the file by hand can guess.

## Reproduction

```jsonc
// settings.json — real values, deliberately chosen, no version number
{
  "theme": "dark",
  "scrollback_lines": 12345,
  "env_include_enabled": false,
  "env_include_script_path": "/custom/env.sh",
  "env_include_timeout_secs": 42,
  "default_ai_cli": "Pi",
  "pi_activity_component": false
}
```

Before the fix, `JsonFileSettingsStore::load` on this file returns `LoadStatus::Recovered` and
`Settings::default()`, and the file is now at `settings.json.bak`. Adding `"settings_version": 4`
and nothing else makes the same file load every value in it.

## Artifact Traceability

### spec.md

- **Affected user story**: User Story 3 — the persisted user override.
- **Affected requirements**:
  - **FR-009** (`spec.md:143-144`) — the application must persist the user's theme preference
    across restarts. A stored preference in a document without a version number does not survive a
    restart; it is moved aside.
  - **FR-019** (`spec.md:173-174`) — a missing or invalid stored preference reverts to
    "follow system". That is the right answer for a preference that is absent or unreadable. It was
    being applied to a preference that was present and valid, because a *different* field was
    absent.
- **Gap identified**: the spec says what happens when the stored preference is missing or invalid,
  and never says which parts of the stored document are load-bearing. The contract answered that
  question — `settings_version` **required** — and the answer was wrong in the one direction that
  costs data, because nothing reads the field it made mandatory.

### contracts/settings-schema.md

- **Affected sections**: the field table (`settings_version` — Required: yes), the compatibility
  rules (which name `theme` as the field that defaults, and say nothing about the version number),
  and the versioning section (which says the field gates future migrations — it does not gate any).
- **Impact**: `settings_version` becomes optional, defaulting to `0`. The compatibility rule is
  stated once for the whole document rather than field by field: **every** field takes its default
  when absent, so no absent field can make a document unreadable. A *present* field still can — a
  wrong-typed value, or a string naming a variant this build does not know — and the amendment says
  so explicitly, because that asymmetry is the deliberate part and a rule that promised any JSON
  object would load would be the same kind of wrong contract as the one being fixed. The versioning
  section loses its claim that an unrecognised newer version recovers to defaults; no reader has ever
  done that.

### plan.md

- **Affected sections**: §Technical Context → Storage, which describes the
  "missing/corrupt-recovers-to-default pattern" as reused from `store.rs`. The pattern is right; the
  defect is that a complete, readable document was being classed as corrupt.

### tasks.md

- **Affected tasks**: T023–T029 (User Story 3, the persisted override) implemented
  `StoredSettings` and the roundtrip tests. No false completion: the tests written there cover a
  missing file, a corrupt file, and later features' missing fields, and every one of them passes.
  The case never tested is a document that omits `settings_version` alone — a case that only a
  hand-written file produces, which is why it survived four schema versions.
- **Added**: T040 (the failing test) and T041 (the fix), Phase 8.

## Resolution

`settings_version` takes `#[serde(default)]`, so a document that omits it loads with `0`.

`0` rather than `SETTINGS_VERSION` deliberately. Nothing reads the field, so the value cannot
change any behaviour today, and the choice is only about what the number would mean to a reader —
a person, or a migration gate that does not yet exist. `0` is a version no build has ever written,
so it says "this document named no version". `SETTINGS_VERSION` would say "this document was
written by this build", which is a claim about a file we know nothing about. No migration path is
introduced: there is none in the repository to extend, and adding one to express a default is the
cost the doc comments in `settings.rs` and `store.rs` have repeatedly declined to pay.

Gated by `a_document_without_a_version_number_keeps_every_value_it_holds` in
`crates/micold-core/tests/settings_roundtrip.rs`: a document holding non-default values for every
field but no `settings_version` loads all of them, reports `LoadStatus::Loaded`, and leaves no
`settings.json.bak`.

## What this does not fix

**Absence is silent, so a misspelled key still loses a setting quietly.** An unknown key is ignored
(and preserved on save — 010's rule S-5), so `"env_include_script"` for `env_include_script_path`
leaves that field at its default, the document loads as `Loaded`, and nothing is reported. That was
already true of any document carrying a version number, and this fix extends it to documents without
one: a hand-written file that omits the version *and* misspells a key used to be recovered from, with
the `.bak` and the recovery report that tells the user their settings were reset, and now loads
cleanly with the misspelled setting missing. The user-visible symptom that opened this report —
starting on a default the user did not choose — is therefore still reachable by that route. It is
recorded in the contract's compatibility rules rather than fixed: distinguishing "this key is from a
newer release" from "this key is a typo" is not something a reader can do, and treating either as a
failure would undo rule S-5.

**`specs/006-real-terminal-emulator/contracts/settings-schema.md:23`** shows the on-disk example as
`"theme": "FollowSystem"`, which does not parse — `ThemePreference` serializes snake_case, so only
`"follow_system"` does. A hand-writer copying that example produces a document this schema rejects.
Not corrected here; it is another feature's contract, and the values are stated correctly in this
one.

## Sibling stores

`store.rs` has the same shape in two places — `StoredCatalog::schema_version`
(`crates/micold-core/src/store.rs:88`) and `StoredProjectState::schema_version`
(`crates/micold-core/src/store.rs:389`) are both bare `u32` with no serde default, while every
field around them is defaulted, and the doc comments there make the same "no `schema_version` bump,
the field is additive and defaulted" argument. A `projects.json` or a project state file without
its version number is therefore rejected and recovered the same way.

Not changed here. Those files are the durable contract of feature 002
(`specs/002-project-workspace-management/contracts/storage-schema.md`), a different closed feature,
and they differ from `settings.json` in one way that matters: no one writes them by hand. They are
recorded as a follow-up rather than folded into this fix.
