# Bug Report: Closing a session is silently undone by session reconciliation

**Type**: Spec conflict
**Severity**: High
**Feature**: 005-worktree-session-terminal (also implicates 002-project-workspace-management,
where the companion storage-fault-isolation work this conflicts with lives)
**Reported**: 2026-07-23
**Status**: Patched
**Patched**: 2026-07-23

## Description

Closing a session (`Message::SessionCloseRequested`) kills its `claude` process and deletes its
persisted record outright (`list.retain(|s| s.id != id)` in `src/app.rs`), per **FR-015a**
("removing the session from the sidebar"). Separately, the session-reconciliation fix added by
002/BUG-001 (**FR-020b**) scans the AI CLI provider's transcript directory on every project open
and reconstructs a session for any transcript with no matching persisted record — precisely so a
lost/corrupted store doesn't orphan a real conversation.

These two correctly-implemented requirements contradict each other in practice: `claude`'s own
transcript file is never deleted by closing a session, so closing a session and reopening the
project **immediately resurrects it** via reconciliation. The user's explicit "close" is silently
undone the next time the project is opened.

Worse, a naive fix — tracking "this session was closed" only in the app's own JSON store — would
itself be vulnerable to the exact storage-corruption/loss scenario 002/BUG-001 was about:
reconciliation's whole purpose is to treat that store as untrustworthy, so anything that blocks
reconciliation must not depend on that same store being intact.

The requested fix has three parts:
1. A new, explicit **Remove** action (permanent delete, behind a confirm dialog mirroring the
   existing worktree-delete confirm pattern) distinct from Close.
2. **Close** repurposed to *archive* the session: kill the process, keep the record (hidden from
   the sidebar — an invisible tombstone, never browsable again), excluded from reconciliation.
3. The archived/removed status must be **durable against the app's own store being corrupted or
   lost entirely** — achieved by writing a small marker file (e.g. `<session-id>.archived`) next
   to the session's transcript in the AI CLI provider's own directory
   (`~/.claude/projects/<encoded-cwd>/`), via a new `AiCliProvider` seam (`mark_archived`/
   `is_archived`), so reconciliation's skip-check survives even if `projects.json` and the
   per-project state file are both gone. Both Close and Remove write this marker — they differ
   only in whether the app's own local `Session` record survives (Close keeps a hidden
   `archived: true` record for fast in-memory filtering; Remove deletes it outright).

## Artifact Traceability

### spec.md

- **Affected user story**: User Story 3 — Start a session and interact with the embedded terminal
  (P1), specifically its close/remove sub-behavior.
- **Affected requirements**:
  - **FR-015a**: "System MUST allow the user to close/stop an active session, terminating its
    `claude` process and removing the session from the sidebar." Written before FR-020b existed;
    "removing... from the sidebar" was assumed to mean "gone," but says nothing about whether a
    later reconciliation pass may bring it back.
  - **FR-020b** (002/BUG-001): reconciles a project's sessions against the provider's transcripts
    on open, reconstructing any orphan with no persisted record — with no exception for a session
    the user intentionally closed, because FR-015a gave it nothing to check against once the
    record was deleted.
- **Gap identified**: FR-020b was added without auditing its interaction with FR-015a. Neither
  requirement is individually wrong; their combination produces the contradiction (an explicit
  user action — close — is reversed by an unrelated background action — reopening the project).
  The spec needs: (a) a Close/Remove distinction, (b) an explicit statement that a
  closed-or-removed session's suppression MUST survive even if the app's own persisted store is
  corrupted or lost (i.e. FR-020b's reconciliation must consult a source of truth independent of
  the same store 002/BUG-001 already established as untrustworthy).

  BUG-002) and the 002/BUG-001 storage-split note, but has no mention of session
  archival/removal or a durable out-of-store suppression marker.
- **Impact**: add a design note describing the marker file mechanism and where it lives relative
  to the existing provider seam (`src/provider.rs`), so the "why a file next to the transcript,
  not in our own store" reasoning is recorded architecturally, not just in code comments.

  - **T065/T066** (bugfix 002/BUG-001, session reconciliation) — correctly implemented FR-020b as

- **Missing tasks**: (a) `Session.archived` field + `Session::archive()` + persistence
  (`StoredSession.archived`); (b) `AiCliProvider::mark_archived`/`is_archived`/
  `archived_marker_path`; (c) repurpose the Close handler to archive instead of delete, and call

  reconciliation's discovery loop skips any orphan transcript for which `is_archived` is true;
  (f) sidebar filtering (`State::active_sessions()`) excludes archived sessions.

## Root Cause Analysis

**Spec gap from an un-audited interaction.** FR-020b (002/BUG-001) was added specifically to make
session state recoverable from a source independent of the app's own store — a deliberate
response to that store being untrustworthy. But nothing at the time checked FR-020b against
FR-015a's existing "close deletes the record" behavior, so the new recovery mechanism now recovers
sessions the user explicitly asked to get rid of. The same reasoning that motivated FR-020b (don't
trust the app's own store) also means the fix can't simply record "closed" in that same store —
it has to live somewhere reconciliation already treats as authoritative: the provider's own
transcript directory.
