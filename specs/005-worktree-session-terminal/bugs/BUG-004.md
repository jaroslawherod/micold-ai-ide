# Bug Report: the crash-loop guard never trips for a session that fails slower than one supervision tick

**Type**: Implementation defect
**Severity**: Medium
**Feature**: 005-worktree-session-terminal
**Reported**: 2026-08-21
**Status**: Open
**Found by**: quickstart V7, run manually for the first time (evidence/T061-manual-validation.md)

## Description

**FR-022a** requires that "after a bounded number of failed restarts **within a short interval**"
the system stops auto-restarting and surfaces a clear error. The bound is
`MAX_RESTART_ATTEMPTS = 3` (`crates/micold-core/src/session.rs:85`) and the counter lives in
`SessionLifecycle::Restarting { attempts }`.

The counter is reset by *liveness*, not by elapsed time. The daemon's supervision tick
(`SUPERVISION_INTERVAL = 250 ms`, `crates/micold-daemon/src/server.rs:136`) calls
`Catalog::mark_running_if_restarting` for every session it observes still alive
(`crates/micold-daemon/src/state.rs:1055-1062`), and `Session::mark_running` sets `Running`, which
`on_unexpected_exit` then reads as `attempts = 0`.

So the guard only counts restarts that die **within 250 ms of spawning**. A child that reliably
comes up, lives about a second, and then exits non-zero is marked healthy on every cycle, the
counter returns to zero on every cycle, and the session restarts **forever**.

## Reproduction (observed, not theorised)

Fixture: `/home/jaro/.aaa-vp83d/w5repo`, a session on the `feat-abc-123_login-page` worktree,
`claude` v2.1.238. The harness's `claude` runs with transcript saving off (it inherits a
`CLAUDE_CODE_CHILD_SESSION` marker), so `claude --resume <session-id>` has nothing to resume and
exits non-zero after roughly a second — an ordinary slow failure, not a contrived one.

1. Start a session on a worktree; confirm its `claude` PID.
2. `kill -9` that PID (FR-022's "terminated externally").
3. Auto-restart fires immediately — correct, FR-022 passes.
4. Every restart then fails the same way, and a new PID appears about once per second:

```
t=0.8s  619698     t=3.2s  619966     t=9s   620807     t=13s  621164
t=1.6s  619827     t=4.8s  620107     t=10s  620936     t=14s  621278
t=2.4s  619827     t=5.6s  620223     t=11s  621038     t=16s  621414
```

5. Left alone for ~4 minutes it was still going (`626262`, then `626479` three seconds later).
   It never reached `Failed`; the status readout oscillated between `restarting…` and `running`
   (`evidence/v46-restart-loop.png`). Closing the session stopped it — the only exit.

## Why the automated tests miss it

`crates/micold-daemon/src/supervision.rs:84-142` drives `supervise_exit` directly, so consecutive
`Crashed` outcomes do accumulate to `GiveUp` — the core FSM is correct and its tests are right.
Nothing exercises the daemon's own liveness reset in between, which is where the counter is lost.

## Impact

- FR-022a's stop condition is unreachable for any failure slower than 250 ms, which is most of
  them: a bad `--resume`, a missing credential, an exit inside the CLI's own startup.
- The user is never shown the "clear error" the requirement promises, and the manual-retry path
  behind it is never reached — the session simply looks busy forever.
- One process spawn per second, indefinitely, for as long as the app is open.

## Note on the reset itself

The reset is deliberate and documented in place — it "closes the L5 gap: crashes far apart no
longer accumulate toward `Failed`". That gap is real; the fix for it just went too far. A
time-windowed counter (N failures within a rolling interval, which is what FR-022a actually says)
satisfies both: crashes minutes apart still don't accumulate, and a once-a-second crash loop still
trips the guard. Resetting on liveness alone cannot express "within a short interval".

## Secondary observation (same reproduction, cosmetic)

rather than "Claude Code" (`evidence/v46-restart-loop.png`). The default name is lost on restart
instead of falling back to the unnamed label. Not filed separately; it disappears when the same
