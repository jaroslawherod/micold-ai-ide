# Bug Report: A session spawns at the 100×30 seed and stays there — the pane size is only ever sent as a *change*, and a size sent before the process exists is dropped

**Type**: Spec gap (nothing states *when* a session learns the viewer's size — only what happens when
it *changes*) → resulting implementation defect spanning the client/daemon seam
**Severity**: High (the terminal is unusable at its intended size on most session starts: the process
lays out `claude`'s interface for a 100×30 screen inside a pane two or three times that, leaving the
rest of the pane blank; every session start after the first is affected, and the only recovery is a
window resize the user has to know to perform)
**Feature**: `006-real-terminal-emulator` (FR-014, FR-015, SC-004) — seam with
`010-daemon-session-persistence` (its "Resize while detached" edge case, FR-020). Observed on branch
`fix/the-terminal-is-not-started-full-screen`, client build `micold-ai-ide/0.6.0`
**Reported**: 2026-08-09
**Status**: Fixed (2026-08-09) — Phase 12 (T060–T064) in `006-real-terminal-emulator` and Phase 25
(T131–T132) in `010-daemon-session-persistence`. The daemon now holds a size per session
independently of its processes and seeds all three spawn sites from it; the client states the pane's
size before every `SessionStart`.
**Patched**: 2026-08-09 — FR-014a, SC-011 and a Clarifications entry added to
`006-real-terminal-emulator/spec.md` (FR-014/FR-015 annotated), its `contracts/terminal-render-input.md`
auto-resize rule extended with the start-time obligation, and Phase 12 (T060–T064) added to its
`tasks.md`. `010-daemon-session-persistence` gained FR-020a and SC-023, an annotation on its "Resize
while detached" edge case, the third bullet in `contracts/protocol.md`'s spawned-start section, and
Phase 25 (T131–T132). No task reopened in either feature.

## Description

The embedded terminal frequently starts at a fixed, small area of an otherwise empty pane instead of
filling it. The process's interface (`claude`'s UI, a shell prompt, `htop`) is laid out for a screen
of roughly 100 columns by 30 rows and wraps its output there, while the pane around it stays blank —
see the reported screenshot, where the session's text stops well short of both the right edge and the
bottom of the window.

Resizing the window corrects it permanently for that session: the content immediately reflows to the
full pane and stays correct.

**Expected** (FR-014): the size reported to the process matches the visible character area, from the
session's first byte of output.

## Root Cause Analysis

Three mechanisms compose. Each is locally reasonable; together they guarantee that a session started
after the pane last changed size runs at the spawn seed.

**1. The daemon spawns every process at a hardcoded 100×30 and nothing else ever seeds it.**
`PtySession::spawn` takes `initial_size: Option<(u16, u16)>` and falls back to `INIT_COLS = 100` ×
`INIT_ROWS = 30` (`crates/micold-daemon/src/supervisor.rs:34-35,140`). Every one of the daemon's spawn
sites passes `None`:

- `state.rs:806` / `state.rs:809` — `start_session` (the `SessionStart` path, both modes),
- `state.rs:996` / `state.rs:998` — `respawn_primary` (crash restart),
- `state.rs:1119` — `open_shell` (an additional Regular-terminal instance).

**2. A resize for a session whose process does not exist yet is silently discarded.**
`ClientMsg::SessionResize` walked `state.session_ptys(session)` (`server.rs:625-641`), and
`session_ptys` returns an empty vector for a session with no live entry (`state.rs:1046-1054`). The
loop therefore runs zero times and the requested size is dropped: **the daemon holds no notion of a
session's desired size, only of its live PTYs' current one.** This is not a rare race. `SessionStart`
is deliberately *spawned*, not run inline (BUG-009/T125, FR-026a) — it resolves the environment-include
script first, which the user may configure with a timeout of up to 60 s — so a resize sent immediately
after a start routinely arrives while the session still has no process at all.

**3. The client only ever reports the size as a *change*, and never at the moment a session starts.**
The pane widget publishes `Message::TerminalResized` only when its computed grid differs from the last
one it published (`terminal_pane.rs:548-556`, `PaneState::last_grid`). The handler forwards it to *the
currently active session only* and drops it entirely when there is none (`main.rs:1805-1817`). Nothing
re-reports the size when a session is started, selected, or created: `view_and_start`
(`main.rs:2183-2192`) and the `SessionSelected` arm (`main.rs:1567-1583`) send `SessionStart` +
`SetViewedSession` and nothing more.

So for the common case — the app is already open at a stable window size and the user starts or
selects a session — the pane's pixel size never changes, no `TerminalResized` is ever published, and
the new session lives out its life at 100×30. A window resize is the only event that produces a fresh
size, which is exactly the observed workaround.

`App::last_grid` (`main.rs:140-144`, written at `main.rs:1807`) was added for precisely this purpose —
its own doc comment and the regression test
`terminal_resized_remembers_the_pane_size_for_future_spawns` (`main.rs:3116-3170`) say new sessions are
to be seeded from it — but **no code reads it**. The field is remembered and then never used; the test
pins the remembering and not the use, so it passes over a bug it was written to prevent.

Why no artifact caught it: FR-014 states the invariant ("the size the terminal reports to the process
MUST match the visible character area") and FR-015 states the *change* trigger ("when the window or
terminal pane is resized"). Both were written for feature 006's in-process terminal, where the `Term`
was created by the same code that knew the pane's size, so the invariant held at spawn for free and
only the change path needed stating. Feature 010 moved the spawn into a separate long-lived process
that has never seen the pane — and its own spec anticipated exactly this ("**Resize while detached**:
… the session keeps a defined size and **adopts the attaching client's size on attach**", spec.md:288)
but promoted it to no requirement, so nothing was built for it and no test asserts it. The obligation
that fell in the gap: **a session must learn the viewer's size when it starts, not only when that size
changes.**

## Artifact Traceability

### spec.md — `006-real-terminal-emulator`

- **Affected user story**: **US4** — "Correct sizing, resize, and scrollback".
- **Affected requirements**: **FR-014** (reported size matches the visible character area) — violated
  from the session's first output until an unrelated user action; **FR-015** (reflow *when resized*) —
  works as written, and is the only path that sets the size at all, which is the defect;
  **SC-004** (reflow within one visible redraw after a resize) — passes, and cannot catch this: it
  measures the change path exclusively.
- **Gap identified**: no requirement covers the *initial* size of a session's process. FR-014 states
  the invariant without naming an event that establishes it, and FR-015 names only a change. Nothing
  says a newly started session must be given the current pane size, nor that a size reported for a
  session that is not running must be honoured when it starts.

### spec.md — `010-daemon-session-persistence`

- **Affected requirements**: **FR-020** (input, resize, kill and start actions are dispatched without
  blocking the UI) — the dispatch is correct; what is missing is any statement that a resize is
  *durable state of the session* rather than a command to a running process. The **"Resize while
  detached"** edge case (spec.md:288) already specifies the intended behaviour — the session "adopts
  the attaching client's size on attach" — but has no FR, no task, and no test behind it, and the
  implementation does the opposite.
- **Gap identified**: the service owns session spawning but has no concept of a session's desired
  viewport, so it cannot honour a size that arrives before a process, nor re-apply one across the
  respawn it performs on a crash.

### plan.md

- **`006-real-terminal-emulator`**: the widget/runtime split ("`RuntimeTerminal`: dynamic rows/cols +
  resize (Term+PTY)", plan.md:97) put sizing entirely inside the in-process runtime the pane could
  see. That component no longer spawns anything; the plan has no successor statement for who seeds a
  size across the daemon boundary.
- **`010-daemon-session-persistence`**: the workstream that moved spawning behind the service. Its
  protocol contract describes `Resize` only as an ordering and resnapshot trigger
  (`contracts/protocol.md:132,232-236`) — a message about frames, never about session state.

### tasks.md

- **Affected tasks**: `006-real-terminal-emulator` **T029** (emit `TerminalResized` on layout change;
  apply it via `RuntimeTerminal::resize`) — implemented as specified, and specified only for the
  change path. **T028** (failing gui tests for the layout→(cols, rows) computation) — its coverage
  stops at the widget's arithmetic, which is correct; nothing tests what a session is *started* at.
  `010-daemon-session-persistence` **T053** (session management through the daemon) — the spawn sites
  that hardcode `None`.
- **False completions**: none. T029 and T028 are correct for their stated scope; they are incomplete
  against FR-014 rather than wrong. Worth recording that the client-side regression test
  `terminal_resized_remembers_the_pane_size_for_future_spawns` (`main.rs:3116`) asserts a value is
  stored for a consumer that was never written — a green test standing in for an absent behaviour.
- **Missing tasks**:
  1. Give the daemon a per-session desired size that exists independently of a live process: record
     it on `SessionResize` whether or not the session is running, and seed every spawn site
     (`start_session`, `respawn_primary`, `open_shell`) from it.
  2. Make the client state the size at the moment it matters: send `SessionResize` from
     `App::last_grid` *before* `SessionStart` in `view_and_start` and the `SessionSelected` arm, so a
     session is created at the pane's real size rather than corrected afterwards.
  3. Regression test in `crates/micold-daemon/tests/`: a size requested for a session that is not
     live is adopted by the subsequent spawn (and survives a respawn), rather than being discarded.
  4. Regression test in `micold-client`: selecting/starting a session queues `SessionResize` with the
     known pane size ahead of `SessionStart` — closing the gap the existing `last_grid` test leaves.
  5. Record the rule in the artifacts: a session's size is state, established at start and updated on
     change — not a command that requires a running process to receive it.

## Reproduction

1. Open the app on a display where the terminal pane is meaningfully larger than 100×30 (any
   maximised window on a modern display).
2. Select a session in the sidebar, or create one, without resizing the window first.

Expected: the session's process lays out its interface for the whole pane. Actual: it lays out for
100 columns × 30 rows in the pane's top-left, and the rest of the pane stays blank until the window is
resized.

**Verification status**: reproduced executably and closed.
`a_session_spawns_at_the_size_last_requested_for_it` (`crates/micold-daemon/tests/session_start.rs`)
requests 220×60 for a session that has no process, starts it, and reads the spawned grid: pre-fix it
was `(100, 30)`, the seed, against the requested `(220, 60)`. It now passes, and covers an additional
shell instance in the same test; `a_respawn_comes_back_at_the_sessions_recorded_size`
(`tests/supervision_restart.rs`) covers the crash-respawn site. On the client,
`displaying_a_session_states_the_pane_size_before_starting_it` (`micold-client`'s `main.rs` tests)
asserts the `SessionResize`-then-`SessionStart` order on a real `Outbox`, with a companion test for
the no-size-yet case.

**Visual pass** (T064, 2026-08-09, `visual-pass` skill): Xvfb `:77` at 1600×1400 with lavapipe,
running against a private daemon and catalog (`XDG_RUNTIME_DIR` / `XDG_DATA_HOME` in a temp dir) so
no live session of the user's was involved. A session started with **no window resize after launch**
came up with the AI CLI's interface spanning the full pane, and `stty size` on the spawned process's
pty read **69 rows × 165 columns** — the pane's own size, where the pre-fix build would have reported
30 × 100. Static appearance and the reported size are covered; nothing about animation or frame pacing
was, and the pass ran on one platform (Linux/Xvfb) only.

## Related

- **BUG-009** (`010-daemon-session-persistence`) — the change that made `SessionStart` a spawned task
  rather than an inline one. Not a cause (the size was already dropped when no process existed), but
  it widened the window in which a client's resize arrives before the session has a PTY from
  microseconds to potentially tens of seconds.
