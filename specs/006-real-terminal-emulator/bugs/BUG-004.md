# Bug Report: Ctrl+Shift+C with nothing selected writes an empty string to the system clipboard, destroying whatever the user had copied

**Type**: Implementation defect (the chord path lacks the emptiness guard its sibling
auto-copy-on-release path already has)
**Severity**: Medium (silent, unrecoverable loss of clipboard content the user put there from
another application; nothing in the UI indicates it happened, and the clipboard has no undo)
**Feature**: `006-real-terminal-emulator` (FR-013, US2/US3). Observed on branch
`docs/cleanup-completed-features`, client build from this branch
**Reported**: 2026-08-25
**Status**: Open

## Description

Pressing the copy chord **Ctrl+Shift+C** while the terminal pane is focused and **no text is
selected** writes an empty string to the standard clipboard. The clipboard's previous contents —
typically something the user copied from their browser or editor a moment earlier — are gone.

A real terminal treats a copy with an empty selection as a no-op. This one treats it as "copy
nothing", which is a destructive write.

**Expected**: with no selection, the copy chord does nothing and the clipboard is left alone.

## Root Cause Analysis

Two paths in `TerminalPane::update` copy the selection. They disagree about the empty case.

The mouse path guards it (`crates/micold-client/src/ui/material/terminal_pane.rs:902-911`):

```rust
Event::Mouse(mouse::Event::ButtonReleased(mouse::Button::Left)) if state.dragging => {
    state.dragging = false;
    // Auto-copy the selection to the clipboard on release (FR-013).
    let selected = self.selectable_content();
    if !selected.is_empty() {
        clipboard.write(ClipboardKind::Standard, selected);
    }
    ...
```

The keyboard path does not (`terminal_pane.rs:1039-1042`):

```rust
KeyRouting::Copy => {
    clipboard.write(ClipboardKind::Standard, self.selectable_content());
    shell.capture_event();
}
```

The **third** copy surface — the right-click menu's "Copy" — is guarded too, and differently: it
routes through `shell::clipboard::on_copy_requested`, whose `selection_copy_request`
(`crates/micold-client/src/shell/clipboard.rs:44-54`) returns `None` for an unresolvable or
whitespace-only selection, so nothing is written at all. Verified in the same run: with
`alpha beta gamma delta` on the clipboard and no selection, the menu's Copy left it intact.

So of the three surfaces FR-013 names, two are correct and one is not.

`selectable_content` (`terminal_pane.rs:528`) returns an empty `String` when there is no selection,
so the chord's write goes through unconditionally. `KeyRouting::Copy` is produced by the keymap for the
platform copy chord regardless of selection state — routing is a pure function of the key event and
has no view of the grid — so the guard has to live here, where the selection is known.

Why no test caught it: the routing decision (`Ctrl+Shift+C → KeyRouting::Copy`) is unit-tested in
the keymap, and `selectable_content`'s empty case is covered by its own tests. What is untested is
the composition — that a `Copy` routing with an empty selection must not reach `clipboard.write` —
because `update` needs a real `Shell` and `Clipboard`, i.e. a GPU-backed renderer. That is the same
Constitution I GUI-wiring exception T042 exists to cover, and this is exactly the class of defect it
is meant to find.

## Artifact Traceability

- **Affected user story**: **US2** (input and interaction) / **US3** (focus gating) — the copy
  gesture belongs to both.
- **Affected requirement**: **FR-013** — "Users MUST be able to copy selected terminal text …
  through … platform-standard terminal chords". The requirement says *selected* text; it does not
  say what happens with no selection, and the implementation chose the destructive reading.
- **Gap identified**: no requirement states that a copy gesture with an empty selection is a no-op.
  The auto-copy clause and the chord clause are one bullet each, and only the auto-copy path was
  implemented with the invariant in mind.
- **Affected task**: **T042** (this quickstart pass) is what surfaced it. No implementation task is
  falsely completed — the chord is wired, which is what its task claimed.
- **Missing task**: guard the empty case in `KeyRouting::Copy`, and add a headless regression test
  through feature 019's apparatus asserting no clipboard write occurs for a copy chord with no
  selection.

## Reproduction

Reproduced on Xvfb `:83` + lavapipe, 2026-08-25, entirely inside the app (no external clipboard tool
needed):

1. In a Regular Terminal session, run `echo CLIPSENTINEL-ALPHA`.
2. Drag across the `CLIPSENTINEL-ALPHA` output line. Auto-copy-on-release puts it on the clipboard.
3. Press **Ctrl+Shift+V** — `CLIPSENTINEL-ALPHA` is inserted at the prompt, proving the clipboard
   holds it (`evidence/bug-004-clipboard-before.png`).
4. `Ctrl+U` to clear the line, then single-click empty pane space to clear the selection.
5. Press **Ctrl+Shift+C** with nothing selected.
6. Type `PASTE>>`, press **Ctrl+Shift+V**, type `<<END`.

**Actual**: the prompt reads `PASTE>><<END` — nothing was pasted; the clipboard is empty
(`evidence/bug-004-clipboard-after.png`).
**Expected**: `PASTE>>CLIPSENTINEL-ALPHA<<END`.

**Verification status**: reproduced manually end-to-end; no executable regression test yet.

## Recommended Fix

Mirror the mouse path:

```rust
KeyRouting::Copy => {
    let selected = self.selectable_content();
    if !selected.is_empty() {
        clipboard.write(ClipboardKind::Standard, selected);
    }
    shell.capture_event();
}
```

Then run `/speckit-bugfix-patch` to state the invariant in FR-013 (a copy gesture with an empty
selection leaves the clipboard untouched) so both paths are specified rather than one being
accidentally correct, and add the headless regression test.
