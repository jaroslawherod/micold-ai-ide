# Bug Report: The terminal's focused state has no visual indication at all — the focused and unfocused panes are pixel-identical

**Type**: Implementation gap (a requirement clause was never built; the colour it needs exists and
has no call site)
**Severity**: Medium (the user cannot tell whether their keystrokes will reach the process or the
app. The two states differ only in where input goes, which is discoverable only by typing — and
typing into the wrong one is exactly the mistake the indicator exists to prevent)
**Feature**: `006-real-terminal-emulator` (FR-010, US3 AS2, US3 Independent Test). Observed on branch
`docs/cleanup-completed-features`, client build from this branch
**Reported**: 2026-08-25
**Status**: Open

## Description

FR-010 requires that "the focused state MUST be visually indicated", and US3's acceptance scenario 2
states it again: "the terminal gains focus **and this is visually indicated**". Nothing is drawn.
A focused terminal pane and an unfocused one are the same image, to the pixel.

**Expected**: some persistent, visible difference — the accent-coloured border the palette already
carries a colour for is the obvious one.

## Root Cause Analysis

The builder accepts the state and its own doc comment records that nothing is drawn from it
(`crates/micold-client/src/ui/material/terminal_pane.rs:470-474`):

```rust
/// Mark the pane focused (routes keyboard input to it; no border is drawn for this).
pub fn focused(mut self, focused: bool) -> Self {
    self.focused = focused;
    self
}
```

`self.focused` is read throughout `update` — it gates key routing, middle-click paste, mouse
reporting — and never in `draw`.

The colour for the indicator exists and is dead. `TermPalette::accent()`
(`crates/micold-client/src/ui/terminal.rs:92-95`) is documented as "The focus-indicator accent
color" and has **zero call sites** in the client:

```
$ grep -rn '\.accent()' crates/micold-client/src/ | grep -v toggle_chip
(no matches)
```

So the palette was built for the indicator, the widget was given the state the indicator needs, and
the drawing between them was never written. This is a gap rather than a regression — no commit
removed it.

Why no test caught it: the gui gates compare **layout**, and a border drawn inside an existing
widget's own bounds changes no rectangle. The `visual-pass` skill states this class explicitly —
geometry checks are structurally blind to colour and to anything that lives only in `draw`. Nothing
else was watching, because FR-010's visual clause has no task of its own: T042 (the manual pass) is
the only artifact that covers it.

## Artifact Traceability

- **Affected user story**: **US3** — "Focus gating between app and terminal".
- **Affected acceptance scenario**: **AS2** — "the terminal gains focus and this is visually
  indicated". Fails. AS1, AS3 and AS4 all pass (verified in the same run: keys typed while released
  never reach the process; Ctrl+Shift+E releases and the session keeps running).
- **Affected requirement**: **FR-010** — its routing clauses hold; its final clause ("The focused
  state MUST be visually indicated") is unimplemented. **FR-010a** is unaffected.
- **Affected tasks**: **T012** (`TerminalPane::draw`) — its enumerated scope covers cell rendering
  and never mentions the focus indicator, so it is not a false completion; the indicator simply has
  no task. **T042** is what surfaced it.
- **Missing tasks**:
  1. Draw the focus indicator in `TerminalPane::draw` from `self.focused`, using
     `TermPalette::accent()` — a 1–2 px inset border is the least intrusive form and the one the
     palette was designed for.
  2. Cover it in the `style_snapshot` gate rather than in layout: the snapshot records values, so a
     focused/unfocused pair with differing border colour is checkable without a renderer.
  3. Keep the FR-010 clause and its check paired in the quickstart so a future silent removal fails
     something.

## Reproduction

Reproduced on Xvfb `:83` + lavapipe, 2026-08-25, at 1600×1400:

1. Open a session with a Regular Terminal, click the pane to focus it.
2. Press **Ctrl+Shift+E** to release focus. Capture the frame.
3. Click the pane to focus it again. Capture the frame.
4. `compare -metric AE unfocused.png focused.png` → **`0 (0)`** — full frame *and* cropped to the
   terminal area alone (`1460x1310+140+58`), both zero.

That the two states genuinely differ was proved separately in the same run, so the comparison is not
vacuous: with focus released, typing `UNFOCUSED-KEYS` put nothing on the prompt; after the focusing
click, typing `FOCUSED-KEYS` appeared immediately (`evidence/bug-005-focus-gate.png`). Different
behaviour, identical pixels.

**Verification status**: reproduced and measured numerically. No executable regression test yet.

## Recommended Fix

Run `/speckit-bugfix-patch` to add a task under US3 for the indicator (FR-010 needs no amendment —
it already requires this), then `/speckit-implement`: draw the accent border in
`TerminalPane::draw`, delete the "no border is drawn for this" note from `focused()`, and pin it in
`style_snapshot`.
