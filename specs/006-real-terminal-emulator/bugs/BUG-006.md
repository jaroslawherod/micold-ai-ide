# Bug Report: Paste is not bracketed — a multi-line paste executes every line but the last, in any process

**Type**: Implementation gap (the paste paths write the clipboard's bytes raw; the terminal mode that
would wrap them is tracked and never read)
**Severity**: High (a paste of text the user did not intend to run *runs*. Pasting a snippet into
`claude`, or a multi-line command into a shell, submits the leading lines immediately and
irreversibly — the classic paste-execution hazard bracketed paste was invented to close)
**Feature**: `006-real-terminal-emulator` (FR-013, US2/US3; quickstart step 5). Observed on branch
`docs/cleanup-completed-features`, client build from this branch
**Reported**: 2026-08-25
**Status**: Open

## Description

The quickstart's step 5 states the expectation directly:

> **Expect**: selection copies; paste inserts text into `claude` without auto-submitting each line
> (bracketed paste honored).

It is not honoured. Pasting two lines runs the first and leaves the second on the prompt. The copy
half of step 5 works — auto-copy-on-release, Ctrl+Shift+C on a real selection, Ctrl+Shift+V and
middle-click all move text correctly. Only the *bracketing* is missing.

**Expected**: when the process has enabled bracketed-paste mode, the pasted bytes are wrapped in
`ESC[200~` … `ESC[201~`, so the process receives them as one literal block and readline (or
`claude`'s input widget) inserts newlines rather than acting on them.

## Root Cause Analysis

Nothing anywhere in the workspace mentions bracketed paste:

```
$ grep -rn 'bracketed\|BRACKETED\|200~' crates/micold-client/src crates/micold-core/src crates/micold-daemon/src
(no matches)
```

All three paste paths write the clipboard's bytes unchanged
(`crates/micold-client/src/ui/material/terminal_pane.rs`):

- middle-click, `:929-931` — `shell.publish(Message::TerminalBytes(pasted.into_bytes()))`
- the paste chord, `:1043-1048` — the same
- the right-click menu's "Paste", `crates/micold-client/src/shell/clipboard.rs:58-62` —
  `iced::clipboard::read().map(|c| Message::TerminalBytes(c.unwrap_or_default().into_bytes()))`

The information needed to do it right is already present and already used for something else. The
pane reconstructs the terminal's mode bits from the grid snapshot (`terminal_pane.rs:480-482`):

```rust
fn mode(&self) -> TermMode {
    TermMode::from_bits_truncate(self.grid.mode())
}
```

and `alacritty_terminal` sets `TermMode::BRACKETED_PASTE` (bit 4) from the process's own
`CSI ?2004h` (`alacritty_terminal-0.25.1/src/term/mod.rs:61,1970`). The same `mode()` helper already
drives `mouse_mode()` and `app_cursor`, so those bits demonstrably survive the daemon→client
snapshot. The wrapping was simply never written.

Why no test caught it: the keymap tests assert that Ctrl+Shift+V routes to `KeyRouting::Paste`, which
it does. What no test asserts is what bytes leave the widget afterwards — that needs `update` with a
real `Clipboard`, i.e. the Constitution I GUI-wiring exception that T042 covers.

## Artifact Traceability

- **Affected user story**: **US2** (input reaches the process faithfully) / **US3**.
- **Affected requirement**: **FR-013** — the three paste gestures are all wired, so the bullet list
  is satisfied literally. The bracketing obligation exists **only in the quickstart's step 5**, not
  in any FR. That is the gap: a hazard-class behaviour was specified in the validation procedure and
  nowhere in the requirements, so no task was ever generated for it.
- **Affected tasks**: nothing falsely completed — the paste tasks claimed the gestures and delivered
  them. **T042** is what surfaced it.
- **Missing tasks**:
  1. Promote the bracketing rule to an FR beside FR-013 ("when the process has enabled bracketed
     paste, pasted text MUST be delivered as a single bracketed block").
  2. Wrap pasted bytes in `ESC[200~`/`ESC[201~` when `self.mode().contains(TermMode::BRACKETED_PASTE)`
     — one helper, shared by all three paste paths.
  3. Strip `ESC[201~` occurrences from the pasted text itself, so a crafted clipboard cannot close
     the bracket early.
  4. Regression test through the feature 019 headless apparatus: a paste with the mode bit set
     produces bracketed bytes; with it clear, raw bytes.

## Reproduction

Reproduced on Xvfb `:83` + lavapipe, 2026-08-25:

1. In a Regular Terminal, `clear; printf 'echo AAA\necho BBB\n'` — two literal lines on screen.
2. Drag-select across **both** lines; auto-copy puts the two-line block on the clipboard.
3. Click once to clear the selection, then press **Ctrl+Shift+V** at the prompt.

**Actual** (`evidence/bug-006-multiline-paste.png`):

```
…/r10$ echo AAA
AAA
…/r10$ echo BBB
```

`echo AAA` was executed by the embedded newline; only `echo BBB` remains editable.
**Expected**: both lines sit on the prompt unexecuted, exactly as in any standalone terminal.

**Verification status**: reproduced manually end-to-end; no executable regression test yet.
