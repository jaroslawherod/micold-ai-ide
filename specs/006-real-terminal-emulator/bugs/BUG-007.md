# Bug Report: A program that asks the terminal for its background is told "light" in a dark pane — `claude` prints black text on black

**Type**: Spec gap, with an implementation defect downstream of it. FR-003 makes the default
foreground and background follow the theme *as drawn*, and never says a program that **asks** the
terminal for those colours must get the same answer. Since feature 010 the asking reaches a separate
service that has never been told the theme, and its contract (010 `contracts/protocol.md` §8, T034)
answers from a fixed palette "without involving the client's theme"
**Severity**: High (unreadable output in the application's primary use. `claude` on its default
`auto` theme picks its light palette and draws its body text, prompts and questions near-black on the
dark pane; the user cannot read what the agent is asking them. Any other program that adapts to the
terminal background — `vim`'s `background` detection, `bat`, `delta`, `pi` — makes the same mistake)
**Feature**: `006-real-terminal-emulator` (FR-003, US1/US2) — seam with
`010-daemon-session-persistence` (`contracts/protocol.md` §8, T034)
**Reported**: 2026-09-14
**Status**: Patched
**Patched**: 2026-09-14 — FR-003a and SC-014 added; tasks T074–T080; 010 `contracts/protocol.md` §8 and `contracts/messages.md` (`TerminalColorScheme`)

## Description

Reported with a screenshot of a `claude` session in the embedded terminal, dark theme: the
AskUserQuestion escalation text is dark grey/black on the black pane and "for a human is not
readable". Only the text `claude` draws in explicit accent colours (the purple `❯ 1.` option) is
legible.

**Expected**: a program that queries the terminal's default colours (`OSC 10 ; ?` foreground,
`OSC 11 ; ?` background, `OSC 12 ; ?` cursor) receives the colours the pane is actually painted with
under the active scheme, so a background-adaptive program chooses a palette that is readable on it —
and a program that asks again after a theme change gets the new colours. (Telling an already-running
program that the theme changed — DEC private mode 2031, which `claude` listens for — is not supported
before or after this fix; see the follow-up under Root Cause Analysis.)

## Reproduction (on `origin/main` `fadb8e9f`)

1. A `Term` wired with the daemon's real `DaemonListener` — built as `tests/support/mod.rs`'s
   `DrivenTerm` builds it, but over a writer the test keeps a handle to (an `Arc<Mutex<Vec<u8>>>`
   wrapped as the `SharedWriter`; `DrivenTerm`'s own `Vec` is private) — fed
   `ESC]10;?ESC\ ESC]11;?BEL ESC]4;0;?BEL` through `vte::ansi::Processor`, writes back to the PTY:

```text
ESC]10;rgb:e5e5/e5e5/e5e5ESC\      ← foreground: light grey
ESC]11;rgb:e5e5/e5e5/e5e5BEL       ← background: light grey  (the pane is dark)
ESC]4;0;rgb:0000/0000/0000BEL
```

2. `~/.claude/settings.json` has `"theme": "auto"`, so `claude` resolves its theme from that `OSC 11`
   reply. Run `claude` under a pty (e.g. Python's `pty.fork`) and answer its startup `ESC]11;?BEL`:
   answered `rgb:e5e5/e5e5/e5e5` it draws body text in its light palette (`38;2;102;102;102`);
   answered a dark colour it uses its dark palette (`38;2;153;153;153`). A background of `#e5e5e5`
   is light → light theme → dark-grey body text on a dark pane.

## Artifact Traceability

### spec.md (006)
- **Affected user stories**: US1 — See colored, faithful terminal output; US2 — Work interactively
  with the claude CLI.
- **Affected requirements**: **FR-003** ("When output specifies no explicit color, the terminal's
  default foreground and background MUST follow the application's active light/dark theme, and MUST
  update when the theme changes"); SC-002 (styled output renders equivalently to a standalone
  terminal — a standalone terminal answers these queries with its own colours).
- **Gap identified**: FR-003 binds only what the terminal *draws*. It says nothing about what the
  terminal *reports*. Before feature 010 that did not matter as much: the client owned the `Term` and
  could have answered from the palette it drew with. Once the VT moved into the session service, the
  answer came from a component with no knowledge of the theme, and nothing in 006 required otherwise.

### spec / contracts (010, the seam)
- **`contracts/protocol.md` §8** routes `ColorRequest` to "Daemon answers by writing to the PTY
  itself" — correct about *where* it is answered (a round trip to the client would stall the query),
  silent about *what* it answers with.
- **`crates/micold-daemon/src/terminal.rs` `StandardPalette`** (T034) is "a stable, conventional
  answer … without involving the client's theme". `StandardPalette::color` folds every index ≥ 256 —
  which is where `alacritty_terminal` puts the dynamic colours (`NamedColor::Foreground` 256,
  `Background` 257, `Cursor` 258) — to entry 7, `rgb(229,229,229)`. So foreground and background get
  the *same* light grey, which is not a colour pair any real terminal reports.
- **No wire message carries the scheme.** `ClientMsg` has no variant the daemon could learn the
  client's resolved `ColorScheme` from, and `DaemonSettings` carries only the persisted
  `ThemePreference`, which cannot resolve `FollowSystem` without the client's OS detection.

### plan.md (006)
- **Affected sections**: research R3 "Color & style mapping honoring the app theme" — defaults from
  `tokens::roles(scheme)` (`on_surface` / `surface`); plan's `ui/terminal.rs` palette row.
- **Impact**: R3's derivation has to be shared by the side that draws and the side that answers, or
  the two drift. It needs a home both binaries compile (`micold-core`), and the plan needs a bugfix
  note naming the new wire message.

### tasks.md (006)
- **Affected tasks**: T011 (`TermPalette` defaults from `tokens::roles(scheme)`, FR-003), T013 (theme
  change re-derives the palette, FR-003).
- **False completions**: none in 006 — T011/T013 deliver what FR-003 literally says. In 010, the
  `StandardPalette` doc comment T034 added (`crates/micold-daemon/src/terminal.rs`) claims the fixed
  palette "keeps VT programs correct"; for indices 256–258 it does not.
  T034 stays closed (its routing is right); the correction is recorded here and in 010's §8.
- **Missing tasks**: a failing daemon test for the `OSC 10/11/12` replies under both schemes; a shared
  default-colour derivation in `micold-core`; a client→daemon message reporting the resolved scheme
  (on every connection and on every change), with the protocol-version bump; the daemon holding the
  last reported scheme and answering from it; a client test that the report is sent; a visual pass
  with `claude` in the dark theme.

## Root Cause Analysis

A requirement written for a terminal that lived in one process survived the split into two. 006
specified the default colours in terms of rendering, which the client still does correctly. Feature
010 moved the emulator — and therefore the handling of colour *queries* — into the daemon, and
decided (rightly) that queries are answered there rather than round-tripped. It then answered them
from the only palette it had, an xterm table whose out-of-range fallback happens to be light grey. No
requirement tied that answer to the theme, no test issued an `OSC 11` query, and the symptom appears
only in programs that adapt to the background — which `claude`, the application's main tenant, does
by default.

Secondary, not fixed here: the daemon answers `OSC 4` for indices 0–15 from the xterm system colours,
while the client draws those indices from its own `STANDARD_ANSI16`. The two tables differ, so a
program that reads back an ANSI colour gets a value the pane does not use. Nothing observed depends on
it; it is recorded as a follow-up.

Also not fixed here: the terminal implements no theme-change *notification*. `claude` enables DEC
private mode 2031 (`ESC[?2031h`) and re-queries `OSC 11` only when the terminal sends
`CSI ? 997 ; 1|2 n`; `alacritty_terminal` 0.26 drops the mode as unknown and nothing sends 997. So a
`claude` started before a theme switch keeps its old palette until restarted. Most standalone
terminals lack mode 2031 too; supporting it is a follow-up (spec Edge Cases).
