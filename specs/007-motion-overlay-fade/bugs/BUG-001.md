# Bug Report: exit transitions start and are then cut off; entrances run to completion

**Type**: Regression against this feature's headline claim (FR-002, FR-003, SC-002)
**Severity**: Major — the feature's stated purpose is "overlay fade in **AND** out"; the out half
plays a few percent and is then discarded
**Feature**: 007-motion-overlay-fade (FR-002, FR-003, SC-002), and through the shared primitives
also 022-dedicated-select-component §B2 (SC-002/SC-003)
**Reported**: 2026-08-25
**Status**: Fixed — 2026-08-26
**Found by**: `007/quickstart.md` §3/§4 and `022/quickstart.md` §B2, both run for the first time on
2026-08-25 — [007 evidence](../evidence/T024-quickstart-pass.md),
[022 evidence](../../022-dedicated-select-component/evidence/B2-the-transition.md)

## Description

Every **entrance** animates and settles. Every **exit** renders a handful of frames covering a few
percent of its range and is then removed outright, mid-transition.

In the client the truncation happens so early that nothing is visible at all — one frame, present
then absent. In the showcase, which renders faster, the head of the exit survives long enough to be
photographed, and that is what identifies the defect as *truncation* rather than *absence*.

Measured by recording the X server at 60 fps (`gst-launch-1.0 ximagesrc … framerate=60/1`), so a
frame count is a count, not an impression.

### The client (`micold-ai-ide`)

| Transition | Rendered frames |
|---|---|
| About — open | ~16, 530×256 → 560×278, scrim dimming with it |
| Settings — open | ~14, 408×456 → 434×482 |
| About — close (Close button / Esc) | **1** |
| Settings — close (Cancel / successful Save) | **1** |
| Overflow menu — open | 3 |
| Overflow menu — close (Esc) | **1** |
| Main view — switch between two sessions | **1** |

Sidebar collapse (25 frames), sidebar expand (26), the resize-handle hover ramp (≥34) and the
button ripple (8) are all unaffected — none of them removes a widget from the tree.

### The pickers (022 §B2)

| Transition | Rendered frames | Range covered |
|---|---|---|
| Select list — open | 14 | compressed → full, settles |
| Typeahead list — open | ~5 | compressed → full, settles |
| Select list — close | 3 | 166 → 164 px, **~1%** |
| Typeahead list — close | 3 | 300 → 278 px, **~7%** |

### The primitives, in isolation (showcase Motion section)

This is the part that localises it. The gallery poses `Fade` and `Scale` with their own **Replay**
and **Reverse (play it out)** buttons — no overlay, no dialog, no dismissal gesture, nothing but the
primitive:

| | |
|---|---|
| `Fade` — Reverse | 6 rendered steps at a constant ~4.6% of alpha each — **23% of the visible range** — then the remaining ~77% in a single frame |
| `Scale` — Reverse | 6 steps, 246 → 236 px, then gone in one frame |
| `Scale` — Replay (for contrast) | first drawn frame already at 240 px, then 242, 244, 246 — arrives and settles |

So the exit is *wired*: the motion track advances, on a smooth, evenly-spaced ramp, for several
frames. It is then terminated before it finishes. Every surface in the app that leaves the tree
shows the same signature at whatever sampling rate it happens to render at.

## What it is not

- **Not frame starvation.** The obvious hypothesis was that `step_for` is frame-count stepped
  (`ui/cdk/motion.rs:37`, `FRAME = 16`), so an exit only advances while something else is
  requesting redraws — the pressed button's ripple, say — and dies when that stops. It was tested
  directly: the `Scale` Reverse was repeated while the pointer was driven continuously back and
  forth across two buttons, guaranteeing a redraw every frame. **It cut off at exactly the same
  place**, 236 px, same step count. The exit does not stop because frames stop arriving.
- **Not a premature `HIDDEN` threshold.** `HIDDEN` is `0.001`
  (`ui/material/animation.rs:36`), far below where these exits are being cut.
- **Not specific to a dialog, a gesture, or Escape.** Cancel, Esc, a successful submit, a second
  press on a trigger, and a `Reverse` button in a gallery with no overlay in sight all do it.
- **Not the harness.** The same instrument, on the same display, in the same session, resolves
  sixteen steps entering and one leaving.

## Consequences for the specs

- **FR-002** ("closing an overlay fades it out … via Cancel, Esc or a successful submit") — not met
  on any path, for either dialog tested.
- **FR-003** ("the app beneath progressively reappears") — cannot be met; the scrim goes from full
  to absent between two frames.
- **SC-002**'s 0.15–0.5 s band is met by the entrances and vacuously failed by the exits.
- **022 SC-002/SC-003** — "it fades out on the way, in noticeably less time than it took to arrive"
  is false for both pickers: it does not fade out, it is cut.
- Two 007 §5 clauses — *reveal-beneath* and *reopen during exit* — are **unanswerable while this
  stands**, because the interval they describe barely exists.

The renderer-independent half of "does an interrupted transition resume or snap?" is settled
separately and favourably, by `an_interrupted_transition_resumes_from_where_it_is` and
`rapid_toggling_never_sticks_part_way` in `crates/micold-client/src/ui/cdk/motion.rs`. The observed
reversal is consistent with them: a Select list interrupted after its enter went 167 → 165 → 164 →
gone, resuming downward from its current value rather than jumping to an end.

## Why the test suite is green

Nothing asserts that an exit *renders*. The two tests that own this area assert the pieces around
it:

- `tests/overlay_transition_identity.rs` — that a closing dialog keeps a stable identity, so the
  renderer does not restart the transition. Total, faithful, injective. It never asks whether a
  frame was drawn.
- `tests/overlay_dismissal_delta.rs` — *which* gestures close *which* surface, not what closing
  looks like.

`idle_requests_no_frames.rs` guards the opposite failure — an exit track that never finishes and
burns CPU forever — which is presumably why the truncation is there. Whatever cuts the exit short
is doing so far too eagerly.

The machinery reads correctly on inspection: `main.rs:365-375` takes the snapshot before every
message and hands it over when the open dialog goes to `None`; `ui/mod.rs:400-430` draws the
snapshot through the same registration as the live dialog with `.shown(false)`; `material::Modal`
gives the body `EXIT = SHORT_4` and `.exiting_over(EXIT)`; `animation.rs`'s `Motion::step` picks the
accelerate curve when the target is below the current value. The primitive-level evidence above says
the fault is below all of that, in whatever decides an exiting element is finished — this report is
the observation, not the diagnosis.

A regression test belongs with the fix, and it has to assert **frame count**, not identity: an exit
driven to completion must render more than one intermediate value and must reach its target before
the element is dropped.

## Root cause

**Not truncation.** Every one of these exits rendered every intermediate value and reached its
target. They were simply over before a 60 fps capture could photograph them.

`Progress` advanced a fixed `FRAME / duration` per redraw, with `FRAME = 16ms`
(`ui/cdk/motion.rs`), so a transition's duration was a **frame count**, not a time — and nothing
caps this application's frame rate. Instrumenting the track with an `eprintln!` per step, on the
same Xvfb display and in the same session as the captures above, measured the real cadence:

| Transition | Nominal | Steps rendered | Wall clock | Frame interval |
|---|---|---|---|---|
| Overflow menu — open | 150 ms | 10 | 53 ms | 5.9 ms |
| Overflow menu — close (Esc) | 150 ms | 10 | 45 ms | 5.1 ms |
| Dialog scrim — in | 300 ms | 19 | 96 ms | 5.4 ms |
| Dialog scrim — out | 200 ms | 13 | 59 ms | 5.0 ms |
| Showcase `Fade` — Reverse | 600 ms | 38 | 245 ms | 6.4 ms |

Every transition, in both directions, ran at 0.30–0.35× its stated duration. Nothing was cut: the
showcase `Fade` reverse logged all 38 of its steps down to `v=0.01882->0.00000`, and every dialog
exit published `on_hidden` exactly once, on the frame it reached zero.

What made only *exits* look broken is §6.3's easing. An entrance gets a **decelerate** curve, whose
`y` is front-loaded — `emphasized_decelerate` is past 0.7 by `t ≈ 0.15` — so the two or three frames
a 60 fps capture catches of a 60 ms entrance are most of its visible range, and it photographs as a
transition. An exit gets an **accelerate** curve, whose `y` is back-loaded:
`emphasized_accelerate = (0.3, 0.0, 0.8, 0.15)` is nearly flat for its first third. The same two or
three frames are then its flat head, and the whole rest of the range falls between capture frames.
Hence "3 frames covering ~1%", and hence "1 frame" wherever the capture landed a little later still.

The report's own numbers agree once read that way:

- `Scale` — Reverse's "246 → 236 px, then gone" is 1.0 → 0.959 against `MIN_SCALE = 0.96`. The exit
  **reached its target**; what came after it was a widget at rest, correctly not drawn.
- The **"not frame starvation"** experiment — driving the pointer to guarantee a redraw every frame,
  and finding it "cut off at exactly the same place, 236 px, same step count" — was evidence *for* a
  fixed step per frame rather than against it. A frame-stepped transition is deterministic in
  frames: more frames per second buys the same steps, sooner, not more of them.

So the localisation in *The primitives, in isolation* was right about where the fault lived and
wrong about what it was; "the fault is below all of that" holds, and it is the primitive's clock.
The module had already named the fix and deferred it — *"Moving to elapsed-time interpolation is a
visual change, and therefore feature 018's to make"* — and feature 018 did not make it.

## Resolution

`Progress` steps by the wall-clock time elapsed since its own previous frame, so a transition takes
the duration it states whatever rate the window renders at. Two bounds keep that from becoming a new
way to snap:

- **The first frame of a transition has no previous frame of its own.** Its clock started on the
  between-frames event that set the destination, and `last_frame` is whatever redraw the widget last
  saw — in a quiescent window, minutes ago. It steps by one nominal `FRAME` instead.
- **A gap longer than `MAX_STEP`** (64 ms, four frames) is clamped, so a stalled window makes a
  transition run long rather than jump the distance it "should" have travelled while nothing was on
  screen to travel it.

`Progress::on_event` now takes the traversal duration rather than a pre-computed per-frame step.
`step_for` stays, for the two callers that step by nominal frames on purpose: `Ripple::advance` and
`tests/adding_an_animation_touches_one_file.rs`.

### The gates

Both assert frame count *and* wall clock, as this report asked for, and both were confirmed to fail
against the old arithmetic before the fix went in.

- **`a_transition_takes_its_stated_time_however_fast_frames_arrive`** (`ui/cdk/motion.rs`) — the same
  200 ms exit driven at 16 ms and at 4 ms a frame must take the same wall clock, and the fast run
  must get there by drawing proportionally *more* intermediate values rather than by arriving early.
  Against the old code: 208 ms against 52 ms.
- **`a_dialogs_exit_animates_the_whole_way_out`** (`ui/material/animation.rs`) — the real
  `Modal` → `cdk::overlay` composition, rebuilt and diffed every frame the way the runtime does, and
  driven out at 4 ms a frame: more than one intermediate value, monotonically decreasing, reaching
  0.0, `on_hidden` published exactly once, and the whole exit spanning its stated `SHORT_4`. Against
  the old code: 52 ms for a 200 ms exit.

Neither weakens `tests/idle_requests_no_frames.rs`, which guards the opposite failure — an exit
track that never finishes and holds the render loop awake. Both new gates require the track to come
to rest, and the composed one stops counting the moment it stops asking for frames.

## Reproduction

Fastest, with no overlay involved — in the showcase gallery's **Motion** section:

1. `cargo run -p micold-client --bin micold-showcase`
2. Scroll to `Scale`. Press **Reverse (play it out)** and watch the card.
3. It shrinks a little, then vanishes rather than completing.

In the application:

1. Open the overflow menu, click **About**. It grows in, clearly.
2. Press **Esc**. Gone, with no intermediate state. Same via the Close button, and via Settings'
   Cancel and Save.

As data rather than impression, on a headless X server:

```bash
gst-launch-1.0 -q ximagesrc display-name=:83 startx=350 starty=250 endx=1249 endy=1149 \
  use-damage=false ! video/x-raw,framerate=60/1 ! videoconvert ! pngenc snapshot=false \
  ! multifilesink location=cap/f%04d.png &
# … drive the dismissal with xdotool while that runs, then diff consecutive frames
```

Both evidence notes carry the full per-frame traces.
