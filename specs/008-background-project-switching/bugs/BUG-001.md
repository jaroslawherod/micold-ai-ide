# Bug Report: returning to a project forgets which session you were on, unless that session is still running

**Type**: Spec gap — a design decision that was right for the world it was written in
**Severity**: High — it is the *normal* case now, not an edge one, and it reads to the user as the
application losing their place.
**Feature**: 008-background-project-switching
**Reported**: 2026-08-11
**Status**: Fixed — see [The fix](#the-fix). Reported by the user against a running build.

## Description

Switching to another project and back lands on the project overview rather than on the session you
left. Deterministic: first switch, both directions, both projects, on both switching paths (the
top-bar switcher and the folder picker).

The sessions are still there and still listed. Nothing was lost. The application simply declines to
select one.

## What the diagnostic said

`micold-client.log`, written by `log_foreground_choice` at each switch:

```
switch: entered /home/jaro/workspaces/max-speed     -> active_session=None
        choice=Some(NoneActive { sessions: 7 }) resolve_key=/home/jaro/workspaces/max-speed
        session_keys=[".../max-speed", ".../micold-ai-ide", ".../micold_time_track"]
switch: entered /home/jaro/workspaces/micold-ai-ide -> active_session=None
        choice=Some(NoneActive { sessions: 8 }) resolve_key=/home/jaro/workspaces/micold-ai-ide
        session_keys=[".../max-speed", ".../micold-ai-ide", ".../micold_time_track"]
```

Two things it settles immediately:

- **The lookup is correct.** `resolve_key` is one of the `session_keys`, so this is not a key
  mismatch — the hypothesis the log was built to catch, and it exonerated it in one line.
- **The projects have sessions — 7 and 8 — and none of them is active.** `NoneActive` is the
  resolve saying so.

## The mechanism

`explain_foreground` restores the remembered session only when it `is_active()` — `Starting`,
`Running` or `Restarting`. That is not an accident of implementation; it is written down, in this
feature's own `data-model.md`:

> `foreground_by_project[p]` MUST reference a session id present in `workspace.sessions[p]`; stale
> entries are ignored on restore and overwritten on the next switch-away. **A referenced session
> that is no longer running is treated as "no stored foreground"** (fall back to first running
> session, else `None`).

That was a reasonable call for the feature it was written for. Feature 008 is *about* sessions
continuing to run in the background; a session that had stopped was the exception, and falling back
to a running one put the user somewhere useful.

**What changed is the world around it.** Session lifecycle is not persisted — the record on disk is
`id`, `worktree_dir`, `title`, `mode`, `archived`, and nothing else — so every session is idle after
a restart until something starts it. Sessions accumulate: the reporting user has 7 and 8 non-archived
sessions in two projects, none running. The rule's edge case became its normal case, and the
fallback has nothing to fall back to.

## Why this is a defect and not just a preference

**The application is perfectly willing to display a stopped session.** Clicking one in the sidebar
selects it — `Message::SessionSelected` sets `active_session` with no lifecycle check at all, and
the terminal shows its scrollback.

So the two paths disagree about the same session: the user may select it by hand, but the app will
not return them to it. That inconsistency is the bug. A user cannot see why the row they were on
yesterday is selectable but not restorable, because from the outside those are the same act.

FR-003 itself is silent on the condition — it says *"restoring the previously foreground session to
the foreground"*, with no qualifier. The restriction lives only in the data model.

## Reproduction

1. Have a project with sessions that are not currently running (any project, after a restart).
2. Switch to another project.
3. Switch back.

Lands on the project overview. `micold-client.log` records `NoneActive { sessions: N }`.

## Artifact traceability

- **spec.md FR-003** — asks for the previously foreground session to be restored, unqualified.
  Amended by FR-003a below rather than reinterpreted.
- **data-model.md** — the invariant quoted above is where the running-only rule actually lives, and
  it is what changes.
- **quickstart.md** — "`switch_active` restores the stored foreground session, else first running,
  else `None` (BS-3)" needs the same amendment.

## The fix

**The remembered session is restored whether or not it is running**, provided it still exists and
has not been closed. The fallbacks are unchanged: no usable memory → the project's first *running*
session → nothing.

`archived` is the one condition that stays. A closed session is hidden from the sidebar entirely
(feature 010 BUG-003), so restoring one would display a session the user cannot see listed — trading
this bug for a stranger one.

Landing on a stopped session shows its scrollback and its lifecycle, which is exactly what clicking
it does. Nothing is started implicitly: restoring a session is a display decision, and starting a
process is not (FR-001/FR-002 are about not disturbing session lifecycle on a switch, and this
keeps that).

## Still open

**The memory itself does not survive a restart.** `foreground_by_project` lives on `State`, not in
the persisted workspace, so this fix only covers switching within a run. Restoring the last session
at launch is a separate feature — it needs persistence (Principle IV), and decisions this bug does
not reach: what happens when the remembered worktree is gone, and whether launch restore should
ever start anything.
