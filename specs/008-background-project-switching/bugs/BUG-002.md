# Bug Report: the project switcher stays open after you pick a project

**Type**: Contract violation — the behaviour is written down and the application does not do it.
**Severity**: Low — the switch itself is correct; the panel is left hanging over the view you just
switched to, so the second interaction the contract budgets for is spent dismissing it.
**Feature**: 008-background-project-switching
**Reported**: 2026-08-21, during T034's first manual run.
**Status**: **Fixed** — an accepted switch closes the switcher, and a refused one leaves it open over
the row's new unavailable badge (Phase 8, T036–T037; gated by
`shell::workspace::tests::picking_a_project_in_the_switcher_closes_it`).
**Fixed**: 2026-09-13 — see [The fix](#the-fix).
**Patched**: 2026-09-13 — FR-005 clarification note, plan.md "Bugfix: closing the panel and
rescanning on open".

## Description

Open the top-bar switcher, select an available non-active project. The project switches — the chip,
the title, the sidebar and the active marker all update — and **the panel remains open**.

`evidence/e26-switcher-stays-open.png`: red-bordered is before the press (chip `repo-b`, marker on
`repo-b`); blue-bordered is ~2 s after (chip `myrepo`, marker on `myrepo`, the switcher still there).

## What the contract says

[`contracts/project-switcher-ui.md`](../contracts/project-switcher-ui.md), "Interactions → Messages":

> | Select an **available**, non-active project | `Message::KnownProjectReopened(path)` (reused) |
> Runs `State::switch_active(path)`; sessions of both projects keep running (FR-001/002); incoming
> foreground restored (FR-003). **Panel closes.** |

Every other clause of that row holds. The last sentence does not.

It also costs SC-002 its own margin: *"Switching via the switcher is ≤ 2 interactions: open,
select"*. Open and select are two, and then a third press is needed to get the panel off the view.

## The mechanism

`KnownProjectReopened` lands in `crates/micold-client/src/shell/workspace.rs:136`:

```rust
pub(crate) fn on_known_project_reopened(app: &mut App, path: PathBuf) -> Task<Message> {
    app.core.workspace.refresh_availability(app.caps.scanner());
    let previous = app.core.workspace.active.clone();
    if app.core.switch_active(&path) {
        app.core.set_worktrees(discover_worktrees(app.caps.git(), &path));
        crate::log_foreground_choice(app, &path);
        switch_daemon_attachment(app, previous, &path);
    }
    Task::none()
}
```

It never assigns `project_switcher_open`. The only three assignments of `false` in the crate are
`app.rs:954` (HelpMenuToggled), `app.rs:960` (ProjectSwitcherToggled) and `app.rs:1256`
(SidebarFilterMenuToggled) — the overlay's *own* toggle and the two overlays that are mutually
exclusive with it. Selecting a row is not one of them.

The same message is also emitted by the body's "Known projects" list, where there is no panel to
close, which is probably why the assignment reads as unnecessary at the call site.

## Why no test caught it

The switcher's open/closed state is well covered — `toggling_switcher_opens_and_closes_it`,
`opening_switcher_closes_the_overflow_menu`, `opening_the_overflow_menu_closes_the_switcher`,
`right_click_opens_the_menu_and_the_switcher_stays_open_behind_it` (015 FR-009) — and
`switcher_entries_reflect_active_running_and_availability` covers the rows. Not one of them presses
a row and then asserts the panel is gone. Nothing in `crates/micold-client` mentions
`KnownProjectReopened` inside a test.

## Recommended fix

Set `app.project_switcher_open = false` inside the `if app.core.switch_active(&path)` arm of
`on_known_project_reopened` — on the accepted switch only. The rejected branch is reachable: a row
whose folder vanished since the last availability scan still carries its message, the scan at the
top of this function then marks it unavailable, and `switch_active` refuses (see
[BUG-003](./BUG-003.md)). Leaving the panel up there is the right outcome, because the press is what
makes the badge appear and the user should see it.

Then add the assertion the existing toggle tests never make: press a row, the switcher is closed.

## The fix

As recommended: `on_known_project_reopened` sets `project.switcher_open = false` first thing inside
the accepted-switch arm (the field is `app.core.project.switcher_open` since feature 028), and
nowhere else. The body's "Known projects" list sends the same message with the panel already
closed, where the assignment changes nothing.

Because the shell now reads and writes the flag, `project.switcher_open` no longer qualifies under
028's FR-007a component rule, and its entry leaves `COMPONENT_LOCAL` in
`crates/micold-client/tests/root_state_is_shared.rs` — that guard's own stale-entry check asks for
exactly that.

**Tests**: `picking_a_project_in_the_switcher_closes_it` (failed by assertion before the fix) and
`a_refused_pick_leaves_the_switcher_open` (a guard for the rejected branch, green before and after),
both in `crates/micold-client/src/shell/workspace.rs`.
