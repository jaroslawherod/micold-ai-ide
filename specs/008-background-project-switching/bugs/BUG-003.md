# Bug Report: a project's availability is scanned twice a lifetime, so the switcher's unavailable badge is always out of date

**Type**: Missing behaviour — the indication exists, is correct, and is fed from a value nothing
keeps current.
**Severity**: Medium — the badge is wrong in *both* directions, and the second one has no recovery
short of relaunching: a folder that comes back stays permanently unselectable.
**Feature**: 008-background-project-switching
**Reported**: 2026-08-21, during T034's first manual run (quickstart step 6).
**Status**: Open.

## Description

Two halves, observed in one sitting against the same pair of projects.

**A missing folder is not indicated.** With `myrepo` active and `repo-b` known, move `repo-b` aside
on disk and open the switcher. `repo-b` renders as a perfectly ordinary, selectable row — full-
strength label, no badge. Only when it is *pressed* does the badge appear, because the press is what
runs the scan.

**A restored folder stays marked.** Move it back. The row does not recover, and cannot: an
unavailable row carries no message, so pressing it runs nothing, and the scan that would clear the
flag is only reachable through the press. It is stuck until the application restarts.

`evidence/e25-unavailable-badge.png`: red-bordered is `repo-b` **after** its folder was moved and
before it was pressed — no badge; blue-bordered is the same row after one press — dimmed, with the
error-coloured marker.

The rendering is not at fault. Once the flag is right, the row is exactly what the contract
describes, and the switch is refused rather than silently accepted.

## What the spec says

`spec.md`, acceptance scenario 3 for the switcher:

> **Given** a known project's folder is missing or unavailable, **When** the user opens the
> switcher, **Then** that project is shown with an unavailable indication.

*When the user opens the switcher* — not when the user presses the row. The application satisfies
FR-008's second clause ("MUST NOT silently activate an unavailable project", confirmed below) and
misses its first ("MUST indicate projects whose folders are unavailable or missing").

## The mechanism

`Workspace::refresh_availability` (`crates/micold-core/src/workspace.rs:187`) is the only thing that
recomputes `Project::availability`, and it has exactly two callers in the whole workspace:

```
crates/micold-client/src/shell/startup.rs:104    core.workspace.refresh_availability(caps.scanner());
crates/micold-client/src/shell/workspace.rs:138  app.core.workspace.refresh_availability(app.caps.scanner());
```

Startup, and `on_known_project_reopened`. Nothing runs on `ProjectSwitcherToggled`, and there is no
periodic rescan. `switcher_entries()` (`app.rs:1794`) projects the stored flag —
`available: p.availability == Availability::Available` — so the panel shows whatever the last of
those two events left behind.

That the scan sits at the *top* of `on_known_project_reopened`, before `switch_active`, is what
saves FR-008's second clause: the press re-scans, `switch_active` (`workspace.rs:240`) then sees
`Availability::Unavailable` and returns `false`. Nothing was activated. The guard is real; it is
just also the only scan the running application ever performs.

## Confirmed by hand

| Step | Observed |
|---|---|
| `mv repo-b repo-b-moved`, open the switcher | `repo-b` bright, no badge, selectable |
| press `repo-b` | **no switch** — chip, title and active marker all stay on `myrepo`, which keeps its "2 running"; the row becomes dimmed + badged |
| `mv repo-b-moved repo-b`, press `repo-b` again | nothing at all — the row is disabled, so the press has nothing to run and the flag cannot clear |
| relaunch | `repo-b` available again, selectable, and it is the active project (from `last_active`) |

## Why no test caught it

The unit level is thorough and green: `refresh_availability_marks_missing_folder_unavailable`,
`switch_to_unavailable_is_rejected_and_leaves_state_unchanged`,
`reopening_unavailable_project_is_rejected_and_leaves_active_unchanged`,
`switcher_entries_reflect_active_running_and_availability`,
`a_switcher_row_reports_availability_and_activity_separately`, and — for the shared row widget the
switcher renders through — `ui::material::picker_press::an_unavailable_row_consumes_its_press`.

Every one of them calls `refresh_availability` itself, or sets the flag directly, and then checks
what follows. None asks *when the application calls it* — which is the entire defect.

## Recommended fix

Scan when the panel opens: call `refresh_availability` in the `ProjectSwitcherToggled` arm
(`app.rs:960`) on the transition to open. That is where the acceptance scenario points, it is
bounded work over the catalog, and it clears the latch as a side effect — a restored folder is
available again the next time the panel is opened.

Worth considering alongside it: the body's "Known projects" list reads the same flag and has the
same staleness, and its rows disable to a visible **Unavailable** button (014 scenario C), so a
folder restored while the app runs is stuck there too.

Then test the thing that is actually missing — open the panel, assert the scan ran — rather than the
seven variations of what happens once the flag is already correct.
