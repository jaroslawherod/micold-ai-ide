# Bug Report: Every worktree delete reports a folder-removal error despite succeeding

**Type**: Implementation drift
**Severity**: High
**Feature**: 008-worktree-sidebar-refinement (branch `fix/each-worktree-drop-results-in-error`)
**Reported**: 2026-07-20
**Status**: Patched
**Patched**: 2026-07-20

## Description

Deleting a worktree via right-click → Delete → confirm succeeds at the application level —
sessions are terminated, the git worktree and branch are removed, and the row disappears from
the sidebar — but an error banner is shown every time:

> Deleted worktree "<name>", but its folder could not be removed: No such file or directory
> (os error 2). Left at <path>

The path in the message does not exist, because it was already removed. The error is a false
positive: nothing was left behind, and there is no failure for the user to act on.

## Artifact Traceability

### spec.md

- **Affected user story**: User Story 2 — "Delete a worktree and everything it owns" (P2),
  acceptance scenario 3 (`spec.md:83`).
- **Affected requirements**:
  - **FR-020** — "On confirmation, the system MUST ... remove the worktree's working
    directory, all of its sessions, and its git branch, and MUST remove the worktree from the
    sidebar." Behaviour is satisfied; only the reporting is wrong.
  - **FR-023** — "If removal cannot fully complete, the system MUST surface a clear error and
    leave the system in a consistent state." **This is the violated requirement**: removal
    *does* fully complete, yet an error is surfaced. The requirement is stated one-directionally
    ("if it cannot complete → error") and never states the converse ("if it completes → no
    error"), which is the gap the implementation fell through.
- **Gap identified**: FR-023 does not require the success path to be silent, so an
  unconditional error on a successful delete is not literally forbidden by the spec text.

### plan.md

- **Affected sections**: `plan.md:75` — "`(worktree_remove(force)` → `worktree_prune` →
  `branch_delete)` plus `fs::remove_dir_all`"; `plan.md:130` — main.rs delete orchestration.
- **Impact**: The plan sequences `fs::remove_dir_all` *after* `git worktree remove --force`
  without noting that `git worktree remove` already deletes the working directory. The fs step
  is therefore a best-effort cleanup for the leftover case, not a step whose failure is
  meaningful. The plan should say so.

### tasks.md

- **Affected tasks**:
  - **T024** (`tasks.md:117`) — "Implement delete orchestration in `src/main.rs` ...
    `worktree_remove(force=true)` → `worktree_prune` → `branch_delete` → `fs::remove_dir_all`,
    then `update` reducer → `discover_worktrees` → `persist` (order per `CleanupStep`,
    **idempotent**)." The task explicitly called for idempotency; the implementation is not
    idempotent on the fs step.
  - **T018** (`tasks.md:108`) — `tests/worktree_delete.rs` covers the `FakeGit` orchestration
    only. `FakeGit` never touches the filesystem, so no test exercises the real post-remove
    state where the directory is already gone. `tests/worktree_delete.rs:107` asserts a locked
    worktree surfaces an error — true for `FakeGit`, but `GitCli::worktree_remove`
    (`src/git.rs:122-132`) swallows every git failure and always returns `Ok(())`, so that arm
    is unreachable in the real app.
- **False completions**: T024 is marked `[x]` but does not meet its own "idempotent"
  acceptance. T018 is marked `[x]` but leaves the failing path untested.
- **Missing tasks**:
  1. Treat `io::ErrorKind::NotFound` from the post-remove `fs::remove_dir_all` as success.
  2. Add a regression test asserting no notification is pushed when the worktree directory is
     already gone after git removal.
  3. Reconcile `GitCli::worktree_remove` swallowing git errors with FR-023's real-failure path
     (currently a genuine git failure is also silent).

## Root Cause Analysis

`git worktree remove --force <path>` deletes the working directory itself — that is its
documented behaviour. The orchestration in `src/main.rs:896-906` then unconditionally calls
`std::fs::remove_dir_all(&wt.path)` on the now-absent path:

```rust
// src/main.rs:896-906
match remove_worktree(&GitCli::new(), &repo, &wt.path, wt.branch.as_deref()) {
    Ok(()) => {
        if let Err(err) = std::fs::remove_dir_all(&wt.path) {
            app.core.notify_error(format!(
                "Deleted worktree \"{name}\", but its folder could not be \
                 removed: {err}. Left at {}",
                wt.path.display()
            ));
```

The call returns `ErrorKind::NotFound`, which is piped straight into `notify_error`
(`src/app.rs:625-627` → banner at `src/ui/mod.rs:89-110`). The fs step was intended as
belt-and-braces cleanup for the case where git leaves the directory behind (e.g. untracked
files under some git versions), but its "failure" was treated as a real failure.

The correct guard already exists at the sibling call site: the create-rollback
`CleanupStep::RemoveDir` at `src/main.rs:1229` uses `let _ = std::fs::remove_dir_all(&target);`,
deliberately ignoring the result. The delete path simply did not get the same treatment.

This is implementation drift rather than a spec gap: T024 asked for an idempotent sequence and
the code is not idempotent. FR-023's one-directional phrasing is a secondary, contributing
wording gap.

## Recommended Fix

   - Note in `plan.md` that `git worktree remove` already deletes the directory, so the

   - Reopen **T024** and **T018**; add the three missing tasks above.
2. Run `/speckit.bugfix.verify` to confirm consistency.
3. Resume `/speckit.implement` to apply the code fix at `src/main.rs:901` (treat
