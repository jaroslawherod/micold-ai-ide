# Bug Report: A worktree delete blocked by foreign-owned files reports a bare errno, abandons its sessions, and the worktree returns as an orphan

**Type**: Spec gap
**Severity**: High
**Feature**: 008-worktree-sidebar-refinement (delete semantics) / 010-daemon-session-persistence (T053 orchestration)
**Reported**: 2026-08-04
**Status**: Patched
**Patched**: 2026-08-04

## Description

Deleting a worktree whose directory contains files owned by another uid fails, and the worktree
then reappears in the navigation panel. Observed on three worktrees in the `max-speed` project:

```
INFO  worktree delete requested project=/home/jaro/workspaces/max-speed
      worktree=delivery-testcontainers stop_sessions=true delete_branch=true
ERROR worktree delete failed project=/home/jaro/workspaces/max-speed
      worktree=delivery-testcontainers error=Permission denied (os error 13)
```

Each of the three contains `delivery/.gradle/` and `delivery/build/` owned by `root:root` —
build output written by a containerized Gradle build through a Docker bind mount. The daemon runs
as the user, so it cannot unlink them.

What actually happens, in order:

1. `git worktree remove --force` **succeeds** and deregisters the worktree. Confirmed: none of the
   three appear in `git worktree list` afterwards, though all three directories remain on disk.
2. `remove_worktree_dir` then fails on the root-owned leftovers, and its `?` fails the whole
   operation (`crates/micold-daemon/src/server.rs:865`).
3. Because the operation is reported as failed, the session archiving gated behind it never runs
   (`server.rs:870-882`), leaving sessions bound to a worktree git no longer knows.
4. The surviving directory has no git registration, so `worktree::reconcile`
   (`crates/micold-core/src/worktree.rs:223-232`) classifies it `WorktreeStatus::Invalid` — an
   orphan — and the next catalog refresh **puts the row back in the sidebar**.

To the user this reads as the app resurrecting a worktree they deleted. It is in fact correctly
reporting a half-deleted one, but nothing in the message says so.

Two distinct defects:

1. **The error names no path.** `std::fs::remove_dir_all` reports only the first errno and never
   which entry stopped it, so the user gets `Permission denied (os error 13)` for a tree of tens
   of thousands of files with no way to identify the blocker or its owner.
2. **A partial success is reported as total failure.** git already released the worktree; only the
   directory survives. Treating that as a failed delete is what strands the sessions and produces
   the orphan row.

## Artifact Traceability

### spec.md

- **Affected user story**: User Story 2 — "Delete a worktree and everything it owns" (P2),
  acceptance scenarios 2 and 5 (`spec.md:79-89`).
- **Affected requirements**:
  - **FR-020** (`spec.md:263`) — "On confirmation, the system MUST first terminate any running
    session processes belonging to the worktree, then remove the worktree's working directory, all
    of its sessions, and its git branch, and MUST remove the worktree from the sidebar." Written as
    one indivisible act. In the daemon implementation it is at least two independently-failing
    steps (git deregistration, then directory removal), and the requirement says nothing about the
    state in which the first succeeds and the second does not.
  - **FR-023** (`spec.md:269`) — "if removal cannot fully complete, the system MUST surface a clear
    error and leave the system in a consistent state (**no partially-removed worktree lingering**)."
    **This is the violated requirement, and it is unsatisfiable as written**: when the blocker is a
    foreign-owned file, a partially-removed worktree lingering is the *only* reachable outcome. The
    daemon cannot unlink the files at any privilege it holds, so no amount of retry or rollback
    reaches the consistent state FR-023 demands. The spec offers no third outcome between "fully
    removed" and "failed".
  - **FR-023b** (`spec.md:280`) — "A genuine failure of any removal step MUST NOT be silently
    swallowed — it MUST reach the user via FR-023's error path." Satisfied in the letter (an error
    does reach the user) but not in the spirit: FR-023 requires a *clear* error, and a bare errno
    naming neither the path nor its owner gives the user nothing to act on.
- **Gap identified**: the spec models removal as atomic and total. It has no vocabulary for
  **partial success** — git released the worktree, the directory did not go away — even though that
  is a permanent, user-resolvable state rather than a failure. Nor does it say what a "clear error"
  must contain for the user to be able to resolve it.

### plan.md

- **Affected sections**: `plan.md:75-78` — "(`worktree_remove(force)` → `worktree_prune` →
  `branch_delete`) plus `fs::remove_dir_all` … the trailing `fs::remove_dir_all` is *best-effort*
  cleanup for the residual case, not a step whose failure is meaningful."
- **Impact**: the plan already calls the fs step **best-effort**, and BUG-001 acted on exactly that
  reading for the `NotFound` case. The daemon port then wired it as `remove_worktree_dir(&target)?`
  — a hard, operation-failing step — which contradicts the plan's own characterisation for every
  errno except `NotFound`. The plan should state what "best-effort" means for a *genuine* leftover:
  the delete still succeeded, and the residue is reported, not fatal.

### tasks.md

- **Affected tasks**:
  - **T053** (`010-daemon-session-persistence/tasks.md:244`) — its main-sync clause requires "the
    kill + archive + record-drop for a `WorktreeDelete` must be **gated on the removal actually
    succeeding** … On a failed delete (locked worktree, branch checked out elsewhere, **permission
    error**) the sessions must be left **untouched** … otherwise the durable archive marker turns an
    FR-023-recoverable failure into permanent session loss." The reasoning is sound but conflates the
    two removal steps. It was written for a delete where **git** refused, which is genuinely
    recoverable by retry once the user clears the obstruction. A permission error on the *directory*
    happens after git has already released the worktree, so the gate misfires: it withholds archiving
    for a worktree that no longer exists, and retrying can never succeed while the foreign-owned
    files remain.
  - **T024** (`008-worktree-sidebar-refinement/tasks.md:117`) — the original delete orchestration,
    superseded by T053 but the source of the `remove_dir_all`-last sequencing.
  - **T018** (`008-worktree-sidebar-refinement/tasks.md:108`) — `tests/worktree_delete.rs` covers
    orchestration via `FakeGit`, which never touches the filesystem. The one filesystem case it does
    exercise (`fr_023_leftover_directory_is_still_reported`) uses a plain file standing in for a
    surviving directory, so it asserts only that *an* error appears — never that the error is
    actionable, and never the partial-success state where git succeeded and the directory did not go.
- **False completions**: none. T053's gating behaves exactly as its text specifies; the text itself
  is what does not distinguish the two failure modes.
- **Missing tasks**:
  1. Make the directory-removal step report **which** entries survived and their owning uid, rather
     than propagating a bare errno.
  2. Treat a surviving directory as **partial success**, not failure: archive the worktree's
     sessions and refresh the catalog (git has already released it), and carry the leftover paths to
     the client as a distinct, non-fatal outcome — alongside `branch_delete_failed`, which is the
     existing precedent for exactly this shape.
  3. Keep a **genuine git failure** (nothing deregistered) a hard failure with sessions untouched,
     preserving T053's original intent.
  4. Regression tests: a directory that cannot be emptied yields named leftovers and still archives
     its sessions; an already-absent directory still yields none (BUG-001 must not regress).

## Root Cause Analysis

This is a spec gap, not implementation drift: the code does what FR-023 and T053 tell it to do, and
what they tell it to do is impossible to satisfy in this state.

FR-023 was written when deletion was a single local orchestration and the working directory was
assumed to be the app's to remove. Two things have since changed and neither was reflected back
into the spec:

- **Ownership is not guaranteed.** Worktrees are working directories for real builds, and a
  containerized build writing through a bind mount as root leaves files the daemon can never unlink.
  This is not an exotic edge case — it is the normal outcome of running Docker-based tooling in a
  worktree, and it will recur on every such worktree.
- **Removal is two steps that can diverge.** `git worktree remove --force` and the directory removal
  fail independently, and the second failing after the first succeeded is a state the spec's
  binary success/failure vocabulary cannot express.

The consequence is that the honest outcome — "the worktree is gone from git; these paths are left
behind and belong to uid 0" — cannot be represented, so the system reports the nearest available
approximation (total failure) and inherits its side effects: stranded sessions and an orphan row
that reads as resurrection.

BUG-001 fixed the mirror-image of this same seam (`NotFound` treated as failure). The seam was
narrowed to one errno rather than reconsidered, which is why the remaining errnos still fall through
it.

## Recommended Fix

1. Run `/speckit.bugfix.patch` to update spec artifacts:
   - Amend **FR-023** to admit a third outcome: removal that releases the worktree from git but
     cannot fully remove its directory is a **partial success**, not a failure — the worktree's
     sessions MUST still be archived and the sidebar MUST still drop the row.
   - Add **FR-023c**: a leftover report MUST name the specific paths that survived and, where the
     platform provides it, their owning uid — enough for the user to resolve it without guessing.
   - Note in `plan.md` what "best-effort" means for a genuine leftover, extending the BUG-001 note.
   - Amend **T053**'s gating clause to distinguish a git-level refusal (hard failure, sessions
     untouched) from a directory-level residue (partial success, sessions archived).
2. Run `/speckit.bugfix.verify` to confirm consistency.
3. Resume `/speckit.implement` to apply the code fix:
   `crates/micold-core/src/worktree.rs:673` (`remove_worktree_dir` reports leftovers),
   `crates/micold-daemon/src/server.rs:865` (partial-success branch),
   `OperationResult::WorktreeDeleted` (carry the leftovers; wire-visible, so bump
   `PROTOCOL_VERSION`), and the client notice.

## Workaround

Until fixed, clear a stuck worktree by hand:

```bash
sudo rm -rf <project>/.claude/worktrees/<dir_name>
git -C <project> worktree prune
```

Avoid recurrence by making the container write as the invoking user
(`--user $(id -u):$(id -g)`) or by moving `GRADLE_USER_HOME` and the build output outside the tree.
