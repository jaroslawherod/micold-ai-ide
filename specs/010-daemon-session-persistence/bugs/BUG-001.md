## Description

The daemon writes a per-session `--settings` file so `claude` posts its lifecycle hooks
(`SessionStart`, `UserPromptSubmit`, `PreToolUse`, `PostToolUse`, `Stop`, `Notification`) to the
daemon's loopback HTTP receiver. Claude Code's settings validator rejects this file for every one
of the six events, e.g.:

```
Settings (<dir>/hooks/<session>.json › hooks.PostToolUse.0.hooks): Expected array, but received undefined
```

Claude Code's real hooks schema requires each event's array entries to be matcher-group wrapper
objects, with the actual hook definition nested one level deeper:

```json
"PostToolUse": [{ "matcher": "", "hooks": [{ "type": "http", "url": "...", "headers": {...} }] }]
```

The daemon instead flattens the hook object directly into the event array, omitting the
`matcher`/`hooks` wrapper entirely:

```json
"PostToolUse": [{ "type": "http", "url": "$URL", "headers": {...} }]
```

Claude Code's loader reads index `0` of the array as a matcher-group object and looks for its
`.hooks` field, which doesn't exist on a bare `{"type": "http", ...}` object — hence "Expected
array, but received undefined" on all six events, every session.

Confirmed against the official Claude Code hooks reference (via the `claude-code-guide` agent,
citing `https://code.claude.com/docs/en/hooks.md`) that `"type": "http"` is itself a real,
currently-supported hook type — POSTing the payload as JSON with custom headers is valid. The
defect is specifically the missing wrapper layer, not the choice of hook type.

## Root Cause Analysis

Both `contracts/hooks.md`'s "Configuration" example and the `settings_json()` implementation that
followed it assumed the per-event array holds hook objects directly. The real schema requires a
`matcher`/`hooks` wrapper around every hook definition — the same shape every other Claude Code
hook type (`command`, `mcp_tool`, `prompt`, `agent`) uses. The contract's own "Verification required
before implementation" table (lines 177–187) tracked one specific uncertainty about the `http` type
(whether `headers` is accepted) and marked it "Unverified," but never flagged the array-shape
assumption as something to verify — that assumption was simply asserted with unwarranted confidence
and carried straight into the implementation and its test, so nothing in the test-first process
(Principle I) exercised the real `claude` binary's validator to catch it.
