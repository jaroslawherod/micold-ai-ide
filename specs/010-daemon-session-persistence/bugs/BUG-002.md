# Bug Report: Daemon is not restarted (or flagged stale) when a new `.deb` is installed over a running instance

**Type**: Spec gap
**Severity**: High
**Feature**: `010-daemon-session-persistence` (branch `feat/micold-daemon`, observed on `fix/daemon-should-be-restarted-automatically-upon-new-deb-install`)
**Reported**: 2026-07-27
**Status**: Resolved
**Patched**: 2026-07-27 — added FR-022a + a 4th User-Story-6 acceptance scenario + an Edge Case +
SC-009a to spec.md; a build-staleness implementation note to plan.md §W6; Phase 12 (T088–T091) to
tasks.md.
**Resolved**: 2026-07-27 — `PACKAGE_VERSION` (`crates/micold-core/src/protocol/version.rs`, backed by
the workspace-shared `CARGO_PKG_VERSION`) is now exchanged in the handshake alongside
`PROTOCOL_VERSION`/`SCHEMA_HASH`. A same-contract package-version difference refuses with a new
`RefusalReason::BuildMismatch`, surfaced by the client as a distinct, lower-severity "Restart
service" banner reusing FR-022's existing restart mechanics. `PROTOCOL_VERSION` bumped 1→2 (the new
`client_package_version` field on `Hello` is itself wire-visible); `docs/daemon.md` explains the new
banner. `cargo test --workspace` (103 groups), `cargo clippy --workspace --all-targets -- -D
warnings`, `cargo fmt --check` all clean. Mid-implementation, the original task text's "compare
`daemon_build()`" was found non-viable as written (see T088's note) — confirmed the wire-field
approach with the user before proceeding rather than silently picking one.

## Description

Installing an upgraded `micold-ai-ide` `.deb` over a system where `micold-daemon` is already
running does not restart, or even flag as stale, the already-running daemon process. `dpkg`
replaces `/usr/bin/micold-daemon` on disk, but the live process keeps executing the *old* binary's
code in memory indefinitely — until the user manually runs `systemctl --user restart
micold-daemon`, logs out, or reboots. Any daemon-side fix or feature shipped in the new package is
silently inert until one of those happens, with no diagnostic telling the user why.

This is not covered by the existing version-mismatch/restart mechanism (User Story 6, FR-021/022):
that mechanism only fires when the **wire protocol** changes (`PROTOCOL_VERSION` /
`SCHEMA_HASH`, `crates/micold-core/src/protocol/version.rs`, checked in
`crates/micold-core/src/protocol/handshake.rs::evaluate`). The common case — a daemon-side bugfix
or feature that doesn't touch the wire schema — bumps neither constant, so `handshake::evaluate`
returns `Ok(())` for the *old* running daemon exactly as it would for the new one, and the new
client happily attaches to the stale process via the `AlreadyRunning` path in
`crates/micold-daemon/src/singleton.rs`. Nothing in the handshake, the client, or the packaging
ever asks "is this the daemon I just installed?" — only "can I still speak to whatever daemon is
running?"

Root-cause confirmation: `crates/micold-daemon/src/server.rs::daemon_build()` already computes
`"micold-daemon {CARGO_PKG_VERSION}"` — the exact per-release identifier needed to detect this —
but it is only interpolated into the *human-readable refusal message* of
`RefusalReason::VersionMismatch` (`crates/micold-core/src/protocol/handshake.rs`); it is never
compared against anything on the accepted path, so it has no effect on whether a stale-but-wire-
compatible daemon is detected.

## Artifact Traceability

### spec.md

- **Affected user story**: User Story 6 — Contract mismatch fails loudly and recoverably. It is the
  closest existing coverage but is scoped to *wire-incompatible* mismatches only.
- **Affected requirements**:
  - **FR-021/FR-022**: mandate refusal + a manual restart action, but only "on version mismatch,"
    where "version" is defined (per `handshake.rs`) as the wire contract, not the installed
    package/binary.
  - **FR-037**: "the service MUST work identically whether launched by [the systemd] manager or
    spawned directly by a client, from a single binary" — silent about what happens when that
    single binary is *replaced* while an instance from the old binary is still live.
  - **Settled Decision 5**: "Portable self-start by default... A freshly built binary must work on
    any checkout with no install step" — again silent on the upgrade-while-running case.
  - **Settled Decision 8**: "Overriding priority: minimize the ways client/service interaction can
    go wrong... Prefer a single source of truth and loud, early failure over cheap paths that can
    drift silently." This bug is precisely the silent drift that decision rules out — it just was
    never checked against the "same-contract, different-binary" case.
- **Gap identified**: no requirement in spec.md treats "the installed `micold-daemon` binary
  differs from the running one" as a condition that must be detected and surfaced. Only wire-schema
  drift is a first-class, tested condition; binary/package drift under a stable wire schema is an
  unhandled case that falls through to indefinite silent staleness.

### plan.md

- **Affected sections**:
  - **W6. Exclusivity, reconnect, packaging, docs, test redistribution** — covers shipping the
    systemd user units "not enabled at install, with the client enabling in-session" (research
    R5.1/R5.6), but that research was scoped to *first-run enablement*, never revisited for
    *restarting an already-enabled instance on upgrade*. The reasons R5.1/R5.6 give for keeping
    postinst out of the loop (root, no user session, no `XDG_RUNTIME_DIR`, package-rejection risk
    of enumerating `/home`) are sound for *enabling* a unit, but restarting an *already-enabled*
    per-user unit the client itself started is a narrower, client-side-reachable operation that
    was never designed for.
  - Technical Context / Summary — "Strict exact-match contract version. No negotiation, no ranges"
    is the mechanism that was (correctly) built, but its scope is narrower than "is this the daemon
    the currently installed package ships."
- **Impact**: W6 needs a task to add a second, independent staleness signal alongside the existing
  wire-contract check — comparing `daemon_build()` (or an equivalent installed-package identifier)
  against what the connecting client expects — and to decide the restart mechanism for when they
  diverge (extend the existing FR-022 client action to also fire on build mismatch, and/or have the
  systemd-managed daemon itself detect it should hand off, e.g. via `Restart=` semantics on a
  self-detected exit).

  - **T076** `[X]` "Ship systemd user units... shipped but NOT enabled at install; the client
    enables in-session." Accurately describes what it built — not a false completion — but its
    scope stopped at first-run enablement and never extended to upgrade-triggered restart.
- **False completions**: none. T076 did what it says; the gap is a missing task, not an incorrect
  one.
- **Missing tasks**:
  1. Extend the handshake (or add a lightweight pre/post-connect check) to compare `daemon_build()`

## Root Cause Analysis

Two independently correct designs compose into a gap. First, FR-021/022's version-mismatch
detection was deliberately scoped to the wire protocol only (Settled Decision 3: "strict exact-match
contract version... no negotiation, no ranges") — a narrower, correctness-motivated check that says
nothing about package/binary freshness. Second, the self-spawn-and-lock design (research R5.4: "if
a live daemon already owns the endpoint, act as a client") was built to make startup race-free and
platform-portable, and correctly treats "a daemon is already listening" as sufficient to proceed.
Neither design was wrong on its own terms, but between them no code path ever asks whether the
already-listening daemon is the one the currently-installed package ships. `daemon_build()` was
built as exactly the right signal for this but was wired only into the refusal message of a branch
that a same-contract upgrade never reaches.
