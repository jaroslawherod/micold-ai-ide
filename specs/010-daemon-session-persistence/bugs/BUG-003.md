# Bug Report: `micold-daemon` never resolves `env_include`, so no daemon-spawned session ever sees variables exported from `~/.bashrc` (or any configured include script)

**Type**: Implementation drift
**Severity**: Critical
**Feature**: `010-daemon-session-persistence` (branch `fix/env-file-is-not-loaded-properly-by-daemon`)
**Reported**: 2026-07-27
**Status**: Resolved
**Patched**: 2026-07-27 — FR-012b added to `spec.md`; `plan.md`'s W2 gained a design-correction note
(daemon settings projection + per-directory cache); `tasks.md` reopened T053's env-include clause
and added Phase 15 (T095–T099).
**Resolved**: 2026-07-27 — All three of the daemon's spawn sites (`start_session`, `respawn_primary`,
`open_shell` in `crates/micold-daemon/src/state.rs`) now call a new `DaemonState::
env_include_vars_for(cwd)`, which resolves `micold_core::env_include::resolve` (merged with
`merge_with_term`) against the session's own directory, cached per directory on `DaemonState`'s
inner state and invalidated on a `WorktreeDelete` or a `SettingsSet` that changes any of the three
env-include fields. `DaemonSettings` and `ClientMsg::SettingsSet` (`crates/micold-core/src/
protocol/messages.rs`) gained the three `env_include_*` fields, mirroring the existing
`scrollback_lines` precedent; `Catalog::set_env_include`/`DaemonState::set_env_include` mirror
`set_scrollback`. A new regression test (`crates/micold-daemon/tests/session_start.rs::
a_daemon_spawned_session_sees_env_include_resolved_variables`) spawns a real disposable script via
a daemon-owned session and confirms the exported variable reaches the spawned process. Verified:
`cargo test --workspace` (103 groups) green; `cargo clippy --workspace --all-targets -- -D
warnings` clean (after boxing `Connected::Ready`'s connection field — the added `String` settings
field tipped that enum over clippy's `large_enum_variant` threshold); `cargo fmt --check` clean.
See `tasks.md`'s Phase 15 for full per-task detail, including a known pre-existing follow-up (the
GUI client doesn't yet send `SettingsSet` to a running daemon for any setting, so a live
settings-while-running edit needs a daemon restart to take effect — out of scope here, since the
default configuration this bug was actually about never goes through that path).

## Description

Every PTY the daemon spawns — a fresh AI-CLI session (`start_session`), a crash respawn
(`respawn_primary`), or a "regular terminal" shell instance (`open_shell`), all in
`crates/micold-daemon/src/state.rs` — builds its child process environment as exactly:

```rust
let env = vec![("TERM".to_string(), "xterm-256color".to_string())];
```

Nothing else. `micold_core::env_include` — the module feature 011 built specifically to source a
configured rc-style script (default `~/.bashrc`) in a real disposable shell and diff its resulting
environment against a clean baseline, so a session's AI-CLI/shell process sees the same variables an
interactive terminal opened in that directory would — is never referenced anywhere in the
`micold-daemon` crate. Confirmed:

```
$ grep -rn "env_include" crates/micold-daemon/src/*.rs
crates/micold-daemon/src/state.rs:601:    /// resolve `env_include` in the session's own directory (main `2862bab`).
```

The only hit is a doc comment, not a call. It reads in full (`state.rs:600-601`):

> **T053 refinement pending**: the environment is a minimal `TERM` today; the full launch must
> resolve `env_include` in the session's own directory (main `2862bab`).

The code's own comment admits the work described by T053 was never done.

This is not merely an unresolved TODO — `env_include`'s own settings never even reach the daemon's
env-building code. `Catalog::settings_wire()` (`crates/micold-daemon/src/catalog.rs:87-91`) projects
the durable `micold_core::settings::Settings` struct to its wire form as:

```rust
pub fn settings_wire(&self) -> DaemonSettings {
    DaemonSettings {
        scrollback_lines: self.settings.scrollback_lines,
    }
}
```

`Settings` carries `env_include_enabled`, `env_include_script_path`, and
`env_include_timeout_secs` (`crates/micold-core/src/settings.rs:94-102`), and `DaemonSettings`
(`crates/micold-core/src/protocol/messages.rs:620-623`) has no fields for any of them — only
`scrollback_lines`. `ClientMsg::SettingsSet` (`crates/micold-daemon/src/server.rs:553-558`) likewise
only ever calls `state.set_scrollback(lines)`. So even setting aside the three `state.rs` spawn
sites, the daemon has no path by which env-include's enabled flag, script path, or timeout could
reach the code that builds a spawned session's environment.

By contrast, the GUI app (`micold-client`) resolves this correctly today: `src/main.rs`'s `boot()` /
`resolve_env_include` / `launch_spec` call `env_include::resolve(path, cwd, timeout)` per
session-launch directory and merge the result via `env_include::merge_with_term` before spawning
(the mechanism BUG-001 and BUG-002 in `specs/011-env-include-script/bugs/` already hardened). The
daemon's independent PTY-spawn path — used whenever the daemon itself creates or resumes a session
(spec 010) rather than the GUI directly spawning one — has no equivalent at all.

## Impact / Symptom

A `claude` session running under the daemon cannot see any variable exported by the user's
`~/.bashrc` (or whatever script `env_include` is configured with), even a plain, unconditional
`export` with no interactive guard and no directory-dependent hook — i.e. even the simplest case
`env_include` is supposed to handle unconditionally. Observed concretely: `GRAFANA_DEV_TOKEN`,
exported in `~/.bashrc` on the host, was absent from a daemon-launched `claude` session's
environment, so the Grafana dev MCP server (configured in `.mcp.json` to read that variable) could
not start. Any MCP server or tool that depends on an env-include-sourced variable — auth tokens,
API keys, version-manager PATH entries, anything a user's shell rc normally provides — silently
fails the same way for every session the daemon spawns.

## Reproduction

1. Add `export SOME_TOKEN=abc123` to `~/.bashrc` (a plain, unconditional export — no interactive
   guard, no version-manager hook).
2. Leave `env_include` at its defaults (enabled, path `~/.bashrc`).
3. Start (or resume) a session so the daemon spawns it — `micold-daemon`'s `start_session` (fresh
   `SessionCreate`), `respawn_primary` (crash restart), or `open_shell` (regular-terminal instance).
4. Inspect the spawned process's environment (e.g. `echo $SOME_TOKEN` inside the session, or an MCP
   server configured to depend on it) — `SOME_TOKEN` is absent, even though the exact same
   `~/.bashrc` line reaches a session spawned by the GUI (`micold-client`) directly.

## Artifact Traceability

### spec.md

- **Affected user stories**: User Story 1 — "Work continues without a window" and User Story 2 —
  "Attach, drive, detach" both implicitly assume a daemon-spawned/respawned session behaves like any
  other session a user would open — nothing in either story's acceptance scenarios calls out
  environment fidelity as a distinct concern, because at the time this spec was written the daemon's
  spawn path was expected to reuse the same env-resolution behavior the GUI already had (per T053's
  own "main-sync" note, added retroactively once feature 011/`2862bab` landed on `main`).
- **Affected requirements**: **FR-008/FR-009** (the service is the single writer of durable state and
  the client must hold only a projection of it — `env_include_*` are exactly this kind of
  service-owned setting per feature 011, yet `DaemonSettings` never projects them). **FR-012a**
  establishes the pattern this should follow: a durable, service-owned setting (there, scrollback)
  that "must apply... at all times, including while no client is attached" and that a client can read
  and request a change for, taking effect "for all sessions." `env_include_enabled` /
  `env_include_script_path` / `env_include_timeout_secs` are the same shape of setting and need the
  identical treatment; none of it exists today.
- **Gap identified**: spec.md never states a requirement that daemon-spawned sessions resolve
  `env_include` at all — this feature's spec was written and largely implemented (Phases 1-8) before
  feature 011 (`env_include`) existed on `main`. The only place the dependency is recorded is a
  "Main-sync" addendum inside task T053 itself, which is a task-list note, not a spec requirement —
  so there is no FR this bug is checked against, only an implementation-level promise that was never
  kept.

### plan.md

- **Affected sections**: none of `plan.md`'s existing sections (W1-W8) name environment resolution as
  part of session spawn — spawn is treated purely as a PTY-open + supervision concern
  (`supervisor.rs`/`PtySession`). The plan was written before feature 011 existed and was never
  amended when T053's scope grew via the "Main-sync" note to include `env_include`.
- **Impact**: `plan.md` needs a decision recording how `env_include` resolution integrates with the
  daemon's architecture — specifically: (a) where the `cwd`-keyed resolution/cache described in
  `specs/011-env-include-script/bugs/BUG-002.md`'s Resolution lives when the daemon (not
  `micold-client`) is the one spawning, since the daemon has no `App` struct to hold a
  `HashMap<PathBuf, EnvIncludeSnapshot>` cache — and (b) how `env_include_enabled` /
  `env_include_script_path` / `env_include_timeout_secs` travel from `Settings` (already loaded by
  `Catalog`) through `DaemonSettings`/`SettingsSet` so a client-initiated settings change actually
  reaches spawn time, mirroring the scrollback precedent.

### tasks.md

- **Affected task**: **T053** [US3] (`tasks.md` line 206), marked `[X]` Done. Its own "Main-sync" text
  says: *"env setup for spawned sessions must resolve the environment in the session's own directory
  (main `2862bab`, `env_include`)"* — this clause of the task was never implemented.
- **False completion**: T053 is checked off in full, but the specific env-include clause added to it
  by the main-sync note is not satisfied by any code in `crates/micold-daemon/`. This is the same
  shape of gap as this feature's own BUG-001 (a task marked `[X]` whose described behavior does not
  actually work end-to-end) and as BUG-001/BUG-002 in `specs/011-env-include-script/bugs/` (a
  spec-sanctioned assumption/task that reads as satisfied but silently fails for the case that
  actually matters — there, the default `~/.bashrc`'s interactive guard and directory-dependent PATH
  hooks; here, the daemon spawn path entirely).
- **Missing tasks**:
  1. Add an `env_include::resolve(script_path, cwd, timeout)` call (with `merge_with_term`) at all
     three spawn sites in `crates/micold-daemon/src/state.rs` — `start_session` (line 633),
     `respawn_primary` (line 820), `open_shell` (line 952) — replacing the hardcoded
     `vec![("TERM", ...)]`, gated on `env_include_enabled` and short-circuiting to just `TERM` when
     disabled or the path is blank (mirroring `micold-client`'s existing caller-side short-circuit
     convention, contracts/env-include-resolution.md's Non-goals).
  2. Extend `DaemonSettings` (`crates/micold-core/src/protocol/messages.rs:620-623`) with
     `env_include_enabled: bool`, `env_include_script_path: String`, `env_include_timeout_secs: u64`,
     and `Catalog::settings_wire()` (`crates/micold-daemon/src/catalog.rs:87-91`) to populate them
     from `self.settings`.
  3. Extend `ClientMsg::SettingsSet` handling (`crates/micold-daemon/src/server.rs:553-558`) so a
     client can change the three env-include settings through the daemon (today only
     `scrollback_lines` is settable), persisting via the same `Catalog`/`SettingsStore` path
     `set_scrollback` already uses.
  4. Decide and implement a per-directory resolution cache (or accept re-resolving per spawn, given
     spawns are already infrequent/bounded events) equivalent to `micold-client`'s
     `env_include_cache: HashMap<PathBuf, EnvIncludeSnapshot>`, invalidated on a `SettingsSet` that
     changes any of the three fields and on `WorktreeDelete` for the deleted path (mirroring the two
     follow-on fixes recorded in `specs/011-env-include-script/bugs/BUG-002.md`'s Resolution).
  5. A regression test analogous to the real-subprocess pattern established by
     `tests/env_include_resolve.rs` (BUG-001/BUG-002 in feature 011): spawn a session through the
     daemon's state/catalog test harness against a script containing a plain unconditional `export`,
     and assert the resulting `PtySession`'s child process actually has that variable set — the
     current suite has no such coverage, which is why this shipped unnoticed.

## Root Cause Analysis

Feature 010 (`daemon-session-persistence`) and feature 011 (`env-include-script`) were developed
concurrently against the same `main` branch, with 010's `tasks.md` retroactively growing a
"Main-sync" note on T053 once `2862bab` landed, to acknowledge that spawn sites now needed to call
`env_include`. That note recorded the *intent* correctly but the corresponding code change was never
made in `crates/micold-daemon/` — only `micold-client`'s `main.rs`/`app.rs` (the pre-existing,
GUI-owned spawn path) picked up feature 011's `resolve`/`merge_with_term` calls, because that is
where `env_include` was originally developed and wired in before the daemon's independent spawn path
(`state.rs`) existed as a second, parallel place sessions get launched from. Once the daemon crate
became a second spawn site, it needed the same wiring `micold-client` has, and no task or review step
ever verified daemon-spawned sessions saw resolved variables (there is no daemon-side test for it) —
so the gap between "T053 says this should work" and "the code that would make it work" went
unnoticed exactly the way BUG-001 (010) and BUG-001/BUG-002 (011) each describe: a task checked off
on the strength of its literal, narrower acceptance criteria, while a downstream integration promise
(here, daemon/GUI env parity) silently never held.
