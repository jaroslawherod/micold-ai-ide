# Bug Report: Sessions that predate a client restart go silently read-only — every keystroke is dropped as `Stale`

**Type**: Untested flow (with a spec gap — the input-continuity contract is stated only for
detach/reattach of a *connection*, never for a new *client process*)
**Severity**: High (silent, total loss of user input on every pre-existing session; violates the
named G2 invariant; triggers on the feature's headline workflow — restarting the UI while the
daemon keeps running. Not Critical only because no durable state is corrupted and a workaround
exists: restart the daemon, which itself kills every live process.)
**Feature**: `010-daemon-session-persistence` (US1/US2, G2, FR-019/FR-028, protocol.md §7) —
observed on branch `fix/session-connects-in-readonly-mode`
**Reported**: 2026-07-27
**Status**: Fixed (SC-020 closed by an automated two-process substitute — see T115)
**Patched**: 2026-07-27 — `spec.md` gained FR-028a, FR-045a, a new Edge Case (a new client process
attaching to a session it did not start) and SC-020; `plan.md` annotated (W4 *Tests first* line, and
Risk 8 — mismatched lifetimes across the boundary, plus a contract test that encodes the mismatch as
its premise); `tasks.md` gained Phase 20 (T110–T115) and **reopened T039 and T044**.
**Implemented**: 2026-07-28 — T110–T114 landed; T039 and T044 re-closed. The daemon now publishes
each live session's expected input serial as `SessionSummary::input_serial`, overlaid from the live
registry in `overlay_live_summaries` (not the catalog, which cannot see the receiver); the client
adopts it absent-only on `DaemonConnected` and each `CatalogChanged`; the stale-input drop is a
`warn!` carrying both serials and no bytes; and `SessionInputStamper::forget` is called on session
close/remove. `PROTOCOL_VERSION` 2 → 3 (`SCHEMA_HASH` follows automatically). Whole workspace green
(120 test groups). **T115 closed 2026-07-28** by `crates/micold-daemon/tests/client_restart_input.rs`
— the real daemon binary as a separate OS process, driven through three client generations each with
a brand-new stamper: generation 2's *first* keystroke must be applied, and generation 3 is
deliberately unseeded to prove the failure mode. Red confirmed by stubbing the seeding to a no-op,
which fails `left: 12, right: 13` — the bug exactly. The GUI keymap path and rendering remain covered
by unit tests only, and this build's own upgrade still needs one daemon restart because the wire
moved — see the task's note.

## Description

After the UI is restarted against a still-running daemon — the exact situation produced by
installing a new `.deb`, or by simply quitting and reopening the app — **every session that existed
before the restart stops accepting input.** The terminal still renders, scrollback still streams,
the session still shows `running`; keystrokes simply have no effect. Sessions *created after* the
restart work normally. The failure is independent of project, shows no banner, no notification, and
no log entry.

Observed sequence (from `journalctl --user -u micold-daemon`, 2026-07-27):

```
19:10:22–19:10:46  WARN refusing client: contract or build mismatch
                        client_build=micold-ai-ide/0.5.0 daemon_package_version="0.4.0"   (25×)
19:10:48           INFO micold-daemon starting build=micold-daemon 0.5.0
19:10:48           INFO presented interrupted-resumable sessions after restart count=32
19:14:51           INFO client attached to daemon            ← client generation 3
   …               (client 3 drives 7c096949, 37813e56, dc2f245f, 1aa71468, 428bc769)
20:40:10           INFO client disconnected client=3
20:42:52           INFO client attached to daemon            ← client generation 9 (current window)
20:43:37           INFO session started c946c166 launch=Fresh ← the only session it created; works
```

Every session in that middle block is read-only in the current window. `c946c166` is not. The
daemon has run continuously since 19:10:48, so this is purely a *client*-generation boundary.

## Root Cause Analysis

Input is specified as a lossless, append-only, ordered log (**G2**, `data-model.md:345`;
`contracts/protocol.md:273`). Both ends carry a per-session serial that starts at `0`:

| Side | Type | Lives in | Survives a **client process** restart? |
|---|---|---|---|
| Client | `SessionInputStamper` → `InputSeq` (`crates/micold-client/src/input.rs:24`) | the client **process** (`App.stamper`, `main.rs:117`, built by `SessionInputStamper::new()` at `main.rs:352`) | ❌ resets to `0` |
| Daemon | `InputReceiver` (`crates/micold-daemon/src/state.rs:99`) | the **`LiveSession`**, created once at `register_session` (`state.rs:768`) | ✅ keeps its high-water mark |

**The two have mismatched lifetimes, and nothing reconciles them.** A client disconnect tears down
no session state — `DaemonState::detach` (`state.rs:414`) never touches `sessions`, deliberately, so
sessions keep running headless (G4/FR-002). `InputReceiver` is therefore only ever reset by the
daemon exiting or the session being closed.

So after a UI restart, for a session with `expected = N`:

1. Fresh client → `SessionInputStamper::new()` → empty `HashMap`.
2. First keystroke into that session is stamped serial **`0`** (`input.rs:37-38`).
3. Daemon: `0.cmp(&N)` is `Ordering::Less` → `InputOutcome::Stale`
   (`crates/micold-core/src/input.rs:98`).
4. `session_input` **returns without writing to the PTY** (`state.rs:1131-1134`).
5. Serials `1, 2, 3 …` are all `< N`, so *every* subsequent keystroke is dropped too.

The session is read-only until the client has burned through `N` input batches into the void, or
until the daemon restarts.

This explains each observation exactly:

- **Newly created sessions work** — `register_session` starts them at `0`, matching the fresh client.
- **Independent of project** — both counters are keyed by `SessionId`, never by project.
- **No banner** — this is not the US5 `Displaced` path (`main.rs:1743`); nothing is displaced.
- **Restarting the daemon fixes it** — it drops every `LiveSession`, so resumed sessions get a fresh
  `InputReceiver::new()` that matches the fresh client.

### Why it is invisible (a second, compounding defect)

The `Stale` arm is the only one of the three that logs below WARN:

| Outcome | Log level | Site |
|---|---|---|
| `Lost { missing }` | `warn!` | `state.rs:1124` |
| unknown session | `warn!` | `state.rs:1117` |
| PTY write failure | `warn!` | `state.rs:1138` |
| **`Stale` (drops the bytes)** | **`debug!`** | **`state.rs:1132`** |

The shipped unit sets `Environment=MICOLD_LOG=info` (`packaging/micold-daemon.service:20`), so the
one branch that silently discards user keystrokes is the one branch filtered out of the log. It is
also therefore absent from the FR-046 recent-errors ring, which captures WARN and above only
(`logging.rs:89`). A user-visible total input loss produces no diagnostic anywhere.

### Why the contract test did not catch it

`crates/micold-core/tests/input_ordering.rs:68`
(`input_survives_a_detach_reattach_boundary_without_loss_or_reordering`) covers a *transport*
reconnect and explicitly assumes the client counter object outlives it:

> ```
> // The reconnect touches only the transport: `seq` is the SAME counter (never re-created via …)
> ```
> — `input_ordering.rs:80`

That assumption is the bug. The test reuses one `InputSeq` across the simulated reattach, so it
models a detach/reattach but never a **client process restart**, which is the case that re-creates
the counter. No test in the suite constructs a second `SessionInputStamper` against a surviving
`InputReceiver`.

Corroborating signal that the stamper's lifecycle was never wired up at all:
`SessionInputStamper::forget` (`input.rs:49`) — documented as the hook for clearing a counter when a
session ends — **has no caller anywhere in the client.**

## Artifact Traceability

### spec.md — `specs/010-daemon-session-persistence/spec.md`

- **Affected user stories**:
  - **User Story 1** — sessions outlive the UI. `spec.md:11` states the premise: *"terminal/agent
    processes keep running when no UI is attached"*. Restarting the UI is thus the **headline**
    scenario, not an edge case, and this bug makes every surviving session unusable after it.
  - **User Story 2** — attach, drive, detach. `spec.md:108`: *"the keystrokes reach the running
    process and the resulting output appears"*. They do not.
- **Affected requirements**:
  - **FR-019** — keyboard input MUST be translated by the client into the byte sequence sent to the
    service. The bytes are sent and then discarded on arrival.
  - **FR-028** — *"On reconnect, the client MUST resynchronize by re-reading current authoritative
    state rather than replaying missed events."* The daemon's per-session input high-water mark
    **is** authoritative state, and the client neither re-reads it nor is offered it — the snapshot
    has no field for it.
  - **FR-045** — the service MUST log operation failures with the diagnostic preserved. Silently
    discarding a session's entire input stream is not logged at the shipped level.
  - **FR-046** — the client MUST surface the service's recent errors. A `debug!` drop never reaches
    the ring, so this failure is unreachable from the UI.
- **Edge case — "Clock/ordering"** (`spec.md:287-288`): *"input typed immediately before a detach
  must not be lost or reordered relative to input typed after reattach."* Scoped to a **detach**.
  The stronger case — a new client *process* attaching to a session it did not start — is never
  stated, and it is the common one.
- **Gap identified**: the spec never says how input-serial continuity is re-established when the
  client's process-local state is lost. G2 (`data-model.md:345`) asserts input is *"never coalesced,
  dropped or reordered — including across a detach/reattach boundary"*, but the mechanism chosen to
  guarantee it depends on client-process-lifetime state that the feature's own architecture
  explicitly does not preserve.

### plan.md — `specs/010-daemon-session-persistence/plan.md`

- **Affected section**: **W4. Client retarget** (`plan.md:335-341`). Its *Tests first* line —
  *"input is never coalesced or reordered across a detach/reattach boundary"* (`plan.md:341`) —
  carries the same detach/reattach framing into the test plan, which is how the untested flow
  reached implementation.
- **Impact**: W4 needs the serial-resync step named as client-retarget work: on `DaemonConnected`,
  seed the stamper from authoritative state rather than starting empty.

### tasks.md — `specs/010-daemon-session-persistence/tasks.md`

- **Affected tasks**:
  - **T039** [P] [US2] — the `input_ordering.rs` contract test (`tasks.md:162`). Its completion note
    claims *"continuity holds across a simulated detach/reattach (same counter, per-session
    receiver)"*. "Same counter" is precisely the untested assumption.
  - **T044** [US2] — the client stamper (`tasks.md:179`). Its note states the stamper lives *"in the
    client's long-lived state, so it is never reset by a detach/reattach"*. "Long-lived" is
    process-lived; against a daemon designed to outlive the process, that is not long enough.
  - **T080** — the diagnostics surface (`tasks.md:321`). Complete as written, but the `Stale` drop
    never reaches the ring it built.
- **False completions**: **T039** and **T044** should be reopened. Neither is wrong in what it
  built; both are incomplete against the case that matters, and T039's green result is what
  certified the gap as covered.
- **Missing tasks**:
  1. Carry each session's expected input serial in the catalog snapshot — add a field to
     `SessionSummary` (`crates/micold-core/src/protocol/messages.rs:527`), fed from
     `InputReceiver::expected()` (`micold-core/src/input.rs:103`).
  2. Seed `SessionInputStamper` from that value in the `Message::DaemonConnected` arm
     (`crates/micold-client/src/main.rs:525`), alongside the existing resync of
     `disconnected`/`displaced`/settings.
  3. Red-first test: a **second** `SessionInputStamper` against a surviving `InputReceiver` applies
     input rather than dropping it — the case `input_ordering.rs:68` does not cover. Extend T039's
     file rather than adding a new one, so the contract stays in one place.
  4. Raise the `Stale` drop from `debug!` to `warn!` (`state.rs:1132`) so silent input loss is
     visible at the shipped `MICOLD_LOG=info` level and reaches the FR-046 ring. Confirm FR-047
     still holds — log the serial and session id, never the bytes.
  5. Either wire `SessionInputStamper::forget` to session end or delete it; an uncalled lifecycle
     hook is what let the lifecycle mismatch go unnoticed.

## Related finding (not part of this bug — **filed as `BUG-007.md`, 2026-07-28**)

While tracing the read-only symptom, the US5 takeover path was ruled out but found defective on its
own terms: `app.displaced` is inserted on `Displaced` (`main.rs:785`) and on a `ProjectBusy` refusal
(`main.rs:797`), but is only ever cleared by a full reconnect (`main.rs:534`) or the explicit "Take
over" button (`main.rs:858`). `DaemonMsg::Attached` is deliberately ignored (`main.rs:799`), so a
project that was once refused stays flagged read-only through any later *successful* non-forced
attach — the window owns the project but suppresses its own input, with the takeover banner still
showing. This affects **US5 / FR-024 / T069** and warrants its own BUG entry.

## Recommended Fix

The contract's intent — proving no input was lost across a reconnect — is worth keeping, so the fix
should *realign* the counters, not remove them. Make the daemon authoritative: publish each
session's expected serial in the snapshot and have a fresh client resume from it, so loss detection
still holds within a client's lifetime while a new client process starts in step.

1. Run `/speckit.bugfix.patch` to update the spec artifacts — state the client-restart continuity
   requirement in `spec.md`, extend the W4 test line in `plan.md`, reopen T039/T044 and add the five
   tasks above to `tasks.md`.
2. Run `/speckit.bugfix.verify` to confirm consistency across `spec.md` / `plan.md` / `tasks.md`.
3. Resume `/speckit.implement` to apply the code fix in
   `crates/micold-core/src/protocol/messages.rs`, `crates/micold-client/src/main.rs`,
   `crates/micold-client/src/input.rs` and `crates/micold-daemon/src/state.rs`.
