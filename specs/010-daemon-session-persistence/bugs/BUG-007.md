# Bug Report: A window that reacquires a project it was once refused stays read-only, with a takeover banner naming a window that may no longer exist

**Type**: Untested flow (with a spec gap — the read-only state has a documented way to *begin* and
only one documented way to *end*, and the client can reacquire a project by a route neither covers)
**Severity**: Medium (user-visible read-only on a project the window legitimately owns, and the
banner misattributes it to a holder that may be gone. Not High because the failure is *visible* — a
banner is shown, unlike BUG-006 — and two ordinary actions recover it: the banner's own "Take over"
button, and any reconnect.)
**Feature**: `010-daemon-session-persistence` (US5, FR-023/FR-024/FR-025, T069) — observed on branch
`fix/session-connects-in-readonly-mode`
**Reported**: 2026-07-28
**Status**: Open

## Description

`App.displaced` is the client's record of which projects this window has lost to another window, and
it is what makes a window read-only (`main.rs:1465-1468` suppresses `Message::TerminalBytes` before
stamping) and what raises the takeover banner (`connection_status`, `main.rs:1786-1790`).

It is written on two events and cleared on two, and the sets do not match:

| Event | Effect on `displaced` | Site |
|---|---|---|
| `DaemonMsg::Displaced` — another window took the project | insert | `main.rs:796` |
| `DaemonMsg::Refused { ProjectBusy }` — this window was refused | insert | `main.rs:808` |
| `Message::DaemonConnected` — a fresh connection | `clear()` (all projects) | `main.rs:534` |
| `Message::ConnectionTakeoverRequested` — the banner's button | remove (active project) | `main.rs:869` |
| **`DaemonMsg::Attached` — an attach this window asked for was accepted** | **nothing** | **`main.rs:811`** |

The last row is the bug. `Attached` falls into the catch-all arm, under a comment that treats it as
uninteresting:

```rust
// Other control messages (Pong, Attached) are consumed as their flows land.
_ => {}
```

`Attached` is not a passive acknowledgement — it is the daemon confirming this client now holds the
project (`messages.rs:335`, sent from `server.rs:337`). It is precisely the event that falsifies
`displaced`, and it is the only one of the three attach outcomes the client ignores.

### Reproduction

1. Window **A** attaches to project **P**.
2. Window **B** starts and targets **P**. The daemon refuses with `ProjectBusy`; B sets
   `displaced[P]` and shows the takeover banner naming A. *(Correct — FR-023.)*
3. The user leaves B's banner alone and switches B to a different project **Q**.
4. Window **A** closes, or switches away from **P**. The project is now free (FR-025).
5. The user switches B back to **P**. `switch_daemon_attachment` (`main.rs:1912`) sends
   `Attach { project: P, force: false }`. The daemon **accepts** and replies `Attached { P, .. }`.
6. B now holds P — the daemon streams its frames and would route its input — but `displaced[P]` was
   never cleared, so `active_project_displaced` is still true. **B renders P and refuses to type
   into it**, above a banner that says another window holds it, naming A's build string. A may no
   longer be running.

The same sequence works with the roles from a real takeover: A takes P from B (`Displaced`), A later
releases it, B switches back to P and is accepted — same stale flag, same outcome.

### What recovers it

- **The banner's "Take over" button** (`main.rs:863-875`) removes the entry and re-attaches with
  `force: true`. It works, which is why this is Medium and not High — though it is a forced
  displacement of nobody, and the user is being asked to seize a project they already own.
- **Any reconnect.** `DaemonConnected` clears the whole map, so a daemon restart, or the keepalive
  loop's auto-reconnect after a transient drop (`daemon.rs`, T068), silently fixes it.

Neither is discoverable as *the* fix, because neither is what the window actually needs — it needs
to notice it already succeeded.

## Root Cause Analysis

The client models "am I displaced?" as **state it maintains from events**, rather than as a fact it
re-reads from the authoritative side. Attachment ownership is the daemon's to know: the daemon
tracks the holder per project (`exclusivity.rs` proves it does), and it tells the client the answer
on every attach — `Attached` or `Refused`. The client stores a shadow copy and updates it from the
negative replies only.

That is the same shape of defect as BUG-006, in a different pair of values: **state split across the
client/daemon boundary, where the client's copy is only ever corrected in one direction.** BUG-006's
input counter was never re-read on connect; here the ownership flag is never cleared on success.
plan.md's Risk 8 already names the general remedy — *"for any pair of values that must agree across
the boundary, name which side is authoritative and re-read it on connect"* — and this instance
extends it: re-read it on every **reply that carries it**, not only at connect time.

### Why the tests did not catch it

`crates/micold-daemon/tests/exclusivity.rs` covers US5 thoroughly on the **daemon** side —
`a_second_attach_is_refused_then_force_displaces_the_holder`, `a_displaced_client_is_not_terminated`,
`a_crashed_holder_frees_the_project_without_a_restart`, `two_clients_on_two_projects_do_not_interfere`.
All four assert the wire messages the daemon sends. None asserts what the *client* does with them,
because the client's `displaced` map is not visible from there.

On the client side the only coverage is
`connection_status_orders_mismatch_over_displaced_over_disconnected` (`main.rs:2952`), which pins the
*precedence* of the five connection states given a populated map. It never exercises the map's
lifecycle. No test anywhere drives `Refused{ProjectBusy}` → `Attached` through `update_inner` and
asserts the window can type again.

The daemon tests prove the daemon frees the project. Nothing proves the client notices.

## Artifact Traceability

### spec.md — `specs/010-daemon-session-persistence/spec.md`

- **Affected user story**: **User Story 5** (`spec.md:176`) — "One viewer per project, with
  deliberate takeover".
  - **Acceptance Scenario 3** (`spec.md:196-197`) is the closest the spec comes: *"Given a window was
    displaced, When the user triggers its reconnect action and no other window holds the project,
    Then it reattaches and shows current state."* That scenario passes — it is the takeover-button
    path. The failing case is reacquiring the project by an ordinary **project switch**, which the
    scenario does not describe and which no requirement covers.
- **Affected requirements**:
  - **FR-023** (`spec.md:429`) — at most one client per project; a second attach is refused. The
    refusal is correct; what the refusal *leaves behind* in the client is not scoped.
  - **FR-024** (`spec.md:431`) — the displaced client MUST stop rendering and stop sending input.
    Correctly implemented, and this bug is its over-application: the window keeps obeying FR-024
    after it has stopped being displaced.
  - **FR-025** (`spec.md:434`) — a project held by a client that disconnects MUST become attachable.
    The daemon honours this; the *reattaching* client then fails to use what it was granted, so the
    user-visible effect of FR-025 is lost on the one window most likely to be waiting for it.
- **Gap identified**: the spec says when a window **becomes** read-only and describes one way it
  stops (the reconnect action). It never states the invariant that actually matters — **a window's
  read-only state must reflect current attachment ownership, and ownership is the service's to
  report.** Written as a rule about ownership rather than about takeover events, the bug is
  unreachable: any accepted attach clears it by definition.

### plan.md — `specs/010-daemon-session-persistence/plan.md`

- **Affected section**: **W4. Client retarget** (`plan.md:335-341`) — "Disconnected-state and
  takeover affordances as shared builder-API primitives" is where the banner and its state live.
- **Affected section**: the exclusivity workstream (`plan.md:364`) and its *Tests first* line
  (`plan.md:394-396`): *"a second attach is refused with an actionable error; after takeover the
  displaced client sends zero further input and does not exit."* Both clauses are about entering and
  holding the displaced state. Neither asks what leaves it, so the test plan has no place for the
  case.
- **Impact**: Risk 8 (added for BUG-006) should be extended, or a sibling added — the same
  boundary-state failure recurring in a second pair of values is evidence the mitigation needs to
  cover *every* reply that carries authoritative state, not connect-time resync alone.

### tasks.md — `specs/010-daemon-session-persistence/tasks.md`

- **Affected tasks**:
  - **T069** [US5] (`tasks.md:297`) — builds `ConnectionBanner`, the `ConnectionStatus` computation,
    and the read-only suppression. Its completion note is accurate for everything it claims: the
    banner exists, the takeover action is wired, and `TerminalBytes` is suppressed before stamping so
    no serial is consumed. What it does not claim, and did not build, is the exit condition.
  - **T068** [US5] (`tasks.md:295`) — the keepalive/auto-reconnect loop. Not at fault, but it is why
    the bug is intermittent in practice: an auto-reconnect clears the map, so the stale flag can
    vanish on its own between one observation and the next.
- **False completions**: **none**. T069 should not be reopened — its stated scope was the banner
  primitive, the status computation and the input suppression, and it delivered all three. Nothing
  in Phase 8 owned the `displaced` map's full lifecycle, which is exactly how the gap survived.
  *(Same disposition as BUG-005's T048.)*
- **Missing tasks**:
  1. Clear the project's `displaced` entry on `DaemonMsg::Attached` (`main.rs:811`) — replace the
     catch-all's treatment of it with a real arm. Note that `Attached` also carries `sessions`, which
     the client currently discards; decide whether that is a second omission or intentional given
     `CatalogChanged`.
  2. Red-first test through `update_inner`: `Refused{ProjectBusy}` for a project, then `Attached` for
     the same project, then assert `active_project_displaced` is false and `connection_status` is
     `Connected` — and assert the pre-fix sequence reproduces the bug, so the regression is pinned
     from both sides (as T112 does for BUG-006).
  3. Decide the fate of the stale holder identity: when a window shows the takeover banner, the
     `by` string is the holder as of the refusal and is never refreshed. Either re-derive it or
     state that it is a point-in-time label.
  4. Consider whether `Detach` should also drop the entry — a window that deliberately leaves a
     project has no live claim to be displaced from it — or whether leaving it is harmless given (1).

## Related

- **BUG-006** (`bugs/BUG-006.md`) — the same class of defect (client-side shadow of daemon-owned
  state, corrected in one direction only) in the input-ordering counters. This bug was found while
  tracing that one: "read-only" matched the takeover banner's wording verbatim, so the `displaced`
  path was investigated first and ruled out as the cause of BUG-006 — but found defective on its own
  terms. Recorded there under "Related finding" and filed here as agreed.

## Recommended Fix

Make the client's read-only state a function of what the daemon last told it about ownership, rather
than a flag accumulated from refusals. The daemon already sends the deciding fact on every attach;
the client need only stop ignoring the positive case.

1. Run `/speckit-bugfix-patch` to update the spec artifacts — state the ownership invariant in
   `spec.md` (a US5 acceptance scenario for reacquiring a released project by an ordinary switch, and
   a requirement that read-only status track current attachment), extend the exclusivity *Tests
   first* line in `plan.md`, and add the tasks above to `tasks.md`. No task needs reopening.
2. Run `/speckit-bugfix-verify` to confirm consistency across `spec.md` / `plan.md` / `tasks.md`.
3. Run `/speckit-implement` to apply the code fix in `crates/micold-client/src/main.rs`.
