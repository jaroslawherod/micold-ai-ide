# Bug Report: Success criteria written as human walkthroughs have no executable path, so they sit unverified indefinitely — and a green CI column can stand in for coverage that does not exist

**Type**: Spec gap (acceptance criteria specified without a way to run them; the plan's *Tests first*
discipline stops at the GUI boundary and nothing owns what happens past it)
**Severity**: Medium (no user-facing defect — this is about what the project can *prove*. It earns
Medium rather than Low because it has already hidden one real bug for the life of a feature, and
because the resulting record overstates coverage: three tasks read "blocked by the environment" when
one of them was blocked by an unwritten function.)
**Feature**: `010-daemon-session-persistence` (T083, T084, T085, T104, T109, T115; SC-013, SC-019,
SC-020) — observed on branch `chore/verification-gap`
**Reported**: 2026-07-28
**Status**: **Fixed** (2026-08-27) — the rule is written, the dispositions exist, and a check enforces them; one clause deferred as T144 with its unblocking condition named. Was: Open — and 2026-08-19 produced a concrete instance of its cost: [BUG-013](./BUG-013.md), a session unreachable after a client restart, sitting inside T084's unrun quickstart walkthrough. Found with the `visual-pass` skill, which is the executable path this report says did not exist

## Description

This feature has six verification tasks whose stated method is a person operating the GUI. As of
today, after every implementation task is closed:

| Task | Verifies | State |
|---|---|---|
| T083 | Cross-platform CI gate + three Windows behaviours | Gate ✅ 2026-07-28; **Windows behaviours never exercised** |
| T084 | quickstart.md scenarios S1–S15 | Open since the feature landed |
| T085 | Retargeted `TerminalPane` repaint cost at 60 Hz (Risk 2) | Open since the feature landed |
| T104 | BUG-004's badge glyph, by eye | Open |
| T109 | SC-019 — one leading indicator, no row shift | **Closed 2026-07-28** as redundant against T108 |
| T115 | SC-020 — a pre-existing session accepts input after a UI restart | **Closed 2026-07-28** by an automated substitute |

Five of six are still open, and the one that closed did so by being *rewritten* as a two-process
integration test (`crates/micold-daemon/tests/client_restart_input.rs`), not by anyone performing the
walkthrough. That is the tell: the criteria were satisfiable all along, but only after someone found
an observable that a machine could read. Nothing in the spec or plan asked for that observable up
front, so each task was written as "look at it" and then could not be run.

The environment makes it concrete — no input-injection tool exists (`xdotool`, `ydotool`, `wtype`,
`dotool`, `xte` all absent under Wayland), GNOME Shell's `Eval` is disabled, and a freshly started
client opens with worktrees collapsed so no session row is even on screen without a click — but the
environment is not the root cause. A criterion whose only verification is a human eye is unverifiable
by *any* automated agent, in any environment, and will be skipped for as long as no human is
available. Which, judging by the table, is indefinitely.

## Root Cause Analysis

The plan's central discipline is *Tests first* — every workstream W1–W6 names the tests that must
fail before the code is written. That discipline covers everything up to the rendering boundary and
stops there. Past it, the artifacts switch, without saying so, from "assert this" to "confirm this
looks right", and no task owns closing the gap between the two.

That is defensible for genuinely visual properties (does this glyph read as a filled dot?). It is not
defensible for the ones that were written that way *by default*:

- **SC-020** ("100% of pre-existing sessions accept keyboard input on the very first keystroke") is a
  statement about the input-ordering contract, not about pixels. It became testable the moment
  someone noticed the daemon publishes an observable — `input_serial` advances only for input it
  applied — and reframed the criterion around it. Nothing about that required a GUI.
- **SC-019** ("exactly one leading indicator … 0 horizontal shift") is geometry, and T108 already
  asserts both halves at the widget level. T109 is a *duplicate* of a check that is already
  automated; its residue is genuinely only "look at it once".
- **T085** (repaint cost at 60 Hz) is a measurement, and measurements have units. It was written as
  an observation rather than a threshold, so there is nothing to assert even in principle.

The common failure: **the criterion was specified in terms of the observer rather than the
observable.** Written the other way round — name the value, its source, and its bound — most of these
have an executable form, as T115 demonstrated after the fact.

### The compounding effect: a green column that means less than it looks like

T083 makes the second half of this worse. Its note read *"Blocked in this environment (no
macOS/Windows runners)"* for the life of the feature. That was never true of CI —
`.github/workflows/ci.yml` has run a `[ubuntu, macos, windows]` matrix on every pull request all
along. When the matrix was finally observed green (PR #43, run 30335853202), the obvious conclusion
was that T083 was satisfied.

It was not. T083 also requires exercising Windows job-object teardown, the `0x03` interrupt path, and
the inverted `portable-pty` `kill()` result. `crates/micold-daemon/src/platform/windows.rs` is **8
lines**, and its `terminate_process_tree(_pid: u32) {}` is an empty no-op. There is nothing to
exercise. A green Windows column means "the suite compiles and passes on Windows" — real value, and
not the claim the task makes.

So the record contained a blocked-by-environment note masking a not-yet-implemented function, and the
first honest look at CI nearly converted that into a false completion. This is the same shape as
BUG-006's T039 and BUG-007's T069: **a task whose completion note describes what was built, while the
thing it was supposed to prove goes unexamined.**

## Artifact Traceability

### spec.md

- **Affected success criteria**: **SC-013** (T085's repaint cost), **SC-019** (T109), **SC-020**
  (T115). SC-020 is now closed and is the worked example; SC-019 is duplicated by T108; SC-013 has no
  threshold to assert.
- **Gap identified**: the spec states success criteria without stating, for any of them, **what is
  observed and by what**. Criteria that happen to name a number (SC-011's "≤ 10 s", SC-012's attempt
  counts) got automated tests without anyone having to think about it. Criteria phrased as
  experiences did not. Nothing in the document distinguishes "must be seen by a person" from "was
  merely written that way", so no one can tell which of the six tasks above is genuinely blocked.

### plan.md

- **Affected section**: every workstream's *Tests first* line, and **Risk 2** (streaming/repaint cost
  measured daemon-side only, which is what T085 exists to close).
- **Impact**: the plan needs to say what happens at the rendering boundary — that a criterion which
  cannot be asserted must either name its observable, or be explicitly marked
  human-only-and-why. Risk 8 was widened twice already for the client/daemon boundary; this is the
  same species of gap at the client/screen boundary.

### tasks.md

- **Affected tasks**: T083, T084, T085, T104, T109 (and T115, now closed).
- **False completions**: **none — and that is worth stating.** Every one of these tasks was left
  honestly unchecked with its blocker recorded, which is why this report can be written at all. The
  defect is in the *specification* of the checks, not in anyone's bookkeeping. T083's note was
  inaccurate about its cause, not about its status.
- **Missing tasks**:
  1. For each open verification task, decide and record one of: (a) an observable that makes it
     assertable — the T115 treatment; (b) genuinely human-only, with the reason; (c) redundant
     against an existing automated check, and closed as such. **T109 was (c)** against T108 and was
     closed on that basis on 2026-07-28 — the first disposition applied, and the cheapest kind: the
     coverage already existed and only the bookkeeping was missing. Remaining to triage: T084, T085,
     T104, and T083's Windows-behaviour clause.
  2. Give **SC-013** a threshold so T085 has something to fail against, or retire it.
  3. Split T083's Windows-behaviour clause into its own task, blocked on implementing
     `platform/windows.rs::terminate_process_tree` — it is not a CI problem.
  4. Add a rule that a task recorded as blocked must name *what* would unblock it, precisely enough
     that the claim can be checked. "No macOS/Windows runners" survived a whole feature without
     anyone noticing CI had them.

## Related

## Recommended Fix

Do not attempt to make every criterion automatable — some genuinely need eyes. The fix is to make the
project able to *tell the difference*, and to stop unverifiable-by-construction criteria from being
written by accident.

1. Run `/speckit-bugfix-patch` to update the artifacts — have `spec.md` state the observable for each
   success criterion (or mark it human-only with a reason), extend `plan.md` past the rendering
   boundary, and add the tasks above to `tasks.md`, including closing T109 as redundant against T108.
2. Run `/speckit-bugfix-verify` to confirm consistency.
3. Run `/speckit-implement` for the parts that turn into code — SC-013's threshold, and the Windows
   platform work if it is taken on now rather than deferred again.

## Resolution (2026-08-27)

### What was actually wrong

Not the bookkeeping — the report says so itself, and it was right. Every one of the six tasks was
left honestly unchecked with its blocker written down. The defect is that the project had no way to
tell a criterion that *must* be seen by a person from one that was merely *written* that way, so all
six looked equally blocked and all six were treated as equally someone else's problem.

The fix is therefore a rule, a set of dispositions, and something that fails the build when a new
criterion arrives without one. Not an attempt to automate the three that genuinely cannot be.

### The table in the report is stale, and its cost is worth reading

| Task | Report said | Now |
|---|---|---|
| T083 | gate ✅, Windows behaviours never exercised | unchanged — and now **split**: the clause is T144, open, with its unblocking condition named |
| T084 | open since the feature landed | `[X]` — walked 2026-08-25 on Xvfb with `xdotool`, thirteen of fifteen scenarios passing |
| T085 | open since the feature landed | `[X]` — measured 2026-08-25: 0.31 ms mean / 0.40 ms p95 idle, 0.42 / 0.58 under flood, against 16.7 ms |
| T104 | open | `[X]` |
| T109 | closed as redundant against T108 | unchanged |
| T115 | closed by an automated substitute | unchanged |

Five of the six moved, and T084's walkthrough is where **BUG-015, BUG-018, BUG-019, BUG-020,
BUG-021/022 and BUG-023** came from — six defects that had sat behind a green suite for the life of
the feature. That is this report's thesis paid out in full: the criteria were not decorative, and
nobody had run them.

The route that unblocked them was the `visual-pass` skill, which drives the real binary on Xvfb with
lavapipe. It did not exist when this was filed, and it is why "needs a GUI" is no longer an
acceptable reason to mark a criterion human-only.

### The rules

Both live in `plan.md` Principle I, which had stopped at the rendering boundary. That is the honest
place for them: Principle I is the one that says *test-first, non-negotiable*, and the gap was that
it silently exempted everything past the last widget.

1. **A success criterion MUST name its observable, or be marked `human-only` with the reason it
   cannot have one.** A criterion phrased in terms of the observer has no failing test to write
   first, so it is not merely untested — it is outside the principle, and nothing notices.
2. **A task recorded as blocked MUST name what would unblock it, precisely enough that the claim can
   be checked.** The evidence is T083: "no macOS/Windows runners" survived an entire feature while CI
   had had all three platforms for months, because the claim named no condition anyone could go and
   test. T144 now carries its own: `wc -l crates/micold-daemon/src/platform/windows.rs`, and read the
   body of `terminate_process_tree`.

### The dispositions

`spec.md` gains **`### How each criterion is observed`**, one row per criterion — the observable, and
the file asserting it. All 28 (SC-001–SC-025 plus SC-004a, SC-009a, SC-011a).

Rows name **files, not test functions**. Requirement ids here are feature-scoped: `SC-001` names a
different criterion in six other features, so a reader following a bare id with `grep` lands
somewhere else entirely. The file is the smallest handle that is unambiguous.

Three rows come out `human-only`, and each says why:

| Criterion | Why no instrument here can read it |
|---|---|
| SC-003 | the 3 s cold-start budget is wall-clock on the user's hardware; this machine's only headless display is a software rasteriser |
| SC-004a | the repaint budget is measured on a display, not gated — a wall-clock assertion on a shared CI runner is a flake generator |
| SC-015 | the 5 s is a person's reading speed. The half that is not human-only — the information reaching the row at all — is asserted |

**Three** is the number the project can now state, where before it could state nothing. That is the
whole deliverable: not that the count is low, but that it exists and each entry is defended.

### SC-004a, and a mis-citation the report made

The repaint criterion had no threshold, so T085 had nothing to fail against. It has one now:
**2 ms mean / 4 ms p95 over at least 400 counted frames** — a quarter of a 60 Hz frame, leaving the
rest to everything else on screen. T085 measured 0.31 / 0.40 idle and 0.42 / 0.58 under flood, so the
bound is roughly five times the measured cost: loose enough not to fire on a slower machine, tight
enough that a real regression trips it.

The report names this criterion **SC-013** three times. SC-013 is the test-migration criterion ("the
existing headless suite passes, with every migrated test recorded and justified"); the latency
criterion is **SC-004**. Recorded rather than quietly corrected, because a reader following the
report's citation would otherwise conclude a criterion had been renumbered.

### The gate

| Gate | Where | Holds |
|---|---|---|
| `check-criteria-observables.sh` | `scripts/` | in a spec carrying the table: every criterion has a row, every row names a real criterion, no duplicates, and a `human-only` marker is not the end of its own sentence |
| its own cases | `scripts/tests/check-criteria-observables.test.sh` | 13 cases, run in CI **before** the gate |

**Opt-in per spec, deliberately.** A spec with no table is not failed. Thirty-six features predate
this rule; failing them all today means either thirty-six tables written in one sitting by someone
who did not write the criteria, or — far more likely — the check being deleted. The table's presence
is the opt-in, and adoption is how the rule spreads.

The cases run first because that ordering has already been paid for once: the assertion-freeze gate
beside it shipped with cases that "existed and nothing ran them", which is this bug one level down.

One case deliberately expects a **pass**: a row reading "human-only, because it needs a graphical user
interface". That is a bad reason and the check accepts it. A grep cannot judge a justification, and
pretending otherwise would be the same mistake in a new costume — the rule is in `plan.md` and the
reviewer enforces it. Recorded as a case so the next reader knows it is a boundary and not an
oversight.

### Probes

Each mutation applied to `HEAD`, the named target run on its own, then `git checkout -q --`.

| Probe | Mutation | Result |
|---|---|---|
| A | the missing-row rule is not reported | 3 cases **failed** — including the section-boundary one |
| B | a row naming an undefined criterion is not reported | `a row for a criterion this spec lacks fails` **failed** |
| C | duplicate rows are allowed | `two rows for one criterion fails` **failed** |
| D | `human-only` needs no reason after it | `human-only with no reason fails` **failed** |
| E | rows are read from the whole file, not the table's section | `a row outside the section does not count` **failed** |
| F | the opt-in is dropped — every spec is checked | `a spec with no table is not failed` **failed** (exit 1 where 0 was wanted) |
| G | the vacuous-pass guard is dropped | `a table with no criteria at all is an error` **failed** |
| H | a new `SC-026` added to the real spec, no row | the real check **failed**, naming SC-026 |
| I | SC-004a's row deleted from the real spec | the real check **failed**, naming SC-004a |

Probes A and E both break `a row outside the section does not count`, which is worth saying rather
than hiding: that case is held by two rules at once, and neither probe isolates it. H and I are the
ones that matter most — they are the gate firing on the actual document, in the exact shape the next
omission will take (a criterion appended to the list, table untouched).

### What is not done

**T144.** The three Windows behaviours T083 names are still unexercised, and now say so in their own
open task rather than inside a ticked box. They are blocked on
`platform/windows.rs::terminate_process_tree` — 8 lines, empty body — and a Windows test written
today would assert against a no-op and pass, which is the failure this report is about. Not blocked
on runners; `.github/workflows/ci.yml` has run `windows-latest` since PR #43.

**The other thirty-six specs.** None has a table. The check passes them by design, and every one of
them may contain a criterion phrased in terms of its observer. This fixes 010 and makes the next
omission loud; it does not audit the past.
