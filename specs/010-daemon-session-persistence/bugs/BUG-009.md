# Bug Report: A worktree create with submodules goes silent on its own connection, so the liveness deadline reaps a healthy daemon — and the reconnect is then refused by the still-parked client that was creating it

**Type**: Implementation drift (a step designed to be slow was moved onto a connection whose contract
reads silence as death; nothing in either feature's artifacts owns the seam)
**Severity**: High (every worktree created from a submodule repository whose fetch exceeds 9 s ends in
a disconnect banner, an unknown outcome, and a window locked read-only against itself; the create's
real result — including *which* submodule failed, FR-006 — is written to a socket nobody is reading)
**Feature**: `010-daemon-session-persistence` (FR-026, SC-011, FR-031/035, FR-024/024a; the
`WorktreeCreate` arm added by T053) — triggered by `010-submodule-worktree-support` (FR-004, FR-006,
SC-002, SC-003). Observed on branch `fix/create-worktree-fails-with-error`, client build
`micold-ai-ide/0.6.0`
**Reported**: 2026-08-06
**Status**: Fixed (2026-08-06) — Phase 22 (T120–T124) for the worktree arms, Phase 23 (T125) for the
session-start arm the audit found. No arm that can outlast the liveness deadline still runs on a
connection loop; `contracts/protocol.md` carries the per-arm table and the rule.
**Patched**: 2026-08-06 — FR-025a, FR-026a, FR-035a, SC-011a and a new Edge Case added to
`010-daemon-session-persistence/spec.md`; W6 annotated and Risk 9 added in its `plan.md`; Phase 22
(T120–T124) added to its `tasks.md`. `010-submodule-worktree-support` gained FR-004a and an
annotation on its synchronous-create assumption; `013-create-worktree-refinement` gained FR-008a.
No task reopened in any of the three.

## Description

Creating a worktree in a repository that uses git submodules fails from the user's point of view. The
form reaches **"Setting up submodules"**, the progress bar stops advancing, and after roughly ten
seconds two error banners appear while the fetch is still running:

> The session service disconnected before confirming the request to create the worktree
> "fix-olx-form-is-visible-even-when-module-is-disabled" — it may or may not have taken effect;
> reconnecting will show the current state.

> Another window took over this project — micold-ai-ide/0.6.0 is now attached — this window is
> read-only until you take it back.

There is no other window. `micold-ai-ide/0.6.0` is this window's own build string, reported back to it
as the holder that displaced it.

## Root Cause Analysis

Four mechanisms compose. Each is individually reasonable; together they guarantee the failure for any
submodule fetch longer than `LIVENESS_DEADLINE`.

**1. The create parks the connection's message loop.** `route()`
(`crates/micold-daemon/src/server.rs:317`) is one sequential `while let Some(frame) =
incoming.next().await` per connection, and it is the *only* place `ClientMsg::Ping` is answered
(`server.rs:325`). The `WorktreeCreate` arm moves the git work off the runtime with
`spawn_blocking` — and then `.await`s the join handle inline (`server.rs:658-697`). `spawn_blocking`
frees the *runtime*; it does not free the *connection loop*. For the entire duration of `git submodule
update --init --recursive`, this client's frames are not read and its `Ping`s are not answered. The
comment at `server.rs:645` — "git worktree add can take minutes (a submodule fetch), so it runs off
the async runtime" — names the exact hazard and addresses only half of it.

**2. The one signal that could have covered for that is filtered out.** `on_progress` deduplicates by
stage: "A stage emits several lines; only transitions are worth a frame" (`server.rs:666-679`).
`create_worktree` tags every live line of submodule-fetch output with the same
`CreateStage::SettingUpSubmodules` (`crates/micold-core/src/worktree.rs:881-890`), so the stage emits
exactly **one** frame — at the start — and then nothing until the fetch ends. The connection carries
no traffic at all.

**3. Silence is the liveness signal.** The client's deadline is reset by *any* inbound frame, and
lapses after `LIVENESS_DEADLINE = 9 s` (`crates/micold-core/src/protocol/keepalive.rs:22`). At ~10 s
`Keepalive::poll` returns `Expired` and the pump returns `PumpEnd::Disconnected`
(`crates/micold-client/src/daemon.rs:267`). This is FR-026 working exactly as specified — against a
daemon that is alive, working, and holding the reply.

**4. The reconnect is refused by the corpse of the old connection.** `DaemonDisconnected` drains
`pending_ops` into the "may or may not have taken effect" notice (`main.rs:1082-1088`). The
subscription reconnects and re-attaches with `force: false` (`main.rs:759`). But the old connection is
still registered: its socket has EOF'd, and `route()` will not observe that until the create it is
parked on returns, so `state.deregister(id)` (`server.rs:295`) has not run and the project's
`Attachment` still names the dead client (`state.rs:378-391`). The attach is therefore refused as
`ProjectBusy` with `holder` = the old client's build string, and the client turns that refusal into
the takeover banner (`main.rs:1023`). Hence a window displaced by itself, read-only for the remainder
of the fetch.

The consequences past the two banners:

- The create's actual outcome — `OperationOk`, or `OperationError` carrying *which* submodule failed
  and why — is sent to a socket with no reader. The user never sees it. The rollback still happens
  daemon-side, so a failed create silently vanishes rather than reporting a reason.
- Any create whose slowest stage exceeds 9 s of silence hits this, not only submodule ones — a large
  `git worktree add` checkout is the same shape.

Why no artifact caught it: submodule fetching (`010-submodule-worktree-support`, 2026-07-18) was
specified and built as an **in-process** step, where "slow" only meant the create form spun — its
tasks target `src/app.rs`/`src/main.rs` directly, and its assumption "submodule fetching runs as a
synchronous part of the create flow" was true and harmless in that architecture. Worktree creation
then moved behind the daemon (T053), onto a transport whose liveness contract is *measured in
silence*. Neither feature's artifacts state the resulting obligation: **a connection must keep serving
its own protocol while an operation it initiated is in flight.**

## Artifact Traceability

### spec.md — `010-daemon-session-persistence`

- **Affected requirements**: **FR-026** / **SC-011** (a half-open link is surfaced within 10 s) — the
  detector is correct and its premise is wrong: daemon silence no longer implies a dead link.
  **FR-031** (every mutating operation resolves to exactly one of success / failure / explicitly
  unknown) — the create resolves as *unknown* while the daemon is alive and knows the answer, which
  is the escape hatch being used as the normal path. **FR-035** (unknown outcomes reconciled from
  authoritative state on reconnect) — the reconnect is refused, so no reconciliation happens.
  **FR-024** / **FR-024a** (read-only tracks *current* attachment ownership) — ownership is stale by
  construction here: the holder is a connection that is gone but not yet deregistered.
- **Gap identified**: nothing states that a client connection must remain responsive to protocol
  traffic (at minimum `Ping`) while a long operation it requested is running, nor that an
  attachment must be released when its owner's socket closes rather than when its parked loop
  notices.

### spec.md — `010-submodule-worktree-support`

- **Affected user stories**: **US2** (know that fetching is happening) — the indication survives ~9 s
  and is then replaced by a disconnect banner, which is precisely the "is it hung?" state the story
  exists to prevent. **US3** (understand and recover from a fetch failure) — the failure detail never
  reaches the client.
- **Affected requirements / criteria**: **FR-004**, **SC-002** (in-progress indication);
  **FR-006**, **SC-003** ("the user can identify which submodule failed and why … in 100% of failure
  cases" — currently 0% once the fetch passes 9 s); **FR-005** (rollback still runs, but its outcome
  is unobservable).
- **Gap identified**: the spec's assumption that submodule fetch "runs as a synchronous part of the
  create flow" was written for an in-process create and never revisited when the create became a
  daemon round-trip.

### plan.md

- **`010-daemon-session-persistence`**: the workstream owning the connection loop and the keepalive.
  Both were designed against sessions and grid streaming, where the daemon is never quiet for long.
  Long, silent, client-initiated operations are an unmodelled traffic shape.
- **`013-create-worktree-refinement`**: the stage-progress design (FR-006/FR-007). The
  one-frame-per-stage-transition contract is what makes the quiet window total; whatever fix is
  chosen, this is where "the wire also carries liveness" has to be written down.

### tasks.md

- **Affected tasks**: `010-daemon-session-persistence` **T053** (worktree management through the
  daemon) — the arm where the inline `.await` lives.
  `010-submodule-worktree-support` **T005** (the create step), **T012** (the in-progress UI),
  **T014**/**T017**/**T020** (manual quickstart validation).
- **False completions**: none in the bookkeeping sense — T005/T012 are correct for the in-process
  architecture they were written against, and T014/T017/T020 were validated there. They are stale,
  not wrong. Worth noting that three manual validations passed and none of them would catch this,
  because the local test repo's submodule fetch finished inside the deadline.
- **Missing tasks**:
  1. Stop the create from parking `route()` — run it as a spawned task that replies through the
     client's frame channel, so `Ping`, `Detach`, `Goodbye` and everything else keep flowing while it
     runs. This is the primary fix; the ones below do not substitute for it.
  2. Release a client's attachment on socket close rather than on loop exit, so a reconnect is not
     refused by a connection that is already gone.
  3. Let the fetch's live output through as periodic progress (throttled, not per-line) so the user
     sees a fetch advancing rather than a frozen bar — a UX fix, not a liveness fix: a fetch that is
     genuinely silent for 30 s must still keep the connection alive.
  4. Regression test in `crates/micold-daemon/tests/` alongside `liveness.rs`: a client whose
     operation blocks for longer than `LIVENESS_DEADLINE` still receives `Pong`s throughout, and its
     final `OperationOk`/`OperationError` is delivered. Neither existing liveness test
     (`a_responsive_daemon_is_never_reaped`, `a_half_open_connection_is_surfaced_within_10s`) covers a
     busy connection.
  5. Decide and record the general rule: which daemon operations may exceed the liveness deadline, and
     what the loop owes the connection while they run.

## Related

- **BUG-007** (`010-daemon-session-persistence`) — `displaced` as a latch written by every refusal.
  Same banner, different cause: there the state never cleared; here the refusal itself is spurious,
  produced by a stale attachment. FR-024a fixed the exit condition; this report is about the entry.

## Reproduction

1. Open a project whose repository declares at least one submodule large enough that
   `git submodule update --init --recursive` takes more than ~10 s.
2. Create a new worktree.
3. At "Setting up submodules", wait ~10 s.

Expected: the form stays in progress until the create concludes, then reports success or a specific
submodule failure. Actual: the two banners above; the window goes read-only against its own build; the
create's outcome is never reported, though the worktree may in fact have been created.

**Verification status**: reproduced and closed. `crates/micold-daemon/tests/busy_connection.rs`
(T122) drives a real `git worktree add` held open by a real `post-checkout` hook. Pre-fix, both
halves reproduced exactly as described above: every `Pong` arrived only after the create had
finished (all six probes completed at 4.2 s against a 3 s hook), and the reconnect was refused
`ProjectBusy` naming the departed connection's own build string. Post-fix both pass, and a third
test pins that the *live* holder still keeps its project while a create runs, so the fix cannot turn
a spurious takeover banner into a real one.
