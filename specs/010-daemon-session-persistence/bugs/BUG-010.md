# Bug Report: The hook receiver's 64 KiB body bound is smaller than a real `PostToolUse` payload, so editing a large file makes `claude` log an HTTP 413 for every hook the daemon was built to receive

**Type**: Spec gap (the contract mandates a bound but never sizes it; the implementation sized it from
an assumption — "hook payloads are small JSON objects" — that the payload schema contradicts)
**Severity**: High (every edit of a file larger than ~60 KB surfaces a red hook error inside the
user's own `claude` session — the same user-visible failure class as BUG-001 — and the receiver
silently discards a lifecycle signal it exists to receive)
**Feature**: `010-daemon-session-persistence` (FR-016a/FR-016b, `contracts/hooks.md` §Listener rule 5,
T045). Observed on branch `fix/deamon-replies-413-on-post-edit-hook`
**Reported**: 2026-08-07
**Status**: Fixed (2026-08-07) — Phase 24 (T126–T130)
**Patched**: 2026-08-07 — `spec.md` gained FR-016g and SC-022; `contracts/hooks.md` §Listener rule 5
is now sized against measured payloads (with rule 7 added for the auth-ordering defect, a "refused or
undelivered hook" entry in §State machine, and payload *size* added to the verification table);
`plan.md` Risk 4 widened to name shape *and* size; `tasks.md` gained Phase 24 (T126–T130). No task
reopened.
**Fixed**: 2026-08-07 — Phase 24 (T126–T130) all closed. `MAX_BODY` 64 KiB → 4 MiB (~43× the measured
maximum), the size check moved after the token check, and an over-bound request is now drained
(bounded by 8 MiB *and* a 2 s deadline) before it is answered. Two regression tests in
`hooks_receiver.rs`, both observed red first. `mise run test` green (162 groups, 1,416 tests),
`cargo clippy --workspace --all-targets -- -D warnings` and `cargo fmt --check` clean.

**Found by the red test, not by review** — worth recording, since both would have shipped otherwise:
1. The agent-sized POST did not merely get a `413`, it got **no status at all** (`ConnectionReset`):
   the receiver answered and closed while the peer was still writing. That turned secondary defect 2
   from a hypothesis into a decision — drain, don't just close.
2. The first drain implementation then **hung**: a peer that declares a large `Content-Length` and
   sends less, without closing its write half, parks the handler forever. A byte cap does not bound
   that; only a deadline does. Hence `DRAIN_TIMEOUT`.

## Description

While working in a daemon-spawned session, `claude` logs:

```
PostToolUse:Edit hook error
HTTP 413 from http://127.0.0.1:34891/hook/aea1def7-cb6c-43eb-9cca-6ce90fa8c38c
```

`crates/micold-daemon/src/hooks.rs` caps a hook request body at 64 KiB:

```rust
/// Maximum request-body size accepted (contracts/hooks.md §5). Hook payloads are small JSON objects;
/// anything larger is rejected with `413` rather than buffered.
const MAX_BODY: usize = 64 * 1024;
```

and rejects anything above it (`hooks.rs:189-191` on the declared `Content-Length`, `hooks.rs:212-214`
on the streamed body).

**Hook payloads are not small JSON objects.** A `PostToolUse` payload embeds the tool's *entire*
input and response. For `Edit`/`Write` that means `tool_response.originalFile` — the whole pre-edit
file — plus `tool_input.old_string`/`new_string` (or `content`). The payload therefore scales with
the size of the file being edited, and 64 KiB corresponds to a source file of roughly 25–30 KB once
the file appears in both the input and the response.

### Measurement

Reconstructing the `PostToolUse` payload for every `Edit`/`Write` recorded in this project's own
Claude Code transcripts (`~/.claude/projects/-home-jaro-workspaces-micold-ai-ide*/*.jsonl`, payload
modelled as the documented envelope + `tool_input` + `tool_response`):

| Samples | Over 64 KiB | Largest payload |
|---|---|---|
| 3,332 | 3 | **97,087 bytes (95 KiB)** — `specs/017-material3-visual-system/tasks.md` |

The next two were 68,227 B and 67,933 B, both `specs/**` markdown. So the bound is exceeded rarely
in aggregate (~0.1% of edits) but **deterministically** — any edit to a large spec, `tasks.md`,
`Cargo.lock`, or a big module reproduces it every single time, which is exactly the working pattern
this repository has (its own `tasks.md` files are the largest artifacts in the tree).

### Why it is not merely cosmetic

Per `contracts/hooks.md` §State machine, `PostToolUse` carries **no** FSM transition, so the dropped
hook in the reported symptom does not corrupt the activity signal. But the same bound gates every
event on the same endpoint, and two of them do carry transitions on payloads that can grow:

- `PreToolUse` (→ `Working`) carries `tool_input`, which for a large `Edit`/`Write` alone can pass
  64 KiB. Losing it strands a session in its prior state.
- `UserPromptSubmit` (→ `Working`) carries the user's prompt, which a large paste can push over.

Both failures degrade *toward* stale-`Working`, never toward a false `AwaitingInput`, so **H1/H1c
still hold** — this is a signal-loss bug, not a wrong-signal bug. That is what keeps it High rather
than Critical.

Two secondary defects in the same path, found while tracing:

1. The `Content-Length` rejection at `hooks.rs:189` fires **before** the token check at
   `hooks.rs:195-201`, so an unauthenticated caller can distinguish "too large" from "forbidden".
   This is a small deviation from §Listener rule 3's intent that the receiver disclose nothing
   pre-authentication, though it discloses nothing about the *session*.
2. Both 413 paths respond and close without draining the request body, so the peer can observe an
   `ECONNRESET` on its remaining write rather than the status. This may be why the failure surfaces
   as a bare `HTTP 413` line rather than a graceful hook rejection.

## Artifact Traceability

### spec.md

- **Affected user story**: User Story 2 — attach to a running session and see, without opening it,
  which sessions are working and which are waiting.
- **Affected requirements**:
  - **FR-016a** — "MUST derive and report an activity signal for every session." A hook the receiver
    refuses is a signal not derived.
  - **FR-016b** — the authoritative-signal requirement. It mandates *where* the signal comes from and
    forbids quiescence inference, but says nothing about the receiver being obliged to accept the
    signals the agent actually sends.
  - **FR-047** — "MUST NOT record session terminal content or user input." Still satisfied; the body
    is never logged, and no fix here may change that.
- **Gap identified**: no requirement states that the activity receiver MUST accept payloads whose
  size is set by the agent's own tool I/O, nor that a payload the receiver refuses MUST degrade under
  H1 (report `Unknown`, never a wrong state) rather than surface an error to the user inside their
  session. The spec treats the signal as arriving; nothing owns the seam where it is rejected.

### contracts/hooks.md

- **Affected section**: §Listener requirements, rule 5 — "**MUST** bound request bodies and reject
  oversized payloads."
- **Impact**: this is the origin of the defect. The rule is correct as a security constraint and
  wholly unsized as an engineering one — it gives no basis for choosing a number, so `MAX_BODY` was
  chosen from an intuition about payload size that the payload schema contradicts. Rule 5 needs the
  sizing rationale attached: the bound exists to stop an unbounded buffer, and must therefore sit
  well above the largest payload the agent can legitimately send, which scales with edited-file size
  and not with the hook envelope.
- Also missing from the contract: what a rejected payload means for the state machine (nothing in
  §State machine covers a refused hook), and that the receiver only ever needs `hook_event_name` —
  a few dozen bytes — from a body it may be buffering by the megabyte.

### plan.md

- **Affected sections**:
  - Constitution Check, Principle IV (line ~115) and Complexity Tracking (line ~527) — the mitigation
    list for admitting an HTTP listener ("bind `127.0.0.1` only, per-session bearer token, no
    capability beyond reporting activity"). Bounding is part of that justification, so the bound's
    sizing belongs in the same argument.
  - Mechanism note (lines ~443-444) — Claude Code hooks to a loopback, token-authenticated endpoint.
  - Risk 4, "Claude Code hook behaviour is a moving target" (line ~545) — payload *size* growth is a
    second axis of that drift, alongside the schema drift already listed. This bug is the first
    instance of it.
- **Impact**: no structural change. The plan's architecture is right; the risk register should name
  payload size, and the Principle IV mitigation should say the bound is sized to admit real payloads.

### tasks.md

- **Affected tasks**:
  - **T045** (Phase 4, US2, `[X]`) — "Implement the loopback HTTP hook receiver: … bounded bodies …".
    Its completion note states the handler "enforces every listener rule … `MAX_HEAD`/`MAX_BODY`
    bounds (431/413)". That claim is *true against the contract as written* — which is precisely why
    this is a spec gap and not implementation drift. T045 implemented rule 5 faithfully; rule 5 was
    underspecified.
  - **T086/T087** (Phase 11, BUG-001) — the previous fix to this same file. Unaffected; the
    settings-shape fix is orthogonal and remains correct.
- **False completions**: none. T045 should **not** be reopened — it built what it was asked to build.
  The corrective work is new, in its own phase, alongside the contract amendment.
- **Missing tasks** (for `/speckit.bugfix.patch` to add as a new phase):
  1. Amend `contracts/hooks.md` §Listener rule 5 to size the bound against real payloads and record
     the rationale, and note that only `hook_event_name` is ever read from a body.
  2. Raise `MAX_BODY` in `crates/micold-daemon/src/hooks.rs` to a bound that admits the measured
     payload range with headroom, keeping it a hard bound (the memory guarantee in SC-006's spirit —
     no unbounded buffering — must survive).
  3. Regression coverage in `crates/micold-daemon/tests/hooks_receiver.rs`: a `PostToolUse` body at
     realistic `Edit` size is accepted and drives the FSM; a body past the new bound is still `413`.
  4. Move the `Content-Length` rejection to after the token check, so nothing is answered
     pre-authentication beyond `403` (secondary defect 1).
  5. Decide and record whether an over-bound request should drain before responding (secondary
     defect 2), or whether `Connection: close` mid-body is acceptable.

## Root Cause Analysis

`contracts/hooks.md` §Listener rule 5 mandates a bound without sizing it. The rule was written as a
security constraint — stop a hostile or looping sender from making the daemon buffer without limit —
and in that frame any number works, so no number was justified. T045 then had to pick one, and picked
it from a plausible but unverified model of the payload ("hook payloads are small JSON objects",
`hooks.rs:38`). The real `PostToolUse` payload embeds the edited file's full contents, so its size is
set by the user's source tree, not by the hook envelope. The two models disagree by more than an order
of magnitude on exactly the files this repository edits most.

This is the same failure shape as **BUG-001**: an unverified assumption about Claude Code's hook
interface, encoded in `hooks.rs`, that held right up until it met a real payload. BUG-001 was the
hook *shape*; this is the hook *size*. `contracts/hooks.md`'s own "Verification required before
implementation" table is the right home for the class — payload size was never on it.

The bug survived T045's tests because every test in `hooks_receiver.rs` and every unit test in
`hooks.rs` posts a hand-written body of a few dozen bytes. Nothing in the suite has ever sent a
payload the size of a real one, so the bound has never been exercised from the direction that breaks.
