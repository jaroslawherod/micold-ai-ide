# Bug Report: A resumed session never leaves the "interrupted, resumable" state, so the bar offers `restart` for a session that is already running

**Type**: Spec gap (FR-006a specifies how a session *enters* the interrupted-resumable state and never
how it leaves; the implementation is faithful to what was written)

**Severity**: Medium as first observed (no data loss and no crash, but the control offered would
restart a live agent session, and the status the user reads is wrong for the entire life of the
process). **Arguably High once the second face below is counted**: the same omission means *no*
session in the application is ever reported as running, including brand-new ones

**Feature**: 010-daemon-session-persistence

**Reported**: 2026-08-16

**Status**: **Fixed** (2026-08-16) — Phase 27 (T135–T138). Both faces were confirmed on screen first;
see **Reproduction**

**Patched**: 2026-08-16 — `spec.md` gained **FR-006d** (a session whose process the service started
MUST be reported as running, by every route into a live process, and the report MUST reach
already-attached clients) and **SC-025**; `tasks.md` gained Phase 27. No task reopened: the FR-006a
work implements what was specified, and what was specified never said how a session *leaves* the
interrupted-resumable state

**Fixed**: 2026-08-16 — `Catalog::mark_session_running` (ungated, returns the owning project on a
transition), called from `DaemonState::start_session` after `register_session` with a
`broadcast_catalog()` outside the lock. Three regression tests in `session_start.rs`, observed red
first at the seam that had none — asserting on the snapshot a client would receive, not on the FSM

**Evidence**: [one bar, two opposite truths](../evidence/BUG-011-same-bar-two-states.png),
[a new session reading `starting…`](../evidence/BUG-011-new-session-starting.png)

## Description

Resume a session that the service is presenting as *interrupted, resumable* — either by reopening the
application onto it (feature 025's restore, FR-004a) or by clicking the session row by hand. The
process starts, the terminal streams real output, and the session works.

The bottom bar continues to read `interrupted`, and continues to offer a `restart` control, for as
long as the process runs.

Observed during feature 025's §B2 verification, in two independently-built sandboxes on the same
commit. It does not settle: sampled at 12s, 24s and 1m45s with `ps -o stat=,etime=` confirming the
process alive at `Ssl+ 01:45`, and it survives switching to another session and back, so it is not a
refresh lag. It reproduces on the hand-click path as well as the restore path, so it is **not** a
regression from feature 025's BUG-002 — that change only made the state reachable far more often,
because it made every reopen a resume.

This is the mirror image of feature 025's BUG-001. There, the pane said `Starting…` about a session
with no process behind it: the bar was right and the body lied. Here the body is right and the bar
lies.

## Root cause

The lifecycle is never advanced. This is not a case of the daemon knowing and the client not being
told — the daemon's own catalog still holds `SessionLifecycle::InterruptedResumable` after the spawn
has succeeded.

`DaemonState::start_session` (`crates/micold-daemon/src/state.rs:803-850`) spawns the PTY and inserts
a `LiveSession` into the live registry, and touches `session.lifecycle` not at all:

```rust
pub fn start_session(&self, id: SessionId, launch: LaunchMode) -> io::Result<()> {
    if self.live_session(id).is_some() { return Ok(()); }
    let plan = { /* read cwd/mode/scrollback from catalog */ };
    let session = match plan.mode { TerminalMode::AiCli => PtySession::spawn_claude(...)?, ... };
    tracing::info!(session = %id.0, mode = ?plan.mode, ?launch, "session started");
    self.register_session(session);   // live registry only
    Ok(())
}
```

`Session::start()` and `Session::mark_running()` both exist (`crates/micold-core/src/session.rs:392`,
`:413`) and neither is on this path. The only `mark_running` in the daemon is
`mark_running_if_restarting` (`crates/micold-daemon/src/catalog.rs:473-482`), gated to `Restarting`
and called from the supervisor tick (`state.rs:955-961`) — a resumed session is
`InterruptedResumable`, never `Restarting`, so that gate is a permanent no-op for it.

Three things then keep the stale value in place:

1. **Nothing is broadcast.** `ClientMsg::SessionStart` (`crates/micold-daemon/src/server.rs:455-471`)
   calls `spawn_session_start(..., LaunchMode::Resume, None, ...)`, and in `spawn_session_start`
   (`server.rs:1352-1391`) the trailing `broadcast_catalog()` sits inside `if let Some((client, req))
   = reply`. `reply` is `None` for `SessionStart`, so a resume broadcasts nothing.
2. **The live overlay deliberately excludes it.** `overlay_live_summaries` (`state.rs:341-351`)
   projects runtime facts onto the wire snapshot — `activity`, `input_serial`, `title` — and not
   `lifecycle`. `session_summary` (`catalog.rs:560-572`) takes `lifecycle` straight from the durable
   record. So even a forced `CatalogChanged` would still report `InterruptedResumable`.
3. **The client has no independent opinion.** `Message::SessionRunning` is defined (`app.rs:318`) and
   handled (`app.rs:1474-1478`), and is **emitted nowhere** in `crates/micold-client` — the comment at
   `app.rs:1499` claiming the binary "follows up with SessionRunning/ShellInstanceRunning once it's
   actually up" describes a follow-up that does not exist for `SessionRunning`. And
   `reconcile_catalog` (`shell/daemon_sync.rs:219-226`) assigns `existing.lifecycle = lifecycle`
   unconditionally, so a local optimistic `Running` would be overwritten on the next snapshot anyway.

Client rendering is downstream and correct given its input: `session_status`
(`crates/micold-client/src/ui/terminal.rs:510-530`) maps `InterruptedResumable => "interrupted"` at
`:521`, and `attached_process_restartable` (`terminal.rs:558-575`) matches `Idle | Failed |
InterruptedResumable`, which is what puts `restart` on screen at `:405`.

## The second face: no session is ever reported as running

The report above is about *resumed* sessions, which is where it was noticed. The omission is not
specific to them.

`Session::start_new` (`crates/micold-core/src/session.rs:254`) creates a session at
`SessionLifecycle::Starting`. Nothing moves it on either, for the same reason: `start_session` does
not touch the durable record, and `mark_running_if_restarting` is gated to `Restarting`. So a
**brand-new** session reads `starting…` in the bar for as long as it exists.

Put the two together and the reachable states are:

| Session | Durable lifecycle | Bar reads | `restart` offered | Truth |
|---|---|---|---|---|
| Newly created | `Starting` (`start_new`) | `starting…` | no | running |
| Resumed after a service restart | `InterruptedResumable` (`present_interrupted_resumable_at_startup`) | `interrupted` | **yes** | running |
| Respawned after a crash | `Running` (`mark_running_if_restarting`) | `running` | no | running |

**The only route to `Running` in this application is to crash a session and let supervision respawn
it** — which is exactly, and only, what `crates/micold-daemon/tests/supervision_restart.rs:145`
asserts. `Session::start` has no production callers at all; `mark_running` has one.

That also explains why neither side's tests could see it. The daemon's lifecycle tests
(`session_lifecycle.rs`, `session_crash_restart.rs`, `supervision_restart.rs`) call `start()` and
`mark_running()` themselves, so they prove the state machine is correct and cannot notice that
production calls neither. The client's fixtures call `mark_running()` by hand
(`crates/micold-client/tests/support/mod.rs:35`), so every client assertion about a running session
starts from a state the daemon never produces. Both sides tested against the same assumption from
opposite ends, and the assumption was never the thing under test.

## Reproduction

Confirmed on screen on 2026-08-16, in an isolated Xvfb + lavapipe sandbox, **without any provider
credentials**: `claude` was replaced on `PATH` by a three-line stub that prints its own arguments and
then `exec cat`. The process is then unambiguously alive, its output unambiguously reaches the pane,
and nothing in the reading depends on the real CLI. The daemon's log supplies the ground truth the
screen is checked against.

1. **A new session**, created through the UI. Daemon: `session started … launch=Fresh`. Pane: the
   stub's output. `ps`: alive at 19 s and again at 45 s. Bar: **`starting…`** at both readings —
   [evidence](../evidence/BUG-011-new-session-starting.png).
2. **A resumed session.** Client *and* daemon stopped, then relaunched. Daemon: `session started …
   launch=Resume` for the remembered id, no clicks. Pane: `stub-claude up: args=[--resume 7f230d6e-…]`
   and a live cursor. Bar: **`interrupted`**, offering **`restart`**.
3. **A session that genuinely did not start.** Same restart with `claude` removed from `PATH`.
   Daemon: `session start failed … Unable to spawn claude … No viable candidates found in PATH`.
   Pane: "This session is not running. Choose restart below to resume it." Bar: **`interrupted`**,
   offering **`restart`**.

Readings 2 and 3 are the bug in one image: cropped at identical geometry, the two bars are
indistinguishable — [evidence](../evidence/BUG-011-same-bar-two-states.png), red the running session,
blue the one that never started. The bar is not wrong in state 3. It is right there, and carries the
same words in state 2, which is why nothing it says can be believed.

Step 3 also settles a question feature 025's B2 had left open — see **Cross-feature** below.

## Artifact Traceability

### spec.md

- **FR-006a** is the requirement at issue. It is precise about entering the state — durable records
  found at startup "MUST be presented in a distinct 'interrupted, resumable' state, visibly different
  from both 'running' and a session the user stopped deliberately, and MUST be resumable by a single
  explicit user action" — and says nothing about what the state becomes once that single explicit
  action succeeds. The implementation satisfies every clause as written. The session is presented
  distinctly, and it is resumable by one action; it simply stays presented that way afterwards, at
  which point "visibly different from running" is violated by a session that *is* running.
- **FR-005 / FR-006b** are why the `Restarting` gate is narrow, and are not at fault: supervision
  deliberately does not run at service startup, so routing the fix through it would be wrong.
- **Suggested resolution**: an FR-006d stating that a resumable session which the user has resumed
  MUST be reported as running once its process is live, and MUST NOT offer resumption while it runs.
  A success criterion in the shape of the existing SC-016 ("reported as *working* for that period")
  would make it checkable.

### Cross-feature

- **025-last-session-memory** — found during §B2 (see that feature's `quickstart.md`, *B2 under
  FR-004a*). BUG-002 there did not cause this, but it raised the exposure sharply: before it, a
  restore started nothing and the `interrupted` label was accurate; after it, every reopen resumes,
  so every reopen displays a running session labelled interrupted.
- **025's FR-014, and BUG-012's guess about it.** [BUG-012](./BUG-012.md) suggests a deleted-worktree
  session "offers FR-014 a reachable path". It does not: that session is started anyway, so the
  daemon streams it and the pane is never empty. The route that *does* work is reading 3 above — a
  start the daemon cannot perform at all. Recorded in 025's quickstart under *FR-014, reached
  deliberately*, and it is the first demonstrated path to that screen after three failed attempts.
- **025 BUG-001** is the same class of defect — the bar and the pane body disagreeing about one
  session — reached from the opposite side. Its FR-014 (the terminal area must not claim to be
  starting a session nothing is starting) is the precedent for treating a truthful-status mismatch as
  worth its own requirement rather than a cosmetic detail.

## Recommended Fix

Advance the lifecycle where the process actually becomes live, in `start_session`, rather than adding
a second source of truth in the client:

- Call `Session::start()` / `mark_running()` on the durable record when `register_session` succeeds,
  and `broadcast_catalog()` afterwards so attached clients see it. The early-return at the top of
  `start_session` (`if self.live_session(id).is_some()`) already makes a redundant start a no-op, so
  this does not fire twice for the same process.
- Alternatively, add `lifecycle` to `overlay_live_summaries`, deriving "running" from the presence of
  a live session. That is a smaller change and self-correcting, but it puts the durable record and the
  wire snapshot permanently out of agreement, which is worth avoiding for a value that other logic
  reads.

The first is preferred. Whichever is chosen, `Message::SessionRunning` in the client should either be
wired up or deleted — an unemitted variant with a comment describing a follow-up that does not exist
is what made this look like a transport problem rather than a state problem.

Because the fix sits in `start_session`, it covers the second face without further work: a new
session reaches `Running` by the same call that a resumed one does.

**Where the regression test belongs**: at the seam nothing currently covers. Drive a real
`SessionStart` through `DaemonState` and assert on **the snapshot a client would receive**, not on
the FSM. Every existing lifecycle test asserts on the FSM, which is why the state machine is provably
correct and provably unreached.
