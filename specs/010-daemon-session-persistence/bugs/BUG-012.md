# Bug Report: A session whose working directory no longer exists is started in `$HOME` instead of being refused, so an agent runs against the wrong tree

**Type**: Spec gap (nothing in the spec says what a start must do when the session's directory is
gone; the resulting behaviour is chosen by a dependency's fallback rather than by this project)

**Severity**: High (an AI CLI session is spawned, silently, rooted at the user's home directory
instead of the project it names. Nothing on screen says the directory was substituted, and an agent
given a task in that session operates on `$HOME`)

**Feature**: 010-daemon-session-persistence

**Reported**: 2026-08-16

**Status**: Open

## Description

Delete a worktree from outside the application, so the session that lives in it is listed with the
`missing` status. Then start that session — by clicking it, or by reopening the application onto it
(feature 025's restore, FR-004a).

The session starts. The row still reads `missing`, and `readlink /proc/<pid>/cwd` gives the user's
home directory rather than the worktree path that no longer exists. Nothing reports a substitution.

Observed during feature 025's §B2 verification: `readlink /proc/<pid>/cwd` returned the sandbox's
`$HOME` (`/tmp/mb81/home`) for a session whose worktree had been removed.

The concerning case is not the empty shell. It is that an agent session is a thing the user gives
instructions to. A user who resumes what they believe is a project session and asks it to "fix the
failing test" has pointed a tool with write access at their home directory.

## Root cause

Two independent gaps compound: nothing checks the directory, and the dependency's fallback is silent.

**Nothing checks.** The cwd is computed by string join, with no filesystem contact
(`crates/micold-core/src/session.rs:200-205`):

```rust
pub fn cwd(&self, repo: &Path) -> PathBuf {
    match self {
        SessionLocation::Worktree(dir) => repo.join(".claude/worktrees").join(dir),
        SessionLocation::Default => repo.to_path_buf(),
    }
}
```

`start_session` (`crates/micold-daemon/src/state.rs:803-853`) and `respawn_primary` (`state.rs:1024-1041`)
never call `exists()` / `is_dir()` / `try_exists` on the resulting path. The only such calls in the
daemon are in worktree *creation* and branch preflight (`server.rs:742`, `server.rs:826`), which are a
different path entirely.

**The fallback is the dependency's.** `spawn_claude` (`crates/micold-daemon/src/supervisor.rs:88-110`)
passes the path to `portable-pty`:

```rust
let mut cmd = CommandBuilder::new(ClaudeProvider.command());
cmd.cwd(&spec.cwd);          // supervisor.rs:96
```

`CommandBuilder::cwd` only stores it. The substitution happens on conversion to a
`std::process::Command`, in `portable-pty-0.9.0/src/cmdbuilder.rs:498-526`:

```rust
let home = self.get_home_dir()?;
let dir: &OsStr = self
    .cwd
    .as_ref()
    .map(|dir| dir.as_os_str())
    .filter(|dir| std::path::Path::new(dir).is_dir())   // a vanished path drops out here
    .unwrap_or(home.as_ref());
...
cmd.current_dir(dir);
```

`get_home_dir` (`cmdbuilder.rs:560-575`) returns `$HOME`, else `getpwuid(getuid()).pw_dir`, else `/`.
So the missing directory is filtered out and replaced without an error, a log line, or any signal the
daemon could act on. This also silently changes binary resolution, since the same `dir` is used for
`search_path(&self.args[0], dir)` — and `spawn_shell` (`supervisor.rs:125`) behaves identically, so
regular terminals have the same fallback.

**The status the UI already computes is never consulted.** `WorktreeStatus::Missing` is derived in
`crates/micold-core/src/worktree.rs:205-211`:

```rust
pub fn classify(record: &WorktreeRecord, dir_exists: bool) -> WorktreeStatus {
    if record.prunable || !dir_exists { WorktreeStatus::Missing } else { WorktreeStatus::Valid }
}
```

cached by `refresh_worktrees` (`state.rs:588-601`) into `Inner::worktrees`, and projected to the wire
only for the UI snapshot (`wire_worktree_status`, `state.rs:141-149`, called once at `state.rs:323`
inside `snapshot_locked`). `Inner::worktrees` is read nowhere on the spawn path — `start_session`
consults only `catalog.workspace().sessions` and `s.location.cwd(project)`. The daemon therefore knows
the directory is gone, shows the user that it is gone, and starts the process there anyway.

The one near-miss: if env-include is enabled, `env_include_vars_for` (`state.rs:250-277`) runs `bash`
via a real `std::process::Command` with `current_dir(cwd)` (`crates/micold-core/src/env_include.rs:324`),
which *does* fail on a missing directory — producing `tracing::warn!(... "env-include resolution did
not succeed")` at `state.rs:271`. That warning is discarded rather than turned into a refusal, and it
does not occur at all when env-include is off.

## Artifact Traceability

### spec.md

- No functional requirement covers this. **FR-006** guarantees a session "remains resumable after its
  process ends for any reason", which is about durable identity and does not contemplate the working
  directory disappearing. **FR-006a** requires a resumable session to be "resumable by a single
  explicit user action" without qualifying what happens if the directory it names is gone.
- **SC-008** ("Zero cases in which a failed worktree or project operation leaves a catalog entry, a
  directory, or service state inconsistent") is the nearest existing criterion in spirit, but its
  subject is operations this application performs. A worktree deleted externally is exactly the case
  it does not cover.
- **Suggested resolution**: a requirement that starting a session whose working directory does not
  exist MUST be refused, with the reason shown, and MUST NOT substitute another directory. This has a
  ready-made surface: feature 025's **FR-014** already specifies what the terminal area shows when a
  start is refused, and 025's §B2 could not find any route that reaches that wording — a refusal here
  would give it one.

### Cross-feature

- **025-last-session-memory** — found during §B2 (see that feature's `quickstart.md`, *B2 under
  FR-004a*). 025 deliberately decided that a session whose worktree was deleted should still be
  *restored*, on the reasoning recorded in its clarifications: the application already lists such a
  session and lets the user select it, so declining to return them to it would be inconsistent. That
  reasoning was sound under FR-004, where restoring meant displaying and starting nothing. **BUG-002
  changed restoring to mean starting**, and the clarification was not revisited against the new
  meaning. Displaying a session rooted in a directory that is gone is harmless; running an agent there
  is not.
- **012-multiple-regular-terminals** shares the defect through `spawn_shell`, though with lower stakes
  — a shell in the wrong directory is visible to the user at the first prompt, where an agent's cwd is
  not.

## Recommended Fix

Check before spawning, in `start_session` and `respawn_primary`, and refuse rather than substitute:

- Resolve `plan.cwd` and verify it `is_dir()` before calling `spawn_claude` / `spawn_shell`. On
  failure, record the reason on the session (the give-up-state mechanism FR-005 already requires for
  exhausted retries is the natural place) and report it, rather than returning `Ok(())` with a live
  process in the wrong tree.
- Do not rely on `Inner::worktrees` for the decision. It is a cache refreshed on its own schedule, and
  the directory can vanish between refresh and spawn; the check must be against the filesystem at
  spawn time. The cached status remains the right thing for the row's `missing` badge.
- Consider passing an explicit cwd to `portable-pty` only after the check, so the library's
  `unwrap_or(home)` becomes unreachable rather than merely unlikely. A silent fallback that changes
  both the working directory and binary resolution is worth not depending on either way.
