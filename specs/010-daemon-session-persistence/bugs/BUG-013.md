# Bug Report: A session survives the client restart in the service and never comes back on screen

**Type**: Implementation gap (SC-001's headline claim is false from the user's side: the session
survives, and the interface cannot reach it)

**Severity**: High — this is the feature's reason for existing. Nothing is destroyed: the process
keeps running, the durable record keeps the session, and the work is still there. It is simply
unreachable, and the only visible remedy is to start a new session, which abandons a live one and
leaks it — the daemon goes on hosting a process no window lists

**Feature**: `010-daemon-session-persistence` (SC-001)

**Reported**: 2026-08-19

**Status**: Fixed 2026-08-19 — cause found with the attach log this report asked for, and confirmed on screen

**Evidence**: [the same sidebar, before and after a client
restart](../evidence/BUG-013-sessions-after-client-restart.png)

## Description

Open a project, start a session, quit the interface, reopen it. The project comes back. **The session
does not.** The sidebar's worktree row is empty, as though the project had never had one.

Meanwhile the service is still hosting it. In the reproduction below the daemon still owned the AI
CLI process and three shell instances, and its durable record still listed the session with
`archived: false` and named it `last_session`.

So all three of the things the feature promises are true — the process lives, the record lives, the
service lives — and none of it reaches the window.

## Reproduction

Xvfb `:77` + lavapipe, stub `claude`, pinned client/daemon pair, private `XDG_RUNTIME_DIR`.

1. Open `~/vp/proj` (a git repo). Start a session with the worktree row's `+`.
2. The sidebar shows the session; the bar reads `running`. The AI CLI pane is live.
3. Kill **only** the client. Leave the daemon running — this is a reattach, not a cold start.
4. Relaunch the client.

**Expected**: the session is listed and reattaches (SC-001).
**Actual**: the project is listed; the worktree row is empty.

The evidence image is that sidebar before (green) and after (red), same build, cropped at identical
geometry.

## Not a regression from the catalog-fold move

Checked deliberately, because the move landed the same day and touches exactly this path:

- The fold's body is byte-identical across the move — `diff` clean over all 147 lines of
  `reconcile_catalog`.
- The parent commit `bd67826` was built separately (confirmed pre-move: zero `catalog_sync` strings
  in its binary) and reproduces the identical symptom.

It predates the move, and predates BUG-003/BUG-004 as well — those made *lifecycle* reachable, which
is a different axis from *existence*.

## What has been established

Working outward from the durable layer, each step verified rather than assumed:

1. **The durable store is correct.** Loading the failing run's own on-disk files through
   `Catalog::load` and calling `snapshot()` yields the project with **one** session
   (`load_status=Loaded`, `sessions=1`). Nothing is lost on disk or in the projection.
2. **The fold is correct.** `crates/micold-daemon/tests/catalog_join.rs` drives
   `DaemonState::welcome_payload` → `reconcile_catalog` → client `State` and the session arrives.
   That test is exactly this shape and it passes.
3. **The service still holds the live processes** at the moment of the failure (`ps` against the
   daemon's children: the AI CLI plus three shells).

So the break is **between the service holding the session and the window drawing it** — the
connect/welcome path or the render — and not in the durable layer, the snapshot projection, or the
fold. That is a real narrowing: three of the five candidate layers are eliminated by evidence.

## What had not been established *when this was filed*

**Resolved — see [Cause, found](#cause-found) below. It was the second candidate.** Kept as written
rather than rewritten: the value of this section is the record that the question could not be
answered from outside the process, which is what motivated the logging that then answered it in one
run.

**Whether the relaunched client receives a welcome catalog at all.** This is the next thing to find
out, and it could not be answered from the outside: the client's whole log for the failing run is one
line —

```
switch: entered /home/jaro/vp/proj -> active_session=None choice=Some(NoSessionsForKey)
  resolve_key=/home/jaro/vp/proj session_keys=[]
```

— which is emitted at project entry *before* any catalog could have arrived, and is byte-identical in
the run that **worked** (the first launch) and the run that failed. It therefore distinguishes
nothing. The client logs no attach, no handshake result, no catalog receipt; the daemon wrote no log
file at all under the sandbox's data dir.

Two candidate explanations remain open, and they want opposite fixes:

- **The client never attached.** A second client against an already-running daemon may be refused
  (exclusivity, handshake, a stale socket), in which case the window is rendering purely local state
  and the empty sidebar is a *disconnected* state drawn as if it were an empty one. FR-028 and the
  `displaced` machinery exist for this, so if it is happening it is being swallowed somewhere.
- **The client attached and the catalog was not applied or not rendered.** `on_connected` calls
  `reconcile_catalog` before it reads `active_project()`, so ordering there is worth a second look.

## Traceability

- **SC-001** — "100% of running sessions survive closing, crashing, and rebuilding the user
  interface, on Linux, macOS, and Windows." The session *survives*; what fails is reaching it. Read
  from the user's side, the criterion is not met — a session you cannot open has not survived in any
  sense they care about.
- **BUG-008** (open) is the reason this went unnoticed for so long, and this report is a direct
  instance of its argument: T084 (`quickstart.md` S1–S15, which includes the restart walkthrough) has
  been open since the feature landed because its stated method is a person at a display. This was
  found by the `visual-pass` skill, which is the executable path BUG-008 says did not exist.
- **`010` BUG-006** is *adjacent but not this*. It says sessions that predate a client restart go
  silently read-only — which presupposes they come back and then reject input. Here they never
  appear. Whether BUG-006's fix was ever exercised end-to-end is worth re-checking once this is
  fixed, since its symptom is unobservable while this one holds.

## Recommended fix (as filed — followed, and it worked)

Find out which of the two candidates it is before writing anything, and make that answer *cheap to
get*: the client should log the attach outcome (attached / refused / version-mismatch, and the
session count in the welcome it applied). The absence of that line is why this report ends with two
hypotheses instead of one cause, and it will be why the next reader of this path is stuck too.

Then gate it where the gap actually is. `catalog_join.rs` already covers daemon → fold → state, and
it passes while the application is broken — so the missing coverage is one layer out, over the
connect path: a client that attaches to a daemon already hosting a session must end up with that
session in its state. `crates/micold-daemon/tests/client_restart_input.rs` already drives a real
daemon binary from real client code and is the natural place for it.

## Cause, found

The attach log this report recommended answered it on the first run, and eliminated the candidate it
was written to test:

```
attach: connected projects=0 sessions=0 active=<none> active_sessions=<project not in catalog>
switch: entered /home/jaro/vp/proj -> ... choice=Some(NoSessionsForKey) session_keys=[]
attach: connected projects=1 sessions=1 active=/home/jaro/vp/proj active_sessions=1
```

The client **did** attach, and the catalog **did** carry the session. "Never attached" was wrong.
Read the three lines in order and the defect is in the ordering itself:

1. The client boots, restores its project, and `restore_after_activation` asks which session to
   show. Sessions live on the daemon, so at that instant the project has none and
   `explain_foreground` answers `NoSessionsForKey` — which is correct, and which the middle line
   records.
2. The welcome catalog then arrives and `reconcile_catalog` files the session under the project.
3. **Nothing asks again.** `active_session` stays `None` for the rest of the run.

### Why that looked like the session was gone, rather than merely unselected

This is the part worth keeping. A location row is drawn open by
`features::sidebar::effective_open(user_open, holds_current_session, reveal_suppressed)`, and the
sidebar emits a node's sessions only `if node.expanded`. With nothing current, the Default row held
no current session and the user had not opened it, so it stayed shut — and the session inside it was
never drawn. It was in `State`, it was in the catalog, it was running in the daemon, and it was
invisible.

So a missing *selection* presented as missing *data*, which is why the reproduction reads as data
loss and why the first three layers all checked out.

## The fix

`State::resolve_foreground_after_catalog` (`features/session.rs`), called from `on_connected`
between folding the catalog and reading `active_session` — so the attach that follows views the
restored session instead of the overview.

The guard is `ForegroundChoice::NoSessionsForKey` specifically, not "nothing is current". FR-007
forbids choosing a session for the user when they land on the project overview, and `on_connected`
cannot tell a boot from a mid-session reconnect. `NoSessionsForKey` is the one answer that indicts
the *key* rather than the sessions — it means the resolve looked somewhere empty — so re-running it
corrects a question asked too early rather than overriding an answer. `NoneActive` (the project has
sessions, none running) is a real overview landing and is left alone, as is any session already
chosen.

### Tests

- Three in `tests/features_session.rs` for the rule: the re-resolve happens after a catalog arrives
  late; a deliberate `NoneActive` landing is left alone; a reconnect does not relocate a user who
  already has a session.
- One **wiring** gate, `the_connect_path_re_resolves_the_foreground_after_folding_the_catalog`,
  which reads `on_connected` out of the source and asserts the call sits *between* the fold and the
  read of `active_session`. Order is load-bearing: re-resolving after that read would set the
  session and then not act on it. Proven by deleting the call and watching it fail.

  That gate exists because an unwired fix is this codebase's most common failure mode — `010`
  BUG-011, `012` BUG-003 and `012` BUG-004 were all a correct function nothing called.

### Confirmed on screen

2026-08-19, Xvfb + lavapipe, stub `claude`. Start a session, quit the client, reopen: the session is
listed, selected, its pane shows the AI CLI's own scrollback, and the bar reads `running`. The
process is older than the restart, so it was **reattached, not respawned**.
[Evidence](../evidence/BUG-013-fixed.png) — the same sidebar before (red) and after (green).

## What this leaves open

The attach logging added here is the diagnostic this report asked for, and it should stay. Note what
it still cannot say: it reports the catalog the client *received*, not what the daemon *sent*, so a
daemon-side omission would look identical to a client-side drop. That has not been needed yet.
