# Bug Report: Saving Settings silently reverts the user's theme — the service persists a boot-time snapshot of a client-owned field

**Type**: Implementation defect at the state-ownership seam (two writers to one file; only one of
them does a read-modify-write)
**Severity**: Medium (a setting the user deliberately chose is lost, silently, on an unrelated
action. It is invisible until the next launch, so the user has no way to associate the loss with
what caused it — and it recurs every time they touch Settings)
**Feature**: `010-daemon-session-persistence` (FR-008, FR-010, FR-012a, FR-012b) — seam with
`006-real-terminal-emulator` (scrollback) and `011-env-include-script`. Observed on branch
`docs/cleanup-completed-features`, client build from this branch
**Reported**: 2026-08-25
**Status**: **Fixed** — the code fix landed in `079e562` (feature 027) before this report was
read; verified and gated here 2026-08-26, and the artifact gap the report identified is closed by
**FR-010a** (see **Resolution** at the end)

## Description

Set the app theme to **Light** (or Dark) from the overflow menu, then open **Settings** and save any
change — the scrollback limit, or any environment-include field. `settings.json`'s `"theme"` reverts
to whatever the value was when **the daemon started**, discarding the user's choice.

The app does not appear to change: the in-memory theme is still the one the user picked, so the
window stays light. The loss surfaces only on the next launch, when the app comes back in the wrong
theme.

**Expected**: the service writes the settings it owns and leaves the client-owned `theme` as it
found it on disk.

## Root Cause Analysis

`settings.json` has two writers, by design. `010` FR-010 assigns `theme` to the client; FR-012a and
FR-012b assign the scrollback limit and the environment-include fields to the service. They share
one file and there is no reconciliation between them.

**The client is careful.** `persist_settings`
(`crates/micold-client/src/shell/persist.rs:95-106`) re-reads the file and merges, and says so:

```rust
// Preserve the persisted scrollback limit (feature 006) and environment-include settings
// (feature 011) when saving a theme change — this function only ever changes `theme`.
let existing = store.load().settings;
if let Err(err) = store.save(&Settings { theme: core.theme_pref, ..existing }) { … }
```

**The service is not.** `Catalog::load` reads the settings file **once, at daemon start**, and holds
the whole struct — including `theme`, which the daemon has no business owning
(`crates/micold-daemon/src/catalog.rs:65-78`):

```rust
let settings = settings_store.load();
Self { workspace: loaded.workspace, settings: settings.settings, … }
```

Every service-owned mutation then persists that entire stale struct
(`catalog.rs:205-212`, and identically in `set_env_include` at `catalog.rs:217-235`):

```rust
pub fn set_scrollback(&mut self, lines: usize) -> io::Result<usize> {
    let clamped = clamp_scrollback(lines);
    self.settings.scrollback_lines = clamped;
    if let Some(store) = &self.settings_store {
        store.save(&self.settings)?;   // <-- also writes self.settings.theme
    }
    Ok(clamped)
}
```

So the write-back is last-writer-wins over a field the writer never owned and never refreshed. The
reverted value is specifically the **daemon's boot-time snapshot**, not the previous on-disk value —
which is why the observed result is often neither what the user just chose nor what they chose
before.

The client's own save order makes it worse rather than better: `on_settings_saved`
(`persist.rs:137-226`) writes the merged file *first* and *then* sends `ClientMsg::SettingsSet` to
the daemon, so the daemon's stale write lands last and always wins.

Why no test caught it: both sides' persistence is tested in isolation, against its own temp store.
The client's roundtrip tests never involve a daemon; the daemon's `set_scrollback` tests assert the
scrollback value and ignore the rest of the struct. Nothing exercises **one file, two processes, in
order** — which is the only configuration in which the defect exists.

## Artifact Traceability

- **Affected requirements**:
  - **FR-008** ("The service MUST be the single writer of all durable state") and **FR-010** ("The
    client MUST own and persist only per-window presentation state: theme, …") — read together,
    these two split one file between two writers. FR-008's "single writer" is scoped to
    service-owned state, and FR-010 carves `theme` out of it, but **neither states the obligation
    that follows**: a writer must not persist fields it does not own.
  - **FR-012a** / **FR-012b** — the mutations that carry the defect. Both behave correctly for the
    field they name.
- **Gap identified**: the ownership split is stated per-field but the file is written whole. No
  requirement says a shared settings file must be updated by read-modify-write over the writer's own
  fields. The client implements that rule anyway (its comment shows the author reasoned it out); the
  service does not, and nothing in the artifacts would have told it to.
- **Affected tasks**: none falsely completed — the scrollback and env-include tasks deliver what they
  claim. Found by `006-real-terminal-emulator` **T042**'s quickstart pass.
- **Missing tasks**:
  1. Make the service's settings writes read-modify-write: reload the file immediately before
     `store.save`, overwrite only the service-owned fields, and keep the rest as found. (Refreshing
     `self.settings` at save time also fixes the symmetric hazard where a client theme change made
     during the daemon's lifetime is overwritten.)
  2. Better still, split the persistence so neither process can express the other's fields — the
     ownership boundary then holds by construction rather than by discipline.
  3. Cross-process regression test: with a theme on disk, a `SettingsSet` from the client must leave
     `"theme"` untouched while changing `scrollback_lines`.

## Reproduction

Reproduced twice on Xvfb `:83` + lavapipe, 2026-08-25, against a private daemon and catalog
(`XDG_RUNTIME_DIR=/tmp/vp83`, scratch `XDG_DATA_HOME`):

1. Set `"theme": "dark"` in `settings.json`, launch client + daemon.
2. Overflow → **Settings**, change the scrollback limit, **Save**.
3. `settings.json` now reads `"theme": "follow_system"` — the daemon's boot snapshot.

Repeated with `"theme": "light"` on disk: same result, `"follow_system"` again — confirming the
value written is the daemon's snapshot rather than the file's previous contents.

**User-visible symptom, end to end**: with the app running in **Light** (chosen from the overflow
menu, in memory and on disk), a Settings save was performed; the app stayed light. After quit and
relaunch the overflow menu read **"Theme: Auto"** and the window came back dark
(`evidence/bug-014-theme-after-relaunch.png`).

**Verification status**: reproduced manually, twice, with the on-disk value inspected each time. No
executable regression test yet.

## Recommended Fix

Run `/speckit-bugfix-patch` to state the shared-file obligation beside FR-008/FR-010 (a writer
persists only the fields it owns, over a fresh read), then `/speckit-implement`: reload in
`Catalog::set_scrollback` and `Catalog::set_env_include` before saving, plus the cross-process
regression test.

## Resolution (2026-08-26)

**The fix was already on `main`, and not as a fix for this report.** Feature 027 —
`079e562 feat(027): run the session daemon inside a container sandbox` — replaced both
`store.save(&self.settings)` calls with `Catalog::persist_service_settings`, which re-reads
`settings.json` and writes back only the five fields the service owns:

```rust
fn persist_service_settings(&self) -> io::Result<()> {
    if let Some(store) = &self.settings_store {
        let mut on_disk = store.load().settings;
        on_disk.scrollback_lines = self.settings.scrollback_lines;
        on_disk.env_include_enabled = self.settings.env_include_enabled;
        on_disk.env_include_script_path = self.settings.env_include_script_path.clone();
        on_disk.env_include_timeout_secs = self.settings.env_include_timeout_secs;
        on_disk.default_ai_cli = self.settings.default_ai_cli;
        store.save(&on_disk)?;
    }
    Ok(())
}
```

027 had its own reason to care, and it is a stronger one than this report's: 027 gives the client a
service placement and a whole sandbox profile to own — runtime, image, resource budget, network
posture, and the credential opt-ins — which turns *"the daemon reverts what the client wrote"* from
a theme-shaped annoyance into losing every credential the user had shared, on a save that changed
nothing. That is written into the function's own doc comment, which is where the reasoning belongs.

This is the report's **missing task 1**, done. Task 2 (splitting the persistence so neither process
can express the other's fields) was **not** done and is not proposed here: the file is one document
with one schema, and the protocol deliberately does not carry the client's fields — *"a theme is not
a session-service setting, and a protocol that carried one would make this daemon the authority on a
question it has no opinion about."*

### The symmetric hazard is closed too

`Catalog::load` still snapshots the whole `Settings` at boot, so `self.settings.theme` is still a
value this process holds and has no business holding. It is now unreachable: every read the daemon
serves or acts on goes through `catalog.settings_wire()` — the welcome payload, `SettingsChanged`,
the spawn plan's scrollback, the env-include cache — and that projection carries only service-owned
fields. Nothing else reads `self.settings`, and after 027 nothing writes it out whole.

### Gates (missing task 3, done — also before this report was read)

Two, both on `main`, both passing:

| Gate | What it holds |
|---|---|
| `crates/micold-daemon/tests/settings_default_ai_cli.rs::a_client_written_theme_survives_a_service_owned_change` | Boot the catalog, write a `Dark` theme to the file **behind its back** the way `persist_settings` does, then `set_scrollback` — the theme on disk must still be `Dark`, and `default_ai_cli` untouched by the same call |
| `crates/micold-daemon/tests/catalog_adoption.rs::a_service_settings_write_leaves_the_clients_own_fields_alone` | The same sequence across **both** service-owned mutations (`set_scrollback` **and** `set_env_include`), asserting the client's fields survive each |

The first is deliberately kept in `settings_default_ai_cli.rs`, where feature 026 had recorded this
defect as an out-of-scope observation rather than assuming it away. It is the same test; only its
name and its assertion changed when 027 fixed the cause.

Neither is the *cross-process* test the report asked for — both drive `Catalog` in-process rather
than sending a real `SettingsSet` over a socket. That is a deliberate stop: the write-back is a
`Catalog` method, the client's half (`persist_settings` re-reading and merging) has its own
roundtrip tests, and the ordering the report blamed — client writes the file, *then* sends
`SettingsSet` — is exactly what these tests reproduce by writing the file behind the booted
catalog's back. A socket in the middle would test the socket.

### Probes

Both gates were probed by undoing the fix — `persist_service_settings` restored to
`store.save(&self.settings)?`, the pre-027 body — and each failed at its theme assertion:

| Probe | Result |
|---|---|
| `a_client_written_theme_survives_a_service_owned_change` | FAILED — `left: FollowSystem, right: Dark`, *"a service-owned change must leave the client's own fields exactly as the file has them"* |
| `a_service_settings_write_leaves_the_clients_own_fields_alone` | FAILED — `left: FollowSystem, right: Dark`, *"the daemon reverted the theme the client had just saved"* |

`FollowSystem` is the daemon's boot snapshot, which is precisely the value the manual reproduction
above recorded on disk both times. The probes restore the reported symptom exactly, so the gates
hold the reported defect and not a neighbour of it.

### What this change actually delivers

Only the artifact half. The report's **"Gap identified"** — *"no requirement says a shared settings
file must be updated by read-modify-write over the writer's own fields"* — was still open: 027 fixed
the code and left FR-008/FR-010 saying what they had said. **FR-010a** now states the obligation, so
the next writer of that file is told the rule rather than having to re-derive it, as the client's
author did and the service's author did not.

### Not re-measured on a display

The manual reproduction in this report is the 2026-08-25 one, against the defective build. The fix
was not re-run on Xvfb: the assertion that matters is a value on disk after a sequence of writes,
which is what the two gates read directly, and the user-visible half (*the app comes back in the
wrong theme*) is downstream of exactly that value.
