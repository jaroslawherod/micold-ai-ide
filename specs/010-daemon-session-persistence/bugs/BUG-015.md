# Bug Report: an inherited `JOURNAL_STREAM` silences the daemon's log file entirely — and the documented log path is not the one the code writes

**Type**: Environment-detection defect (an inherited variable is read as evidence about *this*
process's fd 2), plus a documentation/implementation divergence on the log location
**Severity**: Medium. The daemon runs with **no log at all** — not on stderr, not in a file — whenever
it is auto-spawned from a process that was itself started by systemd. That is the ordinary case for a
desktop launch: the client inherits `JOURNAL_STREAM` from the user session's graphical target, and
passes it to the daemon it spawns. FR-046's whole point is that the log survives to be read after the
fact; here there is nothing to read, and no message says so.
**Feature**: `010-daemon-session-persistence` (FR-046 logging/diagnosability, research R2.3).
Observed on branch `docs/cleanup-completed-features`, pinned client+daemon `0.8.0` built 2026-08-20
**Reported**: 2026-08-25
**Status**: **Fixed** (2026-08-27)

## Description

Two separate findings about the same function, `micold_daemon::logging::init`.

### 1. `JOURNAL_STREAM` is treated as a fact about our own stderr

Reproduced in the sandbox. Launch the client — which auto-spawns the daemon — from a shell that
inherited `JOURNAL_STREAM`, and no log file is created:

```
$ ls "$XDG_DATA_HOME/micold-ai-ide/"
projects/  settings.json          # no micold-daemon.log
```

Relaunch with the single variable removed and the file appears immediately, first line included:

```
$ env -u JOURNAL_STREAM …/micold-ai-ide &
$ head -1 "$XDG_DATA_HOME/micold-ai-ide/micold-daemon.log"
… micold_daemon::logging: logging initialised sink=File log_path=Some("…/micold-daemon.log")
```

Nothing else differed between the two launches. Because the daemon is detached, its stderr goes to
the client's redirect (`/dev/null` in a real desktop launch), so choosing `Journald` here means
choosing to discard every line.

### 2. The documented log path is not the implemented one

| | Path |
|---|---|
| research R2.3, quickstart S13 step 3 | `~/.local/state/micold-daemon/logs/` (`state_dir()`) |
| `logging::default_log_path` (`crates/micold-daemon/src/logging.rs:185-188`) | `~/.local/share/micold-ai-ide/micold-daemon.log` (`data_dir()`) |

`ls -l ~/.local/state/micold-daemon/logs/` — the command the quickstart gives — returns "No such file
or directory" on a working install. Anyone following the walkthrough concludes the logging is broken
when it is merely elsewhere.

## Root Cause Analysis

`crates/micold-daemon/src/logging.rs:205`:

```rust
// systemd sets JOURNAL_STREAM on units whose stdout/stderr go to the journal; the journal
// supplies timestamps and metadata, so ours would be redundant noise.
if std::env::var_os("JOURNAL_STREAM").is_some() {
```

The comment is right about what systemd does and wrong about what the check proves. `JOURNAL_STREAM`
is an **inherited environment variable**, not a property of the current fd 2: it survives every
`fork`/`exec` down the tree, including into a child whose stderr the parent has redirected somewhere
else entirely. Presence therefore means "some ancestor's stderr went to the journal", which says
nothing about ours.

systemd's own documentation specifies the check this code is missing. `JOURNAL_STREAM` carries
`device:inode` of the journal stream, and the contract is to compare it against `fstat()` of the
descriptor in hand — that comparison is exactly what distinguishes "my stderr *is* the journal stream"
from "an ancestor's was". `sd_journal_stream_fd(3)` states it: *"applications may check whether their
standard output or standard error output match this value"*.

Note the ordering makes the consequence worse: the `JOURNAL_STREAM` branch comes **before** the
`io::stderr().is_terminal()` branch, so it wins even in a terminal, and before the file sink, so it
wins over the case it should have deferred to.

For finding 2, `data_dir()` vs `state_dir()`: R2.3 chose `state_dir()` deliberately and recorded the
reason (*"Not `cache_dir()` — cache is defined as safely deletable and cleaners do delete it, eating
logs mid-investigation"*). `data_dir()` is not subject to that hazard, so the implementation is not
*unsafe* — it simply is not what the research and the quickstart say, and it also drops the `logs/`
subdirectory the rotation files were meant to live in.

## Fix

Compare, do not merely detect:

```rust
fn stderr_is_journal_stream() -> bool {
    let Some(v) = std::env::var_os("JOURNAL_STREAM") else { return false };
    let Some((dev, ino)) = v.to_str().and_then(|s| s.split_once(':')) else { return false };
    let (Ok(dev), Ok(ino)) = (dev.parse::<u64>(), ino.parse::<u64>()) else { return false };
    std::fs::metadata("/proc/self/fd/2")   // or `fstat(2)` via rustix
        .map(|m| m.dev() == dev && m.ino() == ino)
        .unwrap_or(false)
}
```

Then either move `default_log_path` to the `state_dir()`-based helper R2.3 specifies (with the
`cfg`-matched macOS/Windows arms it calls for), or amend R2.3 and quickstart S13 to document
`data_dir()`. One of the two has to move; today a reader following the spec looks in an empty
directory.

## Regression Test

- Unit: a `stderr_is_journal_stream` test asserting `false` for a `JOURNAL_STREAM` value naming a
  device/inode pair that is not fd 2's — the exact inherited-variable case above. It is a pure
  function of the variable and one `fstat`, so it needs no daemon.
- Integration: spawn the daemon detached with `JOURNAL_STREAM` set and stderr on a pipe, and assert
  the log file exists. `logging::init` already reports its choice (`sink=… log_path=…`), so the
  assertion has something to read.

## Evidence

- `evidence/` — the two-launch contrast is reproduced in the T084 quickstart record.
- `crates/micold-daemon/src/logging.rs:200-221` (the branch), `:185-188` (the path).
- Related: BUG-015's finding 2 is why S13's *content* check (no session text in the log) had to be

## Resolution (2026-08-27)

Both findings are fixed, on branch `fix/bug-015-journal-stream`.

### 1. Compare the stream, do not detect the variable

`logging::init` now asks `stderr_is_journal_stream()` instead of
`std::env::var_os("JOURNAL_STREAM").is_some()`. That helper does what `sd_journal_stream_fd(3)`
specifies: it parses the `device:inode` value and compares it against `fstat(2)` of the descriptor
**we** hold on fd 2 (`names_this_stream`, `crates/micold-daemon/src/logging.rs:214-230`). An
inherited value now names some ancestor's stream, fails the comparison, and the daemon falls through
to the file sink — which is the whole point of FR-046.

`fstat` on the fd in hand, rather than `metadata("/proc/self/fd/2")` as the report suggested: the
`/proc` path resolves through the symlink to the *target* file, so it would return the journal
socket's own device and inode for a descriptor that is merely open on it — and it needs `/proc`
mounted. The syscall answers the question directly. A value we cannot parse is **not** a match: the
fallback is a log we can read, so an unreadable value costs nothing and systemd stays free to change
the format.

Only `stderr` is compared, not `stdout`. The daemon writes diagnostics to stderr and nothing else,
so stdout's destination cannot make journald the right sink here.

### 2. The path: `data_local_dir()`, and R2.3 amended rather than the code moved

R2.3 asked for `state_dir()`; the code used `data_dir()`. The code moved one word, to
`data_local_dir()`, and **R2.3 was rewritten to match** — with the reasoning recorded there rather
than silently changed:

- The sandbox (feature 027) binds the host's **data** dir into the container as
  `STATE_CONTAINER_DIR`. A log under `state_dir()` would land outside that mount, invisible from
  inside the container, and would break the sandbox's diagnosability story along with six
  integration tests that read the log through it.
- `ProjectDirs::state_dir()` is `None` on macOS and Windows, so two of three targets would need a
  hand-written fallback anyway.
- R2.3's only *safety* rule is the one it argued for: never `cache_dir()` (cleaners delete it), and
  never a roaming profile (logs must not sync). `data_local_dir()` satisfies both on every target;
  on Windows `data_dir()` **is** the roaming one, which is the one-word bug.

quickstart S13 now names `~/.local/share/micold-ai-ide/micold-daemon.log*` and adds the quicker
check: the daemon states its own choice on its first line (`sink=File log_path=Some("…")`), and a
`sink=Journald` from an auto-spawned daemon means the log is being discarded.

The integration file is `#![cfg(target_os = "linux")]`; `JOURNAL_STREAM` is systemd's, and the
`device:inode` identity it encodes has no meaning elsewhere.

### Probes

`cargo test` stops at the first failing target and the lib's tests run before `tests/`, so each
probe ran the two targets as **separate** invocations.

| # | Reverted layer | Result |
|---|---|---|
| A | `stderr_is_journal_stream()` → `var_os("JOURNAL_STREAM").is_some()` — the reported defect exactly | `logging_sink.rs:90` — no log file |
| B | the branch → `if false` — never journald, the over-correction | `logging_sink.rs:117` — the daemon logged nothing to its stderr |
| C | compare the inode only, drop `st_dev` | **passed everything** — see below |
| D | an unparseable value returns `true` | `logging.rs:408` (now `:445`) |
| E | `data_local_dir()` → `data_dir()` | **passed everything** — see below |

**Probe C exposed a real gap.** Inode numbers are only unique within a filesystem, so dropping the
device comparison is a genuine weakening, and every gate then written still passed. The fix was a
new gate — `the_device_half_of_the_comparison_is_not_optional` — after which the same revert fails
at `logging.rs:414` (`:413` at HEAD). That is the only probe here that changed the fix.

**Probe E found no failure, and that is honest rather than fixed.** On Linux `data_dir()` and
`data_local_dir()` are the same directory, so on the machine this suite runs on the revert is a
no-op and nothing local can gate it. `the_log_never_lands_in_the_roaming_profile` is
`#[cfg(windows)]` and therefore only runs in the `build + test (windows-latest)` CI job — that job
is the gate for this half, and no Linux run will ever catch a regression of it.

### Not re-run on a display

The two-launch contrast in the original report came from a sandboxed GUI run. This fix was not
re-walked there; the integration gate spawns the real daemon binary with the same environment shape
(inherited `JOURNAL_STREAM`, stderr redirected elsewhere) and asserts the same observable, which is
what made the finding reproducible in the first place.
