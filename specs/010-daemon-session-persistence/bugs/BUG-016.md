# Bug Report: a service restart resumes an agent unasked — the client auto-starts the boot-restored session, defeating FR-006b

**Type**: Cross-feature contradiction between two features' functional requirements, resolved in code
in favour of one of them without either spec recording the loss
**Severity**: Medium–High as a *specification* defect. The behaviour itself may well be what a user
wants; what is wrong is that `010`'s stated safety property — "a service restart must never cause an
agent to take action unasked" — is written down as holding and does not hold. An agent that resumes
on its own reads the conversation, can call tools, and costs tokens, so the guarantee is not
cosmetic, and quickstart S5 asserts it as *the* safety property of User Story 6.
**Feature**: `010-daemon-session-persistence` (FR-006a/b, quickstart S5) — conflict with
`025-last-session-memory` (FR-004a, its BUG-002). Observed on branch `docs/cleanup-completed-features`,
pinned client+daemon `0.8.0` built 2026-08-20
**Reported**: 2026-08-25
**Status**: **Settled** (2026-08-27) — decided as option (1), with (3)'s narrowing folded in; no product code changed

## Description

Quickstart S5, run headlessly on Xvfb `:83`:

1. Two sessions in project `r10`, one displayed (`4d1b3702…`), one not (`f911c1f1…`), both running.
2. `kill -9` the daemon, then start a client again.

**Expected** (S5): both sessions come back in a distinct interrupted-resumable state, **no agent
process is auto-relaunched**, and a single explicit action resumes each.

**Observed**: split.

- The **non-displayed** session behaves exactly as specified. It renders with the
  `InterruptedResumable` tint (`ui/sidebar.rs:493-505` — a `r.primary` purple label, plainly distinct
  from a Running one), the pane says *"This session is not running. Choose restart below to resume
  it."*, and no process exists for it until one deliberate click produces
  `session started session=f911c1f1-… launch=Resume`.
- The **displayed** session is resumed with no user action at all. The daemon log shows
  `claude --resume 4d1b3702-…` spawning seconds after the client attaches, before any input reaches
  the window.

Reproduced twice: once with the client left running across the daemon kill, and once from a
completely fresh client process, so it is not a stale in-memory view.

The daemon half of FR-006a/b is **correct and not implicated**. `server.rs:60-77` marks every
recovered session `InterruptedResumable` — commented as "the ONLY lifecycle daemon startup may
produce (data-model L4)" — and `catalog.rs:554-580` (`present_interrupted_resumable`) loads durable
sessions `Idle` and flips only those with a recorded conversation. The daemon relaunches nothing. The
start request comes from the client.

## Root Cause Analysis

`crates/micold-client/src/shell/daemon_sync.rs:635-649`, on the attach path:

```rust
match app.core.active_session {
    // Feature 025 restored a session at boot. Displaying it means *starting* it,
    // exactly as selecting it by hand does (FR-004a, contract §3.3a) — BUG-002.
    Some(session) => view_and_start(app, session),
    None => daemon.send(ClientMsg::SetViewedSession { project, session: None }),
}
```

`view_and_start` (`daemon_sync.rs:1214`) sends `send_pane_size`, then
`ClientMsg::SessionStart { session }`, then `SetViewedSession`. The `SessionStart` is the unasked
action.

This is deliberate, and its reasoning is sound in its own frame. `025`'s BUG-002 superseded FR-004
("Restoring a session MUST NOT start, resume, or otherwise change any process") with **FR-004a**
("Restoring a session MUST bring it up the same way selecting it by hand does, **including resuming
its process when it is not running**"), because the old rule contradicted FR-003's "matching what
selecting the session by hand does" — and selecting by hand resumes. `025` even asked itself the
question directly and recorded the answer:

> Q: FR-004 existed to stop a launch running processes the user did not ask for. What is left of that
> protection? → A: The scope, not the prohibition. A launch resumes **exactly one** session — the one
> the user was looking at when they quit — and touches no other session's run state.

So `025` knowingly traded the prohibition for a scope limit. What it did not do is notice that the
prohibition it was trading away is also written, unqualified, in `010` FR-006b:

> The restart supervision of FR-005 applies only to a process that exits while the service is
> running. It MUST NOT be triggered by service startup, so a **service restart can never cause an
> agent to take action without the user asking for it**.

Both sentences are current. Only one of them describes the build. Note the two are not even about the
same actor — FR-006b constrains the *service*, and the service obeys it; the client then does the
thing the service was forbidden to do, which is how the gap stayed invisible to `010`'s tests.

## Fix

A decision first. Three coherent outcomes:

1. **Accept `025`'s trade and amend `010`.** Rewrite FR-006b to constrain what it actually
   constrains — *the service* MUST NOT relaunch on startup, and supervision MUST NOT be triggered by
   startup — and state explicitly that the client may resume the single restored session per
   `025` FR-004a. Rewrite quickstart S5's expectation to match: the *non-displayed* sessions are the
   ones that must stay processless. This is the smallest change and matches shipped behaviour.
2. **Distinguish a restore-after-crash from a restore-at-launch.** `025` FR-004a is about *the user
   quitting and coming back*. A daemon that was `kill -9`'d mid-session is a different event, and the
   user's last intent is less certain. Gate `view_and_start` on whether the attach follows a clean
   client start or a reconnect to a daemon that restarted underneath, and view-only in the second
   case. This preserves both specs' intent but adds a distinction neither currently makes.
3. **Keep the code, narrow the claim.** As (1), but also stop `010`'s User Story 6 from calling this
   "the safety property" — the property that survives is *scope* (at most one session, in one
   project), which is worth stating precisely because it is the one that is true.

Recommendation: **(1)**, with (2) recorded as a follow-up question rather than built speculatively.
The behaviour has a deliberate rationale and a bug report behind it; what needs fixing today is a spec
that promises otherwise.

Whichever is chosen, the two specs must cross-reference each other. `025`'s FR-004a should name
`010` FR-006b as the requirement it supersedes at this seam, the way it already names its own FR-004.

## Regression Test

Whatever (1)–(3) decides, the property is testable at the client without a GUI: attach against a
daemon whose catalog reports both sessions `InterruptedResumable`, and assert on the `ClientMsg`
sequence — exactly one `SessionStart`, naming the restored session and no other. That is the scope
guarantee `025` says survives, and nothing currently pins it from `010`'s side.

## Resolution (2026-08-27)

### The decision

**Option (1)**, taken with **(3)** folded into it rather than kept as an alternative. (3) is not a
different outcome — it is the sentence (1) cannot be written honestly without. Rewriting FR-006b to
constrain the service while leaving quickstart S5 calling the old prohibition "the safety property"
would move the false claim rather than remove it, so both were rewritten in one pass, and so were the
two other places that stated it: data-model **L4** and User Story 6's third acceptance scenario.

**Option (2) is deferred, not declined**, and is recorded where a future reader will meet it — a new
Clarifications session in `spec.md` dated 2026-08-27. The distinction it proposes (a restore after a
crash is not the same event as a restore at launch) is real, but nothing in either feature makes it
today, and building it would add a client-side notion of *why am I attaching* that no other behaviour
needs. The evidence that would justify it is a user reporting an unwanted resume after a crash; that
report does not exist.

### No code changed

Worth stating plainly, because a bug report that ends without a diff usually means someone gave up.
The daemon obeys FR-006b exactly — `server.rs` marks every recovered session `InterruptedResumable`
and `catalog.rs` relaunches nothing — and the client's resume is the behaviour `025` FR-004a asks for,
argued for in that feature's own BUG-002 and its clarifications. The defect was that `010` promised
otherwise. The fix is the promise.

This is also why `010`'s suite could not have caught it, and the amended text now says so: FR-006b
named the *service*, the service complied, and the client — the actor that sends the `SessionStart` —
was outside the requirement's own scope. A green suite was consistent with the words; the words were
wrong.

### What the specs say now

| Where | Was | Is |
|---|---|---|
| `010` FR-006b | "a service restart can never cause an agent to take action without the user asking for it" | the *service* relaunches nothing on startup; the client resumes the one session the reopened project displays (`025` FR-004a), and no other session changes run state |
| `010` quickstart S5 | "no agent process is auto-relaunched" — "this is the safety property" | count the agent processes: at most one new one, belonging to the session on screen; every other session stays interrupted-resumable with nothing behind it |
| `010` US6 scenario 3 | "when the user opens a session that was live before the restart … it is not silently relaunched" | every pre-restart session needs one explicit action, *except* the restored one, for which opening the project is that action |
| `010` data-model L4 | "a service restart can never cause an agent to act unasked" | startup produces only `InterruptedResumable`; that invariant is what keeps the client's resume a bound of one rather than one per remembered session |
| `010` Clarifications (2026-07-20) | "never auto-resumed" | qualified: never auto-resumed *by the service* |
| `025` FR-004a | superseded this feature's own FR-004 | also names `010` FR-006b as a prohibition it supersedes at this seam, and says amending either means amending both |

### Gate

| Gate | Where | Holds |
|---|---|---|
| `a_service_restart_resumes_only_the_session_being_restored` | `micold-client/src/main.rs` | attaching to a catalog in which *every* session is `InterruptedResumable` sends exactly one `SessionStart`, naming the restored session |

This is the test the report asked for, and it is not the one already there.
`connecting_starts_only_the_session_it_restores` (feature `025`) makes the same claim from `025`'s
side but with the same-project neighbour `Idle` — a session nobody had started. The case a service
restart actually produces is the one where the neighbour was *running* and came back interrupted, and
that is where an over-eager restore would resume it. Both sessions in the reopened project are
`InterruptedResumable` here, plus one in another project, and the assertion is on the whole
`SessionStart` sequence rather than on its first element.

### Probes

Each mutation applied to `HEAD`, the gate run on its own, then `git checkout -- crates/`.

| Probe | Mutation | Result |
|---|---|---|
| A | the attach path starts every `InterruptedResumable` session in the attached project | gate **failed** — 2 starts, `[restored, interrupted_neighbour]` |
| B | the attach path starts every `InterruptedResumable` session in the whole catalog | gate **failed** — 3 starts, the other project's included |
| C | the attach path views the restored session without starting it (`025` FR-004's old rule restored) | gate **failed** — 0 starts |

Probe C is the one that matters for the decision as much as for the gate: it is option (2)'s
behaviour applied unconditionally, and it breaks `025`'s `connecting_starts_the_restored_session_rather_than_only_viewing_it` at the same time. The two requirements really do point in opposite
directions at this seam, which is why the answer had to be a decision and not a fix.

### Not re-walked on a display

S5 was found by an operator on Xvfb `:83`. It has not been re-run. What that run observed — the
non-displayed session processless, the displayed one resumed — is now the *expected* result rather
than a split verdict, so the row it fails against no longer exists; but the amended row asks for a
process **count** across every session, and nobody has counted on a display.
