# Bug Report: the give-up reason is never recorded and the attempt count is a constant — a `Failed` session tells the user only that it failed

**Type**: Requirement not implemented, behind a ticked task. Three layers each drop part of the
payload; the wire format is the only one that still has a place to put it
**Severity**: Medium. The state itself is correct and visible — a failed session is unmistakably
distinct in the sidebar and its status bar reads `failed` with a `restart` control — so nothing is
broken or lost. What is missing is the *diagnosis*: after a crash loop that happened while nobody was
watching, the UI cannot say why or how many times it tried, which is precisely the information the
unattended case exists to preserve
**Feature**: `010-daemon-session-persistence` (FR-005, SC-012, quickstart S4, task T062). Observed on
branch `docs/cleanup-completed-features`, pinned client+daemon `0.8.0` built 2026-08-20
**Reported**: 2026-08-25
**Status**: **Fixed** (2026-08-26) — steps 1 and 2 of the Fix below; step 3 deliberately not, see
**Not in this fix**

**Fixed**: 2026-08-26 — the payload is carried the whole way, in the order the layers dropped it.
`SessionLifecycle::Failed { reason, attempts }` in the core, with the sentence assembled in
`on_unexpected_exit` — the one place that owns the budget, so the attended and unattended paths
cannot word it differently (SC-012). `ExitOutcome::Crashed { how }` carries the exit, because the
daemon is the only layer holding the status; `ExitOutcome::from_status` names a signal rather than
reducing it to the code `1` that `portable_pty` reports for one, and `PtySession` caches the outcome
instead of a success bit. `wire_lifecycle` maps both fields straight through and synthesises
neither; `catalog_sync::wire_to_lifecycle` keeps them. The enum loses `Copy`, which is what the
diff's breadth is — twenty call sites clone

The empty reason was not merely thin, and this is the part the report understated:
`catalog_sync::announce_start_failures` announces a failure **exactly when the wire reason is
non-empty** (feature 026, T088). So the crash-loop give-up — the one case that exists precisely
because nobody was watching — was the one case nothing said anything about. It is now announced

**Gate**: `crates/micold-daemon/tests/supervision_giveup.rs`, which already reached the give-up
state and asserted `attempts` against the constant. It now asserts the reason is non-empty, names
the exit, and names the attempt count — and then the **join**: the snapshot `welcome_payload` would
really publish, fed to the real `micold_client::catalog_sync::reconcile_catalog`, must surface that
sentence in the client's notification queue. Neither side can fail that on its own, which is the
shape three earlier bugs lived in (see `catalog_join.rs`'s header). `session_crash_restart.rs` gates
the wording at the FSM, where it is assembled

**Probes** (2026-08-26, each reverts one layer and runs only the gates that should catch it; all
five fail, each at the assertion it targets):

| Probe | Reverted | Fails at |
|---|---|---|
| A | `wire_lifecycle` synthesises an empty reason again | the non-empty reason (`supervision_giveup.rs:115`) |
| B | the FSM records the budget but not the exit | the exit in the sentence — core `:33`, daemon `:121` |
| C | `attempts` is a constant again (`0`) | the count — core `:26`, daemon `:106` |
| D | `PtySession` caches classification only, not the status | the exit in the sentence (`:121`) |
| E | the announcement's non-empty guard never matches | the join — the user is told nothing (`:139`) |

Probe D is the one worth stating: without it the sentence still reads correctly and still names the
budget, and only the diagnosis is missing — which is exactly the failure this bug is about, one
layer further down. Note also that the daemon-side `reason.contains('1')` is discriminating only
because `MAX_RESTART_ATTEMPTS` is 3; the core gate asserts the full `exit status 1`

**Not in this fix**, and both are named in the report:

- **Step 3, the display.** The status bar still reads the bare word `failed` — `session_status`
  returns `&'static str`, so showing the sentence there is a signature change and its own change.
  What the user gets today is the notification banner, which is more than the bar ever said.
- **Durability across a daemon restart.** `SessionLifecycle` is not persisted at all (its own doc
  says so, and `version_recovery.rs` gates records loading `Idle`), so a give-up survives an
  unobserved period and a reattach — the case the report observed — and not a restart of the
  service. FR-005's "durably" in that stronger sense needs the store schema

**Also changed**: BUG-024's gate hard-coded the old empty terminus in its expected walk. Its rung
assertion is unchanged; its terminus now checks an `attempts` that could not have differed from the
constant before this. Three doc comments that justified a design by "the domain `Failed` has nowhere
to put a message" were corrected rather than left to mislead — `state.rs`'s `start_failures` (which
stays separate for a different and better reason: a start that never reached a first process is not
a crash loop), `catalog_join.rs`'s T088 header, and `start_failure_notice.rs`'s empty-reason case.
`docs/daemon.md` now states what a give-up says and how long it lasts

**Whole suite**: green with the fix — 251 test binaries, `cargo fmt --check` and
`cargo clippy --workspace --all-targets -D warnings` clean

## Description

Quickstart S4, second half, run headlessly on Xvfb `:83` with a shim `claude` on `PATH` that exits
nonzero immediately (so no respawn can survive a 250 ms supervision tick and the counter accumulates):

```
08:32:05.180  INFO  session started    session=f911c1f1-… mode=AiCli launch=Resume
08:32:05.361  WARN  session crashed; restarting   reason="unexpected exit"
08:32:05.611  WARN  session crashed; restarting   reason="unexpected exit"
08:32:05.861  ERROR session gave up after repeated crashes (Failed)  reason="crash loop"
```

Two restarts then give-up — exactly the L1 note (`MAX_RESTART_ATTEMPTS = 3` yields **two** actual
restarts), one supervision tick apart. The client was then stopped, the daemon left alone for 20 s
with no observer, and a fresh client attached.

**Expected** (S4): *"on the next attach it shows the failed state with the reason and attempt
count"*.

**Observed**: the failed state survives the unobserved period and is presented — the sidebar label
switches to the error tint (salmon, distinct from the interrupted-resumable purple beside it) and the
status bar reads `failed  restart`. But **no reason and no attempt count appear anywhere**, and the
data to show them does not exist by the time the client sees the session.

The pane happens to show `shim: refusing to start (S4)` — that is the child's own stderr held in the
PTY, not the daemon's account of what it did. A session killed by a signal, which is the realistic
case, leaves no such line.

## Root Cause Analysis

The payload is dropped three times over.

**1. The core FSM has nowhere to put it.** `crates/micold-core/src/session.rs:65-82`:

```rust
Restarting { attempts: u8 },
/// Auto-restart gave up after repeated quick failures (FR-022a); user may retry manually.
Failed,
```

`Restarting` carries `attempts`; `Failed` is a unit variant. So the moment
`Session::on_unexpected_exit` settles `Failed`, the count it had been maintaining is discarded, and
no reason was ever captured — `supervise_exit` classifies the exit as `Clean`/`Crashed`
(`supervision.rs:15-33`) and keeps nothing finer, though the daemon *does* have the exit status in
hand at that point.

**2. The daemon synthesises both fields.** `crates/micold-daemon/src/catalog.rs:649-658` — and its own
doc comment says so:

```rust
/// The wire `Failed { reason, attempts }` carries a reason the in-process enum does not yet track;
/// a plain `Failed` maps with an empty reason here.
SessionLifecycle::Failed => WireLifecycle::Failed {
    reason: String::new(),
    attempts: micold_core::session::MAX_RESTART_ATTEMPTS,
},
```

`reason` is always empty. `attempts` is a **constant**, not a measurement: it is right by coincidence
for a crash loop, which gives up exactly at the maximum, and wrong for the other case the wire type
documents — *"Retries exhausted **or spawn failed**"* — where one failed spawn would be reported as
three attempts.

**3. The client throws away what does arrive.** `crates/micold-client/src/catalog_sync.rs:54`:

```rust
WireLifecycle::Failed { .. } => SessionLifecycle::Failed,
```

The client's core reuses `micold_core`'s unit `Failed`, so even a fully-populated wire message would
be flattened on arrival. `ui/terminal.rs` then renders the bare word `failed`.

The wire format (`protocol/messages.rs:612-618`) is the one layer that got it right. It was designed
for this and has been carrying two placeholder values ever since.

**Why the task is ticked.** T062 reads *"Surface the `Failed` state (reason + attempt count) in the
session list via `SessionSummary` (FR-016a `Ended`)"* and is marked `[X]`. The `SessionSummary` field
exists and the state is surfaced; the parenthesis never was. `supervision_giveup.rs:90` matches
`WireLifecycle::Failed { attempts, .. }` and asserts on `attempts` — against the constant, so it
passes without the count ever having been real, and `reason` is deliberately not asserted.

## Fix

Carry the payload the whole way, in the order the layers drop it:

1. `SessionLifecycle::Failed { reason: String, attempts: u8 }` in `micold-core`. `on_unexpected_exit`
   already knows the count; give `supervise_exit` the exit status so `ExitOutcome::Crashed` can carry
   a code/signal, and format the reason there — one place, shared by attended and unattended paths,
   which is what makes SC-012's "indistinguishable" hold for the reason too.
2. Delete the synthesis in `catalog.rs:649-658`; map the fields straight through. Persist them with
   the durable record, since FR-005 says *"record the give-up state **and reason** durably"* and the
   state currently outlives the process only in memory.
3. `catalog_sync.rs:54` keeps the fields; the status bar shows something like
   `failed — exited 1, 3 attempts`, and the empty-terminal message says the same at length beside the
   existing `restart` control.

Step 3 alone is worthless without 1 and 2 — there is nothing to display yet. Step 1 is the one that
matters and the only one that touches an FSM.

## Regression Test

`crates/micold-daemon/tests/supervision_giveup.rs` already reaches the give-up state; it needs to
assert on values that could differ from the constant. Add a case where the **first** spawn fails, so
the correct answer is `attempts: 1` — today that reports `3` and nothing catches it. Assert `reason`
is non-empty and names the exit status.
