# Bug Report: `ActivitySignal::Ended` is unreachable — a stopped session reads *unknown*, never *ended*

**Type**: Requirement not implemented. The state, the wire variant, the icon and the badge branch all
exist and are unit-tested; the one missing piece is the line that *emits* the event
**Severity**: Low-to-medium. Nothing is shown wrongly — a stopped session falls back to `Unknown`,
which draws nothing, so the H1 rule ("no answer beats a wrong answer") is still honoured. But
quickstart S3's third expectation cannot be met, one third of the badge's vocabulary is dead code
outside the showcase, and a stopped session is visually indistinguishable from a live one whose hooks
never fired
**Feature**: `010-daemon-session-persistence` (US2, SC-015/SC-016, quickstart S3). Observed on branch
`docs/cleanup-completed-features`, pinned client+daemon `0.8.0` built 2026-08-20
**Reported**: 2026-08-25
**Status**: **Fixed** (2026-08-27)

## Description

Quickstart S3 asks for three session states side by side in the list, and expects the third to read
*ended*:

> **Expected**: the waiting session reads *awaiting input*, the busy one reads *working* for the
> **entire** run with **zero** spurious flips to awaiting-input, and the stopped one reads *ended*.

Run headlessly on Xvfb `:83` with four sessions and a `claude` shim on `PATH` (so hooks could be
fired by `curl` against the daemon's real loopback receiver, at zero token cost), the first two
expectations hold exactly. The third does not. Session 4 was stopped cleanly —

```
2026-08-25T15:35:41.400104Z  INFO micold_daemon::state: session stopped
    session=42664d7f-4ccc-431f-9d5b-b2f1464b3412 reason="clean exit"
```

— 200 ms after its shim was told to exit 0, and its row went dim, as a stopped session should. But
**no badge is drawn in its slot at all**: the 9×9 patch at the badge's centre is the row background
alone, the same as session 3's, which never received a hook and is correctly `Unknown`.

## Cause

`ActivityEvent::Ended` has no producer in production code. Every `apply`/`note_activity` call site in
the workspace is one of two events:

| call site | event |
|---|---|
| `crates/micold-daemon/src/hooks.rs:254` | `ActivityEvent::Hook(kind)` |
| `crates/micold-daemon/src/state.rs:1108` | `ActivityEvent::SpinnerObserved` |

`ActivityEvent::Ended { reason }` is constructed only inside `activity.rs`'s own unit tests
(`activity.rs:176, 227, 243, 260`) and by the showcase's posed gallery
(`showcase/sections/atoms.rs:210`). Nothing in `state.rs`'s exit handling — neither the clean-exit
path nor `SupervisionAction::Stop` — applies it.

Compounding it, the fallback is `Unknown` rather than a stale signal: `state.rs:840` notes that a
session with no live entry keeps the catalog's values, and the catalog "never carries activity
(H3/A4)". So the moment the live entry is dropped, whatever the session last read is discarded. Even
if `Ended` were applied at exit, it would have to survive that drop to be visible on the row.

Everything downstream is already in place and needs no change:

- `ActivitySignal::Ended { reason }` — `activity.rs:47`, absorbing, tested
- `WireLifecycle`'s sibling `Ended` variant — `protocol/messages.rs:635`
- `Icon::ActivityEnded` — the hollow ring, `icons.rs:85`
- the badge branch — `activity_badge.rs:96`, `on_surface_variant`, unit-tested at `:131`

## Impact

- Quickstart S3's third clause cannot pass, and neither can the part of SC-015/SC-016 that rests on it.
- The hollow-ring badge is reachable only in the showcase, so a visual regression in it would never
  be caught by using the app.
- A user scanning the list cannot tell "this session finished" from "this session never reported" —
  both draw nothing. The first is a fact worth showing; the second is deliberately silent.

## Suggested fix

Apply `ActivityEvent::Ended { reason }` where the daemon already logs `session stopped` and where
`SupervisionAction::{Stop, GiveUp}` are dispatched (`state.rs:1010-1062`), reusing the same `reason`
string it logs — then make the signal outlive the live entry, either by persisting the last activity
onto the catalog summary for stopped sessions or by deriving `Ended` at snapshot time from a
lifecycle that is no longer running.

The second half is the design question worth settling first: **is *ended* an activity signal at all,
or is it a projection of lifecycle?** The FSM treats it as the former (absorbing state, carries a
reason); the persistence rule H3/A4 — "the catalog never carries activity" — assumes the latter.
Deriving it at snapshot time from `SessionLifecycle` would satisfy both without weakening H3, and
would cost one match arm rather than a new persisted field.

## Reproduction

1. Start two sessions; leave both without hooks.
2. Stop one of them (clean exit).
3. Look at the sidebar rows.

**Actual**: neither row draws a badge; the stopped one is distinguishable only by its dimmed label.
**Expected**: the stopped row draws the hollow `on_surface_variant` ring.

## Evidence

`specs/010-daemon-session-persistence/evidence/S3-activity-badges.png` — rows 1–4 as
*working* (filled `primary`), *awaiting input* (filled `error`), *unknown* (nothing), *stopped*
(nothing, where the ring is expected).

## Resolution (2026-08-27)

Fixed on branch `fix/bug-018-activity-ended`, daemon-side only — nothing on the wire or in the
client changed, because everything downstream was already in place (as the report found).

### Where the signal comes from

The two supervision outcomes that stop a session for good — a clean exit (`SupervisionAction::Stop`)
and a crash-loop give-up (`GiveUp`) — now call `DaemonState::note_ended`, immediately before the live
entry is dropped and beside the `session stopped` / `session gave up` log lines they already emit.
It applies `ActivityEvent::Ended { reason }` to the session's own FSM and keeps what the FSM
returns, so `Ended`'s absorbing rule still decides the result rather than the call site.

`reason` is the tick's own one-word account of the outcome — `"clean exit"`, `"crash loop"` — the
same word the log line carries. The detailed give-up sentence is deliberately **not** copied here:
it lives on `SessionLifecycle::Failed { reason, .. }`, which the client already reads (BUG-017), and
two copies of one sentence are two things that can disagree.

### Where it survives

A new runtime-only `Inner.ended: HashMap<SessionId, ActivitySignal>`, projected in
`overlay_live_summaries` for a summary with **no** live entry. This is the same shape as
`start_failures` beside it: a per-session fact about this daemon right now, never persisted, so
activity still resets to `Unknown` on a daemon restart (H3/A4).

It is cleared when the session runs again (`register_session`) and when it leaves the catalog for
good (`remove_live_by_ids` — the archive/forget paths).

### The design question the report raised

> **is *ended* an activity signal at all, or is it a projection of lifecycle?**

Deriving it from the lifecycle would have needed no new field, and it does not work: a clean exit
leaves the session `Idle`, and so does a session that was **created and never started**. Deriving
`Ended` from `Idle` would put a "finished" ring on a session that has never run — the invented state
H1 exists to forbid. `Failed` alone is unambiguous, but covering only the crash-loop half would
leave S3's actual case (a session that exited cleanly) still drawing nothing.

The alternative — a new `SessionLifecycle::Stopped` variant, mapped to `WireLifecycle::Idle` so
nothing on the wire changes — would model it cleanly, but it adds a variant to an enum shared with
the client that the client can never receive, and touches every exhaustive match on it in both
crates. Not worth it for this; if a stopped session ever needs to *read* differently from a
never-started one in the UI, that is the change to make, and it is a wire change, not this one.

### Gates

| Gate | File | Asserts |
|---|---|---|
| `a_session_that_exited_cleanly_reads_ended_and_says_why` | `tests/activity_ended.rs:78` | a real process exits 0, one supervision tick runs, and the published snapshot reads `Ended` (`:90`) with a non-empty reason (`:96`) |
| *(same gate, second half)* | `:102` | the **over-correction**: a session in the same project that was never started still reads `Unknown` |
| `a_new_run_does_not_inherit_the_previous_run_s_ending` | `tests/activity_ended.rs:107` | after stop → start, the row reads `Unknown` while running (`:129`), and still `Unknown` (`:140`) once the live entry is dropped without a producer |
| `a_crash_loop_settles_failed_and_drops_the_session` | `tests/supervision_giveup.rs` | extended: after the give-up the row reads `Ended { reason: "crash loop" }` (`:144`) |

The second gate drops the live entry via `remove_session` — the `SessionKill`/`SessionStop` handler's
path, which has no producer of its own. `Unknown` there is the correct answer, not a gap being
papered over: nothing observed *that* run ending, and H1 says no answer beats an answer about the
wrong run. (Today no client sends either message, so the path is reachable only from the daemon's
own API.)

### Probes

Each probe reverts one layer and runs the two targets as separate `cargo test` invocations.

| # | Reverted layer | Result |
|---|---|---|
| A | both `note_ended` call sites removed — the reported defect exactly | `activity_ended.rs:90` and `supervision_giveup.rs:144` |
| B | apply `Ended` to the live FSM but do not retain it past the live entry | same two assertions — the retention is what makes it visible |
| C | retain it but never project it onto the snapshot | same two assertions |
| D | never clear it when the session runs again | `activity_ended.rs:140` — see below |
| E | over-correction: any session with no live entry reads `Ended` | `activity_ended.rs:102` — the never-started session |
| F | do not forget the ending when the session is archived | **passed everything** — see below |

**Probe D changed a gate.** On its first run it passed: the original second gate only asserted that
a *running* session reads `Unknown`, and a live entry shadows the retained signal anyway, so the
clear was unobservable. The gate was rewritten to drop the live entry afterwards without a producer,
which is where a stale ending would actually surface; the same revert then fails at `:140`.

**Probe F found no failure, and there is nothing to fix.** An archived session has no summary in the
snapshot, so a leftover map entry cannot be observed — it is bounded hygiene (one entry per session
that ever ended, freed when the session is deleted), not behaviour. That line is uncovered and this
records it rather than implying otherwise.

### Not re-run on a display

The original finding came from an Xvfb run reading the 9×9 patch at the badge's centre. This fix was
not re-walked there: the gates read the same `ActivitySignal` the badge is drawn from, off the
snapshot the daemon really publishes, and `activity_badge.rs` already unit-tests the `Ended` branch
that turns it into the hollow ring.
