# Bug Report: the hostile-`/tmp` refusal never fires — `resolve()` chmods the directory before verifying it

**Type**: Requirement not implemented, behind a green unit test. The verifier is correct; it is
called one line too late, and the test calls it directly rather than through the code path that
would reveal this
**Severity**: Medium. The immediate outcome is safe-ish — a loose directory is *tightened* rather
than bound loose — but the quickstart's stated requirement ("**MUST bail loudly, not bind anyway**")
is not met in either hostile case, and the wrong-owner case degrades from a specific, actionable
message to a bare `EPERM` from `chmod`
**Feature**: `010-daemon-session-persistence` (FR-004, quickstart S11 third block, protocol.md §2).
Observed on branch `docs/cleanup-completed-features`, pinned client+daemon `0.8.0` built 2026-08-20
**Reported**: 2026-08-25
**Status**: **Fixed** (2026-08-27)

**Fixed**: 2026-08-27 — the verifier now runs on the directory *as found*, and never after a repair.

`guard_predictable_dir` replaces the `ensure_dir_mode` + `verify_owned_0700` pair on the `/tmp`
path. It distinguishes the two cases atomically instead of collapsing them:
`fs::DirBuilder::new().mode(0o700).create(dir)` either makes the directory — locked down at
creation, so there is no window where it exists loose — or returns `AlreadyExists`, and *either way*
`verify_owned_0700` is the only way past the function. Nothing chmods a directory it did not just
create. `ensure_dir_mode` stays for the XDG and `$HOME` branches, where the parent is already ours
and unconditional repair is sound; its doc comment now says which branch is which, since the
distinction is the whole defect.

The fresh directory is verified too, which is not redundant: `mkdir`'s mode argument is masked by
the umask, so a `0700` umask would leave the new directory `0000`. Cheap, and it means the rule is
"the verifier decides", with no exceptions to remember.

**The seam that makes it testable.** `resolve()` chose `/tmp/micold-<uid>` *and* guarded it in one
function, so the only way to drive the guarding was to make the machine's real
`/tmp/micold-<uid>` world-writable — next to a daemon that may be using it. The path choice is now
split from the guarding as `resolve_in_predictable_dir(dir)`, which is what the gates below call.
What that leaves uncovered is one line: the `format!("/tmp/micold-{}", euid())` above it. A reader
who wants that covered should know no test asserts it.

**Gates** — six, all in `crates/micold-core/src/endpoint.rs`:

| Gate | Asserts |
|---|---|
| `a_pre_existing_loose_directory_is_refused_not_repaired` | a `0777` directory is refused, the refusal names the mode it found, **and the directory is still `0777` afterwards** |
| `a_symlink_in_place_of_the_directory_is_refused` | a symlink to a directory that is ours and `0700` is refused as "not a directory" — the case `symlink_metadata` exists for |
| `a_directory_owned_by_someone_else_is_refused_by_owner_and_says_so` | the owner branch, which no test touched at all |
| `a_missing_directory_is_created_locked_down` | the ordinary first run: created, `0700`, endpoint returned |
| `a_directory_that_is_already_ours_and_locked_down_is_accepted` | the ordinary second run — refusing every pre-existing directory would be safe and useless |
| `a_loose_mode_is_rejected_by_the_verifier` | the predicate alone. Renamed from `wrong_owner_dir_bails_loudly`, which promised an owner check and performed a mode one |

Two of these deserve a note. The **second assertion** of the first gate is what separates the fix
from the defect: repair-then-verify also ends with the directory at `0700`, so a gate that only
checked the mode afterwards would pass against the bug. And the owner gate needs a directory owned
by another uid, which a test cannot create — so it reads `/`, root-owned on every machine this runs
on and creating nothing, and returns early when the suite itself runs as root, where `/` *is* ours
and the branch is genuinely unreachable.

**Probes** (2026-08-27, each reverts one layer and runs `cargo test -p micold-core --lib endpoint`;
all six fail, each at a gate that names the layer it reverted):

| Probe | Reverted | Fails at |
|---|---|---|
| A | `ensure_dir_mode` then `verify_owned_0700` — **the reported defect exactly** | the loose-dir gate's `expect_err`, `endpoint.rs:391` |
| B | `fs::create_dir` instead of `DirBuilder::mode(0o700)` — the new directory takes the umask's mode | `a_missing_directory_is_created_locked_down`, `:356` |
| C | the verifier dropped entirely | the loose-dir gate `:391` **and** the symlink gate `:422` |
| D | `AlreadyExists` chmods to `0700` before verifying — the same defect, written the other way round | the loose-dir gate `:391` |
| E | `fs::metadata` instead of `fs::symlink_metadata` | the symlink gate `:422`, and only there |
| F | verify first, refuse correctly — but tidy the directory up on the way out | `:406` only, `left: 448, right: 511` — i.e. `0o700` where `0o777` was expected |

Probe F is the reason the "left as found" assertion is there. A, C and D all fail before reaching
it, so without F it would be an assertion nothing had shown to be load-bearing; F is the plausible
implementation that refuses *and* repairs, and that assertion is the only thing in the suite that
notices.

**The spec said the checks, not their order.** protocol.md §1 listed the three verifications and
"any failure MUST bail loudly", which the old code satisfied vacuously — its failures were
unreachable, so there were none. §1 now requires verification to precede any repair and forbids
repairing a pre-existing directory at all, and quickstart S11's third block now asks that the
directory be left as found, since that is the part a reader walking it can actually observe.

**Not re-run on a display.** The reproduction that produced this report — `XDG_RUNTIME_DIR` unset,
a `0777` `/tmp/micold-1000`, a real client on Xvfb — has not been repeated. The gates drive the same
function `resolve()` calls, and both callers already surface its error loudly (the daemon logs
`could not resolve the endpoint to bind` at `error` and propagates; the client turns it into
`Message::DaemonConnectFailed`), but nobody has watched the refusal appear on a screen.

## Description

Quickstart S11's third block:

> Hostile directory (Linux `/tmp` fallback) — with `XDG_RUNTIME_DIR` unset and a wrong-owner or
> wrong-mode `/tmp/micold-<uid>`, startup **MUST bail loudly**, not bind anyway.

Run headlessly on Xvfb `:83`:

```bash
mkdir -p /tmp/micold-1000 && chmod 0777 /tmp/micold-1000
ls -ld /tmp/micold-1000        # drwxrwxrwx 2 jaro jaro
env -u XDG_RUNTIME_DIR ... micold-ai-ide
```

**Actual**: the client started normally, spawned a daemon (pid 930170), and bound
`/tmp/micold-1000/daemon.sock`. No error, no message, no refusal. The directory's mode was
**silently changed** to `0700`:

```
srwxrwxr-x 1 jaro jaro 0 daemon.sock
-rw-rw-r-- 1 jaro jaro 6 daemon.lock
drwx------ 2 jaro jaro 80 /tmp/micold-1000
```

**Expected**: a loud bail, naming the directory and its mode.

## Cause

`crates/micold-core/src/endpoint.rs:104-108`:

```rust
// Fallback: /tmp is world-writable and the path is predictable, so create-then-VERIFY.
let dir = PathBuf::from(format!("/tmp/micold-{}", euid()));
ensure_dir_mode(&dir, 0o700)?;
verify_owned_0700(&dir)?;
```

and `ensure_dir_mode` (`:56-59`) is unconditional:

```rust
fs::create_dir_all(dir)?;
fs::set_permissions(dir, fs::Permissions::from_mode(mode))
```

`create_dir_all` succeeds on an existing directory, and `set_permissions` then *overwrites* whatever
mode it had. By the time `verify_owned_0700` looks, the mode is always `0700` — so its mode branch
(`:83-93`), with the message "has mode {:#o}, expected 0o700 — refusing to bind", is **unreachable
on Linux** through `resolve()`.

The wrong-owner branch (`:69-80`) is unreachable for a different reason: `set_permissions` on a
directory owned by another uid fails with `EPERM` first, so `ensure_dir_mode`'s `?` returns a bare
"Operation not permitted" and the verifier's specific message — "owned by uid X, not Y — refusing to
bind" — is never produced either.

So the comment on line 104 states the intended order ("create-then-VERIFY") and the code implements
create-then-**overwrite**-then-verify, which cannot fail.

## Why the test suite does not catch it

`endpoint.rs:221-232`:

```rust
#[test]
fn wrong_owner_dir_bails_loudly() {
    // A dir with mode 0o755 (not 0o700) must be rejected by the /tmp verifier.
    ...
    let err = imp::verify_owned_0700(&dir).expect_err("loose mode must be rejected");
```

It calls `verify_owned_0700` **directly**, so it proves the predicate is right and says nothing about
whether `resolve()` ever reaches it with a loose mode. The name also promises more than it tests —
it says *owner*, and tests *mode*; no test covers the wrong-owner path at all (it needs a second
uid, which is why it was probably skipped).

## Impact

A predictable, world-writable path is the reason this verifier exists. The residual exposure after
the silent repair is narrow but real: anything an attacker placed inside the directory during the
window it was world-writable — a socket, a lock file, a symlink — survives the `chmod`, and the
daemon's stale-endpoint reclaim will then unlink and rebind over it rather than treat it as
suspicious. The loud bail exists precisely so that a human decides what to do with such a directory.

Note that this affects only the `XDG_RUNTIME_DIR`-unset fallback. On a normal desktop session
`XDG_RUNTIME_DIR` is set and the XDG branch is taken, which does not call the verifier at all (by
design — the XDG dir is already user-owned `0700`).

## Suggested fix

Verify before repairing, and make the repair conditional:

1. If the directory does not exist, create it `0700` — that path is safe and needs no verification
   beyond the create itself (use `create_dir` and treat `AlreadyExists` as the other branch, so the
   two cases stay distinguishable).
2. If it already exists, call `verify_owned_0700` **first** and propagate its error unchanged.

Then give `wrong_owner_dir_bails_loudly` a sibling that drives `resolve()` with `XDG_RUNTIME_DIR`
unset against a pre-created loose directory, which is what would have caught this. (It needs a
per-test root rather than the real `/tmp/micold-<uid>`; extracting the directory as a parameter is
enough to make the path testable.)

## Reproduction

```bash
mkdir -p /tmp/micold-$(id -u) && chmod 0777 /tmp/micold-$(id -u)
env -u XDG_RUNTIME_DIR micold-ai-ide
ls -ld /tmp/micold-$(id -u)     # now 0700; the app started anyway
```
