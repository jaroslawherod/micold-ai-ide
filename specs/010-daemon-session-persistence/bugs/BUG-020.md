# Bug Report: a mutation whose daemon dies mid-flight spins forever — the client never reaches "outcome unknown"

**Type**: Requirement not implemented. The reconnected *state* is correct; the pending *indicator* is
never resolved, so the one screen the user is looking at is the one that stays wrong
**Severity**: Medium. Nothing is lost or corrupted — the worktree really was created, and the sidebar
behind the dialog shows it correctly after reconnect. But the dialog claims the operation is still
running, indefinitely, and the only way out is Cancel, which reads like abandoning work that has in
fact already completed
**Feature**: `010-daemon-session-persistence` (SC-007/SC-008, User Story 3, quickstart S8 last row).
Observed on branch `docs/cleanup-completed-features`, pinned client+daemon `0.8.0` built 2026-08-20
**Reported**: 2026-08-25
**Status**: **Fixed** (2026-08-27)

## Description

Quickstart S8's last row:

| Trigger | Expected |
|---|---|
| `pkill -f micold-daemon` mid-worktree-creation | Client shows **outcome unknown**, then the actual state after reconnect — never a stale list or a silent success |

Run headlessly on Xvfb `:83`. To make the mutation long enough to interrupt deterministically, a
`post-checkout` hook that `sleep 12`s was installed in the sandbox repo — `git worktree add` runs it,
so the daemon's git child stays busy for a known window. Then:

1. New worktree → type `feat`, name `probe two` → **Create**. The dialog shows its pending state
   correctly: an indeterminate progress bar, "Creating branch and worktree", and a disabled Create.
2. Three seconds in, the daemon was `kill -9`ed **by pid** (17:52:24).

| moment | dialog | sidebar |
|---|---|---|
| +2 s | "Creating branch and worktree", bar animating | emptied |
| +6 s | unchanged | still empty |
| +31 s | unchanged | (behind the dialog) |
| +90 s | **unchanged** — bar still animating | — |

Meanwhile a replacement daemon had been spawned (pid 993411) and the client had reconnected, and the
worktree itself had been created on disk — `git worktree add` was a *child* of the killed daemon, so
`SIGKILL` to the parent did not stop it, and its sleeping hook ran to completion:

```
/home/jaro/.aaa-vp83d/r10/.claude/worktrees/feat-probe-two   07c3e24 [feat/probe-two]
```

Pressing **Cancel** dismissed the dialog and revealed a sidebar listing all three worktrees, *Probe
two* included — so the post-reconnect state is right. Only the dialog is wrong, and it is wrong
forever.

## What is missing

The mutation's pending state is tracked entirely in the client, keyed on a request that will never be
answered because the connection carrying it is gone. Nothing in the reconnect path walks the
outstanding mutations and marks them indeterminate.

The quickstart's phrase for the correct outcome is precise and worth keeping: **outcome unknown**.
Not "failed" — the operation may well have succeeded, as it did here — and not silence. The user
needs to be told the daemon went away mid-flight and that the list now shows whatever actually
happened.

## Impact

- The only failure mode S8 names as unacceptable is "a stale list or a silent success". This is the
  third thing: a stale *dialog* over a correct list, which is arguably worse, because it actively
  contradicts the truth sitting behind it.
- A user who trusts the dialog waits indefinitely; a user who cancels reasonably assumes the work was
  abandoned and may retry, which then fails with "a worktree folder named 'feat-probe-two' already
  exists" — a confusing end to a sequence in which they did nothing wrong.

## Suggested fix

On connection loss, resolve every in-flight mutation to an explicit *unknown* outcome rather than
leaving it pending: dismiss the progress state, show a message naming the operation and saying the
daemon restarted mid-flight, and point at the refreshed list as the authority. The list refresh
already works and needs no change.

Two smaller notes for whoever picks this up:

- The stale error text from a *previous* failed attempt stays on screen during the next attempt's
  pending state (visible in `s8/10-pending.png`); clearing it when a new submission starts is a
  one-liner and removes a genuinely confusing frame.
- A failed mutation logs nothing on the daemon side. The read-only-parent failure below produced a
  perfect message in the UI and no log line at all, which is a gap against S13 ("for each failure in
  S7, S8 and S11, confirm the cause is determinable from logs").

## What did pass, in the same session

Recording these so the fix does not disturb them:

- **Create a worktree on an already-checked-out branch** — prevented rather than attempted. The
  *Existing branch* tab says "No branches are available to reuse — every branch is already checked
  out", and annotates each row with why (`feat/side-work · in use by feat-side-work`, `main · in use
  by the project checkout`). The rows are inert; Create never enables.
- **Colliding path** — a specific app-level refusal before git is invoked: "A worktree folder named
  'feat-side-work' already exists." / "Choose a different name, or remove the existing folder first."
  No catalog entry, no directory, no git call.
- **Read-only parent** — git's own stderr preserved verbatim, including the command:
  ```
  git failed to create the worktree: git worktree add -b feat/readonly-probe
  /home/jaro/.aaa-vp83d/r10/.claude/worktrees/feat-readonly-probe HEAD failed: Preparing worktree
  (new branch 'feat/readonly-probe')
  ```

  No leftover directory, no phantom worktree entry.
- **Pending state and duplicate submission** — during the 12 s hook-slowed create, the bar animates,
  the label reads "Creating branch and worktree", and Create is disabled; a second click on it did
  nothing and exactly one worktree was created.

## Resolution (2026-08-27)

### Where the pending state actually lived

`on_disconnected` already drained `pending_ops` and raised one notification per op — that block
postdates this report and was, on its own, the right idea in the wrong place. Two things kept it from
being visible:

- **The form's pending state is separate.** `WorktreeFormStatus::Creating` lives on
  `State::worktree_form`, and the drain never touched it. `ui/worktree_form.rs` mounts the
  indeterminate `StageProgress` on that field alone, and an indeterminate indicator has no target to
  arrive at — it asks for a frame on every frame it exists (feature 018, FR-039d). So the bar did not
  merely look stuck; the application never returned to rest.
- **The notification is invisible here.** The add-worktree form is a modal, and a notification is
  raised into the surface its scrim covers. `OperationError`'s own arm says so in as many words and
  routes the two branch queries to the form's error line for exactly this reason.

So resolving the op had to resolve the *indicator*, and had to do it where the user was looking. A
`WorktreeCreate` whose connection drops now goes through the form:

```rust
PendingOp::WorktreeCreate(_) if app.core.worktree_form.is_some() => {
    app.core.update(Message::WorktreeForm(FormMsg::CreateInterrupted(text)));
}
_ => app.core.notify_error(text),
```

The guard is not decoration. With no form on screen there is no scrim, and the notification is the
right place — a create whose form the user had already cancelled would otherwise be reported
nowhere (probe C).

### Why the message is a new field and not `worktree_error`

`WorktreeForm::interrupted`, not the existing error line, because `State::set_worktrees` reports
`WorktreesReplaced` **unconditionally** and the root's arm clears `worktree_error` on it (T067a-4).
That clear is right for a create failure shown against a list that has since changed, and exactly
wrong for this message, whose whole content is *the list is the authority now*: reconnection follows
the drop within a second or two, so the notice would have been cleared by the very refresh it points
at, roughly one and a half seconds after appearing (probe B).

It is also rendered muted rather than tinted `error`. The operation may well have succeeded — in the
reported case it had — and colouring it as a failure would state something the client does not know.
`create_interrupted` leaves every input alone for the same reason: a drop is not a reason to discard
what the user typed (FR-007), and it may be a retry they want.

### The two smaller items

- **The stale error.** `create_started` now clears `State::worktree_error`. The previous attempt's
  error used to stand through the whole of the next attempt's pending state — an error line and an
  animating progress bar on screen together, describing different attempts.
- **The missing log line (S13).** `server.rs` has twenty-five `OperationError` sites and none logged,
  so the read-only-parent failure produced a perfect message in the UI and nothing on the daemon
  side. Logging at each site is twenty-five chances to forget, so the line is emitted where they all
  converge — `DaemonState::send` — and carries `detail`, usually the only part that names the cause
  (git's own stderr). It is a `warn!`, so it also lands in the recent-errors ring the diagnostics
  panel shows, which is what "reachable through the UI" asks for. `detail` is never terminal content
  or session input, the only thing FR-047 forbids; `tests/log_redaction.rs` still passes.

### Gates

| Gate | Where | Holds |
|---|---|---|
| `a_create_whose_connection_drops_stops_claiming_to_be_running` | `micold-client/src/main.rs` | a drop takes the form out of `Creating` and names the operation |
| `the_unknown_outcome_survives_the_list_refresh_it_points_at` | same | the notice outlives `set_worktrees` |
| `a_disconnect_with_no_create_in_flight_leaves_the_form_alone` | same | nothing in flight invents no notice, and keeps the typed inputs |
| `a_create_with_no_form_open_is_still_reported` | same | with no scrim, the notification is still raised |
| `a_new_attempt_does_not_show_the_previous_attempts_error` | same | a new create clears the last one's error |
| `a_create_whose_connection_dropped_stops_its_indicator` | `micold-client/tests/indeterminate_stops_with_its_operation.rs` | the real view stops asking for frames — the reported symptom, at frame level |
| `a_refused_mutation_says_so_in_the_log` | `micold-daemon/tests/refused_mutations_are_logged.rs` | a refusal driven over a real connection is logged, with its `detail` |

### Probes

Each mutation applied to `HEAD`, the named target run on its own, then `git checkout -- crates/`.

| Probe | Mutation | Result |
|---|---|---|
| A | `on_disconnected` does not route the create through the form | `a_create_whose_connection_drops_stops_claiming_to_be_running` **failed** |
| B | the notice is written to `worktree_error` instead of its own field | `the_unknown_outcome_survives_the_list_refresh_it_points_at` **failed** |
| C | the `worktree_form.is_some()` guard is dropped | `a_create_with_no_form_open_is_still_reported` **failed** |
| D | every disconnect resolves the form, in flight or not | `a_disconnect_with_no_create_in_flight_leaves_the_form_alone` **failed** |
| E | `create_started` does not clear the stale error | `a_new_attempt_does_not_show_the_previous_attempts_error` **failed** |
| F | `DaemonState::send` logs nothing for an `OperationError` | `a_refused_mutation_says_so_in_the_log` **failed** |
| G | the log line drops `detail` | same gate **failed**, on its second assertion |
| H | `create_interrupted` records the notice but leaves the form `Creating` | `a_create_whose_connection_dropped_stops_its_indicator` **failed** |

**Probe A does not break the frame-level gate**, and that is worth stating rather than hiding: A
mutates the shell's routing, while that gate drives `State` directly through `Msg::CreateInterrupted`.
It gates the reducer, not the wiring. Probe H is the one that holds it — remove the `status` reset and
the real view goes on asking for frames for ever, which is the reported symptom exactly. The two
probes together cover the path end to end; neither covers it alone.

### Not re-walked on a display

S8's last row was found by an operator on Xvfb `:83` with a `post-checkout` hook slowing the create.
The fix has not been re-run that way. What is asserted here is the client's and daemon's own
behaviour under a dropped connection, driven in-process; the walkthrough's `pkill -f micold-daemon`
mid-creation has not been repeated.
