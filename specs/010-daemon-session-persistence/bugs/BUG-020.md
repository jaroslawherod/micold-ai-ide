# Bug Report: a mutation whose daemon dies mid-flight spins forever — the client never reaches "outcome unknown"

**Type**: Requirement not implemented. The reconnected *state* is correct; the pending *indicator* is
never resolved, so the one screen the user is looking at is the one that stays wrong
**Severity**: Medium. Nothing is lost or corrupted — the worktree really was created, and the sidebar
behind the dialog shows it correctly after reconnect. But the dialog claims the operation is still
running, indefinitely, and the only way out is Cancel, which reads like abandoning work that has in
fact already completed
**Feature**: `010-daemon-session-persistence` (SC-007/SC-008, User Story 3, quickstart S8 last row).
Observed on branch `docs/cleanup-completed-features`, pinned client+daemon `0.8.0` built 2026-08-20
**Reported**: 2026-08-25
**Status**: Open

## Description

Quickstart S8's last row:

| Trigger | Expected |
|---|---|
| `pkill -f micold-daemon` mid-worktree-creation | Client shows **outcome unknown**, then the actual state after reconnect — never a stale list or a silent success |

Run headlessly on Xvfb `:83`. To make the mutation long enough to interrupt deterministically, a
`post-checkout` hook that `sleep 12`s was installed in the sandbox repo — `git worktree add` runs it,
so the daemon's git child stays busy for a known window. Then:

1. New worktree → type `feat`, name `probe two` → **Create**. The dialog shows its pending state
   correctly: an indeterminate progress bar, "Creating branch and worktree", and a disabled Create.
2. Three seconds in, the daemon was `kill -9`ed **by pid** (17:52:24).

| moment | dialog | sidebar |
|---|---|---|
| +2 s | "Creating branch and worktree", bar animating | emptied |
| +6 s | unchanged | still empty |
| +31 s | unchanged | (behind the dialog) |
| +90 s | **unchanged** — bar still animating | — |

Meanwhile a replacement daemon had been spawned (pid 993411) and the client had reconnected, and the
worktree itself had been created on disk — `git worktree add` was a *child* of the killed daemon, so
`SIGKILL` to the parent did not stop it, and its sleeping hook ran to completion:

```
/home/jaro/.aaa-vp83d/r10/.claude/worktrees/feat-probe-two   07c3e24 [feat/probe-two]
```

Pressing **Cancel** dismissed the dialog and revealed a sidebar listing all three worktrees, *Probe
two* included — so the post-reconnect state is right. Only the dialog is wrong, and it is wrong
forever.

## What is missing

The mutation's pending state is tracked entirely in the client, keyed on a request that will never be
answered because the connection carrying it is gone. Nothing in the reconnect path walks the
outstanding mutations and marks them indeterminate.

The quickstart's phrase for the correct outcome is precise and worth keeping: **outcome unknown**.
Not "failed" — the operation may well have succeeded, as it did here — and not silence. The user
needs to be told the daemon went away mid-flight and that the list now shows whatever actually
happened.

## Impact

- The only failure mode S8 names as unacceptable is "a stale list or a silent success". This is the
  third thing: a stale *dialog* over a correct list, which is arguably worse, because it actively
  contradicts the truth sitting behind it.
- A user who trusts the dialog waits indefinitely; a user who cancels reasonably assumes the work was
  abandoned and may retry, which then fails with "a worktree folder named 'feat-probe-two' already
  exists" — a confusing end to a sequence in which they did nothing wrong.

## Suggested fix

On connection loss, resolve every in-flight mutation to an explicit *unknown* outcome rather than
leaving it pending: dismiss the progress state, show a message naming the operation and saying the
daemon restarted mid-flight, and point at the refreshed list as the authority. The list refresh
already works and needs no change.

Two smaller notes for whoever picks this up:

- The stale error text from a *previous* failed attempt stays on screen during the next attempt's
  pending state (visible in `s8/10-pending.png`); clearing it when a new submission starts is a
  one-liner and removes a genuinely confusing frame.
- A failed mutation logs nothing on the daemon side. The read-only-parent failure below produced a
  perfect message in the UI and no log line at all, which is a gap against S13 ("for each failure in
  S7, S8 and S11, confirm the cause is determinable from logs").

## What did pass, in the same session

Recording these so the fix does not disturb them:

- **Create a worktree on an already-checked-out branch** — prevented rather than attempted. The
  *Existing branch* tab says "No branches are available to reuse — every branch is already checked
  out", and annotates each row with why (`feat/side-work · in use by feat-side-work`, `main · in use
  by the project checkout`). The rows are inert; Create never enables.
- **Colliding path** — a specific app-level refusal before git is invoked: "A worktree folder named
  'feat-side-work' already exists." / "Choose a different name, or remove the existing folder first."
  No catalog entry, no directory, no git call.
- **Read-only parent** — git's own stderr preserved verbatim, including the command:
  ```
  git failed to create the worktree: git worktree add -b feat/readonly-probe
  /home/jaro/.aaa-vp83d/r10/.claude/worktrees/feat-readonly-probe HEAD failed: Preparing worktree
  (new branch 'feat/readonly-probe')
  fatal: could not create leading directories of
  '/home/jaro/.aaa-vp83d/r10/.claude/worktrees/feat-readonly-probe/.git': Permission denied
  ```
  No leftover directory, no phantom worktree entry.
- **Pending state and duplicate submission** — during the 12 s hook-slowed create, the bar animates,
  the label reads "Creating branch and worktree", and Create is disabled; a second click on it did
  nothing and exactly one worktree was created.
