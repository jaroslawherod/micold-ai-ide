# Bug Report: scrolling back through history fetches from the revealed line to the *live tail* every notch, so the pane goes blank for seconds

**Type**: Requirement not implemented — FR-017's "fetched by range, not held whole" is defeated by
the range the client asks for. Behind a ticked task and a green suite: every range served is
*correct*, so nothing that checks content can see this.
**Severity**: High. Scrolling back ~400 lines in an ordinary terminal empties the pane and leaves it
empty for seconds; scrolling faster keeps it empty for the whole gesture and then trips the
liveness keepalive (see [BUG-022](BUG-022.md), which this one triggers).
**Feature**: `010-daemon-session-persistence` (FR-016/FR-017/FR-018, quickstart S10). Observed on
branch `docs/cleanup-completed-features`, client+daemon `0.10.0` built 2026-08-25
**Reported**: 2026-08-25
**Status**: Open

## Description

Quickstart S10, run headlessly on Xvfb `:83` (lavapipe) against a Regular terminal holding ~4,010
lines, `scrollback_lines: 10000` so the whole history is retained.

**Expected** (S10): *"scrolling stays responsive (history is fetched by range, not held whole)"*.

**Observed**: the fetched range is not the revealed rows — it is everything from the revealed line
to the live tail, re-requested on every wheel notch.

At a **brisk human speed** (50 notches per 3 s, ≈17 notches/s, a 1 s pause between rounds; one notch
= 2 lines):

| round | notches so far | lines back | top line shown | result |
|---|---|---|---|---|
| 1 | 50 | 100 | `3836` | fine |
| 2 | 100 | 200 | `3736` | fine |
| 3 | 150 | 300 | `3636` | fine |
| 4 | 200 | 400 | `3536` | fine |
| 5 | 250 | 500 | — | **pane entirely blank** |
| 6 | 300 | 600 | — | **pane entirely blank** |

Stop touching it and the content arrives ~5 s later, at exactly the right place (`3336` at the top —
600 lines back, as asked). So the *data* is right and the *latency* is the defect. Every step above
is exactly 100 lines per 50 notches, which is also this scenario's continuity check passing.

At **fast speed** (300 notches in 3 s) the pane stays blank and the daemon keeps working long after
the input stops. CPU (ticks of 10 ms, `/proc/<pid>/stat` utime+stime):

| window | client | daemon |
|---|---|---|
| during the 3 s of scrolling | 29.0 s | 2.1 s |
| the next 5 s (no input) | 1.5 s | **5.2 s** |
| the following 10 s (no input) | 3.1 s | **7.3 s** |
| the following 15 s (no input) | 4.7 s | 0.1 s |

The daemon is saturated for ~15 s of *silence* after a 3 s gesture. (The client's own 29 s is
lavapipe software rendering and says nothing about a real GPU; the daemon's does not render.)

## Root cause

`crates/micold-client/src/main.rs:836-855`, `scroll_view`:

```rust
let top = (vt - new_off as i64).max(oldest);
// ... find `need_from` = the lowest un-cached line in [top, top + rows)
d.send(ClientMsg::ScrollbackRequest {
    session: id,
    req,
    ranges: vec![LineId(from)..LineId(vt)],   // <-- to the live tail, not `from + rows`
});
```

`vt` is the viewport top of the *live* grid. The viewport is ~69 rows, but the request runs from the
first un-cached revealed line all the way to the tail, so its size grows with scroll depth: 400
lines back asks for 400 lines, 600 back asks for 600 — once per notch. Total work over a gesture is
quadratic in depth.

The daemon serves each of them faithfully and serially, under the session's shared terminal lock,
rebuilding a style/hyperlink palette per line (`crates/micold-daemon/src/server.rs:473-510`,
`crates/micold-daemon/src/framer.rs:197-240`). Nothing coalesces or supersedes the queued requests,
so a 300-notch gesture leaves ~300 overlapping ranges to grind through.

`scroll_view`'s own doc comment states the visible consequence as if it were the design — *"un-fetched
lines render blank until the `ScrollbackResponse` fills them (FR-016/017)"*. Blanking briefly while a
*viewport-sized* range is in flight is defensible; blanking for seconds because the request was
depth-sized is not, and it is what FR-017's "not held whole" was written to prevent.

## Reproduction

1. Open a Regular terminal session, `seq 1 4000 | sed 's/$/ ....../'`.
2. Scroll up with the wheel, ~17 notches/s, for four seconds.
3. The pane empties. Stop, wait ~5 s: it fills in at the correct position.

## Suggested fix

Request `LineId(from)..LineId(from + rows)` (plus whatever prefetch margin is wanted) rather than
`..vt`, and drop or supersede an outstanding request when a newer scroll position makes it
irrelevant — the correlation id (`req`) is already on the wire for exactly that. Keeping the last
painted rows on screen while a range is in flight, instead of painting blank, would also make a slow
fetch degrade into a stale view rather than an empty one.

## What passed in the same run

The rest of S10 holds and is not in question: continuity across a fully detached interval (200,000
lines produced with no client attached, then 4,000 more, all present and exactly ordered on
reattach), the scrollbar sized from the advertised watermark (24 px thumb for 69 visible rows of
~4,015 — 1.9% against an expected 1.7%), clamping at the oldest retained line (repeated 400-notch
over-scroll at `scrollback_lines: 170` pins to the oldest line and stays there, no error), and
selection anchored to line ids under new output (a selection of lines 3968–3971 stayed on those
lines as five new lines pushed the view up).
