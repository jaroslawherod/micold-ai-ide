# Bug Report: a window that reconnects displaces *itself* — "Another window took over this project", naming its own build, with no other window running

**Type**: Requirement met in isolation, broken in composition. FR-024's displacement handling and
FR-026/FR-028's automatic reconnect are each correct; together they make a single window lock itself
out of its own project.
**Severity**: High. The only window the user has goes read-only — input suppressed, scroll position
lost — and stays that way until they notice a banner and click "Take over". The stated guarantee for
a reconnect (FR-028: the fresh `Welcome` catalog is the resync, nothing else changes) does not hold.
**Feature**: `010-daemon-session-persistence` (FR-024, FR-024a, FR-026, FR-028; quickstart S10 as the
trigger). Observed on branch `docs/cleanup-completed-features`, client+daemon `0.10.0` built
2026-08-25
**Reported**: 2026-08-25
**Status**: **Fixed** (2026-08-27) — the window is nameable now, and recognises itself. The trigger
([BUG-021](BUG-021.md), the scrollback stall) is still open and is still worth fixing; this makes the
stall stop costing the user their project

## Description

Reproduced while running quickstart S10 on Xvfb `:83`. One client process (PID confirmed unchanged
throughout), one daemon, one project. Scrolling back through history stalls the client's inbound
frames for over nine seconds ([BUG-021](BUG-021.md) is why); the keepalive then declares the link
dead and the outer loop reconnects — both by design:

```
16:42:47  client attached to daemon client_build=micold-ai-ide/0.10.0   <- the same process, new connection
16:42:48  project attached client=6 project=/home/jaro/.aaa-vp83d/r10 force=false
16:42:52  client disconnected client=5                                   <- its own previous connection
```

What the user then sees, with no second window anywhere:

> **Another window took over this project**
> micold-ai-ide/0.10.0 is now attached — this window is read-only until you take it back.  `[Take over]`

The window is read-only, the terminal has snapped back to the tail (the scroll position is gone),
and only clicking **Take over** — which issues an `Attach { force: true }` — restores it.

Reproduced four times in one session, every time the keepalive expired.

## Root cause

The daemon is behaving as specified: a second attach to a held project displaces the holder and
sends it `DaemonMsg::Displaced { by }` (FR-024). It has no way to know the new connection and the
old one are the same window — nothing in the protocol identifies a *window*, only a connection and a
build string, and the build string is identical precisely because it is the same binary.

The client applies it unconditionally
(`crates/micold-client/src/shell/daemon_sync.rs:541-544`):

```rust
DaemonMsg::Displaced { project, by } => {
    app.displaced.insert(project, by);
}
```

Both connections feed one `App`, so the doomed connection's late `Displaced` lands *after* the new
connection's `Attached { project }` — which is the frame that clears `displaced`
(`daemon_sync.rs:569-572`, the FR-024a rule "an accepted attach falsifies a recorded displacement").
Order decides, and the order is the wrong way round: the stale frame wins and re-latches read-only.

## Suggested fix

Ignore `Displaced` frames that arrive on a connection the client has already replaced — the reconnect
loop knows when it has established a new one, so tagging inbound frames with a connection generation
and dropping stale ones is enough, and is more robust than comparing `by` against `CLIENT_BUILD`
(two genuinely different windows of the same build must still displace each other).

Fixing [BUG-021](BUG-021.md) removes the trigger observed here, but not the defect: any stall longer
than `LIVENESS_DEADLINE` (9 s, `crates/micold-core/src/protocol/keepalive.rs:22`) reaches it.

**Evidence**: `../evidence/S10-self-takeover-banner.png`.

## Resolution (2026-08-27)

**A window became nameable on the wire.** The root-cause paragraph above is exactly right about why
nothing could be done at the receiving end before: a connection was identified by a `ClientId` that
dies with it, and a client was described by a build string identical for every window of one binary,
so there was no expressible fact of the form "these two connections are the same window".
`ClientMsg::Hello` now carries a `client_instance` — `{ pid, nonce }`, generated once per process
and stable for its life — and the two frames that say who holds a project,
`DaemonMsg::Displaced::by` and `RefusalReason::ProjectBusy::holder`, carry a `ClientIdentity` of
build **and** instance where they carried a build string. `PROTOCOL_VERSION` 8 → 9, once, for all
three: the outbound halves have nothing to report without the inbound one.

The pid is for a person to read and the nonce is what makes the identity unique — pids are reused,
and two clients dialling one daemon need not share a host. Comparisons are always on the whole
instance; `two_windows_of_one_build_share_a_build_string_and_differ_by_instance` pins that, and it
was written *because* a probe found that nothing did.

**The client acts on it in two places, and they are not the same case.** A `Displaced` naming this
window is ignored. A `ProjectBusy` naming this window is reclaimed with `Attach { force: true }` —
no banner, nobody asked, because the only holder is a connection this process has already replaced
and there is no other window to ask about.

**Why not the suggested connection generation.** The report suggests tagging inbound frames with a
generation and dropping stale ones, and for the sequence it reproduces that would work: the
`Displaced` arrives on a connection the client has already replaced. But the same self-collision
also arrives the other way round, as a `Refused { ProjectBusy }` on the *current* connection, in
answer to an attach this window just sent. That frame is timely by every measure a generation
counter has, and it is the same defect: the window is told it cannot have its own project, by
itself. Identity settles both; staleness settles one. The report is also right that comparing
`by` against `CLIENT_BUILD` is wrong — two genuinely different windows of one build must still
displace each other — which is precisely why the fix adds something the build string is not.

**The daemon compares nothing, deliberately.** Exclusivity stays per connection, and two
connections presenting the same instance are still two attachments, one displacing the other. The
daemon cannot tell a second window from a first window reconnecting — that is the fact it lacks,
not a rule it applies wrongly. What it can do is *report* enough for the window to know, and that
is the whole of the change on that side. `the_holder_is_named_by_window_not_only_by_build` states
both halves in one test.

**Gates** — two in `micold-core` (`tests/handshake.rs`), one in `micold-daemon`
(`tests/exclusivity.rs`), two end to end through a real `App` (`crates/micold-client/src/main.rs`):

| Gate | Asserts |
|---|---|
| `a_client_instance_is_stable_for_the_life_of_the_process` | every connection this process opens presents the same window, and it names this pid |
| `two_windows_of_one_build_share_a_build_string_and_differ_by_instance` | the build cannot tell them apart, the instance can, and the pid alone is not the instance |
| `the_holder_is_named_by_window_not_only_by_build` | the refusal *and* the displacement carry the holder's instance, from two connections of one build |
| `a_window_is_not_displaced_by_its_own_reconnect_but_is_by_another_window` | the reported case, and the case that must keep working, in one place |
| `a_refusal_by_this_windows_own_dead_connection_is_reclaimed_not_offered` | a forced re-attach goes out, and no take-over is offered against the user themselves |
| `a_refusal_by_another_window_is_still_offered_never_forced` | nothing is sent: taking a project from another window stays a confirmed action (FR-023) |

**Probes** (2026-08-27; each reverts one layer and runs the three targets that could notice, as
three separate `cargo test` invocations — one invocation stops at its first failing target, which
in BUG-023 silently hid three gates):

| Probe | Reverted | Fails at |
|---|---|---|
| A | the `Displaced` arm's self-check | `main.rs:1888` — `left: Displaced { by: "micold-ai-ide/test (window …)" }`, the reported banner, reproduced |
| B | the `ProjectBusy` arm's reclaim | `main.rs:1946` — no forced re-attach was sent |
| C | `ClientIdentity::is` compares the pid only | `handshake.rs:200` — a stranger that reused the number reads as this window |
| D | `ClientInstance::current()` mints a new instance per call | `handshake.rs:148`, and **both** client gates: an instance that is not stable is not an identity |
| E | the daemon's `identify` reports the build with an empty instance | `exclusivity.rs:158` — the wire change without the daemon half reports nothing to compare |

Probe C is the one worth reading twice. Its first form — comparing the build string against a
pattern — passed every gate, because every window in every test differed by pid as well as by
nonce, and no assertion said the pid was not enough. The gate above was added in response, and only
then did the probe fail. A layer nothing can break is a layer nothing is testing.

**What is deliberately not gated: the wording.** No test asserts the banner's sentences, for the
reason `crates/micold-client/tests/terminal_empty_state.rs` gives — *"pinning prose in two places
makes the prose unchangeable rather than correct"*. What is load-bearing is structural: `ui/mod.rs`
matches exhaustively on `ConnectionStatus`, so the variants force the arms apart.

**Not re-measured on a display.** The two-window reproduction that produced this report — and the
S10 scrollback stall that triggered it — were not re-run under Xvfb. The gates drive the same `App`
the window does, and the daemon gate drives a real `serve_connection` over a real codec, but nobody
has watched a real window survive a real keepalive expiry since the fix.

**BUG-023's deferred half is settled here.** Its second item — the holder named by a build string
that names nothing, identical for the window reading it — needed exactly this wire change, which is
why it was deferred rather than done twice. The banner now reads
`micold-ai-ide/0.10.0 (window 41207)`.
