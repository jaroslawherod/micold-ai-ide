# Bug Report: a *refused* attach is announced as a takeover that never happened, by a holder name that names nothing

**Type**: Wrong message for a correct decision. The exclusivity rule itself works — the daemon
refuses the second window and the takeover offer is right there — but the banner describing the
refusal states the opposite of what occurred, and identifies the holder by a string that cannot
distinguish one window from another.
**Severity**: Low. Nothing is lost and the offered action is the right one; the user is told a
falsehood about why they are being offered it.
**Feature**: `010-daemon-session-persistence` (FR-024, FR-024a; SC-010, quickstart S6). Observed on
branch `docs/cleanup-completed-features`, client+daemon `0.10.0` built 2026-08-25
**Reported**: 2026-08-25
**Status**: **Fixed** (2026-08-26) — for the sentence: the report's item 1, and the third,
unnumbered consequence below it. Item 2, the holder *identity*, was not fixable here — it is a
protocol change, and it was made on 2026-08-27 with [BUG-022](BUG-022.md)

**Fixed**: 2026-08-26 — the cause now travels with the holder. `app.displaced` was a
`PathBuf -> String`, the holder's name and nothing else; it is now a
`PathBuf -> Hold { holder, cause }` with `cause` one of `TakenOver` or `AlreadyOpen`, stamped by
whichever frame raised it (`shell/daemon_sync.rs`, the `Displaced` and `Refused { ProjectBusy }`
arms). `connection_status` splits on that cause into `ConnectionStatus::Displaced` as before and a
new `ConnectionStatus::ProjectBusy { holder }`, and `ui/mod.rs` gives the latter its own banner:

> **This project is already open in another window**
> `<holder>` was holding it when this window asked, so this one is read-only. Take it over to work
> here.

**The fold itself is kept, deliberately.** One precedence slot and one action for both causes is
right: the user can do exactly one thing about either, take the project over, and waiting fixes
neither. What the fold could not carry is *which of the two happened*, and by the time the banner is
drawn nothing else in the app distinguishes them — the event is over and only its consequence is
still visible. That is why the cause is stored rather than derived, and it is what
`the_cause_is_carried_not_inferred` pins.

**The report's third paragraph is fixed too, and by a smaller change than it looks.** The
displacement banner read "`<holder>` **is now attached** — this window is read-only until you take
it back", a present-tense claim about a label recorded once and never re-derived; a holder killed
minutes ago went on being described as attached. It now reads "`<holder>` took it", which is what
stays true. The banner still does not learn that the holder has exited — nothing tells it, and the
**Take over** button already resolves that in one click — but it no longer asserts something false
while it waits.

**Gates** — three at the decision (`crates/micold-client/tests/features_connection.rs`) and one
end to end through `App` (`crates/micold-client/src/main.rs`):

| Gate | Asserts |
|---|---|
| `a_refusal_and_a_takeover_are_not_the_same_status` | a refusal reaches the banner as `ProjectBusy`, and is not equal to the takeover's status |
| `a_refusal_outranks_a_plain_disconnect_exactly_as_a_takeover_does` | the fold's *correct* half: the new variant keeps the precedence the old one had |
| `the_cause_is_carried_not_inferred` | the constructors stamp the cause they name |
| `a_refused_attach_reaches_the_banner_as_a_refusal_not_a_takeover` | a real `DaemonMsg::Refused { ProjectBusy }` and a real `DaemonMsg::Displaced`, each fed to a real `App`, produce different statuses — and both leave the window read-only |

The fourth is the one that would have caught the bug as reported: it starts from the daemon message,
not from the `Hold`, so it covers the `daemon_sync` arm that did the mislabelling.

**Probes** (2026-08-26, each reverts one layer and runs `--lib --bin micold-ai-ide --test
features_connection`; all four fail, each at a gate that names the layer it reverted. A, B and D
were then re-run against `--test features_connection` alone, for the reason under the table):

| Probe | Reverted | Fails at |
|---|---|---|
| A | `Hold::already_open` stamps `TakenOver` — the constructor forgets the cause | `main.rs:1808`, `left: Displaced … right: ProjectBusy`; alone, all three decision gates (`features_connection.rs:106`, `:126`, `:139`) |
| B | `connection_status` maps `AlreadyOpen` back onto `Displaced` | `main.rs:1808`; alone, `features_connection.rs:106` and `:126` |
| C | the `Refused` arm records `Hold::taken_over(holder)` — **the reported defect exactly** | `main.rs:1808`, and only there — see below |
| D | `if let Some(hold) = hold.filter(\|_\| !disconnected)` — a refusal ranked below a dropped socket | `main.rs:2116` and `features_connection.rs:126`, `:64` |

Two things the probes said that the table does not. **Cargo stops at the first failing target**, and
the binary's tests run before `tests/` — so A, B and D all halted at a `main.rs` gate and the three
new decision-level gates never executed. A second pass restricted to `--test features_connection`
was needed to show those three are load-bearing at all; without it their column would have been
guesswork. And **probe C fails at exactly one assertion in the whole workspace**: `daemon_sync`'s
arm is what the report is about, and `features_connection` never sees a `DaemonMsg`, so the
end-to-end gate is the only thing standing between that line and a silent regression. D also trips
the *pre-existing* ordering tests, which is the point of keeping the fold's precedence rather than
inventing a new slot for it.

**What is deliberately not gated: the wording.** No test asserts the two sentences' text. That
follows the principle `crates/micold-client/tests/terminal_empty_state.rs` states for the same
situation — *"pinning prose in two places makes the prose unchangeable rather than correct"* — and
what is load-bearing here is structural anyway: `ui/mod.rs`'s `match` on `ConnectionStatus` is
exhaustive, so a distinct variant forces a distinct arm, and a future edit cannot collapse the two
sentences back together without deleting a variant that four gates depend on. What that leaves
unguarded is someone writing the *wrong* sentence into the right arm. A reader who wants that
guarded should note that no automated check will catch it.

**Not fixed here — the holder identity.** `{holder}` is still `micold-ai-ide/0.10.0`, the build
string, identical for two windows of one binary; the report's second paragraph and its suggested
"widen the holder identity" are untouched. That needs a per-process identity on `ClientMsg::Hello`,
carried into `RefusalReason::ProjectBusy` and `DaemonMsg::Displaced`, and therefore a
`PROTOCOL_VERSION` bump — the same change [BUG-022](BUG-022.md) needs to stop a window reading a
refusal as itself. Doing it twice would bump the version twice for one wire change, so it is done
once, there. Until then the new banner names a build where it should name a window; it is at least
no longer describing the wrong event while doing so.

**Fixed since, in [BUG-022](BUG-022.md)** (2026-08-27). `ClientMsg::Hello` carries a
`client_instance`, and both `RefusalReason::ProjectBusy::holder` and `DaemonMsg::Displaced::by`
carry a `ClientIdentity` of build *and* instance (`PROTOCOL_VERSION` 8 → 9, once, as planned). The
banner reads `micold-ai-ide/0.10.0 (window 41207)`. Both of this report's items are now closed.

**Not re-measured on a display.** The two-window reproduction that produced this report was not
re-run under Xvfb; the gates drive the same `App` the window does, but nobody has read the new
sentence on a screen.

## Description

Two windows, one project, quickstart S6. Window A holds `r10`. Window B launches and asks for it.
The daemon refuses, correctly:

```
17:11:13  INFO client attached to daemon client_build=micold-ai-ide/0.10.0
17:11:14  INFO attach refused: project busy client=12 project=/home/jaro/.aaa-vp83d/r10
```

B then renders this banner, with a **Take over** button:

> **Another window took over this project**
> micold-ai-ide/0.10.0 is now attached — this window is read-only until you take it back.

Two things in two lines are wrong for the case that produced them:

1. **"took over" describes the opposite event.** Nobody took anything from B — B asked and was
   told no. A takeover is what happens when a window that *held* a project loses it, and the same
   banner is correct there. `daemon_sync.rs:546-555` maps `RefusalReason::ProjectBusy` onto
   `app.displaced` deliberately, with a comment saying so ("surface the same take-over banner as a
   live displacement"). Sharing the state is defensible; sharing the sentence is not.
2. **The holder is named by build string.** `{by}` is `micold-ai-ide/0.10.0` — the same text for
   every window built from the same commit, which in the exclusivity scenario is always both of
   them. The message that SC-010 asks to "name the conflict" therefore names nothing the user can
   act on: it does not say which window, on which display, started when. This is the same
   identifier [BUG-022](BUG-022.md) shows a window reading as *itself*.

A third, smaller consequence of the same latch: once the holder dies, the banner keeps naming it.
`kill -9` on window B (the holder after a takeover) left window A sitting under
"micold-ai-ide/0.10.0 is now attached" with nothing attached at all, until A's **Take over** was
clicked — which then worked immediately (`project attached client=11 … force=true`, no daemon
restart). The banner is only ever falsified by an `Attached` of one's own (`daemon_sync.rs:569-572`),
and no `Attached` is coming for a window that is not asking.

## Steps to reproduce

1. Launch a client, open project P.
2. Launch a second client against the same daemon and the same P.
3. Read the second window's banner.
4. Click **Take over**, then `kill -9` the window that just took over, and read the first window's
   banner again.

## Expected

A refusal says it was refused, and names the holder in terms that pick out a window — at minimum
when it attached, ideally host plus window. A banner naming a holder that has exited stops claiming
it is attached.

## Actual

The refusal borrows the displacement sentence verbatim, and the holder is a build string.

## Suggested fix

Give `ConnectionStatus` a distinct `Refused { holder }` variant (or a boolean on `Displaced`) and
render "This project is open in another window" for it, keeping the existing sentence for a real
displacement. Widen the holder identity the daemon sends past `client_build` — attach time and pid
are already known to it. The staleness resolves on its own once a refusal is retried, which the
existing **Take over** already does.
