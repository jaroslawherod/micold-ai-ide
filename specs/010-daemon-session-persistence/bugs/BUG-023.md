# Bug Report: a *refused* attach is announced as a takeover that never happened, by a holder name that names nothing

**Type**: Wrong message for a correct decision. The exclusivity rule itself works — the daemon
refuses the second window and the takeover offer is right there — but the banner describing the
refusal states the opposite of what occurred, and identifies the holder by a string that cannot
distinguish one window from another.
**Severity**: Low. Nothing is lost and the offered action is the right one; the user is told a
falsehood about why they are being offered it.
**Feature**: `010-daemon-session-persistence` (FR-024, FR-024a; SC-010, quickstart S6). Observed on
branch `docs/cleanup-completed-features`, client+daemon `0.10.0` built 2026-08-25
**Reported**: 2026-08-25
**Status**: Open

## Description

Two windows, one project, quickstart S6. Window A holds `r10`. Window B launches and asks for it.
The daemon refuses, correctly:

```
17:11:13  INFO client attached to daemon client_build=micold-ai-ide/0.10.0
17:11:14  INFO attach refused: project busy client=12 project=/home/jaro/.aaa-vp83d/r10
```

B then renders this banner, with a **Take over** button:

> **Another window took over this project**
> micold-ai-ide/0.10.0 is now attached — this window is read-only until you take it back.

Two things in two lines are wrong for the case that produced them:

1. **"took over" describes the opposite event.** Nobody took anything from B — B asked and was
   told no. A takeover is what happens when a window that *held* a project loses it, and the same
   banner is correct there. `daemon_sync.rs:546-555` maps `RefusalReason::ProjectBusy` onto
   `app.displaced` deliberately, with a comment saying so ("surface the same take-over banner as a
   live displacement"). Sharing the state is defensible; sharing the sentence is not.
2. **The holder is named by build string.** `{by}` is `micold-ai-ide/0.10.0` — the same text for
   every window built from the same commit, which in the exclusivity scenario is always both of
   them. The message that SC-010 asks to "name the conflict" therefore names nothing the user can
   act on: it does not say which window, on which display, started when. This is the same
   identifier [BUG-022](BUG-022.md) shows a window reading as *itself*.

A third, smaller consequence of the same latch: once the holder dies, the banner keeps naming it.
`kill -9` on window B (the holder after a takeover) left window A sitting under
"micold-ai-ide/0.10.0 is now attached" with nothing attached at all, until A's **Take over** was
clicked — which then worked immediately (`project attached client=11 … force=true`, no daemon
restart). The banner is only ever falsified by an `Attached` of one's own (`daemon_sync.rs:569-572`),
and no `Attached` is coming for a window that is not asking.

## Steps to reproduce

1. Launch a client, open project P.
2. Launch a second client against the same daemon and the same P.
3. Read the second window's banner.
4. Click **Take over**, then `kill -9` the window that just took over, and read the first window's
   banner again.

## Expected

A refusal says it was refused, and names the holder in terms that pick out a window — at minimum
when it attached, ideally host plus window. A banner naming a holder that has exited stops claiming
it is attached.

## Actual

The refusal borrows the displacement sentence verbatim, and the holder is a build string.

## Suggested fix

Give `ConnectionStatus` a distinct `Refused { holder }` variant (or a boolean on `Displaced`) and
render "This project is open in another window" for it, keeping the existing sentence for a real
displacement. Widen the holder identity the daemon sends past `client_build` — attach time and pid
are already known to it. The staleness resolves on its own once a refusal is retried, which the
existing **Take over** already does.
