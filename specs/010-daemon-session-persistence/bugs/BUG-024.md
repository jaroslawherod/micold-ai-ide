# Bug Report: a respawn that cannot spawn leaves the session `Restarting` forever — no process, no further supervision, no report

**Type**: Defect. The crash-loop policy is applied and then its answer is thrown away, so the daemon
acts on neither of the two things it can say.
**Severity**: Medium. Nothing is lost and the user can recover by pressing restart, but the row
reads `restarting` indefinitely for a session that nothing is restarting, and the state never
advances to `Failed` — which is the state that would tell them to look at it.
**Feature**: `010-daemon-session-persistence` (FR-005, FR-045; the crash-loop budget and its
`Failed` terminus)
**Reported**: 2026-08-26
**Status**: Open

## Description

A session whose primary process exits is supervised: `supervise_exit` advances the crash-loop
budget, and while the budget holds, the daemon respawns. If that **respawn itself fails to spawn**,
the session is left in `Restarting { attempts }` with no live entry — and the supervision loop only
walks `inner.sessions`, so nothing will ever observe it again.

The result is a session that is:

- not running (there is no process),
- not `Failed` (the budget never exhausts, because no further exit can be observed),
- reported as `restarting` to every client, for as long as the daemon lives.

## Reproduction

The likeliest route is **this project's own guard**, not an exotic one:

1. Start a session in a worktree.
2. Delete that worktree from outside the application — the scenario BUG-012 was reported from.
3. Let the session's process exit (or kill it).

The supervisor sees the exit, `supervise_exit` returns `Restart`, and `respawn_primary` calls
`PtySession::spawn_ai_cli`, whose first statement is `ensure_cwd_exists` (BUG-012's fix,
`crates/micold-daemon/src/supervisor.rs:124`). It returns `NotFound`, and the session is stuck.

An earlier note on this finding (feature 026, T046's third probe) guessed it needed "the binary to
vanish mid-loop" and filed it as not reachable. That was wrong about the reachability and is
corrected here: any spawn failure reaches it, and the missing-directory one is a case the project
deliberately created.

## Root cause

`DaemonState::respawn_primary`, `crates/micold-daemon/src/state.rs:1491-1499`:

```rust
Err(_) => {
    // Couldn't even respawn — count it as a further crash so the budget still advances,
    // and drop the dead entry so it does not masquerade as alive.
    let _ = self
        .lock()
        .catalog
        .supervise_session_exit(id, ExitOutcome::Crashed);
    self.remove_session(id);
}
```

`supervise_session_exit` mutates the lifecycle **and returns the action the daemon must carry out**.
Here the return is discarded, so both of its answers are dropped on the floor:

- **`Restart`** (the budget still holds) — the record is now `Restarting { attempts + 1 }`, and
  `remove_session` takes the live entry away on the next line. `supervise_tick` iterates
  `inner.sessions`; with no entry there is nothing to observe, so no later tick can advance the
  budget or retry. Stuck.
- **`GiveUp`** (the budget is exhausted) — the record *is* correctly `Failed`, but the project is
  never pushed onto the tick's `changed` list, so no `CatalogChanged` is broadcast. The clients keep
  drawing the last thing they were told until some unrelated event publishes a catalog.

The tick's own `changed` was assembled under the lock in phase 1; this runs off the lock in phase 3,
after it. So a transition decided here reaches no one either way.

The doc comment above the function states the opposite of what it does, in the success case too:

> Respawn a session's primary process after a crash and swap it into the live registry, **marking
> the session `Running`** (resets the crash-loop counter).

It does not — the body's own comment says so correctly ("The session stays `Restarting { attempts }`
… it is NOT reset to `Running` here"), and the reset is `mark_running_if_restarting`'s, a tick later.
Whatever fixes this should fix the comment with it.

## Expected

A respawn that cannot spawn is a failed restart attempt, and the two states the policy can name are
both reachable and both reported:

- while the budget holds, the session is retried on a later tick, or is left in a state a later tick
  can still observe — never in one nothing walks;
- when the budget is exhausted, the session is `Failed` **and the clients are told**, which is the
  whole point of `Failed` existing.

## Notes

- The user *can* recover: pressing restart calls `start_session`, whose ungated
  `mark_session_running` (BUG-011) moves the record to `Running`. The bug is that nothing says the
  session needs it.
- Not specific to feature 026: `respawn_primary` handles both `TerminalMode::AiCli` and
  `TerminalMode::Regular`, and the missing-directory route hits `spawn_shell`'s copy of the same
  guard identically.
