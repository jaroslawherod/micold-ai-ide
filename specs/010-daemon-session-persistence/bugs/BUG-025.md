# Bug Report: `settings.json` has two writers and neither is protected — two ways it resets every setting

**Type**: Spec gap, two arms. FR-010a divides the *fields* of a shared file between two writers but
never serialises the *writes* (arm 1), and never says where the *base* of a write may come from
(arm 2) — each with an implementation defect downstream of it
**Severity**: High (every setting the user has chosen — theme, scrollback, environment-include,
default AI CLI, service placement, and the whole sandbox profile: runtime, image, budget, network,
credential opt-ins — is silently replaced by defaults. The loss is written at save time and only
discovered at the next load, so the user cannot associate it with what caused it, and the shared
temp path makes it recur)
**Feature**: `010-daemon-session-persistence` (FR-008, FR-010, **FR-010a**, FR-012a, FR-012b) —
seam with `027-sandboxed-daemon-runtime` (FR-011, the state-directory bind mount) and
`011-env-include-script`. Observed on branch
`fix/settings-are-removed-or-reset-after-restart-or-upgrade-of-deb-package`
**Reported**: 2026-09-03
**Status**: **Fixed** — artifacts and code
**Patched**: 2026-09-03 (FR-010b, FR-010c, SC-026; plan.md §Storage; tasks T153–T162)
**Fixed**: 2026-09-12 (Phase 30, T153–T162; full workspace green)

## Description

The user reports that application settings are lost after an app restart or a `.deb` reinstall: the
app comes back with everything at its defaults.

Restarting and reinstalling are not what destroys the settings. **The `.deb` ships no maintainer
scripts and no conffiles** — nothing in `[package.metadata.deb]`
(`crates/micold-client/Cargo.toml:62-86`) or in `packaging/micold-daemon.service` touches
`~/.local/share/micold-ai-ide/`, and an install or upgrade cannot remove a file it never declares.
A restart is only when the damage becomes *visible*: `JsonFileSettingsStore::load` is the only code
that inspects the file, so a document corrupted during an earlier save sits there unnoticed until
the next launch reads it, moves it to `settings.json.bak`, and adopts `Settings::default()`
(`crates/micold-core/src/settings.rs:326-340`). An upgrade restarts both the client and the daemon,
which is why it reliably surfaces the loss.

What destroys the settings is a save. `settings.json` has two writers, and there are two independent
ways a save loses data:

1. **A torn write** — both writers stage through one temp path, so concurrent saves can leave an
   unparseable file, which the next `load` moves aside and replaces with defaults. Evidenced by the
   2026-08-26 `.bak` below.
2. **A write over a failed read** — a load that could not return the stored document yields defaults,
   and a writer merges into them and persists them. Evidenced by the 2026-09-03 reset in
   *Second arm*, further down; that one did not involve corruption at all.

Either alone produces the reported symptom. The rest of this section covers the first.

## Reproduction and evidence

**Forensic — the user's own machine.** `~/.local/share/micold-ai-ide/settings.json.bak`, 205 bytes,
2026-08-26 10:15, holds a complete `settings_version: 3` document followed by 23 trailing bytes of a
*different, longer* document:

```
  "env_include_timeout_secs": 15
}ude_timeout_secs": 15
}
```

That is a short document written over the first 205 bytes of a 228-byte one. It is not valid JSON,
so the next `load` moved it aside and reset the user's settings — the reported symptom, with the
file that proves it still on disk. The atomic temp-file-plus-rename write was already in the build
that produced it (`5b484cf`, 2026-08-26), so a single writer cannot have made this file:
`std::fs::write` truncates.

**Mechanism, reproduced.** Two writers, each doing what `save` does — open the shared temp path with
`O_WRONLY|O_CREAT|O_TRUNC`, write, rename — interleaved so both truncate before either writes:

| step | writer | effect |
|---|---|---|
| 1 | client | truncates `settings.json.tmp` |
| 2 | daemon | truncates `settings.json.tmp` (again — no-op) |
| 3 | client | writes its 208-byte document |
| 4 | daemon | writes its 182-byte document from offset 0 |
| 5 | either | renames the 208-byte file into place: 182 good bytes + 26 bytes of tail |

Run as a two-thread harness this produces byte-for-byte the shape of the user's `.bak` —
`...include_timeout_secs": 15\n}` hanging off the end of a complete document — and
`json.loads` rejects it with `Extra data: line 8 column 2`. Either writer may win the rename; the
loser's tail survives either way.

**Why the two writes are near-simultaneous by construction.** They are not an unlucky coincidence.
`handle_settings_saved` writes the file and then *immediately* sends `ClientMsg::SettingsSet`
(`crates/micold-client/src/shell/persist.rs:217-230`), and the daemon's handler responds with
`persist_service_settings`, which does its own `load` then `save`
(`crates/micold-daemon/src/catalog.rs:242-250`). Every single Settings save therefore issues two
writes to one temp path, microseconds apart, from two processes that never coordinate.

**Why sandboxing does not separate them.** One might expect the containerised daemon to write its
own file. It does not: the host state directory is bind-mounted to `STATE_CONTAINER_DIR`
(`crates/micold-core/src/sandbox/mod.rs:351`, `:598`), and the image sets `XDG_DATA_HOME=/var/lib`
precisely so both resolve to the same inode — deliberate, and correct for `projects.json`. Both
writers land on `settings.json.tmp` in that one directory.

## Artifact Traceability

### spec.md — `010-daemon-session-persistence`

- **Affected user story**: the state-ownership block, US "the service owns durable state" — spec.md
  §*State ownership*, lines 400-438.
- **Affected requirements**:
  - **FR-008** — "The service MUST be the single writer of all durable state". `settings.json` is
    the documented exception to this, and the exception is where the defect lives.
  - **FR-010** / **FR-012a** / **FR-012b** — the field-ownership split that makes two writers
    necessary in the first place.
  - **FR-010a** *(added by BUG-014, 2026-08-26)* — "each writer MUST write only the fields it owns,
    over a read of the file taken at save time."
- **Gap identified**: FR-010a governs **which fields** each writer may write and **how fresh** its
  copy must be. It says nothing about **two writers writing at the same moment**, and nothing about
  the file each writer writes *through*. Both obligations are satisfied by the current code — the
  client and the daemon each read-modify-write their own fields — and the file is still destroyed,
  because read-modify-write is not an atomic section and the temp path is shared. The requirement
  needs a third clause: concurrent saves must not be able to interleave, and no writer may use a
  staging path another writer can also open.

  There is an uncomfortable detail here. **FR-010a's own fix made the window wider.** Before
  BUG-014, the daemon wrote its boot snapshot straight out; afterwards it does `load` *then* `save`,
  so it now holds the file open across a longer span, at exactly the moment the client has just
  written it. The observed corruption is dated 2026-08-26 — the same day FR-010a was added.

### plan.md — `010-daemon-session-persistence`

- **Affected section**: §*Storage* (plan.md:66) — "Local files only. `projects.json` and
  `settings.json` in the existing data directory."
- **Impact**: the plan names the files and their location and stops there. It never states a
  concurrency model for a file with two process-level writers, so "atomic write" was implemented as
  temp-plus-rename — which is atomic against a *reader* and against a crash, and is no defence at
  all against a second writer. The plan needs to say which of the two mechanisms applies (an
  advisory lock over read-modify-write, a per-writer temp path, or a single-writer protocol that
  removes the second writer) and to record that rename-atomicity alone does not cover this.

### tasks.md — `010-daemon-session-persistence`

- **Affected tasks**:
  - **T021** *(marked `[X]`)* — "Implement the Catalog as the single writer of durable state
    (projects, worktrees, sessions, settings)… atomic `persist()`." The catalog is *not* the single
    writer of settings, and the task's own completion note describes the atomicity it delivered as
    the `store.save()` temp-and-rename. Correct as far as it goes; it does not reach this.
  - **T100** *(marked `[X]`)* — the task that wired `SettingsSaved` to send `ClientMsg::SettingsSet`
    right after the local write. This is the change that put the two writes microseconds apart. The
    task was right to make the change (FR-012a needs the running daemon to see it); nothing asked it
    to consider that the daemon would answer by writing the same file.
- **False completions**: none. Every task listed did what it was asked. This is the signature of a
  spec gap rather than implementation drift — the code satisfies each requirement it was given, and
  the requirements between them do not add up to a file that survives.
- **Missing tasks** (for `/speckit.bugfix.patch` to add):
  1. Serialise saves to `settings.json` across processes — an advisory lock (`flock`) held across
     the read-modify-write, not just the write, since a lock around the write alone still permits a
     lost update.
  2. Give each writer its own staging path (e.g. `settings.json.<pid>.tmp`), so that even an
     unlocked interleaving can only lose an update and can never produce a torn document. Cheap,
     independent of (1), and it is the clause that turns High severity into Low.
  3. A regression gate that runs two concurrent savers against one path and asserts the file parses
     afterwards — the shape reproduced above, as a test.
  4. Decide and record whether `.bak` recovery should be louder. Today `LoadStatus::Recovered` is
     surfaced, but the user in this report did not connect it to their loss.

### Cross-feature — `027-sandboxed-daemon-runtime`

- **FR-011** ("persistent service state MUST survive the sandbox being stopped, recreated, or
  upgraded") and the `STATE_CONTAINER_DIR` bind mount are what keep the sandboxed daemon writing the
  *host's* `settings.json`. This is intended and should not change — but it means sandboxing does
  not fix this bug, and the concurrency clause FR-010a needs must be written knowing that one of the
  two writers may be inside a container.

## Second arm, found while patching — a failed read becomes a write of defaults

**Added 2026-09-03.** While the artifacts were being patched, the reporter's `settings.json` reset
again, at 19:48, and the shape was *different* from the one above.

The whole `daemon` block reverted to `DaemonConfig::default()` at once — `placement` from
`local_sandbox` to `host_process`, every budget number to `null`, all four credential opt-ins
dropped, `network` to `no_outbound`, `survive_logout` to `false`, and the image to `DEFAULT_IMAGE`
(`registry` + `ghcr.io/jaroslawherod/micold-daemon:0.12.1`, which for this build *is* the default).
Meanwhile every field the service owns kept a live, non-default value: `scrollback_lines` 20000,
`env_include_script_path` `/tmp/does-not-exist.sh`, `default_ai_cli` `Copilot`.

Two things rule out the first arm. The file **parses** — it is not torn. And `settings.json.bak`
still carries its 2026-08-26 timestamp, so `load` never found a corrupt file and never moved one
aside. Copy preserved at `BUG-025-evidence/settings.json.daemon-block-reset.2026-09-03`.

**Mechanism.** `load` returns `Settings::default()` for a file that is missing, unreadable, or
corrupt, so the app opens rather than failing (Principle IV) — and returns a `LoadStatus` saying
which. Every caller drops it:

| site | what it does |
|---|---|
| `catalog.rs:243` | `let mut on_disk = store.load().settings;` → overwrite 5 owned fields → `save` |
| `persist.rs:110` | `let existing = store.load().settings;` → `Settings { theme, ..existing }` → `save` |
| `persist.rs:154`, `persist.rs:193`, `startup.rs` | read-only; defaults are fine here |

The first two use the result as the **base of a write**. `Missing` and `Recovered` are both
`Settings::default()`, and neither is distinguishable at those call sites from "the user has chosen
the defaults". Note the unreadable-for-any-other-reason branch (`settings.rs:317-322`) leaves the
file *in place* and returns defaults — so a transient read failure against an intact file is enough,
and the subsequent save destroys a document that was never corrupt.

`merged_with_existing` is what makes it total rather than partial. It preserves **top-level keys
only** — documented, deliberate, and correct for its purpose — so a default `daemon` value in the
fresh document replaces the stored `daemon` object **whole** rather than merging into it. One
unguarded save takes the entire sandbox profile with it.

**Attribution is by elimination, not by evidence.** The split — every service-owned field live, every
other field at its default — is exactly what `persist_service_settings` produces over a defaulted
base. But the client's Settings draft is seeded from the same kind of load, so a draft seeded from
defaults, saved after the user changed `default_ai_cli` to `Copilot`, produces the same bytes.
Neither log records that a settings write happened at all, which is why **T162** adds that logging.
The requirement (FR-010c) is written to cover both writers, since the defect is in the pattern rather
than in one call site.

**This arm is independently sufficient.** Fixing the temp paths and the lock (T153–T157) would not
have prevented the 19:48 reset.

## Root Cause Analysis

Three decisions, each defensible alone:

1. **The field-ownership split** (FR-010, FR-012a, FR-012b) put two processes in one file. That
   split is sound — a theme is not a session-service setting, and the daemon should not be the
   authority on one.
2. **BUG-014's fix** (FR-010a) made both writers read-modify-write. Also sound, and it fixed a real
   lost-update bug — but read-modify-write is a critical section, and the requirement that
   introduced it did not say so.
3. **"Atomic write"** was read as temp-file-plus-rename. That is the standard answer to *crash*
   atomicity and to torn *reads*. It is not an answer to a concurrent writer, and because the temp
   path is derived from the target path (`self.path.with_extension("json.tmp")`,
   `crates/micold-core/src/settings.rs:266-268`) it actively creates a second shared file for the
   two writers to collide in.

4. **Recovery-to-defaults** (Principle IV) let the app open on a bad file. Also sound — and it
   produced a value that is safe to *show* and catastrophic to *write*, while the `LoadStatus` that
   distinguishes the two cases was returned and then dropped by every caller.

No single author was wrong. The gap is between the artifacts: ownership was specified per field,
freshness was specified per save, and neither mutual exclusion nor the
provenance of the base was specified anywhere — while the code
comment at `catalog.rs:230-234` states plainly that the two writes arrive back-to-back.

## Fix as delivered (2026-09-12, Phase 30)

Three distinct data-loss modes, three distinct fixes, each reproduced before it was closed:

| Mode | Fix | Reproduction before the fix |
|------|-----|------------------------------|
| **Torn write** — both writers `O_TRUNC` the one shared `settings.json.tmp` derived from the target, so rename-atomicity never applies | T153: `store::temp_path_for` gives every save its own `settings.json.<pid>.<n>.tmp`, and `store::write_then_rename` removes the staging file on either failure | `settings_concurrent_writers` reproduced the reported `.bak` shape — a short document followed by the tail of a longer one — at round 117 |
| **Lost update** — read-modify-write with no mutual exclusion | T154: a blocking `File::lock` on a `settings.json.lock` **sidecar**, held across the whole read-modify-write in `update_reporting`. The sidecar rather than the file itself, because the write replaces the target by rename, so a lock on the target is a lock on an inode the next writer never opens | `interleaved_updates_keep_both_writers_changes` reproduced at round 0 |
| **Write over a failed read** — an unreadable file loads as defaults, and the next save writes those defaults over it | T159: `update_reporting` refuses when `status != Loaded` **and the document is still on disk**. The refusal line is the file, not the status: `Missing` is a first run and `Recovered` after a corrupt file was already moved to `.bak` are both allowed; unreadable-but-intact is refused | `settings_refuses_save_over_failed_read`, and `settings_service_write_refuses_failed_read` at the daemon call site |

Two silences were also closed, because the eight days between the reset and the report were a
diagnostics failure as much as a concurrency one:

- **T158** — `LoadStatus::Recovered` reached nobody. Every one of the five settings call sites
  discarded the status; the only reader in either binary was `server.rs:126`, and that reports the
  *projects* store. `shell::persist::notify_settings_recovery`, wired at
  `shell/startup.rs`, now raises a `notify_info` that **names the preserved `.bak`** — the
  difference between an apology and something the user can act on (research R10).
- **T162** — no settings write was recorded anywhere, so "which of the two writers did this, and
  what did it think it was merging into?" had no answer. `SettingsWrite::log_line` is a pure
  formatter in the library (so it is asserted, the way `attach_log_line` is) and reaches disk at the
  boundary: `tracing::info!` in the daemon, `crate::log_line` in the client. A refused write is
  logged too — a save that did not happen is exactly the event nothing recorded.

Design notes are in `research.md` **R9** (why blocking rather than `try_lock`, why a sidecar, and
why `save` must *not* take the lock — flock is per open-file-description, so a second acquisition
from the same process would deadlock every `update`) and **R10**.
