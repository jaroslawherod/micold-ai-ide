# Bug Report: A refused shell open is only logged, so the Terminal toggle does nothing on screen

**Type**: Spec gap (FR-006c says a start into a missing directory is refused, but not that the
refusal reaches the user; the request that was refused is fire-and-forget)

**Severity**: Medium (no data is lost and nothing runs in the wrong tree, but the control reports
nothing and changes nothing, on every retry, with the only trace in the daemon log)

**Feature**: 010-daemon-session-persistence (FR-006c, BUG-012; seam with 011 shell instances and
025 FR-014)

**Issue**: #592

**Reported**: 2026-10-05

**Status**: Fixed (2026-10-05) — Phase 32 (T164–T167)

## Description

For a session whose worktree directory was removed while the session was still listed, switching to
the terminal does nothing: the view stays on the Claude CLI and no message appears.

Reproduction (on `origin/main`):

1. Create a session on a worktree.
2. Delete the worktree directory from outside the app (`git worktree remove`, or merge and clean up)
   while the session is still listed.
3. Select that session and toggle to the terminal (or press the "+" for an additional terminal).
4. The pane keeps showing the CLI; no toast or inline error. `micold-daemon.log` has, per attempt:

```
WARN micold_daemon::server: open shell failed session=44bc… instance=1 err=session working directory does not exist: …/.claude/worktrees/feat-583-rpm-package
WARN micold_daemon::server: attach requested for a process the session does not have session=44bc… process=Shell(ShellInstanceId(1))
```

Observed 2026-10-05 13:35:32–13:36:06 for session `44bc2a7f…` (worktree `feat-583-rpm-package`),
instances 1, 2 and 3 and every retry. Only this one session appears in the log; whether every
"affected session" the reporter sees has a missing cwd is unconfirmed and out of this fix's scope.

## Root cause

`ClientMsg::SessionOpenShell` has no reply. In `crates/micold-daemon/src/server.rs` the
`SessionOpenShell` arm (~line 932) calls `state.open_shell(session, instance)`; on `Err` it does
`tracing::warn!` and nothing else. `open_shell` (`state.rs:3899`) fails because `spawn_shell`
(`supervisor.rs`) calls `ensure_cwd_exists` (FR-006c, BUG-012). The client has already acted
optimistically: `on_shell_instance_open_requested`
(`crates/micold-client/src/shell/daemon_sync.rs:~1853`) calls `session.set_mode(Regular)` and
`open_shell_instance()`, sends `SessionOpenShell`, then `attach_current_process`, which sends
`SessionAttachProcess(Shell(n))`. The daemon has no such process, logs the second warning
(`server.rs` `SessionAttachProcess` arm), and keeps streaming the CLI while the client believes it
shows the shell. Same class as BUG-001 (a silent attach), one hop earlier: the cause of the missing
process is now logged, but only the log sees it.

## Artifact Traceability

### spec.md

- **FR-006c** requires the refusal and forbids a registered process, and BUG-012 delivered both. It
  is silent on who is told. The user story it serves (a start into a missing directory must not be
  silent) already intends the report; this closes an edge the BUG-012 patch left open on the one
  start path that has no reply (`SessionOpenShell`; the primary start reaches 025 FR-014).
- No new behaviour: the report reuses the client's existing `notify_error` surface.

### plan.md / contracts

- `contracts/messages.md` lists the daemon-to-client messages; it gains `ShellOpenFailed`.

### tasks.md

- No false completions: T133–T134 (BUG-012) did what they claimed; they did not claim the client
  hears about it.

## Recommended Fix

- Add `DaemonMsg::ShellOpenFailed { session, instance, reason: ShellOpenFailure }` with
  `ShellOpenFailure::WorkingDirMissing` and `Other(String)`, sent to the requesting client from the
  `Err` arm of `SessionOpenShell` (keep the warn). `ensure_cwd_exists` (`supervisor.rs:111`) returns a
  distinguishable error (a dedicated error type wrapped in the `io::Error`, not a string match) so
  `open_shell` can map it to `WorkingDirMissing`.
- Client: on it, `Session::close_shell(instance)` (core already reverts `mode` to `AiCli` when the
  last instance goes), `attach_current_process` so the daemon and client agree on the CLI, and
  `notify_error` with the reason: "Worktree directory is missing" for `WorkingDirMissing`, else "Couldn't open a terminal: {text}". The client never stays on a shell view the daemon refused.
- Out of scope: flagging sessions whose worktree is gone in the UI, or offering to recreate it or
  close the session (the issue's "Ideally" bullet; the row already shows `missing`).
- Same treatment for `SessionRestartShell`'s `Err` arm is not needed: it falls back to the primary
  already (`server.rs`), only the toast is missing, and the same message can be sent from there
  at no extra cost (T165).
