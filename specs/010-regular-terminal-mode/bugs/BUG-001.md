# Bug Report: Switching a session to Regular Terminal mode does nothing, silently

**Type**: Implementation drift
**Severity**: High
**Feature**: 010-regular-terminal-mode (FR-003/FR-007) / 010-daemon-session-persistence (daemon port) / 012-multiple-regular-terminals (T009)
**Reported**: 2026-08-04
**Status**: Patched
**Patched**: 2026-08-04

## Description

Clicking the AI CLI ↔ Regular Terminal toggle in the terminal's bottom bar does not switch the
session to a shell. Reported by the user as "I can't switch claude to terminal mode, it's not
working."

The toggle's icon and tooltip still flip — the client updates its own state unconditionally — so
the app claims to be in Regular Terminal mode while the pane keeps showing whatever it showed
before. Nothing is logged, no error notification appears, and no failure is visible anywhere.

**Confirmed by code inspection** (see Root Cause Analysis): the daemon's `open_shell` spawns the
shell process and then **discards it** if the session is not currently live, returning `Ok(())`;
`attach_process` then silently no-ops for the same reason. Every step on the path reports success.

**Confirmed 2026-08-04 by an automated test**, not only by inspection:
`shell_instances::opening_a_shell_on_a_session_whose_primary_is_not_running_still_attaches_a_shell`
drives `DaemonState::open_shell` against a durable session with no live entry and shows that
`attach_process` afterwards returns `None` — the instance does not exist, though `open_shell`
returned `Ok(())`. The mechanism is therefore established. Whether it is what the user hit in the
GUI on 2026-08-04 remains unproven, since the path leaves no trace to check against; but it
reproduces the reported symptom exactly and needs fixing regardless.

## Artifact Traceability

### spec.md (010-regular-terminal-mode)

- **Affected user story**: User Story 1 — "Switch a session's terminal to a plain shell"
  (`spec.md:22-26`), acceptance scenario 1; and User Story 2's round-trip (`spec.md:38-46`).
- **Affected requirements**:
  - **FR-003** (`spec.md:83`) — "Switching to Regular Terminal mode MUST start a plain shell
    process, scoped to the session's worktree directory, if one is not already running for that
    session." **This is the violated requirement.** The shell process *is* started, then dropped
    before it is registered, so from the user's side nothing started at all.
  - **FR-007** (`spec.md:87`) — "At any given time, exactly one of the two processes (AI CLI or
    shell) MUST be attached to the visible terminal pane." Violated in the divergent direction: the
    client believes a shell instance is attached (it flipped `mode` and pushed a `ShellInstance`),
    while the daemon has no such process and leaves the previous stream in place. The two sides
    disagree about what is attached, which FR-007 exists to prevent.
  - **FR-009** (`spec.md:89`) — "The mode toggle button's icon … MUST always reflect which mode is
    currently active, updated immediately on every switch." The icon updates on a switch that did
    not happen, so it reports a mode the session is not in.
- **Gap identified**: none in the spec text — the requirements are clear and the implementation
  does not meet them. This is drift, not a specification defect.

### plan.md

- **Affected sections**: the daemon port of the mode-toggle path — `SessionOpenShell` /
  `SessionAttachProcess` handling in `crates/micold-daemon/src/server.rs:501-510`, and
  `DaemonState::open_shell` / `DaemonState::attach_process` in `crates/micold-daemon/src/state.rs`.
- **Impact**: the plan treats "open a shell instance" as a fire-and-forget command. That is only
  sound if the operation cannot fail in a way the user needs to know about. It can, so either the
  command needs a failure reply, or the daemon must guarantee the instance exists once it has
  spawned the process. The plan should say which.

### tasks.md

- **Affected tasks**:
  - **T009** (`012-multiple-regular-terminals/tasks.md:104-110`) — "if `active_shell` is `None`,

  - **T015** (`012-multiple-regular-terminals/tasks.md:165-174`) — the sibling

  - **T031 / T053** (`010-daemon-session-persistence/tasks.md:136`, `:244`) — the daemon-side PTY
    spawn and RPC handlers this behaviour now lives in.
- **False completions**: none outright — each task's stated acceptance was met for a *live*
  session, which is the only case anyone exercised.
- **Missing tasks**:
  1. Make `open_shell` fail loudly instead of dropping a spawned PTY: if the session has no live
     entry, do not spawn (or tear down and report), and log it.
  2. Decide the intended behaviour for toggling a not-live session — most likely start the
     session's primary first, as `SessionSelected` already does, so FR-003 holds regardless of

  3. Give `SessionAttachProcess` a failure path rather than a silent no-op, so a client asking for
     a process the daemon does not have learns that it does not.
  4. Log both, matching the diagnostics added for the worktree-delete path (BUG-002 in feature
     008): a user-visible action that silently does nothing must leave a trace.
  5. Regression test: toggling to Regular Terminal mode on a session whose primary process has
     exited still yields an attached shell.

## Root Cause Analysis

`DaemonState::open_shell` (`crates/micold-daemon/src/state.rs`) ends:

```rust
let pty = Arc::new(PtySession::spawn_shell(session, &cwd, &env, scrollback, None)?);
let mut inner = self.lock();
if let Some(live) = inner.sessions.get_mut(&session) {
    live.procs.insert(key, new_proc(pty, session));
}
Ok(())
```

When the session has no entry in the live registry the `if let` does not match, `pty` falls out of
scope, and `PtySession`'s `Drop` kills the child and joins its reader — the shell is spawned and
immediately destroyed. The function still returns `Ok(())`, so the caller
(`server.rs:501-505`) logs nothing.

The client then calls `attach_current_process`, which sends
`SessionAttachProcess { process: Shell(id) }`. `DaemonState::attach_process` opens with:

```rust
let live = inner.sessions.get_mut(&session)?;
if !live.procs.contains_key(&process) { return None; }
```

Both guards return `None`, and the handler treats `None` as "nothing to do":

```rust
ClientMsg::SessionAttachProcess { session, process } => {
    if let Some((pty, framer)) = state.attach_process(session, process) {
        restart_view(state, id, &mut view_stream, pty, framer);
    }
}
```

No log, no reply, no error. Meanwhile the client has already flipped `mode` to `Regular` and
appended a `ShellInstance` to `shells`, because its reducer does that unconditionally
(`crates/micold-client/src/app.rs:1545-1552`). The two sides are now permanently inconsistent for
that session until something else resynchronises them.

**When is a session not live?** The live registry holds only sessions with a running process.
Selecting a session sends `SessionStart` (`main.rs:1491`), so the ordinary path does start it. It
is not live when:

- its primary process exited — `claude` was quit, or crashed past the retry budget, at which point
  `supervise_exited_sessions` drops the live entry while the durable record remains;
- `start_session` failed (logged `session start failed`, but the client is not told and carries on);
- the daemon restarted and the session came back `InterruptedResumable` — 26 of the 33 catalog
  sessions were in exactly this state after the 19:45 restart (7 `session started` entries against
  33 durable records), so at that moment the toggle would have been inert for 26 of them.

The third case makes this considerably more likely right now, because the daemon was restarted
twice this session.

**Alternative mechanism — RULED OUT (2026-08-04).** `State::session_mut` (`app.rs:1945`) resolves a
session only within `workspace.active`, whereas the surrounding code in `main.rs` uses
`workspace.find_session`, which searches every project. That divergence would matter only if
`active_session` could name a session outside the active project. It cannot: `switch_active` →
`restore_after_activation` (`app.rs:1869-1873`) reassigns `active_session` from
`restore_foreground(&key)` — that project's own remembered foreground — on every switch, and the
forget path clears it explicitly when the active project goes away (`app.rs:1163-1174`). The
narrower lookup is consistent with the invariant, so this is not a second defect.

**Version note.** The running client is PID 434003, started 17:47 — *before* the 19:43 package
install — so it is the pre-PR-#57 binary. The changes merged in #57 (which removed the client's
`persist()` calls from this very toggle path) are on disk but not in the running process, and
therefore cannot be the cause of the reported behaviour. They should still be re-checked against
this path once the app is restarted, since they touch it.

## Recommended Fix

1. Run `/speckit.bugfix.patch` to update spec artifacts:
   - Record under **FR-003** that starting the shell is required regardless of the session's
     lifecycle, and name the not-live case explicitly.
   - Note in `plan.md` that `SessionOpenShell`'s fire-and-forget shape requires the daemon to
     guarantee the instance exists once spawned, or to gain a failure reply.
   - Reopen **T009**/**T015** for the daemon port; add the five missing tasks above.
2. Run `/speckit.bugfix.verify` to confirm consistency.
3. Resume `/speckit.implement` to apply the code fix in
   `crates/micold-daemon/src/state.rs` (`open_shell`, `attach_process`) and
   `crates/micold-daemon/src/server.rs:501-510`.
