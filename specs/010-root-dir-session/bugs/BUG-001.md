# BUG-001 — a session whose working directory does not exist sits at `starting…` forever

**Feature**: 010-root-dir-session
**Found by**: quickstart step 11 ("Project root becomes unavailable"), run 2026-08-21 (T027/T029)
**Type**: Implementation defect
**Severity**: Medium
**Status**: **Fixed** — a start refused because the session's folder is gone now records a reason
naming the folder, so every client shows the session `failed` with that sentence instead of
`starting…` (Phase 7, T031–T033; gated by `session_start.rs`'s
`starting_a_session_whose_directory_is_gone_reports_failed_with_the_directory`).
**Fixed**: 2026-09-13 — Phase 7 (T031–T033). Refusal recorded in `start_failures` by
`DaemonState::start_session`. Confirmed by quickstart step 11 re-run headlessly against a pinned
build (`../evidence/T033-step11-rerun.md`): `failed` with the reason, and `running` again after the
folder was restored and restart pressed.
**Patched**: 2026-09-13 — FR-012, SC-007; Phase 7 (T031–T033).
**Scope**: not specific to Default sessions — the same path serves worktree sessions, and both
were observed failing identically. 010's quickstart is simply the first procedure that asks.

## What happens

With a project open, rename its root directory out from under the app
(`mv r10 r10-moved`) and then press the Default entry's **+**:

- a session row appears, titled "New session";
- the status bar reads **`starting…`**;
- and it stays that way. Observed for **80 seconds** before the run moved on. No error
  banner, no snackbar, no inline message, no lifecycle transition to a failed or
  disconnected state.

No process is ever spawned: the daemon's only child throughout is the *other*, healthy
session. So the session is not slow to start — it will never start, and nothing says so.

The same is true for a worktree session whose own directory has been renamed away: press
that row's **+** and it too sits at `starting…` indefinitely
(`../evidence/step11-stuck-starting.png` — red is the Default entry with the project root
gone, blue the worktree entry with its directory gone).

That consistency is what the quickstart's step 11 asks for, and it holds. Its other clause
does not: *"not a crash or a silently-stuck session"*. It is a silently-stuck session.

## Why

`spawn_session_start` in `crates/micold-daemon/src/server.rs:1487` awaits
`start_session(..)` and then:

```rust
match outcome {
    Ok(Ok(())) => {}
    Ok(Err(err)) => {
        tracing::warn!(session = %session.0, %err, "session start failed");
    }
    Err(join) => { … }
}
…
if let Some((client, req)) = reply {
    task_state.send(client, DaemonMsg::OperationOk {
        req,
        result: OperationResult::SessionCreated { session },
    });
```

A start failure is **logged and then discarded**. The client is told `OperationOk` /
`SessionCreated` on the failing path exactly as on the succeeding one, so it has nothing
to render but the optimistic `Starting` state the record was created in — and nothing ever
moves it off, because the supervisor only advances sessions that have a live process.

The warning is not a consolation prize either. The daemon the client auto-spawns inherits
`/dev/null` for stdout and stderr (`ls -l /proc/<daemon>/fd` — `1 -> /dev/null`,
`2 -> /dev/null`), so on the ordinary launch path that `tracing::warn!` is written nowhere
a user or an operator can read it.

## Impact

The user presses a button and gets a row that looks like it is working. There is no way to
tell "starting" from "will never start", and the failure reason — the directory is gone —
is known to the daemon at the moment it happens and is thrown away. Recovery requires
noticing the row is wrong and closing it by hand.

## Suggested fix

Give the failing arm a reply of its own: an `OperationError` carrying the error, and a
session lifecycle transition to a failed/disconnected state so a client that was not the
requester also sees it. The wire type already exists — `DaemonMsg::OperationError` with
`ErrorKind` — and `task_failed` beside this function shows the shape.

Worth doing at the same time: the client-spawned daemon discarding its own logs makes every
defect of this family invisible. A log file under the app's data dir would have made this a
one-line diagnosis.

## What changed on main before the fix (2026-09-13)

Feature 026 (T087) has since changed `spawn_session_start`: a failed start now broadcasts the
catalog, and `start_session` records a reason in the daemon's `start_failures` overlay — which the
snapshot projects as `Failed { reason, attempts: 0 }` and the client announces — for the two
refusals it detects itself (an AI CLI not installed; a conversation gone). A **spawn** refusal
still returned through `?` with no reason, so the broadcast carried the unchanged `Starting`, and
this report's reproduction still held.

## Decision (2026-09-13): catalog, not `OperationError`

The suggested fix proposes an `OperationError` reply for the failing arm. Not taken. The session
*was* created — its row exists, and the client selects it by the `SessionCreated` reply — and only
its start failed. An error reply would make the requester read a created session as a failed
creation, and a `SessionStart` (a resume) has no `req` to address one to anyway. The failure is a
fact about the session that every client must see, which is what the catalog overlay carries and
what 026 FR-010 already uses for the same shape of failure. So the fix is to record the reason for
every spawn refusal; the reply and the wire are unchanged.

The daemon-log half of the suggestion (a log file for the client-spawned daemon) is a separate
change and not part of this fix.
