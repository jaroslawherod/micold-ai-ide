# Bug Report: Non-interactive sourcing skips the default `~/.bashrc`'s own exports

**Type**: Spec gap
**Severity**: Critical
**Feature**: 011-env-include-script (branch `fix/env-are-not-set-by-bashrc`)
**Reported**: 2026-07-21
**Status**: Resolved
**Patched**: 2026-07-21
**Resolved**: 2026-07-21

## Description

Environment variables exported in the user's `~/.bashrc` (the feature's own default script
path, FR-004) are not propagated to either the AI CLI (`claude`) process or the regular-terminal
shell process, on a completely stock Debian/Ubuntu install with no unusual customization.

Root cause: `attempt_env()` (`src/env_include.rs`) sources the configured script via:

```rust
Command::new("bash")
    .arg("--noprofile").arg("--norc").arg("-c")
    .arg(r#"... trap ... source "$1" ... env -0 ..."#)
    .arg("--").arg(path);
```

This is a **non-interactive** bash invocation (no `-i` flag). Debian and Ubuntu's stock
`~/.bashrc` (installed by default in `/etc/skel/.bashrc` and present on essentially every
fresh Debian-family install) opens with:

```sh
# If not running interactively, don't do anything
case $- in
    *i*) ;;
      *) return;;
esac
```

Since the sourcing shell is never interactive, `$-` never contains `i`, so this guard
`return`s immediately — before any of the exports, `PATH` prepends, or version-manager
init blocks that follow it ever execute. The feature resolves successfully (`Success`, no
error surfaced) but silently captures nothing beyond whatever the guard-less prefix happens
to set. Confirmed by hand on this workstation:

```
$ bash --noprofile --norc -c 'source ~/.bashrc; echo "MYVAR=$MYVAR"; echo "dash-flags:$-"' --
MYVAR=
dash-flags:hBc
```

`$-` is `hBc` — no `i` — so the guard fires and the rest of the file (where a real user's
`export`s and `PATH` changes live) never runs.

## Artifact Traceability

### spec.md

- **Affected user story**: User Story 1 — "Sessions automatically pick up my shell
  environment" (P1), and its Acceptance Scenario 1: *"Given a fresh install with no prior
  settings, When the user opens their first session, Then the AI CLI process and the
  regular-terminal shell process both see variables sourced from the platform's default
  include script (e.g. `~/.bashrc`...), with no setup required from the user."*
- **Affected requirements**: FR-004 (default path is `~/.bashrc`), FR-005 (resolve by actually
  sourcing, not parsing), FR-017 (source via bash specifically).
- **Gap identified**: The spec's **Assumptions** section already names this exact failure mode:
  *"Non-interactive sourcing of an interactive-oriented rc file (e.g. a `.bashrc` that
  early-exits when it detects a non-interactive shell) is a known limitation of 'source it for
  real' resolution; this spec does not require working around scripts that intentionally skip
  their own setup in non-interactive contexts."* That framing treats this as a rare,
  script-specific edge case. In reality it is the **stock, unmodified default** `~/.bashrc` on
  Debian and Ubuntu — the two most common Linux desktop targets — which directly contradicts
  SC-001 and User Story 1's explicit "no setup required from the user" / fresh-install promise.
  The spec never reconciles this: FR-004 mandates defaulting to `~/.bashrc`, while the
  Assumptions section simultaneously disclaims making that exact default work.

### plan.md

- **Affected sections**: The Unix sourcing approach documented for `attempt_env`
  (`bash --noprofile --norc -c ...`), inherited from research R1–R6 in `research.md`.
- **Impact**: The plan/research never evaluated interactive-vs-non-interactive sourcing as a
  design axis — no research entry discusses `$-`, the `-i` flag, or the interactive guard
  pattern. The plan needs a decision on how to source `~/.bashrc` such that its interactive
  guard doesn't defeat the whole feature (e.g. sourcing via `bash -i -c` bounded appropriately,
  or another mechanism that still resolves promptly and stays scriptable/non-interactive for
  everything else the wrapper needs — the EXIT trap, `env -0` dump, timeout/kill handling).

## Root Cause Analysis

Implementation drift from an under-scoped spec assumption, not a coding mistake relative to
what was written: FR-017 says "source using the bash interpreter specifically" and T009
literally does that in the most direct way (`bash --noprofile --norc -c`). But the spec's own
Assumptions section pre-emptively waved away exactly the failure mode this produces, without
recognizing that the *default* script path (FR-004) is itself the interactive-oriented rc file
the assumption describes. The gap is in the spec: it never asked "does sourcing bash
non-interactively actually work for the stock rc file we default to?" — and the answer is no on
the two most common Linux distros.

## Reproduction

Added a real-subprocess regression test —
`unix::debian_default_bashrc_guard_blocks_export_from_reaching_session` in
`tests/env_include_resolve.rs` — that writes a script shaped exactly like Debian/Ubuntu's stock
`~/.bashrc` (the standard `case $- in *i*) ;; *) return;; esac` guard followed by an `export`)
and asserts the exported variable is captured. Run it with:

```
mise run test -- --test env_include_resolve unix::debian_default_bashrc_guard_blocks_export_from_reaching_session
```

It currently **fails** (`captured vars: []`), confirming the bug is real and reproducible
outside of any GUI — a real disposable `bash` subprocess is spawned and its actual resolved
environment is inspected, per the existing FR-005 "actually source it" testing convention used
by the rest of that file. The rest of the suite (`mise run test`) remains green — this is the
only failing test.

## Resolution

`attempt_env` (`src/env_include.rs`, Unix branch) now invokes `bash --noprofile --norc -i -c
'<wrapper>' -- <path>` — the added `-i` makes `$-` report `i`, so a script's own
interactive-vs-non-interactive guard (Debian/Ubuntu's stock `~/.bashrc`) no longer short-circuits
before its exports run. `baseline_env` picks up the same flag for free, since it calls
`attempt_env` against `/dev/null`. The EXIT-trap diagnostic capture, timeout/process-group-kill
behavior, and diffing are unchanged in shape; an interactive shell's own stray job-control
warnings (when there's no controlling tty) land on stderr, never on the parsed `env -0` stdout
dump.

Verified: T030's regression test (`unix::debian_default_bashrc_guard_blocks_export_from_reaching_session`)
now passes; full suite (`mise run test`, 54 test binaries) green with 0 failures; `cargo clippy
--no-default-features --all-targets -- -D warnings`, `cargo clippy --features gui --all-targets --
-D warnings`, and `cargo fmt --check` all clean.
