# Bug Report: `env-include` resolves the shell environment in the wrong directory, silently dropping project-scoped PATH tooling (mise/asdf/nvm/etc.)

**Type**: Spec gap
**Severity**: High
**Feature**: 011-env-include-script (branch `fix/the-env-file-is-not-properly-handled`)
**Reported**: 2026-07-23
**Status**: Resolved
**Patched**: 2026-07-23
**Resolved**: 2026-07-23

## Description

`claude` sessions launched by micold-ai-ide (via `spawn_pty` in `src/ui/terminal.rs`) get an
environment that is missing any PATH modification a version manager (mise, asdf, nvm, pyenv, …)
would apply *for that specific project directory* — even though the exact same `~/.bashrc` line
works fine in a plain "regular terminal" session in the same project. Concretely: a project pins
`uv = "0.11.22"` in its `mise.toml`; `~/.bashrc` runs `eval "$(mise activate bash)"`; inside a
`claude` session, `uvx` resolves to nothing (an MCP server configured with `"command": "uvx"` in
`.mcp.json` fails to spawn with ENOENT), while plain `export FOO=bar` lines from the same
`~/.bashrc` come through correctly.

Root cause: `env-include` (this feature, `src/env_include.rs`) resolves the user's shell
environment **exactly once per app run**, by sourcing the configured rc script in a throwaway
`bash --noprofile --norc -i -c '...'` subprocess and diffing its resulting `env -0` dump against a
clean baseline (`attempt_env`, `src/env_include.rs:199`; `resolve`, `src/env_include.rs:266`;
`diff_env`, `src/env_include.rs:62`). That subprocess never has `.cwd()` set — confirmed by
inspection of the current `attempt_env`/`baseline_env` implementations, neither of which calls
`Command::cwd()` on Unix or Windows — so it runs in whatever directory the app process itself
started in, never the project/worktree directory.

The call chain confirms this is resolved with no project context at all (all line numbers verified
against current `src/main.rs`):

- `src/main.rs:174` — `fn resolve_env_include(enabled: bool, script_path: &str, timeout_secs: u64)`
  takes no `cwd` parameter.
- `src/main.rs:362` — called exactly once, from `boot()`, before any project/session is even
  opened.
- `src/main.rs:190` — `refresh_env_include` (re-run on settings save, and on a session's manual
  restart control per FR-007) also takes no `cwd`.
- `src/main.rs:677` — `launch_spec(&cwd, id, LaunchMode::Fresh, &app.env_include.vars)`: the actual
  project/worktree `cwd` *is* known at session-launch time, but it's only used for the PTY's
  working directory — `app.env_include.vars` is the stale, boot-time-resolved global snapshot,
  completely decoupled from `cwd`.
- `src/ui/terminal.rs:286`-`292` (`spawn_pty`) — sets `cmd.cwd(&spec.cwd)` (correct project dir) for
  the `claude` process, but overlays `spec.env` — the stale snapshot — as the *only* source of
  environment variables. `claude` is executed directly
  (`CommandBuilder::new(ClaudeProvider.command())`); it never re-sources `~/.bashrc` itself, so
  this stale snapshot is all it (and every MCP server / subprocess it spawns) ever sees.

Why this makes plain exports work but PATH-via-version-manager fail: `mise activate bash` doesn't
set a static PATH string — it defines a hook that calls `mise hook-env`, which computes PATH
additions by walking up from **the current shell's cwd** looking for a `mise.toml`/
`.tool-versions`. When `env-include`'s one-shot bash sources `~/.bashrc` from the app's own launch
directory (not the project directory), `mise hook-env` finds no relevant `mise.toml` and computes
no PATH change — so the diff against baseline is legitimately empty for `PATH`. A plain
`export TOKEN=value` line, by contrast, is directory-independent and always survives. This is not a
bug in `diff_env`'s filtering logic (it correctly captures *any* changed value, PATH included) — the
bug is that the input directory to the sourcing step is wrong.

This explains why "regular terminal" sessions don't exhibit the bug: `spawn_shell_pty`
(`src/ui/terminal.rs:306`-`319`) spawns a real interactive `$SHELL` attached to a PTY, with `cwd`
correctly set to the project directory — that shell is genuinely interactive (real tty, no `-c`),
so bash sources `~/.bashrc` itself, in the right directory, on its own, independently re-deriving a
correct PATH regardless of whatever stale `env` was overlaid at spawn time. `spawn_pty` (the
`claude` launch path) has no equivalent self-correction, because `claude` is not a shell and never
sources anything.

## Impact

Any MCP server or tool invocation inside a `claude` session that depends on a project-scoped PATH
addition from a version manager (mise, asdf, nvm, pyenv, rbenv, etc.) silently fails to resolve —
typically as `ENOENT` when the app tries to spawn it — with no indication that the cause is a
stale, wrong-directory environment snapshot rather than a missing dependency or bad config. Users
will reasonably (and incorrectly) suspect their `.mcp.json` or the missing tool itself. This
directly contradicts SC-001's explicit promise that "a user's version-manager `PATH` entries ...
are available in a newly opened session's AI CLI process ... without the user performing any
manual setup."

## Reproduction

1. Set up a project with a `mise.toml` pinning a tool only available via mise (e.g. `uv`), and
   `~/.bashrc` containing `eval "$(mise activate bash)"` guarded by the standard
   `case $- in *i*) ;; *) return;; esac` non-interactive guard.
2. Configure a `.mcp.json` MCP server with `"command": "uvx"` (bare name, relying on PATH).
3. Open the project in micold-ai-ide, start a `claude` session, and either try to use that MCP
   server or run `echo $PATH` inside the session — the mise shims directory
   (`~/.local/share/mise/shims`) is absent, even though it's present in a "regular terminal" session
   opened in the same project.

## Artifact Traceability

### spec.md

- **Affected user story**: User Story 1 — "Sessions automatically pick up my shell environment"
  (P1), specifically Acceptance Scenario 1 ("...both processes see variables sourced from the
  platform's default include script... with no setup required from the user") and Acceptance
  Scenario 2 (AI CLI and regular-terminal mode "see the identical set of resolved variables" — this
  one still formally holds, since both spawn sites share the same wrong global snapshot together;
  the real violation is against SC-001, not FR-006).
- **Affected requirements**: FR-004 (default script auto-includes with no user action), FR-005
  (resolve by actually sourcing, not parsing), FR-007 (single shared snapshot, resolved once per
  app run and cached), SC-001 (version-manager `PATH` entries specifically named as in scope).
- **Gap identified**: The spec's Key Entities section defines the "Resolved Environment Snapshot"
  as *"A single shared snapshot ... used by every session"*, and FR-007 mandates it be *"(re-)
  sourced once per application run"*. This design is architecturally incompatible with SC-001's own
  promise about version-manager `PATH` entries: version-manager hooks (mise/asdf/nvm/pyenv/rbenv)
  compute their PATH contribution by inspecting the *current working directory* at the moment the
  hook runs, so a single global, directory-agnostic snapshot can never reproduce what a real
  interactive shell opened in the project directory would produce. The spec never asked "does a
  single per-app-run resolution actually satisfy SC-001's version-manager promise across different
  project directories?" — the answer is no whenever different projects/worktrees pin different
  tool versions or only some of them are inside a mise/asdf-managed directory tree.

### plan.md

- **Affected sections**: Constitution Check, Principle III ("Worktree Integration: Unaffected —
  the include script resolves environment *variables*, not `cwd`; every session's
  worktree/Default-root resolution is untouched. `LaunchSpec.cwd` and `spawn_shell_pty`'s `cwd`
  parameter are not touched by this feature.") and the Scale/Scope line ("One shared
  resolved-environment snapshot per app run (not per session, per spec Key Entities)").
- **Impact**: The Constitution Check's Principle III reasoning conflates two different things: the
  *session's* `cwd` (correctly untouched — `LaunchSpec.cwd`/`spawn_shell_pty`'s `cwd` still resolve
  the project/worktree directory as before) versus the *resolution engine's own* `cwd` input, which
  the plan never identifies as a variable the feature needs to control at all. Because Principle
  III concluded "unaffected," no design section ever considered threading a directory into
  `attempt_env`/`resolve`, and the Scale/Scope line locked in a single global snapshot without
  weighing the directory-dependent PATH case. The plan needs a new decision: either (a) resolve
  per-project/worktree `cwd` at session-launch time (with per-directory caching to preserve the
  "not per session" cost goal), or (b) explicitly re-scope FR-007/SC-001 if per-directory
  resolution is out of scope — but the current plan does neither; it asserts a false premise
  ("unaffected") that closed off the question before it was asked.

### tasks.md

- **Affected tasks**: T009 ("Implement the impure `resolve(...)` orchestrator", `src/env_include.rs`
  — no `cwd` parameter), T013 ("Add ... `App.env_include` field ... computed once in `boot()`" —
  resolved before any project is even open, so no project `cwd` could be threaded in even if
  `resolve()` accepted one), and T014 ("In `launch_spec()`, replace the hardcoded `env` ... with
  `env_include::merge_with_term(&app.env_include.vars)`" — merges the stale global snapshot instead
  of re-resolving or looking up a snapshot for `spec.cwd`). All three are marked `[X]` complete.
- **False completions**: None of these tasks are incorrectly implemented relative to their own
  literal, as-written acceptance criteria — T009 makes T003 pass, T013 correctly wires a
  boot-time-computed field onto `App`, and T014 correctly threads `app.env_include.vars` into
  `launch_spec`. The false completion is at the planning level: satisfying these tasks was believed
  sufficient to satisfy SC-001 for every project, which does not hold for directory-dependent PATH
  tooling — the tasks were under-scoped by the plan gap described above, not miscoded.
- **Missing tasks**: (1) add a `cwd: &Path` parameter to `env_include::resolve`/`attempt_env` and
  call `cmd.cwd(cwd)` before sourcing, keeping `baseline_env` on a neutral directory as it does
  today; (2) thread the project/worktree `cwd` through `resolve_env_include`/a new per-directory
  resolution path at the session-launch call site (`src/main.rs:677`) instead of relying solely on
  the `boot()`-time global snapshot, with per-directory caching so resolution cost still isn't paid
  per session-open; (3) a regression test asserting a `mise.toml`-style directory-dependent PATH
  mutation in the rc script IS captured when the sourcing `cwd` is a directory containing that
  config, and is absent otherwise — mirroring the real-subprocess regression-test pattern BUG-001
  established in `tests/env_include_resolve.rs`.

## Root Cause Analysis

Same shape as BUG-001: a plausible, spec-sanctioned design decision (here: exactly one
directory-agnostic global snapshot per app run, FR-007/Key Entities) that works correctly for the
common case (static, directory-independent `export` lines) but silently fails for a whole class of
widely-used rc-file behavior — there, interactive-only guards; here, version-manager hooks that key
their PATH contribution off the current working directory. The plan's Constitution Check
affirmatively reasoned this was "Unaffected" (Principle III), which foreclosed the question rather
than answering it: it correctly noted the *session's* `cwd` isn't touched, but never asked whether
the *resolution engine* needs `cwd` as an input to faithfully reproduce what an interactive shell in
that directory would export. The gap is in the spec/plan's model of "one global snapshot," not in
any single line of code diverging from what was written.

## Resolution

`env_include::resolve`/`attempt_env` (`src/env_include.rs`) now take a `cwd: &Path` parameter and
call `cmd.current_dir(cwd)` on the *attempt* subprocess before sourcing, so a version-manager
hook's directory-dependent `PATH` contribution resolves correctly for the session's own
project/worktree directory. `baseline_env` also now takes `cwd` and runs in the *same* directory
as the attempt (discovered necessary during implementation: bash exports `PWD`/`OLDPWD` from the
shell's own cwd, so a baseline run in a genuinely different, neutral directory produced a spurious
`PWD` diff on every resolution — the same class of bash-internal artifact the function's existing
doc comment already flagged for `SHLVL`). Since baseline still only sources `/dev/null`, running it
in `cwd` does not trigger any directory-dependent hook the real script might contain.

`src/main.rs`'s `App.env_include` field was split into `env_include_cache: HashMap<PathBuf,
EnvIncludeSnapshot>` (resolved and cached lazily per directory via the new
`env_include_vars_for(app, cwd)`, read at every `launch_spec`/`spawn_and_register_shell_instance`
call site) and `env_include_last_outcome: EnvIncludeOutcome` (the single value Settings displays
for FR-013, since "most recent attempt" no longer maps onto one cache entry once resolution is
per-directory). A new `default_resolution_cwd(core)` helper (active session's directory, else the
active project's root, else the app's own current directory) supplies the one representative
directory `boot()` and `Message::SettingsSaved` need synchronously. `refresh_env_include` now takes
a `cwd` and refreshes only that one cache entry; `TerminalRestartRequested` passes the restarted
session's own directory, while `SettingsSaved` first clears every cached directory (the
enabled/path/timeout settings themselves changed, so all of them are stale) before eagerly
re-resolving one representative directory for immediate feedback.

`spec.md` gained FR-020, a new User Story 1 acceptance scenario, and a new Edge Case; the
"Resolved Environment Snapshot" Key Entity was superseded from a single shared instance to one
cached per directory. `plan.md`'s Constitution Check Principle III and Scale/Scope lines were
corrected; `research.md` R5 and `contracts/env-include-resolution.md` were annotated; `data-model.md`'s
cardinality note was superseded.

Verified: `tests/env_include_resolve.rs`'s new BUG-002 regression tests (Unix and Windows variants
of `directory_dependent_export_is_captured_only_when_cwd_contains_marker`) pass; full suite green —
`mise run test` (`cargo test --no-default-features --all-targets`) and `cargo test --features gui`
both 0 failures; `cargo build --features gui` clean; `cargo clippy --no-default-features
--all-targets -- -D warnings` and `cargo clippy --features gui --all-targets -- -D warnings` both
clean; `rustfmt --check` clean on every file this bugfix touched (pre-existing `cargo fmt --check`
drift in untouched files is unrelated and unchanged).

**Post-implementation code review** (`/code-review medium`) caught two follow-on defects in this
same fix, both corrected:

1. `Message::WorktreeDeleteConfirmed` (`src/main.rs`) never removed the deleted worktree's entry
   from `env_include_cache` — since a worktree recreated for the same branch reuses the exact same
   path (dir names are derived from the branch name), the stale pre-deletion snapshot would
   otherwise be served forever for that path until an unrelated Settings save cleared the whole
   cache. Fixed: the `Ok(outcome)` arm now calls `app.env_include_cache.remove(&wt.path)`.
2. `resolve()`'s doc comment (`src/env_include.rs`) claimed the baseline is "deliberately NOT run
   against `cwd`" — stale text left over from before the `PWD`/`OLDPWD` baseline fix above, and
   directly contradicting `baseline_env`'s own doc comment and implementation. Fixed: corrected to
   describe what the code actually does (baseline also runs in `cwd`; it just never sources the
   real script there).
