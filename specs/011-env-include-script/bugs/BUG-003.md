# Bug Report: `resolve()` is not bounded by the timeout it is given — the baseline probe carries its own

**Type**: Implementation drift (the budget does not cover the work the function does)
**Severity**: Medium — intermittent on CI today; the same code path is what bounds a user's
`env_include_timeout_secs`, so the exposure is a hang at project-open, not only a red build.
**Feature**: 011-env-include-script
**Reported**: 2026-08-10
**Status**: Fixed — see [The fix](#the-fix). Found while merging feature 024, which touches no file
under `crates/micold-core/`.

> **This report was filed with the wrong mechanism, and the title above is its second one.** The
> first version blamed a missing Windows process-group kill, on the reasoning that `read_to_end`
> waits for the last pipe *writer* rather than for the child. That gap is real but it is not what
> the evidence showed, and it explained none of the three other failures. The original diagnosis is
> kept in full under [The first diagnosis, and why it was
> wrong](#the-first-diagnosis-and-why-it-was-wrong) rather than quietly replaced — it was acted on,
> so it should stay legible.

## Description

`crates/micold-core/tests/env_include_resolve.rs`'s `windows` module fails intermittently on
`windows-latest`, and the failures are getting broader rather than random: two tests, then four,
across three CI runs. The clearest single number in them is this one, from
`hanging_script_times_out_promptly`:

```
resolve() took 10.8037897s, expected to return promptly after the timeout
```

That test asks `resolve()` to give up after **500 ms**. It came back after **10.8 seconds** — 21×
its own budget. The other three failures are the same fact seen from the other side: tests with a
**10 second** budget that expected `Success` and got `TimedOut { diagnostic: "" }`.

```
assertion `left == right` failed
  left: TimedOut { diagnostic: "" }
 right: Success
```

So one script overran a 500 ms bound by ten seconds, and three scripts that should finish instantly
failed to finish inside ten. Those are consistent with a single cause, not four.

## The mechanism

`resolve()` takes two subprocesses to answer, and only the second one was ever given the caller's
budget:

```rust
let baseline = baseline_env(cwd);                 // its own hardcoded Duration::from_secs(10)
match attempt_env(path, cwd, timeout) { ... }     // the caller's budget
```

`baseline_env` establishes a clean environment to diff against, by running the same wrapper against
`/dev/null` (Unix) or dumping the process environment (Windows). Both branches passed
`Duration::from_secs(10)` — a literal, unrelated to what the caller asked for.

So the wall clock of `resolve(path, cwd, timeout)` was bounded by **`10s + timeout`**, not by
`timeout`. That is the whole of the 10.8-second measurement: the 500 ms budget was honoured
exactly, by the half of the call it applied to, after the baseline had already spent ten seconds.

The other three failures are the same slowness one layer along: given a 10-second budget, the
*attempt* also failed to finish, so scripts that do nothing returned `TimedOut` where `Success` was
expected. PowerShell on a cold runner is simply slower than these budgets assume.

There is a second defect underneath the first, and it is the worse of the two:

```rust
match attempt_env(Path::new("/dev/null"), cwd, Duration::from_secs(10)) {
    RunOutcome::Exited { stdout, .. } => parse_env_dump(&stdout),
    _ => HashMap::new(),          // <- a failed probe is indistinguishable from an empty environment
}
```

A baseline that timed out returned an **empty map**, and `diff_env` then reported every variable in
the sourced environment as newly set by the user's script. A timeout became a successful-looking
answer containing the entire environment. Nothing in the outcome said so.

## The first diagnosis, and why it was wrong

The first version of this report blamed the absence of a Windows process-group kill:

> `read_to_end` returns when the pipe has no writers left — not when the child this function
> spawned has died. Any descendant that inherited the handle keeps it open, and this call waits
> for it. […] Windows gets `child.kill()`, which terminates one process and none of its
> descendants.

That description of `run_bounded` is accurate, and the asymmetry is real: `kill_process_group` is
`#[cfg(unix)]` and nothing stands in for it on Windows. But it was **not the cause here**, for two
reasons that were available at the time and that I did not check:

1. **It explains none of the other three failures.** `empty_script_succeeds_with_no_vars` sources an
   empty file. There is no grandchild to hold a pipe. A theory that covers one of four failures and
   calls them "one cause, not four" is asserting the conclusion.
2. **Even on Unix the hazard is largely closed already, by redirection rather than by the kill.**
   The wrapper runs `source "$1" >"$diag_file" 2>&1`, so anything the script backgrounds inherits a
   *temp file* as its stdout, not the pipe. The deadlock the doc comment records was observed
   against an older wrapper that captured output with `out=$(source …)`.

I tested (2) rather than assuming it: disabling `kill_process_group` on Linux and running a script
that backgrounds `sleep 120` still returned in 0.04 s. Had the pipe-holding theory been right, that
experiment would have hung.

**The Windows gap is left open deliberately**, and not folded into this fix. It is a latent
asymmetry with no evidence behind it, and closing it means a `windows-sys` dependency and Job Object
FFI that nothing in this environment can exercise — untestable code written against a hypothesis is
how the first diagnosis happened. It is recorded in
[Still open](#still-open) so it is not lost.

## Artifact traceability

- **spec.md** — feature 011's bounded-resolution guarantee. The spec bounds *sourcing the script*;
  the code also runs a baseline probe to make the answer meaningful, and nobody asked whether the
  bound covered it. It did not.
- **research.md R2** — chose `spawn()` + `try_wait()` over `wait_timeout` so the sourcing attempt
  could be bounded. The reasoning is about one subprocess, and the implementation grew a second.
- **BUG-002** — added `directory_dependent_export_is_captured_only_when_cwd_contains_marker` on
  both platforms. Its Windows copy is among the four failures, which is how a correctness test ends
  up reporting a budget defect.

## The fix

**One budget for the whole call.** `baseline_env` takes the caller's timeout instead of a literal
ten seconds, and the attempt gets what is left of it:

```rust
let started = Instant::now();
let Some(baseline) = baseline_env(cwd, timeout) else { /* TimedOut, and say why */ };
let remaining = timeout.saturating_sub(started.elapsed());
```

`timeout` is the user's `env_include_timeout_secs`, and its promise is about how long opening a
project may stall — not about one of the two subprocesses it takes to answer that.

**A baseline that did not complete is reported.** `baseline_env` returns `Option`, and `None` ends
the call with a `TimedOut` naming the baseline rather than diffing against nothing. The two timeouts
mean different things to whoever reads them — the script was slow, or the budget was never big
enough to look at the script at all — and the second is a setting to raise, not a script to debug.

**The test budgets are untouched.** They may still be thin for a cold Windows runner, but that was
recommendation 3 for a reason: widening them is what hides this class of defect, and this one hid
behind them for long enough already. If the Windows job stays noisy after this, the next step is to
measure where the time goes on that runner, not to raise the numbers.

## Still open

**Windows has no counterpart to `kill_process_group`.** Unaddressed here, on purpose — see [The
first diagnosis](#the-first-diagnosis-and-why-it-was-wrong). If it is taken up, it wants a Job
Object with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`, and it wants someone who can run the result on
Windows.

**`run_bounded`'s post-kill drain is unbounded on both platforms.** `read_to_end` after a kill is an
unbounded call inside a function whose whole purpose is to be bounded. On Unix the group kill closes
the pipes so it returns; that is a reason it has not bitten, not a guarantee. A deadline on the drain
would make the bound structural.

## Note on how this was found, and why it will not recur that way

The reproduction above happened on
[#133](https://github.com/jaroslawherod/micold-ai-ide/pull/133), a pull request whose entire diff
was one markdown checkbox. That is what made it worth recording: no Rust, and four Windows tests
failed anyway.

**That route is now closed, and not because anything here was fixed.** CI gained a `classify change`
job shortly afterwards, so a docs-only pull request skips the build-and-test matrix entirely and
reports `ci complete` without running the Windows job at all. #133 was rebased onto that workflow
and merged.

This is worth stating plainly rather than leaving as a loose end, because it changes what a green
build means for this defect. The env-include Windows tests now run on code changes only. That is
correct — a checkbox has no business spending three minutes on a Windows runner — but it also means
this bug's symptom is now *less* likely to be seen, while the cause is untouched: `run_bounded`
still has no Windows counterpart to its process-group kill, and the user's
`env_include_timeout_secs` is still bounded by the runner being fast rather than by the code.

The evidence that stands is the recorded run,
[31391385569](https://github.com/jaroslawherod/micold-ai-ide/actions/runs/31391385569), and the
10.8-second measurement in it against a 500 ms budget.
