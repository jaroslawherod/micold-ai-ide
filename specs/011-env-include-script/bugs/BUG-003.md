# Bug Report: `run_bounded` has no Windows equivalent of its process-group kill, so a timed-out script can block the caller long past its timeout

**Type**: Implementation drift (the Unix path implements a guarantee the Windows path does not)
**Severity**: Medium — intermittent on CI today; the same code path is what bounds a user's
`env_include_timeout_secs`, so the exposure is a hang at project-open, not only a red build.
**Feature**: 011-env-include-script
**Reported**: 2026-08-10
**Status**: Open — not fixed here. Found while merging feature 024, which touches no file under
`crates/micold-core/`.

## Description

`crates/micold-core/tests/env_include_resolve.rs`'s `windows` module fails intermittently on
`windows-latest`, and the failures are getting broader rather than random: two tests, then four,
across three CI runs. The clearest single number in them is this one, from
`hanging_script_times_out_promptly`:

```
resolve() took 10.8037897s, expected to return promptly after the timeout
```

That test asks `resolve()` to give up after **500 ms**. It came back after **10.8 seconds** — 21×
its own budget. The other three failures are the same fact seen from the other side: tests with a
**10 second** budget that expected `Success` and got `TimedOut { diagnostic: "" }`.

```
assertion `left == right` failed
  left: TimedOut { diagnostic: "" }
 right: Success
```

So one script overran a 500 ms bound by ten seconds, and three scripts that should finish instantly
failed to finish inside ten. Those are consistent with a single cause, not four.

## The mechanism

`run_bounded` (`crates/micold-core/src/env_include.rs:125`) polls `try_wait()`, and on timeout it
kills the child and then **reads both pipes to EOF**:

```rust
#[cfg(unix)]
kill_process_group(pid);
#[cfg(not(unix))]
let _ = child.kill();

let mut stdout = Vec::new();
if let Some(mut out) = child.stdout.take() {
    let _ = out.read_to_end(&mut stdout);      // <- blocks until every writer closes
}
```

`read_to_end` returns when the pipe has no writers left — **not** when the child this function
spawned has died. Any descendant that inherited the handle keeps it open, and this call waits for
it.

The Unix path is built around exactly that hazard and says so in its own doc comment: it puts the
child in its own process group (`cmd.process_group(0)`) and signals the **whole group**, "so no
orphaned grandchild can keep the pipes open". `kill_process_group` is `#[cfg(unix)]`.

**Windows gets `child.kill()`**, which terminates one process and none of its descendants. There is
no job object, and nothing else stands in for the group kill. So the guarantee the Unix path was
written to provide — that a timeout returns promptly — is simply absent on Windows, and the
`10.8s` measurement is what its absence looks like.

Two caveats I cannot settle from here, and will not assert:

- I have no Windows machine in this environment, so this is read from the source and the CI
  output rather than observed under a debugger.
- The trigger looks environmental. PowerShell on a cold GitHub runner is slow enough for a
  10-second script budget to expire on a script that does nothing (`empty_script_succeeds_with_no_vars`
  writes an empty file). A faster runner hides all four failures, which is why this has been passing
  most of the time. The environment is what varies; the missing group kill is what turns "slow" into
  "blocked".

## Why this is not only a CI problem

`run_bounded` is not test scaffolding. It is the function that bounds
`Settings::env_include_timeout_secs`, resolved at project-open and on every settings change
(`resolve_env_include`, `crates/micold-client/src/main.rs`). The user-facing promise of that setting
is "this will not hold up opening a project for longer than N seconds".

On Windows, a sourced profile that backgrounds anything holding stdout — and profiles background
things — makes that promise unenforceable. The timeout fires, the process is killed, and the caller
then waits on a pipe held open by a grandchild nothing killed. That is a hang at project-open with
no message, which is worse than a slow one.

## Artifact traceability

- **spec.md** — the timeout requirement this undermines is feature 011's bounded-resolution
  guarantee; the Windows half of it has never been enforced by anything but the runner's speed.
- **research.md R2** — chose `spawn()` + `try_wait()` over `wait_timeout`, and the process-group
  kill is the part of that design that makes the choice safe. It was implemented for one platform.
- **BUG-002** — added the `directory_dependent_export_is_captured_only_when_cwd_contains_marker`
  test on both platforms. Its Windows copy is among the four failing, which is how a
  correctness test ends up reporting an unrelated timing defect.

## Recommended fix

1. **Give Windows the group kill it is missing.** Assign the child to a Job Object with
   `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`, so terminating the job takes every descendant with it —
   the Windows counterpart of `process_group(0)` plus `kill(-pid)`. This is the actual defect.
2. **Do not let the drain outlive the timeout regardless.** Even with (1), reading to EOF after a
   kill is an unbounded call in a function whose whole purpose is to be bounded. Read with a
   deadline and accept a truncated diagnostic; a partial `stderr` is worth more than a hang.
3. **Then reconsider the test budgets.** A 10-second allowance for a script that does nothing is
   thin for a cold Windows runner. Widening it would make the suite quieter — but only do it after
   (1) and (2), because widening it first would hide the defect rather than fix it, and the suite
   has been quietly hiding it for some time already.
