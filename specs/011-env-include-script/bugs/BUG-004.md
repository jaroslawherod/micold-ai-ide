# Bug Report: the Windows env-include tests flake because they race each other, not because they are slow

**Type**: Test-harness defect (the tests create the contention they then fail on)
**Severity**: Medium — no user impact; blocks CI intermittently, and blocks any task whose
completion criterion is "green on all three platforms" (feature 021's SC-004b and T077).
**Feature**: 011-env-include-script
**Reported**: 2026-08-16
**Status**: Fixed — see [The fix](#the-fix). Found while completing feature 021 T057, whose diff is
three files and no Rust.

> **This is BUG-003's symptom with a different cause, and BUG-003 predicted it.** That report closed
> with: *"They may still be thin for a cold Windows runner… If the Windows job stays noisy after
> this, the next step is to measure where the time goes on that runner, not to raise the numbers."*
> The job stayed noisy. This report is that measurement, and the numbers are still not raised.

## Description

`crates/micold-core/tests/env_include_resolve.rs`'s Windows tests fail intermittently on
`windows-latest`. Across feature 021's T053 and T054 the job needed **five attempts to produce two
greens** — three failures, one of which hung for two hours in the same step and had to be
cancelled. The failure is on `main` independently of any branch that hits it.

Every failure has the same shape — an outcome that should be `Success` (or `NonZeroExit`) coming
back as:

```
TimedOut { diagnostic: "the timeout expired while establishing the baseline environment,
                        before the script was sourced — raise the env-include timeout" }
```

That diagnostic is BUG-003's own contribution, and it is doing exactly the job it was added for: it
says the budget was gone *before the script ever ran*, so this is not a slow script.

## The measurement

Four tests failed **simultaneously** (run 31803491299), all on the baseline, none reaching its
script. Timing the whole test binary from the CI logs, across three runs of the same code:

| Run | Wall time for `env_include_resolve` | Result |
|---|---|---|
| 31969821788 | **3.94 s** | pass |
| 31968190389 | **7.06 s** | pass |
| 31803491299 | **14.57 s** | 4 failed, all on the baseline |

Eight tests in this binary spawn a shell, and `resolve()` spawns **twice** per call — once for the
baseline environment, once for the script. Cargo runs them in parallel, so a two-core runner is
starting **sixteen** cold `powershell.exe` processes at once, first launch of the session, with
Defender scanning each.

When it passes, all sixteen starts complete in 3.9–7.1 s of wall time — roughly half a second of
core time each. When it fails, the same work exceeds 10 s *per test*. The per-spawn cost is not
drifting slowly in one direction; its variance is about 3×, which is what Defender plus a cold cache
plus two cores of contention looks like.

**So the margin is the finding.** In the good case each test's two spawns finish well inside a
second against a 10 s budget — a ~10× margin. Running eight of them at once collapses that to under
2×, and a 3× excursion then takes four tests down together. The tests are not thin; they are
racing.

## Why this is the harness and not the code

The contention is an artifact of the test binary. The client resolves one directory at a time and
never races itself, so no user is in this scenario. Two further pieces of evidence point the same
way:

- **The unix module has the same shape with a *tighter* budget** — five seconds against Windows's
  ten — and has never flaked, because `bash` starts in milliseconds. The variable is PowerShell's
  cold-start cost, not the test design.
- **The failures are simultaneous.** A genuinely slow runner degrades tests one at a time as each
  crosses the line. Four crossing together is the signature of a shared resource.

BUG-003's fix is not implicated and must not be reverted. One budget covering the whole call is
correct — it is the promise `env_include_timeout_secs` makes to a user about how long opening a
project may stall. What it did change is the *margin*: before it, the baseline carried its own
hardcoded ten seconds on top of the script's, so contention had roughly twice the room to hide in.
Sharing the budget was right and exposed this; it did not cause it.

## The fix

**Serialise the spawning tests, on Windows only.** A file-level `SpawnGuard` holding a `static
Mutex`, taken as each spawning test's first statement — before any `Instant::now()`, so time spent
waiting for the lock never lands inside a measured window.

```rust
struct SpawnGuard {
    #[cfg(windows)]
    _held: std::sync::MutexGuard<'static, ()>,
}

#[cfg(windows)]
static SPAWNING: std::sync::Mutex<()> = std::sync::Mutex::new(());
```

Three decisions inside that, each of which could have gone the other way:

**The budgets are untouched, and for two tests a bigger number provably cannot work.**
`a_hanging_script_costs_its_own_budget_and_not_the_baselines_as_well` asserts
`elapsed < timeout * 4`, so its budget *is* the thing under test: raising it raises the ceiling
proportionally, while the contended cold-start cost is an additive term that scales with nothing.
Its margin is `3 × timeout` minus the baseline start, and no choice of `timeout` widens that.
Removing the contention is the only move that helps every test in the file at once. This is also
what BUG-003 asked for in as many words.

**The lock is poison-tolerant** (`unwrap_or_else(|e| e.into_inner())`). A failure in this file
manifests as a panic while the lock is held, and a poisoned mutex would turn one real assertion
failure into seven others reporting the poisoning instead of what they were testing — converting a
legible failure into a confusing one at exactly the moment legibility matters.

**Unix keeps running in parallel.** The guard is an empty struct there, so `spawn_guard()` compiles
to nothing. Serialising it would slow two of the three CI platforms to fix a problem neither has.

The two tests that do *not* take the guard are the `nonexistent_path_is_missing_script_with_no_vars`
pair: `resolve()` returns `MissingScript` before spawning anything, so they contend for nothing.

## The guard against a ninth spawning test

Serialising the fourteen call sites that exist does nothing about the fifteenth. Forgetting the
guard is **silent** — the new test passes locally, passes on unix where the guard is a no-op, and
passes on Windows most of the time; it shows up as one more process in a race that other tests then
lose, which is a failure this file has now needed two bug reports to attribute.

`every_test_that_sources_a_script_takes_the_spawn_lock` reads this file and requires that any test
writing a script and resolving it also takes the lock. Its needles are assembled at runtime
(`format!("{}_{}(", "write", "script")`) because the test reads the file it is written in, so a
literal would match its own body — the same self-matching trap `service_capability_fakes.rs`
records hitting, where a fixture naming a real port reported itself as a live violation.

**The vacuity check is a separate test, and the reason is a probe collision.** Both live-fire probes
initially failed the same single test, so the failure sets could not tell them apart. Feature 021
T055 hit exactly that shape and the answer there was to split the test rather than drop a probe;
`the_body_scan_finds_the_tests_it_is_meant_to_read` is that split.

**Three probes, three distinct failure sets:**

| Probe | Fails |
|---|---|
| A spawning test loses its `spawn_guard()` | the rule |
| The body scan's needle matches nothing | the vacuity check |
| A missing-script test starts writing a script | both, plus the test itself |

**What could not be probed, recorded rather than omitted**: the serialisation itself. On Linux the
guard compiles to an empty struct, so removing the mutex changes nothing any local test can observe.
Its evidence is the measurement above, not a red test.

## The cost, stated rather than discovered later

Serialising sixteen starts that previously overlapped roughly doubles this binary's Windows wall
time — an estimated **~4 s → ~8 s**, derived from the passing runs above. That is the price of the
margin and it is worth paying; the binary is a small part of a job that takes minutes.

**Measured after the fix landed, and the prediction is not confirmed.** The first Windows run of the
guarded binary (31971389095) finished in **6.14 s** — inside the 3.94–7.06 s range the *unguarded*
passing runs occupied, not the ~8 s predicted. One sample cannot separate the two explanations: the
serialisation may cost less than modelled because the sixteen starts were already queueing on two
cores rather than truly overlapping, or this runner may simply have been a fast draw. What the
number does rule out is a cost large enough to notice — whatever serialisation is charging here, it
is smaller than the run-to-run spread it was meant to remove. The estimate above is left as written
so the prediction and its outcome stay legible together.

## Reproduction

Not reproducible on demand — it is a scheduling race against a runner's I/O and antivirus. The
evidence is the three CI runs tabulated above, all of the same code. The clearest single
observation is that the four failures share a timestamp to the millisecond
(`2026-08-14T13:15:10.28…`).

## Verification limits

**The Windows path cannot be executed locally.** `SpawnGuard`'s mutex field exists only under
`#[cfg(windows)]`, so the code that matters is first *run* on CI. It is type-checked before that
with `cargo clippy --target x86_64-pc-windows-msvc -p micold-core --tests -- -D warnings`, which is
the same pre-flight BUG-003 used for its Job Object fix and the same limit it recorded.

**Absence of the flake is weak evidence.** The Windows job passed on three consecutive runs
*before* this fix (#178 and both of #182's), and passed again on the first run *after* it (#189's
31971389095). A green run does not demonstrate the fix worked; only a sustained absence across many
runs does, and the honest read of this change is that it removes a
mechanism the evidence identifies, not that it has been proven to end the symptom. If the job stays
noisy, the next step is per-spawn instrumentation on the runner — this report measured at binary
granularity, and the half-second-per-start figure is derived from that, not observed directly.

Feature 021's T057 is a documentation task: three files, no Rust. The flake was already recorded as
