# Bug Report: the daemon's environment-include cache loses an invalidation that races a resolve, and runs the script once per concurrent first ask

**Type**: Implementation drift (FR-007 and FR-020 already promise both behaviours; the concurrent
case was never written down, so nothing tested it)
**Severity**: Medium — no crash and no data loss, but a Settings change can silently fail to take
effect for a directory until the daemon restarts, and repeated start-menu opens can each pay the
script's full cost (up to `env_include_timeout_secs`)
**Feature**: 011-env-include-script (branch `fix/env-include-cache-loses-an-invalidation-and-re-runs-the-script`).
The cache itself was written by feature 010's T098 (BUG-003 of 010) to carry this feature's FR-007 /
FR-020 into the daemon; feature 029's BUG-001 added a third caller (the AI-CLI availability answer).
**Reported**: 2026-09-27
**Status**: Patched
**Patched**: 2026-09-27 — FR-021 and an Edge Case added to `spec.md`; `plan.md` gained a design
correction; `data-model.md`'s lifecycle annotated; `tasks.md` gained Phase 9 (T037–T040); a
cross-feature note added to feature 010's T098.

## Description

`DaemonState::env_include_vars_for` (`crates/micold-daemon/src/state.rs:531-559`) is the daemon's
per-directory environment-include cache, used by every spawn site (`start_session`,
`respawn_primary`, `open_shell`) and, since feature 029's BUG-001, by the AI-CLI availability
answer (`ai_clis_available_in`, reached from `server.rs:659` through `spawn_blocking`). It reads the
settings and probes the cache under one short lock, drops the lock, resolves (a real subprocess, up
to the configured timeout), then takes the lock again and inserts. Nothing records that a resolve is
in progress. Two failures follow:

1. **A lost invalidation.** `set_env_include` (`state.rs:995-1011`, the `SettingsSet` path) calls
   `invalidate_env_include_all` (`state.rs:626`), and `WorktreeDelete` (`server.rs:1407`) calls
   `invalidate_env_include` (`state.rs:619`). Both only remove entries that exist *now*. A resolve
   that started before the invalidation holds no entry, so the invalidation leaves no trace, and its
   unconditional insert at `state.rs:555-557` puts the pre-change environment back. Every later
   spawn or availability answer for that directory is then served the stale value from the cache,
   for the rest of the daemon's run or until the next invalidation.
2. **No single flight.** Two first-time asks for the same directory both miss at `state.rs:543`,
   and both run the script. The start menu's availability request (029 BUG-001) is sent on each
   open, and its handler is a detached task, so a user who opens the menu repeatedly while the
   first resolution is still running starts one full script run per open, each bounded only by
   `env_include_timeout_secs`.

This was found by feature 029's M1 review A and declined there as pre-existing, recorded in
`specs/029-pi-cli-provider/bugs/BUG-001.autopilot.md` under *Follow-ups not done*, with the two
review findings in *Declined review findings* (`state.rs:565`, `server.rs:659`).

## Is cache coherence specified? Yes, both halves — implicitly

- **Invalidation wins.** FR-007: the script "MUST also be re-sourced fresh … whenever … (a) the
  user saves a change to the enabled flag, script path, or timeout". FR-016: a change "MUST apply
  to sessions/terminal processes spawned after the change". Feature 010's FR-012b repeats it for
  the daemon: "a change MUST take effect for every subsequently spawned session/shell process
  without requiring a service restart". A spawn after a save that runs with the pre-save
  environment breaks all three. Directory-level invalidation on worktree deletion is not in 011's
  spec text; it is 010's T098 applying the same hazard BUG-002 (011) recorded (a recreated worktree
  reuses its path), and FR-020's "once per (application run, directory)" is what it protects.
- **One run per directory.** FR-020: "only the first launch against a given, not-yet-cached
  directory pays it"; the Key Entity *Resolved Environment Snapshot*: "recomputed once per
  (application run, directory) pair". Two concurrent first asks paying twice breaks that.
- **What the spec never says** is what happens when these meet concurrency: a refresh that lands
  during a resolve, or two first asks at once. That is a missed edge case, not a new behaviour, so
  this is a patch to feature 011 (FR-021) and not a new spec.

## Reproduction

On `origin/main` at `23a0e0ee`, Linux. Put this file at
`crates/micold-daemon/tests/probe_env_include_cache_race.rs` and run
`scripts/build-lock.sh cargo test -p micold-daemon --test probe_env_include_cache_race -- --nocapture --test-threads=1`.
The script logs each run, reads a marker, then blocks until a gate file exists, so the test decides
exactly when a resolve is in flight. Observations go through the public `ai_clis_available_in`,
which shares the spawn sites' cache.

```rust
#![cfg(unix)]
use std::{path::{Path, PathBuf}, sync::Arc, time::{Duration, Instant}};
use micold_core::settings::{JsonFileSettingsStore, Settings, SettingsStore};
use micold_core::store::JsonFileStore;
use micold_daemon::{catalog::Catalog, state::DaemonState};

fn service(store: &Path, script: &Path) -> Arc<DaemonState> {
    JsonFileSettingsStore::at(store.join("settings.json")).save(&Settings {
        env_include_enabled: true,
        env_include_script_path: script.to_string_lossy().into_owned(),
        env_include_timeout_secs: 30,
        ..Settings::default()
    }).unwrap();
    Arc::new(DaemonState::new(Catalog::load(
        Box::new(JsonFileStore::at(store.join("projects.json"))),
        Box::new(JsonFileSettingsStore::at(store.join("settings.json"))),
    )))
}
fn gated_script(dir: &Path) -> (PathBuf, PathBuf, PathBuf, PathBuf) {
    let (runs, marker, gate, script) =
        (dir.join("runs"), dir.join("marker"), dir.join("gate"), dir.join("env-include.sh"));
    std::fs::write(&script, format!(
        "echo run >> '{}'\nV=$(cat '{}')\nwhile [ ! -e '{}' ]; do sleep 0.02; done\nexport PROBE_MARK=\"$V\"\n",
        runs.display(), marker.display(), gate.display())).unwrap();
    (script, runs, marker, gate)
}
fn runs(p: &Path) -> usize { std::fs::read_to_string(p).map(|s| s.lines().count()).unwrap_or(0) }
fn wait_runs(p: &Path, n: usize) {
    let end = Instant::now() + Duration::from_secs(20);
    while runs(p) < n { assert!(Instant::now() < end); std::thread::sleep(Duration::from_millis(10)); }
}

#[test]
fn probe_invalidation_racing_a_resolve_is_lost() {
    let (dir, project) = (tempfile::tempdir().unwrap(), tempfile::tempdir().unwrap());
    let (script, runs_file, marker, gate) = gated_script(dir.path());
    std::fs::write(&marker, "old").unwrap();
    let state = service(dir.path(), &script);
    let (s, cwd) = (Arc::clone(&state), project.path().to_path_buf());
    let first = std::thread::spawn(move || s.ai_clis_available_in(&cwd));
    wait_runs(&runs_file, 1);                                  // resolve in flight, has read "old"
    std::fs::write(&marker, "new").unwrap();
    state.set_env_include(Some(true), None, None).unwrap();   // the SettingsSet path
    std::fs::write(&gate, "").unwrap();
    first.join().unwrap();
    state.ai_clis_available_in(project.path());               // a later ask must re-resolve
    assert_eq!(runs(&runs_file), 2, "invalidation overwritten by the stale insert");
}

#[test]
fn probe_concurrent_first_asks_run_the_script_twice() {
    let (dir, project) = (tempfile::tempdir().unwrap(), tempfile::tempdir().unwrap());
    let (script, runs_file, marker, gate) = gated_script(dir.path());
    std::fs::write(&marker, "v").unwrap();
    let state = service(dir.path(), &script);
    let (s1, c1) = (Arc::clone(&state), project.path().to_path_buf());
    let a = std::thread::spawn(move || s1.ai_clis_available_in(&c1));
    wait_runs(&runs_file, 1);
    let (s2, c2) = (Arc::clone(&state), project.path().to_path_buf());
    let b = std::thread::spawn(move || s2.ai_clis_available_in(&c2));
    std::thread::sleep(Duration::from_millis(800));           // let the second ask reach the cache
    std::fs::write(&gate, "").unwrap();
    a.join().unwrap(); b.join().unwrap();
    assert_eq!(runs(&runs_file), 1, "two first asks each ran the script");
}
```

Observed on `origin/main` (2026-09-27; re-run by the bug-rubric reviewer with the same result),
both fail for the reported reason:

```
  left: 2
 right: 1
test probe_invalidation_racing_a_resolve_is_lost ... FAILED

  left: 1
 right: 2

```

The probe exercises the `SettingsSet` path only. The `WorktreeDelete` path
(`invalidate_env_include`, `state.rs:619-621`) has the same shape — a `remove` of an entry that an
in-flight resolve has not inserted yet, then the same unconditional insert — so it fails the same
way by reading; T037's Case 2 establishes its red run when the test is written.

Probe A's count of 1 means the later ask never ran the script: it was served the environment
resolved under the settings from before the save. The probe was removed from the tree after the
run; the fix milestone's T037/T038 turn it into committed regression tests.

## Root Cause Analysis

`state.rs:531-559` is a check-then-act split across two lock acquisitions, and the "act" is an
unconditional `insert`. Dropping the state lock around `env_include::resolve` is required (the
module invariant: no subprocess and no timeout-long wait under the state lock), but dropping it
gave up two things the lock had been providing for free: that nothing changes the cache between the
check and the insert, and that no second caller can start the same work. Neither was put back —
there is no generation or epoch for an insert to compare against, and no in-flight entry for a
second caller to wait on. The invalidation functions (`state.rs:619-628`) therefore act only on
completed entries. The spec's own words for the cache ("once per (application run, directory)",
"re-sourced fresh whenever … the user saves") were written for the pre-010 client, where resolution
ran synchronously on the single UI thread and neither overlap could occur; moving the cache into a
multi-connection daemon made both reachable, and 029's availability answer made the second one
routine.

## Recommended Fix

A per-directory entry that is either *ready* (the merged vars) or *in progress* (a shared slot the
resolving caller fills), plus a generation counter on the cache:

- Reading the settings, probing the cache and claiming the *in progress* entry (recording the
  generation) happen in **one** critical section; `set_env_include` bumps the generation in the same
  critical section that persists the new settings. Otherwise a resolver can read the old settings,
  lose the lock to a save, and then claim a slot at the new generation.
- A miss inserts an *in progress* entry under the lock, then resolves off-lock. A concurrent ask for
  the same directory finds the *in progress* entry and waits on it off the state lock (the wait is
  bounded by the resolver's own timeout), so the script runs once. A drop guard on the resolver fills or abandons its slot
  and removes its entry if the resolve unwinds, so a waiter never parks on a slot nobody will fill:
  it falls back to resolving itself.
- `invalidate_env_include_all` bumps the generation and clears every entry, *in progress* ones
  included; `invalidate_env_include(path)` removes that path's entry. A resolver inserts its result
  only if its entry is still the one it created (same generation, same slot); otherwise it hands the
  value to the callers already waiting on it (they asked before the change) and caches nothing.
- An ask after the invalidation finds no entry and starts a fresh resolve under the new settings.

Tests first (T037, T038 — the probe above, made deterministic without the 800 ms sleep where
possible, e.g. by waiting until the second ask is observably parked), then the fix (T039), then the
doc comments and the `docs/user-guide/settings.md` note (T040).
