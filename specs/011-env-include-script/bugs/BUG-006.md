# Bug Report: a stored environment-include script path that does not exist is never reported while the feature is off

**Type**: Spec gap. The code does what the spec and contract say. The report asks for behaviour
feature 011 never intended: an opinion about the path while the feature is switched off.
**Severity**: Medium. Nothing crashes, but a bad stored pair (off plus a missing path) looks like a
deliberate choice. In the observed case it stood between the user and a CLI that was installed and
working.
**Feature**: 011-env-include-script (branch `fix/github-issues`)
**Reported**: 2026-09-29, GitHub issue #435
**Status**: Open. Routed to Phase 1 (a new spec that cites BUG-006). Feature 011's artifacts are
**not** patched: see [Size decision](#size-decision).

## Description

`~/.local/share/micold-ai-ide/settings.json` held
`"env_include_script_path": "/tmp/does-not-exist.sh"` with `"env_include_enabled": false`. It sat
there unnoticed through many launches. The pair came from the client's unit tests, which used to
write the real settings store. That leak is fixed under feature 029's T069 (PR #410) and is out of
scope here. The report is about what the application does with the pair afterwards:

- Settings shows the stored string and nothing else.
- Sessions get the service's own environment, so a CLI that `~/.bashrc` would have put on `PATH`
  is missing. The user saw this as the application lacking a feature.
- Nothing anywhere says the script cannot be found.

The issue leaves three points open:

1. Should Settings validate the path when it is shown or saved?
2. Should a resolution that cannot find the script report it once, rather than falling back
   silently?
3. What is the right recovery for a stored path that has gone missing?

## Reproduction

On `origin/main` at `feb3b474`, Linux. Add this as a temporary
`crates/micold-core/tests/zz_repro_435.rs` and run
`CARGO_TARGET_DIR=$(scripts/build-lock.sh --print-target-dir) cargo test -p micold-core --test zz_repro_435 -- --nocapture`:

```rust
use micold_core::env_include::*;
use std::{path::Path, time::Duration};
#[test]
fn repro() {
    for enabled in [false, true] {
        let s = snapshot_for(&SubprocessResolver, enabled, "/tmp/does-not-exist.sh",
                             Duration::from_secs(5), Path::new("/tmp"));
        println!("REPRO enabled={enabled} outcome={:?} vars={}", s.outcome, s.vars.len());
    }
}
```

Observed:

```
REPRO enabled=false outcome=Disabled vars=0
REPRO enabled=true outcome=MissingScript vars=0
```

The client stores this outcome as `App::env_include_last_outcome`, at boot
(`crates/micold-client/src/shell/startup.rs:299-307`) and on every save or settings echo
(`shell/persist.rs:387`, `shell/daemon_sync.rs:569,982`). The Environment page renders it through
`failure()` in `crates/micold-client/src/ui/settings/environment.rs:37-46`, which maps `Disabled`
to `None`. So:

- **Feature off, path missing** (the reported pair): no note. This reproduces as reported.
- **Feature on, path missing**: the page shows the caution "Script not found" under the timeout
  field. Here FR-013 is met.

## Artifact Traceability

### spec.md

- **User Story 3, Acceptance Scenario 1**: "Given the configured script path does not exist, When
  a session is launched, Then … the failure is visible to the user". This scenario assumes the
  script is sourced, which needs the feature to be on.
- **FR-013**: the indication is required "when the most recent attempt to resolve the include
  script failed". With the feature off, no attempt is made (FR-001, User Story 2 Acceptance
  Scenario 2: "no script is sourced"), so nothing is required.
- **Edge Cases**: a blank path "is treated the same as disabled". Nothing covers a non-blank path
  that is stored but not used.
- **SC-006**: "When the most recent include attempt failed, a user can discover that fact". Again,
  this is about an attempt.
- **Gap**: the spec has no requirement about a stored path that is invalid while the feature is off.
  It also has none about validating a path when it is typed or saved.

### contracts/settings-ui.md

- Layout step 4 settles the reported state explicitly. The failure block is "Rendered only on
  failure — nothing is shown here on `Success`/`Disabled` (SC-006)." Staying silent while the
  feature is off is therefore the contracted behaviour, not drift.

### plan.md

- The plan's Summary and the Constitution Check describe the failure note as in-memory diagnostics
  of a resolution attempt (FR-008/FR-013). There is no validation step at save time.

### tasks.md

- **T025** (the failure-diagnostic block) and **T022** (the save flow) match their contract.
- **False completions**: none. Every task does what it says.
- **Missing tasks**: any task here would add new behaviour. Those tasks belong to the Phase 1 spec.

## Root Cause Analysis

This is not an implementation error. Feature 011 treats the path only as an input to a resolution
attempt: `snapshot_for` (`crates/micold-core/src/env_include.rs:587-602`) returns `Disabled` before
the path is ever examined when the flag is off. The only existence check is `resolve()`'s
`path.exists()` (`env_include.rs:421-423`), and that runs only as part of an attempt. So no code
path can form an opinion about a path the feature is not using. The spec (FR-013, SC-006) and the
contract (`settings-ui.md` layout step 4) wrote this down deliberately.

## Size decision

**Phase 1.** Every fix the issue invites is behaviour that feature 011 never intended, and that its
contract rules out for the reported state:

- validating the path when it is shown or saved, whether the feature is on or off;
- reporting "cannot find the script" beyond the Settings note that exists today;
- a recovery for a stored path that has gone missing (for example, offering the platform default
  from FR-004).

The bug rubric (`.claude/skills/speckit-autopilot/references/review-rubrics.md`, Bug rubric bullet 3)
classifies new behaviour as a MAJOR finding that sends the flow to Phase 1. So `speckit-bugfix-patch`
is not run against this Closed spec. The new spec cites BUG-006 as its input, and it decides the
issue's three open points in its clarify phase.

## Observations for the Phase 1 spec (not fixed here)

- **Only the client's representative directory is reported.** The client resolves the script for
  one directory (`default_resolution_cwd`) to feed the note. The daemon resolves the script
  separately for each session's directory (`DaemonState::env_include_vars_for`,
  `crates/micold-daemon/src/state.rs:548-578`). When one of those resolutions fails, the daemon
  only calls `tracing::warn!` and never reports it to a client. For an absolute missing path the
  two resolutions agree, so the reported case is unaffected. But a script that fails only in one
  project's directory, or a relative path, fails silently for that directory's sessions. That
  falls short of FR-013's "MUST NOT be silent". The new spec should decide where the outcome of a
  resolution is reported.
- The notice about a missing AI CLI (`missing_cli_notice`, feature 027 FR-023b) says which CLI is
  missing. It does not connect the absence to environment-include being off, even though that was
  the cause in the observed case.
