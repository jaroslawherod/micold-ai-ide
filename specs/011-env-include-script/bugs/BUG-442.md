# Bug Report: a session's manual restart does not re-source the environment-include script

**Type**: Implementation drift (FR-007(b), the Clarifications answer and User Story 3's Acceptance
Scenario 4 all promise it; feature 010 moved spawning and the cache into the daemon and carried
only the Settings-save trigger across)
**Severity**: Medium — no crash and no data loss, but the documented recovery path ("fix the script,
then use the session's restart control") does nothing until the service restarts or Settings are
saved, and nothing on screen says so
**Feature**: 011-env-include-script (issue #442, branch `claude/project-thread-9zhd63`). The daemon's
cache was written by feature 010's T098; the restart paths are feature 010's
`ClientMsg::SessionStart` and `ClientMsg::SessionRestartShell`.
**Reported**: 2026-10-06
**Status**: Patched
**Patched**: 2026-10-06 — FR-007 clarified in `spec.md`; `plan.md` gained a design correction;
`data-model.md`'s lifecycle annotated; `tasks.md` gained Phase 10 (T041–T046).

## Description

FR-007 requires the include script to be re-sourced fresh, for the restarted session's directory
(FR-020, BUG-002), when **(a)** the user saves a change to the environment-include settings, or
**(b)** the user invokes a session's manual restart control. Since feature 010 every session
process — AI CLI and Regular Terminal shell alike — is spawned by the daemon, from the daemon's own
per-directory cache (`DaemonState::env_include_vars_for`, `crates/micold-daemon/src/state.rs`).
That cache is dropped only by:

- `set_env_include` (the `SettingsSet` path) — trigger (a);
- `invalidate_env_include` — called from `ops.rs` on a worktree delete and from
  `mcp/tools.rs` after a refused AI-CLI start;
- `refuse_and_forget_env` — the launch gate's own refusals (feature 037).

No restart path reaches any of them:

- **The AI CLI tab's restart control** (`TerminalRestartRequested`,
  `crates/micold-client/src/shell/daemon_sync.rs::on_terminal_restart_requested`) re-sources the
  *client's* own copy of the cache (`refresh_env_include`, `shell/env_include.rs`), then sends
  `ClientMsg::SessionStart` — the same message every passive start sends (selecting a session,
  reconnecting, `daemon_sync.rs` around L242, L738, L955, L1319, L1712). The daemon cannot tell
  the restart from a plain start, and its `SessionStart` arm (`server.rs`) spawns from the cache.
  The client's refreshed copy feeds only its own displays (Settings outcome, `issues.rs`); no
  process is spawned from it.
- **A Regular Terminal instance's restart control** (`ShellInstanceRestartRequested`) sends
  `ClientMsg::SessionRestartShell`. Its arm in `server.rs` runs `close_shell` then `open_shell`,
  and `open_shell` (`state.rs`) reads `env_include_vars_for(&cwd)` — a cache hit.

Supervision's automatic respawn of a crashed primary (`respawn_primary`, `state.rs`) also reads the
cache. That is correct: FR-007(b) names only the user's manual control, and an automatic respawn
re-sourcing would put the script's cost back on a crash loop.

### Reproduction (on `origin/main` f613369)

A throwaway connection-level test (the harness of
`crates/micold-daemon/tests/shell_open_refused_reported.rs`, environment-include on, a script that
appends one line to a log per run, a Regular session at the project root): `SessionOpenShell`
instance 1, then `SessionRestartShell` instance 1. Output:

```
REPRO runs after open=1 after restart=1
```

The restart spawned a fresh shell and the script did not run again: a change made to the user's rc
file between the two would not reach the restarted shell. The AI-tab path is shown by the code
trace above: its only wire message is `SessionStart`, indistinguishable from a passive start.

### Drift, not a decision

Nothing in feature 010 (spec, plan, tasks, contracts) or later says the restart trigger was
dropped. The evidence points the other way: the client's `on_terminal_restart_requested` still
cites FR-007 and still refreshes (its own, now display-only, cache); 010's T100 carried trigger (a)
to the daemon (`SettingsSet`) and named no equivalent for (b); and feature 037's spec
(`specs/037-explain-hidden-cli/spec.md`, "The state changes while Settings is open") assumes "A
session restart re-sources the script". The fix is in the code; FR-007(b) stays as written.

## Root Cause Analysis

Feature 010 moved session spawning and the per-directory cache from the client into the daemon
(T098) and wired trigger (a) across the wire (T100: `SettingsSet` clears the daemon cache). Trigger
(b) lived in the client's `TerminalRestartRequested` handler as a direct call to the client's own
cache, and the port left it there: the restart became a `SessionStart`, which carries no "fresh"
intent, and the `SessionRestartShell` arm was written against the daemon cache
without an invalidation. No test asserted that a restart re-runs the script in the daemon, so the
gap stayed invisible; BUG-005's trace found it (`BUG-005.autopilot.md`, "Follow-ups not done").

## Recommended Fix

1. `ClientMsg::SessionRestartShell`'s arm drops the restarted session's directory from the daemon
   cache before `open_shell`.
2. A new `ClientMsg::SessionRestart { session }` — a `SessionStart` that first drops the session's
   directory from the cache — sent by the AI tab's restart control in place of `SessionStart`;
   `PROTOCOL_VERSION` 29 → 30 and the 010 messages contract.
3. Plain `SessionStart` and supervision's `respawn_primary` keep reading the cache.
4. Run `/speckit.bugfix.patch`, `/speckit.bugfix.verify`, then implement.
