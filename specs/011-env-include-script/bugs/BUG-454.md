# Bug Report: a session directory's environment-include failure is only logged by the service, never reported

**Type**: Implementation drift. FR-013 requires a user-visible indication of a failed attempt, and
FR-020 makes the attempt per session directory. The service resolves per directory but reports
nothing; the only indication comes from the client's own, separate resolution for one
representative directory.
**Severity**: Medium. Sessions still start (User Story 3 holds), but the sessions of the failing
directory run without the script's variables and nothing in the interface says why. The log line
that is written also puts the script's captured output into the service's on-disk log.
**Feature**: 011-env-include-script
**Reported**: 2026-10-06, GitHub issue #454 (found by the fresh reviewer of BUG-006,
`bugs/BUG-006.md` "Observations for the Phase 1 spec")
**Status**: Patched
**Patched**: 2026-10-06 — FR-022 added to `spec.md`; `contracts/settings-ui.md` step 4 and the
Interaction contract annotated; `plan.md` gained a design correction; `tasks.md` Phase 10
(T041–T046). No task reopened.

## Description

When the service (`micold-daemon`) resolves the environment-include script for a session's
directory and the outcome is not `Success`, it only writes a `tracing::warn!`. The outcome and its
captured stdout/stderr are then dropped, the merged environment without the script's variables is
cached for that directory, and every later spawn there uses it.

The Settings Environment page's failure note is fed by a **different** resolution: the client's own
`refresh_env_include` / boot resolution for `default_resolution_cwd` (the active session's
directory, else the active project root, else the process cwd). The two agree for an absolute path
that is missing everywhere. They disagree when:

- the script path is relative, so it resolves differently per working directory;
- the script fails only in one project's directory (a version-manager hook that errors for that
  project's configuration, or a slow per-directory step that runs into the timeout);
- the failing session is not the active one, so the representative directory is another one.

In those cases the failing directory's sessions get no script environment, and Settings reports
nothing (or success) because its own resolution succeeded.

## Reproduction

On `origin/main` at `107ab7ed`, by trace (deterministic; no timing involved):

1. `DaemonState::spawn_env_for` (`crates/micold-daemon/src/state.rs:813-854`) is the only place the
   service sources the script. Its initializer is:

   ```rust
   let (vars, outcome) = micold_core::env_include::resolve(Path::new(&script_path), cwd, …);
   if outcome != micold_core::env_include::EnvIncludeOutcome::Success {
       tracing::warn!(?outcome, cwd = %cwd.display(), "env-include resolution did not succeed");
   }
   ResolvedEnv { vars: merge_with_term(&vars), env: attempted(&outcome) }
   ```

   `attempted` keeps only the category (`SpawnEnv`); the `diagnostic` carried by `NonZeroExit` and
   `TimedOut` is dropped with `outcome`.
2. The category reaches a client in exactly two places, both from feature 037 and both only when an
   AI CLI is **missing**: the availability answer (`availability_in`, `state.rs:932`) and the start
   refusal (`state.rs:2806-2840`). A Regular session, or an AI-CLI session whose CLI is on the
   service's own `PATH`, starts normally and no message carries the failure: `snapshot_locked`
   (`state.rs:1039`) projects `start_failures`, `ended` and live state, never the cache.
3. The client's note reads `App::env_include_last_outcome`, written only by its own
   `refresh_env_include(app, default_resolution_cwd(..))` (`crates/micold-client/src/shell/env_include.rs:64-93`,
   `shell/startup.rs:286`, `shell/persist.rs:442`, `shell/daemon_sync.rs:647`) and rendered by
   `ui/settings/environment.rs`. Nothing from the service writes it.
4. A directory-dependent failure is trivial to set up: a script
   `[ -f .fail-here ] && { echo "hook failed"; exit 3; }; export FOO=1` with `.fail-here` in
   project A only. A session in A spawns without `FOO`; the client's resolution for project B (or
   for A while a B session is active) succeeds; the Environment page shows no note.

Second facet, same line: when the service runs detached it logs to a file
(`crates/micold-daemon/src/logging.rs:296-326`, `default_log_path()` =
`<data_local_dir>/micold-daemon.log`, default filter `info`). `?outcome` formats
`NonZeroExit { code, diagnostic }` / `TimedOut { diagnostic }` with the script's captured output,
so that output is written to an on-disk log, which FR-013 forbids ("MUST NOT be written to the
persisted settings file or any other on-disk log").

## Artifact Traceability

### spec.md

- **User Story 3, Acceptance Scenarios 1-3**: "the failure is visible to the user in a non-blocking
  way" when "a session is launched". For a session whose directory failed, it is not.
- **FR-013**: "When the most recent attempt to resolve the include script failed … the system MUST
  surface a non-blocking, user-visible indication … MUST NOT be silent … MUST include the failure
  category … plus the script's own captured stdout/stderr output … MUST NOT be written to … any
  other on-disk log." Both halves are broken by the service's resolution.
- **FR-020**: resolution runs per session directory, so the attempt that matters for a session is
  the one made for its directory. FR-013 was written when there was one attempt; it never said

- **SC-006**: "a user can discover that fact … from within the app (e.g. the Settings interface)".
- **Gap identified**: FR-013 is silent on *which* attempt's failure is shown once there is one

## Root Cause Analysis

The report path was designed when the client did the only resolution (one snapshot, one outcome,
one note). BUG-002 made resolution per directory but kept one "last outcome" in the client. Feature
010 then moved session spawning, and with it the per-directory resolution that actually feeds
sessions, into the service; the port logged the outcome instead of reporting it, because the wire
had no place for it and the client's own representative resolution still fed the note. From then on
the note described a resolution no session necessarily used. The `?outcome` in the log line was a
debugging convenience that, once the service logged to a file, broke FR-013's no-on-disk rule.

## Decision: where a per-directory failure is reported

**Settings, beside the representative-directory note** (not on the session). Reasons: the 011
contract makes the Settings failure block the sole FR-013 surface and rules out new toasts or
banners; the service already overlays runtime-only state onto the catalog snapshot at send time
(`start_failures` and live activity onto session summaries), so this is one new top-level wire field
(a protocol version bump) and one more list in the existing block; the catalog is broadcast when a
failure is cached or removed, so open windows update, and a window that connects later gets it in
its welcome snapshot.
A per-session banner would be new surface the spec deliberately did not add.

Shape: the catalog snapshot carries, per failing cached directory, the directory, the failure
category and the captured output (runtime-only, projected at send time like `start_failures`,
never written to the catalog file). The Environment page lists each one under the existing note,
naming the directory; an entry whose outcome equals the representative note's own is folded into
it rather than repeated (an absolute path missing everywhere still shows one note). An entry goes
away when its cache cell does (a Settings save, the worktree's deletion, or a refused AI-CLI start
there: `set_env_include`, `invalidate_env_include`, `refuse_and_forget_env`), and a later attempt
that succeeds replaces it. This fix adds no new invalidation trigger. The service log keeps the category and directory only.

## Size decision

Within 011's intent: FR-013 already requires the indication and SC-006 already names Settings; the
fix delivers it for the per-directory attempts FR-020 introduced. Phase 10 adds 6 tasks
(T041–T046), under the 10-task limit.
