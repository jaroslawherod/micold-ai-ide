# Bug Report: The switcher's tabs were specified as containers; "tab" meant an indicator strip

**Type**: Spec conflict — FR-004a, written by BUG-001, contradicts the intended design
**Severity**: Medium — the strip is legible and correct, it is the wrong idiom
**Feature**: 012-multiple-regular-terminals
**Reported**: 2026-08-16
**Supersedes**: BUG-001's FR-004a in part (the container rule only; its layout and colour rules stand)
**Status**: **Fixed** — spec patched 2026-08-16 (FR-004a's two container clauses struck, FR-004b
added for the indicator and its top-edge placement); implemented as the indicator strip and gated by
`crates/micold-client/tests/terminal_tabs.rs`. The expansion below (the AI session as an unclosable
tab) shipped separately as feature `026-ai-session-tab`, now Closed. The deferred rename is not part
of this report.

## Description

BUG-001 fixed a switcher that rendered as one filled pill among loose numbers, and specified the
repair as *container versus container*: active `Filled`, inactive `Outlined`, both drawing a
background or an outline. That shipped and works — the row reads as a strip of distinct pills.

It is not what "tab" meant. The intended idiom is a Material **primary tab**: no container at all,
just the label plus a short accent bar marking the active one, as in a browser or an editor's tab
strip. Two changes from what BUG-001 specified:

1. **No container on any tab.** Both active and inactive are bare labels — the active one takes the
   accent colour and carries an indicator; the inactive ones are muted text.
2. **The indicator sits at the tab's *top* edge**, not the bottom where Material puts it. This bar
   is anchored to the bottom of the window, so the content a tab belongs to is *above* it. A bottom
   indicator would point away from what it selects; the reference for this design is a top-anchored
   tab row, and flipping the edge is what preserves its meaning here.

## Artifact Traceability

### spec.md

- **Affected requirement**: **FR-004a** (added 2026-08-16 by BUG-001) — "every entry ... MUST render
  inside a container of the same shape and size" and "The active/inactive distinction ... MUST be
  carried by the containers' emphasis, never by one entry having a container and another having
  none."
- **Conflict**: the second clause forbids exactly the design intended. The clause exists to rule out
  the *original* defect — container against **bare text** — and it over-corrected: it ruled out the
  correct fix along with the wrong one, because both lack a container on the inactive entries. What
  distinguishes them is that a tab strip marks the active tab by an **indicator**, which the
  original had nothing of.
- **What survives**: FR-004a's other clauses are untouched and still right — the label centred, the
  close control trailing, and the tab's size independent of which tab is active (SC-008). FR-011a
  (nested controls take the tab's own foreground) also stands, and matters more without a container:
  the close glyph must follow the active tab's accent colour rather than the bar's.

### contracts/terminal-instance-switcher-ui.md

- **Affected sections**: "Tab form" and "Active entry", both written by BUG-001. The first mandates
  a container; the second says the distinction must be "container versus container".
- **Impact**: both are replaced by an indicator rule. The `Icon::Close` correction and the
  nested-control colour rule from BUG-001 stay.

### Recorded rationale that turns out to be wrong

`instance_switcher_row`'s doc comment — inherited from the original implementation and preserved
through BUG-001 — argues: *"a background-color difference is legible at a glance, unlike a thin edge
accent (SC-004)."* That is the reasoning being overturned, and it should be struck rather than
silently dropped. An indicator satisfies SC-004 provided it is an accent bar of real thickness
(§7's tab indicator is 3dp, not a hairline) and the active label also takes the accent colour, so
the cue is carried twice — by weight and by colour — rather than by one thin line.

### tasks.md

- **Affected tasks**: T039 and T036/T047's gates from Phase 9.
- **Gates that now encode a superseded rule** — these must be *replaced*, not deleted quietly:
  - `tab_variant_always_draws_a_container` (inline in `ui/terminal.rs`) asserts neither arm is
    `ButtonVariant::Text`. The new design requires `Text` on both.
  - `the_tab_variant_comes_from_the_shared_rule` (`tests/terminal_tabs.rs`) asserts the call site
    delegates to `tab_variant`, which no longer chooses between containers.
  Both were added three days ago by BUG-001 and were correct for it. A test that pins a decision is
  exactly what should fail when the decision changes; the replacement must pin the *new* rule (an
  indicator exists, and only the active tab has one) so the strip keeps a mechanical guarantee.

## Root Cause Analysis

A vocabulary mismatch that a screenshot resolved in one glance and two rounds of prose did not.
BUG-001 read "tab" as "the entries need containers, like a chip strip", which the original
container-vs-bare-text defect supported: the visible wrong thing was a missing container, so the
missing container looked like the whole bug. It was half of it. The other half — that a tab strip
marks its active member with an indicator — was never stated in any artefact, so nothing contradicted
the container reading.

Worth noting where the contract *was* right and got discarded. Before BUG-001 it said the active
entry should mirror `TreeItem::selected`; BUG-001 rejected that analogy for not transferring from a
sidebar row to a numeric strip. Both readings were reaching for "make the active one obvious" without
either naming the idiom, and neither the spec nor the contract ever said the word *indicator*.
FR-004b now says it.

## Recommended Fix

1. `/speckit.bugfix.patch` — amend FR-004a (strike the container clause, keep the rest), add FR-004b
   for the indicator and its top-edge placement, and rewrite the contract's two sections.
2. Replace the two superseded gates with ones asserting the indicator rule.
3. Implement in `instance_switcher_row`, and strike the "unlike a thin edge accent" rationale.
4. Re-run `quickstart.md` §8 with the `visual-pass` skill in both themes — §8's checks were written
   for containers and need rewording to the indicator form first.

## Expansion — the AI session belongs in the strip, as an unclosable tab

**Added 2026-08-16 at the reporter's request.** The tab strip should list the session's **AI CLI
process as a tab too**, at the **right-hand end** of the row (clarified by the reporter after this
section was first written, which said "first in the row"), and that tab must have **no close
control** — one AI CLI
process exists per session by FR-016 and closing it is not a thing a user may do.

This is larger than the indicator change and should be judged on its own, because it does not merely
add an entry — it makes the strip the session's whole surface rather than a Regular-Terminal-only
list, and two shipped requirements are written against the narrower idea:

- **FR-005** — "The instance-switching control MUST be visible only once a session has more than one
  open Regular Terminal instance; it MUST remain hidden while the session has zero or one open
  instance." With the AI process always present as a tab, the row is never empty, and the rule that
  hides it stops making sense: a session with one shell has *two* tabs (AI and the shell), which is
  precisely the case FR-005 says to hide. Either FR-005 is rewritten around a new counting rule, or
  the strip appears in states where today there is deliberately nothing.
- **FR-006** — "The existing primary AI-CLI/Regular mode-toggle control MUST continue to work as it
  does today: a single icon-button that switches the visible pane between the session's AI CLI
  process and Regular Terminal mode." An AI tab **is** a way to switch to the AI CLI, so the toggle
  and the tab become two controls for one action, and they can disagree: pressing the toggle while a
  shell tab is selected has to move the indicator, and selecting the AI tab has to flip
  `Session.mode`. That is a state-synchronisation question, not a styling one.

**Clarified by the reporter**: the AI tab **carries the indicator when the AI pane is showing**. That
answers the state question above, and answers it well — the strip's selection is simply *what the
pane is displaying*, which `Session.mode` and `active_shell` already encode between them:

| Session state | Indicator sits on |
|---|---|
| `mode == AiCli` | the AI tab |
| `mode == Regular` | the tab of whichever instance `active_shell` names |

So the strip **derives** from existing state rather than introducing a selection of its own, and the
drift risk disappears: there is nothing to keep in sync, because there is only one source. Pressing
the mode toggle moves the indicator because it changes `mode`; selecting the AI tab is another way to
write the same field. FR-006's toggle can stay without contradiction — it becomes a shortcut for a
tab that is now also visible, not a competing control. `tab_indicator_colour`'s signature widens from
`is_active: bool` to whatever names the displayed pane, and that is the whole mechanism.

What remains genuinely open is **FR-005's visibility rule** — with the AI process always present, a
session with one shell has two tabs, which is exactly the case FR-005 says to hide. That is a
decision, not a detail: either the strip becomes always-visible in a session (and the bar gains a
permanent row it does not have today), or it hides at one tab and the AI tab appears only alongside a
second, which is odd in the other direction.

**Recommendation, and what happened**: land the indicator change (the rest of this report) first —
it is complete, verified and independent, and the AI tab builds directly on it. **Done**: the AI tab
became its own feature, `specs/026-ai-session-tab`, specified and merged separately. FR-005's
visibility rule is superseded there (the strip becomes always visible), the AI tab sits at the
strip's right-hand end, it is labelled with the existing AI CLI icon, and it carries no close
control. This report's job for it is finished — it is recorded here only because it is where the
requirement was first raised.

## Related — deferred, not in scope here

The user's intent for the strip is that a terminal instance can be **renamed** from a right-click
menu, so a tab shows a name rather than its ordinal. That is a feature, not this bug, and is
recorded here only because it constrains this fix: **the label must not be sized as a two-digit
box**. BUG-001 set `TAB_LABEL_WIDTH = 20.0` for exactly that, which would have to be undone the day
a name appears. The fix below should size the label to its content with a sensible maximum and
ellipsis, which serves both the ordinal today and a name later, at no extra cost now.
