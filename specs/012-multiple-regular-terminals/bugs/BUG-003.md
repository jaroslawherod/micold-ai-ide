# Bug Report: A Regular Terminal instance never leaves `Starting`, so a shell you are typing into reads `starting…` for its whole life

**Type**: Implementation gap (FR-008 states the requirement exactly; nothing implements it)

**Severity**: Medium (no data loss and nothing is offered that would destroy work, but the status is
wrong for the whole life of every shell instance, and `exited` — the state FR-008 exists to make
visible — is unreachable, so a dead shell is indistinguishable from a live one)

**Feature**: `012-multiple-regular-terminals` (FR-008; also `010-daemon-session-persistence`, whose
wire carries no shell-instance state for the client to reconcile against)

**Reported**: 2026-08-16

**Status**: **Fixed** (2026-08-16) — Phase 11 (T057–T062)

**Fixed**: 2026-08-16 — `SessionSummary::live_shells`, overlaid from the live registry in
`DaemonState::overlay_live_summaries` and adopted by `reconcile_catalog`; `PROTOCOL_VERSION` 5 → 6.
Two regression tests, both observed red first. No requirement added: FR-008 already said this, and no
task reopened — the client machinery was correct and simply never driven

## Description

Open a Regular Terminal instance and type in it. It works — the shell is spawned, its output
streams, keystrokes reach it. The bar beside it reads **`starting…`**, and goes on reading
`starting…` until the instance is closed.

When that shell later exits, the bar still reads `starting…`. `ShellLifecycle` is set to `Starting`
by `open_shell_instance` and never moves again, whatever the process does.

**Corrected while writing the fix**: this report first said the instance sat at `NotStarted` and so
read `idle` with a `restart` control offered. That was wrong — `open_shell_instance`
(`micold-core/src/session.rs:304`) creates the instance and immediately calls `start_shell()`, so
`Starting` is reached and `NotStarted` is not. The failing test written from the wrong claim is what
caught it. The consequence is narrower than first described: no destructive control is offered for a
running shell. It is also, exactly, `010` BUG-011's second face — a process that is up, labelled
`starting…` forever, because nothing reports that it started.

Found while fixing [`010` BUG-011](../../010-daemon-session-persistence/bugs/BUG-011.md) and recorded
in that fix's Phase 27 as out of scope: same user-visible defect, different mechanism, its own seam.

## Root cause

Two halves, and neither is the rendering.

**1. The client's transitions are unreachable.** `Session::mark_shell_running` and
`mark_shell_exited` (`micold-core/src/session.rs:358`, `:366`) are called from exactly one place
each — `Message::ShellInstanceRunning` and `Message::ShellInstanceExited`
(`micold-client/src/app.rs:1566`, `:1571`). **Neither message is emitted anywhere in
`crates/micold-client`.** Both appear only in `tests/app_state.rs`, which drives them directly. The
comments at `app.rs:1544` and `:1564` say the binary "follows up with `ShellInstanceRunning` once
it's up"; it does not, and never did.

`Session::open_shell_instance` (`session.rs:304`) creates the instance and calls `start_shell()`, so
`Starting` is reached — and is the last transition that ever happens. `Running` and `Exited` are
unreachable in production, which is three of FR-008's four states missing or wrong.

**2. There is nothing to emit them *from*.** The daemon knows: `LiveSession.procs` is keyed by
`SessionProcess::Shell(id)`, so a live shell instance is a key in that map. It just never says so.
`SessionSummary` has no field for shell instances, and no `DaemonMsg` variant names one — the daemon
models shell instances in its live registry and not on the wire at all. So this is not a client that
ignores what it is told; it is a client that is told nothing.

Rendering is downstream and correct given its input: `session_status`
(`micold-client/src/ui/terminal.rs:523`) maps `Some(ShellLifecycle::Starting)` to `"starting…"`, and
`attached_process_restartable` (`:569`) matches `None | Some(NotStarted | Exited)` — so a stuck
`Starting` withholds the restart control as well, which is the one mercy here: the control is absent
for an exited shell that needs it, rather than present for a live one.

## Artifact traceability

### spec.md

- **FR-008** is the requirement, and it is not vague: *"Each Regular Terminal instance MUST
  independently track its own shell lifecycle (not-started, starting, running, exited), matching the
  lifecycle states already defined for today's single instance, with no automatic restart on
  unexpected exit."* Three of the four states are unreachable in production. This is a plain
  implementation gap — unlike `010` BUG-011 beside it, which was a genuine spec gap.
- **FR-010** (manual per-instance restart) is the collateral damage. The control is derived from the
  lifecycle, and a lifecycle stuck at `Starting` never says a restart is available — so the affordance
  FR-010 requires is unreachable for exactly the instance that needs it, one whose shell has exited.

### Why the gates could not see it

`crates/micold-client/tests/app_state.rs:595` drives `ShellInstanceRunning` and `ShellInstanceExited`
directly and asserts the resulting lifecycles. It proves the reducer's transitions are correct, and
cannot notice that nothing sends them — the same shape that hid `010` BUG-011, in the same file.

## Recommended fix

Report shell-instance liveness on the wire, rather than inferring it in the client:

1. Add the live shell-instance ids to `SessionSummary`, overlaid from the live registry in
   `DaemonState::overlay_live_summaries` — exactly where `activity`, `input_serial` and the live
   title are already overlaid, and for the same reason (the catalog is durable state and cannot see
   the live map). This is wire-visible, so `PROTOCOL_VERSION` must be bumped.
2. Drive the transitions from `reconcile_catalog`, which already adopts every other per-session
   value the daemon publishes. The client stays the allocator of instance ids — the snapshot says
   which of *its* instances are live, and never creates one.
3. Read an absence as death only for an instance previously seen `Running`. `open_shell_instance`
   already leaves a new instance at `Starting`, and a spawn takes a tick or two to appear in the
   snapshot — treating that gap as an exit would flap the bar for every terminal opened.

The alternative — inferring "running" in the client from the arrival of a frame — is what `010`
BUG-011's fix deliberately rejected, and it can never detect an exited shell, since the absence of
frames is indistinguishable from a quiet one.

Whichever is chosen, `Message::ShellInstanceRunning`/`ShellInstanceExited` should be wired up or
deleted. An unemitted variant with a comment describing a follow-up that does not exist is what made
this, and BUG-011 before it, look like a transport problem rather than a state one.
