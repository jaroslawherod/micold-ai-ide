# Bug Report: The bar's `restart` control restarts the session's AI CLI, so an exited Regular Terminal cannot be restarted from it

**Type**: Implementation gap (FR-010 requires the affordance; the one on screen targets the wrong
process)

**Severity**: Medium — with a single Regular Terminal instance it is the *only* restart affordance on
screen, so FR-010 has no reachable route at all in that case. Nothing is destroyed; the control is
simply inert

**Feature**: `012-multiple-regular-terminals` (FR-010)

**Reported**: 2026-08-18

**Status**: Reported

**Evidence**: [the control takes hover, and does nothing](../evidence/BUG-004-restart-hover.png)

## Description

Open a Regular Terminal, type `exit`, and the bar correctly reads `exited` and offers `restart`.
Press it and **nothing happens**: no process is spawned, the status stays `exited`, and the daemon
logs neither a shell open nor a failure.

The control is not mis-drawn or mis-placed. Hovering it raises its state layer, so the pointer is on
a live hit target; two clicks at its centre produced nothing.

## Root cause

The bar's control is wired to the session, not to the process the bar is describing.

`ui/terminal.rs:413` builds it with `.on_press(Message::TerminalRestartRequested)`. That message is
handled by `on_terminal_restart_requested` (`shell/daemon_sync.rs:1146`), which calls
`view_and_start(app, id)` — a `ClientMsg::SessionStart` for the **session**. In Regular mode the
session's AI CLI primary is still alive, so `DaemonState::start_session` takes its
`if self.live_session(id).is_some() { return Ok(()) }` early return and the request is a no-op. The
shell instance the user is looking at is never touched.

The predicate that *shows* the control already knows better. `attached_process_restartable`
(`ui/terminal.rs:558`) splits on `session.mode` and asks about the **attached** process — the shell
instance in Regular mode, the AI CLI in `AiCli` mode. The button beside it does not split at all.
So one fact — "the thing you are looking at is not running" — is read correctly to decide whether to
offer a restart, and then ignored when deciding what the restart does.

`Message::ShellInstanceRestartRequested` exists and works (`daemon_sync.rs:1165` sends
`ClientMsg::SessionRestartShell`), but it is only reachable from the per-tab affordance at
`ui/terminal.rs:729` — and with a single instance there is no tab strip on screen, so that route
does not exist for the commonest case.

## Why this appeared now

It did not regress; it became **reachable**. Before [BUG-003](./BUG-003.md), a shell instance never
left `Starting`, and `Starting` is not in `attached_process_restartable`'s set — so the bar never
offered `restart` in Regular mode and the mis-wiring had nothing to act on. Making `exited` reachable
is what put the control on screen. A fix that makes a state observable will do that.

## Artifact traceability

- **FR-010**: *"The system MUST let the user manually restart an individual Regular Terminal instance
  after it has exited, restarting only that instance."* The control that satisfies this for a
  single-instance session restarts something else, and that something else is already running.
- **`010` FR-013** owns the session-level restart the bar currently performs. The bar is shared
  between modes, so it needs the same split its own predicate makes.

## Recommended fix

Give the button the split the predicate already has: in Regular mode with an active instance, press
`ShellInstanceRestartRequested(session, instance)`; otherwise `TerminalRestartRequested`. Deriving
both the control's *presence* and its *action* from one reading of "which process is attached" is
what stops them disagreeing again — the same lesson as this feature's BUG-001 and `025`'s.

A test belongs where the gap is: assert the message the bar's restart control carries in Regular
mode, not merely that a control is present.
