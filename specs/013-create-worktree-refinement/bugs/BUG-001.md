# Bug Report: Creation overlay dismisses on an outside click while a create is in flight

**Type**: Spec gap
**Severity**: High
**Feature**: 013-create-worktree-refinement (Worktree Creation & Deletion Flow Refinement)
**Reported**: 2026-09-17
**Status**: Patched
**Patched**: 2026-09-18

## Description

Creating a worktree in a repository with several git submodules can take 30 seconds or more. While
that create is running, the add-worktree overlay is still an ordinary dismissible dialog: a press on
the scrim — any click outside the dialog card — closes it, exactly as Escape does.

When that happens:

1. The overlay disappears, taking the progress indicator and the current-stage description with it.
2. The create keeps running in the daemon; nothing cancels it.
3. A success shows only as a new entry in the worktree list; a failure is reported nowhere.
   `create_failed` writes into the form that no longer exists, so its message is dropped on the
   floor. (A connection interruption is already reported as a notification when no form is open —
   `shell/daemon_sync.rs`, 010 BUG-020.)

The user is left with no way to tell whether the worktree was created, is still being created, or
failed. The only recovery is to watch the worktree list and guess.

## Reproduction

1. Open a repository that has several git submodules (so a create takes long enough to act during).
2. Open Add Worktree, fill in a name, press Create.
3. While the progress indicator shows, click outside the dialog card (or press Escape).
4. Observed: the dialog closes; a later failure of that create is shown nowhere. Expected: the
   dialog stays open; only its Cancel button closes it.

Headless: `crates/micold-client/tests/add_worktree_dismissal.rs::a_form_whose_create_is_in_flight_is_dismissed_by_neither_escape_nor_the_scrim`
fails on `origin/main` with `left: Some(WorktreeForm(Cancelled))`.

Expected: while a create is in flight, the overlay must not be dismissible by a scrim click (or by
Escape, which is the same rule via the same message). The only way out during creation is an
explicit Cancel action inside the dialog.

## Artifact Traceability

### spec.md (013-create-worktree-refinement)

- **Affected user story**: User Story 3 — "See what's happening while a worktree is being created"
  (P3), and its acceptance scenario 1 ("a continuously visible progress indicator appears") and
  scenario 4 ("the progress indicator stops advancing, the stage at which it failed is
  identifiable").
- **Affected requirements**:
  - **FR-006** — "the overlay MUST show a continuously visible progress indicator for the duration
    of the creation operation". An outside click removes the whole overlay mid-operation, so the
    indicator is not visible for the duration.
  - **FR-008a** — added by BUG-009 for exactly this class of failure: the indicator must stay on
    screen for a stage that lasts minutes. BUG-009 covered the indicator being replaced by a
    disconnect banner; this is the same "is it hung?" state reached by a stray click.
  - **FR-009** — "If creation fails at any stage, the progress indicator MUST stop advancing and the
    failed stage MUST be identifiable from the display, followed by the existing failure/error
    message." Once the overlay is gone, no failure message is shown at all.
  - **FR-010** — success clears the indicator and closes the overlay. The spec describes closing as
    a *consequence of completion*; it never says the overlay may close for any other reason while a
    create is running.
  - **SC-002** — "100% of worktree-creation attempts that take longer than a couple of seconds show
    a specific, current-stage description at some point beyond the initial state". A dismissed
    overlay shows nothing for the rest of the attempt.
  - **SC-005** — "Creation failures at any stage are reported with the specific stage identifiable".
    A failure after dismissal is reported nowhere.
- **Gap identified**: The spec's Edge Cases section asks "What happens to the 'Create'/'Cancel'
  buttons while the progress indicator is showing?" and answers "Unchanged from today." It never
  asks what happens to *dismissal* of the overlay itself while creation is running. No requirement
  states that the dialog is non-dismissible during an in-flight create, and no requirement states
  what the user is told if the overlay does close before the create resolves.

### Cross-feature: 017-material-component-architecture

- **FR-009** (unified dismissal) already carries the escape hatch this bug needs: "Modal dialogs
  MUST dismiss on Escape and on scrim click, **unless explicitly declared non-dismissible because
  losing input would destroy work**." `micold_core::overlay::Surface::NonDismissibleDialog` exists
  and is covered by `crates/micold-core/tests/overlay_dismissal.rs`, but no production dialog
  declares it — it is currently reachable only from tests. The add-worktree dialog during a create
  is precisely the case FR-009's exception was written for.
- 017 **FR-024** limits its sanctioned behavior change to *how* a surface is dismissed, so declaring
  this dialog conditionally non-dismissible is within 017's model rather than a violation of it.

### plan.md (013)

- **Affected sections**: "Summary" and the US3 progress-display slice — the stage model and its
  render path. The plan treats the progress display purely as a rendering concern and never models
  the overlay's dismissal state as part of the creation lifecycle.
- **Impact**: the plan needs a statement that the form's dismissal rules are derived from its
  status (editing vs. creating), not fixed for the surface. `AddWorktreeDialog::dismissal()` in
  `crates/micold-client/src/features/worktree_form.rs:327` is a constant today; it must become a
  function of `WorktreeForm::status`.

### tasks.md (013)

- **Affected tasks**: Phase for US3, T017–T020 (the `CreateStage` sequence, the reducer arms that
  set `form.stage`, and the progress render). These are correctly complete for what they specify —
  they deliver the stage model and its display.
- **False completions**: none. No task ever claimed to make the overlay hold its ground during a
  create, so no task is falsely marked done.
- **Missing tasks**:
  1. Make `AddWorktreeDialog::dismissal()` return non-dismissible rules while
     `WorktreeFormStatus` is the in-flight-create state, and dismissible rules otherwise
     (`crates/micold-client/src/features/worktree_form.rs:318-331`).
  2. Ensure the modal render path honors that — `crates/micold-client/src/ui/mod.rs:610` wires
     `on_dismiss` from `crate::app::on_escape(state)`, which always answers `Some(Cancelled)` for
     this dialog, so both the scrim and Escape
     must stop producing a cancellation while a create is in flight.
  3. Decide and specify what the in-dialog Cancel does during a create: close the overlay and
     abandon the (still-running) operation, or request cancellation of the operation. Today
     `cancelled()` (`worktree_form.rs:346`) simply drops the form with no daemon-side effect.
  4. Report the outcome of a create whose form is gone. `create_failed` goes through `with_form`, which
     is a no-op when the form is closed, so a failure after dismissal is silent. (`create_interrupted`
     is never reached without a form: `shell/daemon_sync.rs` already notifies in that case.) A notification is the natural home now that one exists.
  5. Tests: a core-level rule test that the creating form is a `NonDismissibleDialog`, and a
     client-level test that a scrim press and an Escape during an in-flight create produce no
     cancellation message.

## Root Cause Analysis

Spec oversight compounded by an unexercised escape hatch.

Feature 013 specified the *content* of the creation overlay during a long operation (progress
indicator, stage description) but not its *modality*. At the time 013 was written, the overlay had
its own bespoke dismissal behavior; feature 017 later unified dismissal across all five floating
surfaces and made "dialogs dismiss on scrim click" the default. 017 anticipated this exact case and
provided `Surface::NonDismissibleDialog`, but nothing in 013's artifacts told 017's implementers
that the add-worktree dialog qualifies while a create is running — so the surface was registered
with the plain `Layer::Dialog` rules and inherits scrim dismissal in every state.

BUG-009 already fixed one way the progress display could vanish mid-create (liveness reaping the
connection). This is the second way, from the opposite direction: the user's own stray click. The
underlying gap is the same one FR-008a names — the display must survive the whole of a long stage —
and the fix belongs in the same place: an explicit requirement that the overlay is not dismissible
while an operation it owns is in flight.

## Recommended Fix

1. Run `/speckit.bugfix.patch` to update spec artifacts:
   - Add an FR to 013 requiring the create overlay to be non-dismissible (no scrim click, no
     Escape) while a create is in flight, leaving explicit in-dialog Cancel as the only way out.
   - Add an FR covering what the user is told if a create resolves while its form is not on screen.
   - Extend 013's Edge Cases with the outside-click-during-creation case.
   - Note in 017's FR-009 that the add-worktree dialog is the first production user of the
     non-dismissible exception.
2. Run `/speckit.bugfix.verify` to confirm consistency across spec, plan, and tasks.
3. Resume `/speckit.implement` to apply the code fix.
