## Description

In the create-worktree form, choosing **an existing branch** is refused for branches that look
perfectly ordinary. The app says the branch is already checked out in a worktree and names that
worktree — but the named worktree is nowhere in the left-hand sidebar, so the user has no way to go
to it, no way to release the branch, and no way to proceed. The flow dead-ends: the blocked panel
offers dismissal only (no reuse, no overwrite), and Create stays disabled.

**Expected**: either the branch can be used, or the app names a holder the user can actually find
and act on.

**Actual**: the app names a holder that does not exist as far as the visible application is
concerned, and the branch becomes permanently unusable through the UI.

### Ground truth from `max-speed`

`git worktree list --porcelain` in `/home/jaro/workspaces/max-speed` returns 15 records. Only 8 of
them live under `.claude/worktrees/`. The rest are invisible to the app:

| Worktree path | Branch it holds | In the sidebar? |
|---|---|---|
| `/home/jaro/workspaces/max-speed` (main checkout) | `main` | no — it is the project itself |
| `/home/jaro/workspaces/ksef-bug001-docs` | `docs/invoice-ksef-bug-001` | **no** — outside the repo |
| `.git-paw/worktrees/fix-allegro-attributes-overridden-persistence` | `fix/allegro-attributes-overridden-persistence` | **no** — wrong parent dir |
| `.git-paw/worktrees/fix-olx-auth-error-mapping` | `fix/olx-auth-error-mapping` | **no** — wrong parent dir |
| `.git-paw/worktrees/fix-olx-missing-attributes` | `fix/olx-missing-attributes` | **no** — wrong parent dir |
| `.git-paw/worktrees/fix-photo-selection-reset-on-refresh` | `fix/photo-selection-reset-on-refresh` | **no** — wrong parent dir |
| `.git-paw/worktrees/fix-various-ui-issues` | `fix/various-ui-issues` | **no** — wrong parent dir |
| `.claude/worktrees/*` (8 records) | various | yes |

Six branches in this repository are therefore held by a worktree the sidebar does not and cannot
show. *(Verified again while fixing: `max-speed` also carries a `.worktrees/` tree, bringing the
count to fourteen. The shape of the defect is unchanged — there is simply more of it than the
first snapshot showed.)* Selecting any of them in the branch picker produces, for example:

> `'fix/olx-auth-error-mapping' is already checked out in the worktree 'fix-olx-auth-error-mapping'.`

The user reads `'fix-olx-auth-error-mapping'` — a bare directory basename, formatted exactly like a
sidebar worktree name — scans the sidebar, finds nothing, and concludes the app is wrong.

## Root Cause Analysis

**Two different definitions of "the app's worktrees" are in play, and the blocked-branch path
straddles them.**

1. **The sidebar's definition is narrow.** `reconcile()`
   (`crates/micold-core/src/worktree.rs:194`) keeps only records whose parent is the project's
   `.claude/worktrees/` directory — everything else is dropped on the floor
   (`worktree.rs:205`). `discover()` (`worktree.rs:557`) feeds that filtered set to both the client
   sidebar and the daemon catalog.

2. **The block check's definition is total.** `checked_out_branches()` (`worktree.rs:445`) reads the
   **raw** `parse_worktrees()` records deliberately, and by design — research R1 and task T011 both
   call this out, because `reconcile()` would discard the project's own main checkout, which FR-021's
   second case needs. But "raw" does not mean "main checkout plus app worktrees"; it means *every
   worktree git knows about, anywhere on the filesystem*. `preflight()` step 2 (`worktree.rs:470`)
   and `branch_candidates()`'s `blocked_by` annotation (`worktree.rs:534`) both inherit that scope.

The two sets differ by exactly the worktrees in the table above, and nothing in the design accounts
for the difference. `BlockReason` has only two variants — `CheckedOutInProjectRoot` and
`CheckedOutAt { path }` — so a third-location holder is classified as `CheckedOutAt` and described
with the vocabulary reserved for an app-managed worktree.

**The message then discards the one piece of information that would have made it comprehensible.**
`block_sentence()` (`crates/micold-client/src/ui/worktree_form.rs:282`) and
`describe_create_error()` (`crates/micold-daemon/src/server.rs:1282`) both reduce the holder's path
to `path.file_name()`. The full path — `.git-paw/worktrees/…`, or a sibling directory entirely —
is available at both sites and thrown away, leaving a basename that *looks* like a sidebar entry.
Had either printed the path, the user would have understood immediately.

So the defect is not a wrong check. `git` genuinely will not check a branch out twice, and blocking
is correct. The defect is that **the spec only ever imagined two kinds of holder, so the
implementation had no third thing to say** — and the wording it does use actively misdirects.

### Why it was not caught

Every artifact describes the holder as a two-case universe, consistently:

- **spec.md FR-021** — *"in another worktree managed by the app, or as the repository's own current
  checkout"*.
- **spec.md User Story 5** narrative — *"(in another of the app's worktrees, or as the repository's
  own current branch)"*, with acceptance scenarios 1 and 2 covering exactly those two.
- **research.md R1** — *"That single call therefore answers **both halves** of FR-021"*.
- **tasks.md T053** — *"`Blocked` distinguishes `CheckedOutInProjectRoot` from `CheckedOutAt
  { path }`"*: two variants, tested as two.

The test suite matches the spec, so it passes. A repository whose worktrees all live under
`.claude/worktrees/` never reveals the gap — and the development repo is exactly such a repository.
`max-speed` is not: it carries a `.git-paw/worktrees/` tree from another tool and a worktree checked
out in a plain sibling directory.

### Two further variants of the same mismatch

Both produce the identical symptom — a holder that is named but not visible — even when the holder
*is* under `.claude/worktrees/`:

- **Agent-owned holders are hidden by design.** `visible_worktrees()`
  (`crates/micold-client/src/features/worktree.rs:77`) filters out agent-owned worktrees (feature
  014, FR-002) unless the reveal control is on. A branch held by an `agent-<hex>` worktree is blocked
  by something the sidebar is deliberately hiding.
- **An active tag filter hides the holder.** Feature 009's sidebar filter narrows the visible set
  further; the holder can be present but filtered out of view at the moment the message is read.

These need no new `BlockReason` — the holder is genuinely one of the app's worktrees — but they do
mean "name the holder" is not by itself sufficient for the user to find it.

## Artifact Traceability

### spec.md

- **Affected user story**: **User Story 5 — Understand when an existing branch cannot be used**
  (Priority: P5). Its stated purpose — *"a clear explanation naming where the branch is already in
  use, so they can go to that location instead of guessing"* — is precisely what fails: the location
  is named in a form the user cannot go to.
- **Affected requirements**:
  - **FR-021** — the **gap**. *"When the existing branch is already checked out — in another worktree
    managed by the app, or as the repository's own current checkout — …"*. The enumeration is
    exhaustive in the spec and non-exhaustive in reality. A worktree that git knows about but the app
    does not manage (`.git-paw/worktrees/`, a sibling directory, any path outside
    `.claude/worktrees/`) is a third case with no requirement covering it, so the implementation was
    free to describe it as the second.
  - **FR-012** — *"Branches that cannot be checked out because they are already in use MUST appear in
    the list marked unavailable with the reason"*. Satisfied to the letter: the branch is marked, a
    reason is given. Defeated in purpose: the reason is unactionable.
  - **FR-022** — **not** implicated. This is not a directory clash;
    `preflight()` step 1 does not fire. Worth stating explicitly, because "says that worktree
    exists" in the original report sounds like FR-022 and is not.
- **Affected success criteria**:
  - **SC-006** — *"100% of attempts … produce an explanation that names the location holding it,
    rather than an unexplained failure."* Currently measured as met (a location string is produced)
    while the user experience is an unexplained failure. The criterion cannot distinguish the two,
    because it asks only that a location be *named*, not that it be *reachable*.
- **Missing edge case**: no Edge Cases entry covers a branch held by a worktree outside the app's
  management, nor one held by a hidden (agent-owned) or filtered-out worktree.

### plan.md

- **Affected sections**: the pre-flight/`BranchSituation` design (the section noting that *"the
  'branch already checked out' block (FR-021) is what keeps the … cases from being constructed"*),
  and the `BlockReason` shape that flows from it.
- **Impact**: the plan inherits the two-case universe from the spec; the holder taxonomy and the
  message contract are what a fix would touch.

### research.md

- **R1** — *"How to detect that a branch is already checked out, and where"*. Its reasoning is sound
  and its conclusion (read raw records, not `reconcile()`) is correct. What it does not do is notice
  that raw records are a **superset** of {main checkout} ∪ {app worktrees}. The phrase *"both halves
  of FR-021"* is where the third case is ruled out without being considered.

### tasks.md

- **Affected tasks**:
  - **T011** — implements `preflight()` over raw records. Correct as specified; scope of "raw" not
    examined.
  - **T031** — implements `branch_candidates()`'s `blocked_by` from the same records, so the branch
    picker marks these branches unavailable with the same unactionable reason.
  - **T036** — shows the blocked explanation and disables Create; the dead-end the user hits.
  - **T053** — the failing tests for `Blocked`; tests two variants because the spec named two.
  - **T056** — renders the blocked panel with dismiss only.
- **False completions**: none. Every task listed is genuinely complete against the requirement it
  was written for. This is a gap in the requirement, not drift from it.
- **Missing tasks**: none created — see *Scope of this report*.

## If a fix is later authorized

Recorded so the analysis survives; **not** to be acted on without explicit instruction. *(All five
were carried out on 2026-08-09; item 5 was decided in favour of a hard block with a better
explanation.)*

1. Extend FR-021's holder taxonomy to a third case: a worktree git knows about that the app does not
   manage. Add the matching Edge Cases entries (unmanaged holder; hidden/agent-owned holder;
   filtered-out holder).
2. Add a `BlockReason` variant for the unmanaged case so the message can say *where* rather than
   implying *which sidebar row*.
3. Stop reducing the holder path to its basename in `block_sentence()` and `describe_create_error()`
   when the holder is not a visible sidebar worktree — show the path.
4. Tighten SC-006 so it measures that the named location is reachable by the user, not merely that a
   string was produced.
5. Decide the product question this exposes: should a branch held only by an unmanaged worktree be
   *offered* some path forward (e.g. an explicit "that worktree is outside this app" state), or
   remain a hard block with a better explanation? The current behaviour is a hard block by accident,
   not by decision.
