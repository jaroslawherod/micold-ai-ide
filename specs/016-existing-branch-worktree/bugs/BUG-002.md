## Scope of this report

Written as diagnosis only; the reporter authorized the patch on 2026-08-14 and chose to patch both
halves in feature 016 — including the adoption question BUG-001 item 5 deferred. The analysis below
is kept as written, so what was proposed can be read against what was specified.

## Description

A branch exists, and a worktree for it exists on disk, but that worktree is not registered with the
app — it does not appear in the sidebar. The user wants to bring that existing worktree into the
app explicitly.

**Expected**: either a way to include the existing worktree, or — at minimum — a refusal the user
can read and act on, with the form still open and their inputs intact.

**Actual**: two failures, one on top of the other.

1. The branch cannot be chosen. It is listed in the existing-branch picker marked in use, and
   pressing it is defined to do nothing (021 FR-012a). So the user's goal is unreachable by design:
   there is no "include this worktree" path anywhere in the product.
2. Pressing that row does not do nothing — **the whole add-worktree dialog closes**, discarding the
   form and every input in it. There is no message, no explanation, and no way to tell a refusal
   from an accidental dismissal.

This is a strict regression of the guarantee 021 FR-012a states in as many words: *"Attempting to
pick it MUST do nothing — in particular it MUST NOT close the result list."* It closes the dialog
the list lives in.

## Root Cause Analysis

### Why the dialog closes (written from code reading; since reproduced — see *Confirmed* below)

A press on an unavailable row is never captured by anything, and falls through to the modal's
scrim, whose press message is the dialog's cancellation.

Four facts, each in the code today, compose into it:

1. **An unavailable row is a button with no press message.**
   `row_element()` (`crates/micold-client/src/ui/material/picker.rs`) builds the row with
   `.on_press_maybe(press)` and, when `press` is `None`, returns the bare button. The branch picker
   produces exactly such rows: `branch_picker()`
   (`crates/micold-client/src/ui/worktree_form.rs:205`) calls `.disabled()` on every candidate where
   `is_available()` is false. A button with no press message does not capture the event.

   *(Corrected during implementation: this report first named `menu.rs:212`, which is
   `menu::item_column` — the overflow menu's rows, not the picker's. Same shape, same defect, wrong
   file. Both are fixed, so the two kinds of inert row cannot diverge.)*

2. **The floating list forwards inside-presses to its content and captures nothing itself.**
   `Menu::update()` (`crates/micold-client/src/ui/cdk/picker.rs:493`) captures a left press only
   when the cursor is *outside* both the list and the field. A press on a row is inside, so it is
   handed to the content — the button in (1) — and if that does not take it, nothing has.

3. **The dialog panel only swallows presses within its own bounds.**
   `Surface::positioned()` (`crates/micold-client/src/ui/cdk/overlay.rs:153`) wraps the panel in
   `opaque` precisely so *"a click on the panel's padding falls through and reads as 'outside'"*
   cannot happen — but `opaque` guards the panel's layout rectangle only. The branch list is
   anchored below its field and floats over the form (021 FR-011/AS8), so its lower rows sit
   *outside* the dialog card. A press there is outside the opaque region.

4. **The scrim beneath is a full-window press handler wired to cancel.**
   `Surface::backdrop()` (`crates/micold-client/src/ui/cdk/overlay.rs:135-136`) is
   `mouse_area(fill).on_press(dismiss)` filling the window, and `ui::mod.rs:388` sets that dismisser
   to `on_escape(state)` — for this dialog, `AddWorktreeCancelled`
   (`features/worktree_form.rs:282`). `dismisses(Surface::Dialog, Trigger::OutsideClick)` is `true`
   (`crates/micold-core/src/overlay.rs:138`), so the backdrop is live.
   `Message::AddWorktreeCancelled` sets `self.worktree_form = None` (`app.rs:1254`) — the dialog is
   gone, inputs and all.

So: **a press on an unavailable row that renders below the dialog card's bottom edge cancels the
dialog.** An available row is unaffected — its button has a press message and captures. An
unavailable row that happens to render *inside* the card is also unaffected — `opaque` swallows it,
which is the FR-012a behaviour. The defect is therefore geometry-dependent, which is exactly why it
survives: it is invisible in a short list and reliable in a long one.

### Why it was not caught

The reducer is correct. `Message::AddWorktreeBranchSelected` returns early for an unavailable
candidate (`app.rs:1289-1291`), with the comment *"Silently, and without closing the list."*
`tests/branch_search_state.rs` tests that rule at the state level and passes — because at the state
level the press produces no message at all, and the message that actually arrives
(`AddWorktreeCancelled`) is dispatched by the *widget tree*, from a surface the state tests never
build. No test drives a press at a coordinate. This is a hit-testing defect, and every test that
covers the requirement is written above hit-testing.

### Why the worktree cannot be included

Separately, and prior to the dialog closing: nothing in the product can adopt a worktree that exists
on disk into the app.

- `reconcile()` (`crates/micold-core/src/worktree.rs:229`) keeps only records whose parent is the
  project's `.claude/worktrees/`, so a worktree registered with git anywhere else is dropped from
  the sidebar and cannot be reached.
- `checked_out_branches()` (`worktree.rs:533`) sees it, so the branch is blocked —
  `CheckedOutOutsideApp` when it is elsewhere on disk, `CheckedOutAt { owner: Agent }` when it is a
  hidden agent worktree.
- `preflight()` (`worktree.rs:575`) returns `DirectoryTaken` when the derived directory already
  exists, which *"outranks every branch case"* and offers nothing but "choose a different name, or
  remove the existing folder first" (`ui/worktree_form.rs:403-425`).

Every path is a refusal. That is the deliberate outcome of BUG-001 *If a fix is later authorized*
item 5, which asked whether an unmanaged holder should be offered a path forward and answered "hard
block with a better explanation". This report is the same question arriving from the user side: the
explanation is now honest, and the user still has work they cannot reach. Note also that BUG-001's
"a hard block by accident, not by decision" reasoning applied to a holder the user did not create;
here the user knows the worktree exists and is asking to adopt it.

## Artifact Traceability

### spec.md (016)

- **Affected user story**: **User Story 5 — Understand when an existing branch cannot be used**
  (P5). Its scenario 5 — *"the repository is unchanged and the user can amend their inputs and try
  again without restarting the flow"* — fails outright: the flow is what restarts.
- **Affected requirements**:
  - **FR-007** — *"On cancel … MUST return the user to the creation form with their entered values
    preserved."* The dialog is cancelled by a press that was not a cancel, so nothing is preserved.
    The requirement is written for a user-initiated cancel and does not anticipate one manufactured
    by the scrim.
  - **FR-012** — *"Branches that cannot be checked out … MUST appear in the list marked unavailable
    with the reason."* Satisfied in the row's label; defeated when reading the reason costs the
    form.
  - **FR-021 / FR-021a / FR-021b** — the block itself is correct and stays correct. What is missing
    is any requirement for what the user does *next* when the holder is a worktree they want.
  - **FR-022** — implicated for the second half only: a pre-existing target directory is required to
    block, with no option offered. That requirement is what forecloses adoption when the worktree
    sits at the derived path.
  - **Missing requirement (the gap)**: nothing covers *including an existing worktree in the app* —
    neither one git already knows about outside `.claude/worktrees/`, nor a directory under it that
    git no longer knows about (`reconcile()` marks the latter `Invalid`, `worktree.rs:247-256`).
- **Affected success criteria**:
  - **SC-006** — a message that names the holder is produced, then destroyed by the same press that
    would let the user read it. Measured as met; experienced as a dialog vanishing.
  - **SC-007** — *"Cancelling at any point in the flow leaves the repository unchanged."* Still true
    of the repository. Silent about the form's own contents, which is what is lost here.
- **Missing edge case**: no entry covers a press on an unavailable row, nor the existence of a
  worktree the user wants to adopt.

### spec.md (021-branch-typeahead-search) — where the violated rule actually lives

- **FR-012a** — *"An unavailable branch MUST NOT be pickable … Attempting to pick it MUST do
  nothing — in particular it MUST NOT close the result list, and it MUST NOT become the selected
  branch."* Violated: it closes the list, the dialog, and the form.
- **Acceptance Scenario 7a** — *"nothing happens: it does not become the selected branch and the
  result list stays open."* Directly contradicted.
- **FR-011 / AS8** — the list *"floats over the form rather than displacing it"*, which is the
  requirement that puts rows outside the dialog card and makes the fall-through reachable. Correct
  as written; it is the interaction with the scrim that is unhandled.

### spec.md (022-dedicated-select-component)

- **FR-017** — *"A select option MAY be presented as unavailable: shown, muted and unpressable."*
  "Unpressable" is implemented as "carries no message", which in this rendering stack also means
  "does not consume the press". The requirement does not distinguish the two, and that is the seam
  the defect comes through.
- **FR-012** — *"A press outside both the list and the control … MUST close the picker."* The list's
  own handler is correct (`cdk/picker.rs:493`); the problem is what receives a press it declines to
  claim.

### plan.md / research.md

- 016's pre-flight and `BranchSituation` design is unaffected — the classification is right, the
  block is right. The gap is downstream of it: no plan section covers adoption of an existing
  worktree, because no requirement asks for one.
- 021's component contract is where an "unavailable rows consume their presses" obligation would
  belong.

### tasks.md

- **Affected tasks (016)**: T036 (shows the blocked explanation and disables Create) and T056
  (renders the blocked panel) both deliver the message the user never gets to read.
- **Affected tasks (021)**: the FR-012a tasks and `tests/branch_search_state.rs` are complete and
  correct at the state level — see *Why it was not caught*.
- **False completions**: none. Every task is complete against the requirement it was written for.
- **Missing tasks**: none created — see *Scope of this report*.

## Confirmed

2026-08-14, during implementation. The analysis above was code-reading; it is now measured. Two
tests, both written before the fix and both observed failing for the stated reason:

- `material::picker_press` — an available row captures its own press; an unavailable one did not.
- `tests/add_worktree_form_survives_a_refusal.rs` — pressing an in-use branch published
  `AddWorktreeCancelled`. The row it presses is *measured* to lie outside the dialog's card, by
  asking the widget tree beneath the list what it would do with a press there, so the test cannot
  pass over a row the card happens to cover.

The geometry qualifier in step 4 below is therefore confirmed: with a 12-branch list in a 1280×800
window, the very first row already hangs past the card.

## Reproduction

1. In a repository, create a worktree outside the app's `.claude/worktrees/` for a branch — e.g.
   `git worktree add ../elsewhere feat/x` — so the app never lists it.
2. Open the add-worktree form and switch to **Existing branch**.
3. Find `feat/x` in the list; it is marked in use.
4. Press it, with the row rendered below the dialog card's lower edge (narrow the window or scroll
   the list down if the row is inside the card).
5. **Observed**: the dialog closes. **Expected per 021 FR-012a**: nothing happens and the list stays
   open.

Step 4's qualifier is the part still to be confirmed at a display: the analysis predicts that a row
*inside* the card is swallowed harmlessly and only a row outside it closes the dialog. Confirming
that boundary is what would turn this report from code-reading to observation.

## If a fix is later authorized

Recorded so the analysis survives. *(All five were carried into the spec on 2026-08-14; item 5 was
decided in favour of including the worktree by reference — see research R13.)*

1. Make an unavailable row consume its own press instead of declining it — the row is a real target
   that deliberately does nothing, not a hole. That fixes every disabled row in every picker at
   once, not just this one.
2. Alternatively or additionally, have the floating list capture presses within its own bounds
   regardless of what the row underneath does (`cdk/picker.rs:493` already knows the bounds).
3. Add a geometry-level test — a press at a coordinate outside the dialog card but inside the list —
   since no state-level test can see this class of defect.
4. State in 021 (or 022 FR-017) that "unpressable" means the press is consumed, not merely unhandled.
5. Decide the product question the user is actually asking, which BUG-001 item 5 deferred: should the
   app be able to **include an existing worktree** — one git knows about outside
   `.claude/worktrees/`, or a directory under it git has forgotten? Today the answer is no by
   omission rather than by decision, and both of this report's halves lead back to it.
