## 1. The resting label is drawn underneath the leading icon

**Observed**: in the collapsed, empty branch picker, the search magnifier overlaps the "B" of the
"Branch" label. Confirmed at 600% zoom — `evidence/t063-s5-label-zoom.png` — it is an overlap, not
a tight gap.

**Root cause**: the two are drawn by two widgets that do not know about each other.

- The leading icon is a `text_input::Icon` on the **inner** input
  (`ui/material/text_field.rs:161`), so it is inset from the input's own left edge.
- The label is drawn by the **wrapper**, `FormField`, which positions it over the value's line while
  it rests (`ui/material/form_field.rs:225-228`).
- `FormField` has no `leading_icon` — nothing in it takes an icon's width into account.

So any `TextField` with both `.leading_icon(…)` and `.label(…)` overlaps them whenever the value is
empty and the field is unfocused, which is precisely the state `Typeahead` opens in
(`ui/material/typeahead.rs:209-215`). Material insets both label positions past a leading icon;
this one insets neither.

**Not a data problem, and not specific to the branch picker.** It reproduces for every searchable
picker built the same way, which is what makes it worth a report rather than a nudge to the label's
padding.

**Reported twice, independently.** `specs/021-branch-typeahead-search/bugs/BUG-002.md` filed the
same defect on 2026-08-08, eleven days earlier, from the same evidence — the magnifier over the "B"
at magnification, found by the same `visual-pass` skill on its first run. This report did not know
that one existed. Both are closed by the same work; 021's carries the requirement and the contract
row, this one carries the implementation. That two passes found it separately and neither found the
other is worth more than the duplication cost: it says the defect was reachable from two different
directions and that nothing in the repository connected them.

### What was built (2026-08-19)

Two rules for one column was the defect, so there is one now. `FilledField` computes a single
content column — `padding + leading slot + gap` — and both the value **and** the label start on it,
in either of the label's two positions. The diagnosis above named the label's padding as the
tempting fix; nudging it would have satisfied the symptom and drifted again at the next glyph.

Three parts, and the second and third are why the first is not enough on its own:

1. **The icon moved into the field's own leading slot.** It was a `text_input::Icon`, drawn by the
   input — and an icon the input draws is one the *field* cannot see, while the field is what
   positions the label. `filled_field`'s module docs already state the rule this restores: the input
   is the editing engine and decides where nothing sits. `FormField.leading` existed and was used by
   no call site; it is now the only way in.
2. **The slot is a fixed 24dp, not the glyph's advance** (`anatomy::text_field::LEADING_ICON`, gap
   `LEADING_GAP` = 16). §7.2 states this rule for a list row's leading icon and BUG-006 is what it
   was written after: a column that follows the advance lands somewhere different for every icon,
   and `Icon::Search` measures 14dp where the role says 24.
3. **Both adornments are centred on the container's middle**, not pinned to the top of the floating
   value's line. Fixing only the horizontal collision would have replaced it with a vertical one:
   the old rule put a `TypeRole::Action` glyph's centre at 33.1dp in a box whose middle is 28dp, so
   the leading icon would have sat 5dp below the resting label it now shares a line with. The
   trailing adornment moves by the same 5dp because it is the same rule — two adornment slots
   disagreeing about their baseline is what the old one amounted to.
4. **Both are offered the container's height rather than the value line's 24dp** — the follow-up
   below, folded in after the visual pass found it.

§7.7 gained the four rows it did not have — leading slot, gap, content column, adornment baseline.
The missing row *is* the defect: two call sites resolving the same figure by eye is the shape every
bug in that section has had.

Covered by `a_leading_adornment_moves_the_label_and_the_value_together`,
`no_leading_adornment_means_no_indent` and `an_adornment_sits_on_the_fields_centre_line` in
`ui/material/form_field_anatomy.rs`, each checked to fail against the geometry it replaces. The
column is asserted as an *equality* between label and value rather than as "the label clears the
icon", because a label that cleared it by separate arithmetic is the defect surviving its own test.

**The layout fixture had never seen this control either.** Its
`add-worktree-dialog-existing-branch` state renders the dialog before any branch listing arrives, so
the picker draws a caption instead of a field. A sibling state — `add-worktree-dialog-branch-picker`
— now poses it with branches loaded, and the fixture pins the field's own geometry: the leading icon
centred on the container's middle, and the control and the label both starting at
`padding + icon slot + gap`. A gate that reads rectangles still cannot see two glyphs overlap; what
it can do, and now does, is notice the column moving.

**Those assertions did not exist before, and could not have.** The icon was drawn inside the input's
own paint, so there was no layout node for a geometry gate to compare — which is why every gate was
green while the two glyphs overlapped. Moving it into the field's slot is what makes it checkable at
all; the tests are a consequence of part 1, not an addition to it.

Confirmed on screen — the fix is geometric, and a rectangle being in the right place is not the same
claim as two glyphs not colliding:
[evidence/BUG-003-item1-visual-pass.md](./evidence/BUG-003-item1-visual-pass.md), with
`bug003-item1-before-after.png` stacking the T063 crop against the same control after.

#### The follow-up that pass found (2026-08-19)

Reported there as a separate defect and left unpatched; the reporter then authorized it, so it is
recorded here rather than in a report of its own — it is one line of the same function, found while
verifying the same fix.

**The trailing clear `×` was squeezed and drew low.** `FilledField` capped both adornment slots at
`VALUE_LINE` (24dp). An `IconButton` wants §7.3's 48dp target around a container it pads by 8dp, and
24dp of headroom did not refuse it — it squeezed it: 8dp top and bottom left the glyph an 8dp box,
which it drew out of and down the field, ~11dp below the centre line with its target compressed to
half of §7.3's figure. Measured off the pass's own frame: the container occupies rows 507–561
(centre ≈ 534) while the glyph's ink runs 539–552 (centre ≈ 545.5).

Nothing failed, and the reason is worth keeping: the slot was the right size and the child fitted
inside it. A geometry gate that reads a slot cannot see a child overflowing its own box, which is
the same blindness in a different direction from the one that hid the leading icon.

An adornment is not a second line of value, so it is now limited by the **container's** height.
`a_trailing_action_is_centred_and_keeps_its_touch_target` asserts both halves — the 48dp target, and
the *glyph's* centre rather than the slot's, because the slot was already centred while the glyph
was not. §7.7 gained an *Adornment height* row beside the other four.

Re-photographed rather than left to the assertion, because the fix introduces an appearance no test
asks about: an un-squeezed button has an un-squeezed hover layer, and 40×47 inside a 56dp field is a
new look rather than a corrected one. It reads as `IconButton`'s ordinary pill, inset from both
edges. Ink now runs 528–541 against a container of 507–560 — one dp off centre, against eleven and a
half. See §5 of the pass and `bug003-item1-trailing-before-after.png`.

## 2. A descriptive name ending in a number is read as an issue key

**Observed**: the worktree on `feat/reporting-2` renders in the sidebar as **"Feat reporting 2"**
with tags `feat` and `REPORTING-2`. The worktree on `feat/reporting` renders as **"Reporting"** with
tag `feat`.

**This is not, as first reported, a divergence between the picked-branch and typed-name creation
paths.** Both paths call the same function on the same directory name. The trailing `-2` is what
differs, and it is enough:

```
        feat-reporting -> "Reporting"          tags=[Type(Feat)]
      feat-reporting-2 -> "Feat reporting 2"   tags=[Type(Feat), Issue("REPORTING-2")]
      feat-add-retry-3 -> "Add retry 3"        tags=[Type(Feat)]
    feat-abc-123-login -> "Login"              tags=[Type(Feat), Issue("ABC-123")]
```

**Root cause**: `issue_at_start` (`micold-core/src/naming.rs:276`) accepts *any* lowercase
alphanumeric word followed by an all-digit word as an issue key, and `is_issue_project` (:261) puts
no length or shape constraint on the first half. For `feat-reporting-2` the remainder after the type
token is exactly the two segments `reporting` + `2`, so the pair matches, the descriptive remainder
becomes **empty**, and `display_name`'s fallback then re-joins the *whole* directory name — which is
why the type token reappears in a label whose entire purpose is to have it removed.

The function's own doc comment claims this case is handled: "Scanning the whole name would misread a
trailing number in the descriptive part (e.g. `feat-add-retry-3`) as an issue key." Only scanning
from the start is indeed enough for three-or-more segments; it is not enough for exactly two, and
`-2` / `-3` suffixes are the ordinary way a second worktree on a related name gets disambiguated.

**Requirement violated**: 008 FR-017 — derive the name "from the worktree's descriptive name portion
only — removing the conventional type prefix and any Jira-style issue key". `reporting-2` is not a
Jira-style key, the type prefix was not removed, and both failures come from the same match.

**Test coverage**: `micold-core/tests/naming.rs` pins `feat-add-retry-3` → "Add retry 3" (three
segments) and `feat-abc-123-login-page` → "Login page", but no case where the descriptive part is a
single word followed by a number. That gap is the reason the suite is green.

**A second defect, same cause.** A GitHub/GitLab reference is a bare number. `slugify("#123")` is
`123`, and `is_issue_project` requires a leading lowercase letter — so a ticket entered as `#123`
matched nothing, was discarded silently, and its digits stayed in the friendly name:

```
ticket "#123" + name "login page"  ->  dir "feat-123-login-page"
                                   ->  renders "123 login page"   tags=[feat]
```

The form accepted the input and threw it away. Numeric references were unsupported, not merely
mis-tagged.

### What was built (2026-08-18)

The shapes are genuinely indistinguishable — `feat-abc-123` and `feat-auth-2` are one pattern — so
no sharper heuristic exists. The directory name carries the answer instead of implying it.

`slugify` maps every non-alphanumeric character to `-`, so a derived name can never contain `_`.
That makes `_` a boundary with no escaping and no collisions:

```
feat-abc-123_login-page  ->  "Login page"   [feat] [ABC-123]
feat-123_login-page      ->  "Login page"   [feat] [#123]
feat-reporting-2         ->  "Reporting 2"  [feat]
feat-abc-123             ->  "Abc 123"      [feat]
```

Everything between the type and the first `_` is the ticket, verbatim; everything after it is the
name. No boundary means no ticket. A ticket that is all digits renders as `#123`, anything else
upper-cased. `parse_tags` and `display_name` now share one `split_name`, so the chip and the label
cannot disagree about where the ticket ended.

**The boundary is on the branch as well as the directory.** It was directory-only for one commit,
on the reasoning that branches are pushed and matched by CI filters. That left
`dir_name_from_branch` unable to recover a ticket, so a worktree re-created by *picking* an
app-derived branch silently lost it — not a legacy problem but an ongoing one, on feature 016's own
path. The reporter chose the exact round trip instead: `dir_name_from_branch` now slugifies *around*
the boundary rather than through it, and `derive`'s branch carries it.

**Two consequences, both accepted by the reporter:**

1. **No legacy fallback.** A directory already on disk has no `_`, so it reads as ticketless: every
   existing worktree loses its `ABC-123` chip once. Its label improves in the same move
   (`feat-reporting-2` reads "Reporting 2" immediately), and a custom name still persists (008
   FR-014/FR-015). The alternative was keeping the heuristic for `_`-less names, which would have
   left newly created ticketless names ambiguous too — the string cannot say which era it is from.
2. **A `snake_case` branch from outside this app reads as ticketed.** `fix/some_bug` becomes
   `fix-some_bug`: chip `SOME`, name "Bug". `_` means one thing everywhere and nothing can tell a
   foreign underscore from a boundary. One wrong chip on a foreign branch, against every app-made
   branch losing its ticket the moment it is re-picked.

Specified in 008 FR-017a/FR-017b, `008/contracts/naming-tags.md`, and
`005/contracts/naming.md`.

## 3. The same directory clash speaks with two hand-written voices

**Observed**: the clash is worded one way when the client's pre-flight catches it, and another way
when the create fails on it:

| Where | Wording |
|---|---|
| Client pre-flight (`ui/worktree_form.rs:432`) | "A worktree folder named 'X' already exists." + "Choose a different name, or remove the existing folder first." |
| Daemon, on `CreateError::DuplicateDir` (`micold-daemon/src/server.rs:1408`) | "a worktree with that name already exists" |

Same condition, two sentences, and only the first tells the user what to do. The second is what the
user sees on the path T063 Scenario 3 exercises — a clash created *after* pre-flight — captured in
`evidence/t063-s3b-fail-crop.png`.

**Root cause**: the daemon's `describe_create_error` writes `DuplicateDir`'s sentence inline. Its
neighbouring arm does the opposite, and says why (`server.rs:1392-1398`):

> the sentence comes from core, so a block caught here at create time reads exactly as the same
> block caught by the client's pre-flight — two hand-written wordings is how BUG-001's holder
> taxonomy came to be wrong in one place and right in neither.

`BranchInUse` was fixed that way after BUG-001. `DuplicateDir` was not, and it is the same shape of
defect one arm lower in the same `match`.

**Fix shape** (if authorized): give the directory clash the same treatment — one sentence produced
by core, used by both the pre-flight branch of `worktree_form.rs` and by `describe_create_error`, so
neither can drift from the other.

### What was built (2026-08-19)

That shape, with one departure it argued for on the way: core owns **both** halves, not just the
fact.

`explain_directory_taken(dir) -> DirectoryClash` returns `{ fact, guidance }`, and `Display` joins
them with a space. The form draws the two fields as its two lines, in the roles it already used;
the daemon sends the joined string. Neither writes a word of it.

Both halves, because the second sentence of this report is that "only the first tells the user what
to do", and moving the fact alone would have left that true. `BlockReason::explain` deliberately
does *not* carry its guidance: a branch block's remedy depends on which action the form is
currently offering — "Include that worktree" exists for one holder and not the others — so it
belongs to the form. A directory clash offers nothing, ever (FR-022), so there is exactly one
answer and no reason for the daemon's copy to go without it. The asymmetry is the difference
between the two conditions, not an inconsistency between the two fixes.

`CreateError::DuplicateDir` now carries the directory, for the same reason `BranchInUse` carries
the branch: the sentence is built from it. It was the only variant that had thrown away what it
needed to explain itself, which is why the daemon's wording could not have named the folder even if
someone had wanted it to.

Covered by three cases in `micold-core/tests/branch_conflict.rs` — the two halves, the
no-final-component fallback, and that the one-line form is the two parts joined rather than a third
wording — and by `server::create_error_tests` in the daemon, which asserts the mapping *is* core's
string and, separately, that it names the folder and offers the remedy. The second is not
redundant: an equality with core would still pass if core's sentence lost a half.

The form's half needs no gate of its own — it renders the fields; there is nothing there to drift.
The daemon's did, because that is the side an edit had already gone wrong on.

Specified in 016 FR-022a.

## Checked during the same pass and **not** a defect

The picker's field never shows the branch you selected — after a pick it still shows only the
"Branch" label (`evidence/t063-s5-field-zoom.png`). That is 021 **FR-014a** as written: "The search
field MUST hold only the search text — never the selected branch's name. The selected branch MUST
stay visible in the form's existing derived preview regardless of what is typed." The handler says
so at the point of decision (`app.rs:1325`, "The query is deliberately left alone (FR-014a)"), and
the derived preview did show the selection throughout the scenario.

Recorded here because it looks like a defect on screen and will be re-reported otherwise. The only
open question it leaves is a design one, not a bug: whether the preview is prominent enough to be
the sole confirmation of a choice.
