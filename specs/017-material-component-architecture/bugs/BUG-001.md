# Bug Report: `Expand`'s reveal does not clip, so revealed content paints over the widgets below it

**Type**: Untested flow
**Severity**: Medium
**Feature**: `017-material-component-architecture` (the component library's animation wrappers).
Found by `020-component-showcase-gallery` (branch `feat/material-showcase`); user-visible in
`009-sidebar-filter-toolbar`'s tag-filter panel.
**Reported**: 2026-07-28
**Status**: Patched
**Patched**: 2026-07-29 — fixed on `fix/expand-reveal-clipping`; see *Root Cause Analysis*, which
was **corrected** on investigation: the clip was never the problem.
**Independently detected**: see *Detection* below.

## Detection (added 2026-07-29 by feature `019-layout-snapshot-parity`)

Written while this bug was open, against the code before the fix. Kept because it records what the
defect looked like from the outside, and because the gate is what will notice if it returns.

Recommended fix step 1 asked for a reproduction, with the honest fallback being "a layout-level
assertion that the child node's bounds are clipped to the parent's". That assertion exists as
`crates/micold-client/tests/gates/containment.rs` — a third gate alongside the geometry fixture and
the text-overflow check.

Against the unfixed code it fired on **7 of feature 019's 9 covered states**: every state that
renders a sidebar laid a 40–42px accordion body inside a 0px `Expand`. The two that did not were
`main-shell-sidebar-collapsed` (the panel is parked off-window by `NavigationDrawer`) and
`empty-no-project-open` (no sidebar). Attribution was demonstrated rather than argued —
`the_recorded_escapes_are_the_accordion_reveal` drives `sidebar_filter_open` and shows the same
nodes come clean when the panel is open.

Those seven sat in `KNOWN_ESCAPES` with a staleness assertion, so the suite stayed green while the
defect stood and **fixing `Expand` failed the test until the entries were deleted**. That is what
happened: the fix landed on `main`, the assertion fired, and the entries were struck.

The seven settled states caught the defect's *cause* — at `progress` 0 `Expand::draw` returns early,
so the violation was in the layout but nothing was painted. **The overlap as a user met it was
covered too**, by `the_reveal_paints_over_what_moved_up`, which pins the sidebar's filter panel two
frames into its 90ms reveal — past the early return, well short of the end, where the child was both
oversized and painting.

That pin is deterministic despite being mid-animation: a `Progress` advances a fixed step per redraw
rather than by elapsed wall-clock time (`cdk/motion.rs`), and the `Instant` in the redraw event is
not read for the step size. It is deliberately **not** recorded in `layout_snapshot.txt` — feature
019 excludes mid-animation geometry (T030), and a snapshot of a frame partway through a reveal would
churn on any change to a duration or an easing curve.

Both assertions were checked against failing runs rather than assumed: pinning at frame 0 fails the
mid-reveal check, and applying this report's own recommended fix (step 2, clip the child node in
`layout`) fails the escape check with "no longer lays its child outside itself — that is BUG-001
fixed", while the pin still reads mid-flight. The test does invert on a fix, which is what the fix
landing later confirmed.

Two findings from that probe, both of which the fix as applied avoids:

- **Clipping one level would not have been enough.** With the child node clipped, the *grandchild*
  escaped instead (`0/0/0/2/0/0/0/1/0/0`). Neither of the recommendation's two candidates was the
  right shape; animating the size and invalidating the layout was.
- **`NavigationDrawer` read clean on this invariant only incidentally** — `parked()` puts its
  inactive child entirely off-window, where containment is deliberately not asserted. Its horizontal
  reveal had the same staleness defect and was found by inspection in the upstream fix pass, not by
  this gate. A gate that is silent about a component is not evidence about it.

## Description

`material::Expand` is the only animation wrapper that animates its **layout** rather than its
drawing. `Fade` composites a scrim, `Scale` applies a renderer transformation, `Scrim` fills a quad —
all three change only what is painted, every frame, with no layout involvement. `Expand` instead
reports a shrunken height to its parent and relies on a draw-time clip to reveal its child top-down:

```rust
// crates/micold-client/src/ui/material/animation.rs — Expand::layout
let full = child.size();
let height = (full.height * progress).max(0.0);
layout::Node::with_children(Size::new(full.width, height), vec![child])
```

```rust
// Expand::draw
renderer.with_layer(layout.bounds(), |renderer| { /* child drawn at full height */ });
```

The child node keeps its **full** height and is positioned at the top; only the parent node shrinks.
So the parent's siblings move up into the vacated space immediately, while the child continues to
paint at full size. The `with_layer` clip that should hide the not-yet-revealed part does not take
effect, and the child paints over whatever moved up.

**Observed**: pressing *Replay* on the `expand` entry in the component showcase's motion section. The
reveal reads as "nothing happened", followed by the revealed content overlapping the controls and
label beneath it.

**Not confined to the showcase.** `material::Accordion` is `expand(...)`, so the sidebar's tag-filter
panel behaves the same way in the running application. It hides better there for two incidental
reasons: its reveal is 90ms (`Accordion::REVEAL`) rather than the gallery's deliberately slow 600ms,
and what sits below it is a worktree list rather than a labelled row, so a brief overlap of similar
text reads as a flicker rather than as a defect.

## Artifact Traceability

### spec.md — `017-material-component-architecture`

- **Affected requirements**: FR-011 (a component owns the presentation state it animates) and FR-014
  (no component reaches for a central animator) are both **satisfied** — `Expand` owns its
  `Progress` correctly, and the bug is not in how it tracks progress but in what it draws with it.
- **Gap identified**: nothing in 017's requirements says a wrapper that animates its own *layout*
  must clip its child to the animated bounds. The wrappers are specified by who owns their state,
  not by what they must not paint over. Every gate 017 built — boundary, builder-API, opacity
  ratchet, idle frames — asks a *structural* question, and all four pass on this code.
- **Affected success criterion**: SC-005 is demonstrated by
  `tests/adding_an_animation_touches_one_file.rs`, which proves a new animated element needs no
  central registry. It drives `Progress` directly and never renders, so it cannot see a clip.

### spec.md — `009-sidebar-filter-toolbar`

- **Affected user story**: the tag-filter panel, which is where this is user-visible today.
- **Affected requirement**: the panel is specified to open *downward, pushing the list below it
  down* rather than floating over it — which is precisely the property that is broken. The list is
  pushed down correctly; the panel then paints over it on the way.

## Root Cause Analysis

Two causes, and the second is the more interesting one.

> **Corrected 2026-07-29.** The proximate cause recorded on discovery — reproduced below — was
> wrong, and wrong in the direction that flatters the reporter: it blamed the rendering stack for
> not honouring a clip. The clip was fine. The bounds handed to it were a frame stale, and had been
> since the wrapper was written. The original text is kept because a bug report that quietly
> rewrites its own reasoning teaches nothing.
>
> ~~**Proximate**: `renderer.with_layer(bounds, …)` is being relied on to clip a child that is laid
> out larger than its parent. Whether that holds is a property of the rendering stack's layer
> semantics, and it evidently does not hold here — plausibly because the child's own `draw`
> receives the unmodified `viewport` and clips against that instead.~~

**Proximate (confirmed)**: `with_layer` clips exactly as documented — *"The layer will clip its
contents to the provided `bounds`"*. The defect is that `layout.bounds()` was **stale**. The
rendering stack re-runs `draw` on every frame but re-runs `layout` only when a widget asks it to,
via `Shell::invalidate_layout`:

```rust
// iced_winit-0.14.0/src/lib.rs — the redraw tick
let (state, _) = interface.update(slice::from_ref(&redraw_event), ...);
if message_count == messages.len() && !state.has_layout_changed() { break state; }
```

`Progress::on_event` asked for a redraw and nothing else, and **no code in this repository ever
called `invalidate_layout`**. So `Expand::layout`'s `full.height * progress` was computed only when
something *else* forced a layout pass. Between those, the reveal did not move — which is why it
read as "nothing happened" — and the clip was applied to whichever bounds that stale pass had
produced, while the child drew at full height. Hence the overlap.

This also explains why the sibling wrappers were unaffected without anyone having reasoned about
it: `Fade`, `Scale` and `Scrim` animate only what they *paint*, and painting is what a redraw
re-runs. `Expand` is the one that animates a *size*, and sizes come from layout.

`NavigationDrawer` had the identical defect — its `layout` derives the panel width from a track the
same way — and was fixed in the same pass. Its own comment ("Advance first, so the children are
updated against the arrangement they are about to be drawn in rather than the previous frame's")
shows the staleness had been suspected and could not be acted on without this mechanism.

**A second defect, found while fixing the first**: the runtime re-delivers the *same* redraw event
when an update invalidates the layout, up to three further times. A track that advanced on each
delivery therefore ran at four times its stated speed the moment it started asking for re-layouts.
Measured, not predicted: one frame of a 100ms transition advanced `0.64` instead of `0.16`. The fix
carries a per-frame guard so a track steps once per frame however often it is handed that frame.

**Underlying**: this class of defect is invisible to every check the project has. 017's four gates
all read *source structure* — who names what, which signature exposes what, where a frame is
requested. `style_snapshot` records resolved style values and explicitly does not cover layout. A
wrapper can therefore be structurally perfect and paint over its neighbours, and nothing fails.

Both 017 and 009 relied on a recorded manual `quickstart.md` walkthrough to cover appearance. 017's
own convergence pass found that its equivalent visual check *had never been run* — which is the
observation that motivated feature 020. This bug is a direct instance of that: an appearance defect
in a shipped component, surviving two features' manual passes, found in the first walkthrough over a
page that puts every component in one place.

## Why this was not fixed on discovery

Feature 020's FR-019 states that the application's appearance and behaviour must be unchanged by that
feature, and that any visible difference is a defect. Fixing `Expand` changes the sidebar tag
filter's motion — a genuine improvement, and still a change 020 is forbidden to make. It is therefore
reported here rather than patched there.

## Recommended Fix

1. **Reproduce first, in a test that fails.** The reveal's clipping is the property; the natural
   assertion is that `Expand`'s child never paints outside its parent's animated bounds. If that
   cannot be asserted without a renderer, the honest fallback is a layout-level assertion that the
   child node's bounds are clipped to the parent's — plus a `quickstart` step, recorded rather than
   assumed.
2. **Fix the clip.** Candidates, cheapest first: translate/clip the child node in `layout` so it is
   genuinely smaller rather than merely drawn inside a smaller layer; or pass a narrowed `viewport`
   to the child's `draw` so its own clipping agrees with the layer's.
3. **Check the sibling wrappers.** `Fade`, `Scale` and `Scrim` animate only their drawing and are not
   suspect, but `NavigationDrawer` performs a horizontal reveal and should be looked at in the same
   pass.
4. **Verify in the showcase.** `mise run showcase` → the motion section's `expand` entry, and the
   `Accordion` entry's third instance, which pairs the panel with the `FilterTrigger` that drives it.
   Both now exercise this on demand, which is what makes the fix cheap to confirm.

Then: `/speckit-bugfix-patch` to update the artifacts, `/speckit-bugfix-verify` to confirm
consistency, and the code fix on a branch of its own — or folded into feature 018, which owns the
motion system and will be touching these wrappers regardless.

## Fix as applied — 2026-07-29, branch `fix/expand-reveal-clipping`

Against the recommendation above, point 1's fallback was not needed and point 2's candidates were
both wrong, because the recommendation was written against the wrong proximate cause. Neither
"clip the child node in `layout`" nor "pass a narrowed `viewport`" would have helped: the child was
already being clipped correctly, to bounds that were a frame old.

- `Progress::on_layout_frame` — advances a track *and* invalidates the layout, but only while the
  value is actually changing, so a settled component stops asking (FR-025's obligation, carried
  over to layout).
- `Progress` advances at most once per frame, guarding against the runtime's re-delivery.
- `Expand` and `NavigationDrawer` use it; `Fade`, `Scale` and `Scrim` deliberately do not.
- `tests/animated_layout_relayouts.rs` — five behavioural tests and one structural gate (SC-010).

Point 3 of the recommendation was right, and paid: checking the sibling wrappers is what found the
drawer. Point 4 is **done**, both halves, confirmed by the maintainer on 2026-07-29: the showcase's
`Accordion` entry and `expand` entry (T062), and the sidebar tag-filter panel in the running
application (T063) — the instance a user actually meets, and the one whose 90ms reveal made the
original defect read as a flicker rather than an overlap.

**Verified fixed.** The reveal no longer paints over what sits below it.

**On the gate.** Its first version scanned per *file* and passed with `Expand` deliberately
regressed, because another wrapper in the same file used the correct call. It was rewritten to
scan per `impl Widget for X` block and re-sabotaged before being kept. Worth recording because this
bug exists precisely because four structural gates all passed on defective code — a fifth that
could not fail would have been the same mistake again, one layer up.
