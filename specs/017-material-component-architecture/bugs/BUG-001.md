# Bug Report: `Expand`'s reveal does not clip, so revealed content paints over the widgets below it

**Type**: Untested flow
**Severity**: Medium
**Feature**: `017-material-component-architecture` (the component library's animation wrappers).
Found by `020-component-showcase-gallery` (branch `feat/material-showcase`); user-visible in
`009-sidebar-filter-toolbar`'s tag-filter panel.
**Reported**: 2026-07-28
**Status**: Open — reported only, deliberately not fixed (see *Why this was not fixed on discovery*)

## Description

`material::Expand` is the only animation wrapper that animates its **layout** rather than its
drawing. `Fade` composites a scrim, `Scale` applies a renderer transformation, `Scrim` fills a quad —
all three change only what is painted, every frame, with no layout involvement. `Expand` instead
reports a shrunken height to its parent and relies on a draw-time clip to reveal its child top-down:

```rust
// crates/micold-client/src/ui/material/animation.rs — Expand::layout
let full = child.size();
let height = (full.height * progress).max(0.0);
layout::Node::with_children(Size::new(full.width, height), vec![child])
```

```rust
// Expand::draw
renderer.with_layer(layout.bounds(), |renderer| { /* child drawn at full height */ });
```

The child node keeps its **full** height and is positioned at the top; only the parent node shrinks.
So the parent's siblings move up into the vacated space immediately, while the child continues to
paint at full size. The `with_layer` clip that should hide the not-yet-revealed part does not take
effect, and the child paints over whatever moved up.

**Observed**: pressing *Replay* on the `expand` entry in the component showcase's motion section. The
reveal reads as "nothing happened", followed by the revealed content overlapping the controls and
label beneath it.

**Not confined to the showcase.** `material::Accordion` is `expand(...)`, so the sidebar's tag-filter
panel behaves the same way in the running application. It hides better there for two incidental
reasons: its reveal is 90ms (`Accordion::REVEAL`) rather than the gallery's deliberately slow 600ms,
and what sits below it is a worktree list rather than a labelled row, so a brief overlap of similar
text reads as a flicker rather than as a defect.

## Artifact Traceability

### spec.md — `017-material-component-architecture`

- **Affected requirements**: FR-011 (a component owns the presentation state it animates) and FR-014
  (no component reaches for a central animator) are both **satisfied** — `Expand` owns its
  `Progress` correctly, and the bug is not in how it tracks progress but in what it draws with it.
- **Gap identified**: nothing in 017's requirements says a wrapper that animates its own *layout*
  must clip its child to the animated bounds. The wrappers are specified by who owns their state,
  not by what they must not paint over. Every gate 017 built — boundary, builder-API, opacity
  ratchet, idle frames — asks a *structural* question, and all four pass on this code.
- **Affected success criterion**: SC-005 is demonstrated by
  `tests/adding_an_animation_touches_one_file.rs`, which proves a new animated element needs no
  central registry. It drives `Progress` directly and never renders, so it cannot see a clip.

### spec.md — `009-sidebar-filter-toolbar`

- **Affected user story**: the tag-filter panel, which is where this is user-visible today.
- **Affected requirement**: the panel is specified to open *downward, pushing the list below it
  down* rather than floating over it — which is precisely the property that is broken. The list is
  pushed down correctly; the panel then paints over it on the way.

### plan.md

- **017**: the animation-wrapper section, which distinguishes passthrough wrappers (`Fade`, `Scale`)
  from `Expand`'s nested layout node. The distinction is documented; its consequence is not.
- **009**: the accordion's "pushes rather than floats" decision.

### tasks.md

- **False completions**: none. No task in either feature claimed to verify the reveal's clipping, so
  nothing was marked done that should not have been.
- **Missing tasks**: a regression test for the reveal, and the clip fix itself. See *Recommended fix*.

## Root Cause Analysis

Two causes, and the second is the more interesting one.

**Proximate**: `renderer.with_layer(bounds, …)` is being relied on to clip a child that is laid out
larger than its parent. Whether that holds is a property of the rendering stack's layer semantics,
and it evidently does not hold here — plausibly because the child's own `draw` receives the
unmodified `viewport` and clips against that instead.

**Underlying**: this class of defect is invisible to every check the project has. 017's four gates
all read *source structure* — who names what, which signature exposes what, where a frame is
requested. `style_snapshot` records resolved style values and explicitly does not cover layout. A
wrapper can therefore be structurally perfect and paint over its neighbours, and nothing fails.

Both 017 and 009 relied on a recorded manual `quickstart.md` walkthrough to cover appearance. 017's
own convergence pass found that its equivalent visual check *had never been run* — which is the
observation that motivated feature 020. This bug is a direct instance of that: an appearance defect
in a shipped component, surviving two features' manual passes, found in the first walkthrough over a
page that puts every component in one place.

## Why this was not fixed on discovery

Feature 020's FR-019 states that the application's appearance and behaviour must be unchanged by that
feature, and that any visible difference is a defect. Fixing `Expand` changes the sidebar tag
filter's motion — a genuine improvement, and still a change 020 is forbidden to make. It is therefore
reported here rather than patched there.

## Recommended Fix

1. **Reproduce first, in a test that fails.** The reveal's clipping is the property; the natural
   assertion is that `Expand`'s child never paints outside its parent's animated bounds. If that
   cannot be asserted without a renderer, the honest fallback is a layout-level assertion that the
   child node's bounds are clipped to the parent's — plus a `quickstart` step, recorded rather than
   assumed.
2. **Fix the clip.** Candidates, cheapest first: translate/clip the child node in `layout` so it is
   genuinely smaller rather than merely drawn inside a smaller layer; or pass a narrowed `viewport`
   to the child's `draw` so its own clipping agrees with the layer's.
3. **Check the sibling wrappers.** `Fade`, `Scale` and `Scrim` animate only their drawing and are not
   suspect, but `NavigationDrawer` performs a horizontal reveal and should be looked at in the same
   pass.
4. **Verify in the showcase.** `mise run showcase` → the motion section's `expand` entry, and the
   `Accordion` entry's third instance, which pairs the panel with the `FilterTrigger` that drives it.
   Both now exercise this on demand, which is what makes the fix cheap to confirm.

Then: `/speckit-bugfix-patch` to update the artifacts, `/speckit-bugfix-verify` to confirm
consistency, and the code fix on a branch of its own — or folded into feature 018, which owns the
motion system and will be touching these wrappers regardless.
