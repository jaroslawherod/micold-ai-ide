# Bug Report: a `ToggleChip`'s label is top-aligned in the 32dp pill, not centred in it

**Type**: Untested flow
**Severity**: Medium
**Feature**: `018-material3-visual-system` (§7.6 chip anatomy, FR-030).
Visible wherever a chip renders: `020-component-showcase-gallery`'s `material/toggle_chip.rs` row
(screenshot below), `009-sidebar-filter-toolbar`'s tag filters, and `013`/`016`'s worktree-form
toggles.
**Reported**: 2026-08-07
**Status**: Fixed
**Patched**: 2026-08-07 — spec artifacts updated (FR-030a, US4 scenario 10, SC-008a, contract §7.6
label-alignment row, T060 reopened, T086–T089 added).
**Fixed**: 2026-08-07 on `fix/chip-text-position` (T086–T089). See *Root Cause Analysis*, which was
**corrected** on investigation: the label node was never where this report first said it was.
**Second instance**: the sweep (T088) found the same omission in the small app bar. See below.
**Branch**: `fix/chip-text-position`

## Description

Every `ToggleChip` draws its label hard against the top inner edge of the pill instead of on the
pill's vertical centre line. The label's 20dp line box starts at y=0 inside a 32dp container, so
all 12dp of slack collects *below* the text and the word rides roughly 6dp high of centre. It reads
as a chip whose text has slipped upwards — most obvious on the showcase's inactive/active/accented
chip row, where three pills in a line all show the same upward offset.

Nothing about the chip's *box* is wrong: 32dp tall, `full` corner, 12dp of horizontal padding,
`label_large` — all as §7.6 specifies. Only the label's position within the box is wrong.

## Artifact Traceability

### spec.md

- **Affected user story**: US4 — component anatomy.
- **Affected requirement**: **FR-030** — "Chips and tags MUST match Material's chip anatomy —
  height, corner, padding and label type role." The requirement enumerates the four properties it
  cares about and *omits how the label sits inside the height* — which is why an implementation can
  satisfy every clause and still look wrong.
- **Gap identified**: FR-030 and contract §7.6 both treat "height 32" and "label role
  `label_large`" as independent facts. Neither says the label is centred on both axes. A fixed
  height is only meaningful together with an alignment rule, because the height is *larger than the
  label* by construction (32 vs a 20dp line box).

### contracts/design-tokens.md

- **Affected section**: §7.6 Chips and tags (FR-030), the property table at line 538.
- **Impact**: the table needs a row stating the label is centred vertically (and, with the 12dp
  ends, horizontally) within the 32dp container — the same way §7.3's touch-target rule is stated
  explicitly rather than left implied by the numbers.

### plan.md

- **Affected section**: the US4 component-anatomy pass.
- **Impact**: none structurally. This is a one-widget correction inside an already-built component,
  not a change of approach.

### tasks.md

- **Affected task**: **T060** `[P] [US4]` — "Apply chip anatomy in
  `crates/micold-client/src/ui/material/tag.rs` and `toggle_chip.rs` — 32dp height, `full` corner,
  `label_large` (FR-030)", marked `[X]`.
- **False completions**: T060 is *not* fully done for `toggle_chip.rs`. It applied the height that
  created the slack without applying the centring that the height requires. `tag.rs` is unaffected —
  a `Tag` sets no height, so its container is exactly its line box and there is no slack to
  mis-distribute.
- **Missing tasks**: centre the label in `ToggleChip`; add a layout assertion pinning it; add the
  centring row to contract §7.6.

## Root Cause Analysis

> **Corrected 2026-08-07, during the fix.** What follows below the correction is the original
> analysis, kept because being wrong in a specific way is what the next reader needs to see.
>
> **The label node is not at the top of the pill with the slack beneath it.** A button lays its
> content out under `limits.height(Fixed(32))`, and that sets the minimum together with the maximum
> — so the label node is *stretched* to the full 32dp and its bounds are the pill's bounds. The
> first version of the gate read the layout tree, measured 0dp of band above and 0dp below, and
> reported the deliberately top-aligned control it was sabotaged with as *centred*. The geometry is
> identical whether the label is centred or not.
>
> What actually differs is where the glyphs are painted **inside** a node that already fills the
> height, and the text widget defaults that to the top edge. So the defect is in the drawing, and
> only a rasterised check can see it — `material/content_placement.rs` renders the chip over its own
> fill colour and compares the ink's position against the same string drawn at the top of a 20dp
> line box.
>
> The correction does not change the fix's shape or the requirement: the label was 6dp high of
> centre, `Text` now states `height(Fill)` and `align_y(Center)`, and FR-030a stands as written. It
> changes what the *gate* had to be, and SC-008a was amended to say so.

Spec oversight compounded by an inherited framework default.

`crates/micold-client/src/ui/material/toggle_chip.rs:83-89` builds the pill as an iced `button` with
zero top/bottom padding and `height(Fixed(anatomy::chip::HEIGHT))`:

```rust
.padding(iced::Padding { top: 0.0, bottom: 0.0, left: PADDING, right: PADDING })
.height(iced::Length::Fixed(anatomy::chip::HEIGHT))
```

iced's `button` does not centre its content. Its `layout` calls `layout::padded`
(`iced_widget-0.14.2/src/button.rs:242`), which delegates to `layout::positioned` and places the
child at `content.move_to((padding.left, padding.top))` (`iced_core-0.14.0/src/layout.rs:203`) —
top-left, always. With `top: 0.0` the label lands at y=0 and the resolved 32dp height leaves the
remaining 12dp entirely beneath it.

The code comment above those lines shows the reasoning that produced the defect: "The vertical
padding is what makes the height, so it is derived from the two rather than guessed at 1dp." That is
true of `Tag`, which has no height and is sized *by* its padding. It is not true here, where the
height is set explicitly — so zero vertical padding stopped meaning "let the height come from the
label" and started meaning "pin the label to the top". The height (T060) and the padding (written
earlier, for a chip with no height of its own) were changed independently, and the pairing was never
re-examined.

It survived review because nothing asserts it. `label_large` is pinned by
`tests/type_role_call_sites.rs`, the 32dp height by the anatomy tokens, and the colours by
`style_snapshot.rs` — but no gate looks at *where inside its parent* a chip's label sits, so the one
property that broke is the one property nothing measures.

## Recommended Fix

1. Run `/speckit.bugfix.patch` to update the spec artifacts:
   - add a "Label alignment: centred on both axes within the container" row to contract §7.6;
   - extend FR-030 to name alignment alongside height, corner, padding and label role;
   - reopen T060 for `toggle_chip.rs` and add the centring + assertion tasks.
2. Run `/speckit.bugfix.verify` to confirm consistency.
3. Resume `/speckit.implement` for the code fix. Two candidate shapes, in order of preference:
   - give the button's content a centring wrapper (`container(...).center_y(Length::Fill)`), the
     same technique `icon_button.rs:155-159` already uses to centre a small container inside a
     larger fixed box — keeps the chip's own padding honest and does not depend on the label's
     metrics;
   - or set the label's height to `Length::Fill` with `align_y(Vertical::Center)`, which `Text`
     already supports via its `height`/`align_y` builders.
   Prefer whichever leaves the 32dp height and 12dp ends untouched.
4. Add the missing gate: a layout-level assertion that a chip's label node is vertically centred
   within its chip's bounds, alongside the existing gates in `crates/micold-client/tests/gates/`.
   Without it the defect can return silently, exactly as it arrived.

## Evidence

The showcase's chip row, posed inactive / active / accented-active — all three labels sit high in
their pills, with the empty band beneath the text visibly deeper than the one above it.

Confirmed fixed 2026-08-07 in the same view (`mise run showcase`, the `material/toggle_chip.rs`
entry): the three labels sit on the pills' centre line, with equal bands above and below.

## The second instance (T088)

The sweep for other components that fix a height above their content's found one: §7.1's small app
bar. `container(row).height(Fixed(64))` with no `align_y` — the row's own `align_y(Center)` centres
the row's children *against each other*, not the row against a height imposed from outside, and a
container aligns its loosely-laid-out child top-leading by default.

**It was invisible in the application**, and the reason is worth keeping: the shipped bar holds a
full-height action (the project switcher), which stretches the row to the whole 64dp, and a row that
already fills its container cannot be misaligned by one. The bar was correct *by accident* — for
exactly as long as some child happens to fill. A bar with only a title sat 18dp high of centre,
which is what the gate measured and what `Toolbar` now states outright. The layout-snapshot fixture
is unchanged by the fix, for the same reason it was unchanged by the defect.
