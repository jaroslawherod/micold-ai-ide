# Bug Report: an `IconButton`'s 48dp touch target is `Fill × Fill`, so every toolbar it sits in spreads apart

**Type**: Implementation drift
**Severity**: High — visible in the shipped application on the two bars a user looks at most.
**Feature**: `018-material3-visual-system` (§7.3 button anatomy, FR-027).
Visible wherever a non-`compact()` `IconButton` shares a row with a `Length::Fill` sibling:
`001-app-shell-about`'s top app bar (§7.1) and `005`/`010`/`012`'s terminal bottom bar.
**Reported**: 2026-08-07
**Status**: Fixed
**Patched**: 2026-08-07 — spec artifacts updated: SC-008b (spec.md), the builder-aliasing risk row
(plan.md), T057 and T088 reopened and T090–T095 added (tasks.md), the two bars' trailing edges added
to the §B4 manual pass (quickstart.md), and the coverage note in
[019](../../019-layout-snapshot-parity/spec.md).
**Fixed**: 2026-08-07 on `fix/toolbar-layout-is-broken` (T090–T095), behind a failing test.
**Branch**: `fix/toolbar-layout-is-broken`

## Description

`IconButton` wraps its pressable in a container meant to be exactly §7.3's 48 × 48 minimum
interactive target. That container is instead **`Length::Fill` on both axes**: it claims a share of
whatever free space its parent row has, and centres the 24dp glyph in the middle of that share.

The 48dp figure is written in the code and is overwritten one line later
(`crates/micold-client/src/ui/material/icon_button.rs:155-160`):

```rust
container(element)
    .width(Length::Fixed(anatomy::button::MIN_TOUCH_TARGET))   // 48
    .height(Length::Fixed(anatomy::button::MIN_TOUCH_TARGET))  // 48
    .center_x(Length::Fill)   // = .width(Fill).align_x(Center)   ← discards the 48
    .center_y(Length::Fill)   // = .height(Fill).align_y(Center)  ← discards the 48
    .into()
```

Two consequences, both user-visible:

**1. The top app bar (§7.1).** `Toolbar` builds `row![title, Space::Fill]` and then pushes the
actions, so the actions are supposed to be pushed to the trailing edge by the one spacer. There are
in fact **two** `Fill` children — the spacer and the overflow-menu trigger — so they split the free
space in half. The project-switcher chip lands near the middle of the bar and the ⋮ glyph floats
centred in an empty 500dp box roughly three-quarters across, well short of the trailing edge.

**2. The terminal's bottom status bar.** The same row holds a `Space::Fill` plus **two**
non-`compact()` icon buttons (the new-instance "+" and the mode toggle), so three `Fill` children
split the free width into equal thirds. The mode toggle sits about 220px short of the right edge,
contradicting the placement its own call site states — "the mode toggle anchors the bar's
bottom-right corner", `crates/micold-client/src/ui/terminal.rs:454`. The vertical `Fill` also lets
the bar claim height from the terminal body above it instead of staying a slim strip.

Nothing about the *glyph* is wrong — 24dp, `on_surface_variant`, `full` corner, all as §7.3 states.
Only the box around it is, and the box is the one thing §7.3 names a number for.

## Root Cause Analysis

`iced::widget::Container::center_x` and `center_y` **set the axis length in addition to aligning**
(`iced_widget-0.14.2/src/container.rs:145-152`):

```rust
pub fn center_x(self, width: impl Into<Length>) -> Self {
    self.width(width).align_x(alignment::Horizontal::Center)
}
```

So `.width(Fixed(48)).center_x(Fill)` is `.width(Fixed(48)).width(Fill).align_x(Center)`. The
builder reads as "48dp wide, contents centred"; it means "as wide as possible, contents centred".
The two calls that state the requirement are dead code, silently overwritten by the two that were
meant only to centre.

Why it survived to here:

- **Nothing failed.** `tests/tokens_anatomy.rs` pins `button::MIN_TOUCH_TARGET == 48.0` and is
  green — the constant is right, only its use is wrong. SC-008 verifies anatomy "by their
  constants" and cannot see this. SC-008a reads drawn pixels for *content placement*, and the glyph
  genuinely is centred, so that gate passes too. No criterion reads a component's laid-out **size**.
- **The snapshot baked it in.** `layout_snapshot.txt` was regenerated with the defect present, so
  the one artifact that did record 499.9 × 64.0 records it as correct.
- **BUG-001 read it as background fact.** Its closing note explains the app bar was "correct by
  accident … the shipped bar holds a full-height action, which stretches the row to the whole 64dp".
  That full-height action is this bug. The thing that made BUG-001 invisible was another bug, and
  the sweep classified it as scenery rather than opening it.

The class BUG-001 named — "a fixed height above the content's obliges a statement about the
content" — has a mirror image that FR-030a does not cover and that this bug is: **a stated fixed
size that a later builder call silently discards.** BUG-001 was a number that was right with nothing
placing it; this is a number that is right and never applied.

## Recommended Fix

1. Run `/speckit.bugfix.patch` to update the spec artifacts:
   - reopen **T057** and **T088**, recording why the sweep cleared this site;
   - correct **FR-045**'s claim that every icon button outside the sidebar takes the full 48dp;
   - add a success criterion, alongside SC-008a, for a component's laid-out **size** matching its
     anatomy entry — SC-008's constants and SC-008a's pixels between them still miss it.
2. Run `/speckit.bugfix.verify` to confirm consistency.
3. Resume `/speckit.implement` for the code fix at `icon_button.rs:155-160` — drop the two
   `.width`/`.height` calls and centre without resizing:

   ```rust
   container(element)
       .width(Length::Fixed(anatomy::button::MIN_TOUCH_TARGET))
       .height(Length::Fixed(anatomy::button::MIN_TOUCH_TARGET))
       .align_x(alignment::Horizontal::Center)
       .align_y(alignment::Vertical::Center)
       .into()
   ```

   Equivalently `.center(Length::Fixed(anatomy::button::MIN_TOUCH_TARGET))`, which takes the length
   once and cannot be written inconsistently. Prefer that form, and grep the tree for every other
   `center_x(`/`center_y(`/`center(` whose container also sets a width or height — the same
   overwrite is available at any of them.
4. Add the missing gate, before the fix (Principle I): assert a non-`compact()` `IconButton`'s
   laid-out node is 48 × 48 regardless of the row it is placed in, by reading the layout tree the
   way `tests/gates/containment.rs` does. Then regenerate `layout_snapshot.txt` and check that the
   app-bar diff moves the menu trigger to the trailing edge.
5. Confirm in the running application (`mise run run`): the ⋮ sits on the app bar's trailing edge
   next to the project switcher, and the terminal's mode toggle sits in the bar's bottom-right
   corner with the bar back to a slim strip.

## Resolution

All five steps done on `fix/toolbar-layout-is-broken` (T090–T095), in that order.

**The guard first (T090).** `src/ui/material/anatomy_size.rs` — six tests, confirmed red against
the unfixed component before a line of it changed:

> an icon button's width measured 1200dp in a 1200dp box and 400dp in a 400dp one, but its anatomy
> entry states 48dp — it is taking whatever room it is offered, so the stated size is not being
> applied at all.

Each component is laid out under two differently-sized limits, because one measurement cannot
separate `Fixed(48)` from `Fill` — offer exactly 48dp and they agree. Each axis is declared `Fixed`,
`Fill` or `Content`, so the check distinguishes the app bar's intended elastic width from an
accidental one rather than banning `Fill` outright. `the_gate_can_fail` rebuilds the
`.width(Fixed(48)).center_x(Fill)` chain directly, so the check remains demonstrably able to fail
now that the component is correct.

**The fix (T091).** `align_x(Center)`/`align_y(Center)` in place of `center_x(Fill)`/`center_y(Fill)`
— aligning without resizing. Two lines.

**The sweep (T092)** came back clean. Four other `center_*` sites, none the same shape: the overlay
and the terminal's empty states pass `Fill` to containers that are meant to fill and have no stated
size to lose; `activity_badge` passes its `Fixed(badge.size)` through `center_x` itself. The defect
needs both halves — a stated size *and* a later call that takes an argument — and only the icon
button had both.

**The fixture (T093)** carries the proof. The app bar's overflow trigger moves from
`764.1, 0.0, 499.9 × 64.0` to `1216.0, 8.0, 48.0 × 48.0`: right edge 1264, which is 1280 less
§7.1's 16dp trailing padding, so it is flush against the edge it belongs on. The project switcher
follows it out to 1130.3 from the middle of the bar.

**The terminal bar (T094)** now has geometry coverage, which it never had — the reason only the app
bar's half of this defect was recorded anywhere. The new `session-terminal-bottom-bar` covered state
poses a `Regular`-mode session with no shell started, so the bar carries the most it can, and
records the two icon controls at `1168.0, 48 × 48` and `1224.0, 48 × 48` — the second flush against
the bar's trailing padding, with the row's single `Space::Fill` taking all 737.4dp of the slack the
two of them had been splitting. The bar is a 64dp strip at the window's bottom edge rather than the
half-height block its `Fill` height had made it.

**Step 5, confirmed — and it needed a new tool to do it.** Nothing on this machine could take a
screenshot from a shell: `grim` needs `wlr-screencopy`, which Mutter does not implement; `import` is
X11 against a Wayland session; `org.gnome.Shell.Screenshot` answers `AccessDenied`; the portal opens
a consent dialog; RDP would need a package install and a listener on port 3389. So
`scripts/screenshot-session.py` was written against `org.gnome.Mutter.ScreenCast` — the API the RDP
server uses underneath — pulling one frame off the monitor's PipeWire node. `mise run screenshot`,
documented in [`docs/development/screenshots.md`](../../../docs/development/screenshots.md) and
pointed at from quickstart Part B.

The confirming frame holds **both builds at once**, which is better evidence than an after-shot
alone: the installed 0.6.0 behind (pre-fix, full width 0–1920) and the worktree build in front
(post-fix, x 447–1473). Ink extents, same frame:

| | title | project chip | ⋮ | window right edge | ⋮ inset from edge |
|---|---|---|---|---|---|
| installed 0.6.0 (before) | 17–145 | 984–1082 | 1502–1504 | 1920 | **417px** |
| worktree build (after) | 465–593 | 1289–1387 | 1430–1433 | 1473 | **42px** |

Before, 420px of nothing sits between the chip and the ⋮ and another 417px between the ⋮ and the
edge — the two halves of the free space the trigger was splitting with the spacer. After, the gap is
43px and the inset 42px: the chip is immediately left of the ⋮, and the ⋮ is one padding step plus
half its own 48dp target from the trailing edge. That is §7.1 as written, and it matches what the
fixture predicted at 1280 × 800.

**The terminal's bottom bar was not confirmed by eye**, and this is the one claim here made from
measurement alone: reaching it needs a session opened by hand, and nothing here can drive input.
Its geometry is pinned by the new `session-terminal-bottom-bar` covered state at 1280 × 800 and its
controls by `anatomy_size.rs` at two further sizes — the same fix, the same two controls, one frame
short of having been looked at.
