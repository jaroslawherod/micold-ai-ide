# Bug Report: a menu item's content rests against the top of its 48dp instead of centred in it

**Type**: Implementation drift — §7.5 states the placement, FR-030a requires it, and no component applied it.
**Severity**: Medium-high — every row of every menu and popover in the application, on every screen.
**Feature**: `018-material3-visual-system` (§7.5 menus; FR-029, FR-030a).
**Reported**: 2026-08-07, from the running application by the owner, immediately after BUG-003 shipped.
**Status**: Fixed
**Fixed**: 2026-08-07 on `fix/menu-item-vertical-centring`, behind a failing test.

## Description

§7.5's item row reads **"48, with the item's content centred in it"**. BUG-003 applied the 48, the
12dp ends, the 24dp glyph and its tone — and left the content against the top edge. The label sat
8.4dp high of centre on every menu row, which is what the owner saw and what the fixture had been
recording all along.

## Evidence

From `layout_snapshot.txt`, one overflow-menu item, before and after:

| node | before | after |
|------|--------|-------|
| item | `y 73.0, h 48.0` — centre **97.0** | unchanged — centre **97.0** |
| label | `y 78.6, h 20.0` — centre **88.6** | `y 87.0, h 20.0` — centre **97.0** |
| glyph | `y 73.0, h 31.2` — centre **88.6** | `y 81.4, h 31.2` — centre **97.0** |

## Root Cause Analysis

**A `Row` is not a `Container`, and the difference is exactly this.** A container lays its single
child out and aligns it inside the container's own box, so a fixed height plus `align_y(Center)`
centres the child in that height — which is why `button.rs` (T097) and `icon_button.rs` are correct.
A **row** centres its children *against each other*, inside the cross size the flex layout computed
from them, and that band is then laid against the top of whatever node it was stretched into. The
menu item's row was 48dp tall and its content band was 31.2dp — the icon's line box — so the band
sat at the top and took the label with it.

**The reasoning that let it through reads as correct**, which is why it deserves recording rather
than deleting. `4cd33b6` wrote: *"The row already states `align_y(Center)`, and here that is enough:
`button` stretches its content node to the fixed height, so the row is 48dp tall and centres its
children inside it."* Both halves of that sentence are true and the conclusion does not follow.
BUG-003 then quoted it forward, and quoted BUG-001's app bar — the same defect, in a container
rather than a row — while missing that the row needed its own answer. Three commits carried the
claim; none measured it.

**Why the checks did not.** `menu_anatomy.rs` was written by BUG-003 for §7.5's spatial figures and
measured every one of them on the **x** axis — the 12dp ends, the 24dp glyph, the panel's padding,
the gap between items — plus the item's height. It never asked where the content sat inside that
height. `content_placement.rs` (SC-008a) is the check built for exactly this class after BUG-001,
and the menu item was never added to it: it covers the chip, the app bar and the button.
`layout_snapshot` recorded `78.6` as the expected value from the day the state was covered, which is
the third time in four bugs that a fixture has held a defect as its baseline.

## Resolution

The row states `height(Length::Fill)`, so its own box *is* the 48dp and the centring happens inside
it. `a_menu_items_content_is_centred_in_its_height` was confirmed red first — content centred on
23.6dp inside a box centred on 32dp.

**The sweep found one more, and it is fixed here too.** `typeahead.rs`'s result row is the same
shape — a `Row` with `align_y(Center)` inside a `button` with a fixed 48dp — and had the same
defect. FR-029b deliberately keeps that row separate from the shared one, and "not the same
component" is not "not the same mistake". `row_element` is now `pub(super)` and
`a_typeahead_rows_content_is_centred_in_its_height` measures it, so the fixed half is not the half
nothing checks.

Everything else with a fixed height was checked and is clean: `button.rs`, `icon_button.rs` and
`toolbar.rs` all use a container, which aligns its child within its own box.

## What this leaves

`content_placement.rs` still does not cover the menu item. This bug was caught by geometry because
the row's node is *not* stretched — the label is a 20dp box at a measurable y — but the class
SC-008a exists for is the one where geometry cannot tell centred from top-aligned, and a component
that acquires that shape later would need the rasterising check. Recorded rather than fixed here.
