## Description

§7.2 gives the `dense` density a **36dp** row and the `standard` density a **48dp** row. FR-026c
makes that mandatory and derived — the sidebar's rows "MUST be an application of that scale —
density −3 on the standard list row". `density::height(LIST_ROW_BASE, DENSE)` returns 36.0 and is
correct.

No tree row applies it. `tree_view.rs` sizes every row by its content, at any depth and at either
density. A one-line dense row measures **23.6dp** in the shipped sidebar; the standard density
resolves to exactly the same 23.6dp, so the two named densities differ only in horizontal padding
and icon gap and are the *same height as each other* — which FR-026 forbids in as many words ("no
list may invent a third density or size its rows ad hoc").

The user-visible change is on **nested rows**, and it is a regression rather than a standing gap.
Before `1cb9873` the height floor was carried by each row's indent spacer, `Space::new()
.width(Fixed(indent)).height(Fixed(row_height))`. A depth-0 row indents by zero, which makes that
spacer `Fixed(0)` and therefore *void*, and iced drops a void child outright — so the floor had
never reached a top-level row. A depth-1 row indents by `spacing::MD` = 16dp, so its spacer was
**not** void and the floor did apply. Removing the spacer's height removed the only place the floor
was working:

| Row                                             | Before `1cb9873` | After (today) | Change      |
|-------------------------------------------------|-----------------:|--------------:|------------:|
| Sidebar session row (depth 1, `dense`)          |         **36.0** |      **23.6** | **−34%**    |
| Sidebar worktree row with tags (depth 0)        |             41.6 |          41.6 |          — |
| Sidebar `Default` / untagged row (depth 0)      |             23.6 |          23.6 |          — |
| Gallery `TreeView` sample rows (depth 1, `standard`) | **48.0**    |      **23.6** | **−51%**    |

So the sidebar's session rows collapsed to the same height as the worktree rows they nest under,
and the gallery — the one page whose job is to show what the component looks like — has been
demonstrating a `standard`-density list at half its stated height since 2026-08-06.

## Evidence

**Measured**, by laying `TreeView` out under `anatomy_size.rs`'s roomy limit (1200 × 900) and
reading the row node, with one `TreeItem` carrying an icon and an `on_press`:

```
                       HEAD    with the pre-1cb9873 spacer restored
depth=0 (dense)        18.2    18.2      ← floor never applied: the spacer is Fixed(0)-wide, void
depth=1 (dense)        18.2    36.0      ← the regression, in one line
```

**The void-child mechanism, isolated** — a bare `row![Space]` plus one line of text:

```
Space::new().width(Fixed(0.0)).height(Fixed(36.0))   → row measures 20.0   (spacer dropped)
Space::new().width(Fixed(16.0)).height(Fixed(36.0))  → row measures 36.0   (spacer honoured)
```

This is the same trap `snackbar.rs:64-70` documents and works around by leaving the spacer's width
`Shrink` rather than `Fixed(0)`. `tree_view.rs` hit it, and the fix went the other way.

**Recorded**, `crates/micold-client/tests/fixtures/layout_snapshot.txt`, scene
`main-shell-sidebar-expanded` — the four rows of the sidebar tree, byte-identical before and after
`1cb9873`:

| Node                          | w     | h        | what it is                    |
|-------------------------------|------:|---------:|-------------------------------|
| `…/2/0/0/0`                   | 244.0 | **23.6** | the `Default` project row     |
| `…/2/0/0/1`, `/2`, `/3`       | 244.0 |     41.6 | tagged worktree rows          |

**Every row in the fixture is depth 0.** No covered state expands a worktree, so no session row
exists in any of the sixteen scenes. That is why the snapshot was byte-identical across the change,
and why T076 could report "the visible count has not moved at all" in good faith while a third of
the height came off every nested row in the application.

## Root Cause Analysis

Three things had to line up, and they did.

**1. The floor was attached to the wrong element, and the wrongness was invisible.** Putting it on
the indent spacer meant the floor's existence depended on the row's depth, via iced's void-child
rule. Depth 0 silently lost it; depth 1 silently kept it. No one measured a depth-1 row, so the
component looked uniformly floor-less when it was actually inconsistent.

**2. The conflict that motivated removing it was computed against that same wrong element.** T076's
note reads: "applying its 36dp dense row height takes those rows to 36.0 and 54.0 — a ~30% drop in
what fits without scrolling." The **54.0 is an artifact of flooring the name line rather than the
row**. A tagged row is `column![line, tag_row]`; a 36dp floor on `line` makes the row 36 + 2 + 16 =
54. Applied to the row instead, a tagged row is `max(36, 41.6)` = **41.6 — unchanged**. Measured:

```
                      HEAD    36dp floor on the row (not the line)
worktree, untagged    18.2    36.0
worktree, tagged      36.2    36.2      ← unchanged
session (depth 1)     18.2    36.0      ← back to its pre-1cb9873 height
```

In the reference scene (one untagged row, three tagged) the correct construction costs **+7.7%** of
column height, not 30%. FR-026a's ceiling is "not materially"; 7.7% is not material, and 30% was
never the number. The requirements were never in conflict — the construction was.

**3. Nothing could fail.** `tokens_anatomy.rs` and `tokens_scales.rs` pin the *constants*, and 36.0
is still 36.0. `layout_snapshot.txt` records only depth-0 rows. `anatomy_size.rs` measures the
component with a single depth-0 specimen. `content_placement.rs` asks where content sits inside a
height, and a row with no height has no slack to misplace. Each gate was green, and each was green
about something else — the same pattern as BUG-002, one rung further down: BUG-002 was a figure that
was right and never applied; this is a figure that was right, applied at *one depth only*, and then
removed because the depth where it worked was never measured.

The deeper process failure is that a `MUST` requirement was set aside by a commit and a code
comment. FR-026c admits no alternative height — FR-026b's scale has four steps and 36 is the only
one at −3 — so "the purpose wins and the number does not apply" is not a deviation the spec has room
for. It needed either a spec change or a different construction, and there was a different
construction.

## The figures the fix uses

This report recommended restoring §7.2's 36dp. The owner's decision on it went further, and the
reason is worth recording: **the base being scaled was Material 2's.** MDC-web's single-line list
item is 48dp, which is where §7.2's `standard` came from, in a feature whose subject is Material 3.
Material 3 specifies the list item at 56dp for one line, 72dp for two and 88dp for three.

Material's density scale is a **separate, generic axis** — four steps 0/−1/−2/−3 with
`height = base + 4dp × step` — published for the web and already implemented exactly by
`density::height`. It applies to any base, so moving the base does not cost the scale: FR-026b and
FR-026c stand unchanged, and `dense` becomes the M3 base at step −3.

| Density        | One-line | Two-line |
|----------------|---------:|---------:|
| `standard` (0) |       56 |       72 |
| `dense` (−3)   |   **44** |   **60** |

What that costs, against today's shipped sidebar:

| Row                                      | Today | After | Pitch (+4dp gap) |
|------------------------------------------|------:|------:|-----------------:|
| `Default` / session row                  |  23.6 |  44.0 |    27.6 → 48.0   |
| Worktree row with tags                   |  41.6 |  60.0 |    45.6 → 64.0   |
| Reference scene column (1 + 3, gaps included) | 160.4 | 236.0 |        +47%      |

So a one-line row costs 74% more vertical space and a tagged one 40% more: between a quarter and
two-fifths fewer worktrees fit without scrolling, depending on how many carry tags. FR-026a is amended to accept that rather than
forbid it — the amendment is the substantive spec change here, and it is what makes the rest of the
fix legal. Note the direction: this report argued the FR-026a conflict was an artifact and could be
avoided; at the Material 2 base that is true (7.7%), and at the Material 3 base it is not. The
conflict is real now, and it is resolved deliberately instead of by deleting a figure.

## Recommended Fix

1. Run `/speckit.bugfix.patch` to update the spec artifacts:
   - **contracts §7.2** — state the heights as **minimums**, not fixed heights, so a two-line row
     keeps the height its own second line asks for; move the base onto Material 3's list item and
     add the two-line row, which the contract never covered. Note that the ~28dp baseline is a
     *pitch*, so it is not comparable with a row height without adding the column's 4dp gap.
   - **spec.md** — FR-026 and FR-026b say what they should. Add **FR-026d** for where a height
     attaches and that it is a minimum; amend **FR-026c** to name the base as Material 3's; amend
     **FR-026a**, which as written forbade the height that FR-026c requires; correct **FR-045**'s
     36dp; add an acceptance scenario for a **nested** row; and add **SC-008d** — the anatomy gate
     exercises every axis a component varies on, depth included, since one specimen is what hid a
     depth-dependent floor.
   - **tasks.md** — reopen **T056**; record why T076's conclusion does not follow from its
     measurement; add the tasks below.
   - **019's covered set** — add an expanded-worktree state, so a nested row exists in the fixture.
2. Run `/speckit.bugfix.verify` to confirm consistency.
3. Resume `/speckit.implement` for the code fix in `tree_view.rs`, behind a failing test
   (Principle I). Apply the floor to the **row**, and carry it on a spacer whose width stays
   `Shrink` so it can never go void — `snackbar.rs`'s idiom:

   ```rust
   let base = if item.tags.is_empty() {
       density::LIST_ROW_BASE            // 56 — M3 one-line
   } else {
       density::LIST_ROW_TWO_LINE_BASE   // 72 — M3 two-line
   };
   let floor = density::height(base, step);
   let body: Element<'a, M> = row![Space::new().height(Length::Fixed(floor)), content]
       .align_y(Alignment::Center)
       .width(Length::Fill)
       .into();
   ```

   Three properties, one per way this went wrong: the minimum is on the **row**, not on its name
   line; the spacer's **width stays `Shrink`** so it can never become void (`snackbar.rs:64-70`'s
   idiom); and nothing consults `item.depth`. Keep the indent spacer for indentation only. The row
   keeps `Length::Shrink`, so a row taller than its figure still grows rather than being clipped.
4. Update the gate: `anatomy_size.rs`'s tree-row entry becomes `Extent::Fixed(density::height(…))`
   for a one-line row, with a **second** specimen at depth ≥ 1, a **third** at the other density,
   and a fourth taller than the floor asserting `AtLeast` rather than `Fixed`. A depth-0-only
   specimen is what made this invisible twice.
5. Regenerate `layout_snapshot.txt`; the diff for the new expanded-worktree scene is the proof.
6. Confirm in the running application (`mise run run`): expand a worktree and check its session rows
   stand at the same height as the worktree rows above them rather than crowding beneath them, and
   that the worktree count visible without scrolling is unchanged for tagged rows.

## Postscript: the gate this uncovered (T129)

Applying the height moved the sidebar's rows apart from the collapsed filter panel's overhang, and
`layout_text_overflow.rs` failed — not with a new overflow, but because both of its recorded
`KNOWN_OVERFLOWS` exemptions had **stopped firing**, and a stale exemption fails the build.

They were false positives, and had been since they were recorded. The text is the sidebar's
`"Short"` **row label**, drawn at (32, 146.8) and clipped by its own widget to 164 × 15.6 — it fits.
It was measured against a 24.65dp *filter-panel chip node* that the collapsed, zero-height `Expand`
had left lying at the same coordinates. The exemption's own note ("the chip labelled `Short` wants
28.9px in the 19.2px it is allowed") described a squeeze that never happened; what happened is that
two unrelated subtrees overlapped and the deeper one was blamed.

Proven by controlled experiment: reverting **only** `tree_view.rs` reproduces the finding at exactly
the exempted path, and nothing else varied.

The attribution rule now identifies a text's owner by the **clip the painter passed**, falling back
to the deepest containing node only when no node matches — so 019 FR-018's motivating defect, a
widget that clips to nothing of its own, is still caught. With the old row heights restored and the
exemption list empty the gate is clean, which is what distinguishes removing a false positive from
moving one. Recorded as 019 FR-018a.

Worth noting for its own sake: this gate had already changed the same rule once, from *narrowest*
containing node to *deepest*, against this same class of error. That change altered which unrelated
node wins, not whether one can — which is the third time in this feature that a fix addressed the
instance rather than the mechanism.
