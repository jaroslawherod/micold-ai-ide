# Bug Report: a tag chip is indented by an arithmetic that omits most of the row it is aligning under

**Type**: Implementation drift — feature 008's FR-001 says the chips sit beneath the label, and the
indent is computed from a formula that does not describe the row.
**Severity**: Low-medium — cosmetic, confined to rows that carry a **leading icon**, which today is
the component gallery and not the shipped sidebar.
**Feature**: `018-material3-visual-system` (§7.2 list and tree rows) over
[`008-worktree-sidebar-refinement`](../../008-worktree-sidebar-refinement/spec.md) FR-001, which is
where the second line and its claim come from.
**Reported**: 2026-08-08, from the owner's screenshot of `mise run showcase`, while closing T127.
**Status**: Open

## Description

`TreeView` renders a tagged row as two lines and indents the second so the chips start under the
label above them. `tree_view.rs`:

```rust
let tag_indent = indent + label_role.size() + spacing::SM;
```

That is `indent + one icon + one gap`. The row it is aligning under is:

```
indent → twisty slot → gap → leading icon → gap → badge → gap → label
```

so the formula omits the twisty slot and two of the three gaps, and counts the icon whether or not
the row has one. It is not a near-miss of the right expression; it is a different expression that
happens to land close in one configuration.

**Measured**, from the gallery at `standard` density with a leading icon, at 1:1:

| | x |
|---|---:|
| Leading icon | 106 |
| Label | ~134 |
| **Tag chip** | **87** |

The chip starts 47px left of the label and 19px left of the icon — outside the text column
altogether, hanging under the twisty.

**Why the sidebar looks right.** Worktree rows there carry **no** leading icon (FR-010 — status is
cued by an error-tinted name, not a glyph), the density is `dense` so each gap is 8dp not 16, and
`label_role` is `sidebar_name` at 12dp rather than `body` at 16. The two errors — a counted icon
that is absent, and uncounted gaps — very nearly cancel:

| | x |
|---|---:|
| Label | 44 |
| Tag chip | 40 |

Four pixels, which reads as aligned. So the shipped application is unaffected and the gallery is
not, which is the opposite of the usual direction and worth stating plainly: the page whose job is
to show what a component looks like is the one showing it wrongly.

## Artifact Traceability

### spec.md / contracts

- **008 FR-001** — the requirement that puts chips on a second line "beneath the label". Nothing in
  018 restates the alignment, and §7.2's row table has no entry for the second line's indent. That
  gap is why the formula was never checked against anything.
- **Impact**: §7.2 should say what the second line aligns to, in the same way §7.3 gained a
  label-alignment row under BUG-001 and §7.5 gained one under BUG-004. A number with nothing stating
  its intent is the shape all four of this feature's bugs have had.

### tasks.md

- No false completion. T060 applied chip anatomy and T056 the row densities; neither owned the
  second line's indent, and no task ever did.

### Cross-feature

- **020's gallery** — `showcase/sections/surfaces.rs` poses the tree with `.with_icon(Icon::Git)` at
  the default `standard` density, which is precisely the configuration that exposes this.

## Root Cause Analysis

The indent was written as an arithmetic guess at the label's offset rather than derived from it, and
nothing measures where the second line starts. `anatomy_size.rs` reads a row's **box**, not what is
inside it; `content_placement.rs` reads where content sits **vertically** inside a fixed height;
`layout_snapshot.txt` records the chip's x and has recorded 87 as correct since the day the state
was covered. The same three-gates-and-none-of-them-sees-it pattern as BUG-002, BUG-004 and BUG-005.

It also went unnoticed because the one place a person looks — the sidebar — is the one place the
formula's two errors cancel.

## Recommended Fix

1. Give §7.2 a row for the second line's alignment, so there is something to check the code against.
2. Derive the indent from the same parts the first line is built from rather than restating them:
   the leading run is `indent + twisty + gap (+ icon + gap) (+ badge + gap)`, and the row already
   computes each of those. Build the line once and reuse its leading width.
3. Gate it: assert the chip row's x equals the label's x, at both densities and with and without a
   leading icon — the four-way matrix that would have caught a formula right in one corner of it.
4. Regenerate `layout_snapshot.txt`; the recorded 87 is the defect and the diff is the proof.
