# Bug Report: the project switcher is a bespoke trigger and a bespoke panel — a 28dp target beside a 48dp one, and a panel that pops where its neighbour fades

**Type**: Implementation drift over a spec gap — BUG-003's FR-029b unified the menu *row* and left
the *trigger* and the *panel* forked, and nothing states that a control which opens a menu is a
shared button or that a panel hanging off the bar is a menu overlay.
**Severity**: Medium — two controls on the trailing edge of the same app bar, side by side on every
screen, disagreeing about height, glyph size, panel width and whether closing animates. The
switcher's 28dp box and 14dp glyph match no figure §7 gives an app-bar action of either shape.
**Feature**: `018-material3-visual-system` (§7.1 top app bar, §7.3 buttons, §7.5 menus; FR-027,
FR-029a, FR-029b). The forked components belong to
[`008-background-project-switching`](../../008-background-project-switching/spec.md) FR-004, which is
where the switcher was written, and to
[`017-material-component-architecture`](../../017-material-component-architecture/spec.md) FR-008,
which unified the floating *mechanics* and left the styled layer alone.
**Reported**: 2026-08-08, from the owner: the switcher "should use regular icon button and context
menu to not make it a kind of special case".
**Status**: Patched
**Patched**: 2026-08-08 — spec artifacts updated: FR-029c, SC-008e and US4 acceptance scenario 13
(spec.md); §7.1's action-control row and §7.5's panel-width, panel-transition and
"one panel, one trigger" entries (contracts/design-tokens.md); the part-versus-whole and
same-kind-gate risk rows (plan.md); T131–T139 added (tasks.md); FR-004 amended in
[008](../../008-background-project-switching/spec.md) to name the shared button the switcher is.

**Amended**: 2026-08-08, on the owner's correction, before the follow-up landed. The first fix read
"regular icon button" as *icon-only* and moved the project's name into a tooltip. It is an icon
**and** a label — `Button::text(..).leading(..)` — the label being the quickest way to see which
project is active without opening the panel. What was ever wrong was the hand-assembly, not the
label: FR-029c and SC-008e now say *a shared button*, of which there are two shapes, rather than
*the icon button*.

**Follow-up**: 2026-08-09 — the same two-colour defect was recorded here as pre-existing at three
*other* call sites (`shell.rs`'s "Open another project" and "Rename", `project_selector.rs`'s "Up"),
each passing `on_surface` to an outlined button's leading slot beside a `primary` label. Fixed by
giving the slot the variant's own content colour rather than by correcting the three: `Button::leading`
no longer takes a tint, `Button::leading_tinted` is the explicit override for a glyph whose tone
carries meaning (Forget's destructive red), and `IconSurface::AccentButton` — added here so a call
site could name the accent — is gone, because no call site names the colour any more.

## Description

`crates/micold-client/src/ui/material/project_switcher.rs` exposes two components that duplicate two
components the library already has:

- **`ProjectSwitcherTrigger`** hand-builds `button(row![icon, Text])` with `style::text_button`, its
  own `spacing::XS` padding, its own `Ripple` and its own `Tooltip` (project_switcher.rs:64-84).
  `MenuTrigger`, the control immediately to its right, is three lines —
  `IconButton::new(icon, roles).on_press(msg).into()` (menu.rs:240-246). Everything `IconButton`
  decides for every other icon action in the application — §7.3's 24dp glyph, §7.3's 8dp inset, the
  48dp interactive target, the disabled treatment, the ripple tint — the switcher decides again,
  differently.
- **`ProjectSwitcherOverlay`** builds its own `Surface` with its own `PANEL_WIDTH = 260.0` and its
  own restatement of `MenuOverlay`'s default anchor (project_switcher.rs:182-203 against
  menu.rs:299-352). It yields `Option<Surface>` — `None` while closed — so unlike `MenuOverlay`, which
  deliberately outlives its own flag in order to fade out (menu.rs:253-257, 312-328), **the switcher
  panel cannot animate closed at all**. It has no `fade`, no `animate_in`.
- **`ProjectRow`** is a parallel payload type for what `MenuItem` already expresses: `row_column`
  maps one to the other field by field, adding nothing (project_switcher.rs:140-157).

The panel *content* is already shared — BUG-003's FR-029b routed it through `menu::item_column` and
`menu_panel`. What is left is the frame around it, and the frame is where the remaining divergence
lives.

## Evidence

From the checked-in layout fixture, `crates/micold-client/tests/fixtures/layout_snapshot.txt`, scene
`project-switcher-open` (1280×800, light; both triggers present in one scene):

```
base 0/0/0/0/0/0/2      1130.3   18.0    69.7    28.0    switcher trigger   §7.1 ICON_TARGET: 48  ✗
base 0/0/0/0/0/0/2/0/0  1134.3   22.9    14.0    18.2      its glyph        §7.3 glyph: 24        ✗
base 0/0/0/0/0/0/3      1216.0    8.0    48.0    48.0    overflow trigger   §7.1 ICON_TARGET: 48  ✓
base 0/0/0/0/0/0/3/0/0  1228.0   16.4    24.0    31.2      its glyph        §7.3 glyph: 24        ✓
```

The switcher's hit area is **28dp tall** — short of `density::BUTTON_BASE`, the 40dp §7.3 gives the
labelled button it should be, and further still from the 48dp target its icon-only neighbour takes —
and its glyph is 14dp, the *label's* role, where §7.3 puts a button's leading icon at 18 and an icon
button's at 24. It matches no shape §7 defines. This is not the sidebar, so FR-045's recorded
small-target deviation does not cover it: that exemption is scoped to the sidebar's dense header,
and `IconButton::compact()` is how it is taken. The switcher never asks for it — it never reaches a
shared button at all.

The two panels off the same trailing edge, from the same fixture:

```
base 0/2/0   1032.0   65.0   240.0   256.0    overflow menu panel   (menu::PANEL_WIDTH = 240)
base 0/3/0   1012.0   65.0   260.0   160.0    switcher panel        (its own PANEL_WIDTH = 260)
```

Two panels anchored to the same edge with different widths, so their leading edges sit 20dp apart
and the rows inside them start at different x. Both restate `Anchor::TopEnd { top:
anatomy::app_bar::BOTTOM_EDGE, end: spacing::SM }` — the same expression written twice, which is the
shape FR-029a exists to forbid, surviving BUG-003 because BUG-003 fixed the *value* in both copies
rather than deleting one copy.

Motion, from the source: `MenuOverlay` wraps its panel in `super::fade(…, open, FADE, …)` and
`.animate_in()`; `ProjectSwitcherOverlay` returns `None` when closed. Opening the ⋮ menu fades in and
out; opening the switcher beside it appears and vanishes between frames. `tests/motion_tokens.rs`
and `overlay_transition_identity.rs` do not catch it because there is no requirement that two panels
of the same kind transition the same way.

## Artifact Traceability

### spec.md (018)

- **Affected requirements**: FR-027 (48dp minimum interactive target) — unmet by the switcher
  trigger; FR-029a (a position relative to a component is derived, never restated) — the anchor
  expression is still written twice; FR-029b (the menu *row* is one shared component) — closed the
  row and stopped there.
- **Gap identified**: FR-029b unified the row inside the panel. Nothing says the **panel** itself is
  one shared component, and nothing says a control that opens a menu is the shared **icon button**.
  A new requirement is needed on each — the panel one is the natural sibling of FR-029b, the trigger
  one is FR-001's boundary (a feature must not reassemble a shared component) applied to the app
  bar. The trigger requirement must admit **both** button shapes, an action being labelled or not
  according to what it has to say; what it must forbid is assembling either by hand.

### contracts/design-tokens.md (018)

- **Affected sections**: §7.1 (top app bar — the "Action target 48×48" row); §7.5 (menus — the panel
  width row and the "one row, built once" row added by BUG-003).
- **Impact**: §7.5 needs the panel width stated as one figure for every panel of the kind, and the
  "built once" entry extended from the row to the panel and the trigger.

### spec.md (008-background-project-switching)

- **Affected requirements**: FR-004 (a switcher control in the app bar adjacent to the menu button)
  — silent on what the control is built from, which is the gap: it neither asked for the label nor
  said which component carries it. FR-006 (the switcher must clearly indicate the active project) —
  carried by the panel's active marker; the trigger's label says the same thing without a click,
  which is why it stays.
- **Impact**: FR-004 gains the shared button it is, so a later reader cannot take "a switcher
  control" as licence to assemble one. No visible change: same glyph, same label, same position.

### spec.md (017-material-component-architecture)

- **Affected requirements**: FR-007 (a styled component MUST NOT re-implement a behaviour the lower
  layer provides) and FR-008 (all floating surfaces on one overlay primitive). The switcher does sit
  on `cdk::overlay`, so FR-008 holds at the mechanics layer; the duplication that remains is one
  layer up, between two *styled* components.

### tasks.md (018)

- **Affected tasks**: T098-T110 (BUG-003's unification) — completed correctly for the row, and the
  scope they were written to did not include the trigger or the panel.
- **False completions**: none.
- **Missing tasks** (landed as T131–T139): a failing anatomy/geometry test asserting both app-bar triggers measure 48×48
  and both panels measure the same width; the trigger rewritten onto `IconButton`; the panel
  rewritten onto `MenuOverlay`; `ProjectRow` deleted in favour of `MenuItem`; the fixture
  regenerated; showcase and docs updated.

## Root Cause Analysis

Feature 008 built the switcher when the library had no `IconButton` habit for the app bar and no
`MenuOverlay` to hang a list from — so it wrote both, correctly for its moment. Every later pass then
worked *inside* the shape it left: 017 pushed both onto one overlay primitive, 018 fixed §7.5's row
height, BUG-003 fixed the anchor value and shared the row. Each pass treated the fork as terrain
rather than as the defect, because every gate this feature has reads one component at a time and no
gate compares two components of the same kind — which is the same blind spot BUG-003 recorded and
did not close.

The cost is the ordinary cost of a fork: the shared component keeps improving (the 48dp target from
§7.3, the fade from `MenuOverlay`, the disabled treatment) and the copy silently does not receive any
of it.

## Recommended Fix

1. `/speckit.bugfix.patch` — add the panel-and-trigger requirement to 018 (FR-029c), extend §7.5's
   "built once" contract row, and record the trigger's label change in 008.
2. `/speckit.bugfix.verify` — confirm the artifacts agree.
3. Implement, behind a failing test first: `ProjectSwitcherTrigger` becomes the shared labelled
   button, `Button::text(active project, r).leading(Icon::OpenProject, ..)`;
   `ProjectSwitcherOverlay` becomes `MenuOverlay`; `ProjectRow` is deleted and callers build
   `MenuItem`s; `project_switcher.rs` goes with them. Regenerate `layout_snapshot.txt` — the diff is
   the proof: the trigger moves to §7.3's button height with an 18dp leading glyph, and the panel to
   the shared 240dp width.
