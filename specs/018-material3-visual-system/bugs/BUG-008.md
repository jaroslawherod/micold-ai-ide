# Bug Report: the sidebar's worktree and session context menus open at a fixed corner, not at the row they act on — so a right-click near the bottom of the list is answered at the top of the sidebar, over the header and somebody else's rows

**Type**: Spec gap (nothing states where a *row's* context menu opens), over implementation drift
from the one place that does state it (feature 015's US2, applied to the switcher only).

**Severity**: High — the menu offers `Delete` and `Remove`, and its position gives no evidence of
which worktree or session it will act on.

**Feature**: `018-material3-visual-system` (§7.5 menus, context menus, popovers; FR-029/FR-029a).
The offending constant, `SIDEBAR_MENU_ANCHOR`, was written by this feature's **T107**, and this
feature's own **[BUG-003](./BUG-003.md)** named it under "Adjacent risk, not this bug". The
behaviours it misplaces belong to [`008-worktree-sidebar-refinement`](../../008-worktree-sidebar-refinement/spec.md)
(FR-013, the worktree menu) and to the session menu beside it.

**Reported**: 2026-08-20

**Status**: Patched

**Patched**: 2026-08-20 — `spec.md` gained FR-029d, SC-008f and US4 acceptance scenario 14;
`contracts/design-tokens.md` §7.5 gained a **Panel anchor** row; `plan.md` gained the
"a panel that is individually correct and points at nothing" risk row; `tasks.md` gained Phase 20
(T142–T150). [Feature 015](../../015-switcher-forget-context-menu/spec.md)'s FR-005 records that its
rule was lifted to the kind. Nothing is reopened — T107 is complete as written.

**Branch**: `fix/context-menu-at-sidebar-shows-in-wrong-place`

## Description

Right-clicking a **session** row near the bottom of the Worktrees sidebar opens its `Close` /
`Remove` menu at the **top-left of the sidebar**, the full height of the list above the pointer, drawn over the
"Worktrees" header and the first two worktree rows. The reporter's screenshot shows exactly this:
the pointer was on the `Claude Code` session pill, second from the bottom of a long list; the panel
is at the top, adjacent to nothing.

The worktree menu does the same thing, from the same constant.

The menu is not *wrong* — it acts on the row that was right-clicked — but nothing on screen says so.
Its actions include `Delete` and `Remove`, and the user is asked to confirm a deletion whose only
statement of subject is a panel sitting over a different worktree's name.

### What the user sees

| | |
|---|---|
| Right-click a session row near the bottom of the sidebar | menu appears at `(24, 96)` |
| Right-click a *different* row | menu does not move |
| Scroll the list, then right-click | menu still at `(24, 96)` |
| Right-click a **project** row in the top-bar switcher | menu appears **at the pointer** (feature 015) |

The last row is the same gesture, in the same window, one panel over, behaving correctly — which is
what makes this read as broken rather than as a choice.

## Evidence

`crates/micold-client/src/ui/mod.rs:70-74`:

```rust
/// Where the sidebar's own context menus open: just inside the sidebar, below the app bar.
///
/// A fixed point rather than the cursor — these menus are opened from a row whose position the view
/// does not know — and the one place it is stated, rather than the two literals it was (T107).
const SIDEBAR_MENU_ANCHOR: (u16, u16) = (24, 96);
```

Both sidebar menus read it (`ui/mod.rs:314-341`), clamp it against the window, and hand it to
`MenuOverlay::anchor`. The project menu three lines above reads `menu.anchor` instead — the pointer
position captured at the right-click (`app.rs:1071`, `anchor: self.cursor`).

**"a row whose position the view does not know" is no longer true, and was never true of the
gesture.** The comment is a statement about the *message*, not about the widget:

- `ui/material/tree_view.rs:119` — `pub fn on_right_press(mut self, message: M) -> Self`. A message.
  The press point is available at that seam and is discarded.
- `ui/cdk/context_area.rs:58-64` — `on_secondary_press(impl Fn((u16, u16)) -> M)`, whose doc reads
  "`point` is in window coordinates — what an overlay anchor takes."
- `ui/terminal.rs:829-832` — the terminal tab strip already uses it:
  `Message::ShellInstanceMenuRequested(instance.id, x, y)`, and its menu follows the cursor.

So the sidebar is the only right-click surface in the application that throws the press point away,
and the primitive that keeps it was written for a neighbouring bug (`012` BUG-005) and never reached
back.

**Feature 024 made it worse.** The sidebar reveals the current session by scrolling to it, so a
row's y is now a function of scroll position as well as list length. A fixed anchor was already
adjacent to nothing; it is now adjacent to nothing *and* unstable.

## Artifact Traceability

### spec.md (018-material3-visual-system)

- **Affected requirement**: **FR-029** — menus and context menus "MUST match Material's menu
  anatomy". Anatomy here is read as surface, elevation, corner and density; **placement relative to
  the thing the menu belongs to is not stated**, and that omission is the gap. Material's own menu
  spec positions a context menu at the invocation point.
- **Adjacent requirement**: **FR-029a** — a panel positioned *relative to another component* must
  derive that offset from the component's anatomy, never restate it. `SIDEBAR_MENU_ANCHOR = (24, 96)`
  is a restated figure of exactly the prohibited kind — `24` is the sidebar's inset by eye, `96` is
  the app bar's 65dp bottom edge plus an unexplained 31 — but FR-029a as written only reaches
  panels that *hang from* another component, and this one claims to hang from nothing. It is the
  same class one step out: a position that names no owner cannot be checked against one.
- **§7.5 contract** (`contracts/design-tokens.md:596`) — "Panel width | 240 for a panel anchored
  below the app bar; **160 for a cursor-anchored context menu**". The contract already knows the
  kind exists and gives it a width; nothing gives it an anchor, and the sidebar's menus take
  neither.
- **Gap identified**: no requirement anywhere states that a context menu opened *from a row* must
  open at that row or at the pointer. The one place it is stated is feature 015, scoped to the
  switcher (below).

### 015-switcher-forget-context-menu/spec.md

This is the drift half, and the reason the fix is not a design question:

- **US2** — "The menu behaves like a normal desktop context menu… opens at the pointer, not in a
  fixed corner". Its rationale sentence is this bug verbatim: *"A context menu that appears far from
  the cursor, or that runs off the window, reads as broken."*
- **FR-005** — "The menu MUST be positioned at the pointer, with its top-left corner at the click
  point, and MUST re-position when a different row is right-clicked."
- **FR-006** — must remain fully within the window.
- **Scope**: every one of these says *project row in the top-bar switcher*. The rule was written for
  one surface and never lifted to the kind. The sidebar's two menus were shipped before it (008,
  and the session menu beside it) and were never brought under it.
- **FR-010** — "Pointer tracking… MUST NOT degrade idle performance when the switcher is closed."
  This is the constraint the fix must respect, and it is why `State::cursor` cannot simply be read
  here: `shell/subscriptions.rs:95-100` subscribes to pointer moves **only while the project
  switcher is open**, so at a sidebar right-click `state.cursor` holds a stale point or `(0, 0)`.

### 008-worktree-sidebar-refinement/spec.md

- **FR-013** — "Right-clicking a worktree MUST open a context menu offering Rename and Delete."
  Says what it offers, not where it opens. Satisfied by the current behaviour, which is why no gate
  saw this.

### plan.md / tasks.md (018)

- **T107** (`tasks.md:885`) is the direct antecedent, and it is worth quoting because it saw this
  code and left half of it:

  > Sweep for the same shape elsewhere: a constant that restates another component's dimension by
  > eye. … **the two context menus anchored at a literal `Point::new(24.0, 96.0)` with no clamping
  > at all** (`ui/mod.rs`) … Fix or record each, so FR-029a's class is closed rather than its one
  > instance.

  The task was scoped to *clamping* — will the panel stay on screen — and it closed that half
  correctly. It then promoted the literal to a named constant with a doc comment justifying it,
  which converted an unexamined accident into a documented decision without anyone deciding.

- **BUG-003's** own "Adjacent risk, not this bug" note (`bugs/BUG-003.md:177-180`) does the same:
  it records the literal anchor, and everything it says about it concerns the panel running off the
  bottom edge. Two artifacts looked straight at `(24, 96)` and both asked only whether the panel
  fits, never whether it points at anything.

- **No false completions.** T107 is genuinely done as specified. The missing work was never a task.

### Which gate should have caught it, and why none did

- `tests/switcher_forget_menu.rs` and `tests/features_project.rs` cover `clamp_menu_anchor`
  thoroughly — a pure function over (anchor, panel, window). Every case passes the *anchor in*.
  Nothing asserts where the anchor comes from.
- `ui/material/anatomy_size.rs` measures components in isolation; a panel's position relative to a
  row is not a property of either component.
- `019-layout-snapshot-parity`'s probes and `frame_probe` reason about the frame tree, and the menu
  *is* where the code says it should be.

This is BUG-003's closing lesson repeating: "every gate this feature built reads one component at a
time". A menu and the row it belongs to are two components, and their relationship is what is wrong.

## Root Cause Analysis

**A placement was chosen by the constraint of the widget that raised the event, and then written
down as an intention.**

`TreeItem::on_right_press` takes a message, not a point — the same shape `mouse_area::on_right_press`
has. With no point to anchor to, the original author picked a corner. That is a reasonable thing to
do under that constraint. What made it durable is the second step: T107 named the corner
`SIDEBAR_MENU_ANCHOR` and documented it as *"a fixed point rather than the cursor — these menus are
opened from a row whose position the view does not know"*, which reads as a design rationale and is
in fact a description of a missing parameter. `cdk::ContextArea` — which supplies exactly that
parameter, in window coordinates — was already in the tree, used by the terminal tab strip, for the
same reason (`012` BUG-005: "a menu that did not follow the cursor would leave the user guessing
which tab it belonged to"). Nobody connected the two, because the sidebar's menus were never
compared against a menu of the same kind.

Feature 015 then specified the correct behaviour, in full, with acceptance scenarios — for the
surface it happened to be about. A rule stated about one instance does not reach the kind, and
FR-029b/FR-029c are this feature's own record that unifying a part leaves the whole free to diverge.

## Recommended Fix

Sketch, not a decision — `/speckit.bugfix.patch` settles the requirement wording first.

1. **Lift feature 015's US2 to the kind.** A context menu opened from a *row* — switcher project,
   sidebar worktree, sidebar session, terminal tab — opens at the press point, clamped. State it in
   018's §7.5 alongside the width that already distinguishes "cursor-anchored context menu", so it
   is a property of the kind rather than of the three features that happen to have one.
2. **Carry the press point.** Give `tree_view::TreeItem::on_right_press` the `ContextArea` shape
   (`impl Fn((u16, u16)) -> M`) and let `WorktreeMenuToggled` / `SessionMenuToggled` carry `(x, y)`,
   as `ShellInstanceMenuRequested` already does. This resolves FR-010 without widening the pointer
   subscription: the point arrives with the event, so nothing has to be tracked while idle.
3. **Delete `SIDEBAR_MENU_ANCHOR`.** Keep `clamp_menu_anchor` — it is the FR-006 half and it is
   already right — and feed it the press point.
4. **Add the gate the three menus share**: right-click at *p* → panel origin is *p*, clamped; a
   second right-click on a different row moves it. Written once, over each menu, so the next
   right-click surface cannot ship a fourth answer.
