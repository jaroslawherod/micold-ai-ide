# Bug Report: a clicked button keeps a focus layer, and its hover or press layer is drawn on top — §5's "layers never sum" does not hold on screen

**Type**: Spec conflict, surfacing as implementation drift. Contract §5 says a control's states are
mutually exclusive, "so the heaviest **single** layer is the measurement and layers never sum", and
FR-004b's gate measures exactly that. Feature 027 (FR-030) later gave every `Button` a keyboard focus
through `TakesTheKeyboard`, which draws §5's focus layer *over* the child — and the child still draws
its own hover or pressed layer underneath. Two layers, summed. Neither feature is wrong on its own
terms; 018's contract was written when a button could not hold focus (FR-022, FR-043's fidelity gap
#2), and 027's wrapper was written against the opacity table without the sentence under it.

**Severity**: Medium. It is on every button in the application, in both schemes, and it is not
transient: a click leaves the focus layer and the `secondary` ring on the button until something else
is clicked, so the stacked state is the normal state of the last button used. By the gate's own
arithmetic it takes pairs that FR-004b proves below AA (table below) — including the filled button's
`on_primary` on `primary`, the most common label in the interface.

**Feature**: `018-material3-visual-system` (§5 state layers, FR-004b, FR-022, FR-043; SC-008h).
Cause in `027-sandboxed-daemon-runtime` FR-030 (`crates/micold-client/src/ui/material/keyboard_focus.rs`).

**Reported**: 2026-09-13

**Status**: Fixed

**Patched**: 2026-09-13

**Decision**: option 3, both. The focus layer tops the child's hover or pressed layer up to the heavier opacity instead of adding a full layer (FR-022a, §5), and a button draws its focus indicator only for focus that came by keyboard — a traversal or a key it answers; a pointer press still moves focus. The checkbox is unchanged: its style already composites the heavier layer and it draws no ring.

## Root Cause Analysis

The focus indicator was added from outside the control. `TakesTheKeyboard` documents why: a button's
style is resolved when the element is built, so it cannot be told it is focused without a flag at
every call site, and the wrapper draws the indicator itself instead. That is a sound reason, and it
has the consequence that the wrapper and the child each draw a layer from state the other cannot see.
iced's `button::Status` has no focused variant, so the child's `Hovered`/`Pressed` fill is chosen
with no knowledge that a focus layer is about to be laid over it.

Separately, focus is taken by **any** press ("a press takes the keyboard, and a press anywhere else
gives it up"), so the stacked state is reached by the mouse, not only by the keyboard traversal
FR-030 asked for. Material shows a focus indicator for keyboard focus; after a pointer press it does
not.

## Recommended Fix

**Decide the rule before touching the wrapper.** Candidates:

1. **Make the layers mutually exclusive again**: the focus layer replaces the child's hover/pressed
   layer rather than adding to it — the heaviest single one is drawn, as §5 already says. Closes the
   contrast gap with no palette change. Needs the child's status to be known where the focus layer is
   drawn (or the button's style to take a focused flag after all), which is the cost the wrapper's
   docs chose to avoid.
2. **Show focus only when it came from the keyboard** (focus-visible): a pointer press still moves
   focus, so Enter and Space keep working, but draws no layer and no ring. Material-faithful, and it
   removes the lingering tint on the last button clicked — but a keyboard user who tabs to a button
   and then hovers it still gets 17%, so on its own it narrows the bug rather than closing it.
3. **Both** — 1 for conformance, 2 for fidelity.

Then:

1. `/speckit.bugfix.patch` — amend §5 (what a focused control draws while hovered or pressed),
   FR-022 and FR-043 (the focusable set now includes buttons), and FR-004b's layer figure if option 1
   is not taken.
2. `/speckit.bugfix.verify`.
3. `/speckit.implement` — with a failing test first that measures a focused `Button`'s composite in
   both states, not a named pair.
