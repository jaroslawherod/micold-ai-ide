# Bug Report: a long snackbar message squeezes "Dismiss" to a sliver and its label spills past the snackbar's edge

**Type**: Implementation drift. §7.8 gives the snackbar a message, an action and a 600dp maximum width
(`anatomy::snackbar::MAX_WIDTH`, "so a long message wraps rather than spanning the window"); FR-032
makes it a self-contained surface.
The component wraps the message and hands the action whatever width the message did not take, which
past the cap is almost none.

**Severity**: Medium. Every notification long enough to reach 600dp is affected — any message carrying
a folder path does — and the one control that clears a notification before its timeout (FR-032b) is
drawn half outside its container, over whatever lies beside it.

**Feature**: `018-material3-visual-system` (§7.8; FR-032, FR-032b; `contracts/component-api.md` §2.2).

**Reported**: 2026-09-14

**Status**: Patched

**Patched**: 2026-09-14

## Description

Found by 002's BUG-004 visual pass
([`specs/002-project-workspace-management/evidence/bugs-002-003-004-visual-pass.md`](../../002-project-workspace-management/evidence/bugs-002-003-004-visual-pass.md),
"Finding, not fixed here"): the launch notification `Couldn't reopen "repo-gone": its folder … is
unavailable.` wraps to four lines at 600dp, and its `Dismiss` label runs past the snackbar's right
edge — [`bug004-launch-gone-last-active.png`](../../002-project-workspace-management/evidence/bug004-launch-gone-last-active.png)
shows `Dismis` straddling it.

**Reproduction** (on `origin/main` at `226d3a8b`):

1. Lay out `Snackbar::new(notification, roles).on_dismiss(msg)` headlessly for a message longer than
   one 568dp line (600dp less 16dp padding each side), in a 1200dp or 400dp window.
2. Read the action's node: the last child of the container's content row.
3. At a 1200dp window it is **18.95dp** wide where the same button laid out alone is **74.09dp**, and
   it starts at the row's trailing edge. The label is shaped at its natural width from that start, so
   it is drawn past the node and past the container's padded edge.

The test `ui::material::snackbar::tests::a_long_message_leaves_the_action_its_width_inside_the_container`
performs these steps and fails on `origin/main` with those two figures, at its first window; it stops
there, so the 400dp case is not separately logged (its line is narrower, so the remainder is no wider).
A one-word message is unaffected: the line has room for both.

## Root Cause Analysis

`crates/micold-client/src/ui/material/snackbar.rs` puts the message and the action in one `row!`
inside a `container(...).width(Length::Shrink).max_width(600)`. A `Shrink` container lays its content
out **compressed** (`iced_core::layout::Limits::width(Shrink)` sets `compression.width`), and iced's
flex layout (`iced_core::layout::flex::resolve`) treats a compressed main axis by laying every child
out **in declaration order** in its first pass, each against the width still `available`. The message
comes first. As a `Length::Fill` text under compression it takes its intrinsic width up to all of
what is left — for a message that wraps, the whole line — and the button, laid out next, is offered
the remainder: under 20dp. The button's node takes that width, its label is shaped at its natural
width regardless, and it is drawn from the node's origin outward, past the container.

Short messages never showed it because their intrinsic width leaves the button room. The width-cap
gate (`anatomy_size.rs`, `a_snackbar_clears_48dp_and_stays_within_600dp`) lays a long message out
without `on_dismiss`, and feature 019's text-overflow gate has no covered state with a notification.

## Recommended Fix

Lay the action out **first**, at its natural width, and give the message what remains beside it,
while keeping the snackbar sized by its content below the cap. `cdk::reflow::Reflow` (003 BUG-002)
already measures a trailing cluster before its lead for exactly this reason; it resolves to the full
width offered, so it needs to honour a content-sized (`Shrink`) parent — measure the lead at its
intrinsic width and resolve to lead + spacing + trail — for the snackbar to use it without becoming
600dp wide for a one-word message. The §7.8 48dp floor (the height-only spacer beside the message)
stays inside the leading block.
