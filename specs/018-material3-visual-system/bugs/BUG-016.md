# Bug Report: a clicked terminal-bar tab draws the focus ring while the terminal holds the keyboard

**Type**: Implementation drift. FR-022a draws a button's focus indicator only for focus that arrived
by keyboard — "a traversal, or a key the control answers". The shared keyboard wrapper treats a key
the focused terminal has already consumed as a key the button answers.

**Severity**: Medium. Every session shows it: click a tab in the terminal bar, type Space or Enter
into the terminal, and the tab lights up with the `secondary` ring and the focus layer beside the
terminal pane's own ring — two focus indicators, one of them on a control the keyboard is not on.
The same keystroke also re-sends the tab's press (a no-op for the tab already shown, so nothing else
visibly changes).

**Feature**: `018-material3-visual-system` (FR-022, FR-022a, SC-005).

**Reported**: 2026-09-17

**Status**: Fixed

**Patched**: 2026-09-17

## Description

User report: *"check the screen shot the UI is showning highlight for different kind of items. That
was not happening in the past and entered after one of recent changes"*. The screenshot (dark
scheme) shows the terminal pane's lavender focus ring along its bottom edge, and below it the pinned
AI tab (`claude`) wearing its top active indicator **and** a full lavender ring with a focus layer.

**Reproduction** (on `origin/main` at `5c371812`, 2026-09-17, Xvfb + lavapipe, `visual-pass` recipe):

1. Open a project, start a session. The terminal pane is focused and draws its ring (006 BUG-005).
2. Click the `+` in the terminal bar, then click the pinned `claude` tab. No ring on the tab — the
   pointer press took the wrapper's focus without showing it (FR-022a).
3. Press Space. The terminal receives it, and the `claude` tab now draws the focus ring and layer.

## Root Cause Analysis

`TakesTheKeyboard::update` (`crates/micold-client/src/ui/material/keyboard_focus.rs`) answers Enter
and Space whenever its own `Focus::focused` is set, and sets `visible = true` when it does. It never
asks whether the event was already captured. iced delivers every event to every child of a row or
column regardless of capture, and in the terminal view the pane is laid out **before** the bar
(`ui/terminal.rs`), so `TerminalPane::update` writes the key to the process and captures it, and the
tab's wrapper — still holding the focus a click gave it, because the click on the tab moved the
application's keyboard to the terminal without any press landing on another wrapper — answers it a
second time.

`Stack` and the overlays deliver top-first and stop at the first capture, so a dialog or menu over the
terminal is not affected; only siblings inside a row or column see a key another has taken.

**A capture check alone depends on tree order.** It helps only a button laid out *after* the widget
that took the key. A focused button laid out *before* the terminal pane — the sidebar is
`row![left, main]` — would still take Enter or Space first. The first review declined to widen the fix
because neither sidebar path it named reproduced on the rendered frame. The user then asked for the
order-independent half in the same PR: see Recommended Fix, part 2.

History, from `git log`:

- `079e562d` (027, 2026-08-26) wrapped every shared `Button` in `TakesTheKeyboard`: the double
  handling of Enter/Space has been possible since then.
- `3ac8cb82` (018 BUG-013, 2026-09-14) made a key the button answers the thing that shows the ring.
- `5b582301` (006 BUG-005, 2026-09-13) gave the focused terminal its own ring, so the tab's ring now
  appears beside a second indicator — the "different kind of items" highlighted at once.

## Recommended Fix

In `TakesTheKeyboard::update`, answer a key only when no earlier widget has captured it
(`shell.is_event_captured()`): a key someone else consumed is not a key this control answers. The
indicator then stays hidden and the tab's press is not re-sent. A clicked button that nothing else
takes the key from still answers Enter and Space (BUG-013's rule is unchanged).

Part 2, independent of order: wrap the window's content in `cdk::keyboard_elsewhere::KeyboardElsewhere`,
told `State::terminal_focused()`. While the terminal holds the keyboard it runs iced's `unfocus`
operation over the whole tree before any child sees a key press, and on the first event after the
terminal takes the keyboard. No button anywhere keeps focus, so none answers the terminal's keys or
draws a ring beside the terminal's.
