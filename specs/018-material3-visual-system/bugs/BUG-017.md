# Bug Report: the snackbar's message starts 32dp in from its left edge, not §7.8's 16dp

**Type**: Implementation drift. §7.8 pads the snackbar "16 horizontal, 14 vertical"
(`anatomy::snackbar::PADDING_H`), and FR-032 gives it "the snackbar's … padding". The component
applies that padding and then adds the same 16dp again before the message.

**Severity**: Low. Nothing is clipped or unusable, but every snackbar the application raises is
lopsided: its message sits twice as far from the leading edge as the container's padding says, and
twice as far as its trailing text sits from the trailing edge when there is no action. The inset also
takes 16dp of the 600dp cap away from the message, so a long message wraps sooner than it should.

**Feature**: `018-material3-visual-system` (§7.8; FR-032; `contracts/component-api.md` §2.2).

**Reported**: 2026-09-14

**Status**: Patched

**Patched**: 2026-09-14

## Description

Noticed while fixing BUG-015 and recorded under that ledger's *Follow-ups not done*
([`BUG-015.autopilot.md`](BUG-015.autopilot.md)): the zero-width 48dp spacer is one of the message
row's children, so the row's spacing also lands before the message.

**Reproduction** (on `origin/main` at `fadb8e9f`):

1. Lay out `Snackbar::new(notification, roles)` headlessly, with and without `.on_dismiss(msg)`, for
   a one-word message and for a message long enough to wrap, in a 1200dp or 400dp window.
2. Read the message's text node: the last child of the row that holds it (the container's content
   without an action; the leading child of the content with one). Add the offsets of its parents.
3. The message starts **32dp** from the container's left edge. §7.8's horizontal padding is 16dp.

The test `ui::material::snackbar::tests::the_message_starts_at_the_containers_horizontal_padding`
performs these steps and fails on `origin/main` with "the message (7 chars, dismissible: true, 1200dp
window) starts 32dp from the container's left edge; §7.8's horizontal padding is 16dp", at its first
case. It stops there; the other four cases share the row, so they are no different.

**Rendered** (same commit, `micold-showcase` on Xvfb with lavapipe, light scheme): in the showcase's
Snackbar section, a column scan of each pose finds the first text pixel **33px** inside the container's
left edge in all three poses (32dp and the glyph's side bearing), and the last text pixel of the
no-action pose **16px** inside its right edge. The two sides of one surface disagree by exactly 16dp.

## Root Cause Analysis

`crates/micold-client/src/ui/material/snackbar.rs` builds the message as

```rust
row![
    Space::new().height(anatomy::snackbar::MIN_HEIGHT),
    Text::new(message, TypeRole::Body, r).width(Length::Fill),
]
.align_y(Alignment::Center)
.spacing(anatomy::snackbar::PADDING_H)
```

The spacer carries §7.8's 48dp floor. It has no content and a `Shrink` width, so it lays out **0dp
wide** — but it is still a child of the row, and iced's flex layout puts `spacing` between every pair
of adjacent children whatever their width. The 16dp `spacing` therefore lands between the invisible
spacer and the text, and the container's own 16dp `padding` sits outside the row: 16 + 0 + 16 = 32dp.

The `spacing` was not pointless when T052 wrote it: the row then held the action as its third child,
and the spacing was the gap between the message and `Dismiss`. The same gap also went in front of the
message, between the spacer and the text, from the start. BUG-015 moved the action out of the row and into `Reflow`, which has its own
`spacing(PADDING_H)` for that gap, so the row's `spacing` now separates only the spacer from the text —
it does nothing except this defect.

Every gate stayed green because none reads a child's position inside the snackbar: the anatomy gate
bounds the outer box, and BUG-015's tests read the action's width and trailing edge.

## Recommended Fix

Drop the message row's `spacing`. The row holds only the height-only spacer and the text, so the gap
it adds has no other job, and the message–action gap stays where BUG-015 put it, on `Reflow`. Keep the
spacer, and keep its width `Shrink` (its comment explains why a `Fixed(0)` width would delete it). Keep
BUG-015's behaviour: `Dismiss` whole at its natural width inside the padded edge, and the message
wrapping beside it.
