# Bug Report: Every documented layout-snapshot command omitted `--test`, so none of them ran anything

**Type**: Implementation drift (primary) + Untested flow (why it survived)
**Severity**: High — the feature's own acceptance procedure did not execute, and its one deliberate
escape hatch reported success while doing nothing
**Feature**: 019-layout-snapshot-parity
**Reported**: 2026-08-16 (retroactively — the fix is already on `main`, see "Status")
**Found**: while accepting an intended fixture change for `012-multiple-regular-terminals` BUG-001
(PR #174), where the printed hint returned success and regenerated nothing
**Status**: Patched
**Patched**: 2026-08-16 — FR-013 and SC-005 annotated, FR-013a and SC-007a added to `spec.md`;
`contracts/layout-fixture.md` §6 gains the `--test` rule and the judge-by-the-fixture rule;
`tasks.md` Phase 9 added (T045–T049, all closed — T045–T048 in PR #176, T049 run 2026-08-16); the
two suspect quickstart sections re-run and confirmed in place. `plan.md` carries a note recording
that it needed no change and why.

## Status

Unusually, this report is written **after** the fix. The defect was found mid-task, fixed directly,
and merged as PR #176 (`fix(019)` + `style(019)`) before any bug report existed. The report is filed
now because the workflow's value is the traceability, and that is lost whether the fix precedes it
or not. Nothing below is hypothetical: every claim was observed on the pre-fix tree, and the
"Recommended fix" section records what was actually done rather than what should be.

## Description

Every documented invocation of this feature's gate was missing `--test`:

```sh
cargo test -p micold-client layout_snapshot           # as documented, 11 places
cargo test -p micold-client --test layout_snapshot    # what actually selects the target
```

Cargo reads the bare trailing word as a **test-name filter**, not a target selector. No test in
`layout_snapshot.rs` is named `layout_snapshot` — they are
`the_layout_matches_the_committed_fixture`, `the_other_scheme_lays_out_identically`, and the
`containment::*` set. So the filter matched nothing, every test binary in the crate reported
`0 passed; N filtered out`, and the command **exited 0**.

Read the exit code and it worked. Read the fixture and nothing had happened.

Two classes of site, and the second is worse:

1. **The regeneration hints** — the failure message, the fixture's own `# regenerate:` header line,
   `layout_snapshot.rs`'s module doc, `contracts/layout-fixture.md` (×3), and
   `docs/development/layout-snapshot.md`. Following one after a real layout change accepts no
   baseline, prints success, and leaves the next run failing with the same instruction. An advice
   loop that terminates only when someone doubts the instruction.
2. **The quickstart's *run the gate* commands** — Part A's headless check, Part B1's
   deliberate-failure check, and Part B's negative case proving a failing run leaves the fixture
   unmodified. These do not regenerate anything; they exist to *exercise* the gate, and they
   exercised nothing while reporting ok. Part A's `env -u DISPLAY -u WAYLAND_DISPLAY … # must still
   pass` passed vacuously — the strongest claim in the section, evidenced by a command that ran no
   test at all.

11 occurrences across 5 files.

## Artifact Traceability

### spec.md

- **Affected user story**: Story 2 — accepting an intended layout change (the regeneration half).
  Story 1's *verification procedure* is affected too, though not its implementation.
- **Affected requirements**:
  - **FR-013** — "The system MUST provide a **single documented command** that regenerates the
    fixture deliberately, and MUST NOT regenerate it as a side effect of a normal run." The second
    clause held perfectly. The first did not: the command *documented* did not regenerate. The
    mechanism behind it was correct the whole time, which is exactly why this went unnoticed — the
    requirement was satisfiable, and satisfied, by an invocation nobody had written down.
  - **SC-005** — "Accepting an intended layout change takes **one documented command**, and the
    resulting diff is understandable by a reviewer who has not run the application." The diff half
    is fine. The one-documented-command half was not met.
- **Gap identified**: none in the requirements themselves. FR-013 says what it should; a faithful
  reading already forbids documenting a command that does not work. What the spec never asked for
  is *evidence* that the documented string executes — see "Root cause".

### plan.md

- **Affected sections**: none materially. The plan concerns how layout is resolved headlessly, what
  is recorded, and the write-gate's design — all of which were implemented correctly. The defect
  lives entirely in the strings that tell a human how to invoke the result.
- **Impact**: no plan change. Recording that explicitly matters here, because "the plan was right
  and the code was right and the thing still did not work" is the shape of this bug.

### tasks.md

- **Affected tasks**:
  - **T027** (`[x]`) — put regeneration behind `UPDATE_LAYOUT_SNAPSHOT=1`, mirroring 017's
    `UPDATE_STYLE_SNAPSHOT` (FR-013, contract §6). Its recorded evidence — "The fixture updates and
    the check passes. Yes. `UPDATE_LAYOUT_SNAPSHOT=1` regenerated; a re-run was green" — is about
    the **variable**, and is true. The task is not a false completion; its subject worked. What it
    did not cover is the *invocation* printed alongside the variable.
  - **T026** (`[x]`) — five tests over the write decision, including
    `only_the_documented_variable_triggers_regeneration`, which reads the gate's own source
    precisely because "the behavioural tests pass the flag in directly and therefore cannot see the
    trigger widening". That reasoning is correct and it is the reasoning this bug needed applied one
    step further: the behavioural tests also pass the *target* in directly, and therefore could not
    see the printed command being unrunnable. The task stopped at the variable.
  - **T024** (`[x]`) — generated the committed fixture, and with it the wrong `# regenerate:` header
    line that has been copied into the file ever since.
- **False completions**: none among the tasks. Two **recorded quickstart passes** were suspect,
  which is a different thing — flagged rather than corrected, then settled by T049 (see
  "Follow-up"). Both stand:
  - **Part C** — `[x] The fixture updates and the check passes.` The command as written updates
    nothing.
  - **Part B1** — `[x] The check **fails**.` A filter matching nothing cannot fail; it reports ok.
    Either these were run with a different invocation than the one recorded, or the records are
    inaccurate. Both are left as recorded. Rewriting someone else's evidence to fit a later finding
    is not a fix, and which of the two it is can only be answered by whoever ran them.
- **Missing tasks**: one, and it is the durable half — an assertion that every printed regeneration
  command actually selects this target. Text alone decays; this text did.

### contracts/layout-fixture.md

- **Affected sections**: the fixture grammar (the `# regenerate:` header line is specified
  literally), the worked example, and §6 "Regeneration".
- **Impact**: all three carried the broken command, so the contract specified the wrong string as
  the fixture's own content — which is how it reached every regenerated fixture.

## Root Cause Analysis

Not a spec oversight and not a coding error. The requirement was right, the mechanism behind it was
right, and the tests that exist for it are unusually thorough — T026 deliberately reads the gate's
source rather than trusting behaviour, precisely because it understood that a test passing the flag
in directly is blind to how the flag is really obtained.

The defect is that the same insight stopped one step short. `UPDATE_LAYOUT_SNAPSHOT` is half the
documented command; the `cargo test …` invocation is the other half, and nothing read it. A string
printed to a human sat outside everything that verified this feature, in a feature whose entire
subject is that unverified claims decay. `layout_snapshot_regeneration.rs` exists to stop the gate
rewriting its baseline and *reporting success*; this bug is that file's mirror image — telling the
user to rewrite the baseline in a way that reports success without doing it. Both failure modes are
silent by construction, and both end with a fixture nobody agreed to.

Why it survived so long: the failure is invisible unless you check the *effect* rather than the exit
code. `cargo test` printing `0 passed; N filtered out` and returning 0 looks like a clean run at a
glance, and the natural next step after regenerating — re-running the check — also does nothing and
also passes. Two green runs in a row, no fixture change, no reason to look.

## Recommended Fix

Already applied on `main` (PR #176). Recorded here as what was done:

1. **All 11 occurrences given `--test`**, in both the code that prints them
   (`tests/support/layout.rs`, `tests/layout_snapshot.rs`) and the artifacts that document them
   (`contracts/layout-fixture.md`, `quickstart.md`, `docs/development/layout-snapshot.md`).
2. **The failure message now explains the trap**, so a reader who mistypes it understands why the
   run said nothing.
3. **`the_regenerate_hint_selects_this_target`** added to `layout_snapshot_regeneration.rs`: reads
   every printed `UPDATE_LAYOUT_SNAPSHOT=1 cargo test` line in both sources and fails if it lacks
   `--test`. This is the part that keeps the fix from decaying, and it belongs in that file rather
   than a new one — it is the same class the file was written for.
4. **Fixture regenerated**; its only change is the header line. **No geometry moved**, which is the
   mechanical evidence that this was a tooling defect and not a layout one.

Verified: `--test layout_snapshot` → 23 passed and the fixture written (it now does something);
re-run without the variable → 23 passed; `layout_snapshot_regeneration` → 6 passed including the new
gate. CI green on Linux, macOS and Windows.

## Follow-up — closed 2026-08-16 (T049)

The two suspect quickstart checkboxes (Part B1, Part C) were recorded as passed against commands that
could not have produced the recorded observation. Both have now been re-run with the corrected
commands, and **both stand**:

- **B1** — bumping a covered component's padding by 8 made the gate fail (rc 101), name the covered
  state, and print recorded-vs-observed geometry for the moved elements. Every behaviour the marks
  assert reproduces. The specific values differ because the step says "pick any covered component"
  and the re-run picked a different one; that is the step working as written, not a discrepancy.
- **C** — regenerating with an intended change in place produced a fixture that **actually changed**,
  and the re-run passed. That the fixture moved is the only evidence worth having here, since the
  broken and the correct command both exit 0.

So the original marks were accurate observations recorded against a mistyped command. This stays a
documentation defect and does **not** become a coverage finding — which was the open question, and
was worth asking rather than assuming the gentler answer. SC-007a is thereby demonstrated.
