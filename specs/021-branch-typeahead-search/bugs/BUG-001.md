# Bug Report: The gallery's type-ahead is pinned open, so it demonstrates a state the picker never rests in

**Type**: Spec gap (with implementation drift as a consequence)
**Severity**: Medium
**Feature**: 021-branch-typeahead-search (`feat/make-select-match-angular-design-3` at time of report)
**Reported**: 2026-08-07
**Status**: Patched
**Patched**: 2026-08-07 — spec artifacts updated (FR-020a, User Story 3 scenario 5, SC-007a, plan
slice 3 + a new risk row, contract §6 C6.4, data-model §4's `typeahead_open` field and two message
variants, T053 reopened, T072–T076 added).

## Description

The component gallery's `Typeahead` entry hands the component `.open(true)` unconditionally
(`crates/micold-client/src/showcase/sections/controls.rs`), with the reason recorded inline: *"Always
open, because the list is the half worth looking at and this page exists to be looked at. In the
application the caller opens it on focus instead."*

The consequence is that the gallery shows the control in a state the real branch picker is never in
at rest, and never shows the transition that gets it there:

- the entry's **resting** appearance — a closed search field, which is what a developer opening the
  add-worktree dialog actually sees first — is not on the page at all;
- the **open-on-reach** behaviour FR-001b requires is not demonstrated, and neither is closing on a
  pick or on a press outside;
- a developer reading the page to learn what the component does concludes its list is always
  showing, which is the opposite of the rule the picker follows.

The gallery elsewhere holds itself to exactly the standard this violates. `showcase/state.rs`
justifies running the sample rows through the real ranking logic on the grounds that *"a gallery
example matching by its own rules would demonstrate something the application does not do (FR-020)"*,
and `showcase/state.rs` keeps the selection by label rather than by index because *"a gallery that
demonstrated the other behaviour would be demonstrating something the application does not do."* The
open state is the one place that principle was not applied.

**Expected**: the gallery's example is closed at rest, opens when its field is reached, and closes
when a row is picked or the list is dismissed — the same rule `app.rs` applies to the branch picker
(`AddWorktreeBranchFocused` → open, `AddWorktreeBranchQueryChanged` → open,
`AddWorktreeBranchSelected` → close, `AddWorktreeBranchDismissed` → close).

**Actual**: the list is open on launch and cannot be closed.

## Artifact Traceability

### spec.md

- **Affected user story**: User Story 3 — *A reusable type-ahead the rest of the app can adopt*
  (Priority: P3). Its acceptance scenario **4** — *"Given the branch selector's search, When its
  behavior is compared to the gallery entry's, Then they are the same component rather than two
  implementations that happen to look alike"* — is the one the defect undercuts. They are the same
  component, but the gallery drives it into a configuration the picker never uses, so a
  side-by-side comparison shows two different behaviours.
- **Affected requirements**:
  - **FR-020** — *"The component MUST be catalogued in the component gallery with a live, typeable
    example, rendered correctly in both light and dark appearance."* This is the **gap**. The
    requirement asks for *typeable*, and the entry is typeable; it says nothing about the example
    demonstrating the control's resting state or its open/close behaviour, so `.open(true)`
    satisfies the requirement's letter while defeating its purpose.
  - **FR-001b** — *"The list MUST open when the search field takes focus … and MUST close when a
    branch is picked, when the developer dismisses it, or when the field loses focus."* Satisfied by
    the branch picker; not exercised anywhere in the gallery, so nothing on the reference page shows
    that the component supports it.
- **Gap identified**: FR-020 under-specifies what "live" has to cover. It should require the gallery
  entry to exercise the component's **own open/close rule** — the same one FR-001b states — rather
  than any state the entry finds convenient to stage. Stated generally: a live entry must not pin a
  state the application does not rest in.
- **Not affected**: User Story 3's scenarios 1–3 (the entry exists, it narrows and marks matches as
  the developer types, it is legible in both schemes) all hold today and continue to hold after the
  fix. SC-007 ("the type-ahead exists once in the codebase") is untouched — this is one component,
  driven two ways.

## Root Cause Analysis

**A spec oversight that an implementation decision then filled in.**

FR-020 asks for a "live, typeable example" and stops there. When T029 built the entry it was
explicitly a static pose, and pinning the list open was the right call for a pose — the list is the
part of a type-ahead worth looking at, and a closed field on a static page shows nothing. T053 then
made the rows live without revisiting the pose, because nothing in the task, the requirement, or the
gates said the *open state* was part of what "live" covers. `tests/showcase_captions.rs` enforces
that a caption names the states exercised live, but it cannot notice a state that is staged and
undescribed rather than described wrongly.

So this is not an implementation error against a clear requirement. It is a requirement that did not
say enough, and a reasonable reading of it that has since been outgrown: once the entry became
interactive, "always open" stopped being a pose and became a demonstration of the wrong rule.

**Why it matters now.** Feature 022 (`specs/022-dedicated-select-component`) puts the select and the
search picker on a shared foundation and makes the gallery the surface where the two are compared
(its SC-001 and SC-010). A comparison page on which one picker is permanently open and the other
opens on demand cannot serve that purpose, and a select built to match a reference that shows the
wrong resting state would inherit the error. Fixing this before 022's planning is cheap; after it,
it is a correction in two places.
