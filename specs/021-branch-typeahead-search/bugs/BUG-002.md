# Bug Report: the search field's leading icon is drawn on top of its own text

**Type**: Implementation drift
**Severity**: Medium
**Feature**: 021 — branch type-ahead search
**Reported**: 2026-08-08
**Status**: **Fixed** (2026-08-19)

![The magnifier drawn over the B of Branch, at 7x](evidence/bug-002-icon-over-label.png)

## Description

`Typeahead`'s leading search affordance and the field's own text occupy the same pixels.

**Certain** — the resting label. With nothing typed, `FormField` rests the label where the value will
go, and the magnifier is drawn over its first character. "Branch" renders as a smudge and then
"ranch". The evidence image above is that state at 7×; it is unmistakable magnified and easy to miss
at 1×, which is why it survived this long.

**Probable, and to be confirmed while fixing** — the placeholder. Once the field is focused the
label floats and `text_input` draws "Search branches…" instead; in the capture the magnifier appears
to touch the "S". That one is the rendering stack's own inset rather than this application's, so it
is a different mechanism and may be a different bug, or none.

The `Select` shares `FormField` and the same picker base and is **unaffected** — its "Theme" label is
clean. The difference is exactly the leading icon: the select has none.

- **Gap identified**: none in the wording. FR-011a asks for both the label and the leading affordance

- **Impact**: the contract should state that the label's inset is a function of the leading slot —

- **False completions**: none. No task claimed this and then failed to do it.
- **Missing tasks**: a gate that can see it, and the fix. See "Root cause" — the fix is small and the

## Root Cause Analysis

Two siblings, each individually correct, composed without either knowing about the other.

- The **leading icon** is handed to the rendering stack's `text_input` via `.icon(...)`
  (`text_field.rs:145`), so it is drawn *inside the input's own bounds*, and the input insets its own
  text past it.
- The **resting label** is drawn by `FormField`, which positions it at the container's padding.
  `FormField` has no leading-adornment slot and no knowledge that anything is sitting there —
  `TextField` never tells it.

So the label is placed correctly with respect to the container, the icon is placed correctly with
respect to the input, and they overlap. Neither component is wrong on its own terms.

**Why every gate is green on it, which is the more interesting half.** `layout_snapshot`,
`containment`, `anatomy_size` and `content_placement` all read the layout tree, and in the layout
tree each node is exactly where its own layout says it is. A collision between two siblings is not a
containment failure (neither escapes its parent), not a size failure (both are their stated size) and
not a placement failure (each is where its own rule puts it). The suite is *structurally* blind to
overlap, and adding another geometry gate will not help.

What found it was reading the rendered pixels — the `visual-pass` skill, on its first run.

## Recommended Fix

1. `/speckit-bugfix-patch` — add the requirement that a field with a leading affordance insets its
   resting label past it, in spec.md and in `contracts/typeahead-component.md` §1.
2. `/speckit-bugfix-verify`.
3. Implement. Two candidate shapes, and the choice is the interesting decision:
   - **Give `FormField` a leading slot**, as it already has a trailing one, and move the icon into
     it. Symmetric, makes the label's inset derivable, and any future field with a leading
     affordance gets it right for free. Larger change.
   - **Inset the resting label in `TextField`** when `leading_icon` is set. Smaller, local, and
     leaves the two components still ignorant of each other — the same arrangement that produced
     this.
4. Add a check that reads **drawn pixels** rather than the layout tree, in the style of
   `select_anatomy`'s indicator test (which already rasterises). Confirm the placeholder case at the
   same time.

## What was built (2026-08-19)

All four, in the order they are written. The first candidate shape was taken — the one this report
called larger and better.

**1. The requirement.** Added as **FR-011e** and as **C4.1b** in `contracts/typeahead-component.md`
§4: the label and the value start on **one** column, in *both* of the label's positions, and that
column accounts for the leading slot. The shared anatomy went into
`018-material3-visual-system/contracts/design-tokens.md` §7.7, which gained the four adornment rows
it did not have — leading slot, gap, content column, adornment baseline — because the defect is in
the field, not in this picker's use of it. §7.7 having no such row *is* the defect: two components
resolving the same figure by eye is the shape every bug in that section has had.

**3. The implementation.** `FormField` already had a leading slot; nothing used it, and — the part
this report could not see from outside — `FilledField` did not inset the **label** past it either,
so moving the icon there alone would have reproduced the bug with an extra hop. Both were fixed
together: the icon moved into the slot, and `FilledField` now computes one content column that the
control and the label share. The slot is a **fixed** 24dp rather than the glyph's advance, following
§7.2's rule and BUG-006's lesson — a column that follows the advance lands somewhere different for
every icon.

This report's diagnosis was right in every respect that mattered and wrong in one detail: it says
`FormField` has no leading-adornment slot. It had one, unused. The conclusion held anyway, because
the slot existing is not the same as the label knowing about it.

Landed as 016 BUG-003 item 1 — the same defect, found independently by a later quickstart pass that
did not know this report existed. See
`specs/016-existing-branch-worktree/bugs/BUG-003.md` and its visual pass, which carries the
before/after at magnification.

**4. The gate that reads drawn pixels.** `adding_a_label_changes_nothing_where_the_leading_icon_is_drawn`
in `ui/material/text_field_anatomy.rs`, rasterising through `test_support`'s CPU renderer as
`select_anatomy`'s indicator test does. Run against the old geometry and seen to report **15 of the
icon's own pixels painted over**.

Phrased as *adding the label changes nothing where the icon is* rather than as *do the two ink masks
intersect*, because the two parts cannot be posed apart: a field without a leading icon does not
indent its label, so a label rendered alone sits where it never sits in the field under test.
Isolating it by subtraction would have made the answer true by construction — the first version of
this test did exactly that and had to be thrown away. Comparing a field against the same field with
one part removed keeps the geometry fixed and asks the question the eye asks. Both quantities are
asserted non-vacuous first, so a broken rasteriser or a missing font cannot make it green.

**The placeholder case — confirmed, and it is none.** This report called it *probable, to be
confirmed while fixing*. It is not a defect:
`adding_a_placeholder_changes_nothing_where_the_leading_icon_is_drawn` passes against the **old**
geometry as well as the new, so the "S" of "Search branches…" only appeared to touch the magnifier
in the capture. That inset is the rendering stack's own, exactly as this report suspected — a
different mechanism, and this one was already right.

**2. `/speckit-bugfix-verify`** was not run as a command; the requirement, the contract row, the
implementation and the gate are each recorded above, and the workspace is green.
