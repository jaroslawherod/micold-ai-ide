# Bug Report: the frame-budget test measures a debug build against the release budget, so it has no headroom and fails under load

**Type**: Test defect (the measurement and the number it is checked against are not the same build)
**Severity**: Medium — no user impact; an intermittent red build on a shared or loaded machine, and
it will keep costing re-runs. It also means SC-002 is currently **unmeasured** for the build users
actually run.
**Feature**: 021 — branch type-ahead search
**Reported**: 2026-08-16
**Status**: Open — diagnosed, not fixed. Found while verifying an unrelated change
(`fix/env-include-windows-flake`), whose diff touches only `micold-core`'s env-include tests.

## Description

`crates/micold-core/tests/typeahead_budget.rs::ranking_with_all_three_tiers_active_fits_in_a_frame`
fails intermittently:

```
ranking 500 branches with all three tiers active took 16.37ms, over the 16ms frame budget
 — this is the worst case the budget has to cover
```

**The same commit passed and then failed with no code change between the two runs.** It passed in
one full-workspace run and failed in the next, minutes later, on this machine — the only difference
being load average, which was above 8 at the time of the failure while several git worktrees were
compiling into the shared target directory.

## The mechanism

Two independent problems compound, and only the second is obvious.

**1. The measurement and the budget are from different builds.** The budget is a *product* promise:
contract `match-ranking.md` §5 and SC-002 both say ranking completes in ≤16 ms so that typing feels
immediate, which is a claim about the release binary a user runs. The test measures a **debug**
build and checks it against that same 16 ms.

The file argues this deliberately, and the argument is sound as far as it goes:

> *"Measured in a debug build, which is the pessimistic case: the release build every user runs is
> several times faster, so a debug pass is a real pass."*

A debug pass **is** a sufficient condition for the release claim. But it makes the test's margin
equal to `16 ms − debug_time`, which nobody has ever stated or measured — and the failure says it is
now approximately **zero**. At 16.37 ms the debug build is not "several times" inside the budget; it
is fractionally outside it. The test is sitting exactly on its own threshold, which is the one place
a wall-clock assertion cannot sit.

**2. It is a wall-clock assertion on a contended machine.** A single timed pass, no repetition, no
minimum-of-N. Any scheduling excursion is measured as if it were the cost of the algorithm. This
repository shares one `target-shared/` directory across every worktree precisely so that builds
serialise (CLAUDE.md), which means a developer running the suite is *routinely* doing so while
another worktree compiles.

Note the shape is the same one recorded in
`specs/011-env-include-script/bugs/BUG-004.md`: a timing assertion whose margin is fine in
isolation and evaporates under contention. That one is on Windows CI, this one on the dev machine.
Two instances is a pattern worth naming.

**Which of the two matters more is not yet known**, and the report should not pretend otherwise. If
the debug build genuinely costs ~16 ms, problem 1 dominates and load is only the trigger. If it
normally costs 4 ms and one excursion reached 16.37 ms, problem 2 dominates. **Measuring the
uncontended debug time is the first step of any fix**, and it has not been done — the test prints a
duration only when it fails, so the passing runs left no number behind.

## Reproduction

Not deterministic. Observed on this machine, same commit, minutes apart:

| Run | Load average | `ranking_with_all_three_tiers_active_fits_in_a_frame` |
|---|---|---|
| 1 | ~6 | pass |
| 2 | ~8 | **fail at 16.37 ms** |

The other three budget tests in the file passed in both runs, which is consistent with this one
being the worst case by design: it is the only query that reaches all three matching tiers on every
candidate, so it has the least headroom to lose.

## Impact

- **Intermittent red builds**, costing re-runs on a suite that is otherwise reliable.
- **SC-002 is not actually held for the release build.** The test as written can only ever say the
  debug build is fast enough. That is a sufficient condition while it passes with room to spare, and
  it currently passes with none — so the success criterion is being carried by a measurement that is
  about to stop being able to carry it.
- The failure message is good and did its job: it names the measurement, the budget and why this
  case is the worst one. Nothing here is a documentation problem.

## Recommended fix

Not applied — this is a diagnosis, and the ordering matters because step 1 decides the rest.

1. **Measure the uncontended debug time first**, on an idle machine, several runs. That number
   decides whether this is a headroom problem or purely a load problem. Everything below is
   contingent on it.
2. **Take the minimum of N runs rather than a single pass.** The fastest observed run is the best
   available estimate of the uncontended cost, which is what a budget check actually wants to know;
   a single sample measures cost *plus* whatever the scheduler did. This addresses load sensitivity
   without weakening the claim at all — the minimum is never optimistic about the algorithm.
3. **Separate the debug measurement from the release budget.** Either measure in release for the
   SC-002 claim, or keep the debug measurement and check it against an explicit debug budget derived
   from a measured debug/release ratio, with that ratio written down. What must not survive is a
   number that is the product budget by coincidence of being the only number anyone had.
4. If the debug cost is genuinely near 16 ms, that is a **finding about `rank`**, not about the
   test, and it should be recorded as such rather than absorbed by raising a threshold.

**Do not simply raise `BUDGET_MS`.** It is the contract's number — `match-ranking.md` §5 and SC-002
both state 16 ms — so changing it silently rewrites a success criterion to fit a measurement. The
same argument `specs/011-env-include-script/bugs/BUG-003.md` makes about test budgets applies here:
widening is what hides this class of defect.

## Note on how this was found

While running the full workspace suite to verify an unrelated env-include change. The two failures
in that verification pass were both environmental and neither was caused by the change under test —
the other was a test binary deleted mid-run by a concurrent build in the shared target directory,
which is its own hazard and is a consequence of bypassing `scripts/build-lock.sh` with a bare
`cargo`. Recorded here because the pattern is worth seeing: on a machine that deliberately serialises
builds through one target directory, wall-clock assertions and file-path assumptions both get
noisier than their authors expected.
