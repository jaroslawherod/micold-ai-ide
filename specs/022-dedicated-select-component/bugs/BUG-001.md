# Bug Report: the select's list re-runs its entrance and blinks

**Type**: Implementation drift
**Severity**: High
**Feature**: 022 — dedicated select component
**Reported**: 2026-08-08
**Status**: Open — **reproduced and instrumented**. Mechanism identified: the list's transition state is *recreated*, not retargeted. The trigger for the recreation is still unknown.

> **This report was rewritten on 2026-08-09.** Its first version claimed the select "never settles"
> and listed three causes eliminated by experiment. That was wrong, and the way it was wrong is
> worth keeping: see [Corrections](#corrections). Nothing below is inferred from those experiments.

## Description

Opening the select's list makes it fade in repeatedly, so it blinks. Reported by jaro against a
`main` build, in the **add-worktree dialog** during worktree creation.

It is a regression from this feature: the select had no transition before T027.

## Reproduction status

**Reproduced, 2026-08-09**, in the add-worktree dialog of the real client — not the showcase.

Method: the client run on a private Xvfb display against a throwaway sandbox project (its own
`XDG_RUNTIME_DIR`, `XDG_DATA_HOME` and git repo, so no real project or daemon was touched), dialog
opened, Type select pressed, then the list's region sampled with
`convert … -format "%[fx:mean]"` across successive captures.

The list's mean brightness **oscillates and never settles**, still doing it six seconds later:

```
t+1s  0.142483    t+4s  0.143972
t+2s  0.143972    t+5s  0.142483
t+3s  0.142480    t+6s  0.142468
```

**And the discriminating measurement, taken from the same captures**: the dialog's own heading is
constant at `0.210311` in every sample, and the area outside the dialog is constant at `0.0745098`.
So the modal is *not* pulsing. Only the list is — and only when it is inside the modal.

For contrast, the same control in the showcase — same code, no modal — holds constant to six
significant figures (`0.934237` repeated), with or without the cursor over it.

That pair is the finding: **the list blinks only when nested inside the dialog**, and the dialog
itself is settled while it happens.

## The mechanism, from instrumentation

Every `Progress` that asks for a frame was made to log itself, and the client was left **idle** with
the list open — no cursor movement, no keys, nothing.

It never stops logging. Over four seconds of doing nothing, 243 lines; left longer, 4,419. The
shape of them is the finding:

```
PROBE track value=0.8469 target=1.0 t=0.427 from=0.0000
PROBE track value=0.8469 target=1.0 t=0.427 from=0.0000     <- duplicated: two tracks in lockstep
PROBE track value=0.9063 target=1.0 t=0.533 from=0.0000
...
PROBE track value=0.9995 target=1.0 t=0.960 from=0.0000
                                            ^ then a new cycle begins at t≈0, from=0.0000
```

Three facts, each from the whole log rather than a sample:

1. **Every line is duplicated.** Two tracks moving identically — `scale` and `fade`, both on `ENTER`
   with the same default curve. That is `animated_menu`, so this *is* the select's transition and
   not some other animation.
2. **`target` only ever takes one value: `1.0`.** There is no descent and no reversal. The list is
   not being closed and reopened.
3. **`from` only ever takes one value: `0.0000`.** This is the decisive one. `Progress::retarget`
   sets `from` to the *current value* when a target changes, so a genuine retarget mid-flight would
   show `from` at some intermediate number. It never does.

**So the transition is not being restarted — its state is being recreated.** Each cycle is a fresh
`Progress` beginning at zero, with `animate_in()` doing exactly what it is supposed to do for a
newly-appeared element. The animation is behaving correctly; it is being *told* it is new, over and
over.

That rules out a whole class of explanations — target flapping, hover thrash, a reversal race — and
points at one thing: **the widget-tree state under the select's overlay is not surviving between
frames when the control is nested in the dialog.** In the showcase, nested one level shallower, it
survives and the list is still.

What is still unknown is *what* discards it, and why the modal's arrangement is what does it. The
dialog is composed in-tree — `material::Modal` becomes a `cdk::overlay::Surface`, and
`Overlay::from` collapses the layers into a plain `stack(...)` — so the list's `Widget::overlay()`
sits inside a stack child rather than inside a second iced overlay. Which of those levels loses the
identity is the next question, and it is a question about `Tree` identity, not about motion.

## What is actually established

- The `cdk::picker` visibility track is clean. Instrumented per frame: climbs 0 → 1 in seven frames
  at `EXIT` = 100 ms, then reports `RedrawRequest::Wait` and stays there.
- A settled select asks for no frames, once given enough of them.
- The only track that keeps asking for a while is one descending 1 → 0 at 0.08/frame (~200 ms), and
  it terminates.

## Narrowing the reset path

With the fast reproduction, three more things are ruled in or out by measurement:

- **`Select`'s own tree state survives.** `Select::state()` is called exactly **once** across the
  whole run. Whatever is reset is *below* it, in the subtree `Select::layout` diffs in.
- **The only code path that resets a track is `Motion::resync`**, called from every animated
  wrapper's `diff`:

  ```rust
  if track.key != self.key { track.key = self.key; track.progress.restart_at(0.0); … }
  ```

  `restart_at(0.0)` produces exactly the signature the instrumentation saw — value 0, `from` 0, no
  descent. **But it cannot be firing here**: `key` defaults to `0`, `animated_menu` never calls
  `restart_on`, so `track.key == self.key` always and the branch is dead for this control.
- **So the tracks are being newly created, not reset in place.** 11 fresh `Track`s were created
  during one run of the reproduction. That is suspicious but *not yet attributed*: the dialog holds
  several animated wrappers (the modal's own fade and scale, the list's fade and scale, ripples),
  and 11 is consistent with several of them being built once each.

**The next measurement is the small one that finishes this**: label the probe per wrapper — the
macro that emits `state()` is shared, so a `std::any::type_name` or a construction-site tag would
say *which* wrapper is being rebuilt and how often. If the list's fade appears repeatedly, the
question becomes why `Select::layout`'s `diff_children` is not matching it; if it appears once, the
reset is somewhere else entirely and `restart_at` is a red herring too.

## Corrections

The first version of this report was confidently wrong twice, from the same root: **a threshold
chosen without checking what it had to exceed.**

1. It asserted the select "never settles", from a probe that ran **30 frames**. At 300 frames the
   same probe passes. Thirty was simply short of the ~20 frames the transitions need, and a test
   that fails for want of frames looks exactly like one that fails for want of a fix.
2. Two of its three "eliminated causes" — re-assembly in `layout()`, and the `fade`/`scale` wrappers
   — rested on that same 30-frame probe, so they eliminated nothing. The committed `#[ignore]`d test
   asserting it has been **deleted**: a gate that fails for a reason its message misstates is worse
   than no gate.
3. Separately, and worse: `animated_menu` is reached through `Picker::overlay()`, and **none of
   those probes called `overlay()`**. The fade was never ticked in any of them. "Bypassing
   `animated_menu` changes nothing" was therefore true and meaningless.

The general lesson, recorded because it will recur: when a probe's verdict depends on a number the
author chose (a frame count, a timeout, a retry limit), establish what that number must exceed
*before* drawing a conclusion from it.

## Artifact Traceability

### spec.md

- **Affected**: FR-018, FR-019 and FR-020's quiescence promise. The spec asks for one entrance, not
  one per frame; its wording is not at fault.

### tasks.md

- **T027** introduced the transition and is where the regression entered.
- **T032** verified the architecture gates pass together, and they did — see below.

## Why every gate was green

`idle_requests_no_frames.rs` exists to catch a widget that never stops asking for frames, and it
**never covered an open select** — the select was a `pick_list` wrapper when that gate was written,
and nothing added a case when it became a widget with its own overlay.

`picker_motion.rs` measured how long a *closed* list keeps being produced and got the right answer,
because the exit path works. Neither it nor `picker_parity.rs` asked whether an open one ever stops
moving.

The visual pass missed it for an honest reason: it reads still frames, and a blink exists only
across frames. That limitation now belongs in the `visual-pass` skill.

## Recommended Fix

1. ~~Reproduce in the add-worktree dialog.~~ **Done** — see above.
2. Find why nesting changes it. `material::Modal` becomes a `cdk::overlay::Surface`, so the dialog
   is composed *in-tree* by the stacking host rather than through `Widget::overlay()`, while the
   select's list is a genuine `Widget::overlay()` inside that. The question to answer is whether the
   list's overlay state survives a frame in that arrangement — instrument the fade's own `Progress`
   there, which is the one thing no probe has yet observed.
3. ~~Bisect by nesting depth.~~ **Done, and it did not go as expected.** Bare: settles. Inside a
   plain `stack`: settles. Inside a *hand-built* `Surface` and `Modal`: both reported zero and both
   were **vacuous** — the press never landed, so nothing was measured. A non-vacuity assertion is
   what caught that; without it the bisect would have concluded "nesting is innocent", the opposite
   of what the instrumentation shows.

   What does reproduce it is the covered state the layout fixture already had:
   `add-worktree-dialog-type-menu-open`. It builds the real application view, presses the select at
   a node path checked against the fixture, and settles the dialog's entrance first — a modal
   swallows every non-redraw event until it has appeared. **21 of 60 idle frames ask for another
   one**, with the list verified open.

   That is now `tests/dialog_select_settles.rs`, `#[ignore]`d, 0.07s, no GUI required.
4. Fix the cause; add the regression test then, sized against the durations it has to outlast.
5. **Extend `idle_requests_no_frames.rs` to cover an open picker of each kind.** That gate's whole
   purpose is this class of defect, and its blindness here outlives this particular bug.
