# Bug Report: the open select's list re-runs its entrance and blinks

**Type**: Implementation drift
**Severity**: High
**Feature**: 022 — dedicated select component
**Reported**: 2026-08-08
**Status**: Open — reproduced, root cause **not** yet found

## Description

Opening the select's list makes it fade in repeatedly, so it blinks. Reported by jaro against a
`main` build, in the **add-worktree dialog** — the real flow, not the showcase.

This is a regression from this feature. The select had no transition before T027.

## Reproduction

`crates/micold-client/src/ui/material/picker_motion.rs` →
`an_open_select_stops_asking_for_frames`, committed `#[ignore]`d because it fails. Un-ignoring it is
how the fix proves itself.

Thirty frames after opening, the select still returns `RedrawRequest::NextFrame`. A track that never
settles re-runs its entrance every frame — that is the blink — and burns a core while doing it.

## What is established

| Case | Settles? |
|---|---|
| select never opened | **yes** |
| select pressed, then closed again | **yes** |
| select **open** | **no** |
| select open, `animated_menu` bypassed entirely | **no** |
| search picker open | **yes** |

Four hypotheses, three refuted:

- ~~Re-assembly in `layout()`~~ — delivering frames *without* re-running `layout` reproduces it
  identically. The select rebuilding its child every layout is not involved.
- ~~The `fade`/`scale` wrappers T027 added~~ — bypassing `animated_menu` and floating the bare panel
  reproduces it identically. **The obvious suspect is the wrong one.**
- ~~The trigger's ripple~~ — pressing to open and then closing again settles cleanly, so a press
  having happened is not it.
- **Remaining**: something specific to the select *while its list is open*.

## Root Cause Analysis

**Not yet found, and this report deliberately stops rather than guess.** Three plausible causes have
already been eliminated by experiment, and the fourth is a hypothesis, not a finding.

The lead worth pursuing first is where `cdk::picker`'s `Visibility` track *starts*. `Picker::state()`
constructs it as `Progress::new(if open { 1.0 } else { 0.0 })`:

- the **search picker** is built already open, so its track is constructed *at* its target, never
  animates, and `animating()` is false from the first frame — which is exactly why it settles;
- the **select** is built closed, so its track is constructed at `0.0` and has to climb to `1.0`.

`Progress::animating()` is `(value - target).abs() > EPSILON` and `request_frame` asks whenever that
is true. So the question to answer next is why that climb never terminates — `advance_to` clamps
`t` at 1.0 and assigns `value = target` there, so on paper it should converge in ~7 frames at
`EXIT` = 100 ms. Instrument `Visibility`'s `value`/`target`/`t` per frame; that will answer it in one
run.

## Artifact Traceability

### spec.md

- **Affected**: FR-018, FR-019 (the list arrives and leaves), and **FR-020's quiescence promise**.
- **Gap**: none in the wording. The spec asks for one entrance, not one per frame.

### tasks.md

- **T027** wired the transition and is where the regression entered — though note the bypass
  experiment shows the transition itself is not the mechanism.
- **T032** verified the architecture gates pass together, and they did. See below.

## Why every gate was green

`idle_requests_no_frames.rs` exists precisely to catch a widget that never stops asking for frames.
It passed, because **it never covered an open select** — the select was a `pick_list` wrapper when
that gate was written, and nothing added a case when the select became a widget with its own
overlay.

`picker_motion.rs` measured how long a *closed* list keeps being produced, and got the right answer,
because the exit path genuinely works. Neither it nor `picker_parity.rs` asked whether an *open* one
ever stops moving.

The visual pass did not catch it either: it reads still frames, and a blink is only visible in
motion. It is what a person noticed in seconds.

## Recommended Fix

1. Instrument the `Visibility` track per frame and identify why the climb does not terminate.
2. Fix the cause; un-ignore `an_open_select_stops_asking_for_frames`.
3. **Extend `idle_requests_no_frames.rs` to cover an open picker of each kind.** That gate's whole
   purpose is this defect, and its blindness here is the more durable finding than the bug.
