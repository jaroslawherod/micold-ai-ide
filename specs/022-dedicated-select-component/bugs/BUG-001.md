# Bug Report: the select's list re-runs its entrance and blinks

**Type**: Implementation drift
**Severity**: High
**Feature**: 022 — dedicated select component
**Reported**: 2026-08-08
**Status**: **Fixed** — root cause found and gated. `Select` left `Widget::diff` at iced's default, which is `tree.children.clear()`; every rebuild of the view discarded the subtree it assembles in `layout`, so the list's entrance restarted from zero on every frame.

> **This report was rewritten on 2026-08-09.** Its first version claimed the select "never settles"
> and listed three causes eliminated by experiment. That was wrong, and the way it was wrong is
> worth keeping: see [Corrections](#corrections). Nothing below is inferred from those experiments.

## Description

Opening the select's list makes it fade in repeatedly, so it blinks. Reported by jaro against a
`main` build, in the **add-worktree dialog** during worktree creation.

It is a regression from this feature: the select had no transition before T027.

## Reproduction status

**Reproduced, 2026-08-09**, in the add-worktree dialog of the real client — not the showcase.

Method: the client run on a private Xvfb display against a throwaway sandbox project (its own
`XDG_RUNTIME_DIR`, `XDG_DATA_HOME` and git repo, so no real project or daemon was touched), dialog
opened, Type select pressed, then the list's region sampled with
`convert … -format "%[fx:mean]"` across successive captures.

The list's mean brightness **oscillates and never settles**, still doing it six seconds later:

```
t+1s  0.142483    t+4s  0.143972
t+2s  0.143972    t+5s  0.142483
t+3s  0.142480    t+6s  0.142468
```

**And the discriminating measurement, taken from the same captures**: the dialog's own heading is
constant at `0.210311` in every sample, and the area outside the dialog is constant at `0.0745098`.
So the modal is *not* pulsing. Only the list is — and only when it is inside the modal.

For contrast, the same control in the showcase — same code, no modal — holds constant to six
significant figures (`0.934237` repeated), with or without the cursor over it.

That pair is the finding: **the list blinks only when nested inside the dialog**, and the dialog
itself is settled while it happens.

## The mechanism, from instrumentation

Every `Progress` that asks for a frame was made to log itself, and the client was left **idle** with
the list open — no cursor movement, no keys, nothing.

It never stops logging. Over four seconds of doing nothing, 243 lines; left longer, 4,419. The
shape of them is the finding:

```
PROBE track value=0.8469 target=1.0 t=0.427 from=0.0000
PROBE track value=0.8469 target=1.0 t=0.427 from=0.0000     <- duplicated: two tracks in lockstep
PROBE track value=0.9063 target=1.0 t=0.533 from=0.0000
...
PROBE track value=0.9995 target=1.0 t=0.960 from=0.0000
                                            ^ then a new cycle begins at t≈0, from=0.0000
```

Three facts, each from the whole log rather than a sample:

1. **Every line is duplicated.** Two tracks moving identically — `scale` and `fade`, both on `ENTER`
   with the same default curve. That is `animated_menu`, so this *is* the select's transition and
   not some other animation.
2. **`target` only ever takes one value: `1.0`.** There is no descent and no reversal. The list is
   not being closed and reopened.
3. **`from` only ever takes one value: `0.0000`.** This is the decisive one. `Progress::retarget`
   sets `from` to the *current value* when a target changes, so a genuine retarget mid-flight would
   show `from` at some intermediate number. It never does.

**So the transition is not being restarted — its state is being recreated.** Each cycle is a fresh
`Progress` beginning at zero, with `animate_in()` doing exactly what it is supposed to do for a
newly-appeared element. The animation is behaving correctly; it is being *told* it is new, over and
over.

That rules out a whole class of explanations — target flapping, hover thrash, a reversal race — and
points at one thing: **the widget-tree state under the select's overlay is not surviving between
frames.**

**This section was right, and it is the only one that was.** Everything after it went looking for
what the *modal* did differently, because that is where the blink was visible — and the modal does
nothing differently. The state is discarded on every view rebuild, everywhere; the dialog was
merely the one place something else kept the rebuilds coming. See
[The root cause](#the-root-cause).

## What is actually established

- The `cdk::picker` visibility track is clean. Instrumented per frame: climbs 0 → 1 in seven frames
  at `EXIT` = 100 ms, then reports `RedrawRequest::Wait` and stays there.
- A settled select asks for no frames, once given enough of them.
- The only track that keeps asking for a while is one descending 1 → 0 at 0.08/frame (~200 ms), and
  it terminates.

## The root cause

`Select` assembles its only child inside `Widget::layout` — it has to, because `FormField` draws the
open-state indicator when the element is *built* and the open flag lives in widget-tree state that
nothing can read any earlier (module docs, "Why this is a widget rather than a composition"). What
that costs is not obvious, and it is the whole bug:

```rust
// iced_core-0.14.0/src/widget.rs:95 — the default
fn diff(&self, tree: &mut Tree) {
    tree.children.clear();
}
```

That default is right for a widget that hands its children over in `children()`: there is nothing
to keep. `Select` supplies them one step later, and never overrode `diff`. So on **every rebuild of
the view**, iced cleared the subtree, `layout` diffed a fresh child into an empty vec, `Tree::new`
made new state for it, and the menu's `fade` and `scale` began again at zero — `from = 0.0`, target
`1.0`, no descent. Exactly the signature the instrumentation recorded.

The loop is self-sustaining, which is why it never ended: the restarted transition asks for a frame,
the frame re-runs `view()`, the rebuild clears the subtree again.

It also explains the two things that looked contradictory:

- **Why the showcase held still.** A settled select asks for no frames, so nothing redraws, so
  `view()` never re-runs and nothing clears it. Inside the dialog something else was still asking,
  the rebuild reset the list, and from then on the list kept the loop alive by itself.
- **Why the headless probes all reported a serene settle.** Every one of them built the element
  **once** and pumped events at it. A widget test that never re-runs `view()` never calls
  `Widget::diff` at all, so it cannot see this class of defect — no matter how many frames it runs.

## The fix

`crates/micold-client/src/ui/material/select.rs` — an explicit, empty `diff`:

```rust
fn diff(&self, _tree: &mut Tree) {}
```

Nothing is lost by it. `layout` runs on every frame a rebuild does and diffs the freshly assembled
child in, so reconciliation still happens, one step later, against a child that exists.

`cdk::Picker`, `ListWatch`, `Ripple`, `FilledField` and `NavigationDrawer` were all checked and were
already correct — they supply their children in `children()` and diff them properly. `Select` was
the only one.

### Confirmed in the real client

Same method as the reproduction above, on 2026-08-09: Xvfb + lavapipe, a throwaway sandbox project,
add-worktree dialog open, Type list open, then left alone. The list's region, sampled once a second:

```
t+1s  0.130719    t+4s  0.130719    t+7s  0.130719
t+2s  0.130719    t+5s  0.130719
t+3s  0.130719    t+6s  0.130719
```

Constant to six significant figures for seven seconds, against `0.142483 / 0.143972 / 0.142480 …`
before the fix. The dialog heading held at `0.230015` throughout, as the control.

Worth noting what the sandbox happened to include: a Claude Code session was starting in the pane
behind the dialog, so *something else was requesting frames the whole time*. That is precisely the
condition that made the blink self-sustaining, and the list stayed still through it.

## Narrowing the reset path (superseded)

*Kept because the conclusion it reached was wrong in an instructive way — see
[Corrections](#corrections).*

With the fast reproduction, three more things are ruled in or out by measurement:

- **`Select`'s own tree state survives.** `Select::state()` is called exactly **once** across the
  whole run. Whatever is reset is *below* it, in the subtree `Select::layout` diffs in.
- **The only code path that resets a track is `Motion::resync`**, called from every animated
  wrapper's `diff`:

  ```rust
  if track.key != self.key { track.key = self.key; track.progress.restart_at(0.0); … }
  ```

  `restart_at(0.0)` produces exactly the signature the instrumentation saw — value 0, `from` 0, no
  descent. **But it cannot be firing here**: `key` defaults to `0`, `animated_menu` never calls
  `restart_on`, so `track.key == self.key` always and the branch is dead for this control.
- **So the tracks are being newly created, not reset in place.** 11 fresh `Track`s were created
  during one run of the reproduction. That is suspicious but *not yet attributed*: the dialog holds
  several animated wrappers (the modal's own fade and scale, the list's fade and scale, ripples),
  and 11 is consistent with several of them being built once each.

The probe was labelled per wrapper, as that paragraph asked. It said **8 Fade, 2 Scale, 1 Expand**
fresh tracks — and then, counted *during the idle phase only*, **zero**. Both of the conclusions
above were therefore wrong: nothing was being recreated and nothing was being reset, in that harness.
The harness was the problem, not the widget (see [The root cause](#the-root-cause)).

## Corrections

The first version of this report was confidently wrong twice, from the same root: **a threshold
chosen without checking what it had to exceed.**

1. It asserted the select "never settles", from a probe that ran **30 frames**. At 300 frames the
   same probe passes. Thirty was simply short of the ~20 frames the transitions need, and a test
   that fails for want of frames looks exactly like one that fails for want of a fix.
2. Two of its three "eliminated causes" — re-assembly in `layout()`, and the `fade`/`scale` wrappers
   — rested on that same 30-frame probe, so they eliminated nothing. The committed `#[ignore]`d test
   asserting it has been **deleted**: a gate that fails for a reason its message misstates is worse
   than no gate.
3. Separately, and worse: `animated_menu` is reached through `Picker::overlay()`, and **none of
   those probes called `overlay()`**. The fade was never ticked in any of them. "Bypassing
   `animated_menu` changes nothing" was therefore true and meaningless.

4. The rewritten report then made the *same* mistake a second time, in the other direction. Its
   headline number — "21 of 60 idle frames ask for another one" — was compared against bare and
   stacked cases that had counted asks only over their **last 20 of 80** frames. Two different
   windows, read as one result. Recording the frame each ask landed on settled it in one run:
   `last_ask_at_frame=20`, nothing after it. Those 21 frames were a settle tail. The headless
   reproduction was invalid.
5. And underneath all of them, the thing that made every probe blind: **none of them re-ran
   `view()`**. Each built one element and pumped events at it, so `Widget::diff` — where the bug
   lives — was never called even once. Five successive probes agreed with each other and all five
   were measuring an application that does not exist.

Two lessons, both recorded because they will recur:

- When a probe's verdict depends on a number the author chose (a frame count, a timeout, a retry
  limit), establish what that number must exceed *before* drawing a conclusion from it — and make
  the probe report where in its window the signal fell, not just how much of it there was.
- **A widget harness that never rebuilds the view is not a model of the application.** It cannot
  observe `diff`, and `diff` is where a widget's state is kept or lost. Any future probe of this
  kind must rebuild and diff each frame, as `tests/dialog_select_settles.rs` now does.

## Why every gate was green

`idle_requests_no_frames.rs` exists to catch a widget that never stops asking for frames, and this
widget never asked. Every `Progress` in the tree was guarded and correct; the loop was driven by
state being destroyed, one layer above anything that gate could see. It scanned for the wrong door.

`picker_motion.rs` measured how long a *closed* list keeps being produced and got the right answer,
because the exit path works. Neither it nor `picker_parity.rs` asked whether an open one ever stops
moving.

And the general reason nothing caught it: **every widget test in this crate builds its element once**
and pumps events at it. That is a reasonable way to test layout and event handling, and it is
structurally incapable of exercising `Widget::diff` — so an entire class of state-lifetime defects
was invisible to the whole suite.

The visual pass missed it for an honest reason: it reads still frames, and a blink exists only
across frames. That limitation now belongs in the `visual-pass` skill.

## The fix, and what now guards it

1. ~~Reproduce in the add-worktree dialog.~~ **Done.**
2. ~~Find why nesting changes it.~~ **Nesting was never the cause.** The dialog only mattered
   because something else in it was still requesting frames, which made `view()` re-run — and the
   rebuild is what destroyed the state. Bare and stacked cases looked innocent because a settled
   select requests no frames, so nothing rebuilt them.
3. ~~Bisect by nesting depth.~~ Done, and it misled, for the reason above.
4. ~~Fix the cause.~~ **Done** — `Select` now overrides `Widget::diff`.
5. **Two gates, both verified to fail without the fix:**
   - `tests/dialog_select_settles.rs` — the behavioural one, un-`#[ignore]`d and passing. It drives
     the `add-worktree-dialog-type-menu-open` covered state and **re-runs `view()` and diffs it every
     frame**, which is the part that makes it a model of the application. Without the fix: 60 of 60
     idle frames ask for another. With it: zero. 0.11s, no GUI.
   - `idle_requests_no_frames.rs::a_widget_that_assembles_in_layout_keeps_its_subtree` — the
     structural one. Any `impl Widget` whose `layout` calls `diff_children` must declare `diff`. It
     is deliberately **impl-granular**, not file-granular: a file-granular version passed on
     `select.rs` for the wrong reason, satisfied by `ListWatch`'s correct `diff` sitting a few
     hundred lines below the missing one.
