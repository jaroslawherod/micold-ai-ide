# Bug Report: the select's state layer covers 40% of its field, and no input answers focus

**Type**: Spec gap (primary) + implementation drift
**Severity**: Medium
**Feature**: 022 — dedicated select component
**Reported**: 2026-08-09
**Status**: **Fixed** — the layer and the ripple now cover the container that answers the pointer,
and every field answers focus. `FilledField` reads hover off the cursor when it draws, so the flag
that disagreed with it is gone rather than corrected. One part is **not** met and is recorded as
such: the checkbox cannot answer focus, because the stack's `checkbox::Status` has no focused
variant (FR-035's note).
**Patched**: 2026-08-09
**Fixed**: 2026-08-09

## Description

Reported by jaro:

> on hover it should highlight the whole background not only small part around clickable select
> (the whole item should be clickable). Same hover behavior should be also for other inputs.
> Also the colour should change on focus.

## What the evidence shows

The report says "select item", and the obvious reading is the rows of the open dropdown. **The rows
are not the defect.** The defect is on the select's *trigger* — the closed field you press to open
the list — and it matches the description exactly, in the place the description did not name.

Both halves are measured from the recorded layout of the `add-worktree-dialog-type-menu-open`
covered state (`crates/micold-client/tests/fixtures/layout_snapshot.txt:2296`), which captures a
real dialog rather than a posed fixture.

### The rows are already full width

```
over   0/0/0/0                408.0  360.0  464.0  384.0   <- panel interior
over   0/0/0/0/0/0/0/0        408.0  360.0  464.0   48.0   <- row button: full width, 48dp tall
over   0/0/0/0/0/0/0/0/0      416.0  360.0  448.0   48.0   <- content, inside the button's padding
```

`crates/micold-client/src/ui/material/picker.rs:135` builds each row as a `button` at
`.width(Length::Fill)` with `.padding([0.0, spacing::SM])` applied **inside**, so neither the hit
box nor the painted state layer is narrowed. The row is 464 of the panel's 472dp.

The only shortfall is the panel's own 4dp side padding (`picker.rs:225-228`), and it is a known,
deliberate deviation: `menu.rs:120-129` zeroes its side padding precisely "so an item's state layer
runs the full width of the panel", while the picker "keeps the padding it had" pending T108. Worth
closing for edge-to-edge parity with the menu, but 4dp is not "a small part".

### The trigger's state layer covers 40% of the field

```
base   0/6/0/0/0/2            404.0  296.0  472.0   56.0   <- the select's field box
base   0/6/0/0/0/2/0/1        420.0  320.0  440.0   24.0   <- Ripple + state-layer container
```

440×24 inside 472×56 — **40% of the container**, inset 16dp left and right, 24dp from the top and
8dp from the bottom.

The cause is that the layer is painted on the trigger, and the trigger is laid out into
`FilledField`'s *control slot*, which is deliberately small — one value line inside the field's
16dp padding (`filled_field.rs:116-153`, `VALUE_LINE = 24.0`). `select.rs:309` sets
`.width(Length::Fill).height(Length::Fill)`, but "fill" there means the slot, not the field.

**What makes it a defect rather than a choice is the internal disagreement**: hover and press are
detected over the *whole* field, and only the painting is narrow.

- `select.rs:447-452` — the trigger bounds for input are `layout.children().next()`, the full 472×56 band.
- `select.rs:499-509` — `state.hovered = cursor.is_over(trigger)` against that band.
- `select.rs:476-488` — a press anywhere in that band toggles the list.
- `ripple.rs:217-221` — but the ripple only starts on `cursor.position_over(bounds)`, the 440×24 node.

So the pointer resting in the 16dp gutter marks the select hovered and will open it on click, while
the highlight paints only the inner rectangle and no ripple fires. The control is already fully
clickable; it just does not look it.

### No input answers focus, and most answer nothing

- **The select has no focus state at all.** `select.rs:286-292` derives its layer opacity from two
  inputs only — `state::PRESSED` when open, `state::HOVER` when hovered, otherwise nothing. There is
  no focused branch, and the file's only mention of focus is a comment about Tab (`select.rs:628`).
- **Text fields draw nothing on any state.** `style.rs:624` — `field_input` takes a
  `text_input::Status` and **ignores it**, returning a transparent background for every status, so
  neither hover nor focus changes the container. `filled_field.rs:198-233` paints only the container
  tone and the active indicator.
- **Checkboxes** change only their border colour on hover (`style.rs:504-530`).
- `form_field.rs:173-239` is pure composition and owns no layer.

The controls built on `button` — `toggle_chip.rs`, `button.rs`, `icon_button.rs`, `menu.rs` — are
correct, because there the hit area *is* the painted surface.

So "the same hover behaviour for other inputs" and "the colour should change on focus" are both
**new work, not regressions**: those state layers have never existed.

## Visual pass, 2026-08-09

Run with the `visual-pass` skill — the component gallery on **Xvfb `:77` + lavapipe** at 1600×1400,
not a real display and not a GPU. Numbers below are pixels sampled off the captures.

**The extent fix holds, measured across the field rather than eyeballed.** The live select, light
scheme, sampled at the container's left gutter (`x=30`, inside §7.7's 16dp padding — the column that
*could not change colour* before this fix):

| | `x=30` (gutter) | `x=800` (centre) |
|---|---|---|
| at rest | `srgb(230,225,230)` | — |
| hovered | `srgb(214,209,214)` | `srgb(214,209,214)` |

Gutter and centre resolve to the **same** value, which is the whole claim of FR-034. Dark scheme
agrees: `srgb(54,52,56)` at rest → `srgb(68,66,70)` at both positions.

**The ripple now starts in the padding.** Pressing at `x=30` opened the list *and* rippled from the
press point: `srgb(192,187,192)` there against `srgb(210,205,210)` for the open-state layer across
the rest of the field. The darker patch spreading from the field's left edge is visible in the
capture. This is the contradiction this report named, closed.

**The four posed layers are ordered and full-width**, both schemes:

| pose | light | dark |
|---|---|---|
| None | `srgb(230,225,230)` | `srgb(54,52,56)` |
| Hovered | `srgb(214,209,214)` | `srgb(68,66,70)` |
| Focused | `srgb(210,205,210)` | `srgb(71,69,73)` |
| Pressed | `srgb(210,205,210)` | `srgb(71,69,73)` |

**Focused and Pressed are identical, and that is correct rather than a defect**: `state::FOCUS` and
`state::PRESSED` are both 0.10, which is what Material 3 specifies (hover 8%, focus 10%, pressed
10%). Worth recording because the two gallery poses sit next to each other looking the same, and the
next reader will otherwise take it for a bug.

### What the pass found that the suite did not

**FR-035 renders but never fires. No call site reports focus.** `TextField::active` is *supplied*,
not observed — and `grep` finds **zero** `TextField` call sites passing `.active(…)`, in the gallery
or in the application. Clicking into the gallery's live text field puts a caret in it and changes
nothing: no state layer, and no thickened active indicator either.

So the container can draw the focus layer, and nothing ever asks it to. The select is unaffected —
its open state is its own, and it works — but for every text field FR-035 is **implemented and
unreachable**. That is a gap in the plumbing rather than in this fix, and it is older than this bug:
the active indicator has answered focus the same way since feature 018 and has never lit either.
It needs a screen that tracks which field holds the keyboard, which nothing here does.

**Not covered, and not claimed:**

- **The add-worktree dialog itself.** Verified on the gallery's select, which is the same component;
  the dialog needs a running daemon and a sandbox project, and was not exercised. The mechanism is
  per-widget drawing rather than anything the modal supplies, so the gallery is fair evidence — but
  it is not the reported surface, and BUG-001 is the standing reminder that the dialog can differ.
- **The transition's look.** Per the skill's own limits: a screenshot pipeline cannot catch a chosen
  frame of a 150 ms transition, and lavapipe says nothing about frame pacing.

## Artifact Traceability

### spec.md

- **Affected user story**: Story 1 — "The select is a first-class Material control", acceptance
  scenario 6 ("the same hover and press response — including the press ripple").
- **Affected requirements**:
  - **FR-002** — the select presents "the same field anatomy as the shared text field". It does, and
    that is the problem: the text field it matches has no state layer either.
  - **FR-008** — rows use the same state layers as the search picker's. **Met**; the parity gate
    `picker_parity.rs:165` compares both floated lists node for node.
  - **FR-010** — "Pressing a row MUST produce the same press ripple every other pressable surface in
    the app produces." Written about rows; the trigger is a pressable surface whose ripple is
    confined to 40% of it, and no requirement covers that.
  - **FR-029** — legibility of every state in both schemes; a state that is not drawn cannot be
    assessed.
- **Gap identified**: **the spec never says where a state layer must be drawn.** It specifies the
  field's anatomy, the row's anatomy and the ripple, but nothing states that a control's hover,
  focus and pressed layers cover the whole of the container that responds to the pointer. Material 3
  treats the state layer as covering the component's bounds; that rule is not written down anywhere
  in this feature, so an implementation that paints it into a sub-slot satisfies every requirement.
  **Focus is absent entirely** — the word does not appear as a state in any FR, which is why no
  control has one.

### plan.md

- **Affected sections**: the select's trigger composition, and the shared state-layer treatment
  inherited from `style::state_fill` / `style_states.rs`.
- **Impact**: a decision is needed on whether the layer belongs to `FilledField` (which knows the
  container's bounds) rather than to the control placed in its slot. That choice governs the text
  field and any future field alike, so it is foundation work, not a select patch.

### tasks.md

- **Affected tasks**:
  - **T016** — "a pressable trigger row (value or placeholder, spacer, chevron, state layer,
    ripple) composed inside `FormField`". This is where the layer was placed in the control slot;
    the task's wording is satisfied by what was built.
  - **T012** — the trigger anatomy gate (`select_anatomy.rs`). It checks container height, label
    float, chevron and indicator, and **asserts nothing about the state layer's rectangle**.
  - **T031** — added the trigger's state-layer colour pairings to the contrast gate, so the *colour*
    is verified while its *extent* is not.
- **False completions**: none. Every task above did what it said; no gate was wrong.
- **Missing tasks**: a state-layer extent gate; a focus state for the select and the text field; the
  4dp picker panel side padding (T108's pending decision).

## Root Cause Analysis

**A spec oversight, not an implementation error.** Feature 022 specified the select against the
existing text field, and inherited an unstated assumption from it: that a field's interactive
feedback is the active indicator, with the state layer an afterthought applied to whatever element
happens to be pressable. Nothing in the spec or the contracts says the layer must match the region
that responds to the pointer, so `select.rs:309`'s `Length::Fill` — filling the slot it was given —
is a reasonable reading of the requirement it was written to.

The tests could not catch it for the same reason BUG-001 escaped them, in a different form: the
anatomy gates assert *sizes and roles of elements*, and the contrast gate asserts *colours*, but
nothing asserts that two rectangles — the one that detects the pointer and the one that paints —
are the same rectangle. `style_states.rs:77-139` verifies the hover and pressed opacity deltas
without any geometry at all.

## Scope note

Three separable pieces of work, in the order their evidence supports:

1. **The select trigger's layer and ripple should cover the field.** A real defect with a measured
   40% figure and an internal contradiction to point at.
2. **Focus and hover states for the other inputs.** New behaviour, currently absent everywhere
   (`style.rs:624` discards the status it is handed). Needs a spec decision first — it touches every
   field in the app and is arguably its own feature, not a 022 bug.
3. **The picker panel's 4dp side padding**, for edge-to-edge parity with `menu.rs`. Small, and
   already parked under T108.

Only the first is a defect in what 022 promised. The second and third are gaps this report happens
to have measured.

**Decided 2026-08-09 by jaro: all of it goes into 022.** Items 1 and 2 became FR-034 – FR-036 and
Phase 7 (T041–T048); the spec records why the widening is deliberate rather than scope creep — the
select's layer sits in a sub-slot because it inherited the text field's arrangement, so fixing the
control without the arrangement leaves the next field to repeat it. Item 3, the 4dp panel padding,
stays parked under T108.
