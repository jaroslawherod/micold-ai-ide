# Bug Report: no text field reports focus, so nothing a field does on focus ever happens

**Type**: Implementation drift
**Severity**: Medium
**Feature**: 022 — dedicated select component (the defect is older; see [Provenance](#provenance))
**Reported**: 2026-08-09
**Status**: Open — reported only, nothing changed.

## Description

Every text field in the application is drawn as though it can never be focused. Clicking into one
places a caret and changes nothing else: the active indicator stays a muted hairline, the container
takes no state layer, and an empty field's label stays resting on the value's line instead of
floating clear of it.

Found by the visual pass on [BUG-002](./BUG-002.md), while checking that the focus layer that bug
added actually reached the screen. It does not — but the layer is the least of it, because the same
flag drives two things that have been specified since feature 018.

## The mechanism

`FormField::active` is **supplied, not observed** — a deliberate decision, and a correct one. The
state that thickens the indicator differs by control (focus for a text input, open for a picker), so
the wrapper is told which rather than assuming (`form_field.rs`, "Why 'active' is a parameter and
not a question this asks"). `TextField::active` forwards it, and its own doc says so: *"Supplied
rather than observed: the rendering stack reports focus only inside the input's own style closure,
and the indicator is a sibling of the input rather than part of it."*

The design is sound. **Nothing supplies it.**

Every hit is a toggle chip or a filter trigger. **Not one is a `TextField` or a `FormField`.** The
only `.active(true)` on a field in the whole tree is `controls.rs:212`, the gallery's *posed* state,
which exists precisely because the live one cannot reach it.

The seven live text fields — `worktree_rename.rs:19`, `rename.rs:19`, `worktree_form.rs:60` and
`:65`, `settings_form.rs:37`, `:47` and `:51` — all construct a `TextField` and none calls
`.active(…)`, so every one of them is permanently inactive.

`material/typeahead.rs:211` does pass `.active(open)`, and deliberately: §7.7 wants a picker's
indicator to follow **open** rather than focus. The search picker is therefore not affected in the
same way, and whether its *state layer* should follow focus as well as open is a separate question
this report does not answer.

## What it costs, in order of visibility

1. **The label does not float on focus.** `label_floats(populated, active)` is `populated || active`,
   so with `active` permanently false an empty field keeps its label on the value's line until the
   first keystroke. Material floats it when the field takes focus. The placeholder is suppressed
   while the label rests (one rule, in one place — `form_field.rs`), so what a person sees on
   clicking an empty field is **a caret sitting immediately in front of the label text**. Confirmed
   in the visual pass capture: a live gallery text field, focused, caret before "Branch name", label
   unmoved.
2. **The active indicator never thickens or takes the accent.** This is §7.7's whole focus
   affordance for a filled field — there is no border left to recolour — and it has never once
   fired in the application.
3. **The focus state layer never appears** (BUG-002's FR-035). The container draws it correctly when
   told; nothing tells it.

The first is the one a person notices without knowing why; the second is the one the design system
promises.

## Why every gate is green

`form_field_anatomy.rs` and `text_field_anatomy.rs` both build a field **with `active` set by the
test** and assert what it draws. That is the right way to test the component and it cannot see this:
the component does exactly what it is told, and the defect is that nobody tells it. There is no gate
anywhere asserting that a *call site* reports focus, because until now nothing said one had to.

BUG-002's `a_fields_states_are_distinct_and_ordered` has the same shape — it resolves the layer for
a given state rather than asking whether any state is ever reached.

## Provenance

**This is older than the feature it is filed under.** The indicator's focus behaviour is feature
018's (FR-031, §7.7) and has never worked in the application; feature 022 added the focus state
layer on top of the same unset flag, so BUG-002 inherited a dead input rather than creating one.
Filed here because 022 is where it was found and where FR-035 now claims it.

## Root Cause Analysis

A wrapper was correctly designed to be told a fact, and the telling was never built — on either side
of two features. `FormField` made `active` a parameter for good reasons and documented them well,
which is very likely why it read as finished: the parameter exists, the component honours it, the
anatomy gates prove it honours it, and the only missing piece is a `true` that no screen ever passes.

Underneath it is a structural gap rather than an oversight: **no screen in this application tracks
which field holds the keyboard.** iced reports focus inside the text input's own style closure, and
the indicator, the label and the container are all siblings of that input, so the fact has to travel
up into application state and back down — which is a change to every form that has a field, not to
the component.

## Recommended Fix

Not obvious, and the choice belongs to whoever picks this up:

- **Each screen tracks focus in its own state** and passes `.active(…)`. Honest, matches the current
  design, and is an edit to seven call sites plus their message enums.
- **`FilledField` observes focus itself**, the way it now observes hover for BUG-002 — it is a
  widget with the container's bounds and could operate the focus query iced provides. Removes the
  parameter's reason to exist for text inputs while keeping it for pickers, which then makes
  `active` mean two different things depending on the control.

The second is tempting for the same reason reading hover off the cursor was: one owner, nothing to
disagree with. It is also the larger change, and it collides with `form_field.rs`'s documented
rationale for the parameter — so it wants a decision rather than a patch.
