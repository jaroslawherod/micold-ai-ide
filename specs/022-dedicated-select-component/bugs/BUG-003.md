# Bug Report: no text field reports focus, so nothing a field does on focus ever happens

**Type**: Implementation drift
**Severity**: Medium
**Feature**: 022 — dedicated select component (the defect is older; see [Provenance](#provenance))
**Reported**: 2026-08-09
**Status**: Fixed — see [The fix](#the-fix).

## Description

Every text field in the application is drawn as though it can never be focused. Clicking into one
places a caret and changes nothing else: the active indicator stays a muted hairline, the container
takes no state layer, and an empty field's label stays resting on the value's line instead of
floating clear of it.

Found by the visual pass on [BUG-002](./BUG-002.md), while checking that the focus layer that bug
added actually reached the screen. It does not — but the layer is the least of it, because the same
flag drives two things that have been specified since feature 018.

## The mechanism

`FormField::active` is **supplied, not observed** — a deliberate decision, and a correct one. The
state that thickens the indicator differs by control (focus for a text input, open for a picker), so
the wrapper is told which rather than assuming (`form_field.rs`, "Why 'active' is a parameter and
not a question this asks"). `TextField::active` forwards it, and its own doc says so: *"Supplied
rather than observed: the rendering stack reports focus only inside the input's own style closure,
and the indicator is a sibling of the input rather than part of it."*

The design is sound. **Nothing supplies it.**

```

      | grep -v 'material/'
worktree_form.rs:145   .active(form.source == BranchSource::New)        <- ToggleChip

showcase/sections/controls.rs:133,138,144,349,354                       <- ToggleChip / FilterTrigger
showcase/sections/surfaces.rs:110                                       <- FilterTrigger
```

Every hit is a toggle chip or a filter trigger. **Not one is a `TextField` or a `FormField`.** The
only `.active(true)` on a field in the whole tree is `controls.rs:212`, the gallery's *posed* state,
which exists precisely because the live one cannot reach it.

The seven live text fields — `worktree_rename.rs:19`, `rename.rs:19`, `worktree_form.rs:60` and
`:65`, `settings_form.rs:37`, `:47` and `:51` — all construct a `TextField` and none calls
`.active(…)`, so every one of them is permanently inactive.

`material/typeahead.rs:211` does pass `.active(open)`, and deliberately: §7.7 wants a picker's
indicator to follow **open** rather than focus. The search picker is therefore not affected in the
same way, and whether its *state layer* should follow focus as well as open is a separate question
this report does not answer.

## What it costs, in order of visibility

1. **The label does not float on focus.** `label_floats(populated, active)` is `populated || active`,
   so with `active` permanently false an empty field keeps its label on the value's line until the
   first keystroke. Material floats it when the field takes focus. The placeholder is suppressed
   while the label rests (one rule, in one place — `form_field.rs`), so what a person sees on
   clicking an empty field is **a caret sitting immediately in front of the label text**. Confirmed
   in the visual pass capture: a live gallery text field, focused, caret before "Branch name", label
   unmoved.
2. **The active indicator never thickens or takes the accent.** This is §7.7's whole focus
   affordance for a filled field — there is no border left to recolour — and it has never once
   fired in the application.
3. **The focus state layer never appears** (BUG-002's FR-035). The container draws it correctly when
   told; nothing tells it.

The first is the one a person notices without knowing why; the second is the one the design system
promises.

## Why every gate is green

`form_field_anatomy.rs` and `text_field_anatomy.rs` both build a field **with `active` set by the
test** and assert what it draws. That is the right way to test the component and it cannot see this:
the component does exactly what it is told, and the defect is that nobody tells it. There is no gate
anywhere asserting that a *call site* reports focus, because until now nothing said one had to.

BUG-002's `a_fields_states_are_distinct_and_ordered` has the same shape — it resolves the layer for
a given state rather than asking whether any state is ever reached.

## Provenance

**This is older than the feature it is filed under.** The indicator's focus behaviour is feature
018's (FR-031, §7.7) and has never worked in the application; feature 022 added the focus state
layer on top of the same unset flag, so BUG-002 inherited a dead input rather than creating one.
Filed here because 022 is where it was found and where FR-035 now claims it.

## Root Cause Analysis

A wrapper was correctly designed to be told a fact, and the telling was never built — on either side
of two features. `FormField` made `active` a parameter for good reasons and documented them well,
which is very likely why it read as finished: the parameter exists, the component honours it, the
anatomy gates prove it honours it, and the only missing piece is a `true` that no screen ever passes.

Underneath it is a structural gap rather than an oversight: **no screen in this application tracks
which field holds the keyboard.** iced reports focus inside the text input's own style closure, and
the indicator, the label and the container are all siblings of that input, so the fact has to travel
up into application state and back down — which is a change to every form that has a field, not to
the component.

## Recommended Fix

Not obvious, and the choice belongs to whoever picks this up:

- **Each screen tracks focus in its own state** and passes `.active(…)`. Honest, matches the current
  design, and is an edit to seven call sites plus their message enums.
- **`FilledField` observes focus itself**, the way it now observes hover for BUG-002 — it is a
  widget with the container's bounds and could operate the focus query iced provides. Removes the
  parameter's reason to exist for text inputs while keeping it for pickers, which then makes
  `active` mean two different things depending on the control.

The second is tempting for the same reason reading hover off the cursor was: one owner, nothing to
disagree with. It is also the larger change, and it collides with `form_field.rs`'s documented
rationale for the parameter — so it wants a decision rather than a patch.

## The fix

**Both, split at the line the label draws.** The observation is the second option and the holding is
the first, and neither alone works:

- The second option **cannot float the label**. `label_floats(populated, active)` decides the
  label's *type role* and tint — `Caption` floating, `Body` at rest — inside `FormField::from`,
  which runs when the field is **built**. A widget noticing focus afterwards can move an element it
  was handed; it cannot change what that element already is. Symptom 1, the one a person notices,
  is out of its reach.
- The first option **has no event to track**. iced's text input publishes nothing when it gains
  focus — that is the sentence `TextField::active`'s own doc opens with, and the reason
  `cdk/picker.rs` proxies focus with a press inside its bounds. "Each screen tracks focus" needs
  something to tell each screen.

So the field asks, and the application keeps the answer:

- **`FilledField` asks its control** whether it holds the keyboard, after every event, through the
  rendering stack's own focus traversal (`Operation::focusable`). Not from the pointer: a press in
  the 16dp padding lands on the container and not on the input, and focus also moves via Tab, a
  focus operation, or the window itself — none of which reach this widget. The answer is the input's
  own state, so there is no second opinion to disagree with, which was BUG-002's whole lesson.
- **It publishes only changes**, remembering what it last said. Asked on every event, a field that
  re-announced "still focused" on each pointer move would loop the application against itself.
- **The application holds one `Option<FieldId>`** (`State::focused_field`), not a flag per draft:
  at most one field has the keyboard, so `Option` is the shape that says so and "two fields focused"
  is unrepresentable. Cleared when a dialog opens, because the fields that reported focus are being
  torn down and will never report losing it.
- **`ui::focus::track_focus` joins the two halves in one call.** Reporting focus nobody keeps and
  being told a fact nobody reports are the same field permanently at rest; separable halves are how
  this survived two features, so there is no spelling of half of it.
- **`active` keeps meaning what it meant.** It is still supplied, and the search picker still
  supplies **open** (§7.7, FR-013). What changed is that a caller can now find out what to say.

### And the press that reached nothing

Found while fixing the above and repaired with it: a filled field's control is one 24dp value line
inside 16dp of padding, so most of a 56dp box was not the input. A click in the padding landed on a
surface that shades, hovers and looks entirely pressable, and did nothing. FR-034 asks for one
rectangle rather than two, and BUG-002 only read it in the direction the select was wrong in. A
press anywhere in the container now reaches the control — except on the adornment slots, where a
trailing icon button is an action of its own.

### The gates

The anatomy modules could not have caught this and still cannot: they build a field **with `active`
set by the test**, which proves the component obeys and says nothing about whether anything
commands it. Three new checks, at the three places the chain can break:

- `material/field_focus.rs` — the field is *driven* rather than posed: a press reports focus, a
  press in the padding reaches the input, a press on the trailing action does not, leaving reports
  the loss, and a settled field stays quiet.
- `tests/field_focus_call_sites.rs` — **every `TextField` in the application is joined up**. This is
  the check whose absence *is* the bug; it is the grep that found it, kept.
- `tests/app_state.rs` — the reducer, including the ordering case: clicking from one field straight
  to the next, where the blur of the old arrives after the focus of the new.

### Visual pass — 2026-08-09

Run under Xvfb `:77` (1600×1400) with Mesa lavapipe, driving the **application**, not the gallery:
the gallery poses its states and posing is exactly what could not see this bug. An isolated instance
— its own `XDG_RUNTIME_DIR`, `XDG_DATA_HOME` and `XDG_CONFIG_HOME` — so it took nothing over from the
session already running on this machine. The Settings dialog, whose three fields need no project.

Measured at the same column in each pair, with the pointer moved away before every capture so the
hover layer could not be mistaken for the focus one.

**Container fill** — the focus state layer, which had never once been painted:

| Scheme | At rest | Focused |
|---|---|---|
| Dark | `srgb(54,52,56)` | `srgb(71,69,73)` |
| Light | `srgb(230,225,230)` | `srgb(210,205,210)` |

**Active indicator** — §7.7's 1dp muted hairline becoming 2dp of the accent, dark since feature 018:

| Scheme | At rest | Focused |
|---|---|---|
| Dark | 1px, `srgb(202,196,207)` | **2px**, `srgb(207,188,255)` |
| Light | 1px, `srgb(73,69,78)` | **2px**, `srgb(103,80,164)` |

**The label** — symptom 1, the one a person notices. On an emptied "Timeout" field: unfocused, the
label rests centred on the value line at body size in the muted role; focused, it has floated to the
top at the caption size in the accent, **with the caret on the line beneath it**. The report's
finding was "a caret sitting immediately in front of the label text"; it now sits under a floated
label, in both schemes.

**The press that reached nothing.** The light-scheme focused capture above was produced by clicking
**12px above the value line**, inside the container's 8dp top padding — a point that did nothing at
all before. It focused the field.

Not covered, and not claimable from a screenshot pipeline: the label does not animate between its
two positions (accepted fidelity gap #4, unchanged), and lavapipe says nothing about frame pacing on
a real GPU.
