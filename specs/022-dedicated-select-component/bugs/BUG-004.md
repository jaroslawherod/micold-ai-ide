# Bug Report: a control the application has taken the keyboard from keeps answering keys

**Type**: Implementation gap
**Severity**: Medium
**Feature**: 022 — dedicated select component
**Reported**: 2026-08-10
**Status**: **Fixed** — the application's answer is authoritative where the application asked to be
told, and the control adopts it on the frame it changes.
**Fixed**: 2026-08-10

## Description

Found while checking whether [BUG-003](./BUG-003.md) still held after feature 023 landed. Not
reported from use, and no screenshot shows it — it is a disagreement between two copies of one
fact, and the copy that draws is not the copy that acts.

BUG-003 established the arrangement FR-035 needs: focus is **observed** inside the control, because
the control is the only thing that knows, and **held** by the application, because a screen has to
draw from it. The control tells the application; the application supplies it back for drawing.

That is one direction. The application had no way to tell the *control*.

## What the evidence shows

Feature 023 added `State::focus_terminal()`:

```rust
pub(crate) fn focus_terminal(&mut self) {
    self.terminal_released = false;
    self.focused_field = None;
}
```

`focused_field` is now a conjunct of `terminal_focused()` — a field holding the keyboard is exactly
what keeps the terminal from taking it — so clearing it is how navigation hands the keyboard to a
terminal (FR-008b, FR-011, FR-018).

Nothing carried that to the widget:

- the **text field**'s focus lives in the rendering stack's `text_input::State`, which drops it only
  for a press outside its own bounds;
- the **checkbox**'s lives in `TakesTheKeyboard`'s tree state, which drops it only for a press
  outside its own bounds.

So after `focus_terminal()`, a control drew itself at rest — unfloated label, hairline indicator, no
state layer — while still consuming every keystroke aimed at whatever the application believed had
the keyboard. For the text field that is typing into an invisible field; for the checkbox it is a
box toggling under a stray Space.

**Reachability today is narrow, and that is a property of the callers rather than of the design.**
Every `focus_terminal()` caller is a pointer-driven navigation message — session selected, mode
switched, shell instance opened, selected or closed — and `cdk::overlay` blocks input to everything
behind an open modal, which is the only place these controls live. The guard is real but incidental:
one asynchronous caller, or one dialog that is not modal, and the defect is live. A latent defect
with an accidental guard is still a defect.

## The fix

The application's answer is authoritative, and the control adopts it.

**On the frame it changes, not on the next event.** Frames are driven by messages; several can pass
with no input at all, so a flag that went true and back between two keystrokes would never be seen
by `update` alone. `diff` is where a rebuild can be observed, so that is where the change is
noticed. The checkbox reconciles there outright — its focus is a bool in its own tree state. The
field records the intent and spends it at the top of `update`, because taking the keyboard from the
control means running an operation over it and a diff has neither layout nor renderer; `update` runs
that before the input sees the event, which is the moment before it could matter.

**A change in the supplied flag, not a disagreement with it.** A standing disagreement is also what
an unreported focus looks like: the focus traversal both controls join can take focus without
publishing anything, and correcting every mismatch would make the traversal they were deliberately
joined to unable to focus them at all.

**Only where the caller asked to be told.** This is the design and not a shortcut. `active` means
two different things in this library: for a text field it is focus, and for a picker it is **open**
— §7.7 wants the active indicator to follow the list rather than the keyboard, and `typeahead.rs`
supplies `.active(open)` to a field whose control is a real text input. Treating the flag as
authoritative everywhere would take the keyboard out of the search picker's own input every time its
list closed. `on_focus_change` is set by exactly one thing — `ui::focus`'s `track_focus`, which sets
both halves from one fact and is held to it by `tests/field_focus_call_sites.rs` — so where it is
present, the flag *is* focus. `a_picker_that_closes_its_list_keeps_the_keyboard` is the fence around
that difference, and it is the test that would have caught the tempting version of this fix.

## Tests

Three added to `ui/material/field_focus.rs`, all driven rather than posed. They needed one new thing
from the harness — `Mounted::rebuild`, which lays a new element over the **same** tree, because "the
application changed its mind" is not an event that can be sent. It is a rebuild carrying a different
answer, and a fresh mount would lose the state under test.

- `the_application_can_take_the_keyboard_back_from_a_field` — focus it, let the application agree,
  then have it change its mind; typing must reach nothing.
- `the_application_can_take_the_keyboard_back_from_a_checkbox` — the same three frames; Space must
  toggle nothing.
- `a_picker_that_closes_its_list_keeps_the_keyboard` — a field built the way `typeahead.rs` builds
  one, `active` following open and nobody tracking focus; closing the list must leave it typing.

Both of the first two were observed failing before the fix.

## Not covered

The traversal is still one-way: `operate` can take focus without publishing, so a focus taken by a
traversal is not reported to the application and would draw at rest. Nothing in the application runs
a traversal today — the controls are *in* one so that they are reachable when something does — and
closing that is the same shape of work as this, on a path with no caller yet. Recorded rather than
quietly left, so the next person reads the gate for what it covers.
