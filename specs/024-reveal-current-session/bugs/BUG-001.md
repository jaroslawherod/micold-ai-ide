# Bug Report: the current session's name is not drawn heavier, so the mark FR-003a calls the accessible one does not exist

**Type**: Implementation gap (the type role is chosen correctly and then discarded by the widget that
draws the label; every gate that could have caught it inspects the role rather than the pixels)

**Severity**: High (FR-003a exists precisely so the mark does not depend on colour. As shipped the
mark is a container fill and nothing else, which is what that requirement forbids)

**Feature**: 024-reveal-current-session

**Reported**: 2026-08-18

**Status**: Patched

**Patched**: 2026-08-19 — spec.md (FR-003a-i, SC-005a), plan.md (the file tree now names
`ellipsized.rs`), tasks.md (T021 reopened; Phase 8, T061–T065)

**Found by**: quickstart §B2 step 1, run with the `visual-pass` skill (Xvfb :77 + lavapipe). §A was
green on the same commit, and stays green with the defect present.

## Description

`SidebarSessionCurrent` resolves to `LABEL_MEDIUM` — 12px at weight **500** — and `SidebarSession`
to `BODY_SMALL`, 12px at weight **400**. `tree_view.rs` picks the first for the selected row. On
screen the two names are the same weight.

The current row is still distinguishable, because the row is also filled with `secondary_container`.
That is the signal FR-003a was written to *supplement*, not to stand alone.

## What the evidence shows

Both labels are the same string in the same location, cropped at identical geometry — the current
session's row and its sibling one row below, at 600× magnification:
[evidence](../evidence/B2-weight-absent-both-schemes.png) (dark left, light right).

Measured rather than judged, since a weight step this small is exactly what an eye argues about.
Normalised ink area — the sum of each pixel's distance from the row's own background, divided by the
peak, which cancels the two rows' different backgrounds:

| | current | sibling | ratio |
|---|---|---|---|
| dark scheme | 185.3 | 184.8 | **1.003** |
| light scheme | 185.4 | 185.0 | **1.002** |

A 400 → 500 step adds roughly 8–15% ink area. This adds 0.3%. The glyph extents agree: both labels
are 67–68px wide with a 9px cap height in both schemes, so the letter-spacing half of the role
(0.40 → 0.50) is not arriving either.

## Root cause

`Ellipsized::at_role` keeps the size and drops everything else:

```rust
// crates/micold-client/src/ui/material/ellipsized.rs:64
pub fn at_role(content: impl Into<String>, role: TypeRole, color: Rgb) -> Self {
    Self::new(content, role.size(), color)
}
```

`Ellipsized` has no font field, and draws with `font: renderer.default_font()`
(`ellipsized.rs:128`). So a role reaches the label as a *number of pixels* and nothing else. Since
`SidebarSession` and `SidebarSessionCurrent` are deliberately the same size — the roles differ only
in weight, so that marking a session cannot reflow the list — selecting between them changes nothing
that `Ellipsized` can express.

The sidebar's session rows are drawn by `TreeView`, which pushes
`super::Ellipsized::at_role(item.label, row_label_role, item.tint)`
(`tree_view.rs:324`). `Text`, by contrast, does apply `t.role.font()` (`text.rs:289`) — which is why
the showcase's own posed pair *does* show the weight difference.

## Why no gate saw it

- `type_role_call_sites.rs` checks the call site names a role from the scale. It does.
- `type_role_mapping.rs`'s `the_current_session_row_differs_from_its_siblings_only_in_weight`
  asserts the two roles resolve to 400 and 500. They do.
- The geometry gates compare rectangles. Two labels at the same box with different weights occupy
  the same box.
- The earlier §B2 evidence (`evidence/b2-weight-greyscale.png`, 2026-08-10) was captured from
  `micold-showcase`, which poses `SidebarSession` against `SidebarSessionCurrent` through `Text`.
  That image is real and proves the *tokens* differ; it does not prove the *sidebar* differs,
  because the sidebar draws through a different widget. This is the failure mode the quickstart's
  own caveat about the showcase warns of, arriving through the door it warned about.

## Artifact Traceability

### spec.md

- **FR-003a** — "the mark must not rely on colour alone" is not met. The requirement is right; the
  implementation reaches for the one channel its drawing widget cannot carry.
- **SC-005** (greyscale identifiability) still holds, but on the container fill alone. Measured in
  greyscale: dark, current row 86 vs background 28 (hover 42) — a wide margin; light, current row
  228 vs background 244 — a 16-level step, which is thin for a mark that is now carrying the whole
  requirement by itself ([evidence](../evidence/B2-light-scheme-greyscale.png)).

### research.md

- **R4** pre-argued a fallback (an outline on the pill) if the 500 weight proved too subtle, and
  T058 says to apply it if §B judges the weight too subtle. That branch was never reached, because
  §B was not run — and the honest answer to R4's question turns out to be neither "subtle enough"
  nor "not subtle enough" but "absent".

## Recommended Fix

Give `Ellipsized` the role's font, not just its size — a `font: Font` field set from `role.font()`
in `at_role` (and `Font::DEFAULT` in `new`, so the size-only constructor is unchanged), used in
place of `renderer.default_font()` in both the layout template and `draw`.

The measurement path matters as much as the draw path: `Ellipsized` binary-searches for the
truncation point by shaping candidate strings, so a font applied to `draw` but not to the
measurement template would ellipsise at a width the glyphs no longer occupy.

Worth checking for the same shape at every other `Ellipsized` call site before fixing — the widget
whose entire job is text has, until now, had no way to say which face to draw it in.
