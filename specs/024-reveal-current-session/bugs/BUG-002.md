# Bug Report: switching to a project does not scroll the current session into view, so in a long list the row this feature exists to reveal is off screen

**Type**: Implementation gap (the reveal's expand half runs; its scroll half decides the row is
already visible, measuring it against a scroll offset the panel left in another project)

**Severity**: High (US2 and SC-003 are the geometry half of this feature. In a project with enough
worktrees to overflow the panel — SC-003 says 30 — arriving leaves the marked row below the fold,
which is the state the feature was written to remove)

**Feature**: 024-reveal-current-session

**Reported**: 2026-08-18

**Status**: **Fixed** — reproduced on screen 2026-08-20, root cause found, fixed and re-run against
the same sequence. (The report's *first* diagnosis was refuted on 2026-08-19; the cause recorded
below is the third one, and it is the one the failure actually has.)

**Found by**: quickstart §B4 step 1, run with the `visual-pass` skill (Xvfb :77 + lavapipe, 1600×1400).
Reproduced on two separate arrivals at the same project. §A was green on the same commit.

## Description

A project with 30 worktrees, its current session in the 28th. Switch to it from another project.

The sidebar renders from the top: `Default`, then `301 w01` … `319 w19` fill the panel. The row
holding the current session is roughly 1,900px further down and never comes into view. Nothing
scrolls, then or after settling — three captures across the switch and one three seconds later are
identical ([evidence](../evidence/B4-arrival-list-at-top.png)).

Scrolling down by hand shows the *other* half of the reveal did run: `328 w28` is expanded and its
session carries the mark ([evidence](../evidence/B4-marked-row-below-the-fold.png)). So the location
was opened for a session the panel never showed you.

In a short list the defect is invisible — every row fits, so the reveal has nothing to do and the
feature looks correct. That is why B1 passes in a three-worktree project on the same build.

## What the evidence shows

- **Arrival**: first capture after the click, a middle capture, and the settled frame — list pinned
  at the top in all three.
- **After scrolling by hand**: `328 w28` open, `Claude Code` filled and marked.
- The panel does stay where the user puts it afterwards (FR-010/SC-007): the sidebar is
  pixel-identical five seconds after a manual scroll. Nothing moves the list — including the thing
  that should.

## First hypothesis — refuted (2026-08-19)

The report originally proposed that `reveal_scroll` drains inside the switch's own update, so
`operation::scroll_to` is applied to a widget tree still laid out for the outgoing project's short
list and clamps to ~0. **That is not what happens.** Two independent checks:

**The runtime does not work that way.** In iced 0.14 the interface is rebuilt *and laid out* before
the actions returned by `update` are run — `iced_winit/src/lib.rs:863-899` and `1221-1249`, where
`build_user_interfaces(...)` sits between `update(...)` and the `run_action(...)` loop, and
`update()` itself collects widget operations synchronously with the comment "Run immediately
available actions synchronously (e.g. widget operations)". The tree the scroll lands on is the
incoming project's, already laid out. Even if it were stale, `State::scroll_to` stores
`Offset::Absolute(y.max(0.0))` without clamping to content bounds (`iced_widget/src/scrollable.rs:1843`);
clamping happens per-frame at read time, so a too-large offset would survive into the next layout
rather than being lost.

**The instrumented run disagrees too.** Client patched to log what the drain computes and what the
scrollable reports back (`SidebarScrolled` already carries the real offset), run on Xvfb :77 +
lavapipe at 1600×1400 against a purpose-built project of 30 worktrees:

```
reveal_scroll: armed=1 viewport_h=1277 listed=true scroll_offset=0 offset=Some(607)
reveal_scroll: DRAINED, scrolling to 607
SidebarScrolled: the scrollable reports offset 607
```

The drain fires, computes a non-zero offset, and the scrollable ends up at exactly that offset. The
row is on screen in the settled frame.

## What the reproduction attempt found instead

Four arrivals were driven, all with the panel scrolled to the top before switching away:

| Fixture | Row shape | Computed | Scrollable reported | Row on screen |
|---|---|---|---|---|
| 30 worktrees, session in w27 | one-line | 111 | 111 | yes |
| same, panel left mid-list | one-line | `None` (already visible) | — | yes |
| 30 tagged worktrees, session in w28 | two-line | 607 | 607 | yes |
| same, after restarting the client | two-line | 607 | 607 | yes |

The computed offsets match the rendered geometry exactly. One-line rows resolve to
`density::height(56, DENSE)` = 44dp and `ROW_GAP` = 4, a 48px pitch — and the render measures 48px.
Tagged rows resolve to 60 + 4 = 64, and the render measures 64. So `row_heights` is not drifting
from what is drawn, in either row shape.

**So this bug does not reproduce as written, and its stated cause is wrong.** What was observed on
2026-08-18 was real — the evidence images show a marked row below the fold on a list that did not
move — but the mechanism has not been identified, and the fixture that produced it no longer exists.
The 2026-08-18 fixture differed in ways not yet ruled out: sessions were real `claude` processes, in
several worktrees rather than one, and B4 ran after B1/B3 in the same instance rather than from a
clean arrival.

One candidate the reading turned up and the runs did not exercise: `set_current_session`
(`features/session.rs:141`) returns early when `active_session == next`, so a switch that restores
the session already marked neither expands nor arms. Whether any real switch reaches that arm is
unverified — in every arrival driven here the ids differed and the reveal armed correctly.

**Status is therefore Open with the diagnosis withdrawn, not Open with a diagnosis waiting to be
implemented.** Fixing the mechanism described above would have changed nothing.

## Root cause — found (2026-08-20)

**Reproduced, on screen, in the 30-worktree fixture.** The ingredient every earlier attempt was
missing is in plain sight in their own traces: all of them read `scroll_offset=0`. With a zero there
the arithmetic *cannot* produce a false "already visible", so no fixture that starts at the top can
ever fail. The 2026-08-18 pass ran B1 and B3 first — steps that scroll the panel by hand — and that
is the difference.

### The mechanism

`State::sidebar_scroll_offset` is a **mirror** of where the scrollable is. Its only writer is
`Message::SidebarScrolled` (`app.rs`), which the rendering stack publishes from `notify_viewport` —
and `notify_viewport` returns **without publishing** when the content fits its viewport
(`iced_widget-0.14.2/src/scrollable.rs:1592-1597`):

```rust
if content_bounds.width <= bounds.width
    && content_bounds.height <= bounds.height
{
    return false;
}
```

So a reveal that runs in a project whose sidebar *fits* — the short project you pass through on the
way somewhere — issues `scroll_to`, moves the list, and is never told. The mirror keeps the offset of
the project before it. On the next arrival the drain measures the row against a position the panel is
nowhere near, `scroll_target` finds it inside `[offset, offset + viewport]`, returns `None`, and
`reveal_scroll` consumes the arm under FR-009 without issuing anything. Nothing re-arms, so nothing
scrolls, then or ever.

That is precisely the reported symptom, and it explains the half that made the report look
contradictory: the *expand* is state, so it happens; the *scroll* is the only half that depends on
the mirror.

### The reproduction

A `MICOLD_REVEAL_TRACE` build (added by this bugfix — see [Files](#files)), Xvfb :91 + lavapipe,
1600×1400, `~/.aa-big` (30 tagged worktrees) and `~/.aa-small` (1). Sessions in the deepest row of
`aa-big` and in `aa-small`. Then: scroll `aa-big` to the bottom, and switch back and forth.

```
reveal: current session Some(2166…) -> Some(68c2…), arming=true
reveal: geometry: row 2 of 3 spans 112..156, content 156, viewport 1278, offset 734
reveal: drained: viewport_h=1278 scroll_offset=734 -> scrolling to 0     <- aa-small: moves the list
                                                                        <- and is never told: the
                                                                        <- content fits, so no
                                                                        <- SidebarScrolled follows
reveal: current session Some(68c2…) -> Some(2166…), arming=true
reveal: geometry: row 31 of 32 spans 1968..2012, content 2012, viewport 1278, offset 734
reveal: drained: viewport_h=1278 scroll_offset=734 -> no scroll, the row is already visible (FR-009)
reveal: the scrollable reports offset 0                                  <- where the list *actually* was
```

The last two lines are the bug in two lines: the drain declined to scroll because the row lies inside
`[734, 2012]`, and the panel was at `0`. On screen: the list pinned at the top showing `Default`,
`101 w01` … `123 w23`, the first frame after the click and the settled frame **pixel-identical**
(`compare -metric AE` = 0), and the marked, expanded row 1,968px below the fold — reached only by
scrolling by hand. The same two images as 2026-08-18.

### Why the earlier attempts passed

Not because the fixtures were wrong, but because each began with the panel at the top. Attempts one
to three varied session count, arrival order, row shape and the filter — every ingredient except the
one that matters, which is a non-zero mirror at the moment of arrival. A short project passed through
between two long ones is what makes the mirror stale, and nothing in §B tells you to do that.

## The fix

**A drained reveal records where it sent the list, instead of waiting to be told.**

```rust
app.core.sidebar_scroll_offset = offset;
```

One line in `reveal_scroll` (`main.rs`), before the operation is returned. `offset` has already been
clamped into this list's own scrollable range by `scroll_target`, so it is the position the panel
will hold whether or not a notification follows. The mirror stops being a thing the application only
learns second-hand about its own actions.

Three alternatives were considered and rejected:

- **Clear the mirror on a project switch.** It would fix this arrival and break the FR-009 case it is
  there to serve: a switch that lands on a row already on screen would then scroll for nothing,
  because the drain would believe the list is at the top when it is not.
- **Clamp the mirror to the content height before comparing.** Does nothing here — the stale `734`
  *is* the outgoing list's legal maximum, so clamping leaves it unchanged.
- **Re-arm when the reported offset contradicts the mirror.** Repairs the state one frame after the
  wrong decision has already been taken, and only when a report arrives — which in the failing case
  is exactly what does not happen.

Regression: `a_drained_reveal_records_where_it_sent_the_list` (`main.rs`). It builds the state the
short project leaves behind — one location, a tall viewport, and an offset inherited from a longer
list — drains a reveal, and asserts the mirror is what the reveal asked for. It fails on the
unfixed code with `left: 734, right: 0`.

Verified on screen the same way it was reproduced, same fixture, same sequence:

```
reveal: geometry: row 31 of 32 spans 1968..2012, content 2012, viewport 1277, offset 0
reveal: drained: viewport_h=1277 scroll_offset=0 -> scrolling to 735
reveal: the scrollable reports offset 734
```

The panel arrives at the bottom of the list with the deepest row expanded, marked and fully visible
([evidence](../evidence/B4-fixed-arrival-scrolls-to-the-row.png)) — where the trace on the unfixed
build read `scroll_offset=734 -> no scroll` and the list stayed at `0`.

### The trace is now part of the client

The two `eprintln!`s that answered the original question had been patched in and deleted, which is
why the question cost a build every time it was asked. They are back as
`micold_client::reveal_trace`, behind `MICOLD_REVEAL_TRACE` — silent unless the variable is set to
something other than `0`, and reporting arming, the drain's inputs, its decision, the row geometry
and what the scrollable reports back. It is what found this, and re-finding it without the trace
would have meant guessing again.

## Files

- `crates/micold-client/src/main.rs` — `reveal_scroll`, the drain. **Where the fix is**, and where
  the regression test lives.
- `crates/micold-client/src/reveal_trace.rs` — the `MICOLD_REVEAL_TRACE` trace, added here.
- `crates/micold-client/src/app.rs` — the `SidebarScrolled` arm: the mirror's only other writer.
- `crates/micold-client/src/features/sidebar.rs` — `reveal_scroll_offset` and `scroll_target`; the
  arithmetic is correct, and was never the problem. Its `current_offset` argument was.
- `crates/micold-client/src/features/session.rs` — `set_current_session`, which arms the reveal.
- `crates/micold-client/src/shell/workspace.rs` — the switch path.
- `iced_widget-0.14.2/src/scrollable.rs:1592-1597` — `notify_viewport`'s early return, the reason the
  mirror can go stale at all. Not ours to change; the fix is to stop depending on it.
