# Bug Report: switching to a project does not scroll the current session into view, so in a long list the row this feature exists to reveal is off screen

**Type**: Implementation gap (the reveal's expand half runs; its scroll half is issued against a
widget tree that still holds the outgoing project's list)

**Severity**: High (US2 and SC-003 are the geometry half of this feature. In a project with enough
worktrees to overflow the panel — SC-003 says 30 — arriving leaves the marked row below the fold,
which is the state the feature was written to remove)

**Feature**: 024-reveal-current-session

**Reported**: 2026-08-18

**Status**: Open

**Found by**: quickstart §B4 step 1, run with the `visual-pass` skill (Xvfb :77 + lavapipe, 1600×1400).
Reproduced on two separate arrivals at the same project. §A was green on the same commit.

## Description

A project with 30 worktrees, its current session in the 28th. Switch to it from another project.

The sidebar renders from the top: `Default`, then `301 w01` … `319 w19` fill the panel. The row
holding the current session is roughly 1,900px further down and never comes into view. Nothing
scrolls, then or after settling — three captures across the switch and one three seconds later are
identical ([evidence](../evidence/B4-arrival-list-at-top.png)).

Scrolling down by hand shows the *other* half of the reveal did run: `328 w28` is expanded and its
session carries the mark ([evidence](../evidence/B4-marked-row-below-the-fold.png)). So the location
was opened for a session the panel never showed you.

In a short list the defect is invisible — every row fits, so the reveal has nothing to do and the
feature looks correct. That is why B1 passes in a three-worktree project on the same build.

## What the evidence shows

- **Arrival**: first capture after the click, a middle capture, and the settled frame — list pinned
  at the top in all three.
- **After scrolling by hand**: `328 w28` open, `Claude Code` filled and marked.
- The panel does stay where the user puts it afterwards (FR-010/SC-007): the sidebar is
  pixel-identical five seconds after a manual scroll. Nothing moves the list — including the thing
  that should.

## Root cause (hypothesis, not yet confirmed)

`reveal_scroll` (`main.rs:432`) drains an armed reveal after every message, guarded on three
conditions: something armed, a non-zero viewport height, and the projection holding a row for the
current session. On a project switch all three are satisfiable within the switch's own update, because
`on_known_project_reopened` discovers the incoming project's worktrees **synchronously**
(`shell/workspace.rs:143` → `set_worktrees(discover_worktrees(...))`) before the update returns. So
the drain fires with state already describing the new, long list.

The widget tree does not. `iced::widget::operation::scroll_to` is applied to the scrollable as it was
laid out for the *previous* frame — the outgoing project's short list, whose content barely exceeds
the viewport. An absolute offset of ~1,900px against that content clamps to approximately zero, the
arm is cleared (`main.rs:439`, before the offset is even computed), and the next frame lays out the
new long list at offset 0. The reveal has been spent on a list that no longer exists.

That would explain the whole shape of the observation: the expand half is state
(`expanded.insert(dir)` in `set_current_session`) and survives into the new frame; the scroll half is
an operation against a stale tree and does not. And it predicts what §A cannot see — `scroll_target`
is arithmetic and correct, tested directly in `tests/sidebar_tree.rs`; the defect is *when* its answer
is delivered.

Not confirmed. Confirming it means logging the offset the drain computes on a switch and comparing it
with the offset the scrollable ends up at, which no test in the repository can currently observe.

## Recommended Fix

Defer the scroll operation by one frame rather than issuing it inside the switch's own update — the
drain should wait until the tree it is addressing has been laid out with the new list, not merely
until state describes one. Whatever the mechanism (a follow-up message, or a viewport-height report
from the new list as the trigger), the invariant to hold is the one already written down in the
drain's own doc comment: *the arm survives all three conditions failing*. Clearing
`pending_reveal_scroll` before `reveal_scroll_offset()` has produced an offset that the tree can
honour is what turns a deferred reveal into a lost one.

A regression test that would have caught it has to observe the scrollable's resulting offset, not the
computed target. If that is out of reach for the test harness, then this path stays quickstart §B's
job — and §B has to actually run, in a project large enough to scroll.
