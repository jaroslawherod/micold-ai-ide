# Bug Report: the restored session's terminal says "Starting…" about a session that is not starting

**Type**: Spec gap
**Severity**: Medium
**Feature**: 025 — last-session memory
**Reported**: 2026-08-14
**Status**: **Fixed** — the empty state answers from the same predicate that decides whether the
`restart` control exists, so the body and the bar cannot disagree.
**Patched**: 2026-08-14
**Fixed**: 2026-08-14

## Description

Found while running quickstart §B2 (see [quickstart.md](../quickstart.md), *Found while running
this*). Not reported from use — §B2 is the step that puts a restored, not-running session in front
of you and then asks you to look at it, which is the only reason anybody looked.

Reopen the application on a project whose remembered session is not running — the common case, since
run state is not persisted (spec Assumptions). The main terminal area renders a muted **`Starting…`**
and stays that way indefinitely. One row below it, the status bar reads **`interrupted`** and offers
**`restart`**. No process exists.

The two disagree, and the placeholder is the one that is wrong: nothing is starting, nothing will
start, and the user is being told to wait for an event that will never arrive. The control that
*would* make it true is the `restart` button sitting beside the contradicting text.

Left half of [the B2 evidence image](../evidence/B2-restore-starts-nothing.png). The right half is
the same session state reached by clicking, where the placeholder is briefly honest.

## What the evidence shows

The placeholder is the `grid: None` arm of the terminal pane:

```rust
// crates/micold-client/src/ui/terminal.rs:356
None => container(Text::new("Starting…", TypeRole::Caption, r).muted())
```

`grid` is `App::attached_grid()` — a lookup into `grids: HashMap<SessionId, GridCache>`
(`main.rs:73`). That map is populated in exactly one place, `Message::DaemonGridFrame`
(`main.rs:868`), and it is initialised empty at launch (`shell/startup.rs:155`). Nothing persists it.

So a session with no running process produces no frame, gets no cache entry, and renders the
placeholder **permanently** — not for a frame or two while something spins up. Observed still
reading `Starting…` twelve seconds after launch, with zero `claude` processes in the sandbox.

The disagreement is structural rather than a timing artefact. The bar's own predicate already names
the states in which the body is wrong:

```rust
// same file — `attached_process_restartable`, FR-013 of feature 006
SessionLifecycle::Idle | SessionLifecycle::Failed | SessionLifecycle::InterruptedResumable
```

Those three are exactly "not running". For every one of them the bar offers `restart` while the body
claims the session is starting. And the truthful vocabulary is already written, one function away —
`session_status` maps `Starting` to `"starting…"`, `Idle` to `"idle"`, `InterruptedResumable` to
`"interrupted"`. The pane has `state` and `active` in hand and could ask the same question; it does
not ask.

**Reachability before this feature was near zero, and that is a property of the callers rather than
of the placeholder.** At launch no session was current, so the pane took its *other* empty state
("Select or start a session to open its terminal.") and this branch was unreachable. The only other
route to a current session — selecting one in the sidebar — **starts** it: the lifecycle moves to
`Starting`, so the placeholder tells the truth for the second or two before the first frame lands.
Verified during §B2: clicking an interrupted session spawned one `claude --resume` within seconds
and filled the pane with output.

This feature is what changes that. FR-002 makes a session current at launch, FR-004 forbids starting
it, and the spec's own Assumptions note that "the common case at launch is restoring a session that
is not running". The three together make a permanently-wrong placeholder the **first thing most
users see**, on the launch path this feature exists to create. The branch is old; the reachability
is new.

## Artifact Traceability

### spec.md

- **Affected user story**: US1 — *Reopen where I left off*.
- **Affected requirements**:
  - **FR-012** — "The restored session MUST be presented exactly as a session made current by any
    other means". This is the requirement in tension, and it cannot be met literally: a session made
    current by any other means is *running*, because that route starts it. A restored one is not, so
    the two cannot present identically. FR-012's own qualifier scopes the promise to the side panel
    ("so the user cannot tell **from the panel** how they arrived at it"), and the panel is correct —
    the row is revealed and marked exactly as a switch leaves it. The main area was never covered.
  - **FR-004** — restoring starts nothing. Correct, and *upheld*: the defect is that the UI says
    otherwise. The clearest statement of the bug is that the screen contradicts FR-004 while the code
    obeys it.
  - **Assumptions** — "Session run state across restarts. Not persisted... It is the reason the
    common case at launch is restoring a session that is not running." The spec anticipated the
    state exactly and drew no conclusion about what to render for it.
- **Gap identified**: the spec settles which session is current (FR-002), that nothing is started
  (FR-004), and how the *panel* presents it (FR-012, §4.1–4.2). Nothing anywhere in spec, contract,
  or data model says what the **main terminal area** shows for a restored session with no output.
  The area inherited a placeholder written under an assumption this feature invalidates.

### plan.md / contracts

- **Affected section**: `contracts/last-session-memory.md` §4, *How the restored session is
  presented*. Both clauses are about the side panel (§4.1 reveal, §4.2 no "restored" styling). §5,
  *What this contract does not cover*, lists three exclusions and this is not among them — so it is
  a gap in coverage rather than a deliberate omission.
- **Impact**: §4 needs a clause for the main area: a session that is not running must not be
  described as starting. Cheapest correct form is that the empty state reads the session's lifecycle
  and says the same thing the status bar already says.

### tasks.md

- **Affected tasks**: none is wrong. **T010** (§4.1/FR-012 — applying a memory arms the reveal) and
  **T017** (documenting reopening) are the two nearest, and both are about the panel and the docs
  rather than the terminal area.
- **False completions**: none. No task claimed the main area, so no task overclaimed.
- **Missing tasks**: one — make the terminal pane's empty state truthful for a session that is not
  running, with a test that a restored, not-running session does not render `Starting…`.

## Root Cause Analysis

A spec oversight of a specific and unglamorous kind: the feature reasoned carefully about the two
things that were *changing* — which session is current, and whether anything is started — and did not
ask what the screen already said about the state those two combine to produce.

The placeholder itself is not a mistake. It was written for feature 006 when `grid: None` had one
meaning, and it named that meaning correctly. What it encodes is an assumption — *no grid implies a
process is on its way* — which held for every caller that existed until this feature added one for
which it does not.

`session_status` shows the same information being handled correctly a few lines away, which is the
strongest evidence this is an oversight rather than a decision: nobody weighed the two and chose. The
pane was simply never revisited when a new way to have no grid arrived.

Worth recording because the *class* recurs: a shared empty state whose wording quietly asserts a
cause, and a later feature that reaches it by a different one. The wording is the load-bearing part,
and it is invisible in a diff that adds no UI.

## Recommended Fix

Make the empty state say what is true, from information the view already has. `pane()` holds `state`
and `active`, so it can consult the session's lifecycle exactly as `session_status` does one function
below — `Starting`/`Restarting` keep `Starting…`; `Idle`, `Failed` and `InterruptedResumable` say
something that matches the bar and, ideally, points at the `restart` control already on screen.

Deliberately *not* recommended: suppressing the placeholder, or having the restore populate an empty
grid. The first trades a wrong message for a blank rectangle that explains nothing; the second would
have the client fabricate terminal state for a process that never ran, which is the sort of lie that
outlives the person who wrote it.

Not urgent enough to reopen the feature, and it changes no requirement already met — FR-004 is
upheld, and this is about the sentence describing it. Severity is **Medium** rather than High
because no incorrect action is invited and the truthful status is adjacent and visible; the argument
for High is that it is the first screen on the feature's own primary path, and a reader who disagrees
with the grade is not wrong.

## The fix

`empty_terminal_message` is now the one place that decides what an empty terminal says, and it
answers from **`attached_process_restartable`** rather than from a second match on
`SessionLifecycle`.

That choice is the point. The predicate already means "the attached process is not running", already
handles the `TerminalMode` split, and is already what decides whether the `restart` control is there
to be pointed at. Deriving the body and the bar from one function is what makes them *unable* to
disagree — they disagreed for exactly as long as they were two readings of one fact, and a second
`match` would have restored that arrangement while fixing today's symptom.

The recommended-against options above were both declined as recommended.

## Tests

Two layers, because either alone leaves a hole.

Three unit tests in `ui/terminal.rs` drive the function over every lifecycle:

- `a_session_that_is_not_running_is_not_described_as_starting` — the three `attached_process_
  restartable` names, driven separately, since a fix keyed to `InterruptedResumable` alone would
  pass a single-case test.
- `a_session_that_is_starting_still_says_so` — the other half, without which the first passes on a
  blank string. FR-014 asks the wording to *distinguish* the two, not to stop mentioning starting.
- `the_empty_state_and_the_restart_control_never_disagree` — asserts the guarantee directly:
  exactly one of "the bar offers restart" and "the body claims to be starting" is true of any
  session. A future lifecycle added to one is added to the other.

`tests/terminal_empty_state.rs` is a source-level gate, because the unit tests drive the function
directly and cannot see whether the pane still *calls* it. **Mutation-verified**: reverting the pane
to the literal leaves all three unit tests green and fails both gates. Follows
`tests/terminal_bar_stability.rs` under Principle I's GUI-wiring exception.

The **layout snapshot** also caught it unprompted, and was accepted deliberately: the covered state
`session-terminal-bottom-bar` is built from `Session::restored` with no shell started — precisely
this bug's state — and its centred label is 332px wide now that it says something.

## Confirmed on screen

Re-ran §B2's conditions in the isolated sandbox: client and daemon both stopped (0 `micold`, 0
`claude`), then launched. The restored session reads *"This session is not running. Choose restart
below to resume it."*, the bar beside it reads `interrupted`, and the process count stays 0.
[Before and after](../evidence/BUG-001-before-after.png).

Pressing `restart` then started the session and filled the pane with real output — so the control
the message points at does what the message says.

**Not confirmed on screen**: the `Starting…` frame itself. The restart produced output inside a
second, and a screenshot pipeline cannot reliably catch a chosen sub-second frame. That case is
covered by `a_session_that_is_starting_still_says_so` instead, and is called out here rather than
left to look like it was checked.
