# Bug Report: Reopening returns you to the session but not to work

**Type**: Spec conflict

**Severity**: High

**Feature**: 025-last-session-memory

**Reported**: 2026-08-14

**Status**: **Fixed** — the restored session is resumed at both seams that reach it (`DaemonConnected`
at launch, `switch_daemon_attachment` on a switch), so reopening lands on a session that works
rather than on the shape of one.

**Fixed**: 2026-08-14 — Phase 9 (T039–T042). Confirmed by quickstart §B2, re-run by two
independent sandboxes on the same commit, and its FR-014 half on 2026-08-16.

**Patched**: 2026-08-14 — FR-004 → FR-004a, SC-005 → SC-005a; FR-014/SC-008 (BUG-001) retained for
the residual case. Fix in `main.rs`'s `DaemonConnected` arm and `shell/daemon_sync.rs`'s
`switch_daemon_attachment`.

## Description

Reopening the application lands on the remembered session — the row is marked, the location is open,
the terminal has the keyboard — and the session does not work. Nothing is running in it, and nothing
will be until the user presses `restart`. The user's report was that the restored session was "stuck
at starting", and that "only after switching to a different session and switching back makes it work
correct".

[BUG-001](./BUG-001.md) addressed the first half of that sentence: the pane said `Starting…` about a
session nothing was starting, and now says what is true. **This is the second half.** Switching away
and back works because selecting a session *starts* it — so the user's own workaround is the
specification of the fix.

## Root cause

Deciding which session to display and asking the daemon to run it are two halves of one act, and only
one path performed the second:

| Path | Sends |
|---|---|
| Launch (`DaemonConnected`, `main.rs`) | `Attach` + `SetViewedSession` |
| Project switch (`switch_daemon_attachment`, `shell/daemon_sync.rs`) | `Attach` + `SetViewedSession` |
| Hand-selection (`view_and_start`, `main.rs`) | `SessionResize` + **`SessionStart`** + `SetViewedSession` |

`restore_after_activation` — the function both restore paths call — is *client state only*: it
resolves the memory, applies it via `set_current_session`, reveals the row and takes the keyboard. It
says nothing to the daemon. And `SetViewedSession` opens a view stream only for a session the daemon
is hosting (`state.rs`'s `live_session` / `session_framer` read the live map), which after a restart
is none of them — durable sessions reload as `InterruptedResumable`.

So the restore produced a current session the daemon had no process for, could not stream, and had
not been asked to start.

## Artifact Traceability

### spec.md

- **Affected user story**: US1 — Pick up where I left off (P1). Scenario 3 is the one that fails in
  substance: you are returned to the session, and cannot use it.
- **The conflict**:
  - **FR-003** — "…and matching what selecting the session by hand does."
  - **FR-004** — "Restoring a session MUST NOT start, resume, or otherwise change any process."

  Selecting a session by hand resumes it. `Message::SessionSelected` calls `view_and_start`, whose
  own comment reads "resuming it if idle". The two requirements therefore describe opposite
  behaviours for the same act, and both were implemented faithfully — FR-004 by the code, FR-003 by
  everything except the part that mattered. Neither gate could see it, because each requirement was
  individually satisfied.
- **Resolution**: FR-003 wins. FR-004 → **FR-004a** (restoring resumes, at every seam, bounded to
  the one session displayed). SC-005 → **SC-005a** (exactly one process, never a fan-out).
- **Retained**: FR-014 and SC-008 from BUG-001. The resume removes the *ordinary* path into the
  empty pane but not the residual one — a start the daemon refuses because the project is held by
  another window or is unavailable. That case is rarer and less expected, so the pane telling the
  truth matters more rather than less.

### plan.md / research.md

- **research R5** concluded that reusing `restore_after_activation` from `boot()` "costs nothing",
  having audited the three things the function *does* to client state. The audit was over effects;
  the gap was in its silence toward the daemon.
- **research R4**, one section earlier, enumerates the four `SetViewedSession` call sites and names
  `view_and_start` as "what runs when a session is selected" — the very distinction R5 needed. R4
  was answering who *records* the memory, R5 who *applies* it, and the two were never read against
  each other. Nothing was under-researched; two adjacent findings were never compared.
- **plan.md** claimed the launch path was "binary glue" under Principle I's GUI exception, on the
  grounds that the decision (*which* session) lives in the tested reducer. What the client then
  sends is a second decision, made in `DaemonConnected`, and it was covered by nothing.

### tasks.md

- **T011** — "applying a memory **starts nothing**". Passed, and encoded the superseded rule.
  Rewritten rather than deleted: it still holds that the *reducer* moves no lifecycle (the resume is
  a `SessionStart` to the daemon, and a client that set `Starting` itself would render a running
  session with no process behind it — BUG-001's lie from the other direction), and it still guards
  the one-session bound.
- **T015/T016** — applied the memory at launch, correctly and incompletely.

## Why two bugs, not one

BUG-001 and BUG-002 were reported from the same screen and fixed independently. They are not
duplicates:

- **BUG-001** is about what the interface *says*. A session with no process must not claim to be
  starting. That requirement outlives this fix.
- **BUG-002** is about what the application *does*. A restored session should not need a click to
  become usable.

Fixing only BUG-001 leaves a truthful screen and the click. Fixing only BUG-002 leaves the ordinary
path working and the refused-resume path lying. Both were wanted.

## Recommended Fix

Route both restore seams through `view_and_start` rather than adding a third copy of its sends: it
already orders the pane size before the start (BUG-003, `006` FR-014a) and the view after, and a
start naming an already-running session is a no-op on the daemon, so a switch onto a live session
costs nothing.
