# Bug Report: An unavailable default offers the other CLIs without ever saying why

**Type**: Requirement shortfall
**Severity**: Low
**Feature**: 026 — multi-provider AI CLI sessions
**Reported**: 2026-08-27
**Status**: **Fixed** 2026-08-27 — T090, T091 (`ac186f3`)

## Description

Store GitHub Copilot as the default AI CLI, then take `copilot` off `PATH` and press the sidebar's
`+` on a worktree row. The CLI list opens, nothing starts, and the stored default is left alone —
three correct behaviours out of four. The fourth is missing: nothing tells the user that the CLI
they chose is not installed.

What they see is the list they would have got from the secondary control. A user who pressed the
primary half expecting one press to start a session gets a menu instead, with no reason given.

FR-002 and FR-004 scenario 4 ask for both halves of the sentence — say the default is unavailable
*and* offer what is. What ships is the second half.

## Reproduction status

**Observed 2026-08-25** during the T084 §B pass, on Xvfb `:91` + lavapipe with Copilot CLI 1.0.80,
and recorded in `quickstart.md`'s B7 row as a "wording gap" rather than filed. This report is that
row, filed — the §B pass's other four findings each became a task (T086–T089) and were fixed; this
one was left in the table.

Reproducible at the reducer level with no display: `State::start_intent(PressTarget::Primary)` on a
state whose `default_ai_cli` is not in `available_providers`.

## Mechanism

`features/session.rs::start_intent` collapses two different presses into one answer:

```rust
PressTarget::Primary if self.default_ai_cli_is_available() => StartIntent::Start(...),
// The default names a CLI that is not installed: say so and offer what is.
PressTarget::Primary => StartIntent::OfferChoice(self.offered_providers()),
PressTarget::Secondary => StartIntent::OfferChoice(self.offered_providers()),
```

The comment states the requirement; the value does not carry it. `ui/sidebar.rs:391` then maps every
`OfferChoice` to the same `Message::SessionStartMenuOpened(location)`, so by the time anything can
draw, the reason the list opened is gone. A surface downstream cannot say what it was never told.

## Why the suite is green

`crates/micold-client/tests/features_session.rs::an_unavailable_default_offers_the_choice_rather_than_starting_or_substituting`
names, in its own comment, the three wrong answers it exists to rule out — substituting silently,
doing nothing, and starting a binary that is not there — and asserts against all three. It asserts
nothing about telling the user, because `StartIntent` has nothing to assert on.

This is the same shape as T089's finding, where `tests/session_start_press.rs` could not see a menu
opening at the window origin because its assertion was `SessionStartMenuAnchored(_)`. A gate that
covers three of four clauses reads as covering the requirement.

## Fix

Done as suggested, with the two questions the suggestion left open answered by where the reducer
sits rather than by the view.

`StartIntent::OfferChoice` became `{ providers, unavailable_default: Option<AiCli> }` — the CLI, not
a bool, because the sentence names it and the name has to come from the same read that decided it
was missing. `Message::SessionStartMenuOpened` gained the same field, and carries it to
`start_menu_toggled`, which pushes `micold-core`'s notification queue when it fires.

Two rules that the shape does not make obvious:

- **The press says why it happened; the reducer decides whether that is still true.** The binary
  re-probes `PATH` on this very message (research R11's "when the choice is offered"), so the press's
  reason is stale by one event. `start_menu_toggled` re-checks it against the refreshed set, and a
  default that turned out to be installed says nothing.
- **Only an opening says it.** The same press closes an open list, and a user dismissing one does not
  need to be told why it appeared.

The sentence is the daemon's FR-010 wording verbatim — *"GitHub Copilot isn't installed. Install it,
or start this session on another AI CLI."* — because it is the same fact about the same CLI, said one
step earlier by the side that can tell before launching anything.

The chevron's site in `ui/sidebar.rs` passes `None` explicitly, and that is a statement rather than a
behaviour: with two providers, a chevron exists only when both are installed (FR-006), so a stored
default cannot be missing on a press that draws one. Were it ever reachable, the reducer's re-check
would silence it anyway. It is written out so the third provider does not inherit a banner on every
override open.

## Suggested fix (as filed)

Distinguish the two presses — an `OfferChoice { providers, because_default_is_missing: bool }`, or a
second variant — and, on the missing-default arm, push the sentence onto the notification queue that
T088 built for exactly this kind of message (`micold-core/src/notify.rs`, drawn as a
`material::Snackbar` from `ui/mod.rs`). T088's own reasoning applies unchanged: it is the one surface
that is unconditional and can carry a sentence.

Then widen the test above by one assertion, so the fourth clause is gated like the other three.

## Gate

`crates/micold-client/tests/unavailable_default_says_so.rs`, six tests, driving the real reducer and
draining its outcomes the way `State::update` does. Probed on `ac186f3` by removing each behaviour in
turn and running `cargo test -p micold-client --all-targets --no-fail-fast`: the announcement, the
closing guard, the availability re-check and the chevron's `None` each fail their own tests and
nothing else — 1435 pass with one binary red in the first three, 1407 with two in the fourth.

`tests/features_session.rs::an_unavailable_default_offers_the_choice_rather_than_starting_or_substituting`
— the gate that read as covering the requirement — is widened by the fourth clause, so the shape that
let this ship is closed where it happened.

## Was not blocking

Filed against a closed feature the way 001, 002, 003, 006 and 008 record theirs. Nothing was lost or
misreported — the default survived, no substitution happened, and every available CLI was one press
away. The user was left to infer the reason.
