# Bug Report: After a restart, a dead session reference stays in the list

**Type**: Requirement shortfall (a state the spec left undefined: what happens to the row after a refused resume)
**Severity**: Medium
**Feature**: 026 — multi-provider AI CLI sessions
**Reported**: 2026-11-10 (issue #1795)
**Status**: **Open**, fix tasks T092–T098
**Related**: #1794 (`/clear`, restart restores the pre-clear conversation)

## Description

After a restart the sidebar shows a session that is not running and cannot be started; the user
removes it by hand. Acceptance: after a restart no listed session is neither running nor startable;
an unresumable one is cleaned up automatically; a regression test covers the restart case.

## Reproduction status

**No repro** of the exact report. Reproduced at the daemon level only for one producer of the shape:
`start_session_gated` refuses a resume with `conversation_gone_text` (FR-008, FR-010 route) and
leaves the `InterruptedResumable` row in the catalog, with the reason only in `start_failures`. The
row is shown, refuses every later start for the same reason, and blocks the location's
`start_offered`. Other producers (startup, after `/clear`, #1794) are unconfirmed.

## Root cause (partial)

026 FR-008/FR-010 and the edge case "A Copilot session whose store entry was removed" specify the
refusal ("report, start nothing") and say nothing about the row afterwards. The implementation (T050a,
T087) kept it. A row whose conversation is gone can never be started, so it is the dead reference.
At startup, `present_interrupted_resumable` marks only sessions with a recorded conversation; a used
session whose conversation is gone stays `Idle` and is not removed.

## Decision (decided by user)

> "I would like that changes are persistent and will not disapear. I don't want users to see warning
> and need to manually remove sessions that build a bad user experiance"

So: no warning row, no manual removal, no "Remove" action, no new wire message, no protocol bump.
The daemon removes a session whose conversation is gone, on its own, at startup and at the
start-time check, persists the removal, and logs the reason only. (Earlier options "Remove button"
and "wire notice" are rejected.)

## Patch

- spec 026: edge case reworded; FR-008 gets a pointer to new **FR-008a**; `contracts/copilot-cli.md` line 77 reworded.
- spec 943: User Story scenario 7 reworded (old text struck through).
- `docs/user-guide/worktrees-and-sessions.md`: the two statements that a gone conversation "fails as
  a failed resume" / "terminal says Pi no longer has it".
- tasks.md: T092–T098 (7 tasks, one milestone). T046/T050a/T087 are not reopened: their refusal and error report stay true, only the row's fate afterwards is new (FR-008a).
- T094 also covers the crash-restart path (#1459), a second producer of the same row. T098 supersedes 029 FR-008 / 032 invariant 4 (a `Named`/`Derived` row is never removed when its transcript is deleted), which the startup removal contradicts; flagged as a consequence of the user's decision.

## False completions

T050a/T087 are ticked and correct for what they say; their gap is that no task owned the row after
the refusal. T046 asserted the refusal, and no test asserted the row's fate or a restart.

## Evidence / risks for the fix

- Startup evidence of "used" is the label (`Derived`/`Named`): a session with a turn has a
  transcript, so its absence means gone. A `Pending` session is never removed. An unresolvable
  config dir is not gone.
- Archive path persists (`archive_session_ids`) and writes the provider's durable marker (FR-015),
  so a removed session is not rediscovered (FR-014).
- Lifecycle `Failed` is not persisted (`Session.lifecycle`), so after a restart rows are `Idle` or
  `InterruptedResumable` only; T095 audits that every such row can start.
