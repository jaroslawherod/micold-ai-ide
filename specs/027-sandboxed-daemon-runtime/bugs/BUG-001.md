# Bug Report: Save reverts a theme chosen from the app bar while Settings is open

**Type**: Implementation drift
**Severity**: Medium
**Feature**: 027 — sandboxed daemon runtime
**Reported**: 2026-08-27
**Status**: **Fixed** — the app bar's theme controls now carry their choice into an open draft;
gated by `crates/micold-client/tests/settings_draft_tracks_the_live_theme.rs`.

## Description

With the Settings view open, change the theme from the app bar's overflow menu. The theme changes
immediately, as it always has. Then press **Save**.

The theme reverts to what it was when the view was opened.

Nothing reports this. The user's most recent choice — made seconds earlier, visibly applied — is
undone by a button labelled Save, and the control that undid it is not on the section they were
looking at.

## Reproduction status

**Observed twice** during the T075 visual pass on 2026-08-26 (Xvfb + lavapipe), recorded under
*Observation* in `evidence/us3-settings-view.md` and left unfiled there because no FR covers it.

**Reproduced at the reducer level, 2026-08-27**, which is where the mechanism is legible and where
the regression test now lives. `Message::ThemeModeCycled` against a `State` holding a draft seeded
from `theme_pref`: `theme_pref` advances, the draft's `appearance.theme` does not, and
`SettingsDraft::validate().theme` — the exact value Save writes back — still holds the old one.

## Mechanism

The theme is the only setting in this application with **two writers**:

- the app bar's overflow menu (`theme_mode_cycled`, `theme_preference_changed`), which applies its
  choice to `State::theme_pref` immediately, and
- the Appearance section (`settings::theme_changed`), which writes a *draft* applied on Save and
  discarded on Cancel.

The draft is seeded from `theme_pref` when the view opens (`shell/persist.rs::on_settings_opened`)
and never re-read. `on_settings_saved` then assigns `app.core.theme_pref = valid.theme`, and
`ValidSettings::theme` is `draft.appearance.theme` — the value from opening time. So the save path
writes a stale copy over a newer live one.

## It is a regression from this feature

Two writers were harmless before. Settings was a 420dp **modal**, which covered the app bar, so the
menu could not be reached while the form was open and the draft could not go stale. FR-026 made
Settings a full-surface view with the app bar still on screen — which is the point of the change —
and that is what makes both writers reachable at once.

The drift is therefore in this feature, not in feature 003's theme menu or feature 006's draft.

## Fix

`features/settings.rs::apply_theme`, called by both app-bar entry points: set `theme_pref`, and if a
draft exists set `draft.appearance.theme` too. A change made outside the form is *newer* than the
draft, so the draft takes it.

Two things it deliberately does not do:

- **It does not stop drafting the theme.** Cancel must still discard an Appearance edit, so the
  Appearance section keeps writing the draft alone.
- **It does not go through `edit()`.** That helper clears `draft.error`, which is right for the user
  editing the form and wrong here: a theme picked from the app bar is not them acting on the form,
  and clearing the error would empty the message FR-029 sends them to the offending section to read.

## Tests

`crates/micold-client/tests/settings_draft_tracks_the_live_theme.rs`, four rules:

| Rule | What it would catch |
|---|---|
| `cycling_the_theme_from_the_app_bar_is_what_save_then_writes` | the bug itself |
| `choosing_a_theme_outright_is_what_save_then_writes` | a fix applied to the cycle only, leaving `ThemePreferenceChanged` reachable |
| `an_appearance_edit_is_still_only_a_draft_until_save` | "fixing" it by applying the theme live, which would leave Cancel nothing to discard |
| `the_menu_still_works_with_settings_closed` | tracking a value into a form that is not open |

Both failing rules were confirmed red against the unfixed reducer before the fix landed, and all
four are green after it.
