# Bug Report: The sidebar's CLI-override chevron is missing until Settings is opened

**Type**: Implementation drift
**Severity**: High
**Feature**: 027 — sandboxed daemon runtime (regression against 026 — multi-provider AI CLI sessions)
**Reported**: 2026-08-28
**Status**: **Fixed** — `on_connected` now asks after it installs the outbox; gated by
`crates/micold-client/src/main.rs::tests::connecting_asks_which_clis_the_service_can_run`, which was
confirmed red against the unfixed order (it read `Sent instead: [Attach, SetViewedSession]` — the
outbox working, the availability request absent).
**Patched**: 2026-08-28 — 027 FR-023c clarified, 026 FR-006 clarified, plan's gate-sufficiency claim
corrected, T144 reopened and closed again, Phase 16 added (T157 gate, T158 fix).

## Description

User-reported: *"the select of ai cli at side bar tree view — sometimes it's not visible and it's
shown only after changing the default cli at settings."*

On a freshly launched client with two AI CLIs installed, the split affordance in the worktree row's
hover cluster renders as a plain `+`. Its secondary half — the chevron that opens "start a session
on a different AI CLI" (026 FR-004) — is absent. Opening the Settings view makes it appear, and it
then stays for the rest of the run.

The chevron's visibility is `State::start_affordance_offers_a_choice()`
(`crates/micold-client/src/features/session.rs:1549`), which is `known_available().len() >= 2`.
`known_available()` reads `available_providers: Option<CliAvailability>` and treats `None` — "the
service has not said yet" — as the empty set. So the control is absent for as long as the field is
`None`, and the field is `None` from launch until some event asks the service and the reply lands.

A second symptom shares the root cause and is worse than the missing chevron. While the field is
`None`, `State::start_intent` (`features/session.rs:1560`) short-circuits to
`StartIntent::NothingAvailable`, so pressing the `+` starts the stored default unconditionally. When
that default is not installed, 026 FR-002 requires the application to *say so and offer what is
available, starting nothing*; instead the launch goes to the daemon and comes back as FR-010's
missing-CLI failure. The user gets the dead end FR-002 was written to remove.

## Root cause

`shell/daemon_sync.rs::on_connected` asks for the availability set **before** it installs the
outbox the ask needs:

- `crates/micold-client/src/shell/daemon_sync.rs:790` — `ask_cli_availability(app);`
- `crates/micold-client/src/shell/daemon_sync.rs:827` — `app.daemon = Some(outbox);`

`ask_cli_availability` (`daemon_sync.rs:315`) opens with `let Some(d) = app.daemon.clone() else {
return; }` — documented as "a no-op while disconnected, deliberately". At line 790 that guard is
always taken: `app.daemon` is `None` on a first connect, and `on_disconnected`
(`daemon_sync.rs:226`) sets it back to `None`, so it is `None` on every reconnect too. The
connect-time request is never sent. The comment 37 lines below the failing call states the rule the
call violates: *"`app.daemon` is assigned before the sends, not after, because `view_and_start`
below reads it (BUG-002 [of 010])."*

The remaining two ask sites are intact, which is what makes the symptom intermittent rather than
total:

- `shell/persist.rs:142` — Settings overlay opened. **Reachable**, and the only recovery.
- `main.rs:637` — the override menu opened. **Unreachable in this state**: the chevron that opens
  that menu is the control being hidden, and the primary half cannot open the list either, because
  `start_intent` returns `NothingAvailable` before reaching the offer branch.

So the two refresh points 026 research R11 calls "when the choice is offered" collapse to one, and
the run recovers only if the user visits Settings for unrelated reasons. "Changing the default CLI"
is incidental — merely *opening* the view is what fixes it.

- **Affected requirement**: **FR-023c** — "Whether an AI CLI is available MUST be determined where
  sessions run". The determination is correctly *sited* (daemon-side, `available_here()`); it is the
  client's asking that does not happen on connect, so the answer never arrives.
- **Gap identified**: none in the requirement's wording. FR-023c is right and the implementation
  drifted from it.

### spec.md — 026 (what the user sees broken)

- **Affected user story**: US1 — choosing which AI CLI a session runs on, from the sidebar.
- **Affected requirements**:
  - **FR-004** — the per-session override "MUST be a distinct, adjacent secondary control". It is
    absent on a fresh run despite two CLIs being installed.
  - **FR-006** — the override control is to be absent "when fewer than two CLIs are available".

    nothing started. Defeated while the field is `None` (see Description).
- **Affected success criterion**: SC-001's click budget is not violated, but its counterpart — the
  override reachable in one extra interaction — is unreachable at any cost until Settings is opened.

## Root Cause Analysis

An ordering error introduced when 027 T144 replaced a synchronous local answer with an asynchronous
remote one. Before 027, availability was `Capabilities::available_providers()` — a `PATH` walk the
client performed itself, correct at the moment it was called and therefore insensitive to *where* in
`on_connected` it ran. T144 turned it into a request over a handle that `on_connected` had not yet
stored, and the call kept its position in the function while its precondition changed underneath it.

Two things kept it invisible:

1. `ask_cli_availability`'s early return is a legitimate, documented behaviour for the disconnected
   case. At line 790 it silently converts a required refresh into a no-op with no log line and no
   `None`-vs-empty distinction reaching the view.
2. On a development machine every CLI is installed and Settings is opened constantly, so the field
   is populated early in almost every session by the one path that still works — the same "the
   developer's machine hides it" failure mode that
   `cli_availability_comes_from_the_service.rs`'s own header describes for the bug it was written
   to prevent.

## Recommended Fix

Direction (not applied — this command reports only): move `ask_cli_availability(app)` below
`app.daemon = Some(outbox)` in `on_connected`, and gate it with a test that connects and asserts the
request appears on the connection's outbox. Consider also whether `None` should be distinguishable
from "the service answered: none" at the two sidebar decision points, as it already is in the
Settings sentence FR-023b needs — the chevron currently cannot tell "not asked yet" from "one CLI".
