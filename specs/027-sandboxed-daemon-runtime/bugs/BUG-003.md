# Bug Report: Choosing "In a container" saves the choice and does nothing else

**Type**: Implementation drift (with a planning gap as its cause)
**Severity**: High
**Feature**: 027 — sandboxed daemon runtime
**Reported**: 2026-09-03
**Status**: **Fixed** — a save that moves the placement now asks first, and confirming moves the
running service; gated by `crates/micold-client/tests/saving_a_placement_moves_the_daemon.rs`,
`crates/micold-client/tests/settings_reports_the_live_placement.rs`, and the T162 block in
`crates/micold-client/src/main.rs`.
**Patched**: 2026-09-03
**Fixed**: 2026-09-12

## Description

In Settings → Session service, set **Where sessions run** to *In a container* and press **Save**.

The view closes. The note under the select already reads "Currently in a container." The session
service is still the host process it was a moment ago, every session is still unconfined, and
nothing says so. Sessions keep running, the connection banner stays quiet, and the only thing that
actually happened is a line written to the settings file.

The user's report: *"I've selected container as current runtime but nothing has changed. It should
trigger a restart of daemon and switch to container based runtime."*

It is not inert forever — the next launch of the application reads the placement out of the store
(`shell/startup.rs:158`) and does come up sandboxed. But the placement is the one setting in this
form whose whole point is *where the agent can reach*, and the gap between choosing it and it being
true is a window in which the user believes they are contained and is not.

## Artifact Traceability

### spec.md

- **Affected user story**: **US1 — The agent can only touch the project** (P1). Its opening
  sentence is the scenario that does not happen: *"A developer turns on sandboxed mode, **confirms
  the restart**, and carries on working."* There is no confirmation and no restart.
- **Affected requirements**:
  - **FR-032** — *"A setting whose change requires the service to restart MUST say so before the
    change is applied, and the restart MUST require explicit confirmation."* Not implemented. The
    select's supporting text says "Takes effect the next time the application starts", which is a
    different promise: it defers the restart instead of confirming one, and FR-032's "before the
    change is applied" is not satisfied by a static hint that is equally present when nothing is
    being changed.
  - **FR-033** — *"Switching placement while sessions are running MUST warn that running processes
    are stopped and sessions become resumable, and MUST require explicit confirmation."* Not
    implemented at all; no such warning exists anywhere in the client.
  - **FR-035b** (secondary) — the placement select's note renders `draft.daemon.placement`, so it
    reads "Currently in a container." from the moment of selection, over a host process, before and
    after Save. FR-035b exists precisely so *"a user cannot mistake an unconfined session for a
    contained one"*; here the settings view asserts the mistake.
- **Gap identified**: none in spec.md. FR-032 and FR-033 state the requirement correctly. The spec
  is the only artifact in the chain that got this right.

### plan.md / data-model.md

- **Affected section**: `data-model.md` §7, *"`SandboxState` — the lifecycle (FR-032 … FR-036,
  SC-004)"*.
- **The mis-citation**: that heading claims a range starting at FR-032, but the lifecycle
  requirements are FR-034 – FR-036. FR-032 and FR-033 are settings-change requirements and belong
  to the Settings surface (FR-026 – FR-033), not to `SandboxState`. Rule **S-1** then cites FR-032
  for *"`Acquiring` reports continuous progress"* — which is **SC-004**, cited alongside it in the
  same rule. FR-033 is cited nowhere in any design artifact.
- **Impact**: §7's traceability row (`SandboxState | FR-032 – FR-036, SC-004`) is what makes both
  requirements *look* covered. They are covered by a state machine that does not implement either
  of them.

### tasks.md

- **Affected tasks**: none — and that is the finding. `grep -n 'FR-032\|FR-033'` over the whole of
  `tasks.md` returns nothing. 115 tasks, and neither requirement produced one.
- **False completions**: **T070** — *"Build the daemon section … placement, runtime, image, and the
  sandbox controls … (FR-027)"*, marked `[X]`. It built the control that sets the value. Nothing in
  its scope makes the value act, and nothing downstream of it does either, so the section is
  complete against FR-027 and silently incomplete against FR-032/FR-033.
- **Missing tasks** (to be written by `/speckit.bugfix.patch`):
  1. Confirmation before a placement change is applied, naming what a restart costs (FR-032), and
     the running-session warning when sessions exist (FR-033).
  2. Apply the confirmed change on save: move `app.placement.kind`, build the `BootPlan` the host
     placement does not have, and run the bring-up.
  3. Correct the "Currently …" note to render the *live* placement rather than the draft (FR-035b).
  4. A reducer-level test that a save changing the placement produces the bring-up, and one that a
     save not changing it produces nothing.

  **Written as Phase 16, T159–T166** (2026-09-03). One correction to this section as filed: T070 was
  **annotated, not reopened**. Listing it under *False completions* overstated it — T070 built the
  control FR-027 asked for and built it correctly. What is missing is a task that was never written,
  and reopening the section that renders the form would have scheduled the wrong work.

## Mechanism

`shell/persist.rs::on_settings_saved` handles every field it owns — theme, scrollback, the
environment include, the default AI CLI — writes the `Settings` to the store, sends `SettingsSet`
to a connected daemon, and finishes with exactly one non-value step: `survival_step`, for the
logout opt-in. **The placement is not among them.** It goes into `settings` and into the file, and
the function returns.

What would have to move, and does not:

- `app.placement` is set once, at boot, in `shell/startup.rs:182`. The connection subscription is
  `Subscription::run_with(placement, …)` (`daemon.rs:119`), so its identity *is* the placement —
  assigning a new one tears the connection down and re-dials. That mechanism works and is already
  used twice, by `SandboxMsg::RestartRequested` and `SandboxMsg::FallbackAccepted`
  (`shell/sandbox.rs:366`, `:385`). The save path is the third caller that should exist and does
  not.
- `app.sandbox_boot` — the `BootPlan` — is built at startup only when the stored placement is
  already `LocalSandbox` (`shell/startup.rs:198`). A user switching *into* the sandbox therefore has
  no plan to boot even if a save dispatched `RestartRequested`, which is why this cannot be fixed by
  re-sending an existing message.
- `Sandbox::for_placement` (`features/sandbox.rs:231`) maps `LocalSandbox` to `Probing`, which is
  §7's `Disabled → Probing` edge labelled *"user enables"*. Nothing dispatches that edge from
  Settings. The state machine has the transition; the form has no wire to it.

## Root Cause Analysis

A design-artifact mis-citation, not an implementation oversight.

FR-032 and FR-033 were written correctly in the spec and then absorbed into `data-model.md` §7's
requirement range for `SandboxState`, where the section is about container lifecycle and its S-rules
are about failure, fallback and visibility. Once §7's traceability row read `FR-032 – FR-036`, both
requirements were accounted for on paper. `/speckit.tasks` generates from the design artifacts, so
it generated the lifecycle tasks (T099–T108, all citing FR-034/FR-035) and nothing for the two
requirements that had been quietly folded in. `SandboxState` is also the one entity in §7's table
with no contract file — *"client-side; covered by quickstart Part B"* — so the automated gate that
might have caught the omission was, by construction, a human reading a checklist.

The UI's supporting text is the tell. Someone building T070 knew the change did not take effect and
wrote "Takes effect the next time the application starts" — an accurate description of the code and
an undeclared narrowing of FR-032, recorded in a string rather than raised against the spec.

## Workaround

Choose the placement, save, and **restart the application**. `shell/startup.rs` reads the stored
placement and brings the sandbox up from there.

## Fix

Four changes, in the order the save now runs:

1. **`features/settings.rs`** — `placement_step(in_force, saved)`, the same "act on a change, and
   only on a change" shape `persist.rs::survival_step` already had, plus the three messages that
   carry the question and its answer and a `pending_placement` field to hold it while it is open.
   `placement_in_force` is the comparison basis rather than the stored value, because an accepted
   FR-035a fallback leaves the file saying container while the host is running — re-saving
   container should then legitimately ask again.
2. **`ui/confirm_placement.rs`** + a registration — the question itself, a `FloatingSurface` like
   the rest of the `confirm_*` family, so Escape and the scrim reach the same reducer Cancel does
   and none of the three can leave a half-applied save behind.
3. **`shell/persist.rs`** — `on_settings_saved` split into `validated_draft` / `apply_save`, with
   `on_placement_change_confirmed` performing the deferred save *and* `apply_placement`: the
   placement assigned (which is what re-dials the subscription), the outgoing container stopped,
   the sandbox state reset, and the `BootPlan` built from the settings just saved — a user moving
   *into* the sandbox has none from `startup.rs`, which is why an assignment alone could never have
   been the fix.
4. **`ui/settings/daemon.rs`** — the note reads the placement in force instead of the draft, and
   the select's "Takes effect the next time the application starts" is gone. That string was an
   accurate description of the code and an undeclared narrowing of FR-032; FR-033a no longer
   permits what it promised.
