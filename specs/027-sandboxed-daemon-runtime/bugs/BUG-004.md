# Bug Report: The settings rail snaps between its widths instead of sliding

**Type**: Scope gap: new behaviour, not a defect against this spec
**Severity**: Low
**Feature**: 027 — sandboxed daemon runtime
**Reported**: 2026-09-14
**Status**: Routed to [030-settings-rail-slide](../../030-settings-rail-slide/spec.md). No patch to this spec
**Routed**: 2026-09-14

## Description

Open Settings and press **Collapse** under the rail's destinations. The rail goes from its labelled
288px width to its 80px icon width in a single frame, and every line of the section beside it jumps
208px to the left. Expanding it jumps them back.

The user's report: *"the settings side bar should be animated. it should has the hide and show
animation similar like the worktrees tree view"*. The worktree sidebar is the reference: hiding it
slides its panel shut over `motion::duration::MEDIUM_4` and the content beside it follows, and
showing it slides it open again (`ui/material/navigation_drawer.rs`).

Reproduced on `origin/main` (9275a357) by a test that mounts the real settings surface, flips
`settings_rail_collapsed`, pumps redraws the way the runtime does and records where the page beside
the rail starts on each frame. That position is 80.0 on the first frame after collapsing and 288.0
on the first frame after expanding: there is no frame in between.

## Why this is not a bug in 027

**US3 scenario 7** and **FR-026c** name the rail's two states and nothing about moving between them.
The code does what they say. Nothing else in the feature asked for motion either:

- The drawer comment in `settings_view.rs` claims a slide only for *opening* Settings ("the rail
  slides in with the view"). It then keeps collapse apart from that slide: *"collapsing the rail
  (FR-026c) is not the same thing … it is answered by `SectionList`, and the drawer stays open in
  both states."*
- `plan.md` names `NavigationDrawer` only as a component to reuse, and its collapse bullet makes the
  width gates "one width when expanded, one when collapsed".
- Feature 018's motion contract (§6.3) assigns tokens to the animations that existed then and has no
  row for a rail changing width.

So a sliding collapse is a new requirement, and the bug path's rubric sends new behaviour to a spec
of its own. A first attempt patched FR-026f into this spec. A fresh review rejected it for this
reason, and the patch was withdrawn before it merged.

## Defects found on the way (in 027, carried by 030)

- **The drawer never moves.** `settings_view.rs` builds it `.open(true)` with an empty `Space` as
  its closed child. A drawer mounts at its destination
  (`a_drawer_starts_at_its_destination_rather_than_animating_to_it`), so the slide its comment
  describes, the rail sliding in with the view, has never happened. The wrapper does nothing. T066
  asked for it and is done as written. Feature 030 specifies the rail's motion; removing the wrapper
  is left to its plan.

## Root cause of the snap

`SectionList` (`ui/material/section_list.rs`) is stateless. Its `Element` conversion reads
`collapsed` and returns a container of `Length::Fixed(RAIL_WIDTH)` or
`Length::Fixed(RAIL_WIDTH_COLLAPSED)`, with rows built for that state. A rebuilt view is a different
layout, and iced lays it out at once. Nothing holds the fact that the rail was 288px a frame ago.
