# Bug Report: Switching to container mode leaves the client dialling a sandbox nobody starts

**Type**: Spec gap (with implementation drift underneath it)
**Severity**: High
**Feature**: 027 — sandboxed daemon runtime
**Reported**: 2026-09-12
**Status**: Patched
**Patched**: 2026-09-12

## Description

Switch **Where sessions run** to *In a container*. The client stops talking to the host daemon and
starts dialling `127.0.0.1:7727`, where nothing is listening. It says so, once a second, for as long
as the application is open, and nothing ever starts the service it is dialling.

The user's report: *"when switching to container mode it fails as daemon in container is not
started — it should be automatically started by micold application when not running."*

That last clause is the requirement, and it is the one the host placement already has and the
sandboxed placement does not. `daemon.rs::connect_and_pump` is where the asymmetry is stated
outright:

- `PlacementKind::HostProcess` → `connect_or_spawn(endpoint, …)`. Nothing listening means *start
  one*, on every attempt of the reconnect loop, for the life of the process.
- `PlacementKind::LocalSandbox` → `connect_at(…)`, and on `Ok(None)` an error reading *"no sandboxed
  daemon is listening on 127.0.0.1:7727"*. The comment above it is accurate about what it must not
  do (FR-035 forbids falling back to a host process) and silent about what it should do instead.

So under the sandboxed placement the bring-up has exactly three triggers, all of them one-shot:

| Trigger | Where |
|---|---|
| The application launches with the placement already stored | `shell/startup.rs:307` |
| A save moves the placement, confirmed | `shell/persist.rs:391` (BUG-003's fix) |
| The user presses **Restart** | `shell/sandbox.rs` — `Msg::RestartRequested` |

Every other way of ending up with a sandboxed placement and no running container is terminal until a
person intervenes: a bring-up that failed once, a container stopped from the host or lost to a
`docker` restart, a host reboot with survive-logout off while the app stays open, and — the case
below — a bring-up that is still in flight while the connection actor is already calling it a
failure.

## Reproduction

Reproduced from this machine's own state on 2026-09-12, by inspection rather than under the visual
pass.

| Claim | Evidence |
|---|---|
| The client dialled the sandbox and never reached it | `~/.local/share/micold-ai-ide/micold-client.log` — `attach: connected projects=3 sessions=19 active=…/micold-ai-ide` followed immediately by ~90 unbroken `attach: failed reason=no sandboxed daemon is listening on 127.0.0.1:7727` / `attach: disconnected` pairs |
| Nothing ever created the container | `docker ps -a` has no `micold-sandbox`; the daemon inside one could not have been started because there was none |
| A bring-up did get as far as `create` at some point | `docker network ls` still holds `micold-sandbox-net`, which `CliRuntime::create` makes before the container — so the leftover is from an earlier, differently-configured run |
| The image the settings name is not on this machine | settings say `ghcr.io/jaroslawherod/micold-daemon:0.12.1`; `docker images` has only `:0.12.0` and `micold-daemon:dev` |
| …but it *is* published, so the bring-up's next step was a ~384 MiB pull | `docker manifest inspect ghcr.io/jaroslawherod/micold-daemon:0.12.1` exits 0 unauthenticated |

## Artifact Traceability

### spec.md

- **Affected user story**: **US6 — The service survives, and its failures are legible** (P2). Its
  scenario 4 — *"the sandbox is not running, and launching the application starts it"* — is the only
  place the spec says the application starts a sandbox it finds down, and it says it of a launch.
- **Affected requirements**:
  - **FR-014a** — *"With it off, the sandbox starts when the application launches."* Covers the
    launch and nothing after it. The host placement's equivalent behaviour is not scoped to a launch
    at all, because `connect_or_spawn` is on the reconnect path; nothing in the spec notices that
    the two placements are being promised different things.
  - **FR-036** — *"The application MUST detect a sandbox that has been stopped or removed outside
    the application, report it, and recover to a defined state."* Detection and reporting are
    implemented (`check_alive`, `container_lost`). The defined state it recovers *to* is
    `Failed(SandboxStopped)`, whose only exit is a human pressing Restart — and `check_alive` is
    only asked on a disconnect when `accepts_sessions()` already holds (`daemon_sync.rs:286`), so a
    sandbox that never came up is never even asked about.
  - **FR-035** — forbids falling back to an unsandboxed service on its own, and is the requirement
    the `LocalSandbox` dial arm cites. It forbids the wrong recovery without requiring the right
    one; retrying the *sandbox* is not a fallback and nothing in FR-035 stands against it.
  - **SC-004** — *"First-time enablement … completes within 5 minutes and shows continuous progress
    throughout, so the user never has to guess whether the application has stopped responding."*
    Violated in the app, though not in the core — see the drift below.
- **Gap identified**: no requirement states that under a sandboxed placement the application brings
  the sandbox up whenever it finds no service listening — the property `connect_or_spawn` gives the
  host placement unconditionally. FR-014a scopes it to a launch, FR-036 stops at "report", and
  R9's *"nothing restarts on its own"* (data-model §7) was written about a **running** sandbox the
  user might not want interrupted, then inherited by a sandbox that is not running at all, where the
  argument for it does not hold.

### plan.md / data-model.md / contracts

- **Affected section**: `data-model.md` §7 — `SandboxState`, and rule **R9**. R9's marker type
  `RestartRequested` deliberately makes "a person asked" a property of the type rather than of a
  caller. That is right for `Running → Probing` and wrong for `Failed → Probing` and for a
  `Disabled`/`Probing` state that has never had a container: the type currently cannot express
  "re-attempt a bring-up that never succeeded" without a person.
- **Affected obligation**: `contracts/container-runtime.md` **C-8** — *"Progress is reported during
  acquisition … five silent minutes reads as a hang."* The contract binds `acquire_image`, which
  honours it. Nothing binds the application to *pass the callback on*, and it does not.
- **Impact**: §7 needs an edge into bring-up that carries no human in its signature, with its own
  guard (a backoff, and a bound on attempts) so that adding it does not turn a broken runtime into a
  loop; and C-8's obligation needs a client-side counterpart, or a note that the app is the second
  half of it.

### tasks.md

- **Affected tasks**:
  - **T041** — *"…the off-thread runtime calls, **progress** and failure-to-`Message` glue in
    `crates/micold-client/src/shell/sandbox.rs`"*, marked `[X]`. The failure-to-`Message` glue is
    there; the progress glue is not. `boot()` passes `&mut |_| {}` and says so in a comment: *"a
    `Task::future` yields one message, and threading a channel through boot for the sake of the
    first release's progress bar would buy less than the settings view (US3) will"*. That is the
    same shape as BUG-003's *"Takes effect the next time the application starts"* — a known
    narrowing of a requirement, recorded next to the code rather than raised against the spec.
  - **T043** — *"Show `StageProgress` during image acquisition in `crates/micold-client/src/ui/`,
    **driven by the T039 callbacks** (SC-004)"*, marked `[X]`. `ui/sandbox_status.rs` is complete and
    correct — it renders `Probing`, `Acquiring(progress)` and `Starting` and tests its wording. It
    is driven by nothing: T041 dropped the callbacks it names, so the only stage it can ever show is
    the `Probing` that `Sandbox::for_placement` sets, frozen there for the whole bring-up.
  - **T117** — *"Measure SC-004 — first-time enable under 5 minutes with continuous progress"*,
    marked `[x]`. Measured in `micold-core` against `acquire_image` directly, which is why it passes
    over a defect in the client: `evidence/performance.md` records the clock covering *"the
    application's whole enable sequence"* when what it covers is the core's. The same file is
    already candid that the continuity half is *"barely exercised"*.
  - **T045** — records **§B.1 (first enable, cold, through the GUI)** as outstanding and says it
    *"depends on T043's progress indicator to be meaningful"*. §B.1 is exactly this bug's flow, and
    it is the one check in the feature that would have caught both halves.
- **False completions**: T041 and T043 against SC-004/C-8 (each built its own half of a link that
  was never joined). T117 measures the claim somewhere the defect cannot appear. **T070** is *not*
  implicated this time; BUG-003's own correction about annotating rather than reopening applies here
  to T043, whose view needs no edit at all.
- **Missing tasks**: no task anywhere covers bringing the sandbox up other than at boot, at a
  placement change, and on a Restart press. `grep -n 'connect_or_spawn' tasks.md` returns nothing.

## Mechanism

Two defects, and the second is what makes the first read as "it fails" rather than "it is slow".

**1. Nothing re-attempts the bring-up.** `on_connect_failed` (`daemon_sync.rs:292`) logs the reason
and raises a notification. It does not consult `app.sandbox_boot`, which holds the `BootPlan` that
`shell::sandbox::boot` needs and which is populated for every sandboxed placement. The reconnect
loop backs off one second and dials again, forever. For the host placement the identical situation
is resolved inside `connect_or_spawn` before `on_connect_failed` is ever reached.

**2. The bring-up is invisible while it runs, and the dial failure is not.** `boot()` discards every
`observe` call, so `app.sandbox.state` stays on the `Probing` that `Sandbox::for_placement` set until
the whole sequence ends in `Started` or `Failed`. During a first enable that is a probe, a ~384 MiB
registry pull, a create and a start — minutes — and for all of it the application shows *"Checking
the container runtime"*, while `on_connect_failed` posts *"Could not connect to the session daemon:
no sandboxed daemon is listening on 127.0.0.1:7727"* once a second. A bring-up that is working looks
identical to one that has failed, and louder.

The `Probing` freeze has a second consequence: `accepts_sessions()` is false for `Probing`, so the
disconnect handler's `check_alive` never fires, and `container_lost` returns `None` for `Probing`
anyway. The FR-036 machinery is inert for the entire window in which the user is looking at the
problem.

## Root Cause Analysis

FR-002 and FR-014a were written from the sandbox's side: the host placement was the thing that
already worked, so what it *did* for itself — `connect_or_spawn`, auto-starting the service whenever
nothing answers — was never written down as a requirement, and therefore was never carried across to
the placement being added. FR-003 made placement a resolved choice at connect time; nothing made the
*guarantees* of a placement a checklist that a new one has to satisfy. The one guarantee the spec
did carry over, FR-014a, it carried scoped to a launch, because that is the wording US6 scenario 4
happened to use about a reboot.

R9 then closed the door from the other side. *"Nothing restarts on its own"* is a good rule about a
running container full of the user's sessions, and `RestartRequested` makes it structural. Applied
to a container that does not exist it protects nothing and only removes the recovery — and because
it is enforced by a type, the gap looks deliberate at every call site.

The progress half is a plainer omission: T039 built the callbacks, T043 built the view, T041's
comment traded the wire between them for a smaller diff, and the only test of the claim (T117) was
written below the level where the wire is missing.

## Impact

A user who switches to container mode sees the application lose its session service and report a
connection failure indefinitely. Their sessions are not lost — the host daemon is still running and
its state directory is shared — but nothing in the application says so, and the documented way out
(pick the placement again and restart the app) is the same one BUG-003 was filed about.

## Workaround

Press **Restart** on the sandbox banner if one is showing, or restart the application: `startup.rs`
dispatches a bring-up for a stored sandboxed placement. On a first enable, wait — a registry pull of
the image takes minutes and the application will say nothing about it until it finishes.

## Recommended Fix

1. Run `/speckit.bugfix.patch` to:
   - add the requirement the gap names — under a sandboxed placement, the application brings the
     sandbox up when it finds no service listening, with a bounded retry and a reported reason, and
     without ever satisfying it by starting a host process (FR-035 stands);
   - give `data-model.md` §7 an edge into bring-up that does not require a person, with its guard
     stated, and narrow R9 to the running sandbox it was written about;
   - give C-8 a client-side counterpart, or state that the app is the other half of it;
   - append tasks for: the re-attempt on connect failure; passing `observe` through `boot` so
     `Acquiring`/`Starting` reach `ui/sandbox_status.rs`; suppressing or subordinating the
     connection banner while a bring-up is in flight; and logging the bring-up's stages and failures
     to `micold-client.log`, which today records nothing about them.
2. Run `/speckit.bugfix.verify`.
3. Resume `/speckit.implement`. The first test to write is at the reducer, as in BUG-001 and
   BUG-003: a connect failure under a sandboxed placement with a `BootPlan` in hand produces a
   bring-up task, and the same failure under a host placement produces none.
