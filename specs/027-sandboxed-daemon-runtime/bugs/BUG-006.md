# Bug Report: Claude sessions in the sandbox cannot write their session files

**Type**: Spec conflict (with implementation drift underneath it)
**Severity**: High
**Feature**: 027-sandboxed-daemon-runtime (branch `fix/running-in-sandbox-can-t-store-sessions`)
**Reported**: 2026-09-18
**Status**: Patched
**Patched**: 2026-09-18

## Description

A `claude` session started while the service runs in the sandbox shows a warning at startup: the
session files are available read-only, and state will be lost once `claude` restarts. The session
itself runs, but it cannot record its conversation. The loss surfaces later, when the user restarts
the application or the session and the conversation is not there to resume.

Observed with the AI CLI authentication opt-in (`CredentialShare::AiCliAuth`) enabled. This is the
configuration a user ends up in: without that opt-in, `claude` inside the sandbox is not logged in.

### Mechanism

1. `CredentialLayout::conventional` (`crates/micold-core/src/sandbox/mod.rs:509`) defines the AI CLI
   authentication material as the whole `~/.claude` directory.
2. `mount_args` (`crates/micold-core/src/sandbox/argv.rs:220-225`) mounts every credential `:ro`,
   "without exception", at its own absolute path. That path is under the sandbox's `HOME`, so it
   shadows `<state>/sandbox-home/.claude`.
3. `claude` keeps more than authentication in `~/.claude`. It also keeps its conversation
   transcripts (`projects/<encoded-cwd>/*.jsonl`), history, todos, and shell snapshots, and it
   rewrites `.credentials.json` itself whenever it refreshes the OAuth token. All of those writes
   fail against a read-only mount. `claude` detects this and prints the warning.
4. The client's boot prune (`prune_empty_sessions`, `crates/micold-client/src/shell/persist.rs:82`)
   keeps a session only if `ClaudeProvider::has_recorded_conversation` finds a transcript under the
   **host's** `~/.claude/projects/`. A sandboxed session never writes a transcript there, so the
   prune drops the session on the next launch as "never used". Resume (`claude --resume <id>`) has
   nothing to resume either.

Suspected, not yet verified: the same boot-prune loss happens *without* the opt-in. In that case
`claude` writes its transcripts to the sandbox's own home (`<state>/sandbox-home/.claude`), which the
host-side prune never reads.

### Other AI CLIs (Copilot, Pi)

The read-only warning is `claude`-only. `CredentialLayout` maps `AiCliAuth` to `~/.claude` and
nothing else, so no opt-in exists for `~/.copilot` or `~/.pi/agent`. Those CLIs write their state
into the sandbox's own writable home, so they get no warning. They also cannot log in with the host's
authentication, which is a separate gap: FR-004a offers an AI CLI authentication share that covers
only one CLI.

The boot-prune half of this bug is not `claude`-only. `CopilotProvider::config_dir` and
`PiProvider::config_dir` (`crates/micold-core/src/provider.rs:595-600`, `:925`) resolve against the
**host** home, just as `ClaudeProvider` does. A sandboxed Copilot or Pi session records its
conversation under `<state>/sandbox-home/`, which the host-side prune never reads. This is suspected
to drop those sessions on the next launch too. The same real-runtime test should cover all three
CLIs.

## Artifact Traceability

### spec.md

- **Affected user story**: User Story 2 — "The service keeps its promises inside the box" (P1).
  Scenario 1 (sessions re-attach after the app is closed) and scenario 3 (sessions are offered as
  resumable after the sandbox is recreated) both depend on the conversation being recorded.
  User Story 1, scenario 6 (credential opt-ins) is where the configuration comes from.
- **Affected requirements**:
  - **FR-009**: "persistence and resumption across application and machine restarts ... MUST behave
    equivalently when sandboxed". Violated: a sandboxed `claude` session cannot persist its
    conversation, and the boot prune discards it.
  - **FR-004 / FR-004a / FR-004b**: the AI CLI authentication opt-in is specified only as a
    credential share. Nothing says what "the AI CLI's own authentication material" is. The
    implementation takes it to be all of `~/.claude`, which for `claude` is authentication *and*
    session state.
  - **FR-004d**: gives the sandbox a writable home so that `~` writes succeed "without ... requiring
    a credential opt-in". The spec does not say what happens when a credential opt-in is mounted
    *inside* that home and makes part of it read-only again.
  - **FR-023a**: says "shipping a CLI is not shipping an authenticated one". The spec never covers the
    authenticated case: the CLI needs write access to the file that holds its token.
- **Gap identified**: The spec treats the AI CLI's authentication as a read-only credential, like
  `~/.gitconfig` or the SSH agent socket. For `claude`, the authentication material shares a
  directory with the conversation store, and the CLI both rewrites its own token and writes its
  transcripts there. Two things conflict: the rule that credentials are read-only, and FR-009's
  demand for equivalent session persistence. The spec also never says where a sandboxed session's
  conversations live, or that the host-side boot prune must be able to see them.

### plan.md

- **Affected sections**:
  - "The image ships the AI CLIs, and the sandbox gets a home (FR-023a/b/c, FR-004d, SC-012)"
    (plan.md:245). This section designs `HomeMount` so that first-run `~` writes succeed. It does not
    consider a credential mount that lands under that home and makes it read-only.
  - The credential-mount design (data-model.md `CredentialShare::AiCliAuth`, rule N-1;
    `argv.rs` "Credentials are read-only without exception").
- **Impact**: The plan must choose where a sandboxed `claude`'s session state lives, and how the
  client's boot prune and resume find it. It must also decide the mode of the authentication mount:
  either the token file becomes writable, or it stays read-only and token refresh is handled some
  other way. Candidate approaches:
  1. Narrow `AiCliAuth` to the token file(s) only (e.g. `~/.claude/.credentials.json`), and let the
     rest of `~/.claude` live in the sandbox home. The prune and resume must then read the sandbox
     home's `projects/` when placement is sandboxed (this fits FR-023c's "answered where sessions
     run"). The token file still needs to be writable for refresh, or refresh fails.
  2. Mount the host `~/.claude` read-write under the opt-in, and state that capability in the FR-004b
     label. Simplest, and the host sees the transcripts directly. It gives up the "credentials are
     never rewritten" property for this one share.
  3. Keep authentication read-only, and add a separate, non-credential read-write mount for the
     conversation store (`~/.claude/projects`, and whatever else `claude` needs for resume).

## Root Cause Analysis

This is a spec oversight made concrete by an implementation shortcut. FR-004a lists AI CLI
authentication as one more credential opt-in, and the code applies the credential rule (read-only,
at its host path) to the whole `~/.claude`. That rule fits `~/.gitconfig` and the SSH agent socket,
which the sandbox only reads. It does not fit `claude`, whose config directory is also its writable
session store and whose token file it rewrites itself. The plan's home-directory work (FR-004d) made
`~` writable, but the credential mount then made the one directory `claude` needs most read-only
again. The US2 tests check the service's own session catalogue, not the AI CLI's conversations, so
nothing caught it. Separately, the client's boot prune reads the host's `~/.claude`. That was correct
before sessions could run anywhere but the host, and FR-023c's "answer it where sessions run" was
never extended to conversation lookup.
