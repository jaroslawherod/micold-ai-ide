# Bug Report: Sandboxed claude asks for a login method although the shared sign-in is valid

**Type**: Spec gap (with an untested flow underneath it)
**Severity**: Medium
**Feature**: 027-sandboxed-daemon-runtime (branch `fix/github-issues`)
**Reported**: 2026-09-27 — GitHub issue #403
**Status**: Patched
**Patched**: 2026-09-27

## Description

With the service in the sandbox and the AI CLI sign-in shared, the first interactive `claude`
session walks through claude's own first-run onboarding: the theme picker, then "Select login
method" with an OAuth link. `claude auth status` in the same container reports `"loggedIn": true`
at that moment, so the sign-in the user shared is valid and the prompt is not needed.

Following the prompt is worse than an extra step. The share mounts the host's token file writable
(FR-004e), so a new sign-in made there replaces the host's own token.

### Reproduction

On `origin/main` at `2bd447b2`, with the host's `claude` 2.1.283 and a private `HOME` under the
scratchpad (no credentials involved, so nothing of the host's is touched):

| `HOME` contains | First screen of an interactive `claude` |
|---|---|
| nothing | "Let's get started. Choose the text style…" — the onboarding |
| `.claude.json` = `{"hasCompletedOnboarding":true}` | "Accessing workspace … Is this a project you … trust?" — the trust prompt only |

Onboarding is gated on `hasCompletedOnboarding` in `~/.claude.json`, and nothing else. The
2026-09-19 evidence run (`evidence/bug-006-sign-in-sessions.md`, "Found on the way") saw the same in
the real sandbox with the share on: onboarding including "Select login method" with no
`.claude.json`, and a signed-in session ("Claude Max") showing only the trust prompt once the key was
set.

### Mechanism

1. The sandbox's home is `<state>/sandbox-home`, created empty by the bring-up
   (`crates/micold-client/src/shell/sandbox.rs`, `start`, FR-004d).
2. The sign-in share mounts `~/.claude/.credentials.json` and nothing else (FR-004e). By design,
   `~/.claude.json` stays in the sandbox's home (`plan.md`, BUG-006 increment: "Everything else stays
   in the sandbox's home").
3. So the sandbox's `claude` sees a valid token but no record that onboarding ran, and runs it. The
   onboarding includes the login step regardless of whether a token is present.
4. `claude -p`, which every real-runtime probe uses (`crates/micold-daemon/tests/
   sandbox_real_ai_cli_sessions.rs`, T213), skips onboarding entirely, so no test saw this.

## Artifact Traceability

### spec.md

- **Affected user story**: User Story 2 — "The service keeps its promises inside the box" (P1),
  scenario 10 (a session of any offered AI CLI, with or without the sign-in shared).
- **Affected requirements**: FR-004a (the AI CLI sign-in opt-in), FR-004d (the sandbox's own home),
  FR-004e (the share covers only the token).
- **Gap identified**: FR-004e says what the share mounts but not what the user gets from it. The
  point of the opt-in is that a sandboxed `claude` uses the host's sign-in. The spec never says the
  sandbox's CLI must start signed in without asking, so narrowing the share to the token file
  (BUG-006) lost the onboarding record that the old whole-directory share did not carry either
  (`~/.claude.json` sits beside `~/.claude`, not in it) — nothing ever provided it.

### plan.md

- **Affected sections**: "Bugfix BUG-006" increment, "Everything else stays in the sandbox's home".
- **Impact**: The bring-up must also record, in the sandbox's own `~/.claude.json`, that claude's
  onboarding is done — only when the sign-in share actually mounts a token, and only by adding that
  one key to whatever the file already holds.

### tasks.md

- **Affected tasks**: T211 (the narrowed share), T213 (the real-runtime probes, `claude -p` only),
  T215 (the quickstart pass that found this).
- **False completions**: none. T211 and T213 built and checked what FR-004e says; T215 recorded the
  finding as out of BUG-006's scope.
- **Missing tasks**: a regression test that a bring-up with the sign-in shared leaves
  `hasCompletedOnboarding: true` in the sandbox home's `.claude.json` (and leaves it alone without
  the share, and keeps the file's other keys); the bring-up change; a user-guide line.

## Root Cause Analysis

A spec oversight. FR-004e was written to stop the share from exposing claude's configuration, and it
correctly keeps `~/.claude.json` in the sandbox. What it did not account for is that claude reads
"has this user been through setup" from that file, not from the token. A fresh sandbox home is a
first run to claude no matter what token it finds, and the probes that would have caught it run
non-interactively.

The fix writes into the sandbox's own home, which the application owns (FR-004d), and not into the
host's `~/.claude.json`. It is only done when a token is really mounted: without one, skipping the
onboarding would also skip the login step the user then needs.
