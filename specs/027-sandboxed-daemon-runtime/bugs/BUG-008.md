# Bug Report: A sign-in share with no token file on the host is dropped without telling the user

**Type**: Implementation drift (with a spec gap underneath it)
**Severity**: Medium
**Feature**: 027-sandboxed-daemon-runtime (branch `fix/github-issues`)
**Reported**: 2026-09-28 — GitHub issue #405 (follow-up recorded on `bugs/BUG-006.autopilot.md`)
**Status**: Patched
**Patched**: 2026-09-28

## Description

With the service in the sandbox and the AI CLI sign-in share ticked, a host with no
`~/.claude/.credentials.json` shares nothing. The bring-up drops the share (`drop_absent_sign_in`,
`crates/micold-client/src/shell/sandbox.rs`) and writes one line to stderr with `eprintln!`, which a
user of the packaged application never sees. The Settings screen goes on showing the share ticked,
and its caution goes on saying "Shared with the container: AI CLI sign-in. A session can use the AI
CLI sign-in and replace its token". The sandbox's `claude` then starts signed out, and nothing in
the application says why.

A host with no token file is ordinary: `claude` keeps its sign-in in the Keychain on macOS, an API
key needs no file, and before a first sign-in there is nothing to share. On macOS the ticked share
therefore never works, and nothing says so.

`MissingCredential` (`crates/micold-core/src/sandbox/mod.rs`) cannot cover this: it attributes a
failure to an opt-in that is *off*, and here the opt-in is on.

### Reproduction

On `origin/main` at `3b1330b8`. The probe is a throw-away test in `shell/sandbox.rs`'s `mod tests`
(kept in the session scratchpad as `probe_bug008.patch`, never committed). It gathers the host
facts the way `HostFacts::gather` does, against a home with no `.claude/.credentials.json`, and runs
`start` against a runtime scripted to a created and started container, twice with the same state
directory: once with `AiCliAuth` shared and once with no share at all. It records every
`SandboxState` passed to `observe` and the `Ready` that comes back, and asserts that the two differ.

```
sandbox: the AI CLI sign-in is shared, but there is no token file at /tmp/.tmpRymlGC/.claude/.credentials.json. Nothing is mounted for it; sign in on the host, or sign in inside the sandbox.
thread 'shell::sandbox::tests::probe_bug008_absent_sign_in_is_indistinguishable' panicked at crates/micold-client/src/shell/sandbox.rs:1553:9:
assertion `left != right` failed: BUG-008: the view is told nothing about the dropped share
```

The progress stream and the outcome are identical, `Probing → Acquiring → Starting → Running` and
the same `Started` and `SandboxLocations`. Everything the view is told about a bring-up that asked
for the sign-in and got none is exactly what it is told about one that never asked. The only trace
is the stderr line. The Settings page draws the share from the draft (`ui/settings/daemon.rs`,
`view` and `sharing_summary`), which is built from the settings file alone
(`shell/persist.rs`, the settings-open handler), so it cannot know either.

To see it in the application: on a host with no `~/.claude/.credentials.json`, choose *In a
container* with *AI CLI sign-in* ticked, let the sandbox start, open *Settings → Session service*
and start a `claude` session. The share is ticked, the caution says it is shared, and `claude` asks
you to sign in.

### Mechanism

1. `CredentialLayout::conventional` names `~/.claude/.credentials.json` whether or not it is there,
   by design. Presence is a question for the moment the sandbox starts, not for a pure layout.
2. `HostFacts::gather` answers it through `drop_absent_sign_in`, which sets `layout.ai_cli_auth` to
   `None` when the file is absent (BUG-006, review finding F2). That is the right outcome, since a
   runtime would otherwise create the missing bind source as a root-owned directory in the user's
   real home.
3. The only record of the drop is `eprintln!`. `HostFacts` keeps no note of what was dropped, `start`
   returns a `Ready` of `Started` and `SandboxLocations` that has no place for it, and `observe`
   carries a `SandboxState` and nothing else. The doc comment on `drop_absent_sign_in` says so and
   defers the user-visible report to a follow-up.
4. `MountSet::build` then skips the share as it skips any opt-in whose path the layout does not
   know (`an_opt_in_with_no_known_path_is_skipped_rather_than_substituted`), and the container
   comes up without it.

## Artifact Traceability

### spec.md

- **Affected user story**: User Story 1 — "The agent can only touch the project" (P1), scenarios 6
  and 7. Scenario 6 asks that a failure for want of credentials be attributable to the sandbox
  rather than unexplained. That holds for a share that is off (`MissingCredential`). It does not hold
  for a share that is on and mounted nothing. User Story 2 scenario 10 (a `claude` session with the
  sign-in shared) is where the user meets the failure.
- **Affected requirements**:
  - **Edge cases**: "A credential opt-in is enabled while the item it shares is absent on the host",
    and the BUG-006 edge case "The AI CLI sign-in is shared, but the host keeps that CLI's token
    outside any file … This is the absent-item case above, and it is reported as one." The drop is
    implemented. The report is not.
  - **FR-004c**: "The settings view MUST show, at a glance, whether any credential opt-in is
    currently active, so the user can tell a fully-isolated sandbox from a partially-shared one."
    For this share, the view shows an opt-in as active and the sandbox as partially shared, while the
    running sandbox shares nothing of it.
  - **FR-004b / FR-004e**: the caution says a session "can use the AI CLI sign-in and replace its
    token". With no token mounted, that is not true of the running sandbox.
- **Gap identified**: The edge case says the absent item "is reported", but no requirement says
  *where*, or to whom, and nothing ties the settings view's claim about a share to what the running
  sandbox actually mounted. So the implementation had nowhere it was obliged to put the report, and
  put it on stderr.

- **Impact**: The plan needs to say how the fact travels (the bring-up that dropped the share

- **Missing tasks**:
  - A regression test: a bring-up that shares the sign-in on a host with no token file hands the

    application reports it.

## Root Cause Analysis

The drop was added late, in BUG-006's review remediation (finding F2), to stop a runtime from
creating a root-owned directory in the user's home. The report the spec's edge case promises needed
a channel from the bring-up to the view that did not exist. `observe` carries only a stage, and
`Ready` only what is mounted. Building that channel was judged larger than the bug, so the drop
shipped with an `eprintln!` and a follow-up note. The spec made this easy: it says the absent item
"is reported" without a requirement saying where, so no test could ask for it.

## Recommended Fix

**Surface: the Settings page, beside the ticked share. Not the bring-up progress.** The reasons:

- The bring-up progress (`ui/sandbox_status.rs`) renders only while a bring-up is in flight and is
  absent from `Running` onwards, by design (SC-017: an indicator at rest would request a frame
  every tick). A report there would be on screen for the instant between the drop and `Running`, and
  gone by the time the user opens a `claude` session and finds it signed out.
- The standing banner (`ui/mod.rs`, `sandbox_banner`) is for a sandbox that is not doing its job,
  and each banner carries the action that ends it (FR-035b). Here the sandbox is working, and no
  application action ends the condition. The user has to sign in on the host, or inside the sandbox.
  A toast on every start would repeat on every launch for every macOS user whose token lives in the
  Keychain. FR-035b's own edge case is the user who learns to ignore a repeated notice.
- The Settings page is where the claim is false (FR-004c, the ticked box, the caution). It already
  reports facts about the *running* sandbox beside the control they concern: a limit the runtime
  cannot enforce says so under its field (FR-015, fed from `Started.capabilities` through
  `Sandbox` into `DaemonDraft::capabilities`), and a CLI the running image lacks is named under the
  image reference (FR-023b, `missing_cli_notice`). The absent token is the same kind of fact and
  travels the same way.
- It is where a user looks when `claude` is signed out despite a share they remember ticking.

Steps:

1. Run `/speckit.bugfix.patch`. Add a requirement that an enabled sign-in share whose token the
   running sandbox's container does not mount is reported in the settings view, beside the share,
   naming the path it is shared from, and that the view does not describe it as shared. Point the edge case at it,
   add the increment to `plan.md`, and add the fix tasks.
2. Run `/speckit.bugfix.verify` to confirm consistency.
3. Implement as one milestone. The regression test comes first.
