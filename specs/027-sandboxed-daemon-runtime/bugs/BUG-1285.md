# Bug Report: Podman cannot create the no-outbound network, so a Podman sandbox never starts

**Type**: Dependency issue (with a spec conflict: the design fixes a Docker-only mechanism for every runtime)
**Severity**: Critical — `NoOutbound` is the default posture, so every Podman container daemon fails to start
**Feature**: 027-sandboxed-daemon-runtime (branch `claude/project-thread-4rg3m6`)
**Reported**: 2026-10-23. GitHub issue #1285, child of #1279, found by the #1281 end-to-end job's
rootless Podman leg. Measurements in `specs/quick/2026-10-23-1285-podman-no-outbound-network.autopilot.md`.
**Status**: Patched
**Patched**: 2026-10-23

## Description

With network access off (`NetworkPosture::NoOutbound`, the default), the sandbox's start runs
`argv::network_create`, which on Podman is:

```
podman network create --driver bridge -o com.docker.network.bridge.enable_ip_masquerade=false micold-sandbox-net
```

Podman's network backend, netavark, refuses the option:

```
Error: unsupported bridge network option com.docker.network.bridge.enable_ip_masquerade
```

`CliRuntime::create` stops there, so no container is created. The failure is the same rootful and
rootless. A Podman user can start a sandbox only by turning network access on.

### Reproduction

On `origin/main` at `dff37b25`, Podman 4.9.3 with netavark 1.4.0 (Ubuntu 24.04 packages, the CI
runner's combination):

1. `podman network create --driver bridge -o com.docker.network.bridge.enable_ip_masquerade=false repro1285`
   → `Error: unsupported bridge network option com.docker.network.bridge.enable_ip_masquerade`, exit 125.
   Rootless (as an unprivileged user) gives the same error.
2. The argv is the application's: `crates/micold-core/src/sandbox/dialect/podman.rs:19` sets
   `no_masquerade_opt` to Docker's option, and `crates/micold-core/src/sandbox/argv.rs:55-58`
   appends `-o <no_masquerade_opt>` under `NoOutbound`.
3. End to end: the #1281 job's Podman leg (`.github/workflows/ci.yml`, "container daemon end to end
   (podman, linux)"), which adds a container daemon with the default posture, fails at the network.

### What does block outbound on Podman (measured)

A busybox `httpd` published on `-p 127.0.0.1:P:8080`; the host curls the port; inside, `wget
http://1.1.1.1` (a 403 from this machine's proxy means outbound works). Rootless ran as an
unprivileged user with its own `XDG_RUNTIME_DIR` under `/run/user/<uid>`. For each row:

```
podman network create [--internal | -o <opt>] n
podman run -d --name w --network n -p 127.0.0.1:18085:8080 busybox:1.36 httpd -f -p 8080 -h /
curl -s -m 5 -o /dev/null -w '%{http_code}\n' http://127.0.0.1:18085/   # host -> port
podman exec w wget -q -T 5 -O- http://1.1.1.1                         # outbound
podman rm -f w; podman network rm n
```

| network | rootful: host → port / outbound | rootless: host → port / outbound |
|---|---|---|
| default bridge | ok / open | ok / open |
| `--internal` | **timeout** (netavark 1.4 adds no DNAT for an internal network) / blocked | **ok** (rootlessport) / **blocked** ("Network is unreachable") |
| `-o isolate=true` | ok / open | — |
| `-o no_default_route=true` | accepted but **ignored** by netavark 1.4 (default route still present) / open | — |
| bridge with the default route deleted by hand (what `no_default_route` does) | ok / blocked | — |

- Rootless Podman forwards a published port through `rootlessport`, not through DNAT on the
  bridge, so an `--internal` network keeps the port reachable and has no route out. That is the
  pair R4 asks for.
- Rootful Podman forwards through netavark's DNAT, which netavark does not set up for an internal
  network: R4's original measurement on Docker holds there too.
- `no_default_route` is netavark's bridge option for "no route out", added in netavark v1.7.0
  (its release notes). Before 1.7 it is accepted and ignored, which leaves outbound open without a
  word: the failure FR-034 forbids, in the place a user trusts most.
- `podman info --format json` names both facts: `host.security.rootless` and
  `host.networkBackendInfo.version` (`"netavark 1.4.0"`); `host.networkBackend` is `"netavark"` or
  `"cni"`. `parse::info` already reads `rootless`.
- DNS inside an `--internal` network was not measurable here (this machine resolves no external
  name from the host either). R4's "names still resolve" caveat was measured on Docker only.

## Artifact Traceability

### spec.md

- **Affected user story**: User Story 4, scenario 4: "Given network access is turned off for the
  sandbox, When a session attempts a network connection, Then it fails inside the session … and no
  other behaviour changes." On Podman the sandbox does not start at all.
- **Affected requirements**: FR-017 (a fully disabled position), FR-020 (the runtime is
  replaceable; Podman is supported), FR-034 (nothing fails silently).
- **Gap identified**: No requirement says that the disabled position must hold on every supported
  runtime, nor what happens where a runtime setup cannot provide it. The answer the spec already
  intends, from FR-017 and FR-034, is: block outbound in the runtime's own terms, and where that is
  impossible, refuse the start with the reason, never start with outbound open.

### plan.md

- **Affected sections**: the R4 row of the research table; no increment covers the network per
  runtime.
- **Impact**: an increment: the no-outbound network arguments are chosen from the probed
  capabilities, not from a constant in the dialect.

### research.md, contracts, data-model.md

- **R4**: decided on Docker only, and stated as the mechanism for every runtime.
- **contracts/container-runtime.md C-5** ("The network is a user-defined bridge created with IP
  masquerade disabled") and **K-7** ("`NoOutbound` yields the masquerade-disabled network") fix
  Docker's mechanism as the contract. C-5's real obligation, the property, is right: no outbound,
  control channel reachable, a configuration that severs the channel fails the suite.
- **data-model.md §4**: `NetworkPosture::NoOutbound`'s doc names the Docker mechanism.

### tasks.md

- **Affected tasks**: T078 (K-7 test), T085 (`NetworkPosture` and the network), T090 (conformance

- **False completions**:
  - **T078**: asserts for *every* runtime that the masquerade option is emitted and `--internal` is

  - **T093**: Podman's dialect copied Docker's driver option, under the dialect doc's claim "Both

  - T090's claim that Podman passes K-7 was an argv check of Docker's string against itself; it is

- **Missing tasks**: regression tests for the network arguments per runtime setup and for the

## Root Cause Analysis

R4 was measured on Docker, where "no NAT" and "inbound port published" are two separate switches
(`enable_ip_masquerade=false` and DNAT). The dialect table then recorded Docker's driver option for
Podman too, on the belief that Podman takes Docker's network options. Netavark, Podman's default
network backend since 4.0, rejects them. Nothing ran the
application's own `network create` against a real Podman: the argv tests compare strings, the
real-runtime CI job runs Docker only, and the harness's no-outbound helper
(`crates/micold-daemon/tests/sandbox_real_support/mod.rs:464`) passes the same dialect constant
rather than the application's argv. The #1281 job was the first to drive the application's start on
Podman, and it failed at once.

Behind the string is a modelling error: the mechanism depends on the runtime **setup**, not only on
the runtime. On Podman the port path differs by rootless vs rootful (rootlessport vs DNAT), and the
working option for rootful exists only from netavark 1.7. A `&'static str` in the dialect cannot
express that; the probe already reads `podman info`, which states both facts.

## Recommended Fix

1. `/speckit.bugfix.patch`: FR-017a (the disabled position holds on every supported runtime setup,
   or the start is refused with the reason; outbound is never left open silently), US4 scenario 4a,
   C-5/K-7 restated as the property with a per-setup table, R4 amended with the Podman measurements,
   data-model §4, the plan increment, T078 and T093 reopened, fix tasks T236–T241.
2. `/speckit.bugfix.verify`.
3. One milestone. The regression tests come first.

Known and not in this fix: the network is never removed and its name does not depend on the
posture, so switching the posture after a first start reuses the network created under the old one
(`run_idempotent(…, &["already exists"])` in `CliRuntime::create`). Recorded as a follow-up in
`bugs/BUG-1285.autopilot.md`.
