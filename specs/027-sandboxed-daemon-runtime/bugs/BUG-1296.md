# Bug Report: On an SELinux-enforcing host the container cannot read its bind mounts, so sshd exits and the daemon never starts

**Type**: Untested flow (a host security policy nothing in the design or its tests covered; the
real-runtime harness hid it with its own `--security-opt label=disable`)
**Severity**: Critical — on Fedora, RHEL and every other SELinux-enforcing distribution no container
daemon starts, on Podman or Docker
**Feature**: 027-sandboxed-daemon-runtime (branch `claude/project-thread-epw0jt`)
**Reported**: 2026-10-23. GitHub issue #1296, follows #1279 (BUG-1285's parent): it is the next
failure behind #1279's `uid=` tmpfs one.
**Status**: Patched
**Patched**: 2026-10-23

## Description

Settings > Daemons shows a Container daemon as unreachable. The client log says:

```
the container test is not ready: Error: can only create exec sessions on running containers: container state improper
```

The container exits within a second of starting. Its own log (`journalctl`, or `podman logs`) says:

```
Unable to load host key: /run/micold/ssh/host_ed25519_key
sshd: no hostkeys available -- exiting.
```

The SSH key files are bind-mounted from the client's key directory with no SELinux label option, so
they keep their host type (`user_home_t` / `xdg_data_home_t`). The container runs as `container_t`,
which the targeted policy does not allow to read those types; under `Enforcing` the read is denied,
sshd finds no host key and exits, and the container stops with it. The same denial applies to every
other bind mount: the sandbox home, the state directory, the history directory, the projects and the
shared credentials — so even with the keys readable, the daemon would fail on its first write to its
state.

The user sees only "container state improper": the container's own log, which names the cause, is
never shown.

### Reproduction

By the reporter, on Fedora with SELinux `Enforcing` and podman 5.8.9, rootless, with
`--userns=keep-id` and the mounts `argv::create` produces:

1. Add a Container daemon in Settings > Daemons (default settings). It shows unreachable; the client
   log holds the "container state improper" line above.
2. `podman logs <container>` (or `journalctl`): `Unable to load host key: /run/micold/ssh/host_ed25519_key`,
   `sshd: no hostkeys available -- exiting.`
3. The same `podman create` by hand with the same `-v` options: sshd exits as above. Adding
   `--security-opt label=disable`: sshd stays up. (Adding `,z` to each `-v` is the runtimes' standard
   alternative; the reporter did not run it, and Phase 31's **Verify** checks it on an enforcing host.)

On `origin/main` (`f8d2257e`) the argv half is in the code, independent of the host:

- `crates/micold-core/src/sandbox/argv.rs:261-321` (`mount_args`) writes every bind mount as
  `<host>:<container>:rw` or `:ro`, with no label option, on every host.
- `RuntimeCapabilities` (`crates/micold-core/src/sandbox/runtime.rs:108-125`) has no field for the
  host's security policy, and nothing under `crates/micold-core/src/sandbox/` reads one
  (`grep -rni selinux crates/micold-core/src/sandbox` is empty).
- This container has no `/sys/fs/selinux`, so the denial itself cannot be re-run here; the CI
  runners (Ubuntu, AppArmor) cannot either — see *Why nothing caught it*.

### Why nothing caught it

- The real-runtime harness never runs the application's mount argv.
  `crates/micold-core/tests/sandbox_real_handshake.rs:51-104` (`Sandbox::start`) spells its own
  `-v` list; `crates/micold-daemon/tests/sandbox_real_support/mod.rs` (`start_sandbox`) spells its
  own too and adds `--security-opt label=disable` on Podman (`mod.rs:648-653`, commented "SELinux-
  enforcing hosts (Fedora) deny a container the bind mounts above");
  `crates/micold-daemon/tests/sandbox_real_history.rs:158-161` adds it for every runtime. The
  harness met this failure, and worked around it in the harness instead of the product.
- T098's Podman pass (`evidence/us5-podman.md`) ran through that harness.
- Every CI job that starts a container runs on `ubuntu-latest`, where SELinux is off. A Fedora
  *container* on that runner does not change this: SELinux is a host kernel state.

## Root Cause Analysis

The mount design (R2, C-3, T036) was decided and measured on Docker Desktop, Ubuntu and macOS, none
of which enforces SELinux, so a bind mount there is readable by the container by default. On an
enforcing host it is not: the container type may read only files labelled for containers, and the
runtimes relabel a bind mount only when its options ask (`z` shared, `Z` private). `mount_args`
never asks.

The harness met the denial on Fedora and answered it in the harness (`--security-opt
label=disable`), which made the real-runtime tests pass where the product fails, and the handshake
test's own `-v` list meant no real-runtime test ran the product's mount argv at all.

## Decisions

- **D1 — project mounts** (the user's decision, jaro, 2026-10-23, on the orchestrator's card): use
  `:z` on project mounts too, only when SELinux enforces. No `--security-opt label=disable`, and no
  change to C-9. `z` (shared) rather than `Z` (private): a project may be shared by more than one
  sandbox and is the user's own worktree, and a private label would lock other containers out of it.
  Consequence, stated in the user guide: on an enforcing host the runtime relabels the project's
  files `container_file_t`; the user's own processes still read and write them.
- **D2 — which mounts** (agent-resolved, following D1): every bind mount `argv::create` emits gets
  `z` when enforcing — the sandbox home, history, projects, state, the three SSH key files and the
  shared credentials. A credential share without it would be silently unreadable, the failure FR-034
  forbids. One rule for every `-v` is also the one the unit test can state.
- **D3 — the probe** (agent-resolved): `/sys/fs/selinux/enforce` on the host, read once per probe
  beside `info`. `1` is enforcing; `0`, an absent file, an unreadable file or anything else is not.
  Permissive mode logs denials without enforcing them, so it needs no label. Read on Linux only;
  macOS and Windows never relabel, so their argv is unchanged. A remote runtime host is out of
  scope (the feature's runtime is local).
- **D4 — CI** (agent-resolved, per the orchestrator's instruction): no enforcing job is added in
  this fix. GitHub-hosted runners are Ubuntu with AppArmor; a Fedora container there still runs on
  that kernel and does not enforce, so a "Fedora podman" job would pass with or without the fix and
  prove nothing. A truly enforcing job needs a Fedora VM (KVM on the hosted runner, or a
  self-hosted Fedora runner) with the image and binaries inside it; recorded as a follow-up. The
  guards here are the unit tests (U59, U60) and the handshake test driving the application's argv
  (T247), which fails on a mount-argv bug on every runtime it runs on.
- **Known edge**: the runtimes refuse to relabel some system paths and the user's home directory
  itself. A project registered at `$HOME` (or `/`, `/usr`, …) on an enforcing host is refused at
  `create` and reported through `RuntimeError::naming_mount` as the mount that was rejected; that is
  the right answer, since relabelling a whole home would be wrong.
