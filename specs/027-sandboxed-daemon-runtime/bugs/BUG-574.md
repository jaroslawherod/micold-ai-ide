# Bug Report: A sandbox that shares every registered project is still reported out of date

**Type**: Spec gap (with implementation drift on top of it)
**Severity**: Medium
**Feature**: 027-sandboxed-daemon-runtime (branch `claude/project-thread-w87jv6`)
**Reported**: 2026-10-06. GitHub issue #574, found in feature 039's container pass (C3) and
recorded there as decision D33 and a follow-up (`specs/039-session-attention-notifications/autopilot.md`)
**Status**: Patched
**Patched**: 2026-10-06

## Description

With the service in a container, the client showed the `SandboxState::Stale` notice for the whole
C3 run:

> The sandbox does not yet share every registered project. Restart it to apply.

The container had both project mounts at that time (`docker inspect` listed P and Q,
`specs/039-session-attention-notifications/visual-pass/M9/container-pass.md`). This is not a version
mismatch: both clients attached (`client_build=micold-ai-ide/0.16.0`, image built from the same
tree), and `mise run test-sandbox` passed 29 of 29. Two clients ran, and the service log shows one
restart (`C3-micold-daemon-state.log.txt` line 13, 09:34:56) with no record of who caused it. Nobody
clicked Restart, which is the only way out of `Stale`.

The issue asks: should a client leave `Stale` when the container it sees already shares every
registered project? Yes. `Stale` is a claim about the running container, and that claim is false.

### Reproduction

On `origin/main` at `98f41a61`. The probe is three throw-away tests in
`crates/micold-client/src/main_tests.rs` (`mod repro_574`, never committed). Each drives the real
update path: a sandbox in `Failed`, a `Started` message, then `ConnectionMsg::Connected` with a
catalog. A container path equals its host path on Linux and macOS (M-2), so `/proj/P` names the
same directory on both sides.

`scripts/build-lock.sh cargo test -p micold-client --bin micold-ai-ide repro_574`:

Each test asserts `Running` and gets `Stale`. The probe is kept in the session scratchpad as
`probe_bug574.patch`.

- **R1, same set in another order.** The plan, built from this client's workspace, is `[P, Q]`. The
  container is created from it. The service's catalog lists `[Q, P]`. The sandbox goes `Stale`.
- **R2, a container this client did not create.** This client's plan is empty. The bring-up attaches
  to a container that another client created and that mounts P and Q (`Started.mounted` is
  `Some([P, Q])`). The service's catalog lists `[P, Q]`. The sandbox goes `Stale`.
- **R3, no way back.** From R2's start, the first catalog lists only P, and the sandbox goes `Stale`.
  The next catalog lists `[P, Q]`, exactly what the container mounts. The sandbox stays `Stale`.

### Mechanism

1. `adopt_mount_set` (`crates/micold-client/src/shell/daemon_sync.rs:582`) runs on every
   `Connected` and every `CatalogChanged`. It compares the catalog's project list with
   `BootPlan.projects` as a `Vec`, so order counts (R1). It never consults the container.
2. `BootPlan.projects` is not what the container shares. At boot it is this client's own workspace
   list (`shell/startup.rs:262`), and after the first mismatch it is the last catalog seen
   (`daemon_sync.rs:591`). A bring-up that attaches to or starts an existing container keeps that
   container's mounts (`Started.mounted`, feature 031), so the plan can differ from the container in
   either direction (R2). With two clients, each boots from its own workspace and adopts the
   container the other made.
3. `mount_set_changed` (`crates/micold-core/src/sandbox/lifecycle.rs:424`) maps `Running` to `Stale`
   and every other state to itself. Nothing maps `Stale` back to `Running` except
   `Sandbox::started` after a restart the user asks for (R3).
4. A container replaced by another client is not noticed. `check_alive`
   (`shell/sandbox.rs:661`) asks whether *a* container named `micold-sandbox` runs, not whether it is
   the one this client adopted. The client keeps the old id and its idea of the old container's
   mounts across the reconnect. The C3 log is consistent with this: the service started again at
   09:34:56, 0.7 s after the second client attached, and both clients reconnected without a
   bring-up of their own.
5. The notice blames the mount set for every `Stale`. `survive_logout_changed`
   (`lifecycle.rs:443`) reaches the same state when the keep-running setting is saved, and
   `persistent_notice` (`crates/micold-client/src/features/sandbox.rs:502`) then says the sandbox
   "does not yet share every registered project", which is false. The state has no record of why it
   is stale, so a fix that clears staleness when the mounts match would also clear a keep-running
   staleness that still holds.

Which of these produced C3's banner is not established. The two clients' plans and their
bring-up outcomes were not logged. Each of R1 and R2 yields `Stale` over a container that shares
every registered project, and R3 keeps it there for the rest of the run, which matches what C3
showed. The keep-running path (5) is ruled out for C3 only by the pass record, which mentions no
change to that setting.

## Artifact Traceability

### spec.md

- **Affected user story**: User Story 6, "Nothing fails silently". A notice that stays up while
  untrue teaches the user to ignore the banner, which is the failure FR-035b's edge case describes.
- **Affected requirements**:
  - **Edge case** "The user registers a new project *after* the sandbox has started, when what is
    shared with the sandbox was fixed at creation." No requirement answers it.
  - **Assumption** "sharing a project registered after the sandbox started may require the service
    to restart, and the application is expected to say so rather than fail quietly." It says when
    to speak up, not when to stop.
  - **FR-004**: the sandbox must have access to the registered projects and to no other host
    location. Staleness is the application's report that the running container breaks FR-004 in
    one direction or the other.
- **Gap identified**: No functional requirement defines staleness. Research R9 and data-model M-4
  say that *changing* the registered projects marks the sandbox stale. That is a rule about an
  event, and the implementation followed it: it compares the new list with the previous one rather
  than with the container. Nothing says what staleness is measured against, nor that a sandbox
  stops being stale when the mismatch is gone. Nothing separates the two reasons for staleness
  (mount set, keep-running setting) in what the user is told.

### plan.md

- **Affected sections**: the R9 row of the research table, and the BUG-005 increment's note that
  "`on_connected` ends the grace (`answered()`) before `adopt_mount_set` can mark it `Stale`".
- **Impact**: An increment is needed. Staleness of the mount set is computed from the running
  container's project mounts against the catalog's projects, as sets, on every catalog. A
  replaced container is re-read on reconnect. The keep-running staleness is kept apart from it.

### data-model.md

- **Affected sections**: §6 rule M-4 and §7's `Running → Stale` edge "projects changed (R9)".
  There is no `Stale → Running` edge except "user restarts".
- **Impact**: M-4 and the diagram need the measured definition and the edge back to `Running` when
  the container again shares exactly the registered projects and no keep-running change is pending.

### tasks.md

- **Affected tasks**:
  - T101 *(test)*, M-4 in `crates/micold-core/tests/sandbox_state.rs`: "registering a project marks
    the sandbox `Stale` and nothing restarts on its own (R9)".
  - T105, the stale-on-project-change transition and the restart action, driven from the daemon's
    catalog in `shell/daemon_sync.rs`.
  - Feature 028's FR-022a task that added `survive_logout_changed` with the same state and notice.
- **False completions**: None. T101 and T105 do what they say. The defect is in what they were
  asked to do: compare with the last list rather than with the container.
- **Missing tasks**:
  - Regression tests: R1, R2 and R3 above as tests that fail on `origin/main`. Core tests for the
    pure decision. A test that a keep-running staleness is not cleared by a matching mount set,
    and that its notice names the setting rather than the projects.
  - The decision in `micold-core`: given the container's project mounts and the registered projects,
    is the mount set stale. Staleness carries its reasons, so one can clear without the other.
  - The client: record the container's project mounts at `Started` (its `mounted`, or the mount set
    it was created from), decide on every catalog, and leave `Stale` when no reason is left.
  - A container replaced by another client: on reconnect, re-read the container by name, and adopt
    its id and mounts when they differ from the one this client holds.
  - The notice: one text per reason.
  - The user guide's sandbox page says when the notice clears.

## Root Cause Analysis

R9 was decided for one client, one container and a project list that changes by registration. It
was written as an event ("adding or removing a project marks the sandbox stale"), and T105
implemented the event faithfully: a list differing from the previous list. That held while the
plan's list and the container's mounts were the same thing. Feature 031 broke the equivalence when
a bring-up began adopting an existing container with mounts of its own (`Started.mounted`), and
two clients broke it further, since each boots from its own workspace. Nobody restated R9 as a
property of the container, so no test compared the notice with the mounts. The keep-running
setting (feature 028) reused the state without its own reason, which made a clearing edge unsafe
to add, so none was added.

## Recommended Fix

1. Run `/speckit.bugfix.patch`. Add a requirement that the sandbox is reported out of date exactly
   while the running container does not share the registered projects (one is missing, or an
   unregistered one is still shared), or was created under a keep-running answer that has since
   changed. The report clears when neither holds, without a restart. Each reason is named on its own.
   Add the US6 scenario, the plan increment, the data-model edge, and the fix tasks.
2. Run `/speckit.bugfix.verify`.
3. Implement as one milestone. The regression tests come first.
