# Contract: Protocol v5 → v6

**Feature**: [../spec.md](../spec.md) | **Affects**: `crates/micold-core/src/protocol/`

Two additions, both forced by decisions in [research.md](../research.md): an **authentication step**
(R1) and a **build fingerprint** (R8). No message payload changes, so `SCHEMA_HASH` moves only
because the handshake struct does.

## Why the bump

Today's transport authenticates by filesystem permission: the daemon's Unix socket lives in a `0700`
directory, so reaching it already proves you are the user (`micold-core/src/endpoint.rs`, FR-030).
Loopback TCP — which R1 shows is the only transport that works on all three platforms — has no such
property. Any local process can connect to `127.0.0.1:<port>`. Adding TCP without adding
authentication would be a security regression shipped inside a security feature, which is why these
two changes travel together and why the version moves rather than the field being made optional.

## 1. Authentication (R1)

**Token.** 32 bytes from the OS CSPRNG, hex-encoded. Generated by the client at sandbox start, one
per sandbox lifetime — never persisted in `settings.json` (see the settings contract), never logged,
never in argv.

**Delivery.** Written to a `0600` file in the per-user state directory and bind-mounted **read-only**
into the container at a fixed path. The daemon reads it from that path at startup. The same
filesystem permission that protected the socket now protects the secret; the token reaches the
container through the filesystem, not through the command line, so it does not appear in
`docker inspect` or in the host's process list.

**Presentation.** The client sends the token as a field of the existing handshake frame, before any
other message. The daemon compares it in **constant time** and, on mismatch, closes the connection
after a single classified refusal — no retry loop, no oracle for how wrong the token was.

**Applicability.** The field is present in v6 for every placement. For `HostProcess` over a Unix
socket or named pipe it is a defence-in-depth check on top of the filesystem permission, not a
replacement for it — one code path, no per-placement branch in the handshake.

## 2. Build fingerprint (R8)

**Problem.** The handshake already compares three identity values — `PROTOCOL_VERSION` (5),
`SCHEMA_HASH` (a `build.rs` hash over `messages.rs`/`grid.rs`/`envelope.rs`) and `PACKAGE_VERSION`
(`env!("CARGO_PKG_VERSION")`), at `protocol/version.rs:16,23,28`. Within one released version, a
daemon rebuilt yesterday and a client built today present **identical** values for all three. FR-024c
makes the maintainers' rebuild loop a supported path, and FR-024d requires refusing a stale image —
which the existing constants cannot detect. It also explains a previously unexplained symptom: a
mixed client/daemon pair refusing to connect while printing matching version numbers.

**Addition.** `BUILD_FINGERPRINT: &str` — a value that changes on **every** build, not every release.
Emitted by `build.rs` alongside `SCHEMA_HASH`, into the same generated file.

**Comparison rule, deliberately asymmetric:**

| Image source | Fingerprint mismatch |
|---|---|
| `LocalBuild` (a `:dev` image, FR-024c) | **refuse**, naming the image tag and the rebuild command |
| `Registry` / `ImportedFile` (a released image) | **allow** — the three existing constants govern |

A released client and a released daemon of the same version are built separately and legitimately
carry different fingerprints; refusing there would break every normal install. A locally built image
that disagrees with the client is stale by definition, because both came from the same working tree.

## 3. Refusal reasons

The handshake refusal becomes a closed enumeration, so each carries the reason and remedy FR-034
requires and each is testable as a value rather than a formatted string:

| Reason | Cause | Remedy shown |
|---|---|---|
| `ProtocolMismatch` | `PROTOCOL_VERSION` differs | upgrade the older side |
| `SchemaMismatch` | `SCHEMA_HASH` differs | rebuild both |
| `VersionMismatch` | `PACKAGE_VERSION` differs | upgrade to match |
| `StaleDevImage` | fingerprint differs, source is `LocalBuild` | `mise run image`, then restart the sandbox |
| `AuthRejected` | token missing or wrong | restart the sandbox to reissue the token |

## 4. Compatibility

A v6 client and a v5 daemon fail on `ProtocolMismatch` before authentication is reached, which is the
existing behaviour and the correct one — there is no negotiation and no downgrade path, matching the
handshake's current strict-exact-match design. Both binaries ship together in a release, and the
`StaleDevImage` reason exists precisely because the development loop is the one place they can
diverge.

## Test obligations

| # | Check |
|---|---|
| P-1 | correct token accepted; wrong token refused as `AuthRejected`; absent token refused |
| P-2 | token comparison is constant-time (asserted structurally, at the call site) |
| P-3 | the token appears in no log line, no argv, and no `inspect` output |
| P-4 | fingerprint mismatch + `LocalBuild` → `StaleDevImage`; + `Registry` → accepted |
| P-5 | each refusal reason renders a distinct remedy string |
| P-6 | `PROTOCOL_VERSION` is 6 and the daemon rejects a v5 handshake before authenticating |
