# Bug Report: Searching "about" finds nothing, so the About dialog cannot be found by its name

**Type**: Dependency issue. mdBook's search, elasticlunr, drops English stop words and "about" is
one of them. The search check that SC-006 relies on cannot see this (untested flow).
**Severity**: Low. The *Help & About* page is one click away in the navigation, and `help` or
`about dialog` find it. A reader who types the dialog's own name is told there is nothing.
**Feature**: 028-docs-site-github-pages (User Story 2; FR-026, FR-023a, SC-006)
**Reported**: 2026-09-16
**Status**: Open

## Description

On the published site (v0.15.0), typing `about` into the search box on any page gives *No search
results for 'about'.* The quickstart Part B pass found this on 2026-09-15:
[evidence/quickstart-b.md](../evidence/quickstart-b.md) (B2, finding 1), with a
[screenshot](../evidence/quickstart-b2-about-no-results.png).

- `about` from `user-guide/icons.html`: no results. From `index.html`: no results.
- `about dialog`: 20 results, and *Help & About › What the About dialog shows* is second.
- `help`: 20 results, and *Help & About* is first.

A reader who wants "the About dialog" or "About" has the right word for the topic. The site answers
as if the topic does not exist.

## Evidence of the cause

- The published `elasticlunr-ef4e11c1.min.js` defines `stopWords={…about:!0…}`. Stop-word filtering
  runs on the query in the browser, so `about` is removed before anything is looked up. An empty
  query returns no results.
- The published `searchindex-a2393f5f.js` has no `about` term. Under `a → b` it holds `abandon`,
  `abbrevi`, `abov` and `absent`, but nothing under `abou`. The indexer (elasticlunr-rs, inside
  mdBook) drops it too.
- `site/book.toml` `[output.html.search]` sets `enable`, `limit-results` and `use-boolean-and`.
  mdBook provides no setting for the stop-word list.

## Artifact Traceability

### spec.md

- **Affected user story**: User Story 2, *A user reads the user guide for the version they
  installed*, scenario 3: a reader moving between topics can reach any other.
- **Affected requirements**:
  - **FR-026**: "The site MUST offer full-text search across its pages." The search is full-text
    except for a fixed list of common words. One of those words is the name of a guide topic.
  - **FR-023a**: "a search for each guide topic returns that topic's own page first" is asserted
    automatically. The assertion holds, but only for the query the check happens to build.
  - **SC-006**: a reader finds the page for a topic in under 30 seconds by navigation or search. It
    still holds through navigation.
- **Gap identified**: the spec assumes that a topic's name is something search can find. It never
  considers that the name of a topic, or of something in the application, might be a word search
  ignores. Neither the *Edge Cases* nor the *Assumptions* mention stop words.

### plan.md

- **Affected sections**: *Technical Context*, "mdBook (site generation + built-in client-side
  search …)"; *Complexity Tracking*, the mdBook row ("client-side search … ships its search index
  as a static file").
- **Impact**: the plan adopts mdBook's search whole and records no limit on it. Its stop-word
  filtering needs to be recorded, along with what the site does about it.

### research.md

- **Affected sections**: §1 (mdBook and "its built-in (elasticlunr) client-side search"), and the
  verification table's row "A search for each guide topic returns that topic's page first".
- **Impact**: §1 says the search meets FR-026 "out of the box". That needs the stop-word caveat.

### contracts/site-checks.md

- **Affected**: the *Search* row, "a query for a guide topic does not return that topic's own page
  first".
- **Impact**: the contract does not say which query. `site/checks/page-checks.mjs` builds it from
  the page's heading with punctuation removed, so *Help & About* becomes `Help About`. With
  `use-boolean-and`, `about` is dropped, the query becomes `help`, and the check passes. A heading
  made entirely of stop words would be caught; a heading that also contains a searchable word is
  not.

### tasks.md

- **Affected tasks**:
  - **T044**: the search assertion in `page-checks.mjs`.
  - **T039**: its fixture, a site whose search returns the wrong page first.
  - **T002**: `site/book.toml` search configuration.
- **False completions**: none. T044 does what it says; the check's query simply cannot reach this
  case.
- **Missing tasks**:
  - A regression check that searches each word of a guide topic's heading on its own (or at least
    each word that names a topic) and fails when a word returns nothing. Seen red on `main` for
    `about`.
  - A fix that keeps topic words searchable. Candidates for the plan to weigh: a site-side list of
    words to remove from elasticlunr's stop-word set before the searcher runs, applied at index
    time as well as query time; or an alias in the page's searchable text. Whichever is chosen
    must hold under both the indexer and the browser.

## Root Cause Analysis

The site uses mdBook's search unmodified, and the research treated it as meeting "full-text search"
without checking what the indexer drops. The automated SC-006 check was written to prove each topic
page is found *first*. It derives one query from each heading, and a query with any searchable word
left in it passes. So the check could never show that a single word naming a topic is unsearchable.

## Recommended Fix

1. Run `/speckit.bugfix.patch` to add the stop-word edge case to spec.md (FR-026 / *Edge Cases*),
   record the limit and the chosen answer in plan.md and research.md §1, and add the per-word
   search check and the fix to tasks.md.
2. Run `/speckit.bugfix.verify` to confirm consistency.
3. Resume `/speckit.implement`: write the failing check first, then the fix. The live site changes only at
   the next release: a `pages.yml` dispatch builds `site/` from the release tag.
