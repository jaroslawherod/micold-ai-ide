# Bug Report: A `claude` session whose CLI never wrote an `ai-title` reads "New session" for good

**Type**: Dependency issue (with the spec gap it exposes)
**Severity**: Medium
**Feature**: 029-persistent-session-names
**Reported**: 2026-09-19
**Status**: Open. The fix needs new behaviour, so it goes to a new spec (Phase 1),
[032-untitled-session-labels](../../032-untitled-session-labels/spec.md); see *Size decision*.

## Description

User report, verbatim: "bug: see the screen show the name of past session is still not displayed
even when the bug was reported and fixed".

The screenshot shows the `micold-ai-ide` sidebar with five worktrees, one `claude` session each.
Four rows read "New session", running or not. One row reads a real name, "Merge when CI is green".
The user expects a session that has had a conversation to show a name, and expected feature 029 to
have made that happen.

### When `claude` titles a conversation: observed, not explained

The four conversations **do** contain prompts the user typed. For example:

- `9a536c7e`: line 1112 `the link should change cursor icon when it's clickable`, plus `continue`
  and `rebase main`.
- `e0912fd9`: line 479 `Don't label Cancel differently, keep "Cancel"`.
- `f2e8ef75`: line 573 `continue`.
- `2dc1bd13`: line 387 `continue`.

Even so, `claude` wrote no `ai-title` for any of them. Other sessions get one straight after a late
plain prompt: `9a657bb1` at line 712 (`merge it when CI is green`) → line 715, and `67438aa4` at
2082 → 2084.

Survey of the 80 most recently modified transcripts in `~/.claude/projects` (`claude` 2.1.226 to
2.1.278):

- 65 have an `ai-title`.
- 5 have no plain typed prompt and no title.
- 10 have a plain typed prompt but still no `ai-title`: the four above plus `1f927e58`, `e848aa8b`,
  `87ecd9fd`, `9038f40a`, `7ae664ba` and `ebb422ba`.

So **when `claude` decides to title a conversation is not known.** The facts that matter here:

- The CLI's title is **absent** for a real share of conversations with content: 15 of 80 recent
  ones, 4 of the 5 rows in the report.
- The fix cannot wait for `claude` to title every conversation.

`claude` names these conversations in one other place, `~/.claude/sessions/<pid>.json` `"name"`.
That value is `"<worktree>-<hex>"` with `"nameSource":"derived"`: it comes from the cwd, not the
conversation, and exists only while the process runs. Transcripts can also carry
`{"type":"custom-title"}` (from `/rename`) and `{"type":"agent-name"}` records. The four reported
transcripts have neither; see the ledger's follow-ups for what 029 does with them.

## Artifact Traceability

### spec.md

- **Affected user stories**: US1 (find my session again after a restart) and US2 (existing sessions
  get their names back). Both assume every session worth finding has a name somewhere.
- **Affected requirements**:
  - **FR-004**: "MUST NOT record or display a name for a session that has never had one; such a
    session MUST continue to show the neutral 'New session' placeholder." The code does exactly
    this. By the spec's definition, a `claude` conversation the CLI never titled "has never had" a
    name.
  - **FR-006 / FR-010**: "recover the name from the AI CLI's own records … when one is available
    there". For these sessions no title is available there.
  - **Assumptions**: "The name already has a single source — the AI CLI's title for the
    conversation — and this feature changes when and where that name is remembered, not where it
    comes from." And, in US2: "each of them has a real name recorded by the AI CLI that ran it".
- **Gap identified**: the spec assumes that a conversation with content has a CLI-recorded title.
  For `claude` that is false for a real share of conversations: 15 of the 80 most recent, and 4 of
  the 5 rows in the report. The spec
  has no requirement for how such a session is labelled, other than FR-004's placeholder, which is
  exactly what the user reports as the bug.

### plan.md / research.md

- **Affected sections**: research R1 (the OSC-0 title is the name), R4 (recovery reads
  `AiCliProvider::read_title`, the transcript's `ai-title`), and the plan's Summary.
- **Impact**: both name sources the plan chose are downstream of `claude` producing an `ai-title`.
  Neither can name a session `claude` never titled. Any fix needs a new source of a label. Feature
  `029-pi-cli-provider` research R5 already made that choice for `pi`: the latest `session_info`
  name, else the **first user message**, else the placeholder. That matches `pi`'s own picker.

### tasks.md

- **Affected tasks**: T012–T016 (recovery) and T025 / T030 (a CLI's own placeholder title is not a
  name).
- **False completions**: none. Every task does what it says, and the gates test what the spec asks.
  The T024/T027 quickstart passes named sessions with a typed prompt (or a stand-in CLI that writes
  `ai-title`), so they could not have exposed this.
- **Missing tasks**: a label source for a `claude` conversation that has content but no
  `ai-title`. It is not a task that fits this spec. See *Size decision*.

## Root Cause Analysis

`ClaudeProvider::read_title` / `parse_title` (`crates/micold-core/src/provider.rs:337`, `:426`) take
a session's name only from `ai-title` transcript records. `ClaudeProvider::name_in_terminal_title`
(`:432`) takes it only from a non-default OSC-0 title, which `claude` sets from the same title.
For some conversations with typed prompts, `claude` never writes that title, and nothing on this
machine explains when it does or does not. Such a conversation gets no name from either source. FR-004
then keeps the placeholder by design, across every restart. Feature 029's persistence
(`record_session_name`, `recover_session_names`) works as specified: it records and recovers every
name that exists (row `9a657bb1` shows this). There is no name for these four rows.

In short, this is a dependency behaviour the spec's assumption did not anticipate, not
implementation drift.

## Size decision

The change the user wants needs a label for a session the CLI never named. That contradicts FR-004
and the spec's "single source" assumption as written, so it is **behaviour this spec never
intended**. Per the autopilot's Phase 0 step 5 and the bug rubric ("new behaviour … sends the flow
to Phase 1"), 029 is not patched. A new spec takes this BUG as its input. Questions for that spec's
clarify phase:

- **The label source for a `claude` session with no `ai-title`.** Candidates:
  - the first plain typed prompt (every one of the four reported sessions has one);
  - the first turn's text, and for a slash-command turn its `<command-args>` text, or else the
    command name;
  - the `pi` precedent (first user message).
- **Precedence.** A later `ai-title` replaces a fallback label, but a fallback label must never
  replace an `ai-title`. FR-005 is "latest known name". The recorded fallback also has to be told
  apart from a real name, or recovery (C15) will never look again.
- **Whether GitHub Copilot needs the same treatment.**
- **Whether to reduce the noise of the latest-typed-prompt titles** `claude` produces ("Status", "M2
  progress").

## Recommended Fix

1. Phase 1: specify how a session with content but no CLI title is labelled, citing this BUG and
   its reproduction.
2. Do not run `/speckit.bugfix.patch` on 029. It would add new behaviour to a closed spec.
