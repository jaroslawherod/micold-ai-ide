# Bug Report: recovery restores the pre-rename `ai-title`, so a `/rename` is lost

**Type**: Untested flow (the AI CLI's records hold more than one name record, and the code reads the
older one)
**Severity**: Medium
**Feature**: 029-persistent-session-names
**Reported**: 2026-09-26
**Status**: Open

## Description

Carried from [BUG-001](./BUG-001.md)'s follow-ups (`BUG-001.autopilot.md` § *Follow-ups not done*)
and confirmed by the user as the next thing to fix:

> `ClaudeProvider::parse_title` (`crates/micold-core/src/provider.rs:384`) reads only `ai-title`. It
> ignores the transcript's `{"type":"custom-title","customTitle":…}` records, written by the user's
> `/rename`. Also `agent-name` records exist. This may break FR-005 / FR-006.

`claude`'s `/rename` is how a user names a conversation by hand. The CLI records that name in the
transcript and keeps using it — but it *also* keeps writing the **pre-rename** `ai-title` on every
later turn. Because `parse_title` looks at `ai-title` alone, every path that reads a session's name
from the CLI's records takes the name the user replaced, not the one they chose.

## Reproduction

### What `claude` writes after a `/rename` (observed, not assumed)

`claude` 2.1.x writes three kinds of name record. In the 4 transcripts on this machine that carry
`agent-name`, the pattern is exact:

| Transcript | `custom-title` | `ai-title` | `agent-name` |
|---|---|---|---|
| `c4cc3dca…` (`feat-windows-package`, renamed) | `"Windows package"` | `"PR 284 macOS feature"` | `"Windows package"` |
| `6975d155…` | — | `"speckit-autopilot-flow"` | `"speckit-autopilot-flow"` |
| `2ed436c6…` | — | `"Token usage optimization"` | `"Token usage optimization"` |
| `866d3b58…` | — | `"session-title-sync"` | `"session-title-sync"` |

So `agent-name` is the CLI's **current** display name: the `custom-title` when the user renamed,
else the `ai-title`. In `c4cc3dca…` the three records are re-emitted together on every later turn —
lines 12016–12018, 12037–12039, 12058–12060, 12080–12082 — with `ai-title` frozen at the pre-rename
value. A rename is therefore permanent in the CLI's own records, and the `ai-title` beside it is
stale by construction.

Command that produced the table:

```bash
grep -rln '"type":"agent-name"' ~/.claude/projects/*/*.jsonl
grep -n '"type":"custom-title"\|"type":"agent-name"\|"type":"ai-title"' <transcript> | tail
```

### Failing on `origin/main` (`affd23c0`)

A throwaway `micold-core` test (deleted after the run; the output is in the ledger's *Reproduction on
origin/main*) calls `ClaudeProvider.read_title` over a temp `<config>/projects/<encoded cwd>/<id>.jsonl`:

1. **Synthetic fixture** in the exact record order above (`custom-title`, then the pre-rename
   `ai-title`, then `agent-name`):
   `read_title` ⇒ `Some("PR 284 macOS feature")`, expected `Some("Windows package")`.
2. **The real transcript** `c4cc3dca-36e3-4480-b76f-27ad4584181c.jsonl`, copied into the temp layout:
   `read_title` ⇒ `Some("PR 284 macOS feature")`, while `claude`'s own name for that conversation is
   `"Windows package"`.

Both failed; every other `micold-core` test passed.

### What that costs the user

`read_title` is the app's record-reading name source, and it feeds two paths:

- `DaemonState::discover_external_sessions` (`crates/micold-daemon/src/state.rs:1226`) adopts a
  session it has never seen as `SessionLabel::Named(read_title(…))` and persists it. For a renamed
  conversation that is the pre-rename `ai-title`. FR-008 then guarantees the name is **never
  re-read**, so the rename is lost for good — the row reads `"PR 284 macOS feature"` for ever.
- `DaemonState::record_recovered_names` (`state.rs:1381`, from `recover_session_names` /
  `recover_live_session_names`) does the same for any session that is still `Pending` or `Derived`
  (feature 032): recovery writes the **older** of the two names the CLI holds.

Why the four rows of BUG-001 did not show this, and why the row on this machine happens to be right:
`c4cc3dca…` was running inside the app when it was renamed, so the live path got there first.
`claude` sets its OSC-0 title to the *current* name, `record_observed_names` recorded it, and the
catalog entry reads `"title": "Windows package"`
(`~/.local/share/micold-ai-ide/projects/8d4b6897c9929be6.json`) — recorded from the terminal, never
from the transcript. That catalog row is the proof that the app's two name sources disagree: the
live one gives the rename, the record-reading one gives the name the user replaced. The loss lands
on every renamed session the app did not watch being renamed: one discovered from disk, one adopted
after the catalog is lost or on another machine, one renamed in a `claude` run outside the app, or
one still showing a 032 derived label.

## Artifact Traceability

### spec.md

- **Affected user stories**: US2 (existing sessions get their names back) and US3 (the name stays
  true to the conversation).
- **Affected requirements**:
  - **FR-005**: "the remembered name is the latest known name, never the first". Violated: the CLI's
    records hold a newer name (`custom-title`, mirrored in `agent-name`) and the app records the
    older `ai-title`.
  - **FR-006 / FR-010**: "recover the name from the AI CLI's own records for that conversation when
    one is available there". The name available there is the rename; the app recovers a different
    string.
  - **FR-011**: "A session's name MUST remain derived from its conversation and MUST NOT become
    user-editable **as a consequence of this feature**." Honouring `/rename` does not breach this:
    the name is still read from the conversation's own store, and nothing in this application becomes
    editable. `/rename` is the CLI's record of the conversation's name, which is what FR-006 reads.
- **Gap identified**: the spec treats "the AI CLI's title for the conversation" as a single record
  kind. For `claude` it is three, and the one the code reads is not the one the CLI itself displays.
  No requirement says *which* record wins, so nothing caught it.

### plan.md / research.md

- **Affected sections**: research R4 (recovery reads `AiCliProvider::read_title`, "the transcript's
  `ai-title`") and the plan's Summary.
- **Impact**: R4's choice of record is too narrow. It needs the CLI's current name — the latest
  `custom-title`, else `agent-name`, else `ai-title` — with no change to the pass's shape, cost or
  precedence against the live terminal title.

### tasks.md

- **Affected tasks**: T012–T016 (US2 recovery: the pass reads the wrong record), and T014's read
  through `read_title` in particular. T017 (FR-005 "a second, different name replaces the first")
  tests the catalog's replacement, not which record the name came from, so it could not have caught
  this.
- **False completions**: none. `parse_title` predates this feature; 029 consumed it as written, and
  every 029 task does what it says. The defect is the record kind the read is scoped to, which no
  029 requirement pinned down.
- **Missing tasks**: a title read that returns the CLI's current name for a `claude` conversation,
  with a regression gate, plus a contract line fixing the precedence. See *Size decision*.

## Root Cause Analysis

`ClaudeProvider::parse_title` (`crates/micold-core/src/provider.rs:384`) accepts only
`{"type":"ai-title"}` records. `claude` keeps re-emitting the pre-rename `ai-title` after a
`/rename` and records the chosen name as `custom-title` (and as `agent-name`, its resolved display
name), so "the latest `ai-title`" is not the conversation's current name. Every caller of
`read_title` — `discover_external_sessions` (`state.rs:1226`) and `record_recovered_names`
(`state.rs:1381`) — therefore persists the replaced name, and FR-008 makes that write permanent.

This is a missed record kind in a dependency's format, not implementation drift: the spec's FR-005
and FR-006 already require the latest name from the CLI's own records.

## Size decision

**One milestone, patching 029.** The behaviour asked for — record the name the CLI currently holds
for the conversation — is what FR-005 and FR-006 already require; it adds no user-facing behaviour
and no new UI. Feature 032 reached the same conclusion independently, listing this under its *Out of
scope*: "Honouring a user's `/rename` (`custom-title` records) or `agent-name` records over the AI
CLI's title. **That is a candidate 029 bug**" (`specs/032-untitled-session-labels/spec.md:391`).

Interaction with 032, checked: 032's precedence is title-over-label, and a title still outranks a
`Derived` label (`state.rs:1226`, `record_recovered_names`' two-kind check, C6.3/C6.6). This fix
changes only *which string* `read_title` returns, never whether a title exists, so 032's rules are
untouched. 032's C1.4 gate — "`read_title` still returns the latest `ai-title` for a file `read_label`
reads" (`tests/ai_cli_provider.rs:402`, U49) — keeps passing: its fixture has no `custom-title`.

## Recommended Fix

1. `speckit-bugfix-patch` on 029: clarify FR-005/FR-006 and research R4 that the name is the AI
   CLI's **current** name for the conversation when its records hold several, and add the record
   precedence to `contracts/session-name-persistence.md`.
2. One milestone through the Phase 4 loop, first task a regression test:
   `ClaudeProvider::parse_title` returns the latest `custom-title`; else the latest `agent-name`;
   else the latest `ai-title`; an empty value in any of them is not a name. Order between kinds does
   not matter — a rename is sticky in the CLI's records, so kind ranks above position.
3. `speckit-bugfix-verify`, then the bug rubric review.
