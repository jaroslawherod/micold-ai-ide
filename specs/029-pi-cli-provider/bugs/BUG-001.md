# Bug Report: Pi is not offered when `pi` is on the session's PATH but not the daemon's

**Type**: Spec gap
**Severity**: High
**Feature**: 029-pi-cli-provider (reported on branch `fix/ican-t-start-pi-codeing-session`)
**Reported**: 2026-09-18
**Status**: Patched
**Patched**: 2026-09-18

## Description

User report: "I would like to start pi coding session in same way as I start copilot or claude
session but I don't see such option."

Pi does not appear in the Settings default, the per-session override, or anywhere else a CLI is
chosen. Claude Code and GitHub Copilot do. Pi is installed and works in the user's terminal.

Observed on the reporter's machine (installed build of 2026-09-16, which contains Pi support —
`strings /usr/bin/micold-daemon` finds "Pi Coding Agent"):

- Placement is `host_process` (`~/.local/share/micold-ai-ide/settings.json`).
- `claude` and `copilot` live in `~/.local/bin`, which is on the desktop session's `PATH`.
- `pi` was installed with `npm install -g` under mise's Node, so it lives only at
  `~/.local/share/mise/installs/node/24/bin/pi` (plus a mise shim in
  `~/.local/share/mise/shims/pi`). Neither directory is on the desktop session's `PATH`. They are
  added by `~/.bashrc` (`mise activate bash`, and an explicit `export PATH=…/node/24.21.0/bin:$PATH`),
  which only interactive shells run.
- The running `micold-daemon` (started by `/usr/bin/micold-ai-ide`) has
  `PATH=/home/jaro/.cargo/bin:/home/jaro/.local/bin:/home/jaro/bin:/usr/local/sbin:…:/snap/bin:…`
  — no mise, no Node.
- `PiProvider::is_available()` is `resolves_on_path("pi")` against the daemon's own `PATH`, so it
  answers "not available" and FR-003 hides Pi.

Installing `pi` through `npm install -g` under a Node version manager (mise, nvm, fnm, volta) is the
ordinary way to install it, so this is the common case for Pi users, not an edge case. Claude Code
and Copilot escape it only because their installers drop a binary into `~/.local/bin`.

Secondary observation: the reporter's settings also hold `"env_include_enabled": false` with
`"env_include_script_path": "/tmp/does-not-exist.sh"`. That path looks like a test fixture, not a
user choice, and suggests a test or visual pass once wrote to the real settings file. It does not
cause this bug on its own (see Root Cause), but with the default (`~/.bashrc`, on) a Pi session
would find `pi` if it were offered.

## Artifact Traceability

### spec.md

- **Affected user story**: User Story 1 — Start and resume a session on Pi (P1). Acceptance
  scenarios 1 and 2 cannot be reached. Scenario 5 ("Pi is not installed where sessions run … Pi is
  not offered") fires for a Pi that *is* installed where sessions run.
- **Affected requirements**:
  - **FR-001** — Pi MUST be offered everywhere a CLI is chosen "on identical rules to the existing
    CLIs". The rules are identical; the outcome is not, because the rule is only sound for CLIs whose
    installer writes to a directory the desktop session already has on `PATH`.
  - **FR-003** — "MUST NOT offer Pi when `pi` cannot be found **where sessions actually run** —
    inside the sandbox under sandboxed placement, on the host under host placement." Under host
    placement a session runs with the environment feature 011 builds (the env-include script,
    `~/.bashrc` by default), not with the daemon's bare process environment. The spec does not say
    which of the two "where sessions actually run" means, and the implementation picked the one
    sessions do not use.
  - **FR-003a** — availability MUST remain "the presence check every provider gets" and MUST NOT
    cost more for Pi. Any fix has to stay a presence check and apply to every provider, not a
    Pi-specific probe.
  - **SC-001** — "A user with Pi installed starts a Pi session in the same number of interactions"
    as the other CLIs. Not met: the user cannot start one at all.
- **Gap identified**: The spec never defines the environment the availability check runs in. It
  inherits feature 026's assumption that the session service's `PATH` is the user's `PATH`
  (026 FR-006/FR-010, and `docs/user-guide/settings.md` line 68 even names "a `PATH` that hasn't
  loaded" as a transient case). That assumption conflicts with feature 011, which exists precisely
  because the session service's `PATH` is *not* the user's — "PATH additions from version managers
  (nvm, pyenv, rbenv)" come from the shell startup file. There is also no requirement that a
  hidden CLI be explained anywhere: a CLI that is not found simply is not listed, so the user gets
  no hint about why Pi is missing or what to do.

### plan.md

- **Affected sections**: Summary (line 16: "the `PATH` availability check all fit the [seam]"),
  Technical Context (lines 101–102: "`PATH` lookup goes through the existing `resolves_on_path`").
- **Impact**: The plan must say which `PATH` availability is resolved against. The consistent answer
  is the same environment a session is spawned with: under host placement, the daemon `PATH`
  overlaid with the env-include result when env-include is enabled; under sandboxed placement,
  unchanged. It must also say how that environment is obtained without making availability cost
  more (FR-003a) — for example, reusing the env-include capture the daemon already performs for
  spawns, cached and refreshed when the env-include settings change, rather than running the
  startup script on every availability request. This touches the provider seam for all CLIs
  (feature 026), not only Pi (FR-020, FR-021).

### tasks.md

- **Affected tasks**:
  - **T019** [X] — "Implement `PiProvider::is_available()` … through the existing
    `resolves_on_path("pi")`". Done as specified; the specification is what is wrong.
  - **T031** [X] — Pi appears in the Settings default and per-session override. Its test assumes
    `pi` is on the test process's `PATH`, so it never exercises the version-manager install.
  - **T032** [X] — missing `pi` is reported by name. Covers the stored-default case only; nothing

- **False completions**: None in the strict sense — T019, T031 and T032 do what they say. T019

- **Missing tasks**:
  - A failing test first: under host placement with env-include enabled, a CLI found only on the
    env-include `PATH` is reported available (and one found on neither is not).
  - Resolve availability against the session spawn environment (daemon `PATH` plus env-include
    overlay under host placement), for every provider, without a per-request script run.
  - Refresh availability when env-include settings change.
  - User-guide update: explain that availability follows the session environment, and what to do
    when a CLI installed through a version manager is not offered (enable env-include, or install
    to a directory on the login `PATH`).
  - Investigate how a fixture path (`/tmp/does-not-exist.sh`) reached the reporter's real
    `settings.json`, and make the offending test use a private data directory.

## Root Cause Analysis

Spec oversight inherited from feature 026. The availability check was specified as "found on
`PATH`" without naming *whose* `PATH`. The daemon checks its own process environment, which a
desktop-launched application inherits from the login session. Sessions, however, are spawned with
the env-include environment from feature 011, which is where version-manager paths live. So the
application can refuse to offer a CLI that a session it started would have run without trouble.
Claude Code and Copilot hide the flaw because their installers write to `~/.local/bin`; Pi, an npm
package, exposes it for most of its users.

## Recommended Fix

1. Run `/speckit.bugfix.patch` to update spec artifacts (FR-003's definition of "where sessions
   actually run", plan Technical Context, reopen T019 and add the missing tasks above).
2. Run `/speckit.bugfix.verify` to confirm consistency.
3. Resume `/speckit.implement` to apply the code fix.

Workaround until fixed: make `pi` reachable from the login session's `PATH`, for example
`ln -s ~/.local/share/mise/shims/pi ~/.local/bin/pi`, then restart the application so the daemon
is restarted.
