# BUG-001 verification — a CLI on the session's `PATH` is offered and starts

Recorded 2026-09-26, for task T070 on milestone M1 of the BUG-001 bugfix.

The bug: the session service decided which AI CLIs were installed by walking its **own** process
`PATH`. A `pi` reachable only through the environment-include script — the ordinary result of
`npm install -g` under a Node version manager — was therefore never offered, and would also have
been refused at launch. The fix resolves availability against the `PATH` a session spawned in that
directory would actually receive (FR-003b, SC-001a, SC-006a, US1 scenario 5b).

- `scripts/build-lock.sh cargo check --workspace --target aarch64-apple-darwin` green. The diff adds
  no `cfg` arm, but it changes the availability seam every provider implements and the doc comment
  that describes what a Windows spawn inherits, so the second host target was checked as well.

Two earlier runs failed for reasons outside this change, both from sharing one target directory
across worktrees:

- `failed to move dependency graph … No such file or directory` under
  `target-shared/debug/incremental` — another session reclaiming disk by deleting the incremental
  directory mid-build.
- `crates/micold-daemon/tests/autospawn.rs` refusing a cold start with
  `VersionMismatch { client: 14, daemon: 14, … }`, the same protocol number either side but different
  schema hashes. The test spawns the daemon binary at `CARGO_BIN_EXE_micold-daemon`, which resolves

  14 for a different wire change. So the binary on disk was one of theirs, and it was rewritten
  twice while the gate ran. Run on its own, `cargo test -p micold-daemon --test autospawn` passes,
  which settles it. CI builds each branch by itself, where the pair always matches.

## The behaviour itself, through the daemon protocol

The three acceptance behaviours are pinned end to end through `AiCliAvailabilityRequest` and
`start_session`, each red before green in `tdd/cycle-log.md`:

| Behaviour | Test | Red evidence |
|---|---|---|
| A1 — with `pi` only on the `PATH` environment-include adds for a directory, a request for that directory lists Pi | `a_cli_on_the_path_env_include_adds_for_a_directory_is_offered_for_it` (`crates/micold-daemon/tests/ai_cli_availability.rs`) | `left: []`, `right: [Pi]` — the service answered from its own `PATH` and found nothing |
| A2 — starting a Pi session in that directory is not refused as a missing CLI | `a_cli_only_on_the_env_include_path_starts_rather_than_being_reported_missing` (`crates/micold-daemon/tests/session_start.rs`) | `Err(NotFound, "Pi Coding Agent isn't installed…")` — offered, then refused at the launch gate |
| A3 — with environment-include off, the same request does not list Pi | `with_env_include_off_a_cli_only_the_script_would_add_is_not_offered` (`crates/micold-daemon/tests/ai_cli_availability.rs`) | green on the first run, then confirmed against a deliberate mutant, which answered `[Pi]` |

Each of these runs a real environment-include script that prepends a temporary directory holding a
fake `pi` to `PATH`, with the service's own `PATH` lacking it — the reporter's situation, reduced to
what a test can hold. A2 is the half the original patch missed: a CLI can be offered and then
refused a second later by a launch-time check that walks a different `PATH`.

Alongside them, `crates/micold-core/tests/available_in.rs` pins the seam directly: a CLI found only
on the given `PATH` is available, one held only by the process's own `PATH` is not, and an empty
`PATH` resolves nothing rather than falling back to the current directory.

## What the reporter has to do

Their `settings.json` holds `env_include_enabled: false`. With environment-include off, this fix
changes nothing for them: the service falls back to its own `PATH`, which is where `pi` is missing.
They have to turn environment-include back on — or put `pi` on the login `PATH`, which
`docs/user-guide/settings.md` now explains as the alternative.

## Not covered

- Rendering at a display; see above.
- Windows. `supervisor::prefer_process_path` gives a child this process's `PATH` followed by the
  registry's, so the fallback `PATH` the service checks is a subset of what a spawn gets there. That
  direction is safe — nothing is offered that would then fail to start — and is recorded as a
  follow-up in the ledger rather than fixed here.
- A CLI that only a *project-local* environment-include script adds. The start affordance's chevron
  and its primary press read one availability set, which after a reconnect holds the home
  directory's answer. Recorded in the ledger under declined findings and follow-ups.
