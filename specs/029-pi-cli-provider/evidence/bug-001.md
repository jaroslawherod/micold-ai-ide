# BUG-001 verification — a CLI on the session's `PATH` is offered and starts

Recorded 2026-09-26, for task T070 on milestone M1 of the BUG-001 bugfix.

The bug: the session service decided which AI CLIs were installed by walking its **own** process
`PATH`. A `pi` reachable only through the environment-include script — the ordinary result of
`npm install -g` under a Node version manager — was therefore never offered, and would also have
been refused at launch. The fix resolves availability against the `PATH` a session spawned in that
directory would actually receive (FR-003b, SC-001a, SC-006a, US1 scenario 5b).

## Local gate

- `mise run gate` green on the branch head: `cargo fmt --check`, clippy on `micold-core` and then
  the workspace with `-D warnings`, `cargo test --workspace`, then every `scripts/tests/*.test.sh`.
- `scripts/build-lock.sh cargo check --workspace --target aarch64-apple-darwin` green. The diff adds
  no `cfg` arm, but it changes the availability seam every provider implements and the doc comment
  that describes what a Windows spawn inherits, so the second host target was checked as well.

Two earlier runs failed for reasons outside this change, both from sharing one target directory
across worktrees:

- `failed to move dependency graph … No such file or directory` under
  `target-shared/debug/incremental` — another session reclaiming disk by deleting the incremental
  directory mid-build.
- `crates/micold-daemon/tests/autospawn.rs` refusing a cold start with
  `VersionMismatch { client: 14, daemon: 14, … }`, the same protocol number either side but different
  schema hashes. The test spawns the daemon binary at `CARGO_BIN_EXE_micold-daemon`, which resolves
  into the shared `target-shared/debug/`, and three worktrees have each bumped `PROTOCOL_VERSION` to
  14 for a different wire change (this branch has since been rebased, and its own bump is now
  14 → 15). So the binary on disk was one of theirs, and it was rewritten
  twice while the gate ran. Run on its own, `cargo test -p micold-daemon --test autospawn` passes,
  which settles it. CI builds each branch by itself, where the pair always matches. After the branch was
  rebased onto `main` — which moved this change's own bump to 14 → 15, feature 032 having taken 14 —
  the gate and the macOS cross-check both ran clean end to end.

## The behaviour itself, through the daemon protocol

The three acceptance behaviours are pinned end to end through `AiCliAvailabilityRequest` and
`start_session`, each red before green in `tdd/cycle-log.md`:

| Behaviour | Test | Red evidence |
|---|---|---|
| A1 — with `pi` only on the `PATH` environment-include adds for a directory, a request for that directory lists Pi | `a_cli_on_the_path_env_include_adds_for_a_directory_is_offered_for_it` (`crates/micold-daemon/tests/ai_cli_availability.rs`) | `left: []`, `right: [Pi]` — the service answered from its own `PATH` and found nothing |
| A2 — starting a Pi session in that directory is not refused as a missing CLI | `a_cli_only_on_the_env_include_path_starts_rather_than_being_reported_missing` (`crates/micold-daemon/tests/session_start.rs`) | `Err(NotFound, "Pi Coding Agent isn't installed…")` — offered, then refused at the launch gate |
| A3 — with environment-include off, the same request does not list Pi | `with_env_include_off_a_cli_only_the_script_would_add_is_not_offered` (`crates/micold-daemon/tests/ai_cli_availability.rs`) | green on the first run, then confirmed against a deliberate mutant, which answered `[Pi]` |

Each of these runs a real environment-include script that prepends a temporary directory holding a
fake `pi` to `PATH`, with the service's own `PATH` lacking it — the reporter's situation, reduced to
what a test can hold. A2 is the half the original patch missed: a CLI can be offered and then
refused a second later by a launch-time check that walks a different `PATH`.

Alongside them, `crates/micold-core/tests/available_in.rs` pins the seam directly: a CLI found only
on the given `PATH` is available, one held only by the process's own `PATH` is not, and an empty
`PATH` resolves nothing rather than falling back to the current directory.

## Quickstart §B at a display

**Run to completion on 2026-09-26, and all three behaviours were seen.** The pass used a private
Xvfb display with its own runtime, data and config directories, and a client/daemon pair built from
this branch and pinned outside the shared target directory, so that no other worktree's build could
swap the binaries mid-run.

The setup is the reporter's situation, reduced to something a headless run can hold. The client was
launched with `PATH=/usr/bin:/bin` — no `pi`, no `claude`, no `copilot` on it — and it
autospawned the daemon, which inherits that `PATH`. Settings had `env_include_enabled: true` and an
`env_include_script_path` pointing at a script whose only line prepends a scratch directory holding
two executable stubs, `pi` and `claude`, each of which prints its own name and arguments and then
sleeps. So every CLI the application could possibly offer was reachable **only** through the
environment-include script, and none of them through the service's own `PATH`. Before the fix that
configuration offered nothing.

1. **The Settings default-CLI selector draws a "Pi Coding Agent" entry** —
   `bug-001-settings-default-cli.png`. Settings → Environment → *Default AI CLI*, opened,
   lists "Claude Code" (the current selection) and "Pi Coding Agent". Above the list the helper text
   reads "GitHub Copilot isn't installed on this computer, which is where sessions run", which is the
   same answer from the other direction: the one stub that was *not* placed is the one name that is
   missing, so the list is being filled from the script's `PATH` and not from a static table.

2. **The per-session start/override list on a sidebar row draws it too** —
   `bug-001-session-override.png`. Hovering the `Default` row in the Worktrees sidebar reveals the
   chevron beside the `+`; pressing it opens "Claude Code" and "Pi Coding Agent", cleanly drawn, no
   clipping and no glyph collisions. The chevron only appears when more than one CLI is available,
   which is why the second stub was needed to see this control at all.

3. **Choosing Pi starts a session rather than reporting the CLI missing** —
   `bug-001-session-started.png`. Pressing "Pi Coding Agent" started a session instead of the
   "isn't installed" refusal. The terminal's first line is the stub announcing how it was invoked:
   `pi stub --session-id 3e9a4035-7076-4fc7-a066-a7580ba380ab -e <data>/pi/pi-activity.ts`. That id
   is the application's own session id — the daemon log records `session started
   session=3e9a4035-7076-4fc7-a066-a7580ba380ab mode=AiCli launch=Fresh` at the same moment —
   which is FR-005a's identity carried on the command line, and the `-e` argument is the activity
   extension. The sidebar row shows the new session with a `pi` badge and the status bar reads
   "New session  running" beside a pinned AI tab labelled `pi`.

So the rendering half of T070 is no longer resting on inference. The controls draw the entry the
service now sends them, and the launch gate that used to refuse a second later lets the session
through.

One thing is worth recording because it cost the run an attempt. `Settings.settings_version`
(`crates/micold-core/src/settings.rs`) carries no `#[serde(default)]`, so a hand-written
`settings.json` that omits the field fails to deserialize; `load()` then moves the file aside to
`settings.json.bak` and silently falls back to defaults. The first attempt therefore ran against the
default environment-include script, `~/.bashrc`, rather than the one it had written, and only the
Settings screen showing `/home/jaro/.bashrc` in the script-path field gave it away. Adding
`settings_version` fixed it. That is a seeding hazard for any future headless pass rather than a
defect this bugfix introduced, and it is not part of BUG-001; it is noted in the ledger as a
follow-up.

## What the reporter has to do

Their `settings.json` holds `env_include_enabled: false`. With environment-include off, this fix
changes nothing for them: the service falls back to its own `PATH`, which is where `pi` is missing.
They have to turn environment-include back on — or put `pi` on the login `PATH`, which
`docs/user-guide/settings.md` now explains as the alternative.

## Not covered

- Windows. `supervisor::prefer_process_path` gives a child this process's `PATH` followed by the
  registry's, so the fallback `PATH` the service checks is a subset of what a spawn gets there. That
  direction is safe — nothing is offered that would then fail to start — and is recorded as a
  follow-up in the ledger rather than fixed here.
- A CLI that only a *project-local* environment-include script adds. The start affordance's chevron
  and its primary press read one availability set, which after a reconnect holds the home
  directory's answer. Recorded in the ledger under declined findings and follow-ups.
