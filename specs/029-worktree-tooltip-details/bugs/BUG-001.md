# Bug Report: A worktree row's tooltip covers that row when it sits at the bottom of the window

**Type**: Untested flow
**Severity**: Medium
**Feature**: 029-worktree-tooltip-details (Worktree tooltip shows the full name and its details)
**Reported**: 2026-09-27
**Status**: Patched
**Patched**: 2026-09-27

## Description

When the sidebar's worktree list is long enough to reach the bottom of the window and the pointer
enters the last worktree row, the row's hover tooltip is drawn **on top of that row**. The row's
icon, label, chips and trailing actions (for example, the one that starts a new session) are all
hidden under the tooltip panel, so the user cannot see what they are pointing at or where to click.
The tooltip exists to describe the row; at the bottom of the list it replaces it.

Rows higher up are fine: their tooltip opens below them with a small gap.

## Reproduction

On `origin/main` (23a0e0ee), with the client and daemon from the same build:

1. Open a project with enough worktrees that the sidebar's worktree list reaches the bottom of the
   window (25 worktrees in a 1280×720 window is plenty; fewer in a shorter window).
2. Scroll the list to its end, so the last worktree row sits at the bottom edge of the window.
3. Hover a row near the top of the list and wait for the tooltip. **Observed**: the tooltip opens
   below the row, clear of it (control).
4. Hover the last row and wait for the tooltip. **Observed**: the tooltip panel starts above the
   row's top edge and runs to the window's bottom edge; the row's icon, name, chips and actions are
   not visible. **Expected**: the tooltip opens where it does not cover the row, and the row stays
   readable and clickable.

Reproduced 2026-09-27 on a private Xvfb display with the `visual-pass` skill: in a 720px window,
with a row pitch of ≈64px, the last row occupied y≈656–720 and the tooltip panel y≈645–720 — the
whole last row, from just below the previous row's chip to the window's bottom edge.
Screenshot: [evidence/bug-001-bottom-row-covered.png](../evidence/bug-001-bottom-row-covered.png)
— the tooltip reads "Name: Wt 25 …" where the row "Wt 25" itself should be.

The clamp reaches the row for any row whose distance to the window's bottom edge is less than the
tooltip's height (between that and height plus gap it only eats into the gap), so with a four-line tooltip it is usually the last one or two visible rows.

## Artifact Traceability

### spec.md

- **Affected user stories**: all three. Each one has the user hover a row to learn about *that row*
  (User Story 1 "hovers the row and reads the whole name in the tooltip"). A tooltip that hides the
  row it describes defeats the lookup it serves: the user can read which worktree it is, but can no
  longer see or reach the row they were about to act on.
- **Affected requirements**:
  - **Edge Cases**, second bullet: the tooltip "stays readable and bounded — it does not stretch
    past the window or cover the sidebar it describes". The spec guarded against *size* covering the
    sidebar, but not against *placement* covering the very row being hovered.
  - **FR-010**: the tooltip appears on hover "exactly as the current location tooltip does". The
    current location tooltip had the same defect, so FR-010 carried it forward instead of catching
    it.
  - **SC-005**: "The tooltip never extends beyond the application window". This is what the
    rendering stack enforces, and enforcing it is exactly what moves the tooltip onto the row.
  - **Assumptions**, second bullet: "The tooltip stays a single hover surface on the worktree row,
    in the same position it uses today". "The same position" is below the row, which does not exist
    for the last row.
- **Gap identified**: no requirement says the tooltip must leave the row it describes visible. The
  spec never considered a row with no room below it.

### plan.md

- **Affected sections**: Summary item 3 ("The shared `Tooltip` learns to be multi-line"), which
  made the tooltip taller (four or more lines instead of one) and so widened the band of rows it
  covers from part of the last row to the whole of it. The plan names no placement rule.
- **Impact**: the plan needs a placement rule for the shared `Tooltip` and a test layer for it.

### research.md

- **R2**, rejected alternative *Leave it unbounded*: "The rendering stack's own
  `snap_within_viewport` (default `true` in `iced_widget::tooltip`) keeps the tooltip *inside* the
  window". True, but it does so by clamping the tooltip's position, not by flipping it to the other
  side of its anchor. That is the mechanism of this bug, and the research relied on it as a safety
  net without asking where the clamped tooltip lands.

### tasks.md

- **Affected tasks**: T030 (the quickstart §B pass). §B3 expected "Nothing extends past the window
  edge in either direction (the rendering stack snaps it inward)" and checked one row, not the last
  one.
- **False completions**: none. No task promised placement relative to the row, so none is falsely
  ticked; T030 ran the checks §B listed, and those passed.
- **Missing tasks**: a regression test that hovers the last worktree row at the window's bottom
  edge and asserts the tooltip does not intersect the row; the placement fix in the shared
  `Tooltip`; a §B step for the bottom row, rerun with `visual-pass`.

## Root Cause Analysis

Three pieces, each correct on its own:

1. `crates/micold-client/src/ui/material/tree_view.rs:552-553` wraps every row that carries a
   `row_tooltip` in `super::Tooltip::new(interactive, tip, r)` and never sets a position.
2. `crates/micold-client/src/ui/material/mod.rs:248` (`Tooltip::new`) defaults that position to
   `tooltip::Position::Bottom`.
3. `iced_widget-0.14.2/src/tooltip.rs`, overlay `layout` (lines 456–546): the overlay first places
   the panel below the content (`y = content.y + content.height + gap + padding`), then, because
   `snap_within_viewport` defaults to `true`, clamps it: when
   `viewport.y + viewport.height < tooltip.y + tooltip.height`, it sets
   `tooltip.y = viewport.y + viewport.height - tooltip.height`. The viewport is the whole window.
   iced clamps; it never flips to the other side of the content.

So for a row whose bottom edge is closer to the window's bottom edge than the tooltip's height plus
gap, the clamp pulls the panel up by the shortfall, over the row it was placed below. The multi-line
tooltip from this feature (four lines, ≈75px) makes the shortfall larger than a row's height, so the
whole row is covered.

The cause is a spec oversight, not implementation drift: the implementation does what the spec and
plan asked, and neither asked where the tooltip goes when there is no room below the row.
