# Bug Report: The gates restate the minimum window size instead of reading it

**Type**: Implementation drift
**Severity**: Low
**Feature**: 029-worktree-tooltip-details (Worktree tooltip shows the full name and its details)
**Reported**: 2026-09-30
**Source**: GitHub issue #431 (follow-up from BUG-001, PR #425)
**Status**: Patched
**Patched**: 2026-09-30

## Description

`MIN_WINDOW_SIZE` (640×480), the narrowest window the interface is supported at, is a private
constant of the client **binary**, so no integration test can name it. The gates that check the
interface at the minimum window restate it as literals instead:

- `crates/micold-client/tests/gates/tooltip_clears_its_row.rs:35`:
  `const SMALLEST_WINDOW: Size = Size::new(640.0, 480.0);`, with a doc comment saying it is restated
  "because it lives in the binary crate, which no test can reach". Used at lines 456 and 488.
- `crates/micold-client/tests/known_projects_reflow.rs:38`: `(640.0, "the minimum window, no project
  open")` (written for spec 003, T036).

If the minimum window size changes, these gates keep testing 640×480 and pass while checking a size
the application no longer uses. No user-visible behaviour is wrong today; the defect is that the
gates' claim "at the minimum window" is not tied to the minimum window.

**Out of scope** (checked, not the minimum window): `tests/switcher_forget_menu.rs:154,161,204`
`(640, 480)` are click anchor points passed to `MenuToggled` / `clamp_menu_anchor`, and
`tests/layout_record_format.rs:103,105` `640.0` is half of a 1280-wide record. Neither means the
window's minimum size, and tying them to it would make them change for no reason.

## Reproduction

On `origin/main` (74b88dd7):

1. `crates/micold-client/src/shell/startup.rs:64` declares `const MIN_WINDOW_SIZE: iced::Size =
   iced::Size::new(640.0, 480.0);` — private, in module `shell`.
2. `shell` is declared only in the binary: `crates/micold-client/src/main.rs:15` `mod shell;`.
   `crates/micold-client/src/lib.rs` declares no `shell` module (its modules are `app`,
   `catalog_sync`, `daemon`, `features`, `grid`, `icons`, `input`, `keymap`, `overlay`,
   `reveal_trace`, `selection`, `showcase`, `ui`).
3. Integration tests under `crates/micold-client/tests/` link the library crate `micold_client`
   only, so any `use micold_client::…::MIN_WINDOW_SIZE` fails to resolve (E0432): there is no path
   to it. This is deterministic (Rust module visibility), so a compile-level use of the constant
   from a gate is the regression check: it fails to build on `origin/main` and builds once the
   constant is public in the library.
4. `grep -rn "640\.0\|480\.0" crates/micold-client/tests` lists the two restatements above.

- **False completions**: none. T032 allowed the literal, and the gate it wrote is correct for

- **Missing tasks**: move/export `MIN_WINDOW_SIZE` from the library crate and have the binary use

  compile against `origin/main`); run the gate.

## Root Cause Analysis

The constant was introduced in the binary's startup code, next to the window settings it feeds,
before any test needed it. The client's library crate (`micold_client`) and binary share a package
but not modules: `shell` is compiled only into the binary. BUG-001's T032 hit this and, as the task
allowed, restated the value. The earlier `known_projects_reflow.rs` (spec 003) restated the width
for the same reason. The fix is to put the constant in the library (for example beside
`SIDEBAR_MIN_WIDTH` in `app.rs`), have `shell/startup.rs` import it, and have the gates read it.
