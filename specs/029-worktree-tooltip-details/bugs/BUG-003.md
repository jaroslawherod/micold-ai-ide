# Bug Report: Tests copy the harness's settle loop instead of calling it

**Type**: Implementation drift
**Severity**: Low
**Feature**: 029-worktree-tooltip-details (Worktree tooltip shows the full name and its details)
**Reported**: 2026-09-30
**Source**: GitHub issue #432 (follow-up from BUG-001, PR #425)
**Status**: Patched
**Patched**: 2026-09-30

## Description

The layout harness `crates/micold-client/tests/support/layout.rs:346` has a private `settle`: it
hands a laid-out element tree `frames` redraws (`RedrawRequested(origin + FRAME * frame)`, cursor
unavailable, messages discarded), so that a panel's entrance `Fade` is over before a press or a
hover reaches it. Its frame count, `SETTLE_FRAMES = 8` (`:339`), is private too, and its viewport
is the fixed `WINDOW` (1280×800).

Because a test cannot call it, three tests carry a verbatim copy of that loop, each with its own
`const SETTLE_FRAMES: u32 = 8;` and a comment saying the count is the harness's:

- `tests/gates/tooltip_clears_its_row.rs:125-143` (`hover_row`, written by BUG-001 T031), at a
  window size passed in (the gate's worst case is `MIN_WINDOW_SIZE`, not `WINDOW`).
- `tests/gates/context_menu_anchor.rs:211-228` (`right_press_at`), at `lay::WINDOW`.
- `tests/session_start_press.rs:110-127` (`press_at`), at `lay::WINDOW`.

If the harness's count or timing changes (say an entrance gets longer than 8 frames), the copies
keep the old values and their presses and hovers land on a panel still fading in. No user-visible
behaviour is wrong; the defect is duplicated test apparatus.

**Not copies** (checked; the issue lists them, but they settle something else and stay as they
are):

- `tests/settings_rail_motion.rs:889` — `Surface::settle` pumps its own `frame(at, cursor)`, which
  renders and returns messages, for `SETTLE = 120` frames on its own clock. It drives a rendered
  surface, not a bare tree.
- `tests/picker_visibility.rs:152` — `Harness::settle` runs until the picker's overlay is gone and
  **returns the frame count**, which the test asserts on (`:206`). A fixed frame count cannot
  answer that.
- `tests/adding_an_animation_touches_one_file.rs:72` — settles a `Pulse` value model with
  `tick()`; there is no widget tree at all.
- `tests/add_worktree_form_survives_a_refusal.rs:165` also ticks the floating list's overlay each
  frame, which the harness loop does not.

## Reproduction

On `origin/main` (2819b69c):

1. `grep -n "fn settle\|const SETTLE_FRAMES" crates/micold-client/tests/support/layout.rs` →
   `:339 const SETTLE_FRAMES: u32 = 8;` and `:346 fn settle<'a, M: 'a>(` — both private, and
   `settle` passes `&Rectangle::with_size(WINDOW)` as the viewport.
2. `grep -n "const SETTLE_FRAMES: u32 = 8" crates/micold-client/tests -r` lists the three copies
   above.
3. Calling `lay::settle` from a test fails to compile (E0603, private function). This is
   deterministic, so a compile-level call is the regression check: it fails on `origin/main` and
   builds once `settle` is public and takes the viewport size.

## Root Cause Analysis

`settle` was written as a private step of the layout harness's `resolve_pressing` (spec 026,
T071), with the harness's one window size baked in. `session_start_press` and `context_menu_anchor` needed the same
pre-press settle and copied it; BUG-001's `hover_row` needed it at a different window size, which
the private helper could not take, and copied it again. The fix is to give the helper a viewport
size, make it and its frame count public, and have the three tests call it.
