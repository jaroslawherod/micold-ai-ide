# Bug Report: SSH host alias remotes (git@github-alias:o/r) are not recognised as GitHub

**Type**: Spec conflict — FR-002 and research R5 rule out aliases on purpose, but an SSH host alias for github.com is the usual multi-account setup and git/gh work with it.
**Severity**: Medium — every GitHub feature (issue chip, issue-driven `create_worktree`, scoped credential, PR status) is off for such a repository.
**Feature**: 034-github-issue-worktree (FR-002, research R5 "URL forms accepted")
**Reported**: 2026-10-27 (issue #1475)
**Status**: Patched
**Patched**: 2026-10-27

## Description

`origin` = `git@github-micold:jaroslawherod/micold-ai-ide.git` with `~/.ssh/config` `Host github-micold` / `HostName github.com`. `create_worktree` with `github_issue` fails with "This repository has no GitHub remote."; the form's issue chip is disabled; the scoped credential reports no GitHub remote. `gh` and git work in the same checkout.

Reproduce on `origin/main`: `choose_remote(&[GitRemote { name: "origin", url: "git@github-micold:o/r.git" }])` returns `RemoteChoice::NoGithubRemote` (`GithubRepo::from_remote_url` in `crates/micold-core/src/github.rs` accepts only the literal host `github.com`, or `ssh.github.com` over SSH), and `create_worktree` with `github_issue` in such a checkout answers `This repository has no GitHub remote.` while `ssh -G github-micold` prints `hostname github.com`.

## Artifact Traceability

### spec.md
- **Affected requirements**: FR-002 ("a remote on any other host … does not [count]"); Assumptions line "only github.com is supported (FR-002)".
- **Gap identified**: FR-002 treats a host that merely names github.com through SSH configuration as another host.

### plan.md / research.md
- **Affected sections**: research R5 "Repository-local config only, raw URLs" (consequence: aliases not recognised) and "URL forms accepted" (an "unexpanded alias" is not a GitHub remote).
- **Impact**: SSH host aliases are resolved with `ssh -G` on the user's machine by the client, which tells the daemon the aliases of github.com (`ClientMsg::SshHostAliases`); a container daemon has no `~/.ssh` and never resolves on its own. `insteadOf` remains unexpanded.

### tasks.md
- **False completions**: none (T0xx built what R5 decided).
- **Missing tasks**: T107, T108.

## Root Cause Analysis

Deliberate R5 decision, taken to keep the answer independent of where the daemon runs. It did not weigh SSH aliases, which are resolved by `~/.ssh/config`, not by git's `insteadOf`. Root cause: `from_remote_url` compares the URL's literal host; fix is a resolution step before it (`resolve_ssh_aliases_with`), keeping the parser pure. The resolution runs on the host because the alias lives in the host's `~/.ssh/config`: a sandboxed daemon, where the credential and `create_worktree` run, cannot see it.

## Recommended Fix

T107 regression tests (stubbed `ssh -G`), T108 host-side resolution in the client, forwarded to the daemon and applied at every site that reads the remote list or the push URL.
