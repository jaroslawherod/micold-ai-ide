# Bug Report: An open Settings page keeps stale values after another window saves

**Type**: Spec gap (FR-026a fixed what a save writes; nothing said what an open page shows)
**Severity**: Low
**Feature**: 039-session-attention-notifications (branch `claude/project-thread-l0ix9w-475`)
**Reported**: 2026-09-30. GitHub issue #475, found by review A of feature 035 M3 (PR #473) and
recorded in `specs/035-report-missing-include-script/autopilot.md`, *Follow-ups not done*
**Status**: Patched
**Patched**: 2026-10-08

## Description

With Settings open in two windows, a save in window B does not reach window A's open page. A's
fields keep the values A opened with, while the environment-include notice on A's page is re-checked
against the newly stored path (035, trigger T3), so A can show a notice for a path that is not the
one in its own path field.

Since BUG-570 (FR-026a) a save from A no longer writes those stale values back, so what is left is
what A shows. The issue asked for one of three behaviours; this patch takes the first: overwrite the
fields the user has not touched, and keep the ones they edited.

### Reproduction

On `origin/main` at `99a3408d`. `CARGO_INCREMENTAL=0 cargo test -p micold-client --bin
micold-ai-ide an_open_settings_page_shows` (A50, T137) fails at its first assertion: after
`SettingsChanged` with `desktop_notifications: false`, the open draft still has
`environment.desktop_notifications == true`.

### Mechanism

`on_settings_changed` (`crates/micold-client/src/shell/daemon_sync.rs`) applied the service's values
to the window (`adopt_daemon_settings`) and re-checked the script path, but never touched
`settings_draft`, which `open_settings` seeds once.

## Resolution

`SettingsDraft::refresh_untouched` compares each field with the page as opened (the draft built from
its baseline, BUG-570), sets the ones still equal to the value now in force, and makes those
settings the new baseline, so a later save sends only what the user edited (FR-026a still holds).
`refresh_open_settings` seeds "now in force" the way opening the page does: the service's values
from the window, the rest from the store.

## Follow-ups not done

- A save that changes only file-owned settings (theme, sandbox, label-to-type mapping) sends no
  `SettingsSet`, so the service announces nothing and an open page in another window is not
  refreshed. FR-026b is scoped to saves that reach the service; the user guide says to reopen
  Settings for those.
- Fields holding several settings (`notification_kinds`, the label-to-type entries) are kept or
  refreshed whole. An edit to one kind here and another window's change to a different kind keeps
  this page's whole value, and a save then sends it whole (FR-026a compares the same way).
