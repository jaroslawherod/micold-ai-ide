# Bug Report: Any session-bus peer can open a session through a forged `ActionInvoked`

**Type**: Spec gap (with implementation drift on top of it)
**Severity**: Medium
**Feature**: 039-session-attention-notifications (branch `claude/project-thread-v00oac`)
**Reported**: 2026-10-06. GitHub issue #566, from M6 review A finding F5 (MINOR, left under
*Follow-ups not done* in `../autopilot.md`). Refs #481.
**Status**: Patched
**Patched**: 2026-10-06

## Description

The Linux notification backend (`crates/micold-client/src/shell/desktop_notify/linux.rs`) reads the
notification service's signals through one match rule, `SIGNALS`:

```text
type='signal',interface='org.freedesktop.Notifications',path='/org/freedesktop/Notifications'
```

It names no sender, and `Shown::on_signal` asks only for the notification id. So:

1. **Any peer can click.** Any process on the user's session bus can send
   `ActionInvoked(id, "default")` for an id this window holds (ids are small integers counted from 1,
   so they are easy to guess), and the window treats it as a click (FR-011): it raises itself,
   switches project and selects the session. It can also send `ActivationToken` with a token of its
   own and `NotificationClosed` to drop an entry.
2. **Ids outlive the service that gave them.** `Shown` keeps every id until its click or close. A
   notification service that restarts numbers its notifications from 1 again, so an id of the old
   service matches a new, unrelated notification of the new one — another application's, or one
   for another session — and its click opens the wrong session.

### Reproduction (2026-10-06, on `origin/main` `7681c0f4`)

A private `dbus-daemon --session`, and a probe built on the same `zbus` 5.19.0 the client uses
(`blocking::MessageIterator::for_match_rule`, the call `Notifier::listen` makes). One process owns
`org.freedesktop.Notifications` and emits `ActionInvoked(1, "default")`; a third peer, which owns
nothing, sends the same signal twice with `dbus-send`: once broadcast, once unicast to the
listener's unique name. The probe and the script are in `BUG-566-probe/`:

```sh
cargo build --manifest-path specs/039-session-attention-notifications/bugs/BUG-566-probe/Cargo.toml --target-dir <scratch>
specs/039-session-attention-notifications/bugs/BUG-566-probe/repro.sh <scratch>/debug/probe566
```

It printed (the unique names vary from run to run):

```text
== open: type='signal',interface='org.freedesktop.Notifications',path='/org/freedesktop/Notifications'
OWNER :1.1
UNIQUE :1.0
GOT member=Some("ActionInvoked") sender=Some(":1.2") dest=None        <- forged, broadcast
GOT member=Some("ActionInvoked") sender=Some(":1.3") dest=Some(":1.0") <- forged, unicast
GOT member=Some("ActionInvoked") sender=Some(":1.1") dest=None        <- the service
== sender: type='signal',sender='org.freedesktop.Notifications',interface=…,path=…
OWNER :1.4
UNIQUE :1.5
GOT member=Some("ActionInvoked") sender=Some(":1.7") dest=Some(":1.5") <- forged, unicast
GOT member=Some("ActionInvoked") sender=Some(":1.4") dest=None        <- the service
```

So the rule as it is passes every forged signal on, and the fix the issue proposes is not enough
by itself:

- `sender='org.freedesktop.Notifications'` makes the bus drop a *broadcast* signal from a peer that
  does not own the name, and still delivers the owner's (zbus does not drop it either: a rule
  whose sender is a well-known name is not checked against the header, which carries the unique
  name; `zbus` 5.19.0 `src/match_rule/mod.rs:220-229`, "We can't match against a well-known name").
- A signal sent *to* the listener's unique name is delivered whatever the match rules say, and
  zbus, for the reason just given, passes it on. The unique name is no secret
  (`org.freedesktop.DBus.ListNames`).

The second defect needs no bus to see: `Shown` is created once per `Notifier`, nothing removes an
entry but its click or close, and nothing in `linux.rs` reads `NameOwnerChanged`.

### Mechanism

The id in a signal means something only together with the service that numbered it. The reply to
`Notify` comes from that service, so its header's sender is the service's unique name, which the
bus never gives to another connection. Kept with the id, it settles both defects:

1. A signal counts only when its sender is the unique name that answered the `Notify` call for its
   id. A forged signal, broadcast or unicast, comes from another unique name. A restarted service
   has a new unique name, so its id 1 is not the old service's id 1.
2. When `org.freedesktop.Notifications` changes owner (`NameOwnerChanged`, sent by the bus itself,
   sender `org.freedesktop.DBus`, which no peer can own), the entries of the old owner are dropped:
   that service can no longer report a click. Checking the old owner, not clearing everything,
   keeps a notification the new owner has already shown even when the listening thread reads the
   `NameOwnerChanged` after `show` recorded it.
3. The match rule names `sender='org.freedesktop.Notifications'` as the issue proposes, so the bus
   no longer wakes the listener for other peers' broadcasts. It is not what keeps them out.

GNOME Shell sends each signal twice, once from its own connection and once from the helper that
owns `org.freedesktop.Notifications` (research R7). The `Notify` reply comes from the owner, so
under (1) the owner's copies count and the shell's are dropped; the click is still reported once,
and the activation token still arrives (each signal, the token included, comes from both).

## Root Cause Analysis

The click path was designed around the notification id alone (contract N9, research R6): the
table was made the window's own, against other windows, but not the service's own, against other
peers and other lifetimes of the service. The FreeDesktop specification numbers notifications per
server; the bus guarantees only the unique name of a sender. M6 review A noticed it (F5) and judged
it MINOR; it was deferred and is now issue #566.
