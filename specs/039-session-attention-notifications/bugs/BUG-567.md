# Bug Report: A failed write of the attention state is not retried, so a read session is unread again after a restart

**Type**: Implementation defect (FR-008a is right; `persist_attention` does not deliver it when a write fails)

**Severity**: Medium (a session the user read comes back unread after a restart; nothing else is lost)

**Feature**: 039-session-attention-notifications (FR-008a; M1, M4)

**Issue**: #567

**Reported**: 2026-10-04

**Status**: Fixed (2026-10-05) — Phase 12 (T133–T134)

## Description

`DaemonState::persist_attention` (`crates/micold-daemon/src/state.rs`) cleared `attention_unsaved`
before it wrote. When the write failed, nothing set the flag again, so the attention state was
written only when a later attention event or catalog write came. A service that stopped before that
lost the read: the session was unread after the restart. The same function held the state lock
across the blocking write, so every other user of the lock waited for the disk. And no test observed
the supervisor tick making the write (M1 review B; `tdd/verification.md` F1, proposed T124).

## Root cause

`std::mem::take(&mut inner.attention_unsaved)` before `inner.catalog.persist()`, with the `Err` arm
only logging. The write is `Catalog::persist`, which needs `&Catalog`, so it ran under the lock.

## Artifact Traceability

- **spec.md**: FR-008a requires the state to outlive the service. No change.
- **plan.md / contracts**: no change.
- **tasks.md**: the M1 and M4 tasks did what they claimed; the failure path was recorded as a
  follow-up in `autopilot.md`.

## Fix

- On `Err` the flag is set again, and the write is due again after a back-off (1 s, doubling to
  60 s): `has_unsaved_attention` is false until then, so a read-only data directory is not tried and
  warned about every 250 ms. The first failure warns; later ones log at debug until a write succeeds.
- The catalog is copied under the state lock (`Catalog::pending_write`) and written after it is
  released. Every write takes a sequence number under the lock, and the store drops a write older
  than the last one stored, so a late snapshot cannot overwrite a newer catalog write.
- The supervisor loop's body is `server::supervisor_tick`, which a test runs once.
- Out of scope: `record_observed_names` still writes under the lock.
