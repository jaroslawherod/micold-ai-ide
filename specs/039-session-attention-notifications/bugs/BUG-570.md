# Bug Report: A Settings save from one window undoes a change made in another

**Type**: Spec gap (FR-026 says nothing about several windows; T105 then specified the overwrite)
**Severity**: Medium
**Feature**: 039-session-attention-notifications (branch `claude/project-thread-5n79g3`)
**Reported**: 2026-10-06. GitHub issue #570, found in M8 review A (finding F4) and recorded under
*Follow-ups not done* in `specs/039-session-attention-notifications/autopilot.md`
**Status**: Patched
**Patched**: 2026-10-06

## Description

A Save in Settings sends every service-owned field to the service as `Some(draft value)`, and
writes every field of the form to `settings.json`. The draft is seeded when the page opens and is
not refreshed while it is open. A window whose page was opened before another window saved
therefore writes its old values back: the last window to save wins, for fields its user never
touched.

Steps from the issue:

1. Open two windows. Open Settings → Environment in both.
2. In window A switch **Desktop notifications** off and save.
3. In window B change any other setting and save, without reopening the page.
4. **Desktop notifications** is on again.

The same holds for `tool_server_enabled` (feature 034), which behaved this way before 039, and for
every other field the form holds.

### Reproduction

On `origin/main` at `7681c0f4`. The probe is one throw-away test appended to
`crates/micold-client/src/main_tests.rs` (never committed; kept in the session scratchpad as
`probe_bug570.rs`). It drives the real update path of one window (window B):

1. `SettingsChanged` with `quiet_settings()` (notifications on, tool server on), then
   `SettingsMsg::Opened`: the draft holds `desktop_notifications: true`.
2. `SettingsChanged` with `desktop_notifications: false, tool_server_enabled: false`: window A's
   save, echoed to every window by the service (FR-011 of 010).
3. `PiActivityComponentToggled(false)`, then `SettingsMsg::Saved`.

`CARGO_INCREMENTAL=0 cargo test -p micold-client --bins repro_570`:

```
REPRO draft_after_open=Some(true)
REPRO draft_after_open_and_feed=Some(true)
REPRO told=Some((Some(true), Some(true))) session_dn=true
test result: FAILED. 0 passed; 1 failed; 0 ignored; 0 measured; 377 filtered out
```

The service is told `desktop_notifications: Some(true)` and `tool_server_enabled: Some(true)`,
undoing window A's change, and window B's own mirror of the switch goes back to `true`. The test
asserts both are `None` and fails.

### Mechanism

All three in `crates/micold-client/src/shell/persist.rs`, `save_and_prepare_check`:

1. **The message to the service** (lines 422–434) sets every service-owned field to
   `Some(settings.<field>)`, where `settings` comes from the draft. `server.rs` applies every
   `Some` (`crates/micold-daemon/src/server.rs:1052`), so the stale value replaces the current one
   and is pushed to every window as `SettingsChanged`.
2. **The file write** (lines 398–404) replaces the stored document with the draft's settings
   (`*stored = settings.clone()`), keeping only `pr_status_enabled`. While the service runs, its
   own write after a `SettingsSet` re-writes the service-owned fields from memory
   (`persist_service_settings`, `crates/micold-daemon/src/catalog.rs:289`). So once (1) is fixed,
   a save that changes no service-owned field sends nothing the service acts on, and the client's
   stale service-owned values stay in the file until the service next restarts and reads them.
   Client-owned fields (theme, the sandbox settings) are overwritten the same way.
3. **The window's mirror** (lines 385–388) is set from the draft before anything is sent. When
   the service is not told anything, no echo comes back to correct it.

The draft keeps no record of what it was seeded with (`SettingsDraft::from_settings`,
`crates/micold-client/src/features/settings.rs:776`; seeded in `persist.rs` `open_settings`), so a
save cannot tell a field the user changed from one it only carried.

## Root Cause Analysis

Spec oversight carried into the tasks. FR-026 was written for one window. T105 specified
`Some(value)` on every save, following `tool_server_enabled`, which has had the same defect since
feature 034 (M8 review A declined F4 for that reason). The client has always sent the whole form;
the service's partial update (`Option` per field) was never used for its purpose.

## Recommended Fix

The draft keeps the settings it was seeded with. A save compares the validated settings with that
baseline, field by field, and:

- sends `Some` to the service only for the service-owned fields that differ, `None` for the rest;
- in the file update, sets only the fields that differ, leaving every other field as stored;
- updates this window's own copy only for the fields that differ.

Comparing after validation, in `Settings` terms, means a field the user retyped to the same value
counts as unchanged. This fixes every field of the form at once, not only the two the issue names.
