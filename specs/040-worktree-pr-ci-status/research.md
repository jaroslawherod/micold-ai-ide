# Research: Pull Request and Check Status for Each Worktree

**Feature**: [spec.md](./spec.md) | **Plan**: [plan.md](./plan.md)

Each entry records the decision, why, and what was rejected. Paths are repository-relative. "034 R*n*"
is an entry of [034's research](../034-github-issue-worktree/research.md), which this feature builds
on rather than repeats.

---

## R1 — How GitHub is reached: the existing `gh` runner, one GraphQL request per reading

**Decision.** Pull requests are read with `gh api graphql --hostname github.com --include …`, run by
the `GhCli` that feature 034 added to `micold_core::github` (`process::run_bounded`, 10-second bound,
the prompt/pager/colour environment of 034 R6, `gh` located by `locate_gh`, 034 R3). No new crate and
no new way to reach GitHub.

**Rationale.** FR-028 asks for the same sign-in 034 uses and forbids credentials and anonymous
access; 034 R1 shows `gh` gives both by construction. The 10-second bound of FR-021 is the bound
`GhCli` already applies. `--include` is added so the response headers reach the parser (R9).

**Alternatives rejected.**

| Alternative | Why not |
|---|---|
| `gh pr list --json …` / `gh pr status` | Porcelain: fields and defaults change between `gh` releases (034 R2), one call per branch, and no control over how checks are counted. |
| `gh pr view <branch>` per worktree | One request per worktree per reading: 50 worktrees × 12 readings is 600 requests an hour against SC-006's 30. |
| REST `GET /repos/{o}/{r}/pulls?head=owner:branch` | Exact fork filter, but one request per branch, and checks need a further request per pull request. |
| An HTTP client crate | Rejected in 034 R1 for reasons that have not changed. |

## R2 — The query: aliased `pullRequests(headRefName:)` connections, check counts by state

**Decision.** One query document per reading, generated by a pure `status_query(n)` for `n` branches
(1 to 50). Each branch name is a GraphQL variable (`$b0 … $b49`, passed with `-f`), never spliced
into the document. For each branch two aliased connections of the project's repository:

```graphql
o0: pullRequests(headRefName: $b0, states: OPEN, first: 10,
                 orderBy: {field: CREATED_AT, direction: DESC}) { nodes { ...pr } }
r0: pullRequests(headRefName: $b0, first: 10,
                 orderBy: {field: CREATED_AT, direction: DESC}) { nodes { ...pr } }
```

with

```graphql
fragment pr on PullRequest {
  number title url state isDraft createdAt isCrossRepository headRefOid reviewDecision
  commits(last: 1) { nodes { commit { statusCheckRollup { contexts(first: 1) {
    checkRunCount checkRunCountsByState { state count }
    statusContextCount statusContextCountsByState { state count } } } } } }
}
```

and `rateLimit { remaining resetAt }` beside `repository`. More than 50 branches are sent as further
requests of up to 50, one after another; a reading succeeds only when every chunk does, so nothing
half-read is shown (spec Edge Cases).

**Rationale.**

- **One request for up to 50 worktrees** (FR-023, SC-006): 12 automatic readings an hour are 12
  requests. Probed on 2026-10-02 with `gh` 2.54.0 against this repository with three branches: HTTP
  200 in 1.7 s, `rateLimit.cost` 1; 15 branches cost 6. The cost formula counts requested
  connections, nested ones included, so 50 branches (100 `pullRequests` connections of 10, each node
  with a `commits` and a `contexts` connection) cost about 21 points of the 5,000 an hour: about 250
  an hour for the 12 automatic readings.
- **The response does not grow with the number of checks** (FR-023): `checkRunCountsByState` and
  `statusContextCountsByState` return one count per state however many checks there are, and
  `contexts(first: 1)` selects no nodes. The probe returned all 14 check-run states and all 5
  status-context states, zero counts included.
- **Counts, not the rollup's own `state`**: FR-008 gives an exact rule. GitHub's rollup `state`
  applies a similar one, but it is not documented case by case (a cancelled run, a stale one). With
  the counts the rule is ours, pure and tested (R4).
- **Two connections per branch** make FR-004 exact for the common case: the open connection finds an
  open or draft pull request even when ten newer closed ones exist for the same branch name.
- **Variables for branch names**: a branch may hold `"` or `$`; a variable cannot change the
  document. `-f`, not `-F`, so a branch named `true` or `123` stays a string (034 contract §3).

**Known bound.** Each connection holds the 10 newest pull requests whose head branch has that name,
forks' included (R3). A worktree's own pull request is missed only when more than 10 newer pull
requests with the same head-branch name exist in that connection. Recorded in
[contracts/pull-request-source.md](./contracts/pull-request-source.md) §2.

**Alternatives rejected.** `search(query: "repo:o/r is:pr head:<branch>")` (the search API has its
own 30-a-minute limit and an index that lags, 034 R2; `head:` does not tell a fork's branch from the
repository's own either); `repository.ref(qualifiedName:).associatedPullRequests` (returns nothing
once the branch is deleted on GitHub, which is the usual state of a merged pull request — the case
story 3 is about); one connection of 20 per branch (an old open pull request behind 20 newer closed
ones would be shown as closed).

## R3 — Which pull request is the branch's: `select_pull_request`

**Decision.** A pure function over the two node lists of a branch:

1. drop every node with `isCrossRepository: true` — its head branch lives in another repository
   (FR-005, spec Edge Cases "same branch name in someone else's fork");
2. if the open list has a node left, take its most recently created (`createdAt`);
3. otherwise take the most recently created node of the recent list;
4. none → the branch has no pull request.

State: `OPEN` with `isDraft` → draft; `OPEN` → open; `MERGED` → merged; `CLOSED` → closed. Any other
`state` value makes the answer one that cannot be understood (R10).

**Rationale.** It is FR-004 word for word. `isCrossRepository` is false exactly when head and base
are the same repository, and the base is always the queried one, so "lives in that repository"
(FR-005) needs no comparison of owner names. FR-006 holds by construction: the only repository ever
named in a request is the project's own (`GithubRepo` from `choose_remote`), so a pull request that
lives in the repository a fork was made from is never asked for and never found.

**Alternatives rejected.** Comparing `headRepository.nameWithOwner` to `owner/name` (`headRepository`
is `null` once a fork is deleted, and the comparison would need case folding); letting GitHub's
order decide (`createdAt` is compared in the function so a test can state the rule).

## R4 — The combined check status: a pure reduction over the counts

**Decision.** `reduce_checks(counts) -> CheckStatus`, applied only to an open or draft pull request
(FR-003):

| Check-run state (`checkRunCountsByState`) | Status-context state | Counts as |
|---|---|---|
| `FAILURE`, `CANCELLED`, `TIMED_OUT`, `ACTION_REQUIRED`, `STARTUP_FAILURE` | `FAILURE`, `ERROR` | failed |
| `QUEUED`, `IN_PROGRESS`, `PENDING`, `WAITING`, `STALE` | `PENDING`, `EXPECTED` | queued or running |
| `SUCCESS`, `NEUTRAL`, `SKIPPED`, `COMPLETED` | `SUCCESS` | finished without failure |
| any name not listed | any name not listed | queued or running |

Any failed count above zero → `Failing`; otherwise any queued-or-running count above zero →
`Pending`; otherwise, with at least one check, `Passing`; with `statusCheckRollup: null` or both
totals zero → `None` (story 1 scenario 8).

**Rationale.** It is FR-008 with every state GitHub can report placed in one of its three groups.
`STARTUP_FAILURE` is a workflow that could not start: a failure the user must act on. `STALE` is a
run GitHub gave up waiting for; it has not finished, so it is not "passing". A state name this
version does not know is read as not finished, because showing "passing" for something unknown is
the one mistake the indicator must not make; the reading itself still succeeds. The grouping
follows the `gh` CLI's for `gh pr checks`, except that `STARTUP_FAILURE` is a failure here.

**Alternatives rejected.** The rollup's `state` field (R2); failing the whole reading on an unknown
state name (a new GitHub state would then blank every indicator of every user until an update).

## R5 — Where the reading runs: in the client, on the host

**Decision.** As 034 R4: `gh` runs in `micold-client` from a `Task::perform` + `spawn_blocking`. The
daemon is asked only for local git facts: the remotes (034's `RemoteList`, unchanged) and whether a
merged branch has later commits (R11).

**Rationale.** The daemon can run in a container without `gh`, the keychain or the user's network
(feature 027); the spec's Assumptions leave the placement to the plan and require the same behaviour
either way. The client always runs on the host beside the user's sign-in. The client must not run
git itself under a sandbox (`Capabilities::without_local_git`), which is why the two git questions
go to the daemon.

**Alternatives rejected.** Reading in the daemon (breaks under the sandbox; would need the GitHub
credential forwarded into the container).

## R6 — Several windows: only the window that holds the project reads

**Decision.** Only the window that **holds** a project reads its pull request status and shows it.
A window holds its active project from the daemon's `Attached` for it until a `Displaced` or a
`Refused { ProjectBusy }` for it, a project switch or a disconnect — the facts `app.displaced`
already records (`shell/daemon_sync.rs`). No coordination between windows is added.

**Rationale.** A window is a client process (`ClientInstance`), and feature 010 lets exactly one
window hold a project: a second attach is refused with a takeover offer, and a takeover displaces
the first holder (`crates/micold-daemon/tests/exclusivity.rs`, 010 FR-023 to FR-025). The refused or
displaced window does **not** stop showing the project: it stays on it, read-only, under a
take-over banner, and its sidebar keeps following the listing because `CatalogChanged` is broadcast
to every client. So "one reading per project" (FR-022, SC-007) does not hold by itself; it holds
because holding is a start condition (R7) and a condition of the interval subscription (R8), and
because losing the hold clears the window's statuses. A read-only window therefore sends nothing
and shows no indicator; a window that takes the project over receives `Attached` and reads once, as
on opening (FR-018). Windows on different projects read their own project only.

The spec's "Several windows" edge case and SC-007 first asked for every window on a project to show
the same status. They were reworded to the behaviour above (ledger D9): a read-only window cannot
act on a worktree, and giving it indicators would need either a second reader or the daemon as a
relay.

**Alternatives rejected.** Holding the status in the daemon and broadcasting it to read-only
windows too (new wire messages and daemon state; the daemon would hold pull request titles, which
FR-032 wants in as few places as possible); letting every window on a project read (two readings
per interval for one project, against FR-022).

## R7 — What a reading covers, and when one starts

**Decision.** A reading takes the branches of the worktrees in the client's current listing
(`state.worktree.worktrees`, every entry with `branch: Some`), deduplicated. It never sends
`ClientMsg::WorktreeRefresh` and never changes the listing (FR-018a). It starts on exactly these
events, and only while the switch is on and the window holds its active project (R6):

| Event | Source |
|---|---|
| the project's listing arrives after the window came to hold it (opened, switched to, reconnected, taken over) | the first `DaemonMsg::CatalogChanged` after `DaemonMsg::Attached` for the active project |
| the switch turns on while the project is held and listed | `DaemonMsg::SettingsChanged` carrying `pr_status_enabled: true` after `false` |
| the interval elapses | `iced::time::every(300 s)` (R8) |
| a list refresh ends | `WorktreeMsg::RefreshFinished` or `RefreshTimedOut` |

The refresh trigger is the *end* of the list refresh: the daemon broadcasts the new listing
(`CatalogChanged`) before it acknowledges the refresh, so the reading that starts on the
acknowledgement reads the branches the updated listing shows (FR-018a). The refresh control's busy
state and its notice are untouched — they are settled by `RefreshFinished` before the reading begins
(FR-027, story 4 scenario 6).

A source gate, `pr_status_is_read_only_on_named_events.rs`, counts the lines that can start a
reading, as `issues_are_requested_only_on_named_events.rs` and `refresh_is_only_on_demand.rs` do for
their requests.

The first event needs a one-shot flag. The daemon sends `Attached` and then, on its heels, a
`CatalogChanged` with the freshly discovered worktrees (`refresh_worktrees_and_send`); the client
puts that listing into its state in `reconcile_catalog`. `Attached` sets `awaiting_listing` in the
pull request state, and the next `CatalogChanged` clears it and starts the reading. Every other
`CatalogChanged` — a create, delete, rename, include, another window's change — finds the flag
clear and starts nothing. (`WorktreeMsg::Loaded` is not the carrier: production code never sends
it.) Accepted bound: the daemon discovers the worktrees between `Attached` and its `CatalogChanged`,
so a `CatalogChanged` broadcast for another window's change can arrive in that gap and be taken for
the listing; the first reading then covers the listing the client already had, and a branch only
the fresh one shows is read at the next interval or refresh. At start-up the settings arrive in `Welcome` before any `Attached`, so a switch that is already
on starts nothing by itself; the listing that follows the attach does.

**Rationale.** Rows are joined to statuses by branch name at projection time, so a worktree removed
or renamed between readings simply stops matching, and an answer for a project that is no longer
shown is dropped by its sequence number (spec Edge Cases). A worktree created in the application
appears in the listing at once and is covered by the next reading.

**Alternatives rejected.** Reading on every `CatalogChanged` (it fires for every create, delete, rename
and include, turning each into a GitHub request the spec did not ask for); asking the daemon for a
fresh listing before each reading (that is the automatic re-listing 029 FR-012 forbids).

## R8 — The schedule: a render-free reducer, one timer subscribed only when needed

**Decision.** `crates/micold-client/src/features/pr_status.rs` holds a small state machine:

```text
Idle ──start──▶ Reading { seq, again: false }
Reading ──trigger (refresh)──▶ Reading { again: true }      # FR-022: any number of presses, one flag
Reading ──trigger (interval)─▶ Reading (unchanged)
Reading ──finished──▶ Idle, then start again when `again` and not paused
```

A start is refused while `now < pause_until` (R9), which also drops a pending `again`. The interval
is `iced::time::every(PR_STATUS_INTERVAL)` (300 s) in `shell/subscriptions.rs`, pushed **only while**
the switch is on and the window holds its active project (R6); `tests/idle_subscriptions.rs` gains that condition. With the
switch off — the state of a first start — the idle window has no new timer and sends nothing
(FR-026, FR-030, SC-006).

**Rationale.** Every rule of FR-018, FR-022 and FR-024 is a decision, so it lives in a reducer with
an injected clock and is tested without iced (Principle I). A timer that exists only while the
feature is on keeps the idle-window guarantee of feature 021.

**Alternatives rejected.** A tokio interval in the daemon (R5); a one-minute tick that checks whether
five minutes passed (five times the wake-ups for nothing); re-arming a `Task` sleep after each
reading (the interval would drift by the reading's duration and a lost task would stop the schedule
silently — a subscription is re-declared after every update).

## R9 — The request limit: read the reset time from the response headers

**Decision.** `gh api --include` prints the status line and headers before the body. A pure
`split_response` separates them, and `rate_limit_pause(response, now)` yields the time until
which no reading is sent:

1. `Retry-After: <seconds>` (GitHub's secondary limit) → `now + seconds`;
2. else `X-RateLimit-Remaining: 0` → the time in `X-RateLimit-Reset: <epoch>` (the primary limit);
3. else `now + 60 s` (GitHub's documented minimum wait for a secondary limit that names no time).

`X-RateLimit-Reset` alone decides nothing: GitHub sends it on every answer, as the reset of the
primary window, so a secondary-limit answer without `Retry-After` would otherwise pause for up to
an hour.

A rate-limit answer is: a GraphQL error of type `RATE_LIMITED`, HTTP 429, HTTP 403 with "rate limit"
in the message, or one of 034's rate-limit stderr fixtures. While paused, interval ticks and refresh
presses start no reading and the rows keep what they show (FR-024, story 4 scenario 7). The pause is
held in memory by the window that received the answer, and it outlives a project switch in that
window: the limit belongs to the sign-in, not to the project. It ends at its time, or when the
switch is turned off.

**Rationale.** FR-024 needs "the time GitHub gives", and only the headers carry it for both kinds of
limit. `rateLimit.resetAt` in the body is absent from an error answer.

**The pause is per window.** Another window of the same sign-in, showing another project, learns of
the limit from its own next reading: GitHub rejects that request without counting it, and that
window pauses in turn. Sharing the pause would need the daemon to relay it and still would not cover
other tools using the same sign-in. FR-024 was reworded to say so (ledger D10); SC-006's "0 between a
rate-limit answer and the limit's reset" is stated for one open project and holds.

**Alternatives rejected.** Relaying the pause through the daemon (two wire messages and daemon state
to save one rejected request per other window per pause); a fixed back-off (not "the time GitHub
gives"); asking `rateLimit` before every reading (doubles the requests).

## R10 — Two kinds of failure: cannot be read at all, and a passing failure

**Decision.** A pure `reading_failure(outcome, now) -> ReadingFailure` on top of 034's
`github::classify`:

| Evidence | `ReadingFailure` | Effect |
|---|---|---|
| no GitHub remote (`choose_remote` finds none) | `Unavailable` — and `gh` is not run (FR-026) | all of the project's statuses removed (FR-025) |
| `gh` not found; `NotSignedIn`; `NoAccess` (repository `NOT_FOUND`, 403, SAML, missing scope) | `Unavailable` | same |
| `RateLimited` | `RateLimited { until }` (R9) | statuses kept; paused |
| `Offline`, `TimedOut`, a daemon step that fails or does not answer in 10 s, the answer is not the expected JSON, an unknown `state` of a pull request, `Other` | `Passing` | statuses kept (FR-019) |

No outcome raises a notification, a dialog or an error line (FR-025, SC-004). The outcome kind and
the number of branches are logged at `debug`; titles and addresses never are (R15).

**Rationale.** FR-019 and FR-025 split failures by whether waiting can help. 034's classifier
already separates these causes from recorded `gh` stderr, so the split is a mapping of its variants,
tested against the same fixtures plus new ones recorded with `--include`.

**Alternatives rejected.** A second classifier (two readings of the same stderr that could
disagree); treating `NoAccess` as passing (a sign-in that cannot see the repository does not start
seeing it by waiting, and its last status would be shown for ever as stale).

## R11 — "No commits beyond the merged pull request": a read-only daemon RPC

**Decision.** For each branch whose selected pull request is merged, the client asks the daemon,
after `gh` answered, with a new correlated request:

```text
ClientMsg::MergedBranchCheck { req, project, checks: Vec<MergedBranchQuery { branch, head }> }
  → OperationResult::MergedBranchCheck { answers: Vec<BranchContainment> }   // same order
```

`head` is the pull request's `headRefOid`. The daemon, per query: `git rev-parse --verify
refs/heads/<branch>` for the tip; tip = `head` → `Contained`; otherwise `git merge-base
--is-ancestor <tip> <head>`: exit 0 → `Contained`, exit 1 → `Beyond`; the branch or the `head`
object is not in the repository → `Unknown`. The decision is a pure
`containment(tip, head, ancestor)` in `micold_core::git`; the daemon arm is a copy of `RemoteList`'s
(`project_repo`, `reject_non_repo`, `spawn_blocking`). Only `Contained` produces a removal
suggestion. The step is bounded by 10 s in the client; without an answer the reading still applies
its statuses, with no suggestion.

**Rationale.**

- FR-018a wants this worked out anew at every reading from the branch as the repository holds it
  then, so it cannot come from the manually refreshed listing.
- It is git, and under a sandbox only the daemon may run git (R5).
- Comparing with the pull request's head works for merge, squash and rebase merges alike: none of
  them changes the head branch. "Is the branch merged into the base" would fail for a squash merge.
- `Unknown` → no suggestion errs on the safe side of FR-017.

**Known bound.** When the pull request's last commits were pushed from elsewhere and never fetched
to this machine, the local branch is behind the pull request but the daemon cannot prove it
(`head` is not a local object): no suggestion is shown until a fetch brings it. The feature does not
fetch — that would be network traffic from the daemon the spec does not ask for. Recorded in the
spec's Edge Cases and Assumptions (ledger D11).

**Wire cost.** `PROTOCOL_VERSION` 20 → 21, one bump for this RPC and R12's setting (the repository's
rule: one bump per feature's wire change), with the pin in
`crates/micold-core/tests/schema_hash.rs` and the examples in `protocol_roundtrip.rs`. Another
feature in flight may take 21 first; the implementing milestone takes the next free number.

**Alternatives rejected.** Asking GraphQL for the pull request's commit list (up to 100 nodes per
pull request per reading: cost and size grow for a question git answers locally); putting the tip
in the listing (stale by FR-018a); comparing only tip = head (a branch that is behind its merged
pull request has no newer work either, and FR-015 says it MUST be marked).

## R12 — The switch: a service-owned setting, off by default

**Decision.** `Settings.pr_status_enabled: bool`, `#[serde(default)]` (false), in
`micold_core::settings`; mirrored on `DaemonSettings` and settable through
`ClientMsg::SettingsSet { pr_status_enabled: Option<bool> }`, exactly as `tool_server_enabled` is
(034). The client keeps the live value in its `pr_status` state from `Welcome` and
`SettingsChanged`. `SETTINGS_VERSION` is unchanged: the field is additive and defaulted.

In Settings it is a `Checkbox` with a `field_note` at the top of the existing GitHub section
(`ui/settings/github.rs`), whose title becomes **GitHub** now that it holds more than the issue
mapping:

> **Show pull request status on worktrees**
> Reads the pull requests of the open project's GitHub repository with your GitHub CLI sign-in: when
> the project opens, every 5 minutes, and when you refresh the worktree list. Only the repository's
> name and your worktrees' branch names are sent.

**Rationale.** FR-029 wants "at once" for turning off, and FR-030 wants every project a window shows
read at once when it turns on. Windows are separate processes; the daemon's `SettingsChanged`
broadcast is the mechanism that reaches all of them, and `settings.json`'s two-writer split is by
field (`DaemonSettings` doc comment), so a field every window must follow belongs to the daemon's
side. Off by default is FR-030 (Principle IV: the switch is the opt-in).

**Alternatives rejected.** A client-written field like `theme` (other windows would learn of a
change only at their next start); a per-project switch (FR-029 says one switch for the application).

## R13 — Staleness and the clock

**Decision.** Times are Unix seconds (`u64`) passed in explicitly: the shell stamps a reading's
start and each message that needs "now". A project's statuses carry `read_at`, the start time of the
last successful reading. `is_stale(read_at, now)` is `now - read_at > 600` ("older than two
intervals", FR-019). The sidebar projection
and `worktree_tooltip` take `now` as an argument; the view glue passes `SystemTime::now()`.

**Rationale.** FR-019's rule needs a clock at the moment of drawing, and a pure function with the
time passed in is testable (the existing `worktree_tooltip` is documented as "no clock"; it stays
free of one — the caller supplies the value). Every redraw re-evaluates it, and a redraw happens at
the latest on the next interval tick or failed reading. Wall-clock time is used because the
rate-limit reset (R9) is a wall-clock time; a clock jump can at worst show or hide the stale form
one interval early or late.

**Alternatives rejected.** A `stale` flag set by the reducer on ticks only (the tooltip's "how long
ago" would be up to five minutes wrong); `Instant` (cannot be compared with `X-RateLimit-Reset`).

## R14 — The indicator: a shared component in the row's trailing slot

**Decision.** A new shared component `PullRequestIndicator` in
`crates/micold-client/src/ui/material/pull_request_indicator.rs`, builder form
(`PullRequestIndicator::new(state, roles).checks(c).stale(b)` → `.into()`), posed in the showcase in
every state, check status and the stale form (FR-033). It draws two glyphs of the shipped Material
Symbols font, at a fixed size:

| | Glyph (`Icon` variant → Material Symbol) | Role |
|---|---|---|
| open | `PrOpen` → `call_split` | `primary` |
| draft | `PrDraft` → `edit` | `on_surface_variant` |
| merged | `PrMerged` → `call_merge` | `tertiary` |
| closed | `PrClosed` → `block` | `on_surface_variant` |
| passing | `ChecksPassing` → `check` | `primary` |
| pending | `ChecksPending` → `schedule` | `on_surface_variant` |
| failing | `ChecksFailing` → `close` | `error` |

In the stale form both glyphs take `outline`. The sidebar puts it in the row's trailing element,
left of the hover action cluster (`ui/sidebar.rs::build_items`), so its width is fixed, the name is
what gives way (spec Edge Cases "narrow sidebar"), and a row without a pull request is byte for byte
the row of today (FR-001). The removal suggestion is a label-only chip, **can be removed**, in the
row's existing chip slot — the idiom of "outside this app" and "current session".

**Rationale.** Seven shapes, each different, carry the meaning without colour (FR-009); colour only
reinforces it. The font ships with full coverage (`assets/fonts/PROVENANCE.md`), so a new `Icon`
variant is a codepoint, pinned by `tests/icons_font.rs`. `TreeItem::badge` — the slot before the
label — was rejected because rows with and without a pull request would start their names at
different offsets.

**Alternatives rejected.** A text chip "PR open · failing" (as wide as a short name; nothing left of
the name in a narrow sidebar); one glyph per combination (twelve glyphs to tell apart); colour-only
dots like `ActivityBadge` (FR-009).

## R15 — Tooltip lines, opening the pull request, and what is never written

**Decision.**

- `worktree_tooltip` gains a fourth argument, the row's pull request facts (status, age of the
  reading in seconds, removable), and appends
  after today's lines: `Pull request: #<n> <title>`, `PR state: open|draft|merged|closed`,
  `Checks: passing|pending|failing` (when any), `Review: approved|changes requested|review required`
  (when GitHub reports one), `Read: <n> min ago` (only when stale), and `Cleanup: merged — this
  worktree can be removed (right-click, Delete)` (only with a suggestion). The title is cut to 72
  characters with an ellipsis so the number, which comes first, always shows (story 2 scenario 6).
  With no pull request the output is byte-identical to today's (FR-011).
- The row menu (`ui/mod.rs::worktree_menu_items`) gains **Open pull request** above Delete when the
  row has a status. It sends `WorktreeMsg::PullRequestOpenRequested(dir)`; the shell hands the
  stored address to the existing `LinkOpener` (`shell/link_opener.rs`). The address is the one
  GitHub reported, and is opened only when it starts with `https://github.com/` (FR-014). Nothing in
  the application's state changes.
- `PullRequestStatus` has no `Serialize`, and a hand-written `Debug` that prints the number and the
  enums but neither title nor address, so neither can reach a stored file or a log by accident
  (FR-032, SC-011). A source gate asserts both.

**Rationale.** The tooltip stays a string built by one pure function (029's contract), so FR-012
holds as it does today: hovering reads the state the last reading left. The menu entry is the
user's decision (spec Clarifications).

**Alternatives rejected.** Routing the address through the terminal-link confirmation
(`confirm_link_open`) — that dialog exists for addresses printed by untrusted terminal output; this
one comes from GitHub's API over the user's own sign-in, and SC-009 allows two actions.
