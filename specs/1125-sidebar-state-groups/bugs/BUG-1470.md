# Bug Report: Sidebar chip bar takes too much space when many tags are in use

**Type**: Spec conflict (the stated goal, a list that keeps its room, conflicts with FR-016's unbounded wrap)
**Severity**: Medium
**Feature**: 1125-sidebar-state-groups
**Reported**: 2026-10-26 (issue #1470)
**Status**: Patched
**Patched**: 2026-10-26

## Description
With All + `feat fix docs refactor build ci perf issue untyped` the chip bar wraps to three lines
(~110dp) at a ~300dp sidebar, permanently, and grows with the number of types in use, so the
worktree list shrinks as a project gets busier. The pre-1125 filter button and accordion cost no
space until asked for.

The owner chose the bugfix flow (not feature) and so treats US4.7, FR-014 and FR-016 as the defect.
The fix reverses part of what 1125 wrote on purpose; the BUG patch records that.

## Reproduction (on `origin/main`)
1. Open a project whose worktrees use the types `feat fix docs refactor build ci perf` plus *issue* and *untyped* (9 filters on offer).
2. Look at the sidebar at 300 px: the chip bar is three chip lines tall (the T050 layout snapshot at 180 px with six filters already wraps, a deterministic repro).
3. Code: `chip_bar` in `crates/micold-client/src/ui/sidebar.rs` builds `Row::with_children(chips).wrap()`;
   the layout snapshot with six filters at 180 px already wraps (T050).

## Root Cause Analysis
`chip_bar` (`crates/micold-client/src/ui/sidebar.rs`) draws every filter chip in a wrapping `Row`;
the height is `ceil(chips / chips-per-line)` lines, unbounded. The spec chose this (FR-016) when
the typical project had few types. Nothing hides the chips, so the height is permanent.

## Recommended Fix
One-line bar: **All**, a **Filter** toggle, active chips with ✕, a `+N` chip; the existing
`Accordion` under it holds every chip; `filter_open` in sidebar state, persisted; inline chips when
3 or fewer are on offer. See spec FR-016, tasks T062–T067 (Phase 10).
