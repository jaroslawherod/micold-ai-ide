# Contract: wire messages, settings and the `create_worktree` result

Feature 1289. `PROTOCOL_VERSION` 68 → 69. `SCHEMA_HASH` is regenerated by `build.rs`. Every
message lives in `crates/micold-core/src/protocol/messages.rs`. `location` is
`session::SessionLocation` (`Worktree(dir_name)` or `Default`).

## C1. Client → daemon

| Message | Fields | Answer | Rules |
|---|---|---|---|
| `ProjectSetupSet` | `req`, `project: PathBuf`, `command: Option<SetupCommand>` | `OperationOk` | Replaces the daemon's in-memory command for `project`; `None` clears it. An unknown project is still stored (a later `ProjectAdd` may follow) and costs nothing. It never starts a run, and a run in progress is unaffected (edge case). |
| `SetupRun` | `req`, `project`, `location` | `OperationOk`, or `OperationError` | Errors: `InvalidInput` *This project has no setup command.*; `Busy` *Setup is already running in <location>.* (FR-023a); `NotFound` for an unknown project or worktree. On success the daemon pushes `SetupChanged` (Running). |
| `SetupStop` | `req`, `project`, `location` | `OperationOk`, or `OperationError` `NotFound` *Setup is not running in <location>.* | Ends the run's whole process tree. The run is recorded `Stopped` once it exits (FR-023). |
| `SetupOutputWatch` | `project`, `location`, `from_line: u64` | `SetupOutput`, at once, with the backlog from `max(from_line, first kept line)` | This connection receives later `SetupOutput` for that location until `SetupOutputUnwatch` or the end of the connection. A new run on the same location keeps the watch, and its first batch carries the new `run`. Not correlated: no `req`. |
| `SetupOutputUnwatch` | `project`, `location` | — | Idempotent. |

Order guarantee: a connection's frames are handled in order. A `ProjectSetupSet` sent before a
`WorktreeCreate` on the same connection is applied first.

## C2. Daemon → client

| Message | Fields | When |
|---|---|---|
| `SetupChanged` | `project`, `location`, `run: Option<SetupRunSummary>` | To every client attached to `project`, on every state change. To one client right after `Attached`, once per location that has a record. `run: None` when the record went away (worktree deleted). |
| `SetupOutput` | `project`, `location`, `run: RunId`, `first_line: u64`, `lines: Vec<String>`, `dropped: u64` | To watchers only. Batches go out at most every 250 ms while lines arrive (`progress.rs` `ProgressThrottle`). One more batch is sent when the run ends, and its last line is the reason line (SC-004). `first_line` is the index of `lines[0]`, and a gap from what the client holds means lines were dropped in between. |

`SetupRunSummary` = `{ id, command, state, started_at, ended_at, output_lines }` (data-model).
`SetupState` is encoded as `{ "state": "failed", "failure": { "exit": 2 } }`, and as
`{ "state": "running" }` and so on for the others.

## C3. `settings.json`

```json
{
  "setup_commands": {
    "/home/me/src/app": "mise trust && mise install"
  }
}
```

- The key is the project path, as `jira_base_urls` uses it. The key is absent when the project has
  no command. The whole map is absent when it is empty.
- The client writes the map in its normal save (`shell/persist.rs`). The host daemon's
  service-settings write keeps it: the field is in core `Settings` and in its on-disk mirror.
- After a save that changes a project's command, the client sends `ProjectSetupSet` to every
  connected daemon whose catalog holds that project. On every connect it sends one per project
  registered there. Commands are never sent to a daemon that does not hold the project.

## C4. MCP `create_worktree` result (`crates/micold-daemon/src/mcp/tools.rs`)

A successful result's object gains a `"setup"` field, set from the `SetupStart` that
`ops::create_worktree` returns:

| Value | Meaning |
|---|---|
| `"started"` | The project's setup command is running in the new worktree. The agent can read the output by asking the user. Nothing waits for it (FR-013, FR-014). |
| `"none"` | The project has no setup command. |
| `"already running"` | `SetupStart::Busy`: a run was already in progress for that location (FR-023a). Not expected for a new worktree, since a delete removes the old record, but reported rather than hidden. |

Creation never fails because of setup (FR-013). `next_step` is unchanged.
