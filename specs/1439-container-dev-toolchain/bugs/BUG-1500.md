# Bug Report: The AI agent in a container session is never told what persists or how to install tools

**Type**: Spec gap (Story 5 tells the user, through the sandbox page, how a session installs tools
that persist; nothing tells the AI agent that runs the session)
**Severity**: Medium — the agent works blind: it tries `sudo`/`apt-get`, installs into `/tmp` or
outside `PATH`, or re-downloads a tool after a restart, which is what Story 5 exists to prevent
**Feature**: 1439-container-dev-toolchain (US5, FR-014 to FR-018, plan D8)
**Reported**: 2026-10-27. GitHub issue #1500.
**Status**: Patched
**Patched**: 2026-10-27

## Description

#1439 made the sandbox home persistent (FR-016) and pointed every user-level installer into it
(FR-014, FR-015: `NPM_CONFIG_PREFIX`, `CARGO_INSTALL_ROOT`, `GOBIN`). FR-018 documents this for the
**user** in `docs/user-guide/sandboxed-daemon.md` "Tools installed in the sandbox's home". The
**AI agent** in a container or Kubernetes session reads none of that: its user-level instruction
files (`~/.claude/CLAUDE.md`, `~/.codex/AGENTS.md`) in the sandbox home are empty or absent, and the
project's own instructions describe the user's machine. So the agent does not know that it runs as
a non-root user without `sudo`, that `/tmp` and everything outside the home and the project folders
is lost on a restart or image update, or which install commands land on `PATH` and persist.

### Reproduction (origin/main 728eb7238)

1. `grep -rn "AGENTS.md\|CLAUDE.md" crates --include=*.rs` outside tests: no code writes either
   file; the daemon's startup (`crates/micold-daemon/src/server.rs:197-206`) records the `ai-clis`
   directory and the in-sandbox flag and writes nothing into the home.
2. Start a container daemon on the basic image (any version since #1439's M5), open a Claude Code
   or Codex session and run `cat ~/.claude/CLAUDE.md ~/.codex/AGENTS.md`: neither exists (a fresh
   sandbox home holds only what the entrypoint creates, `~/.local/bin` and the mise shims folder).
3. Ask the agent to build a project needing `uv`: it has no instruction saying `mise use -g` or
   `uv tool install` persist and `apt-get` cannot work, and typically tries the latter first.

Confirmed by code reading (step 1) and by the sandbox home layout of plan D3; the cloud container
has no container runtime for step 2, which the real-runtime assertion of T045 covers in CI.

## Root Cause Analysis

A spec oversight. The amendment of 2026-10-26 framed Story 5 around what a session *can* do (no
root needed, installs persist) and documented it where a human reads (FR-018). It did not ask how
the agent learns it, although the agent is the one who runs the installs. The daemon is the right
writer: it knows it runs in an app-owned sandbox (`DaemonState::offered_clis()`, the predicate
`with_sandbox_env` already uses, `crates/micold-daemon/src/state.rs:1202`, `:1227`), it knows the
sandbox `HOME` (the same lookup `with_sandbox_env` makes), and it starts on every container start,
so a newer daemon refreshes the text.

## Fix (owner's choice, decision card option A, 2026-10-27)

On a container or Kubernetes daemon only, at each start, the daemon writes a short guide to
`$HOME/.micold/AGENTS.md` and merges a marked block (`<!-- micold:sandbox-guide begin -->` …
`<!-- micold:sandbox-guide end -->`) summarising it and pointing at it into Claude Code's
`$CLAUDE_CONFIG_DIR/CLAUDE.md` (else `~/.claude/CLAUDE.md`) and Codex's `$CODEX_HOME/AGENTS.md`
(else `~/.codex/AGENTS.md`). Text outside the block is kept; the block is replaced in place;
nothing is rewritten when unchanged. Host and remote daemons write nothing. A failed write is
logged and the daemon starts anyway.

The other offered CLIs (Copilot, Pi, OpenCode) are left out: their user-level instruction files are
not modelled anywhere in the repository, and the owner's choice names Claude Code and Codex. Recorded
as a follow-up in the ledger.
