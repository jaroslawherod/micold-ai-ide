# Bug Report: The start-up offer offers stored sessions that "Resume all" can only refuse

**Type**: Spec conflict — 582 FR-012 (offer attaching everything found, in one action) against 776
FR-012 (attach all catalogues at most the newest session per worktree, none in a worktree that has
one). Feature 776 changed the batch; the offer still offers everything.
**Severity**: High — after every restart the offer appears and "Resume all" fails for every item.
**Feature**: 582-attach-provider-worktrees-sessions (FR-012, User Story 4; batch rule from
776-one-session-per-worktree FR-012, FR-008b/c)
**Reported**: 2026-10-23 (issue #1164)
**Status**: Patched (FR-018, T055–T059)
**Patched**: 2026-10-23

## Description

After a restart the sidebar banner says "Found N stored sessions" and offers "Resume all". Pressing
it raises "5 could not be attached (that worktree already has a session; …)" and the banner stays.
Dismissing it lasts only until the next restart, so it is back every time. The issue also reports
that sessions seem to go missing when the offer is dismissed (see *Second symptom*).

## Reproduction

1. A project whose catalog holds one session in each of worktrees `w1` and `w2`, and whose provider
   store holds older conversations of those worktrees that the catalog lacks (every worktree used
   more than once has them; feature 026's open-time adoption catalogues only the newest per free
   location).
2. Restart Micold: `AttachDiscover` at project open lists those older conversations, and the
   banner appears.
3. Press "Resume all": every item is refused `LocationHasSession`; the banner stays.
4. Without the GUI: `crates/micold-client/tests/attach_offer.rs` module `bug_1164` (T055) builds
   that state (catalog sessions in `w1`, `w2`; report sessions in `w1`, `w2`, `w1`). On `origin/main`
   (f8d2257e) `stored_sessions_of_worktrees_that_have_a_session_are_not_offered` fails: the offer is
   visible and `OfferAttachAll` puts all three in flight. `resume_all_sends_only_the_newest_session_of_each_free_worktree`
   fails too: it sends the occupied `w1` item and both `w2` items. Run:
   `cargo test -p micold-client --test attach_offer bug_1164` (run 2026-10-23 on f8d2257e: those two
   failed, the other 16 passed).

## Root Cause Analysis

The client decides what the offer offers without looking at the catalog:

- `Offer::targets` (`crates/micold-client/src/features/attach.rs:56`) turns every `Resumable`
  session of the report into a plain item (`replace: false`, `allow_additional_session: false`),
  and `offer_visible` (`attach.rs:78`) shows the banner whenever the report is non-empty; the
  banner counts `session_count()`, all of them (`crates/micold-client/src/ui/sidebar.rs:292`).
- The report is everything the catalog lacks, in every location: `DaemonState::attach_discover`
  (`crates/micold-daemon/src/state.rs:4391`) over `attach::discover_resumable`
  (`crates/micold-core/src/attach.rs:276`) subtracts known ids only. That is right for the
  "Attach existing…" dialog, where a single resume into an occupied worktree asks replace or keep
  both (776 FR-008b/c).
- `DaemonState::attach_apply` (`state.rs:4532–4591`) applies 776 FR-012 to a batch of plain items:
  none for an occupied location, the newest for a free one; every other item is
  `Refused(LocationHasSession)`. So each stored session of an occupied worktree is refused.
- When nothing was attached, `Msg::OfferApplied` keeps the report (`attach.rs:386–395`), and the
  next start lists the same sessions again, so the failing offer returns after every restart.

Feature 776 changed the batch rule (its FR-012 names feature 582) but did not change what the
offer offers. No 582 task is a false completion: T032/T033 matched FR-012 as written before 776.

## Second symptom: sessions missing after dismissing

Not reproduced. `Msg::OfferDismissed` (`attach.rs:369`) only records the dismissal in memory;
nothing on that path writes the catalog. Two readings fit the report:

- The sessions "missing" are the offer's own entries: stored conversations that were never in the
  sidebar, which the offer named.
- The one automatic removal on project open is the empty-session prune
  (`DaemonState::prune_empty_sessions`, `state.rs:5333`): it archives a `Pending`-label session
  with no transcript at its own location's store directory. The issue comment's case (one provider
  session whose work moved to a second worktree) would leave such a session if the provider wrote
  its transcript under the other directory. That provider behaviour is unverified. The prune logs
  only a count (`crates/micold-daemon/src/server.rs:2815`), so the case cannot be traced from a log.

The patch does not guess-fix the prune. T058 makes it log each archived session's id, location and
reason, so the next case can be traced; a confirmed case is a new issue.

## Recommended Fix

The client filters the offer against the catalog sessions it already holds
(`State::active_sessions`); no protocol change. `offerable` in `features/attach.rs` keeps the
report's sessions whose location `occupancy::occupancy` calls `Free`; the banner shows and counts
only those, and "Resume all" sends the resumable newest of each location
(`attach::cap_per_location`, the rule `attach_apply` applies). The dialog and `AttachDiscover` are
unchanged. The prune logs each session it archives (T058). Tasks T055–T059, milestone M7.
