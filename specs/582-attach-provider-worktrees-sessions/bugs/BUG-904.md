# Bug Report: A `/clear` in a running session registers the same session twice

**Type**: Spec gap — nothing says a provider conversation id can change under a live session.
**Severity**: Medium — a duplicate "helper" row for one session, recurring (about 12 "resume"-labelled entries in one catalog).
**Feature**: 582-attach-provider-worktrees-sessions (FR-007, User Story 2 scenario 3; the discovery it extends is 026 FR-014)
**Reported**: 2026-10-16 (issue #904)
**Status**: Patched (FR-017, T051–T054)
**Patched**: 2026-10-16
**Review**: round 1 CLEAN; two MINORs fixed as prose

## Description

The sidebar shows two rows that are one session. `/clear` in Claude Code gives the same running
process a new conversation uuid in the same cwd. Real case: session `b9ca08ec` (row "#819 wait
re-arm") ran `/clear` at 2026-10-16T12:26:01Z and the CLI continued as `c8cc3bb3`. Its transcript
`c8cc3bb3-438a-4d12-ad30-abcb78620af6.jsonl` starts with the `/clear` command record
(`<command-name>/clear</command-name>`) and carries that `sessionId` throughout. Discovery saw an id no
catalog entry knew and adopted it as a second session at the same location (non-main, shown
"helper", label "resume").

Reproduced from the real store (`~/.claude/projects/-home-jaro-workspaces-micold-ai-ide--claude-worktrees-feat-533-create-worktrees-from-jira-issues/`)
and by reading the code: `DaemonState::discover_external_sessions` (`state.rs:3057`) subtracts only
ids already in the catalog, and `Catalog::adopt_discovered_sessions` (`catalog.rs:1540`) adopts
whatever remains; `claim_main_if_free` then marks it non-main because the location is taken.

## Reproduction

1. In a project with a session running Claude Code at a location (worktree or root), run `/clear` in it.
   Claude Code writes `<new-uuid>.jsonl` beside the old transcript, first record the `/clear` command.
2. Let discovery run (open the project, or any worktree refresh): the catalog now holds both ids.
3. Without a live Claude: seed a store with `<A>.jsonl` (catalogued) and `<B>.jsonl` whose first line is a
   user record `<command-name>/clear</command-name>`, same cwd; `discover_external_sessions` returns 1
   and adopts B. The regression test T051 does this on `origin/main`.

## Root Cause Analysis

Spec oversight. The session id doubles as the conversation uuid and the `--resume` handle, so the
design assumes one id per session for life. Claude Code's `/clear` breaks that assumption: the
process lives on under a new uuid. Discovery cannot tell the successor from an unrelated session.
The signal it can read is the successor transcript's first record, the `/clear` command.

## Recommended Fix

A provider method `starts_as_continuation(config_dir, cwd, id) -> bool` (default `false`; Claude
reads the bounded transcript prefix for a leading `/clear` command record). In
`discover_external_sessions`, a transcript for which it is `true` is not adopted when a
non-archived same-provider session already exists at that location; the provider's durable archived
marker (`mark_archived`) is written for it, so later passes skip it and no catalog schema changes.
A `/clear` transcript at a location with no session of that provider is adopted as today.

Decisions: (1) the live session keeps its original id, so a later restart resumes the pre-clear
conversation; re-pointing the id under a live process was rejected as a registry change out of
proportion to the bug. (2) Duplicates already in a catalog are left alone; no data is deleted
silently and the user archives the extra row. (3) Known limitation: a brand-new external `claude`
whose first act is `/clear`, started where a session already exists, reads as a continuation.
