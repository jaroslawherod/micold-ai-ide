# Bug Report: A version-mismatched container daemon is a dead end

**Type**: Implementation drift (FR-007's version rule was wired for SSH daemons only), with a spec
conflict resolved below (FR-017's legacy restart gate vs. the mismatch restart of spec 027 FR-023)
**Severity**: High — after a client upgrade, every session on a container daemon is visible but
unusable, and the app offers no way to bring the daemon up to the client's version
**Feature**: 806-container-daemon-ssh-provisioning (branch `claude/project-thread-8l8nas`)
**Reported**: 2026-10-23. GitHub issue #1165, seen in the same restart as #1164 (out of scope here).
**Status**: Patched
**Patched**: 2026-10-23

## Description

A session runs on a container daemon. The user upgrades Micold to a build with a different daemon
version and restarts it. The session is listed again (restored), its worktree's daemon is shown as
`Version mismatch`, and nothing in the app moves the daemon to the client's version:

- The Settings → Daemons row shows `Version mismatch` with **no explanation** and **no Replace**
  action. On a container still on the released image (legacy) it also hides **Stop**, because the
  restored session counts as running.
- The banner's **Restart service** stops the boot sandbox (`placement = sandbox`) or, when there is
  none, the **host** daemon's endpoint, never the mismatched container daemon of the active worktree.
- **Reconnect** runs the provisioning again, whose `remote bridge` connects to the old daemon that
  is still listening in the container, and the handshake is refused again.

Spec 491 FR-008 asks for an explanation and a way out for every mismatched daemon; spec 806 FR-007
says a running container daemon of another version is handled by spec 489 FR-011's rule (explain;
offer replacement when it has no running sessions). Neither happens for a container.

### Reproduction

On `origin/main` at `f8d2257e`.

1. **The row** (pure, no container needed). A probe test against the public reducer, the same fixture
   as `crates/micold-client/tests/ssh_replace_offer.rs` but with the fixture's container daemon `Box`:

   ```rust
   let mut w = daemons_fixture::World::new();           // Box = container daemon, 2 live sessions
   w.links.apply(w.boxed, DaemonEvent::Start);
   w.links.apply(w.boxed, DaemonEvent::Refused { client: "0.5.3".into(), daemon: "0.5.2".into() });
   // optionally: daemons::update(.., Msg::OfferReported(w.boxed, ReplaceOffer::Available))
   // and, for the legacy case, model.legacy_container = Some(w.boxed)
   let row = daemons::views(&state, &model).rows.iter().find(|r| r.id == w.boxed);
   ```

   Result, for every combination of legacy / not legacy and no offer / `ReplaceOffer::Available`:
   `state = VersionMismatch`, `explanation = None`, `replace_offered = false`, and
   `Msg::ReplaceRequested` yields no outcome; `stop_blocked = true` whenever it is the legacy
   container. The same probe with an SSH daemon gives an explanation and, on `Available`, the
   Replace action (`ssh_replace_offer.rs` passes on `main`). Probe output on `f8d2257e`:

   ```
   legacy=false offer=None            state=VersionMismatch { client: "0.5.3", daemon: "0.5.2" } explanation=None replace_offered=false stop_blocked=false  replace outcomes=0
   legacy=false offer=Some(Available) state=VersionMismatch { .. } explanation=None replace_offered=false stop_blocked=false  replace outcomes=0
   legacy=true  offer=None            state=VersionMismatch { .. } explanation=None replace_offered=false stop_blocked=true   replace outcomes=0
   legacy=true  offer=Some(Available) state=VersionMismatch { .. } explanation=None replace_offered=false stop_blocked=true   replace outcomes=0
   ```
2. **The offer is never asked for a container.** `crates/micold-client/src/shell/daemons.rs:213`
   `ask_offer` returns `Task::none()` unless the runtime is `DaemonRuntime::Ssh`, so a container's
   offer stays `None` and the row could not offer Replace even if `remote_mismatch` accepted it.
3. **The banner restart targets the wrong daemon.** `crates/micold-client/src/shell/service_control.rs:37`
   clears the active daemon's mismatch, then stops `app.sandbox_boot` if set, else calls
   `micold_core::spawn::stop_running_daemon(&micold_core::endpoint::resolve()?)`, the host daemon's
   endpoint. `app.sandbox_boot` is set only for `PlacementKind::LocalSandbox`
   (`crates/micold-client/src/shell/startup.rs:320`) and names only the registry's first container
   (`BootPlan::identity_of`). With a container daemon added in Settings (host placement), the
   restart ends the host daemon, which spec 491 FR-007 forbids ("a daemon being … mismatched MUST NOT
   change the state or behaviour of any other daemon"), and leaves the container as it was. With
   `placement = sandbox` and a second container daemon active, it stops the first container.
4. **Reconnect cannot help.** `crates/micold-daemon/src/remote.rs:3-5`: `remote bridge` connects to
   the daemon already listening in the container and starts one only when none listens. The old
   daemon keeps the endpoint, so every re-dial is refused again
   (`crates/micold-core/src/provision/mod.rs` `start_step`, handshake → `VersionMismatch`).

End to end (needs a container runtime): run a session on a container daemon added in Settings, start
a client whose package version differs, open the session's worktree: the row and banner behave as
above. Not run here (no container runtime in this environment); steps 1–4 are the mechanism.

## Artifact Traceability

### spec.md

- **Affected user stories**: US1 #1 ("the daemon reports the client's version"), US4 #3–#4 (a legacy
  container with sessions; its restart).
- **Affected requirements**: FR-007 (the version rule of spec 489 FR-011 for a running daemon of
  another version), FR-017 (legacy restart gated on running sessions); spec 491 FR-007 (independence)
  and FR-008 (explanation and way out per daemon); spec 027 FR-023 (the restart affordance of a
  version mismatch for a sandboxed service).
- **Gap identified**: FR-007 is right and unimplemented in the client for containers. FR-017 gates the
  legacy restart on "no session runs", which the client reads from its own cached session list: for
  a mismatched daemon that list can never be refreshed (the daemon cannot be spoken to), so a restored
  session blocks the restart forever. Spec 027 FR-023 offers a user-chosen restart for a mismatched
  sandboxed service, interrupting running processes and keeping sessions resumable; 806 never says how
  that affordance and FR-017 meet.

  only the provisioning step's failure, not the client's explanation, offer and replacement.
- **Impact**: a fix increment in the client (offer, explanation and replace for containers, the legacy Stop gate, the banner restart retargeted to the mismatched daemon) and
  core (`ssh::status` over a pinned reach).

## Root Cause Analysis

Feature 489 built the mismatch explanation, the `remote status` offer and the `remote stop`
replacement for the SSH runtime, keyed on `DaemonRuntime::Ssh` in four places:
`crate::links::remote_mismatch` (`crates/micold-client/src/links.rs:208`),
`features::daemons::replace_offered` (`features/daemons.rs:611`, via `remote_mismatch`) and
`Msg::ReplaceRequested` (`features/daemons.rs:2057`), and `shell::daemons::ask_offer`
(`shell/daemons.rs:213`); `micold_core::ssh::status::{fetch_offer, stop_if_idle}` take an
`SshTarget` and always build `Reach::UserConfig`. Feature 806 moved container daemons onto the same
SSH provisioning with a `Reach::Pinned` and stated in FR-007 that the 489 rule applies, but only the
provisioning sequence's refusal was wired; the four client sites were left SSH-only. The banner's
restart (feature 021/027, single-daemon era) was never made per-daemon by feature 491: it knows the
boot sandbox and the host endpoint, not the registry entry of the active daemon. FR-017's gate was
implemented on the client's session cache, which is stale by construction for a daemon the client
cannot talk to.

## Resolution of the spec conflict (agent-resolved, ledger D1)

Spec 489's clarification (decided by user) stands for containers: the app replaces a mismatched daemon
only when it proves no session runs, "otherwise the user ends it themselves". FR-017's gate was meant
to read the daemon's report (T058, R10), and a mismatched daemon cannot report, so the client's stale
cache must not hide the user's own Stop. The patch therefore adds no restart the app performs with
sessions running: it gives containers 489's explanation, offer and Replace, states the row's Stop as the
way out when sessions run or cannot be counted, un-hides that Stop for a mismatched legacy container,
and makes the banner's existing restart (spec 027 FR-023, already shipped for the boot sandbox) act on
the mismatched daemon instead of the host daemon (spec 491 FR-007). Whether the app should also offer a
one-click "restart and resume" of a container with running sessions, as the issue suggests, is a
product change to 489's user decision and is left to the owner (ledger *Follow-ups not done*).
