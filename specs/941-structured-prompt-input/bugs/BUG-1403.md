# Bug Report: Structured view: Ctrl+C does not stop the running turn

**Type**: Spec gap — FR-012 names Escape as the only interrupt key.
**Severity**: Medium — a busy turn can still be stopped (Escape or the stop control), but the
Ctrl+C habit of the agent's terminal UI and the PTY view does nothing.
**Feature**: 941-structured-prompt-input (FR-012, FR-013, User Story 3)
**Reported**: 2026-10-27 (issue #1403)
**Status**: Patched
**Patched**: 2026-10-27

## Description

While a structured session is busy, Ctrl+C with the composer or the transcript focused does
nothing; the turn keeps running. Expected: Ctrl+C interrupts like Escape (`ClientMsg::TurnInterrupt`),
except that a selection in the composer is copied instead, and Cmd+C on macOS stays copy. Idle,
Ctrl+C is unchanged.

Reproduced by reading `origin/main` (36459b958 and later): `composer_key`
(`crates/micold-client/src/features/composer.rs:78`) returns `Edit` for any press with ctrl held
(`!plain(press)` at the top), and `transcript_key` (`:104`) matches only `Named(Escape)`; the shell
(`shell/composer.rs:50,55`) only sends `ClientMsg::TurnInterrupt` for `KeyIntent::Interrupt`. So
no path from Ctrl+C reaches the interrupt. The transcript has no text selection today
(`ui/transcript` has no selection state); only the composer editor has one
(`Content::selection()`).

## Root Cause Analysis

Spec oversight: FR-012 listed one interrupt key, and `composer_key`/`transcript_key` implement
exactly that. Fix site: both functions, plus the editor's selection state passed into
`composer_key` (`Editor::has_selection` over `Content::selection()`, read where
`ui/composer.rs::key_binding` and `shell/composer.rs` build the call). When Ctrl+C maps to
`Interrupt` in `key_binding`, the editor's default copy no longer runs, which is why the selection
check must come first.
